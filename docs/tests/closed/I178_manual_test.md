# I178 手動テスト: CODEOWNERS で承認者を管理者に限定し、develop・main で Code Owners の承認を必須にする

対象: GitHub のブランチ保護設定（develop・main）と、設定後の PR の状態

**前提**: ステップ 1〜3 の自動テスト（TC-01〜TC-19。ただしマージ後に行う TC-17 を除く）が合格し、ユーザーが計画書 5-5 の表のとおりブランチ保護を設定した後に行う。bot は保護設定を読めないため、設定値そのものはユーザーが画面で確認し、効き目は PR の状態（`reviewDecision`・`mergeStateStatus`）と API の応答で間接的に確認する。

**使うアカウント**: ユーザー = `oshui0404`（管理者・承認者）／ bot = `osushi0404-bot`（Claude が `gh` で操作）

**使う PR**: No.3〜No.6・No.8 は本イシューの PR #298（bot が作成・develop 宛て）。No.7 はマージ後にユーザーが作る確認用 PR（ブランチ `check/I178-codeowners`）。

**実施の順番と記録の残し方**（adversarial 第2周 Medium・fix-loop 20261018 対応）:

1. **/test**: No.1〜No.3 を行い、結果をこのファイルに記入してコミット・push する（承認前なので承認の取り消しは起きない）。
2. **/close**: Ready にした後に No.4 を行う。close step 6 では、**承認だけ**を依頼する（このファイルには承認の後・マージの前に行う確認 No.6・No.8 があるため。close step 6 の末尾の一文）。ユーザーは No.5 で **Approve だけを押し、Merge は押さない**。
3. **No.5・No.6**: 承認を確かめ（No.5）、bot のマージが拒否されることを確かめる（No.6）。No.4〜No.6 の結果はこのファイル（closed へ移動後）に記入する。
4. **No.8**: No.4〜No.6 の結果をコミット・push する。このコミット自体が「承認後の新しいコミット」になるので、承認が取り消されること（Dismiss stale の効き目）を確かめる。CI の完了を待ってからユーザーに再承認を依頼し、再承認の後にユーザーがマージする。No.8 の結果は #298 にはコミットしない（コミットすると承認がまた取り消されるため）。
5. **マージ後**: No.7 と TC-17 を行う。No.7・TC-17・No.8 の結果と、レビュー文書の AC 判定表（AC-1〜AC-7 のうち未記入のもの。少なくとも AC-1 は TC-17 の結果で確定させ、AC-2〜AC-5 はマージ前後の手動確認の結果で記入する）は、bot が作る記録用 PR（`docs(I178): マージ後確認の記録`・develop 宛て）で記入し、ユーザーが承認・マージする。AC-6・AC-7 は /test の時点で記入できる。

**承認の後に develop が進んだ場合**: マージまでの間に develop が先に進んで PR が `BEHIND` になった場合は、bot が追従のコミット（`bash scripts/claude/pr-base-sync.sh final`）を push する。承認が取り消された場合は、CI の完了を待ってからユーザーに再承認を依頼する（差分が変わらない追従では承認が残ることもある。runbook §6「承認したのに BLOCKED に戻った」）。

**確認が失敗した場合**:

- **No.4・No.5 が期待どおりにならない場合**（承認前なのに `APPROVED`・承認後も `REVIEW_REQUIRED` 等）: マージせずに止め、ユーザーが設定画面（No.1）を見直して直す。No.5 で承認した後に止めた場合は、その承認が残っていると No.3・No.4 の期待値（`REVIEW_REQUIRED`）と合わなくなるため、ユーザーが PR 画面で自分の承認を取り消す（Reviewers 欄の自分のレビューの「…」→ **Dismiss review**）。その後に No.3 からやり直す。
- **No.6 でマージが成功してしまった場合**（develop の push 制限が効いていない）: ユーザーが develop の設定（No.1）を直す。PR #298 はマージ済みになるため、マージ後の記録用 PR（bot が作成）を使って次を確かめ直す。(1) ユーザーが記録用 PR を承認した後、No.6 と同じ手順で bot がマージ API を呼び、push 制限で拒否されることを確かめる。(2) bot が記録用 PR に 1 行のコミットを push し、`reviewDecision` が `REVIEW_REQUIRED` に戻ることを確かめる（No.8 の代わり）。No.4〜No.6 の結果とあわせて、記録用 PR で記入する。（ユーザーが作る No.7 の PR は、作成者のユーザーが承認できないため、この確認には使えない）。(1) でまたマージが成功してしまった場合は、設定がまだ直っていないので、ユーザーが develop（No.1）と main（No.2）の両方の設定画面を見直したうえで、新しい記録用 PR（bot が作成）で (1)・(2) を繰り返す。
- **No.8 で push 後も `APPROVED` のままの場合**（Dismiss stale が効いていない）: マージせずに止め、ユーザーが設定画面（No.1）で「Dismiss stale pull request approvals when new commits are pushed」を直す。直した後に、bot がもう一度 1 行のコミットを push して No.8 をやり直す。
- **マージ後の No.7 または TC-17 が NG の場合**: Issue #297 を開いたまま（閉じていれば開き直し）、原因を調べて直す。設定の誤りならユーザーが設定画面で直し、文書や CODEOWNERS の誤りなら新しい PR（bot が作成）で直す。直した後に No.7・TC-17 をやり直し、結果を記録用 PR で記入する。（#298 の宛先 develop は既定ブランチではないため、マージしても Issue #297 は自動では閉じない）
