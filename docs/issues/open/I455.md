## 背景/目的

**背景**: I431 で、学習記録（`/api/study/` の下）とダッシュボードの全経路に組織の絞り込みを足した。ただし絞り込みは、呼び出す場所ごとに `scope_to_user_org(<queryset>, user, subject_path=..., allow_null=...)` を書く作りで、約 20 か所ある。新しい処理を足すときに書き忘れると、他組織のデータが漏れる。I452 では同じ周辺に手を入れて新しい処理も増えるため、その前に付け忘れを作りで防ぐ。
**目的**: 学習記録まわりのモデルに「利用者本人の記録で、かつ組織の境界の中のもの」を返す取り出し方を 1 つ持たせ、それを使うのを標準にする。呼び出し側から、組織の境界の指定（科目への経路・空を許すか）を無くす。

### 現状の問題（証拠・再現手順）
- `scope_to_user_org` の呼び出しが、`backend/studylogs/views.py`・`services.py`・`mistake_analysis.py`・`backend/dashboard/views.py` に約 20 か所ある（I431 の差分）。`adaptive_selection.py`・`tasks.py` は `available_problems`・`available_subjects` を使い、利用者本人の記録（ProblemAttempt・SpacedRepetitionReview など）を組織で絞らずに読む箇所が残る（数だけの集計として I431 で残した。置き換えるか理由のコメントにするかを計画で決める）。どれも `X.objects.filter(user=...)` を作ってから渡す形で、利用者も 2 回書く
- モデルごとに、科目への経路と空を許すかは決まっている（呼び出しのたびに同じ値を書いている）:
  - StudyLog・QuizSession・MistakePattern: `subject`・空を許す
  - LearningWeakness: `subject`・空を許さない
  - SpacedRepetitionCard・SpacedRepetitionReview・ProblemAttempt: `problem__subject`・空を許さない
  - LearningSuggestion: `subject` と `mistake_pattern__subject` の 2 つ・空を許す（I431 では `mistake_analysis.scope_learning_suggestions` にまとめた）
- 1 か所で空を許すかを取り違えても、テストが無い経路では気づけない（I431 のコードレビューとの BP 評価で指摘）

### 根本原因
組織の境界が、モデル（データの持ち主）ではなく呼び出し側に置かれている。そのため、安全な取り出し方が標準になっておらず、境界の付け忘れや指定の取り違えを作りで防げない。付け忘れを機械で見つける側（横断テスト）は #446 が受け持ち、このイシューは付け忘れが起きにくい作りの側を受け持つ（役割の分担）。

### 解決方針
- 各モデルに独自の QuerySet を持たせ、マネージャーとして使う。例: `StudyLog.objects.for_user(user)` が「`user` 本人の記録で、組織の境界の中のもの」を返す。科目への経路と空を許すかは QuerySet の中に 1 回だけ書く
- 判定の部品（`tenant_scope`）は problems に残し、各モデルの QuerySet がそれを呼ぶ（problems から studylogs への依存を作らない）
- studylogs・dashboard の呼び出し側を、`for_user(...)` に置き換える。I431 の `scope_learning_suggestions` は LearningSuggestion の QuerySet に移す
- 組織で絞らずに取り出す箇所（件数・時間・正答率・連続日数など、科目・問題の中身を返さない集計。I431 の計画書 `docs/plans/closed/plan_I431.md` の「扱いの基準 3」）は、そのまま残す理由をコメントで書く
- 振る舞いは変えない（I431・I166・#446 のテストを守りにして置き換える）
- DB の形（欄・マイグレーション）は変えない見込み。Manager・QuerySet の変更でマイグレーションが出るかは計画で確かめる
- 既定のマネージャー（`objects`）そのものを絞る形にするか（取り出しの既定を安全側にする）、別名のメソッドにするかは、管理画面・非同期処理・データの書き出しへの影響を見て計画で決める（未定・計画で確定）

## スコープ
### 含む
- 次の 8 モデルの、組織の境界つきの取り出し方と、呼び出し側の置き換え: StudyLog・ProblemAttempt・SpacedRepetitionCard・SpacedRepetitionReview・MistakePattern・LearningSuggestion・LearningWeakness（studylogs）・QuizSession（problems）
- 非同期処理（`backend/studylogs/tasks.py`）は利用者を引数で受け取って処理するので、その利用者で `for_user(...)` を使う。利用者を持たない一括処理（期限切れの提案の片付けなど）は、組織で絞らない理由をコメントで書く
- 絞らない取り出しを残す箇所への理由のコメント
### 含まない
- 振る舞いの変更（何が見える・何が断られるかは I431 のまま）
- 壊れた機能の修正（difficulty の型・Problem に無い `is_active` など・I452）
- キャッシュのキーへの組織の追加（#452 に同梱済み）
- 全 API の横断の越境テスト（#446）
- クイズの経路の判定（`QuizService`）の置き換え（呼び出し元を変えない方針。`QuizService.available_subjects`・`available_problems` が `tenant_scope` への中継になっている件を整理するかは、#452 に同梱済みの I431 のレビューの残り F6 で扱う）
