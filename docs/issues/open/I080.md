## 設計確認メモ（/grill-me）
- Q: `git push *` を allow 化すると、フックが捕捉しない push は確認なしで実行される。ガード（フック）の遮断範囲をどこまでにするか（A=保護ブランチ上の素 push のみ / B=A+refspec `<src>:develop|main` / C=B+`--all`/`--mirror`）→ A: **C（網羅）**。理由: allow 化でフックが「protected 書き込みの唯一の権威ガード」になるため、穴ゼロを確定させないとモデル（危険は必ずガードで止まる）が「ほぼ安全」止まりになる。protected へ書き込める経路を全列挙すると、(1) protected 上の素 push（branch 判定が要り permission 層では原理的に不可）、(2) refspec `<src>:develop|main`（refspec 解析が要り permission 層では頑健に書けない）、(3) `--all`/`--mirror`（全 ref 一括）。(1)(2) はフックでしか塞げず、(3) だけ残すのは中途半端。追加コストは正規表現2行＋テスト2件と僅少のため C で確定。
- Q: 実機検証で現状の穴は実在するか → A: 確認済み。develop 上で `git push` / `git push origin` / `git push -u origin` はいずれも exit 0（素通り）。任意ブランチからの `git push origin feat:main` / `HEAD:develop` / `x:main` も exit 0（素通り）。既存遮断は `origin develop|main`（exit 2）・`origin HEAD` on protected（exit 2）・`--force`（exit 2）のみ。
- Q: 確定したガードのアーキテクチャ整理 → A: **フック=protected 書き込みの単一権威ガード**（branch/refspec を解釈できる唯一の層・全経路を網羅）／**deny=テキストで自明な危険系の冗長バックストップ**（`origin develop|main`・`--force`。フックが万一落ちても残る）／**allow `git push *`=フックが網羅的だからこそ無確認化が安全**。fail-open（`git rev-parse` 失敗時はスキップ）は許容：その環境では `git push` 自体も失敗するため無言すり抜けは実質起きない（既存 HEAD チェックと同方針）。
- Q: I080 のフック決定論テストの配置先は（新規 / 既存 checkout テストに追記）→ A: **新規** `scripts/claude/tests/test_pretooluse_push_guard.sh`。push の網羅性は全経路を列挙し各々 exit 2 を注入確認＋false-green 注入する独立した決定論ゲートとし、I081(checkout) の関心と混ぜない。
- Q: protected ブランチ（develop/main）を宛先とする push の DANGER_OK 扱いは（無条件ハードブロック / 現状どおり DANGER_OK 解除可）→ A: 【**訂正済み・下記の release/hotfix 発見により撤回**】当初「無条件ハードブロック」で確定したが、後続 grill で workflow.md のリリース/hotfix フローが正当なローカル protected push であることが判明し撤回。最終決定は下記参照。
- Q: protected 宛先の検出方式は（正規化1本に統一 / 現実形のみ追加）→ A: **正規化1本に統一**（既存 `origin (develop|main)` 規則も置換改修）。各 push 宛先トークンを正規化（先頭 `+` 除去 → コロンがあれば右側 dst → `refs/heads/` 接頭辞除去 → `HEAD` は現ブランチ解決）し、`develop`/`main` と**完全一致**で判定する単一関数に統一。実機確認した未捕捉形 `git push origin +develop`・`refs/heads/develop`・`HEAD:refs/heads/main` を全網羅し、同時に `\b` 部分一致による `develop-fix`/`main-backup`（非保護ブランチ）の誤遮断（FP）を exact-match で解消する（メモリ `reference_string_token_match_anchoring` 準拠）。
- Q: protected 宛先 push を無条件化すると workflow.md の本番リリース（develop→main）と hotfix のローカル push（`git push origin main`/`develop`）が Claude から実行不能になる。無条件か、DANGER_OK 解除可の danger-op か → A: **DANGER_OK 解除可の danger-op**（無条件化は撤回）。protected 宛先 push は既定 exit 2 でブロックするが `if not danger_ok` の**内**に置き、`DANGER_OK=1`＋計画書明記＋danger-approved で release/hotfix 時のみ実行可とする（force push / reset --hard と同じ `danger-ops.md` の枠組み）。前 grill で"穴"とした `DANGER_OK=1 git push origin develop` → exit 0 は、本モデルでは**意図どおりの escape hatch**（穴ではない）と再定義。deny は `DANGER_OK=1` 前置を素通しする（プレフィックスでマッチ外れ）ため、未承認形は deny＋フックで遮断・承認形のみ通る一貫挙動になる。検出網羅（正規化・全宛先形・FP 解消・`--all`/`--mirror`）は本決定と独立に維持。
- Q: 発見したドキュメント不整合の扱いは → A: **必須分のみ I080・深い矛盾は別イシュー**。I080 では直接影響する `docs/claude-code-structure.md` を同期（`git push *` を ask→allow に修正＋フック挙動記述を新仕様に整合）。`docs/runbooks/issue-flow.md:390`（ローカル merge 後 `git push origin develop`）と CLAUDE.md 絶対ルール3（PR 経由・直 push 禁止）の「PR 経由 vs ローカル merge」方針矛盾は I080 より広いため別イシューに切り出す（本 I080 では触れない）。

## 背景/目的

### 現状の問題（証拠・再現手順）
通常の feature ブランチ push（引数なし `git push` 等）で承諾プロンプトが出る。
- `allow` に `Bash(git push -u origin *)` はあるが、引数なしの `git push` は無く `ask` の `Bash(git push *)` に落ちてプロンプトになる。
- 危険な push（develop/main・force）は `deny` ＋ PreToolUse フックで既にブロックされており、安全な feature push にまで毎回確認が入るのは冗長なノイズ。

### 根本原因
「危険な push は deny＋フックで阻止・それ以外は無確認」という運用モデルに対し、settings の `ask: git push *` が安全な push まで一律に止めている。機械的操作（安全な push）と危険操作（保護ブランチ/force）が権限レイヤーで分離しきれていない。加えてローカルガードに1か所穴がある（下記）。

### 解決方針
安全な push を `allow` 化して無確認にし、危険な push は **deny＋フックで既定ブロック（exit 2）し、release/hotfix 等の正当例外のみ `DANGER_OK=1`（＋計画書明記＋danger-approved）で解除可**とする。`git push *` を allow 化するとフックが捕捉しない push は無確認で実行されるため、**フックを危険 push 検出の権威ガードとして網羅化**する。判定は全て `if not danger_ok` の内に置く（`DANGER_OK=1` で解除可）。

**protected 宛先 push の検出（宛先正規化＋完全一致の単一関数に統一）**
- 宛先トークンを**正規化**して `develop`/`main` と**完全一致**判定する: 先頭 `+` 除去 → コロンがあれば右側 dst を採用 → `refs/heads/` 接頭辞除去 → `HEAD` は現ブランチに解決。これで以下を一括網羅する:
  - 明示名 `git push origin develop`/`main`
  - 引数なし `git push` / `git push origin` / `git push -u origin` を develop/main 上で実行（宛先=現ブランチ）
  - refspec `<src>:develop`/`<src>:main`（例 `feat:main`・`HEAD:develop`）
  - force-shorthand `+develop`、完全修飾 `refs/heads/develop`・`HEAD:refs/heads/main`
- 既存の `origin (develop|main)` 正規表現・`HEAD on protected` 判定はこの正規化関数に**置換改修**する（部分一致 FP `develop-fix`/`main-backup` も exact-match で解消）。

**その他の危険 push**
- `--all`/`--mirror`（全 ref 一括）ブロックを追加。`--force` と共に既定 exit 2・`DANGER_OK=1` 解除可。

**DANGER_OK の位置づけ（danger-op モデル）**
- protected 宛先 push は force push / reset --hard と同類の危険操作として扱い、`DANGER_OK=1`＋計画書明記＋danger-approved を満たす release/hotfix 実行時のみ解除する（`danger-ops.md` の枠組みに整合）。未承認の素 `git push origin develop` 等は deny＋フックで遮断され、`DANGER_OK=1` 前置時のみ deny を素通り（プレフィックスでマッチ外れ）→ フックも danger_ok で解除 → 通る、という一貫挙動になる。

deny（`origin develop|main`・`--force`）はテキストで自明な危険系の冗長バックストップとして維持。fail-open（`git rev-parse` 失敗時スキップ）は既存 HEAD チェックと同方針で許容（その環境では `git push` 自体も失敗）。

## スコープ
### 含む
- `git push` の allow 化（ask からの移動）
- フックの protected 宛先判定を**宛先正規化＋完全一致の単一関数に統一**（既存 `origin (develop|main)`・`HEAD on protected` 規則を置換改修）。`+develop`・`refs/heads/develop`・`HEAD:refs/heads/main` を網羅し、`develop-fix`/`main-backup` の部分一致 FP を解消
- protected 宛先 push を **danger-op として既定ブロック（exit 2）＋`DANGER_OK=1` 解除可**に統一（release/hotfix のローカル push を解除経路として維持）。判定を `if not danger_ok` 内に置く
- 危険 push に `--all`/`--mirror` ブロックを追加（既定 exit 2・DANGER_OK 解除可）
- `docs/claude-code-structure.md` を新仕様へ同期（`git push *` ask→allow、protected push の danger-op 化・正規化検出の反映）
- 新規決定論テスト `test_pretooluse_push_guard.sh`（全宛先形の既定 exit 2＋`DANGER_OK=1` 解除可＋`--all`/`--mirror`＋安全 push/`develop-fix` 宛先の exit 0 維持＋false-green 注入）
### 含まない
- `git merge`/`rebase`/`reset`/`cherry-pick` 等、他の git ask エントリの変更
- I079 で扱った編集（Edit/Write）プロンプトのポリシー
- 複数リモート（origin 以外）への push 判定（本リポジトリは origin 単一運用のため対象外）
- `--force`/`--all`/`--mirror`/`reset --hard` 等の DANGER_OK 解除ポリシー自体の変更（従来どおり解除可を維持）
- `docs/runbooks/issue-flow.md:390`（ローカル merge 後 `git push origin develop`）と CLAUDE.md 絶対ルール3（PR 経由・直 push 禁止）の方針矛盾の解消（I080 より広いため**別イシュー**に切り出す）

## 制約・引き継ぎ情報
- I079（feature/I079-relax-edit-permissions・Draft PR #159）とは別軸。I079 マージ後の develop を基点にブランチを切る想定（settings.json の衝突を避けるため）。
