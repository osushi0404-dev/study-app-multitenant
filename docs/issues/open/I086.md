## 設計確認メモ（/grill-me）
- Q: オーケストレーション方式（多観点ファンアウトの司令塔をどこに置くか） → A: **スキル主導方式で確定**。`code-review.sh` は従来どおり単発レビュー＋高リスク判定の機械可読出力までを担当し、高リスク時は `.claude/skills/code-review/SKILL.md`（メインセッションの Claude）が `Agent` ツールで敵対レビューアを並列起動し、周回・修正・再走を制御する（`.sh` から複数 `claude -p` を起動する方式は並列制御・修正→再走の結線が困難なため不採用。I080 で実際に欠陥を捕捉した Agent ツール方式の制度化）。SKILL.md の `allowed-tools` は Bash 単独から Agent 等を含む形に拡張する。
- Q: 高リスクトリガの機械可読化・判定基準 → A: **3点セットで確定**。①code-reviewer 出力の最終部に `RISK: YES|NO` 固定行を追加し、`.sh` が VERDICT 行と同じ anchored grep で解析（**行欠落時は YES 扱いの fail-closed**）。②判定条件リストを `code-reviewer.md` に明記（plan-reviewer.md の 11 条件を流用＋harness 固有条件「hooks・ガード・権限設定・レビュー基盤スクリプトの変更」を追加）。③LLM 判定とは別に変更ファイルパスの決定論トリガを `.sh` に併設し、以下に差分があれば LLM 判定に関わらず強制 YES: `scripts/claude/hooks/`・`scripts/git-hooks/`・`.claude/settings.json`・`.claude/settings.local.json`・`scripts/claude/*.sh`・`.claude/skills/`・`.claude/review-agents/`（レビュー基盤・ガードの自己改変は見逃すと安全網が消えるため機械検出。ユーザー確認「理想基準か」を受けパス範囲を拡充して確定）。アプリ側の認可・認証変更はパスで確定しづらいため②の条件リスト（LLM 判定）で拾う。
- Q: 観点分割の構成 → A: **固定 3 観点＋動的追加最大 2（1 周あたり最大 5 エージェント並列）で確定**。固定 3 観点＝①ロジック回避・実機再現（temp repo・exit code 実測）②テストの false-green・tautology ③要件・脅威モデルの網羅漏れ。固定 3 は I080 で見逃された欠陥 3 類型（R5 ロジック回避／false-green／R6 脅威網羅）に 1 対 1 対応。それ以外の型は差分内容に応じスキル判断の動的枠でカバー。
- Q: 終了条件・コスト上限 → A: **新規 Critical/High ゼロの周回が 1 回出たら終了**（1 周で全観点が独立並列に走るため。「ゼロ周回の連続」要求はコスト倍増に対し検出増が見合わず不採用）。**最大 3 周・サブエージェント総数 15**。上限到達時は自動 OK にせず**打ち切り＝FINAL VERDICT を HIGH 以上に固定しユーザーへエスカレーション**。findings 修正後の再走も周回数にカウント。
- Q: 敵対エージェントのツール権限 → A: **Read/Grep/Glob＋Bash（Edit/Write なし）で確定**。Bash は「読み取り系コマンド＋scratchpad 配下に作る使い捨て temp repo での再現実行」に限定し、本体リポジトリへの書込・push・ネットワークアクセス禁止を `adversarial-reviewer.md` に明記。既存 pretooluse_guard（hooks）はサブエージェントにも適用される。
- Q: 既存フローとの結線 → A: ①記録は `I###_adversarial_review_<timestamp>.md` として既存監査記録と同じ保存先・同じ commit 方式（feature ブランチのみ path-scoped）・PR コメント投稿。②FINAL VERDICT は現行 `max(gate, omission, LLM)` に敵対ステージ結果を加えた max 合成。③findings の自動修正は**レビューを依頼する側（スキル＝メインセッション）が実施し、レビューアのサブエージェントは修正しない**（Edit/Write 非付与と構造的に整合。ユーザー条件付き承認: 修正主体が「依頼側」であること）。修正後はステージ内で再レビューまで自動。設計判断が必要な指摘のみユーザーに確認。

## 背景/目的

### 現状の問題（証拠・再現手順）
`/code-review`（`code-review.sh`）は**単発の `claude -p`**（compliance 監査マンデートの `code-reviewer.md`・tools=`Read,Grep,Glob`）。
反証マンデート・多観点・実機 repro・loop-until-dry・対応後再レビューが無い。

**実証（I080）**:
1. 実装者が書いた実装後レビュー（`I080_review.md`）は当初**自己レビューで「合格」と自己認証**した。
2. 既存 `/code-review`（`claude -p`）も以前の記録 `I080_code_review_20260628_1829.md` で「全形捕捉 ✅ / VERDICT OK」とし、
   **Critical（R5 動的宛先）も High（R6/F1 force）も見逃した**。
3. 実際に欠陥を捕捉したのは、**ユーザーが「サブエージェントにレビューさせたか」と促し**、それを受けて
   `Agent` ツールで「判定を反証せよ」マンデートの多観点サブエージェント（Bash で temp repo・exit code 実測）を
   起動し、さらに対応後に再レビューしたから。＝**品質が人間の介入（安全網）に依存していた**。

### 根本原因
高リスク変更に対する**独立した敵対的検証ステージが自動で走らず、実装者の自己レビューが判定として通用**していた。
敵対的検証の手法（反証マンデート・観点分割・実機 repro・新規ゼロが続くまでの反復・対応後再レビュー）が
仕組み化されておらず、人が思い出して手動起動するかに依存していた（目標運用モデル「人のレビュー無しで高品質」の逆）。

### 解決方針
既に `/code-review` が出力する「**高リスク判定: Yes**」をトリガに、**敵対的レビューステージを自動起動**する。
（現状の「高リスク判定」は `claude -p` レビュー**本文の自由記述**で、`detect_code_verdict` は VERDICT 行のみ解析＝**機械可読でない**。本イシューで機械可読化してトリガに使う。）
- **反証マンデート×多観点**: 「合格を反証せよ」マンデートの複数サブエージェントを観点分割（例: ロジック回避／
  テスト false-green／要件・脅威モデル網羅）で起動。
- **実機検証**: 静的読解に留めず、必要に応じ Bash で再現（temp repo・exit code 実測）できるツール権限を与える。
- **loop-until-dry**: 新規の重大指摘（Critical/High）がゼロの周回が連続するまで継続。
- **対応後再レビュー**: findings 修正後に再走（修正自体が新たな欠陥を作り得るため。I080 で TC-DOC3 を混入させた実例）。
- **自己認証の非権威化**: 実装者が書く実装後レビューは判定根拠にせず、**独立ステージの結論を正**とする。
- **比例性**: 通常変更は現行の単発 code-review のまま。敵対ステージは高リスク時のみ（コスト・時間を抑制）。

> **設計上の論点（grill-me で確定済み・詳細は「設計確認メモ」）**:
> - **オーケストレーション層**: スキル主導方式。`.sh` は単発レビュー＋機械可読出力まで、敵対ステージは
>   SKILL（Claude メインループ）が `Agent` ツールでサブエージェントを並列起動・周回制御する。
> - **高リスクトリガの定義**: `RISK: YES|NO` 固定行（欠落時 YES の fail-closed）＋ code-reviewer.md への
>   条件リスト明記＋パス決定論トリガ（hooks/settings/スキル/レビュー基盤の変更は強制 YES）の 3 点セット。
> - **終了条件・コスト上限**: 新規 Critical/High ゼロの周回 1 回で終了。最大 3 周・サブエージェント総数 15。
>   超過時は打ち切り＝FINAL VERDICT を HIGH 以上に固定しユーザーへエスカレーション。
> - **敵対エージェントのツール権限**: Read/Grep/Glob＋Bash（読み取り＋scratchpad temp repo の再現のみ・
>   本体書込/push/ネットワーク禁止・Edit/Write なし）。
> - **既存フローとの結線**: 記録 `I###_adversarial_review_<timestamp>.md`・同一 commit 方式・PR コメント。
>   FINAL VERDICT は max 合成に敵対結果を追加。自動修正は依頼側（スキル）が実施しレビューアは修正しない。

## スコープ
### 含む
- 高リスク判定をトリガにした敵対的レビューステージ（多観点反証・実機 repro・loop-until-dry・対応後再レビュー）
- 実装者の自己レビューを判定根拠から外す（独立ステージを正とする）規約化
- 比例性（通常変更は現行のまま）の担保
### 含まない
- 決定論ゲートの実走化（I084#167・本ステージはその実 exit code を前提に使う）
- ガード設計のレビュー観点の中身（I085#168・敵対ステージが「探す中身」として参照）
- plan-issue-review / issue-review への同種適用（横展開は別途）

## 受け入れ条件（Acceptance Criteria）
- [ ] `/code-review` が「高リスク判定: Yes」を返す変更で、**敵対的レビューステージが自動起動**する（手動依存でない）
- [ ] 敵対ステージは反証マンデート×複数観点で実行され、必要時に実機 repro（Bash・temp repo）で裏取りできる
- [ ] loop-until-dry（新規 Critical/High がゼロの周回が 1 回出るまで継続・最大 3 周）と、findings 対応後の再レビュー（修正は依頼側＝スキルが実施）が行われる
- [ ] 実装者が書く実装後レビューが**合格判定の根拠にならない**（独立ステージの結論を正とする）ことが review-rules に明記
- [ ] 通常（非高リスク）変更では敵対ステージが起動せず、現行 code-review フローが無回帰
- [ ] I080 の R5/R6 相当を、本ステージが（過去ケース逆引きで）検出できることを確認・記録（ステージが load-bearing であることの裏取り）
- [ ] loop の最大周回数（3 周）・サブエージェント総数上限（15）が実装され、超過時は自動 OK にせず打ち切り＝FINAL VERDICT を HIGH 以上に固定してユーザーへエスカレーションする挙動が定義されている
