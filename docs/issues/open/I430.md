## 背景/目的

**背景**: I200 で、見張り（`scripts/claude/hooks/pretooluse_guard.py`）の確認を (A) GitHub の破壊・(B) 復旧できない状態・(C) 秘密や個人情報の流出だけに絞った。レビュー（コードレビュー・敵対的レビュー 3 周・/simplify）で、止める条件には当たらないが、方針の (B)・(C) に当たるのに確認にならない形と、作りの整理の余地が残った。
**目的**: 見張りを、公式の守り（サンドボックス・許可の設定・ワークツリーの隔離）を土台に組み直し、公式で足りる判定を見張りから消す。許可の設定も auto mode を前提に整理する（2026-11-11 の粒度の見直しで、残った取りこぼしの直しは #444、run-all の決まりは #445 に移した）。

### 現状の問題（証拠・再現手順）
1. **環境変数の表示の取りこぼし（(C)・`SECURITY=yes`）**: 引数なしの `export`・`declare`・`typeset`（オプションなしでも環境変数を全部表示する）と、`env -0`・`env -u X`（引数つきでも全部表示する）が確認にならない（台帳 F10・F12。`pretooluse_guard.py` の `_container_risky` の環境変数の表示の判定は `env` の引数なし・`export`／`declare`／`typeset` の `-p`／`-x` だけを見る）
2. **コンテナ内の書き込み先の取りこぼし（(B)）**: `cp -t <dir>`・`--target-directory=`・`mv` の移動元が `/app/` の場合が、`/tmp/` 以外への書き込みとして見られない（一覧 F9・F11。`_ctr_write_targets` は最後の位置引数だけを見る）
3. **WHERE なしの UPDATE（(B) 大量更新）**: コンテナ内・ホストの `psql -c "UPDATE users SET ..."`（WHERE なし）が、危ない語（`.update(` だけ）に当たらず通る疑い（敵対的レビュー 2 周目の Low）。見張りには WHERE なしの UPDATE・DELETE を見る判定があるが、`psql` の経路で効くかは未特定・計画で確かめる
4. **許可リストの二重化（/simplify の指摘）**: コンテナ内の「安全と確認済みの一覧」（`_container_safe`・約 110 行）は、I200 の後は「危ない語があっても通す例外」の役目だけになった。語の判定と二重の仕組みで、細かい分岐（`sed -n` の e・`find -fprint` など）はもう結果を変えない。`ps` の e の判定も 2 か所にある
5. **イシューの範囲の確かめが run-all に残る（I200 の手戻りの原因）**: I197 の「このブランチで見張りと settings.json を変えていない」確かめ（`test_i197_adversarial_process.sh` の S6）がマージ後も run-all に残り、見張りを変える I200 の CI を落とした（I200 で消した）。さらに、実装の段階の手元の run-all を未コミットのまま流したため、コミットの差分を見るこの確かめが偽合格になり、CI まで気づけなかった
6. **手順書と見張りの写しのずれ**: danger-ops.md の 4. は見張りの規則を言葉で写しているため、見張りを変えると写しがずれる（I200 の手動 M-05 の NG で 1 周の延長が要った・一覧 F13）
   - 2026-10-30 追記（I219 の retro・旧 #398 へのコメント。bot の停止で今は見えない。中身はこの項目に写してある）: 同じ形が `docs/runbooks/worktree.md` §9 でも起きた（primary の早送りの打ち切り方。I219 のコードレビューの F1）。6 の範囲に worktree.md も入れる

7. **見張りが公式の守りを使わずに大きくなった（2026-11-10 追加）**: `pretooluse_guard.py` は 3,856 行（2026-11-10 時点）。シェルの読み解き・Python の構文木の判定・SQL の分類・コンテナ内の許可リストまで自作で持つ。一方、公式のサンドボックスは使っていない（`.claude/settings.json` に `sandbox` の設定が無い）。公式の文書で確かめたこと（確認済み）: サンドボックスは既定で無効・WSL2 で動く・書き込みは作業ディレクトリの下と追加したディレクトリ・一時ディレクトリに限る（リンクされたワークツリーでは共有の `.git` への書き込みは許す）・名前ではなく場所で止める（`rm -rf` 自体は止めない）・ネットワークは許可したホストに限る・フックはサンドボックスの外で動く。ワークツリーのセッションでは、本体への Edit/Write・本体を作業ディレクトリにした Bash・`git -C` 等での本体への書き込みを Claude Code が拒否する（`cp`・リダイレクトは対象外）。未確認（計画で確かめる）: 作業ディレクトリの外にある別のワークツリーへの書き込みがサンドボックスで拒否されるか（文書に明記なし）・docker を使うコマンドをサンドボックスの外に出したとき、コンテナ内の DB 操作の守りが見張りに残るか・サンドボックスの中の Bash を確認なしで通す設定と、今の allow／見張りとの関係
   - I185 が見張りを「残す」とした理由のうち、「公式の隔離はメインの checkout だけ」はサンドボックスの書き込み先の制限で事情が変わった可能性がある。「サンドボックスは docker と両立しない」は今も当てはまる見込み（docker は外に出す必要がある）

### 根本原因
- 7: I185 は見張りを自作を出発点に判定し、I193 は見張りを見直しの対象から外した。そのため公式を土台にした見直しを一度も通っていない
- 1〜3: 見張りの規則を「確認を出す書き方の列挙」で作っているため、同じ意味の別の書き方（オプション違い・コマンドの別名）が漏れる。I200 では脅威モデル（事故）に沿って粗い判定にとどめた
- 4: I200 で判定の主役を語の判定に替えたとき、古い仕組み（許可リスト）を片付けなかった
- 5: 決定論テストの対象の選び方（`docs/runbooks/plan-writing-rules.md`）に「そのイシューの間だけの決まり（ブランチの範囲）は run-all に置かない」が無い。手元の run-all をコミットの前に流してよいかの決まりも無い
- 6: 規則の写しを手順書に持つ作り（I200 の M-05）

### 解決方針
- 7（最初に行う・1〜4 はこの結果を受けて決める）: 公式（サンドボックス・許可の設定・ワークツリーの隔離・自動モード）だけで組んだ守りを先に設計し、(A)〜(C) のうち止まらなくなる漏れを一覧にする。GitHub でも止まらない漏れだけを見張りに残す。サンドボックスで足りる判定（別のワークツリーへの書き込み・外部への送信など）は見張りから消す。失うもの（docker・`gh`・`git push` との両立、承認画面の増減、`claude -p` のレビュー役への影響）は、一時のディレクトリや `claude -p` で実際に動かして確かめてから採用する（I179 の教訓）
- 1〜4・6 と一覧の F5・F7・F8 は #444、5 は #445 で扱う（このイシューの計画書の「公式だけで組んだ守りと、それで止まらない漏れの一覧」を #444 が使う）
- 「見張りに判定を足すときの決まり」（設計確認メモ 2026-10-30）を `danger-ops.md` と `plan-writing-rules.md` に入れる
