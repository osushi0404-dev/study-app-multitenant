# I115: SubjectViewSet.public が未認証で401を返すバグを修正（get_permissions の override が @action の AllowAny を無効化・未認証の登録画面向け科目取得を復旧）

## 関連資料
- GitHub Issue: #213
- 発見経緯: I104（科目管理の更新系を組織管理者限定）の実装中、計画に組み込んだ確認テスト TC-SMOKE-01 で検出。未ログインで `GET /api/subjects/public/` を叩くと 401 が返る（本来 200 で科目リストを返す設計）。
- 関連イシュー: I104（#196）。I104 は `get_permissions()` の更新系分岐のみ変更し、`public` を含む else 分岐は不変更（＝本バグは I104 の退行ではなく変更前から存在する既存バグ）。
- 実測ログ: `docs/tests/open/I104_manual_test.md` の TC-SMOKE-01（未認証 `GET /api/subjects/public/?slug=personal` → 401 を記録）。

## 設計確認メモ（/grill-me）
- Q: `SubjectViewSet` は `/api/subjects/`（`backend/problems/urls.py`）と `/api/organizations/subjects/`（`backend/core/urls.py`）の2ルートに登録されており、新規登録画面（`frontend/src/pages/Register.tsx` → `frontend/src/services/subjectService.ts`）が実際に使うのは後者の `/api/organizations/subjects/public/`。回帰テストと AC は両ルートの未認証 200 をカバーする形に更新してよいか？ → A: **両ルートをカバーする**。修正は viewset 共通の1箇所でテストは URL が1件増えるだけの低コスト。片方だけだと実際に登録画面が使うルートが未検証のまま AC を満たしてしまうリスクの方が大きい。
- （自己解決・記録のみ）新規登録画面の未認証依存は確認済み: `Register.tsx:173` → `SubjectService.getSubjectsWithLoading` → `GET /api/organizations/subjects/public/?slug=...`。BE 修正のみで解消する想定（FE コード変更なし）。
- （自己解決・記録のみ）`backend/problems/views.py` の `get_permissions()` docstring（L86）は既に「public は AllowAny を維持」と記載済みだが実装が追随していない。本修正で記述と実装が一致する。

## 背景/目的

### 現状の問題（証拠・再現手順）
`SubjectViewSet` の `public` アクション（未認証の新規登録画面用に科目リストを返すエンドポイント）が、**未認証アクセスで 401 を返す**。本来は `@action(permission_classes=[AllowAny])` により誰でもアクセスできる設計。

証拠コード（`backend/problems/views.py`）:
```python
# L48 付近: public は AllowAny を明示している
@action(detail=False, methods=['get'], permission_classes=[permissions.AllowAny], url_path='public')
def public(self, request):
    ...

# get_permissions（I104 適用後の現行形）: else 分岐に public が落ち IsAuthenticated になる
def get_permissions(self):
    if self.action in ('create', 'update', 'partial_update', 'destroy'):
        return [permissions.IsAuthenticated(), IsOrgAdmin()]
    return [permissions.IsAuthenticated()]   # ← public もここに落ちる = 401
```

再現手順:
1. 未認証（トークンなし）で `GET /api/subjects/public/?slug=personal` を叩く。
2. 期待は 200（科目リスト）だが、実際は **401 Unauthorized**。
   - 実測: `docker compose exec backend python manage.py shell` で `APIClient().get('/api/subjects/public/?slug=personal', SERVER_NAME='localhost')` → status 401。

### 根本原因
`get_permissions()` を override して `self.action` ベースで固定の権限リストを返しているため、**DRF が `@action(permission_classes=[AllowAny])` を適用する経路（`self.permission_classes` 経由）が無効化される**。`public` は override 内のどの分岐にも明示されておらず else に落ちるため `IsAuthenticated` が課され、未認証で 401 になる。これは「命令的な `get_permissions` override が、宣言的な action 単位の権限設定を黙って上書きする」という DRF の既知の相互作用に起因する。

### 解決方針
`get_permissions()` に **`public` アクションを明示して `AllowAny` を返す分岐を追加**し、`@action` の意図（未認証許可）を override 内でも保全する。
```python
def get_permissions(self):
    if self.action in ('create', 'update', 'partial_update', 'destroy'):
        return [permissions.IsAuthenticated(), IsOrgAdmin()]
    if self.action == 'public':
        return [permissions.AllowAny()]
    return [permissions.IsAuthenticated()]
```
なお `SubjectViewSet` は `/api/subjects/`（`problems/urls.py`）と `/api/organizations/subjects/`（`core/urls.py`）の**2ルートに登録**されており、新規登録画面が実際に使うのは後者の `/api/organizations/subjects/public/`（`Register.tsx:173` → `SubjectService.getSubjectsWithLoading`、依存確認済み）。修正は viewset 共通の1箇所だが、回帰テストは**両ルートの未認証 200 を固定**する（/grill-me 確定）。
