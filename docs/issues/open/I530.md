## 背景/目的

**背景**: マージ依頼の前の最終確認（`pr-base-sync.sh final`）とレビュー段階（`code-review.sh`）は、どちらも「PR の CI が全部合格するまで待つ」処理を別々に持っている。I498 で上限の既定は 1 か所にまとめたが、待ち方の処理は 2 つのまま。最終確認の側には、レビュー段階の側に無い穴がある。
**目的**: 最終確認が、CI のジョブが全部そろって合格するまで待ってから「合格」と言うようにする。CI を待つ処理を 1 つにし、同じ処理の書き写しをなくす。

### 現状の問題（証拠・再現手順）
- `pr-base-sync.sh` の `ci_wait`（`:84`）は、`gh pr checks` の出力に `fail` があれば失敗、`pending` が無ければ合格とみなす
- push の直後で、CI のチェックがまだ登録されていないとき（`gh pr checks` が「チェックが無い」と答える）、`fail` も `pending` も無いので、CI を待たずに合格になる。ワークフローの一部（例: E2E）だけがまだ登録されていないときも、登録済みのジョブが終われば合格になる
- close の手順 5.5 は、close のコミットを push した直後に `final` を流すので、起きうる。`final` が BEHIND を取り込んで push した直後（`:118`）も同じ
- 実害はまだ出ていない（I498 の close では、チェックが登録済みで正しく待った）。マージは GitHub の承認が最後に止めるが、Claude は誤った合格を前提に「Approve & Merge をお願いします」と依頼してしまう
- 再現（スタブで）: `gh pr checks` が空（チェック無し）を返し、`mergeStateStatus` が `BLOCKED` のときに `pr-base-sync.sh final` を流す → `✅ CI 全グリーン` で exit 0

### 根本原因
- CI を待つ処理が 2 か所に別々に書かれ、レビュー段階の `wait_ci` だけが I193 で「PR で動くワークフローのジョブ（`expected_ci_jobs`）が全部 pass か skipping でそろうまで待つ」「PR の最新のコミットが手元の HEAD と同じかを確かめる」形に強くなった。最終確認の `ci_wait` は古い判定のまま取り残された（I498 の上限の食い違いと同じ形の、処理そのものの食い違い）

### 解決方針
- `pr-base-sync.sh` の `ci_wait` を、`code-review.sh` の `wait_ci` を呼ぶ形に置き換える（読み込み方は I498 と同じく、関数だけを読み込む `REVIEW_LIB_SOURCE_ONLY=1` を使う見込み。同じシェルで読むか別の bash で呼ぶかは計画で決める）
- 終わり方は今の `pr-base-sync.sh` のまま保つ: `wait_ci` の時間切れ（戻り値 3）は今の `⚠️ CI タイムアウト（<秒>秒）`・exit 1 に、失敗（戻り値 1）は今の `⛔ CI 失敗`・exit 1 に置き換える。close の手順 5.5 の「exit 1 は原因を見て直す」の扱いを変えない
- `wait_ci` が見る「手元の HEAD と PR の最新のコミットが同じか」（`CI_WAIT: NOT_PUSHED`・戻り値 1）は、最終確認でもそのまま使い、exit 1 で止める（close の手順 3 で push してから 5.5 に進むので、正常な流れでは起きない。起きたら「送っていないコミットがある」で、手順 5.5 の exit 1 の「原因を見て直す」に当たる。backlog の I224 F1〔衝突を直したコミットを push せずに依頼へ進む〕もこれで止まる）。メッセージは `NOT_PUSHED` と分かる形にする
- 上限の上書き（`PBS_CI_TIMEOUT`・`PBS_CI_INTERVAL`）と、`code-review.sh` 側の `CI_WAIT_TIMEOUT`・`CI_POLL_INTERVAL` の対応のさせ方は計画で決める（技術的な選択）

## 制約・引き継ぎ情報
- I498 の判断: 値の置き場所を新しい共有ファイルにしなかった理由は、`code-review.sh` を一時のフォルダに写して動かすテストが 5 本以上あるため（`plan_I498.md` §9）。同じ制約がこのイシューにもかかる
- `code-review.sh` の関数だけを読み込む形（`REVIEW_LIB_SOURCE_ONLY=1`）は、ガードより前に代入と関数の定義しかなく副作用が無いことを I498 のスパイクで確かめた。同じシェルで読むと `set -euo pipefail` が `pr-base-sync.sh` に入るので、`pr-base-sync.sh` の今の分岐の動きが変わらないかを確かめる必要がある
- `wait_ci` は `python3` と PyYAML でワークフローのジョブ名を読む（`expected_ci_jobs`）。`pr-base-sync.sh` を流す環境（close 段階のホスト）にそれがあることは review-gate と同じ前提。ハーネスのテスト（CI の Harness Tests・`run-all.sh`）は uv の環境で PyYAML を持つ（`test_i498_ci_wait_timeout.sh` が既に `CI_WORKFLOWS` に一時の yml を渡して `wait_ci` を動かしている）
- 再現のスタブの形は `test_i498_ci_wait_timeout.sh` の `gh` のスタブ（`pr checks --json` に `pending	A`、`mergeStateStatus` に `BLOCKED`）を、チェック無し（空）に変えたもの
