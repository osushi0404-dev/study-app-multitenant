# I156: backend 依存のロックファイル導入 — 推移的依存が再ビルドのたびに変動する状態を解消し、イメージビルドを再現可能にする

## 関連資料
- GitHub Issue: #273
- I151（Django 5.2 LTS 更新。決定 7-C で「推移的依存は今回触らず、`pip freeze` を記録する」とし、根治は本イシューへ送った）
- I154（未使用の Python 依存の棚卸し。「宣言はあるが使っていない依存」を扱う別軸）
- `docs/tests/open/I151_pip_freeze.txt`（I151 時点で実際にインストールされた全 81 パッケージの記録。本イシューの出発点）

## 背景/目的

**背景**: `backend/requirements.txt` は直接依存を `==` で固定しているが、**推移的依存は固定していない**。そのため `docker compose build` を実行するタイミング次第で、依存の依存が勝手に上がる。

I151 の調査で、これが既に起きていることを実測した。`requirements.txt` は `celery==5.3.4` を固定しているが、コンテナに入っている kombu は **5.6.2** である（celery 5.3.4 の宣言は `kombu (<6.0,>=5.3.2)` なので範囲内）。celery 自体は正常に動作しているが、**いつ入れ替わったのか誰も知らない**状態である。

**目的**: 同じコミットからは常に同じパッケージ構成のイメージが作られる状態にする。

### 現状の問題（証拠・再現手順）

`requirements.txt` に宣言のない推移的依存が多数インストールされている。

```bash
docker compose exec -T backend pip freeze | wc -l
```

I151 時点の実測: **81 パッケージ**。一方 `requirements.txt` の宣言は **18 行**。差の 63 パッケージはすべて推移的依存であり、バージョンが固定されていない。

具体例（I151 時点で確認）:
```
celery==5.3.4      ← requirements.txt で固定
kombu==5.6.2       ← 固定なし（celery の宣言は kombu<6.0,>=5.3.2）
amqp==5.3.1        ← 固定なし
billiard==4.2.4    ← 固定なし
vine==5.1.0        ← 固定なし
```

**実害**:
- **再現性がない**: 同じコミットをチェックアウトしても、ビルドした日によって中身が違うイメージができる
- **障害の切り分けが難しい**: 何かが壊れたとき、自分の変更のせいなのか推移的依存が上がったせいなのかを区別できない。I151 では「celery が落ちたら Django 更新のせいと誤診しやすい」という理由で `pip freeze` の記録を受け入れ条件に入れて凌いだが、これは対症療法である
- **監査結果が揺れる**: `pip-audit` はインストール済みパッケージではなく `requirements.txt` を見るため、推移的依存の脆弱性は現状の PR ゲートを素通りする

### 根本原因

`requirements.txt` が「人間が書く直接依存の宣言」と「実際にインストールされる全パッケージの固定」という**2 つの役割を兼ねている**。前者は手で編集したいので推移的依存まで書きたくない。後者は再現性のために全部書きたい。1 ファイルでは両立しない。

### 解決方針

**宣言と固定を 2 つのファイルに分ける。** 具体的なツール選定は計画時に確定するが、方式は次のいずれか。

- **(a) `pip-compile`（pip-tools）**: `requirements.in`（直接依存の宣言）→ `requirements.txt`（全依存をハッシュ付きで固定）を生成する。既存の `requirements.txt` の位置づけをそのまま「生成物」に変えられるため、Dockerfile と CI の変更が最小で済む。**推奨**
- **(b) `uv`**: 高速だがツールチェーン全体の移行を伴う
- **(c) Poetry / PDM**: `pyproject.toml` への移行を伴い、変更範囲が大きい

**あわせて決めること**:
1. **`requirements-dev.txt` も同じ方式にするか**（開発依存も再現性の対象にするか）
2. **ハッシュ固定（`--generate-hashes`）を使うか**（サプライチェーン攻撃対策として強いが、ビルドが厳格になる）
3. **更新の運用**: 誰がいつ `pip-compile` を回して更新するか。定期監査（Dependency Audit workflow）との関係
4. **`pip-audit` の対象**: 生成後の固定ファイルを監査すれば推移的依存の脆弱性も検出できるようになる。ただし**検出対象が増えると PR が止まる面積も増える**ため、I152（PR ゲートの差分判定化）の完了を前提にするかを判断する

## 実装対象（既知のもの）
| ファイル | 変更内容 |
|---------|---------|
| `backend/requirements.in`（新規） | 直接依存の宣言（現行 `requirements.txt` の 18 行を移す） |
| `backend/requirements.txt` | `pip-compile` の生成物に置き換え（推移的依存を含む全パッケージを固定） |
| `backend/requirements-dev.txt` | 同上（方式を dev にも適用する場合） |
| `backend/Dockerfile` | インストール手順の変更が必要かを確認（`pip install -r requirements.txt` のままで済む見込み） |
| `.github/workflows/ci.yml` | 生成物と `.in` の同期チェック（`pip-compile --check` 相当）を入れるかを判断 |
| `docs/runbooks/` | 依存を追加・更新する手順の記録 |

## スコープ
### 含む
- 宣言ファイルと固定ファイルの分離
- 現行のインストール構成（I151 時点の 81 パッケージ）を壊さない形での固定
- 依存を追加・更新する手順の文書化

### 含まない
- **パッケージのバージョン更新**（本イシューは「今の構成を固定する」ことが目的。上げるのは別作業）
- **未使用依存の除去** — I154 の担当範囲
- **`pip-audit` の対象拡大と CI ゲート化** — I152 の完了後に判断する
- **frontend の依存**（`package-lock.json` で既に固定済み）

## 関連する品質基準
- C7 フェールセーフ/可観測性 — 「同じコミットから同じものが作られる」ことは、障害の切り分けの前提条件
- C8 セキュリティ — 推移的依存を固定すると、意図しないパッケージの混入（サプライチェーン攻撃）を検知しやすくなる

## 受け入れ条件（Acceptance Criteria）
- [ ] 直接依存の宣言ファイルと、全依存を固定したファイルが分離されている
- [ ] 固定ファイルから作ったイメージのパッケージ構成が、`docs/tests/open/I151_pip_freeze.txt` と**意図的な差分を除いて一致**する（差分があれば理由を記録する）
- [ ] 同じコミットから 2 回ビルドして `pip freeze` が完全一致することを確認している
- [ ] 依存を 1 つ追加する手順が文書化され、実際に手順どおり実行できることを確認している
- [ ] backend の既存テストが全件 pass する（導入前と同数）
- [ ] E2E が全件 pass する
- [ ] CI の全 6 チェックが SUCCESS になる
- [ ] ハッシュ固定を使うかどうかを決定し、その理由を記録している
- [ ] `pip-audit` の対象を広げるかどうかを決定し、広げない場合は I152 との関係を記録している

## 影響範囲（想定）
- Backend: 依存ファイルの構成が変わる。パッケージのバージョン自体は変えない
- Frontend: なし
- DB: なし
- Config/Infra: `backend/Dockerfile` のインストール手順。`docker-compose.yml` の 4 サービス（backend / celery / celery-beat / e2e-init）が同じ Dockerfile を参照するため、再ビルドは全体に波及する。CI のキャッシュキー（`cache-dependency-path`）も確認する

## 制約・引き継ぎ情報
- **I151 のマージ後に着手する。** `requirements.txt` を全面的に作り替えるため、同ファイルを変更する I151 と競合する。
- I154（未使用依存の除去）とも `requirements.txt` で競合する。**I154 → I156 の順が望ましい**（不要なものを消してから固定するほうが、固定ファイルが小さくなる）。
- I151 決定 7-C の申し送り: 「kombu だけ固定しても他の推移的依存には同じ問題が残るので中途半端」という判断で、部分的な固定は採らないことになっている。
- トラック: `track:app`（変更対象は `backend/`）。

## Danger Ops（有/無）
- 有
- 内容: 本番イメージの依存解決方式を変更する。固定内容を誤ると、動いていた組み合わせと違うものがインストールされ、本番の挙動が変わりうる。
- 承認: 生成された固定ファイルと現行 `pip freeze` の差分を計画書で提示し、ユーザー承認を得てから実装する。
- ロールバック: 旧 `requirements.txt` へ戻し、backend / celery / celery-beat を再ビルドする。DB 変更を伴わないためデータ復旧は不要。
