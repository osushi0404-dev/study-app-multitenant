## 背景/目的

**背景**: 問題・解説の画像は、ファイルを `MEDIA_ROOT`（`backend/core/settings.py:129`・`BASE_DIR / 'media'`）に書き、DB の `MediaAsset`（`backend/problems/models.py:326`・テーブル `media_assets`）にはキー（`storage_key`）・元のファイル名・MIME・大きさ・SHA256 だけを持っている。書き込みは `ProblemService._save_image_as_asset`（`backend/problems/services/problem_service.py:118`・`:176-179` で `open(full_path, 'wb')`）、消すのは `StorageService.delete_file`（`backend/core/storage_service.py:132`）。配信は `/media/<storage_key>`（`MediaAsset.get_url`・開発は `backend/core/urls.py:40` で Django が、本番の想定は `nginx/default.conf:16-17` の `alias`）。古い形の `Problem.question_image`・`explanation_image`（ファイル名の文字列・`models.py` の Problem・「非推奨」）も残っている。

**目的**: 画像の中身を DB に保存し、ファイルの置き場を使わないようにする。DB に置くことで負荷・容量・控えに問題が出ないかを検討し、要る最適化を入れる。今あるファイルは DB に移し、移せたことを確かめてから捨てる。

### 現状の問題（証拠・再現手順）
1. 画像の中身と、それを指す DB の行が別々の場所にある。DB の控え（`scripts/db_backup.sh`）にファイルは入らないので、DB を戻しても画像が欠ける。逆にファイルだけ残ることもある（`delete_file` が失敗したときは記録を残して続ける・`problem_service.py:456-460`）。実際に app-1 では、行が 4 件あるのにファイルは 4 件とも無く、逆にディスクには行の無い見本のファイルだけがある（上の設計確認メモ）
2. `/media/` の配信はログインや組織の確かめを通らない（開発は Django の静的配信、本番の想定は nginx の `alias`）。キーを知っていれば他の組織の画像も取れる（キーは UUID を含むので推測は難しいが、境界を DB の条件で掛けていない）
3. ワークツリーごとに `backend/media` が分かれ（バインドマウント）、持ち運びや片付けで画像だけ取り残される

### 根本原因
2 つある。(1) 保存の分離: 画像の保存を「ファイルの置き場＋ DB のメタデータ」の 2 か所に分けた設計（#028・#029）で、両者を 1 つのトランザクションでそろえられず、控え・環境の持ち運びも別々になる（問題 1・3）。(2) 配信が認可を通らない: `/media/` を静的な配信にしているため、ログイン・組織の確かめを通らない（問題 2）。(2) はファイルのままでも認可付きの API にすれば直るが、(1) は DB に置かないと直らない。ユーザーの指示どおり DB に置き、配信も API にして両方を直す

### 解決方針
- 画像の中身（バイト列）を PostgreSQL に保存する（問題 1・3 を直す）。配信はログイン・組織の境界を確かめる API から返す（問題 2 を直す）。ファイルの置き場への書き込み・`/media/` の画像の配信をやめる
- 古い `/media/...` の URL: 本文に保存された古い URL は 0 件（設計確認メモ）なので、置き換え・転送はしない。画面は API が返す新しい URL を使う
- DB まわりの検討（計画で決め、結論と理由を計画書に残す）:
  - 置き方: `MediaAsset` に列を足すか、中身だけの別テーブル（1 対 1）にするか。一覧・問題の取得で中身を読まないようにする（`defer`・別テーブル）
  - 列の保存方式: PNG・JPEG はもう圧縮されているので、TOAST の圧縮をしない設定（`ALTER COLUMN ... SET STORAGE EXTERNAL`）にするか
  - 大きさの上限: 今の 5MB・4096px（`backend/problems/utils.py:24-27`）のままでよいか。縮小・再圧縮をするか
  - 配信の負荷: `checksum_sha256` を ETag にし、`Cache-Control: private`（共有のキャッシュに持たせない・組織の境界のため）でブラウザに持たせる。同じ問題の画像を何度も DB から読まない
  - 控えの大きさ・時間（`scripts/db_backup.sh`）と、接続ごとのメモリ・タイムアウト
  - 画面の認証は `Authorization: Bearer` の見出し（`frontend/src/services/api.ts`）なので、`<img src>` のままでは認証が付かない。画面での受け取り方（API から中身を取って表示する・短い期限の URL を返す など）は計画で決める
- 今あるファイルの移行: 移行は `migrate` で動く形（データのマイグレーション、または `migrate` から呼ぶ処理）にし、各環境が develop を取り込んで DB を更新したときに自動で移るようにする。ファイルを読み、中身を DB に入れ、`checksum_sha256` と大きさが一致することを確かめる。ファイルが無い行は、行（と問題との紐づけ）を消して件数を記録する。やり直しても二重に入らない
- 確かめるのは app-1 だけ。ほかのワークツリーの DB はこのイシューでは起動しない・触らない
- 捨てるもの: リポジトリの `backend/media/` にある見本の画像と空の目印ファイル（どの行からも使われていない）は、移さずにリポジトリから消す。`docker-compose.yml` の `backend_media` の定義と `nginx/default.conf` の `/media/` を外す（volume は作られていないので、消す実体は無い）。リポジトリのファイルを消すのは Danger Ops（承認を得てから・下の表）
- 古い形の `question_image`・`explanation_image`: 値のある行は 0 件なので、列と API の古い項目を外す。列を消すマイグレーションは Danger Ops（承認を得てから）
- 置き方の候補（`bytea`・Large Object）・上限の値・縮小するかは、技術の判断なので計画で決める。画面の見え方が変わる判断（例: 縮小で見づらくなる）が出たらユーザーに確認する

## 関連する品質基準
- C4 マルチテナント — 画像の配信を組織の境界の条件で掛ける（今は `/media/` がキーを知っていれば誰でも取れる）
- C7 フェールセーフ — 画像と行が 1 つのトランザクションでそろい、片方だけ残らない。移行は一致を確かめ、ファイルが無い行は消して件数を残す
- C8 セキュリティ — 配信の Content-Type を保存した MIME に固定し、`X-Content-Type-Options: nosniff` を付ける

## 受け入れ条件（Acceptance Criteria）
- [ ] 問題・解説の画像を登録・更新すると、中身が DB に入り、ディスクにファイルが作られない
- [ ] 画像は API から返り、ログインしていない・他の組織の利用者には返らない（404 か 403。テストで固定）
- [ ] 画面（問題のプレビュー・クイズの問題と解説・拡大表示）で画像が表示される
- [ ] 問題の一覧・クイズの問題の取得で、画像の中身を DB から読まない（クエリのテストで固定）
- [ ] 画像の応答に ETag（または同等）と Cache-Control が付き、同じ画像の 2 回目は 304 になる
- [ ] DB まわりの最適化の検討の結論（置き方・保存方式・上限・控えの大きさ）と理由が計画書にある
- [ ] 移行は `migrate` で動き、ファイルのある行は中身が DB に入って `checksum_sha256` と大きさが一致する。ファイルの無い行は行と問題との紐づけが消え、消した件数が出力される。やり直しても二重に入らない（どれもテストで固定）
- [ ] app-1 で移行を流した結果（移した件数・消した件数。2026-11-19 の時点の見込みは移す 0 件・消す 4 件）が記録にある
- [ ] リポジトリの `backend/media/` の見本の画像と空の目印ファイルを、承認を得て消した記録がある
- [ ] 古い `question_image`・`explanation_image` の列と API の古い項目が無くなり、列を消すマイグレーションを承認を得て流した記録がある
- [ ] `organization` か `subject` が null の `MediaAsset` の行（app-1 では 0 件）の扱いが決まり、テストで固定されている
- [ ] `/media/` から画像が配信されなくなり（`backend/core/urls.py`・`nginx/default.conf`）、`docker-compose.yml` から `backend_media` の定義が無くなる
- [ ] 画像の応答の Cache-Control が `private` で、Content-Type が保存した MIME・`X-Content-Type-Options: nosniff` が付く
- [ ] `scripts/db_backup.sh` で取った控えを別の DB に戻し、画像のある問題を画面で開いて画像が表示される。控えの大きさの増え方を記録する

## 制約・引き継ぎ情報
- 本番環境はまだ無いので、移行・破棄の対象は開発の環境だけ。移行を流して確かめるのは app-1 だけで、ほかのワークツリーの DB は起動しない・触らない（`docs/runbooks/worktree.md` §4）。ほかのワークツリーは develop を取り込んで `migrate` したときに同じ決まりで移る

- 画像の検査（形式・大きさ・寸法・`backend/problems/utils.py`）はそのまま使う
- `backend/data/problems/aws_saa/SAA-C03_basics_10_questions.md` に `q02_problem.png` の名前が書かれているが、読み込む処理は無い（2026-11-19 に `grep` で確認）

## Danger Ops（有/無）
- 有
- 何を: (1) リポジトリの `backend/media/` の見本の画像と空の目印ファイルの削除 (2) 古い画像の列（`question_image`・`explanation_image`）を消す破壊的なマイグレーション (3) 移行でファイルの無い `MediaAsset` の行と問題との紐づけを消すこと（app-1 では 4 件）
- なぜ: DB に移した後はファイルを使わず、二重に持つと食い違いの元になる。古い列は値のある行が 0 件で、残すと画像の出どころが 2 つになる。ファイルの無い行は画面で壊れた画像になる
- どう承認: app-1 で移行の試し（件数と `checksum_sha256` の一致・消す行の一覧）を見せ、ユーザーの承認を得てから流す・消す（`docs/runbooks/danger-ops.md`）
- どうロールバック: リポジトリのファイルは git の履歴から戻す。DB は流す前に `scripts/db_backup.sh` で控えを取り、マイグレーションを戻すか控えから戻す
