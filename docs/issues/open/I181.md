## 前提（ユーザーの方針・2026-10-21）
- develop/main は GitHub 側で保護されている（ブランチ保護・CODEOWNERS・承認必須。bot は PR を出すだけでマージできない）。ユーザーが判断を誤って破壊的な変更をマージしない限り、GitHub は壊れない。
- Claude がローカルで破壊的な操作をしても、GitHub から復旧できる（ローカルへの破壊は起こりうるが、GitHub への破壊はできない）。失いうるのは push していない手元の変更だけ。
- ユーザーは開発をもっと速く進めたい。判断の基準は「ループエンジニアリング・ハーネスエンジニアリングのベストプラクティスに沿っていて、速く進められるなら OK」。
- **このため、レビュー工程の重さは「GitHub が最後の守り」という前提で決める**。手元の見張り（フック・ガード・スクリプト）は事故を減らす補助であり、完全さを求めない。
- **この前提の例外（I182 で確定・2026-10-23）**: リポジトリは公開（PUBLIC）なので、マージしなくても GitHub 側に取り返しのつかない影響が出る操作がある（秘密情報を含むコミットの push・ワークフローや秘密情報の検査設定の書き換え・ワークフローが実行するコードからの `GITHUB_TOKEN` の利用・リモートブランチの削除）。一覧と対策は `docs/runbooks/danger-ops.md`「GitHub から復旧できる範囲（I182）」を正とする。**この例外に当たる変更は「GitHub が最後の守り」の対象外**として、レビューの重さを決める（敵対的レビューを回すときも 1 周・時間上限付き）。

## 背景/目的

**背景**: 高リスク判定が YES になると、`/code-review` は敵対的レビュー（1 周 3〜5 体のサブエージェントが反証を試み、重大な指摘が出たら修正して次の周へ・最大 3 周・15 体）を必須にする。この判定はファイルの場所だけで機械的に決まる。そのため、合否を決める仕組み（関所）を弱めない変更まで対象になる。また、1 体あたりの時間上限が手順として決まっていないので、1 回の敵対的レビューが数時間に膨らむことが多い。I174 の作業中にユーザーから「レビューに時間がかかりすぎて開発が進まない」と指摘があり、I180 で同じ問題を実測で確かめた。
**目的**: 守るべき変更（関所に関わる変更）には敵対的レビューを残したまま、対象外の変更では走らせない。走らせる場合も、決まった時間の中で終わるようにする。あわせて、ほかのレビュー工程（計画レビュー・fix-loop の 3 ゲート・基本コードレビュー）にも余分や重複がないかを、実測で確かめる。

### 根本原因
- 高リスク判定が「どの場所のファイルが変わったか」だけで決まり、「その変更が関所を弱めうるか」（関所になるスキルやスクリプトか・既存の検査を緩めるか消すか）を区別していない。
- 敵対的レビューの費用（時間・体数）に上限の決まりが無く、周回の打ち切り条件も「重大な指摘が 0 件」か「3 周・15 体」の 2 つだけである。
- レビュー工程の追加が、そのたびの事故への対処として積み重なり、工程全体の費用と効果を見直す機会がなかった。

### 解決方針
grill-me で確定した（詳細は「設計確認メモ」）。上の「前提」を判断の軸にする。
0. **ハーネスの変更で敵対的レビューを回すのは「GitHub から復旧できない例外」に関わる変更だけ**: 対象は `.github/*`・`.pre-commit-config.yaml`・`.secrets.baseline`・`scripts/claude/hooks/pretooluse_guard.py`・`.claude/settings.json` / `.claude/settings.local.json`。それ以外の手元のハーネス（スキル・スクリプト・レビュー指示・中核文書・テスト）の変更は、決定論ゲートが緑で基本レビューが OK なら先へ進む。アプリの高リスク条件（認証・テナント境界・個人情報など）は変えない。
1. **線引きの見直し**: `path_risk_trigger()` の対象を上の 0. の一覧に置き換える（`.github/*` を追加し、`scripts/claude/*.sh`・`.claude/skills/*`・`.claude/review-agents/*`・`.claude/agents/*`・`scripts/git-hooks/*`・`scripts/claude/hooks/*` の残り・CLAUDE.md・workflow.md・review-rules.md を外す）。`code-reviewer.md` の harness 固有条件を同じ集合に書き換え、`plan-reviewer.md` にも同じ集合を条件として追加する。既存テストの変更・削除を見分ける判定は作らない。
2. **時間の上限**: 1 体 15 分・攻め筋は 1 体 3 本まで・1 周 3 体を、`adversarial-reviewer.md` と `code-review/SKILL.md` に明記する。15 分を過ぎた体はオーケストレーターが止め、記録に「時間切れ」と残す。判定対象の実行は `timeout`・`ulimit -v` 付きのサブシェルで行う。
3. **打ち切り条件**: イシュー全体で 2 周まで（`/code-review` をやり直しても数え直さない）。2 周目は記録に残した `REVIEWED_COMMIT` からの差分だけを対象にする。上限に達して Critical/High が残れば、種類ごとに集計してユーザーに判断を仰ぐ。同じ種類が 2 周続いていれば「止める場所・方式の見直し」を選択肢の先頭に置く（I176 から取り込み）。
4. **工程全体の棚卸し**: I146・I151・I174・I178・I179・I180・I182 の記録から、工程ごとの所要時間と直す価値があった指摘の割合を測る。小さく減らせるものは本イシューで実施し、大きな統合（例: fix-loop の 3 ゲート）は結論を計画書に書いて別イシューにする。

### ガードの棚卸し（2026-10-21 追加・**2026-10-22 に別イシューへ切り出し・本イシューの範囲外**）
> ユーザー判断（2026-10-22）で、この節は別イシュー「『GitHub から復旧できる』前提が成り立たない操作を防ぐ（秘密情報の push など）」として起票した（I182・#307）。本イシュー（I181）はレビュー工程の見直しに絞る。下の記述は切り出し元の記録として残す。

レビュー工程と同じ前提（GitHub が最後の守り・ベストプラクティスに沿って速く進める）で、手元の安全装置（`pretooluse_guard.py`・`.claude/settings.json` の deny/ask・pre-commit・CI）も見直し、**必要なガードの追加・更新と、不要な確認待ちの削減**を検討する。詳細な調査・判断は grill-me 以降で行う。検討の起点（2026-10-21 時点の気づき・未検証）:
- **GitHub が最後の守りにならない事故を優先する**: リポジトリは公開（PUBLIC）で、一度 push した秘密情報は取り消せない。今の守りは手元の pre-commit（detect-secrets）だけで、`git commit --no-verify` で飛ばせ、ガードも止めず、CI にも秘密情報の検査が無い。候補: GitHub の push protection（秘密情報のスキャン。設定はユーザーの UI 操作）・ガードで `--no-verify` を止める・CI に秘密情報の検査を必須チェックとして追加。
- **ローカルで復旧できる操作の確認待ちを減らす**: settings.json の ask にある `rm`・`mv`・`cp`・`chmod`・`chown` など。`docker compose exec` は I174 と重なるので分担を決める。`rm -rf`・`git reset --hard` の承認制は CLAUDE.md の絶対ルール（危険操作は承認制）に関わるため、変えるかどうかを含めて判断する。
- **単純で安いガードは残す**: 保護ブランチへの push・強制 push・MCP からのマージ・別リポジトリの PR の取り込み・`git clean` の f 2 つ以上の承認制など。
- **ガードの異常終了で素通りにしない**（I179 retro P3）: PreToolUse フックは exit 2 以外の異常終了（例外・タイムアウト）ではコマンドを止めないため、判定関数の例外で、後ろの危険操作の検査（強制 push・`rm -rf` 等）がまとめて素通りになる作り。I179 第 10 周で、判定の処理量が爆発してメモリを使い切った実例がある（その判定は計画変更記録 6 で廃止済み）。`main()` の判定部分を「例外なら exit 2」に包むか、処理量に上限のある判定だけにするかを決める（決定論テスト: 例外を注入した複製で exit 2）。

- **記録突き合わせの比べる相手**（2026-10-22 発見）: **I182 で対応済み**（`guard_corpus_diff.py` の比べる相手を develop との分かれた点にした。`scripts/claude/tests/test_i182_corpus_base.sh`）。本イシューの対象から外す。

### I179 の振り返りから同梱する改善（2026-10-22）
- **新しい安全装置を足す前の確認**（I179 retro P1）: I179 では、敵対的レビューの指摘への対応として、計画になかった安全装置（別ワークツリーの削除・破棄ガード）をその場で足し、文字列からシェルの動きを読む判定を作り込んだ。その結果、第 4〜11 周・fix-loop 5 回・7 時間超を使った末に廃止した。守る対象（push していない手元の変更）は GitHub から復旧でき、費用に見合わなかった。fix-loop の対応方針・計画変更の確認観点に「新しい安全装置を足す・強める変更は、守る対象の復旧可否と最後の守りを先に記載し、復旧できる対象には単純な規則だけを使う」を加える（対象: `.claude/skills/fix-loop/SKILL.md`・`.claude/review-agents/plan-reviewer.md`）。上の「前提」と同じ判断軸にそろえる。
- **敵対的レビュー役の資源の上限**（I179 retro P2）: I179 第 10 周で、レビュー役が上限なしでガードの処理時間を測り、メモリを使い切ってセッション（WSL）ごと落ちた。`adversarial-reviewer.md` のツール境界に「判定対象を実行するときは、メモリと時間の上限（`ulimit -v`・`timeout`）を付けたサブシェルで行う。打ち切りやメモリ不足は処理量の欠陥の証拠として報告する」を加える（解決方針 2 の時間上限と同じ変更でまとめて行う）。
