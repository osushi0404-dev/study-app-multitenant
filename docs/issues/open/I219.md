# I219: セッションの開始時の primary の早送りが動かず、打ち切った git status が primary に index.lock を残す（I200 の M-04b の NG・最優先）

## 関連資料
- GitHub Issue: #399
- 起点: I200（#335・PR #397 は 2026-10-30 にマージ済み・8024d2e5）のマージ後の手動テスト M-04b の NG
- 対象: `scripts/claude/hooks/sessionstart_context.py`（`sync_primary`・`_run`・`TIMEOUT_SEC`・`PRIMARY_SKIP_AFTER_SEC`・`PRIMARY_STOP_AFTER_SEC`）・`.claude/settings.json`（`hooks.SessionStart` の `timeout: 30`）
- 手順書: `docs/runbooks/worktree.md` §2・§9（primary の早送りの例外）
- テスト: `scripts/claude/tests/test_sessionstart_context.sh`（TC-07a〜07i・FG-07）

## 設計確認メモ（/grill-me）
- Q（2026-10-30）: primary の早送りは、実際の primary だと `git status` だけで約 5 秒、取得と早送りを合わせると 10〜15 秒かかる見込み。セッションの開始時に待つか？（選択肢: 裏で動かして待たない／開始時に待つ）→ A: **裏で動かして待たない**。開始時のフックは裏の処理を起動するだけですぐ戻り、今の開始の速さを保つ。早送りの結果は、次のセッションの開始時の文脈に出す（例:「primary: 前回 … 早送りしました」）。時間の打ち切りに追われないので、ロックを残す心配も無くす。同時に複数のセッションが始まっても、裏の処理は 1 本ずつ動く（重なったら後から来たほうは何もしない）
- 範囲の追加（Claude が技術的に決めた・2026-10-30）: 今のワークツリー自身の `git status --porcelain`（`sessionstart_context.py:160`・I185 から）も、同じく `subprocess.run` の timeout（SIGKILL）で動いていて、遅いと今のワークツリーにもロックが残りうる。同じ根本原因なので、I219 で一緒に直す（フックの読み取りの git はすべてロックを取らない指定で動かす）

## 背景/目的

**背景**: I200 で、許可の判定の元になる primary（元のフォルダ）を、セッションの開始時のフックが `origin/develop` へ自動で早送りするようにした。マージ後に新しいセッションを始めて確かめたところ（M-04b）、早送りは動かず、さらに primary に `.git/index.lock` が残って、ユーザーの手の `git pull` が「index.lock: File exists」で失敗した（ユーザーがロックを消して手で pull し、2026-10-30 に primary は 8024d2e5 にそろった）。
**目的**: 開始時の早送りが実際の primary（Windows 側のフォルダ・追跡中のファイル約 1,900 個）で動き、どんな打ち切り方でも primary にロックを残さないようにする。

### 現状の問題（証拠・再現手順）
1. **早送りが動かない**: `sync_primary` の `git -C <primary> status --porcelain --untracked-files=no` は、`/mnt/c` の上の primary で **4.7 秒**かかった（2026-10-30 に読み取りだけの診断で計測）。フックの 1 コマンドの打ち切り（`TIMEOUT_SEC = 5`・`sessionstart_context.py:21`）にほぼ当たり、セッションの開始時は打ち切られて「primary: 状態を読めませんでした」を出して止まる（M-04b の実際の出力）
2. **ロックが残る**: `git status` は、ついでに索引を書き直すためにロック（`.git/index.lock`）を取る。`_run` は打ち切るとき `subprocess.run` の timeout で子を強制終了（SIGKILL）するので、ロックが消されずに残る。M-04b の後、primary の `.git/index.lock`（作成時刻が M-04b のセッションの起動時刻と一致・動いている git は 0）が残り、primary の git 操作がすべて失敗した。I200 では fetch・merge だけ SIGTERM の打ち切り（`_run_git_soft`）に直していて、`status` は対象外だった
3. **テストで見逃した理由**: TC-07 は小さい一時のリポジトリで動かすので `status` が速く、打ち切りに当たらない。マージ前の M-04a は、primary に未コミットの変更（I157.md）があったため `symbolic-ref` の次の判定で止まり、`status` まで進まなかった

### 根本原因
- 開始時のフックの時間の上限（1 コマンド 5 秒・全体 30 秒）を、実際の primary（Windows 側のフォルダ・大きい索引）で測らずに決めた
- 打ち切りの方法（SIGKILL）と、git がロックを取る操作（`status` の索引の書き直し）の組み合わせを考えていなかった

### 解決方針
- **ロックを取らない**: primary に対する読み取りの git（`status` など）を、`GIT_OPTIONAL_LOCKS=0`（git の公式が「裏で状態を見るとき」に勧める指定。索引の書き直しをしない）で動かす。これで打ち切られてもロックは残らない
- **裏で動かして待たない**（設計確認メモで決定）: 開始時のフックは、早送りの処理を裏で起動するだけですぐ戻る。裏の処理は時間の余裕を十分に取り（打ち切りは実際の primary で測って計画で決める）、結果を primary の外の決まった場所に書く。次のセッションの開始時に、その結果を文脈の 1 行に出す。同時に動く裏の処理は 1 本だけにする（排他の方法は計画で決める）
- 今のワークツリー自身の `git status --porcelain`（`sessionstart_context.py:160`）もロックを取らない指定で動かす（設計確認メモの範囲の追加）
- `status` の確かめ（未コミットの変更があればそろえない）は、I200 の設計確認メモでユーザーと決めた条件なので残す（変えない）
- 打ち切りはどれも SIGTERM で行い、git が自分で後片付けできる形に統一する
- テスト: 遅い git（打ち切りに当たる）でもロックが残らないことと、ロックが取られないことを、一時のリポジトリで固定する（失敗注入つき）
- 最初のコミットで、I200 の手動テスト M-04b の NG の結果を `docs/tests/closed/I200_manual_test.md` に書き足す
