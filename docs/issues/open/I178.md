## 設計確認メモ（/grill-me）
- Q: CODEOWNERS に書く承認者のアカウント名は？ → A: `oshui0404`（コード調査で確定。`gh api repos/osushi0404-dev/study-app-multitenant/collaborators` で `role_name=admin` は `oshui0404` のみ・bot `osushi0404-bot` は `write`。`osushi0404-dev` は Organization 名であり個人ではない）
- Q: ユーザー自身が作った PR（自分では承認できない）の扱いは？ → A: 管理者 bypass は許さない（develop・main とも「Do not allow bypassing the above settings」= ON を維持）。PR は必ず bot（Claude）に作らせる運用とし、runbook に明記する（過去にユーザー作成の PR は #93 の 1 件のみ）
- Q: 承認後に新しいコミットが push されたら承認を取り消すか？ → A: develop・main とも「Dismiss stale pull request approvals when new commits are pushed」= ON。理由: OFF だと「ユーザー承認後に bot が追加 push → bot がマージ」の抜け道が残る。代償として、承認後に develop 追従（Update branch）が入った場合は再承認が必要
- Q: マージ（push）できる人をユーザーに限定するか？ → A: 限定する。develop・main とも「Restrict who can push to matching branches」= ON・許可対象は `oshui0404` のみ（リポジトリ所有者が Organization のため classic branch protection で利用可）。承認が付いた後でも bot はマージできなくなる。現在もマージは全てユーザーが行っているため運用は変わらない
- Q: 受け入れ条件 4（bot が承認してもマージ要件を満たさない）の確かめ方は？ → A: 次の手順で了承済み（bot による承認の記録が GitHub に残ることも了承済み）
  1. 設定変更後、ユーザーのアカウントで develop 宛てに中身のない確認用 PR を 1 つ作る（bot は自分の PR を承認できないため）
  2. bot で `gh pr review <PR番号> --approve` を実行する
  3. `gh pr view <PR番号> --json reviewDecision,mergeStateStatus` が `REVIEW_REQUIRED`・`BLOCKED` のままであることを確かめる
  4. 確認後、その PR はマージせずに close する（ユーザー作成 PR のため bypass 不可の設定ではそもそもマージできない）
  - 対照（ユーザー承認で `APPROVED` になること）は、bot が作る本イシューの PR 自体で確かめる（受け入れ条件 2・3）
- 補足（コード調査で判明）: `branch-protection-setup.md` L45・L194〜197 の「自己 approve 可」は GitHub の仕様と異なる（PR 作成者は自分の PR を承認できない）。本イシューで誤記を是正する

## 背景/目的

**背景**: I146 では、外部（fork）PR への危険な操作を防ぐ仕組みを入れた。具体的には、Claude 側のフック（`pretooluse_guard.py`）が Bash のコマンド文字列を読んで判定する。ただし、文字列で判定する方式には原理的な限界がある（`bash -c`・`eval`・ユーザーのエイリアスなど。I146 計画書の「設計上の限界」）。retro では、実行時のラッパーで根本的に直す案を出した。これに対してユーザーから、2 つの指摘があった。
- 「private にすればいい」
- 「GitHub の権限でガードしていない？」

実際の状態を確認した結果（2026-10-17）、マージを GitHub 側で止める仕組みはほぼ無かった。ユーザーは「その設定は前にしたはず」と認識していた。実際に設定されていたのは main の承認 1 件だけで、develop には承認の要件が無かった。

**目的**: 外部の PR も bot（Claude）単独の操作も、**リポジトリ管理者（ユーザー）の承認がない限り、GitHub が develop・main へのマージを拒否する**状態にする。Claude 側のガードは補助の層とし、最も危険な「マージ」を GitHub の権限で確実に止める。あわせて、ハーネスの文書が前提にしていることと、実際の設定とのずれを解消する。

### 現状の問題（証拠・再現手順）
2026-10-17 に bot アカウントで確認した。
- `gh api repos/osushi0404-dev/study-app-multitenant --jq "{visibility, permissions}"` の結果は `visibility=public`・`permissions.push=true`・`admin=false`。bot は書き込み権限を持っている。
- **develop は承認不要**:
  - `gh pr view 261 --json reviewDecision,mergeStateStatus` の結果は `reviewDecision=""`・`mergeStateStatus=CLEAN`（承認なしでマージ可能）。
  - develop へマージ済みの直近 15 件（#217〜#277）は、作成者がすべて `osushi0404-bot`、マージした人がすべて `oshui0404`（ユーザー）で、`reviewDecision` はすべて空。承認は 1 件も付いていない。
  - 「ユーザーが毎回マージしている」のは運用であって、GitHub の設定で強制されたものではない。
- **main は承認 1 件が必要**: main 宛ての PR #75 は `reviewDecision=REVIEW_REQUIRED`。
  - ただし承認者の指定（CODEOWNERS）は無い。そのため、書き込み権限のある bot が他人（外部）の PR を承認すれば、要件を満たせてしまう。
- **CODEOWNERS が無い**: `git ls-files -- CODEOWNERS .github/CODEOWNERS docs/CODEOWNERS` の結果は 0 件。docs・runbook にも記載が無い。
- **ルールセットは未使用**: `gh api .../rules/branches/develop` と `.../main` は、どちらも `[]`。
- 必須チェックは 5 種類（Backend Lint & Security・Backend Tests・Frontend Lint & Security・Frontend Tests・Frontend Type Check）。E2E は含まれない。そのため、secrets が届かない fork PR でも、必須チェックは合格しうる。
- **文書が前提にしていることと実際の設定のずれ**:
  - `.claude/skills/close/SKILL.md` L151〜152 と `scripts/claude/pr-base-sync.sh` L6・L114 は、「ユーザーの Approve がマージ条件・承認前の正常な状態は BLOCKED」を前提にしている。
  - 一方、`docs/runbooks/branch-protection-setup.md` では develop を「Require approvals: OFF」と定めており、実際の設定も承認不要（CLEAN）。

### 根本原因
次の 2 つのため、「誰がマージできるか」の最後の砦が、GitHub の権限ではなく運用と Claude 側のガードになっていた。
- ブランチ保護の設計が「bot は信頼できる共同作業者」「外部の人は PR を出してこない」を暗黙の前提にしていた。
  - develop は作業効率のため承認不要にした。
  - main は承認 1 件にしたが、承認者を限定しなかった。
- 公開リポジトリで外部の人が PR を出してくることや、bot が他人の PR を承認できることが、脅威として扱われていなかった。

さらに、スキル（close・pr-base-sync）は「承認が必須」を前提に書かれていたが、実際の設定と突き合わせる確認が無かった。そのため、ずれに気づけなかった。

### 解決方針
- **CODEOWNERS**: `.github/CODEOWNERS` に `* @oshui0404` を置き、すべてのファイルの所有者をリポジトリ管理者だけにする（アカウント名は grill-me で確定。collaborators API で admin は `oshui0404` のみ）。CODEOWNERS 自体の変更も、Code Owners の承認の対象にする。
- **ブランチ保護（ユーザーが GitHub の画面で操作）**: develop と main の両方で次を設定する。
  - 「Require a pull request before merging」→「Require approvals: 1」
  - 「Require review from Code Owners」= ON
  - 「Dismiss stale pull request approvals when new commits are pushed」= ON（承認後の bot 追加 push → bot マージの抜け道を塞ぐ）
  - 「Restrict who can push to matching branches」= ON・許可対象は `oshui0404` のみ（承認後でも bot はマージできない）
  - 「Do not allow bypassing the above settings」= ON を維持（管理者 bypass は許さない）
- **運用**: PR は必ず bot（Claude）が作る。ユーザー自身が作った PR は、自分で承認できず bypass も不可のためマージできない。これを runbook に明記する。
- **文書の整合**: branch-protection-setup.md の develop・main の項を上記の設定に書き換え、変更の理由（外部 PR と bot の承認権限・承認後 push・bot のマージ権限）を書く。「自己 approve 可」の誤記（L45・L194〜197）を是正する。close と pr-base-sync の前提（BLOCKED＝承認待ちが正常）は、そのまま実際の設定と一致するようになる。文言と確認手順を見直す（承認後に develop 追従が入ると再承認が必要になる点も close スキルに書く）。
- **検証**: 設定変更の後、次の 3 点を確かめる。
  - bot の PR（本イシューの PR）が `reviewDecision=REVIEW_REQUIRED`・`mergeStateStatus=BLOCKED` になること
  - ユーザーが承認すると `APPROVED` になりマージ可能になること
  - ユーザー作成の確認用 PR を bot が承認しても `REVIEW_REQUIRED`・`BLOCKED` のままであること（設計確認メモの手順）
- **private 化は採らない**: 無料プランの private リポジトリではブランチ保護が使えず、Actions の無料枠も減るため（ユーザー判断 2026-10-17）。

## 制約・引き継ぎ情報
- bot アカウント（osushi0404-bot）は admin 権限が無い。ブランチ保護の変更 API は 404 になり、保護の詳細（承認要件）も読めない。設定の変更はユーザーが GitHub の画面で行う。確認は PR の `reviewDecision`・`mergeStateStatus` で間接的に行う（メモリ: bot アカウントは repo admin 権限なし）。
- 設定後は、すべての PR のマージ前に、ユーザーが承認（Approve）を 1 回押す必要がある。今もマージはすべてユーザーが行っているので、増える手間は承認の 1 クリックだけ。
- ユーザー自身が作った PR は、自分では承認できず bypass も不可のためマージできない（grill-me で確定）。PR は必ず bot が作る。
- 承認後に develop 追従（Update branch）が入ると承認が取り消され、再承認が必要になる（Dismiss stale ON の代償・grill-me で了承済み）。
- I146 の Claude 側ガード（fork PR の merge・checkout を block）は、このイシューの後も残す。二重の守りにする。
- 着手順: I146 と I174 の進み具合に関係なく着手できる。ただし設定を変えた瞬間から、作業中の PR（#261・#293 など）にも承認が必要になる。マージの段取りを事前に伝える。
