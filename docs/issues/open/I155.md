# I155: guardian の残置物の除去 — django-guardian 廃止（I151）で不要になった 2 テーブルと残置データをバックアップ取得のうえ削除する

## 関連資料
- GitHub Issue: #272
- I151（django-guardian を `requirements.txt` と `INSTALLED_APPS` から削除。本イシューはその残置物の後始末）
- I154（未使用の Python 依存の棚卸し。同じ「使っていないものを片付ける」系列）

## 背景/目的

**背景**: I151 で未使用の django-guardian を依存から除去した。アプリからは完全に切り離されたが、**DB に作られていた 2 テーブルと、guardian が自動作成したデータは意図的に残置**した。不可逆な操作を脆弱性解消と同一 PR に混ぜるとレビューもロールバックも難しくなるためである。

**目的**: 参照されなくなった 2 テーブルと残置データ一式を、バックアップを取ったうえで DB から除去する。

### 現状の問題（証拠・再現手順）

I151 のマージ後、`INSTALLED_APPS` に guardian が無い状態で、以下の 2 テーブルが DB に残る。

```bash
docker compose exec -T db psql -U postgres -d learning_app -tAc "SELECT tablename FROM pg_tables WHERE tablename LIKE 'guardian%' ORDER BY 1;"
```

実測結果（2026-08-22）:
```
guardian_groupobjectpermission
guardian_userobjectpermission
```

あわせて `django_migrations` テーブルに guardian のマイグレーション適用履歴が残る。

**テーブル以外の残置データ（2026-10-14・I151 の敵対的レビューで判明・開発 DB で読み取りのみで実測）**: guardian が既存 DB に自動作成した次のデータも残る。
- `AnonymousUser` ユーザー行 1 件（`email='AnonymousUser'`・`is_active=True`・組織 3「個人利用」所属。パスワードは使用不可でログインはできない）
- **このユーザー行を削除すると CASCADE で連鎖削除されるデータ**: `accounts.UserSettings` 1 行・`accounts.StudyStreak` 1 行（いずれもユーザー作成時に自動作成されたもの。Django の `Collector` による読み取り専用の試算で確認。回答・学習ログ等の他の関連データは 0 件）
- contenttype 2 行（`guardian.groupobjectpermission` / `guardian.userobjectpermission`）
- 上記 contenttype に紐づく `auth_permission` 8 行（contenttype の削除で連鎖削除される。ユーザー・グループへの権限付与は 0 件）

I151 以降に作られる新しい DB にはこれらが作られないため、既存 DB と新規 DB で中身が食い違う。有効フラグの立った組織メンバーとして集計・一覧に混ざりうる。

**実害は小さいが放置すべきではない理由**:
- 参照されないテーブルはスキーマの読み手を混乱させる（「オブジェクト権限を使っているのか？」という誤解を生む）
- DB のバックアップ・ダンプ・移行のたびに無駄なオブジェクトが運ばれる
- I151 で「guardian は認可に使っていない」と結論づけた根拠を、スキーマが裏切って見える状態が続く
- 実体の無い「有効な組織メンバー」が環境ごとに存在したりしなかったりする

### 根本原因

Django は `INSTALLED_APPS` からアプリを外しても、そのアプリが作成したテーブルやデータ（自動作成ユーザー・contenttype・permission）を自動では削除しない（データ保護のための正しい挙動）。除去は明示的な操作を要する。

### 解決方針

**削除対象の全数確認 → バックアップ取得 → 想定外データが無いことの確認 → 削除、の順で行う。**

1. **削除対象の全数確認**: 削除の前に、連鎖削除まで含めた削除対象を `Collector` による読み取り専用の試算で列挙し、記録する。想定は次のとおり。2 テーブルの行数・`AnonymousUser` 1・`UserSettings` 1・`StudyStreak` 1・contenttype 2・`auth_permission` 8。**想定と異なる件数・種類が出たら削除せず停止し、調査する**
2. **バックアップ**: 削除前に、手順 1 で列挙した**すべて**を退避する。2 テーブルは `pg_dump`（テーブル単位）で退避する。行データ（`accounts_user` の該当 1 行・`accounts_usersettings` / `accounts_studystreak` の各 1 行・`django_content_type` の 2 行・`auth_permission` の 8 行）は `pg_dump --data-only` か `manage.py dumpdata` で退避する。復元手順と、復元後の件数確認の方法を記録する
3. **2 テーブルが空であることの確認**: `SELECT count(*)` が両テーブルとも 0 であることを確認する。**0 でない場合は削除せず停止し、なぜレコードが存在するのかを調査する**（I151 の「未使用」判定と矛盾するため）
4. **削除方式の決定**: 次のどちらを採るかを計画時に確定する
   - (a) 手動 SQL（`DROP TABLE` / `DELETE`）— マイグレーション履歴に残らない
   - (b) Django のマイグレーション（`migrations.RunSQL` / `RunPython` を持つ空アプリ）— 履歴に残り、他環境へも自動適用される
   - **推奨は (b)**。開発者ごとのローカル DB・staging・本番と適用先が複数あるため、手動 SQL では適用漏れが起きる。ただし (b) は**不可逆な削除が本番にも自動で流れる**ため、各環境で手順 1〜3（全数確認・バックアップ・空確認）を先に行うこと、想定外の件数があれば失敗して止まることを、マイグレーション自体に組み込む
5. **`django_migrations` の guardian 行**: 削除するかどうかを計画時に決める（残しても害はないが、再導入時に「適用済み」と誤認されるリスクがある）

## 実装対象（既知のもの）
| ファイル | 変更内容 |
|---------|---------|
| `backend/core/migrations/`（新規・または適切なアプリ配下） | 2 テーブルと残置データ一式を除去するマイグレーション（方式 (b) を採る場合）。想定外の件数なら例外で停止する |
| バックアップファイル | 2 テーブルの `pg_dump` と残置データ行のダンプ。出力先と保管方針を計画時に決める（リポジトリにコミットしない） |
| `docs/runbooks/` | 適用手順・復元手順の記録（必要に応じて） |

## スコープ
### 含む
- 削除対象（連鎖削除を含む）の全数確認と記録
- 2 テーブルと残置データ一式のバックアップ取得、および復元手順の記録
- 2 テーブルのレコード数が 0 であることの確認
- 2 テーブルの除去
- `AnonymousUser` ユーザー行（連鎖削除される `UserSettings` 1・`StudyStreak` 1 を含む）・guardian の contenttype 2 行・`auth_permission` 8 行の除去（2026-10-14 追加）
- `django_migrations` の guardian 行の扱いの決定と実施

### 含まない
- **他の未使用テーブル・データの棚卸し**（あれば別イシュー）
- **django-guardian の再導入**
- 依存パッケージの変更（I151 で完了済み）

## 制約・引き継ぎ情報

- I151 で実測済みの事実: guardian の具象モデルは `UserObjectPermission` と `GroupObjectPermission` の 2 つのみ。マイグレーション参照 0 件・コードからの利用 0 件。残置データの件数と連鎖削除の範囲は、2026-10-14 に開発 DB で実測（上記）。

## Danger Ops（有/無）
- 有
- 内容: **DB テーブルの削除と、ユーザー行（連鎖削除を含む）・contenttype・permission の削除（いずれも不可逆）**。判定を誤ると復旧にバックアップが必要になる。
- 承認: 削除対象の全数（テーブル名・モデル別件数・連鎖削除の内訳）・2 テーブルのレコード数 0 の実測結果・バックアップの取得先を計画書で提示し、ユーザー承認を得てから実施する。
- ロールバック: 取得済みのバックアップから復元する。2 テーブルは `pg_dump` から、行データはダンプから復元する。復元後に、手順 1 で記録した件数と一致することを確認する。マイグレーション方式の場合は逆マイグレーションでの再作成も併用する。
