# I155: 未使用の guardian_* テーブル除去 — django-guardian 廃止（I151）で不要になった 2 テーブルをバックアップ取得のうえ削除する

## 関連資料
- GitHub Issue: #272
- I151（django-guardian を `requirements.txt` と `INSTALLED_APPS` から削除。本イシューはその残置物の後始末）
- I154（未使用の Python 依存の棚卸し。同じ「使っていないものを片付ける」系列）

## 背景/目的

**背景**: I151 で未使用の django-guardian を依存から除去した。アプリからは完全に切り離されたが、**DB に作られていた 2 テーブルは意図的に残置**した。不可逆な操作を脆弱性解消と同一 PR に混ぜるとレビューもロールバックも難しくなるためである。

**目的**: 参照されなくなった 2 テーブルを、バックアップを取ったうえで DB から除去する。

### 現状の問題（証拠・再現手順）

I151 のマージ後、`INSTALLED_APPS` に guardian が無い状態で、以下の 2 テーブルが DB に残る。

```bash
docker compose exec -T db psql -U postgres -d learning_app -tAc "SELECT tablename FROM pg_tables WHERE tablename LIKE 'guardian%' ORDER BY 1;"
```

実測結果（2026-08-22）:
```
guardian_groupobjectpermission
guardian_userobjectpermission
```

あわせて `django_migrations` テーブルに guardian のマイグレーション適用履歴が残る。

**実害は小さいが放置すべきではない理由**:
- 参照されないテーブルはスキーマの読み手を混乱させる（「オブジェクト権限を使っているのか？」という誤解を生む）
- DB のバックアップ・ダンプ・移行のたびに無駄なオブジェクトが運ばれる
- I151 で「guardian は認可に使っていない」と結論づけた根拠を、スキーマが裏切って見える状態が続く

### 根本原因

Django は `INSTALLED_APPS` からアプリを外しても、そのアプリが作成したテーブルを自動では削除しない（データ保護のための正しい挙動）。除去は明示的な操作を要する。

### 解決方針

**バックアップ取得 → 中身が空であることの確認 → テーブル削除、の順で行う。**

1. **バックアップ**: 削除前に 2 テーブルを `pg_dump` で退避する（テーブル単位のダンプをファイルに保存し、復元手順を記録する）
2. **空であることの確認**: `SELECT count(*)` が両テーブルとも 0 であることを確認する。**0 でない場合は削除せず停止し、なぜレコードが存在するのかを調査する**（I151 の「未使用」判定と矛盾するため）
3. **削除方式の決定**: 次のどちらを採るかを計画時に確定する
   - (a) 手動 SQL（`DROP TABLE`）— マイグレーション履歴に残らない
   - (b) Django のマイグレーション（`migrations.RunSQL` を持つ空アプリ）— 履歴に残り、他環境へも自動適用される
   - **推奨は (b)**。開発者ごとのローカル DB・staging・本番と適用先が複数あるため、手動 SQL では適用漏れが起きる
4. **`django_migrations` の guardian 行**: 削除するかどうかを計画時に決める（残しても害はないが、再導入時に「適用済み」と誤認されるリスクがある）

## 実装対象（既知のもの）
| ファイル | 変更内容 |
|---------|---------|
| `backend/core/migrations/`（新規・または適切なアプリ配下） | `guardian_userobjectpermission` / `guardian_groupobjectpermission` を除去するマイグレーション（方式 (b) を採る場合） |
| バックアップファイル | `pg_dump` の出力先と保管方針を計画時に決める（リポジトリにコミットしない） |
| `docs/runbooks/` | 適用手順・復元手順の記録（必要に応じて） |

## スコープ
### 含む
- 2 テーブルのバックアップ取得と復元手順の記録
- レコード数が 0 であることの確認
- 2 テーブルの除去
- `django_migrations` の guardian 行の扱いの決定と実施

### 含まない
- **他の未使用テーブルの棚卸し**（あれば別イシュー）
- **django-guardian の再導入**
- 依存パッケージの変更（I151 で完了済み）

## 影響範囲（想定）
- Backend: マイグレーションの追加（方式 (b) の場合）。アプリコードの変更なし
- Frontend: なし
- DB: **2 テーブルの削除（不可逆）**。データは空である前提だが、バックアップを取得してから実施する
- Config/Infra: なし

## 制約・引き継ぎ情報
- **I151 のマージ後に着手する。** I151 で `INSTALLED_APPS` から guardian が外れていることが前提。
- I151 で実測済みの事実: guardian の具象モデルは `UserObjectPermission` と `GroupObjectPermission` の 2 つのみ。マイグレーション参照 0 件・コードからの利用 0 件。
- トラック: `track:app`（変更対象は `backend/`）。

## Danger Ops（有/無）
- 有

- 承認: 削除対象のテーブル名・レコード数 0 の実測結果・バックアップの取得先を計画書で提示し、ユーザー承認を得てから実施する。
- ロールバック: 取得済みの `pg_dump` から該当テーブルを復元する。マイグレーション方式の場合は逆マイグレーションでの再作成も併用する。
