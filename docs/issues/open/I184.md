## 背景/目的

**背景**: I179 でワークツリーの運用を見直した。人が使うワークツリーは primary から公式の `claude --worktree <track>-<連番>` で作る、トラックはワークツリーでなく GitHub ラベルで分ける、と決めた。I179 で変えたのは手順書とスクリプトだけで、今あるワークツリーとラベルの移行は「残作業」として完了記録に残っている（I179 の作業場所が `wt-harness` 自身だったため、その中では移行できなかった）。
**目的**: 今の環境を I179 で決めた形に揃える。具体的には次の 4 点。(1) 旧方式の `wt-harness` を、未コミットのイシューファイルを失わずに撤去する。(2) primary から公式方式でハーネス改善用のワークツリー（harness-1・harness-2）を作れる状態にし、実際に作る。(3) GitHub ラベルの説明文に残っているワークツリー名を消す。(4) 手順書 §11 どおりに進めて、詰まった点があれば手順書を直す。

### 現状の問題（証拠・再現手順）
2026-10-24 に primary で確認:
- `git worktree list` → `/mnt/c/app/wt-harness  e1311fa [feature/I181-slim-review-process]`。旧方式（primary の外・自作スクリプトで作ったもの）のワークツリーが残っている。今は I181 の作業中（`docs/issues/open/I181.md` 変更・`docs/plans/open/plan_I181.md` 未コミット）。
- `git -C /mnt/c/app/wt-harness status --porcelain --untracked-files=all` → `wt-harness` にしか無い未コミットのイシューファイル・イシューレビューが多数ある（I093・I094・I099・I101・I110・I112・I118・I121・I125・I128・I130・I135・I136・I139・I151・I152・I175・I176・I177 の `docs/issues/open/` と、対応する `docs/reviews/*_issue_review_*.md`、I100・I181 のイシューレビュー）。そのまま撤去すると起票済みイシューの本文と採番の根拠が消える。このうち I121・I151 などは closed 済みの古い版で、§11 の「コピーしないもの」にあたる。
- `git symbolic-ref refs/remotes/origin/HEAD` → `refs/remotes/origin/main`。§2 の「作る前の確認 1」に通らない。このまま `claude --worktree` を使うと、中身の無い main を基点にした空のワークツリーができる。
- `gh label list --search track` → `track:harness`「ハーネス改善トラック（worktree: wt-harness）」・`track:app`「学習アプリ開発トラック（worktree: study-app-multitenant）」。I179 で廃止した「トラック＝ワークツリー」の固定対応が説明文に残っている。
- `docker compose ls -a` → `study-app-multitenant` のみ。`wt-harness` の Compose プロジェクトは無い（撤去時に Docker データの削除は不要な見込み。実行時に `wt-remove.sh` が判定する）。

### 根本原因
I179 は `wt-harness` 上で進めたため、自分の作業場所を撤去・移行できなかった。だから設計どおり、移行は完了後の残作業に回した。ラベルの説明文はリポジトリ設定（外部の変更）なので、I179 の PR には入れなかった。`origin/HEAD` は clone した時点の既定（main）のまま残っていて、§2 の確認手順ができたあとも、まだ合わせ直していない。

### 解決方針
`docs/runbooks/worktree.md` §2・§4・§11 の手順をそのまま実行する（新しい仕組みは作らない）。順序:
1. **着手の時期**: `wt-harness` で進めている I181 が完了・クローズしてから行う（§11 の前提「そこで進めているイシューが完了した後」）。I181 の途中では行わない（設計確認メモ）。
2. primary で §2「作る前の確認」を行う（`git remote set-head origin --auto` で `origin/HEAD` を develop に合わせる・primary のブランチが I179 以降の内容を含むことを確かめる）。
3. §11 手順 1: `wt-harness` にしか無い未コミットのファイルを primary へコピーして `cmp` で確かめる。closed 済みの番号はコピーしない。両方にあるファイルは中身を比べる。`!!`（`.claude/settings.local.json` など）は、必要な行だけ primary 側へ手で反映する。
4. §11 手順 2〜3: 入れ子があれば先に撤去する。コピーしたものは `wt-harness` のセッションで削除し、primary から `bash scripts/claude/wt-remove.sh /mnt/c/app/wt-harness` で撤去する。
5. §11 手順 4: primary で `claude --worktree harness-1` と `claude --worktree harness-2` を作る。ポート割当は §5・§6（`wt-ports.sh`）に従う。
6. `gh label edit track:harness --description "ハーネス改善トラック"`・`gh label edit track:app --description "学習アプリ開発トラック"`（bot アカウントに権限が無ければユーザーが UI で行う）。
7. 手順どおりに進まなかった箇所があれば `worktree.md` を直す。
8. `worktree.md` §7 に「ワークツリー間の反映のタイミング」の補足を入れる（設計確認メモの (1)(2) と例外の参照）。

## Danger Ops（有/無）
- 有
- 有の場合: ワークツリーの撤去（`wt-remove.sh`）は、未コミットのイシューファイルを失う恐れがある。primary へのコピーと `cmp` の一致を確かめてから行い、撤去の前にユーザーの承認を得る。Docker データがあると判定された場合は、`wt-remove.sh` の停止メッセージにあるバックアップ手順と danger-ops.md の承認を経て `DANGER_OK=1` で行う。ロールバック: 撤去後でもブランチは消えない（`wt-remove.sh` はブランチを残す）ので、`git worktree add` で作り直せる。未コミットのファイルは primary 側のコピーから戻す。
