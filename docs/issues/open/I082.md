# I082: 計画・テストが依存する外部/ハーネス挙動の検証を制度化（計画時スパイク＋挙動テストの実施環境分類）

## 関連資料
- GitHub Issue: #162
- 起点: I079 振り返り（retro）の予防処置 P1・P3
- 関連: I079 で「broad allow＋deny 例外」の前提（deny が allow を上書きする）が未検証のまま実装まで進み、テスト工程で初めて不成立が判明（手戻り大）。また権限/フック挙動の統合テストがセッション内から観測できず（モード・フックのロードに依存）混乱した。
- 関連スキル/ルール: docs/runbooks/plan-writing-rules.md、.claude/review-agents/plan-reviewer.md、test 関連ルール

## 設計確認メモ（/grill-me）
- Q: スパイク実証の「計画確定前」原則と、稼働中セッションでは観測不能なクラス（ハーネス権限モード/フックのロード）の扱いをどうするか → A: **スパイク可否で二分岐する**。(1) **in-session 実証可**（CLI フラグ挙動・FW 戻り値・設定パース等）は**計画確定前にスパイク必須**とし、結果（成立/不成立）を計画書『調査結果』に記録する（不成立なら設計をやり直してから承認へ）。(2) **in-session 実証不能**（ハーネス権限モード/フックのロード依存）は「未実証」と『調査結果』に明記し、**指定実施環境（プレーン default 新規セッション／Human 目視）での実証を実装ステップ1に前倒し**する。ステップ1の結果は後続を止めるゲートとし、不成立なら計画やり直しとする。I079 の実失敗（deny/allow 優先順位）はこの「実証不能クラス」に該当する。
- Q: 新スパイク規定と既存「未知リスク先行原則」が重複する。どう書くか → A: **既存原則を参照・拡張する形**にし二重定義を避ける（既存＝不確かなものを先頭ステップに／新規＝うち in-session 可は承認前に実証・不能はステップ1の結果をゲート化）。
- Q: plan-reviewer に追加する「依存する外部挙動の前提が未実証」gate の重大度は Blocker か Warning か → A: **条件付き Blocker**。(a) 計画が自ら「未知リスク」と認識する外部前提が**未実証 かつ 実証手段（実施環境・ステップ）の明記もない**＝**Blocker**（差し戻し）。(b) in-session 実証可だったのに未実証＝**Warning**。(c) 実証不能クラスで指定実施環境＋ステップ1前倒しが明記済み＝**問題なし**。
- Q: 追記先ファイル/節と、手動テスト文書の実施環境表現の確定 → A: スパイク規定は `docs/runbooks/plan-writing-rules.md` の「計画書作成前の事前調査（必須）」セクションに**新規サブセクション**として追加。実施環境分類は同ファイルの「手動テスト文書のフォーマットルール」節に追加し、**手動テスト表に「実施環境」欄を追加**して、ハーネス挙動 TC には `プレーン default 新規セッション` を明記必須とする（既存「実施者」列の Claude/Human だけでは実証不能クラスを表現できず、稼働中セッションでの誤検証を構造的に防ぐため）。
- Q: 「実施環境」欄の適用範囲と既存ドキュメント（open 11 件・closed 64 件）の遡及改修の要否 → A: **条件付き列とする（案A）**。手動テスト文書に **権限モード / フック（hook）/ 権限プロンプト / settings 権限** の挙動を確認する TC を含む場合のみ「実施環境」列を追加必須とし、該当行に `プレーン default 新規セッション` または `Human 目視` を明記する。通常の機能テストのみの文書は列を省略可。**既存文書の遡及改修は不要**（closed 文書の改修は歴史的記録の正確性を損なうため）。影響範囲は本イシュー対象の `plan-writing-rules.md` フォーマット規定のみで、`docs/tests/` 配下の既存文書は対象外。発火条件の取りこぼしは確定済みの plan-reviewer 条件付き Blocker gate が計画段階で捕捉するため prose ルール単独に依存しない。

## 背景/目的

### 現状の問題（証拠・再現手順）
1. **計画が依存する外部挙動の前提が未検証のまま実装に進む**: I079 では計画書自身が「deny が broad allow に優先するか」を"最大の未知リスク"と明記していたのに、実証はテスト工程まで先送りされ、結果としてその前提が**不成立**（Edit/Write では重複 allow が優先・deny は上書きしない）と判明。設計の作り直し（→ フック方式）が発生した。
2. **ハーネス挙動の統合テストが in-session で観測不能**: 権限プロンプト/フックの発火は、セッションの権限モード（default/acceptEdits/auto）とフックのロードタイミング（セッション開始時）に依存する。稼働中セッションでエージェントが編集を試しても、プロンプトの発生源（フックの ask／通常権限／モード）を区別できず、合否を妥当に判定できない。

### 根本原因
計画・テストが依存する「不確実な外部（ハーネス/フレームワーク/ツール）挙動」を、**適切な工程・環境で実証/検証する仕組みが無い**。具体的には (P1) 計画確定前に未知挙動を実証するステップが無い、(P3) ハーネス挙動テストの実施環境（プレーン default の新規セッション/Human 目視）が分類・明記されていない。

### 解決方針
plan-writing-rules・plan-reviewer・test 関連ルールに、外部/ハーネス挙動への依存を一次市民として扱う規定を追加する。計画時は**スパイク可否で二分岐**して前提を実証する（in-session 実証可は計画確定前に実証、in-session 実証不能はステップ1へ前倒し＝設計確認メモ参照）。テスト時は実施環境を正しく分類し、手動テスト表に「実施環境」欄を設けてハーネス挙動 TC の実施環境を明記する。

## スコープ
### 含む
- 計画時スパイク（外部挙動前提の実証）の規定と plan-reviewer gate
- ハーネス挙動テストの実施環境分類の規定（手動テスト文書フォーマットへの反映含む）
### 含まない
- 個別イシュー（I079/I080 等）の再実装
- フックや settings の機能変更（本イシューはルール/レビュー観点の明文化のみ）
