## 設計確認メモ（/grill-me）
- Q: 採番方式は横断スキャン / 即コミット強制 / 併用のどれか → A: **横断スキャン単独**で確定（即コミット強制は不採用）。根拠: 現行 `GIT_MAX=git log --all` は共有 `.git` の全 ref を走査するためコミット済みイシューは既に全 worktree から可視。不可視なのは untracked のみ。各 worktree の docs/issues FS 最大を横断集計すればこの穴だけを塞げ、読み取りのみ（I095 は横断読み取りを許可）でワークフロー変更不要。任意の worktree が同一の大域 max を算出でき、採番権威が単一化する（§8 の「primary で採番」人手規律を撤廃＝根治）。即コミット強制は bootstrap がブランチ未作成段階（ブランチ作成は /plan-issue）で任意ブランチにコミットする副作用があり、同じ効果に対し影響範囲が広いため不採用。
  - 注: 下記で挙げる scripts/claude/wt-new.sh・scripts/claude/tests/test_wt_port_offset.sh は体裁/一貫性の参照例であり変更対象外。
- Q: 採番ロジックを一元化するか → A: **一元化する**。`scripts/claude/next-issue-num.sh` を新規作成し、`docs/runbooks/issue-flow.md`（**3 箇所**: 「採番ルール」§ / 「1. イシュー番号の採番」/ 「ステップ1」）と `.claude/skills/issue-bootstrap/SKILL.md`（1 箇所）の重複 bash（計 4 箇所）をこのスクリプト呼び出しに置換（採番アルゴリズムの単一権威化・AC の自動検証と整合・scripts/claude/wt-new.sh 等と一貫）。
- Q: スクリプトの出力契約（consumer との IF）は → A: 標準出力に**3 桁ゼロ詰めの番号のみ**を出力（例: `098`）。consumer は `ISSUE_NUM=$(bash scripts/claude/next-issue-num.sh)` で受けて既存どおり cp template → docs/issues/open/I{番号}.md に使う（`I` 接頭辞やパスは付けない＝既存 `ISSUE_NUM` 変数の意味を踏襲）。重複検出 assert に掛かった場合は stdout に番号を出さず stderr にエラーを出して**非 0 終了**（consumer 側で採番が止まる）。
- Q: 横断採番の入力集合は → A: `NEXT = max( 各 worktree（git worktree list 列挙）の docs/issues FS 最大〔untracked 含む〕, git log --all -- docs/issues の履歴最大〔削除済み含む〕 ) + 1`。8 進誤解釈防止 `$((10#...))`・I###.md/###.md 両対応は踏襲。
- Q: 別マシン/別クローンの worktree も対象か → A: **対象外**（本ホスト上の git worktree list に出る worktree のみ）。スコープ「含まない」の延長として本文明記。
- Q: 重複検出 gate の形は → A: `scripts/claude/next-issue-num.sh` に、確定 I### が**いずれの worktree にもファイルとして存在しないこと**を assert するステップを内蔵し、存在すれば非 0 で停止（fail-loud）。横断集計で max は既に大域だが再実行・取りこぼしの保険。同時 bootstrap の TOCTOU（2 worktree がほぼ同時に採番）は**単一逐次オペレータ前提でスコープ外**（ロック機構は入れない）と本文明記。
- Q: 自動検証の範囲は → A: `scripts/claude/tests/test_next_issue_num.sh` を新規作成。第2 worktree に untracked の高番号イシューを置いた状態で max+1 を返す（本レビュー再現ケース）ことを検証。既存 scripts/claude/tests/test_wt_port_offset.sh 等の体裁に合わせ、I094 の decoy 反証（部分一致・非近接で誤検出しないこと）を含める。

## 背景/目的

### 現状の問題（証拠・再現手順）
`/issue-bootstrap` 直後のイシューファイルは **untracked（未コミット）** で、それを作った worktree からしか見えない。別 worktree で起票すると互いの untracked イシューが不可視なため**採番が食い違う**恐れがある（`worktree.md §8`）。

- 実証（本レビュー中に発生）: `wt-harness` で `issue-flow.md` の採番コマンドを実行すると `FS_MAX=094`（wt-harness の untracked I093/I094）・`GIT_MAX=092`（コミット済み最大）。一方 primary checkout `study-app-multitenant` には **untracked の I085〜I091 が存在**し、`wt-harness` の FS/git いずれからも見えなかった。今回はたまたま primary 側最大(091) < wt-harness 側最大(094) で衝突しなかったが、順序が逆なら**同一番号を二重採番**していた。
- 現状の回避（§8）: 「採番は権威となる作業ツリー（未コミットのイシューが見える primary）で行うか、起票後すみやかに develop へ取り込む」という**人手規律**。issue-flow.md の採番コマンドも**単一 worktree の FS + git 履歴**しか見ておらず、他 worktree の untracked を考慮しない。

### 根本原因
採番の入力（FS 最大 + git 履歴最大）が**現 worktree に閉じており**、他 worktree の untracked イシューを含まない。untracked ゆえ git 共有もされず、採番の権威が「primary で採番する」という規律に依存している。

### 解決方針（横断スキャン単独で確定・grill-me）
**横断スキャン方式に確定**（即コミット強制は不採用）。理由と入力集合は「## 設計確認メモ（/grill-me）」参照。

1. **do（採番ロジックの横断化＋一元化）**: 採番ロジックを新規スクリプト `scripts/claude/next-issue-num.sh` に一元化し、`git worktree list` で全 worktree を列挙して各 worktree の `docs/issues` FS 最大（untracked 含む）を集計、`git log --all` の履歴最大と合わせて `max(...) + 1` を 3 桁ゼロ詰めで stdout に返す。`docs/runbooks/issue-flow.md`（3 箇所）と `.claude/skills/issue-bootstrap/SKILL.md`（1 箇所）の重複 bash（計 4 箇所）をこのスクリプト呼び出しに置換する。読み取りのみ（I095 の読み取り許可方針と整合）。
2. **do（§8 の権威単一化）**: `docs/runbooks/worktree.md` §8 の「primary で採番 / 速やかに取り込む」人手規律を撤廃し、「任意の worktree で `scripts/claude/next-issue-num.sh` を実行すれば全 worktree 横断の一意番号が得られる（採番権威が単一化）」に置換する。
- **gate（重複検出の内蔵）**: `scripts/claude/next-issue-num.sh` に、確定 I### がいずれの worktree にもファイル存在しないことを assert するステップを内蔵し、存在すれば非 0 で停止（fail-loud）。同時 bootstrap の TOCTOU は単一逐次オペレータ前提でスコープ外（ロックは入れない）。

**不採用**: 即コミット強制方式（bootstrap がブランチ未作成段階で任意ブランチにコミットする副作用があり、同じ可視化効果に対し影響範囲が広い）。

## スコープ
### 含む
- 採番の入力に**全 worktree 横断**（untracked 含む）を含める仕組みを `scripts/claude/next-issue-num.sh` として実装（横断スキャン方式で確定）。
- 採番ロジックの一元化（issue-flow.md 3 箇所・issue-bootstrap/SKILL.md 1 箇所の計 4 箇所の重複 bash をスクリプト呼び出しに置換）。
- issue-flow.md / worktree.md §8 の更新（§8 は権威単一化に置換）。
- 横断採番の自動検証（再現ケース＋I094 decoy 反証）。
- 確定番号の全 worktree 存在 assert（fail-loud gate）のスクリプト内蔵。

### 含まない
- **即コミット強制方式**（不採用。理由は解決方針参照）。
- **別マシン/別クローンの worktree の考慮**（本ホストの `git worktree list` に出る worktree のみ対象）。
- **同時 bootstrap の TOCTOU 対策（ロック機構）**（単一逐次オペレータ前提。存在 assert で fail-loud に留める）。
- GitHub Issue 番号との統合採番（GitHub 側は自動採番で別系統・現行どおりローカル番号をタイトルに含めて紐付け）。
- イシュー以外（plan/test/review）のファイル採番方式の変更。
- 3 worktree 以上への一般化を超えた大規模なイシュー管理基盤の刷新。
