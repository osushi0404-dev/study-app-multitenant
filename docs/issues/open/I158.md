# I158: クイズ開始時にセッションが二重作成される（開始リクエストの重複送信）を是正

## 関連資料
- GitHub Issue: #275
- 発見元: I151 手動テスト No.7（`docs/tests/open/I151_manual_test.md` の「No.7 で見つかった既存不具合」#1）

## 設計確認メモ（/grill-me）
（ユーザー指示「ベストプラクティス・モダンな Web アプリとして理想的なやり方で進めて」により、以下は Claude が決定・2026-10-24）
- Q: ほぼ同時に 2 回の開始リクエストが来たときの扱い（既存を返す／後勝ち）は？ → A: **Idempotency-Key 方式**。フロントは開始操作ごとに UUID v4 を生成して `Idempotency-Key` ヘッダで送る（`useRef` に保持し、StrictMode の再マウント・再送でも同じキー）。サーバーは `QuizSession.client_request_id`（`UUIDField(null=True, blank=True)`）に保存し、`UniqueConstraint(fields=['user', 'client_request_id'], name='uniq_quizsession_user_request_id')` を張る。同じキーの再送は既存セッションを **200** で返す（新規作成は 201）。キーが異なる開始（別タブ・意図的なやり直し）は従来どおり「既存の有効セッションを終了 → 新規作成」（後勝ち）。キー無しのリクエストも後勝ちで受け付ける（後方互換）。時間窓（N 秒以内なら同一扱い）のような推測ロジックは使わない。
- Q: 同時実行の直列化と最後の守りは？ → A: `create` を `transaction.atomic` で囲み、`User.objects.select_for_update().get(pk=request.user.pk)` で同一ユーザーの開始処理を直列化する。DB 制約 `UniqueConstraint(fields=['user'], condition=Q(is_active=True), name='uniq_active_quizsession_per_user')` を最後の守りとし、それでも `IntegrityError` になった場合は 500 ではなく **409 Conflict**（`{'error': ...}`）を返す。フロントは 409 を他の失敗と同じくトースト表示＋ダッシュボードへ戻す。
- Q: 使われていない変更・削除 API（PUT/PATCH/DELETE `/api/quiz/<id>/`）で `is_active` を書き換えられる道を閉じるか？ → A: 本イシューで閉じる。`QuizSessionViewSet.http_method_names = ['get', 'post', 'head', 'options']`、`QuizSessionSerializer` の `read_only_fields` に `is_active`・`started_at` を追加。フロント・テストに利用箇所が無いことは確認済み（`frontend/src` は `POST /api/quiz/` のみ・`backend/problems/tests/` は GET のみ）。
- Q: 科目未指定時の `total_problems` が全組織で数えられる件は？ → A: クイズの組織境界を扱う I166（クイズ開始・出題の組織チェック）の範囲として I166 へ引き継ぐ。I158 では扱わない。
- Q: I166 と同じ `create` を変更するが、順番は？ → A: 順不同で並行してよい（セキュリティ上は I166 を先にマージするのが望ましい）。後からマージする側が develop を取り込み、`create` の変更を統合する。
- Q: 既存の重複データの規模は？ → A: dev DB（2026-10-24・読み取りのみで確認）で有効セッション 10 件、うち有効が 2 件以上のユーザー 5 人・解消対象（最新以外）5 件。
- Q（2 回目の /grill-me で追加・Claude が決定）: 別オリジン構成で `Idempotency-Key` ヘッダが CORS で弾かれないか？ → A: `backend/core/settings.py` の `CORS_ALLOW_HEADERS` は明示列挙のため、`'idempotency-key'` を追加する（`REACT_APP_API_BASE_URL` を設定した別オリジン構成で preflight が通るようにする）。
- Q（同上）: UUID の生成手段は？ → A: ブラウザ標準の `crypto.randomUUID()` を使い、依存パッケージは追加しない。CRA（react-scripts 5.0.1）の Jest 環境（jsdom）には `crypto.randomUUID` が無いため、`frontend/src/setupTests.ts` で Node の `crypto.webcrypto` を未定義時のみ割り当てる（テスト環境の不足を補うだけで、本番コードは差し替えない）。
- Q（同上）: キーの不正・再利用時の扱いは？ → A: UUID として解釈できない `Idempotency-Key` は **400**。同じキーで `subject` が異なる再送は **422**（キーの使い回し誤り）。同じキーのセッションがすでに終了済みでも、そのセッションをそのまま 200 で返す（新規作成しない）。
- Q（同上）: 同時実行テストの方法は？ → A: `pytest.mark.django_db(transaction=True)` ＋ `threading.Barrier` で 2 スレッドから同時に `create` を呼び、有効セッションが 1 件であることを確認する（CI は PostgreSQL 15 のため行ロック・部分ユニーク制約をそのまま検証できる）。キーあり（同一キー→1 件作成）とキーなし（後勝ち→有効 1 件）の両方を検証する。

## 背景/目的

**背景**: I151（Django 5.2 更新）の手動テスト No.7 で `i102_user` がクイズを 1 回開始したところ、QuizSession が同時刻（差 0.6ms）に 2 件（id=169 / 170）作成され、両方とも `is_active=True` のまま残った。dev DB を調べると全 120 セッション中 60 組が 1 秒未満差の重複で、最古は 2025-08-18。I151 起因ではなく以前から存在する。
**目的**: クイズを 1 回開始したら QuizSession が必ず 1 件だけ作られ、1 ユーザーにつき有効（`is_active=True`）なセッションが常に高々 1 件である状態にする。フロントの重複送信を止めるだけでなく、サーバー側でも同時リクエストに対して不変条件が守られること。

### 現状の問題（証拠・再現手順）
- 再現: dev 環境（`npm start`）でログイン → ダッシュボードの「クイズを始める」→ DB を確認すると同時刻の QuizSession が 2 件できている。
- 実例（2026-10-07・dev DB）: `i102_user` の id=169（回答 1 件・`is_active=True`）と id=170（回答 0 件・`is_active=True`）。`/api/dashboard/overview/` の `recent_quizzes` に回答 0 件の空セッション 170 が並んで表示される。
- 集計: dev DB の QuizSession 120 件中、同一ユーザー・1 秒未満差の組が 60 組（ほぼ全開始が二重）。

### 根本原因
2 つの原因が重なっている。
1. **フロント（重複送信の発生源）**: `frontend/src/index.tsx:11` で `<React.StrictMode>` が有効。開発ビルドでは effect が mount→unmount→mount で 2 回実行されるため、`frontend/src/pages/QuizSession.tsx:203-211` の `useEffect` が `createNewSession()` を 2 回呼び、`POST /api/quiz/` が 2 回同時に送られる。effect に重複防止（中断フラグ・AbortController・ref ガード等）が無い。
2. **サーバー（不変条件の欠如）**: `backend/problems/views.py:820-845` の `create` は「既存の有効セッションを `update(is_active=False)` → 新規作成」をトランザクション・ロックなしで行う。2 リクエストが同時に来ると、両方の `update` が相手の新規行より先に走るため、**有効セッションが 2 件残る**。DB 側にも「1 ユーザー 1 有効セッション」を保証する制約が無い。

本番ビルドでは StrictMode の二重実行は起きないが、ダブルクリック・ネットワーク再送・複数タブでも同じ競合が起き得るため、2 はフロント修正とは独立に必要。

### 解決方針
- **サーバー（根治）**: 「1 ユーザーにつき有効セッション高々 1 件」を DB 制約で保証する（`QuizSession` に `user` + `is_active=True` の条件付き UniqueConstraint）。`create` は `transaction.atomic` ＋ ユーザー行の `select_for_update` で直列化し、既存有効セッションの終了と新規作成を行う（キーが異なる開始は後勝ち）。開始の重複は `Idempotency-Key` ヘッダ（`client_request_id` に保存・`user` との UniqueConstraint）で判定し、同じキーなら既存セッションを 200 で返す。制約違反は 409。詳細は設計確認メモ。
- **API の締め**: 未使用の PUT/PATCH/DELETE を閉じ、`is_active` を読み取り専用にする。
- **フロント**: `QuizSession.tsx` の開始処理を `useRef` ガードで StrictMode の再実行でも 1 回しか送信しない形にし、`useRef` に保持した UUID を `Idempotency-Key` として送る。
- 既存の重複データ（有効セッションが 2 件以上あるユーザー）は、制約追加のマイグレーション前に解消が必要（最新以外を `is_active=False` にするデータマイグレーション）。

## スコープ
### 含む
- クイズ開始時の QuizSession 二重作成の防止（フロント・サーバー両方）
- 「1 ユーザー 1 有効セッション」の DB 制約化と既存重複データの解消
- 上記の自動テスト
### 含まない
- クイズ回答がダッシュボードの統計（解答問題数・正答率）に反映されない問題（ダッシュボード改善時に対応する方針・`docs/proposals/dashboard_improvement_proposal.md`。I151 手動テスト記録の #2）
- 有効でない過去の重複セッション（`is_active=False` の空セッション）の削除（履歴表示への影響を見て別途判断）
- `create` で科目未指定時の `total_problems` が組織で絞られていない件（`Problem.objects.filter(is_deleted=False)` を全組織で数えている・views.py:833）。クイズの組織境界を扱う I166 へ引き継ぐ

## 関連する品質基準
- 学習データの正確さ: 空のセッションが学習履歴（recent_quizzes）に混ざると、学習者が自分の取り組みを正しく振り返れない。1 開始 = 1 記録を保証する。

## 受け入れ条件（Acceptance Criteria）
- [ ] dev 環境（StrictMode 有効）でクイズを 1 回開始したとき、`POST /api/quiz/` が 1 回だけ送られ、QuizSession が 1 件だけ作成される
- [ ] 同一ユーザーが `POST /api/quiz/` を同時に 2 回送っても、有効な QuizSession は 1 件だけになる（バックエンドテストで並行実行を再現して検証）
- [ ] 同じ `Idempotency-Key` で `POST /api/quiz/` を再送すると、新規作成されず既存セッションが 200 で返る（異なるキーなら既存を終了して新規作成・201。UUID でないキーは 400、同じキーで `subject` が異なる再送は 422）
- [ ] DB 制約により、1 ユーザーに有効セッションが 2 件以上存在できない（制約違反時は 500 ではなく 409）
- [ ] `/api/quiz/<id>/` への PUT/PATCH/DELETE は 405 になり、`is_active` をクライアントから書き換えられない
- [ ] 既存データの重複有効セッションがマイグレーションで解消され、マイグレーションがまっさらな DB と既存 dev DB の両方で通る
- [ ] 既存のクイズ機能（出題・回答・中断・再開・完了）が退行しない（既存テスト・E2E 全件 pass）

## 影響範囲（想定）
- Backend: `problems` の QuizSession モデル・作成 API・シリアライザ（`backend/problems/models.py`・`backend/problems/views.py`・`backend/problems/serializers.py`）
- Frontend: クイズ画面の開始処理（`frontend/src/pages/QuizSession.tsx`）・テスト環境設定（`frontend/src/setupTests.ts`）
- DB: QuizSession に `client_request_id` 列と条件付きユニーク制約 2 つを追加・既存の重複有効セッションを更新（`is_active=False` 化）
- Config/Infra: CORS の許可ヘッダに `idempotency-key` を追加（`backend/core/settings.py`）

## 制約・引き継ぎ情報
- 開始画面は `/quiz?subject=<id>`（id なし）で新規作成、`/quiz/<id>` で既存セッションを読み込む。再開導線を壊さないこと。
- 現状、二重作成されたうち実際に回答が入るのは片方だけ（2026-10-07 の例では 169）。どちらがフロントの state に残るかは応答順に依存する。
- dev DB の確認は `docker compose exec -T backend python manage.py shell -c` で読み取りのみ実施済み（データは未変更）。

## Danger Ops（有/無）
- 有
- 有の場合: 既存の重複有効セッションを `is_active=False` に一括更新するデータマイグレーション（大量更新に該当）。削除はせず、更新対象は「同一ユーザーで有効セッションが 2 件以上ある場合の最新以外」に限定する。適用前に対象件数を確認して承認を得る（2026-10-24 時点の dev DB では対象 5 件）。ロールバックは制約削除のマイグレーションで戻せる（`is_active` の更新は終了扱いになるだけで、回答データは失われない）。
