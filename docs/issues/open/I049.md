# I049: Playwright E2Eテスト基盤を導入しクリティカルパスを保護する

## 関連資料
- GitHub Issue: #102

## 設計確認メモ（/grill-me）
- Q: 「テナント切り替え」とは何を指すか → A: 別OrganizationユーザーでログインしてデータAが見えないことをE2Eで確認（テナント間データ分離の検証）
- Q: CIへの組み込み方針 → A: CIに組み込む。ただし独立ジョブとして追加し、既存の高速ジョブはブロックしない
- Q: テストデータ戦略 → A: 以下の構成を採用する
  - **5-1. 固定マスタデータ**: migration または小さな fixture（変更頻度が低いもののみ）
  - **5-2. E2Eシナリオデータ**: `manage.py seed_e2e --scenario <name>` でシナリオ単位に投入（例: `--scenario login`, `--scenario problem_crud`）
  - **5-3. E2E実行前処理**: DB初期化 → migration適用 → scenario seed → Playwright実行（Playwright globalSetup で自動化）
  - **認証状態再利用**: Playwright の `storageState` でログインUIを毎テスト叩かない
  - **E2Eの範囲規律**: 細かい分岐は API/service/component テストへ分離し、E2Eは主要画面の本線フローのみ

## 背景/目的
- pytest（Backend）・Jest（Frontend）はロジック層をカバーするが、ブラウザ操作を通じたユーザー体験の検証が欠落している
- フロントとバックエンドの繋ぎ目・認証フロー・画面表示など「ユニットテストでは検出できないバグ」を保護するためE2Eテスト基盤を整備する
- テストピラミッドの最上層として、クリティカルパスのみを薄く保護する方針とする

## スコープ
### 含む
- Playwright のインストール・設定ファイル整備
- Docker Compose への組み込み（`docker compose run e2e` で実行可能な状態）
- クリティカルパスのE2Eテスト実装（ログイン／ログアウト・テナント間データ分離確認・学習コンテンツ閲覧〜回答の1往復）
- `/test` スキルへのE2Eステップ追加

### 含まない
- 全機能のE2Eカバレッジ
- ビジュアルリグレッションテスト
- パフォーマンステスト

## 受け入れ条件（Acceptance Criteria）
- [ ] `docker compose run e2e` でPlaywrightが起動しテストが実行される
- [ ] ログイン／ログアウトのE2Eテストが通る
- [ ] テナント間データ分離のE2Eテストが通る（Organization Aのデータが Organization Bユーザーから見えないことを確認）
- [ ] 学習コンテンツ閲覧〜回答のE2Eテストが通る
- [ ] `/test` スキルにE2Eステップが追加されている
- [ ] CI（GitHub Actions）でE2Eが自動実行される（またはローカル実行手順が明記される）

## 影響範囲（想定）
- Backend: `manage.py seed_e2e` カスタム管理コマンド追加
- Frontend: Playwright 設定ファイル・テストファイル追加
- DB: テスト用DB分離（`.env.e2e`）、固定マスタは fixture、シナリオデータは seed コマンド
- Config/Infra: docker-compose.yml に e2e サービス追加、.github/workflows に E2E 独立ジョブ追加
