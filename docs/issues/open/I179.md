## 設計確認メモ（/grill-me）
- 事前調査（コード・公式から自己解決）:
  - 内蔵ワークツリー機能（`claude --worktree`・サブエージェント `isolation: worktree`・`EnterWorktree` ツール）はハーネス内で未使用（`.claude/`・`scripts/claude/`・`docs/runbooks/` を grep して該当なし）。ただし Claude のツール一覧に `EnterWorktree` があり、Claude が依頼に応じて使い得る。
  - 内蔵機能の基点: `worktree.baseRef` 既定 `"fresh"`＝リモートの既定ブランチ。本リポジトリの既定ブランチは `develop`（`gh repo view --json defaultBranchRef` で確認）なので空ツリー（main 基点）の問題は起きない。抜けるのは `.env` コピーとポート割当。
  - WorktreeCreate フック: 入力は共通項目（session_id・transcript_path・cwd・hook_event_name）＋ `name`。出力は stdout 最後の非空行にワークツリーのパス（相対はフックのディレクトリ基準）。非ゼロ終了で作成失敗。matcher 非対応。発火経路として明記されているのは `--worktree`・`isolation: "worktree"`・バックグラウンドセッション。`EnterWorktree` で発火するかは公式未記載。WorktreeRemove の入力は共通項目＋ `worktree_path`。
  - サブエージェント用ワークツリーの既定配置は `.claude/worktrees/<name>/`。
  - (C) 共有物の注意は追記のみで設計判断なし（質問省略）。
  - （2 回目の grill-me・2026-10-19 で自己決定。価値判断を含まない技術詳細のため質問省略）
    - F の作成場所・ブランチ: フック経由でも公式既定どおり `.claude/worktrees/<name>/`・ブランチ `worktree-<name>`・基点 `origin/develop`。フック入力は `name` のみで番号・概要を持たないため、wt-new.sh の `<track> <番号> <概要>` 形式とは別の入口（中核処理の共有）とする。
    - F の失敗時の挙動: `.env` source 欠落・ポート衝突はフックを非ゼロ終了させて作成自体を失敗させる（wt-new.sh と同じ fail-closed。安全策の抜けたワークツリーを作らない）。
    - F の撤去: WorktreeRemove フックは wt-remove.sh と同じ撤去前チェック（未コミット・未 push で中止）と E の判定を使う。Docker のデータがある場合は `DANGER_OK` を得られないため撤去を拒否してワークツリーを残し、理由を stderr に出す（自動クリーンアップでもデータを消さない）。
    - 本イシューは lint/audit 等のツール出力で完了基準が決まるイシューではないため、ツール実走による AC 確定は対象外。
- Q: 同一トラックの 2 つ目以降のワークツリー名は？ → A: `wt-<track>-<連番>`（例: `wt-harness-2`・`wt-harness-3`）。既存の `wt-harness` は改名しない。トラックは GitHub ラベル（`track:harness` / `track:app`）で区別し、ワークツリーは作業場所として複数可。
- Q: primary（`study-app-multitenant`）の「アプリ開発専用」をどうするか？ → A: 専用指定を廃止し、どのトラックでも使ってよい。採番は `next-issue-num.sh` がどのワークツリーからでも大域一意を返すため、primary を採番権威として特別扱いする理由はない（primary は `git worktree list` 先頭＝wt-new/wt-remove の基準位置としての役割のみ残る）。
- Q: 同一ワークツリーで次イシューに移る手順は？ → A: 切替用スクリプトは作らない。新ブランチは `/plan-issue` が develop 最新から作成する。`worktree.md` には「未コミット変更を片付けてから `/plan-issue` を実行する」とだけ書く。
- Q: （grill 中に判明）`/plan-issue` が `git checkout develop` を経由するため、別ワークツリーが develop をチェックアウト中だと失敗する。どうするか？ → A: 本イシューで直す。`git fetch origin` ＋ `git checkout -b feature/I<番号>-<概要> origin/develop` の形にし、develop をチェックアウトしない。同じ手順を載せている `docs/runbooks/issue-flow.md` ステップ5 も同時に更新する。
- Q: §10 の手書きトラック構成表をどうするか？ → A: 表を削除し、「現在の状態は `git worktree list` で確認する」の案内と、トラック⇔ラベル対応（`track:harness`／`track:app`）だけを残す。
- Q: wt-remove.sh の `DANGER_OK=1` 必須をどうするか？ → A: 当該ワークツリーの Compose プロジェクト（既定＝ディレクトリ名）に属するコンテナ・named volume が 1 つも無い場合は `DANGER_OK` なしで `git worktree remove` まで進める（`down -v` は実行しない）。1 つでもある場合は従来どおり `DANGER_OK=1` 必須。撤去後のブランチは削除せず残す。
- Q: 内蔵機能への対応（F）を本イシューで行うか？ → A: 行う。WorktreeCreate / WorktreeRemove フックから wt-new.sh / wt-remove.sh の中核（`.env` コピーと存在検証・ポート割当と衝突検査・撤去前チェック）を呼び、どの経路で作っても同じ安全策をかける。フック発火が未確認の `EnterWorktree` 経路は、作成後に `.env`・ポートの有無を検査し、不足していれば同じ処理で補う仕組みを足す（方式は実機で発火有無を確認して計画段階で確定）。実機確認で規模が大きいと判明した場合のみ計画段階で別イシューに切り出す。

## 背景/目的

**背景**: 2026-10-18、ハーネス改善トラック用に 2 つ目のワークツリーを作ろうとした際、`docs/runbooks/worktree.md` を確認したところ「1 トラック＝1 ワークツリー」前提で同一トラックの 2 つ目が定義されていなかった。これを機にルール全体を Anthropic 公式のワークツリー機能・ベストプラクティスと比較評価し、複数の不整合・欠落が見つかった。grill-me で対応範囲を確定し、本イシュー内で実施する。
**目的**: ワークツリー運用ルールと補助スクリプトが (1) 現在の実際の使い方（同一トラック複数ワークツリー・ワークツリーの複数イシュー使い回し）に合い、(2) Claude Code 内蔵のワークツリー機能を使った場合も同じ安全策がかかる状態にする。

### 現状の問題（証拠・再現手順）
評価で判明した問題（A〜G。G は grill-me 中に判明）:

- **(A) 同一トラック複数ワークツリーが未定義**: `worktree.md` §2「トラック単位で作業ツリー」・§10「トラック = 1 作業ツリー」。ハーネス改善用の 2 つ目を作る運用が書かれていない。また primary（アプリ開発用と定義）で harness の I174 を「例外」として実施中であり、定義と実態がずれている。
- **(B) ワークツリーを複数イシューで使い回す切替手順が無い**: 実際は `wt-harness` が I146 → I178 と使い回されている（`git worktree list` で確認）が、次イシューへの移り方が未記載。
- **(C) 全ワークツリー共有物の注意が不足**: §7 に git stash スタック・git config（hooks 含む）が全ワークツリー共有である点が無い。素の `git stash pop` で他セッションの退避分を取り出す危険がある。
- **(D) §10 のトラック構成が陳腐化**: 「2026-07 時点」のスナップショットのまま、実態（primary=I174・wt-harness=I178）と一致しない。手書きスナップショットは構造的に古くなる。
- **(E) wt-remove.sh の使い勝手**: Docker を使っていないワークツリーでも `DANGER_OK=1`（`docker compose down -v`）必須で撤去できない。撤去後のブランチの扱いも未記載。
- **(F) 内蔵機能で作ると安全策が抜ける**: `claude --worktree`／サブエージェントの `isolation: worktree`／`EnterWorktree` ツールは `.claude/worktrees/<name>/` に作成し、`wt-new.sh` の安全策（`backend/.env` コピーと存在検証・ポートオフセット自動割当・衝突検査）を通らない。
- **(G) `/plan-issue` のブランチ作成が複数ワークツリーで失敗し得る**: `.claude/skills/plan-issue/SKILL.md` ステップ（23〜25 行目）と `docs/runbooks/issue-flow.md` ステップ5（219〜221 行目）が `git checkout develop` → `git pull` → `git checkout -b` の順。git は同じブランチを複数ワークツリーで同時にチェックアウトできないため、別ワークツリーが develop をチェックアウト中だと `git checkout develop` が失敗する。

評価で確認した強み（維持対象）: セッション分離・`.env` コピー検証・ポート分離・Docker volume 分離・採番単一化・横断書込ガードは公式ガイダンス（ポート/DB 等の共有資源に言及なし）より手厚い。

### 根本原因
- A/B/D/G: ルール・手順が作成当時（2 トラック・各 1 ワークツリー・単一作業ツリーでのブランチ切替）の構成を前提に書かれ、その後の運用変化（同一トラック並行・使い回し）に追従していない。
- C/E: 作成時の検討範囲外（共有物の洗い出し・Docker 非使用ケース）。
- F: 自前スクリプトが作成経路の 1 つに過ぎず、Claude Code 側に後から入った内蔵作成経路を経由しない。

### 解決方針
設計確認メモの確定値に従い、A〜G をすべて本イシューで対応する（見送りなし）。
- A: トラック＝GitHub ラベル、ワークツリー＝作業場所として複数可。2 つ目以降は `wt-<track>-<連番>`。primary の「アプリ開発専用」「採番権威」の特別扱いを廃止。
- B: `worktree.md` に「未コミット変更を片付けてから `/plan-issue` を実行する」を追記（スクリプトは追加しない）。
- C: `worktree.md` §7 に stash・git config 共有の注意（素の `git stash` / `git stash pop` 禁止・`git stash push -u -m <タグ>` ＋ SHA 指定 `apply`）を追記。
- D: §10 の手書き構成表を削除し、`git worktree list` 案内とトラック⇔ラベル対応のみ残す。
- E: Compose プロジェクトのコンテナ・named volume が無ければ `DANGER_OK` 不要で撤去、あれば従来どおり必須。ブランチは残す。
- F: WorktreeCreate / WorktreeRemove フックから wt-new.sh / wt-remove.sh の中核を呼ぶ。`EnterWorktree` 経路は作成後検査＋不足分の補完で担保（方式は実機確認後に計画段階で確定）。規模が大きい場合のみ計画段階で切り出し。
- G: `git fetch origin` ＋ `git checkout -b feature/I<番号>-<概要> origin/develop` に変更し、develop をチェックアウトしない。

- ハーネス改善用 2 つ目のワークツリーの作成要望が本イシューの起点。A の実装完了（または計画承認）まで作成は保留中。

## Danger Ops（有/無）
- 有
- 何を: `wt-remove.sh` の `docker compose down -v`（Docker named volume 削除）を要求する条件を「常に」から「当該 Compose プロジェクトのコンテナ・named volume が存在する場合のみ」に変更する。
- なぜ: 消すデータが無いワークツリーの撤去にまで破壊的操作の許可を要求しており、許可の意味が薄れているため。
- どう承認: 計画書に明記し、ユーザーの明示承認を得る。データがある場合の `DANGER_OK=1` 必須は維持し、`docs/runbooks/danger-ops.md` と整合させる。判定に失敗した場合（docker 不在・コマンド失敗）は「データあり」扱いで `DANGER_OK=1` を要求する（fail-safe）。
- ロールバック: `wt-remove.sh` の判定分岐を戻せば従来挙動に復帰（データには影響しない）。
