## 背景/目的

**背景**: I452 で frontend を変えたとき、次の 2 つが起きた。
1. コミット時の ESLint のフック（`.pre-commit-config.yaml` の `eslint`・`entry: bash -c 'cd frontend && npm run lint'`）が、ワークツリーのホストに `eslint` が無く exit 127 で止まった。同じ `npm run lint` を frontend コンテナで流して 0 件を確かめ、そのコミットだけ `SKIP=eslint` にした
2. 会話のリセット（`/clear`）の 3 秒後に、Claude Code が Playwright MCP のサーバーを「前の作業場所で登録された古い接続」として止め、その後つなぎ直さなかった。実装の段階では画面確認ができず test-gate に回し、test-gate ではユーザーに `/mcp` で再接続してもらうまで止まった（接続の記録 `~/.cache/claude-cli-nodejs/<作業場所>/mcp-logs-playwright/*.jsonl` で原因を確かめた。Claude Code 本体の動き）

**目的**: frontend を変えるイシューで、コミットの検査と画面確認が、ワークツリーでも人の手を借りずに進むようにする。

### 現状の問題（証拠・再現手順）
- ESLint: `docs/runbooks/worktree.md:147` は「ホストで `npm install` を使わない（`node_modules` は frontend コンテナの匿名ボリューム）」と決めている。一方、ESLint のフックはホストで `npm run lint` を流す。ワークツリーの `frontend/node_modules` は空のフォルダ（コンテナの匿名ボリュームの取り付け先）なので、frontend の変更をコミットすると必ず `eslint: not found` で止まる。決まり同士が食い違っている
- MCP: `/clear` の直後に MCP のサーバーが止まると、その会話では `ToolSearch` が「接続中」と返し続け、Claude の側からはつなぎ直せない。`docs/runbooks/frontend-verify.md` には、MCP が使えないときの見分け方（接続の記録で「古い接続」として止められたかを見る）と、ユーザーに `/mcp` の再接続を頼む手順が無い

### 根本原因
- ESLint: pre-commit のフックを足したときの前提（ホストに node_modules がある）と、のちにワークツリーの手順書で決めた「依存はコンテナの中だけ」が食い違ったまま、どちらの点検にも引っかからなかった（frontend の変更をワークツリーでコミットする機会が少なかった）
- MCP: Claude Code 本体の動き（`/clear` で MCP のサーバーを古いものとして止める）。手順書は「MCP は会話の初めにつながっている」前提で、つながっていないときの手順が無い

### 解決方針
- ESLint: フックをラッパーのスクリプト（`scripts/claude/` に新規）経由にし、設計確認メモの順で流す（コンテナが起動していれば `exec`・起動していなければ使い捨てのコンテナで `run --rm --no-deps`・Docker が使えなければホストの eslint・それも無ければ止める）。CI の ESLint（`.github/workflows/ci.yml`）と、CI の pre-commit の `SKIP: eslint` は変えない
- MCP: `docs/runbooks/frontend-verify.md` に「MCP が使えないとき」の節を足す（接続の記録の見方・ユーザーに `/mcp` → playwright → 再接続を頼む文例）。implement の画面確認の前に、MCP が使えるかを先に確かめ、使えなければその時点で再接続を頼む（test-gate まで持ち越さない）。手順を足すか、決定論の確かめ（スクリプト）にするかは計画で決める
- Claude Code 本体への報告は、ユーザーの承認つきの `/feedback` で行う（このイシューの範囲外）
