# I142: accounts API の広域 except Exception 丸めを解消 — 想定外例外はログ+500 で顕在化させるエラー応答設計へ見直し

## 関連資料
- GitHub Issue: #253
- Draft PR: #256
- 起点: I131 retro 予防処置 P3（2026-07-19）。I131（#239）で `organization_id` 改名漏れの AttributeError が広域 `except Exception` により汎用 400/500 メッセージへ丸められ、プログラム欠陥が入力エラーと区別できず長期間露見しなかった
- 既存のエラー応答基盤: `backend/core/exceptions.py`（DRF `EXCEPTION_HANDLER` に `custom_exception_handler` 設定済み・`core/settings.py:150`）
- I131 イシュー本文「含まない」で「`except Exception` で 500/400 に丸める例外ハンドリング設計の見直し（別途検討）」と明記済みの件
- 関連イシュー: I140（#251）— slug なし登録の personal 組織不在時、自動作成フォールバックを廃止し既存 400 分岐に載せる（grill-me で確定・2026-07-19）。この「personal 不在」は環境異常（サーバー起因）のため、本イシューで 500 へ再分類する（下記 解決方針 1・AC 参照）

## 設計確認メモ（/grill-me）
- Q: 想定外例外を伝播させたときの 500 レスポンス形式は Django 標準（HTML）のままか、統一 JSON へ変換するか → A: **統一 JSON へ変換する**。`core/exceptions.py:custom_exception_handler` に「DRF が処理しない例外（`exception_handler` が None を返すケース＝プログラム欠陥）」の分岐を追加し、`logging.getLogger('django.request').exception(...)` でスタックトレースを記録したうえで `{"error": {"main_message": "サーバーエラー", "sub_message": "しばらく時間をおいて再度お試しください", "details": {}}}` の 500 を返す。理由: HTML 500 では FE の `extractApiErrorMessage`（`frontend/src/utils/apiError.ts`）が機能せず全 API 共通のエラー応答契約が崩れるため。可観測性は現状同等（本プロジェクトは Sentry 未導入・`django.request` ロガーが `error_file` ハンドラを持つ `core/enhanced_logging.py:327-331`）。`settings.DEBUG=True` のときのみ `sub_message` に `f"{type(exc).__name__}: {exc}"` を含める（本番では出さない）。スコープの「`core/exceptions.py` の応答フォーマット刷新は含まない」は「既存フォーマットは維持し非 APIException のハンドリング分岐のみ追加する」に整合更新する
- Q: personal 組織不在（環境異常）を 500 にする具体的な実装は → A: `backend/core/exceptions.py` に `class EnvironmentMisconfiguredError(APIException)`（`status_code=500`）を追加し、`UserRegistrationView._get_organization` が personal 不在時（`None` 返却をやめて）これを raise する。配置を core にするのは他アプリの同種「環境異常」へ横展開するため
- Q: その 500 のユーザー向け文言は → A: 既存ハンドラの汎用文言（`main_message='サーバーエラー'` / `sub_message='しばらく時間をおいて再度お試しください'`）をそのまま使う。原因（組織設定の不備）は応答に出さずログのみに残す
- Q: logout の想定内エラーの分割方針は → A: 例外任せをやめ明示分岐にする。`refresh` 欠落・`request.data` が dict でない場合は `isinstance` + `.get()` による事前判定で 400 を返し（`KeyError` 捕捉は不要になる）、`except` は `TokenError`（無効/失効トークン）のみとする。文言は現行どおり `{'error': 'ログアウトに失敗しました。'}` の 400 で統一（FE `auth.service.ts:34-44` は失敗時もローカルログアウトを継続するため文言分割の価値がない）。想定外例外は伝播させ 500
- Q: 想定外例外の注入テストの方式は → A: `unittest.mock.patch` で ORM 境界（`Organization.objects.filter`）に例外を注入し、`settings.DEBUG=False` 固定で「500 が返る」「スタックトレースがログに記録される」を検証する。本番コードに注入点を設けないため「テスト都合パッチで設計を歪めない」方針と両立する。**補足（計画時のスパイクで判明）**: `APIClient(raise_request_exception=False)` は不要（`custom_exception_handler` が Response を返すため例外がテストクライアントまで伝播しない）。また `django.request` は `propagate=False` のため `caplog` では捕捉できず、ログ検証は同ロガーへ検証用 `logging.Handler` を装着する方式にする
- Q（計画時追加・2026-07-20 実測）: 広域 except を外すと logout が毎回 500 になる潜在欠陥が判明（`rest_framework_simplejwt.token_blacklist` が INSTALLED_APPS 未登録のため `token.blacklist()` が AttributeError → 現状は広域 except に握りつぶされ**有効な refresh トークンでも常に 400**）。どう扱うか → A: **blacklist アプリを有効化して根治する**。`core/settings.py` の INSTALLED_APPS に `rest_framework_simplejwt.token_blacklist` を追加し `manage.py migrate`（追加テーブル 2 つ・既存データ影響なし）。logout はトークンを実際に失効させて 200 を返す状態にする
- Q（計画時追加・2026-07-20 実測）: `accounts/views.py:90` の `logger.info(f"Registration attempt with data: {mutable_data}")` が平文パスワードをログ出力している問題は → A: **本イシューでは触らず別イシューで対応**（タイトル案「I144: 登録ビューが平文パスワードをログ出力している問題の解消」）
- Q: 規約の記載先と既存コード例の扱いは → A: `rules/ultimate_django_coding_standards.md` に新規節「エラーハンドリング方針」を追加（想定内は種別ごとに捕捉／想定外は捕捉せずログ+500／広域 `except Exception` 禁止・例外的に許容する場合は意図をコメント明記）。既存コード例（同ファイルのサービス層 `create_article` / Celery タスク `generate_report` / `LoggingMixin.dispatch`）は計画時に精査し、規約と矛盾するものは修正、意図的な狭域捕捉であればその旨を注記する

## 背景/目的

### 現状の問題（証拠・再現手順）
`backend/accounts/views.py` に、想定外例外（プログラム欠陥由来の AttributeError / FieldError / TypeError 等）まで一括捕捉して汎用エラーレスポンスに変換する広域 `except Exception` が 3 箇所ある:
1. `views.py:121`（登録 `UserRegistrationView.create`）— あらゆる例外を `{"error": {"main_message": "エラーが発生しました", ...}}` の **400** に丸める。プログラム欠陥がクライアント起因エラー（4xx）として返るため、監視・ログ上も入力ミスと区別できない
2. `views.py:239`（validate-slug `OrganizationSlugValidationView.get`）— あらゆる例外を `{"valid": false, "message": "エラーが発生しました"}` の 500 に丸める（例外種別・原因がレスポンスから消える）
3. `views.py:427`（`logout_view`）— refresh トークン欠落（KeyError）・無効トークン（TokenError）と想定外欠陥を区別せず一律 400 「ログアウトに失敗しました。」

実害の実例（I131・2026-07-19 実測）: migration 0021 の改名漏れによる `AttributeError: 'Organization' object has no attribute 'organization_id'` が (1) で 400・(2) で 500 の汎用メッセージに変換され、**新規登録が全件不能**という重大欠陥が「エラーが発生しました」表示のまま潜伏した。

（補足: `views.py:112` のメール送信 `except Exception` は「送信失敗でも登録は継続する」意図的な狭域設計のため対象外）

### 根本原因
「想定内の例外は種別ごとに捕捉して適切な 4xx を返し、想定外の例外は捕捉せず例外ハンドラに委ねてログ+500 で顕在化させる」というエラー応答設計の規約が存在せず、ビュー実装が防御的な広域 `except Exception` で失敗を握りつぶす形になっている。DRF の `EXCEPTION_HANDLER`（`core.exceptions.custom_exception_handler`）は APIException 系を統一形式に変換し、非 APIException は Django 標準の 500（サーバーログ出力あり）へ流す構造が既にあるため、ビュー側で広域捕捉する必要はない。

### 解決方針
accounts の広域 `except Exception` 3 箇所を「想定内のみ捕捉・想定外は伝播」に再設計する:
1. **登録（views.py:121）**: try 節内で発生し得る想定内例外を特定して個別ハンドリング（現状は serializer 検証・組織不在とも事前分岐済みで、broad except が実際に受けるのは想定外のみの見込み。計画時に try 節を精査し、個別捕捉すべき想定内例外が見つかった場合は既存 4xx 契約＝AC 2 項目目と整合する形で捕捉対象・応答を計画書に明記してから実装する）。広域 except を撤去し、想定外は伝播させて `custom_exception_handler` のログ+500 に委ねる。なお組織不在の 400 契約は **slug 指定で組織が見つからない場合（クライアント起因）のみ維持**し、**slug なし登録で personal 組織が不在の場合（I140 で自動作成フォールバック廃止・環境異常として確定）は `_get_organization` が `core.exceptions.EnvironmentMisconfiguredError`（500）を raise して 500 へ再分類する**
2. **validate-slug（views.py:239）**: try/except を撤去（単純な ORM filter のみで想定内例外なし）。想定外は伝播で 500
3. **logout（views.py:427）**: 例外任せをやめ明示分岐へ。`refresh` 欠落・`request.data` が dict でない場合は `isinstance` + `.get()` の事前判定で 400（現行文言 `{'error': 'ログアウトに失敗しました。'}` 維持）、`except` は `TokenError` のみに限定。想定外は伝播。あわせて、広域 except に隠れていた潜在欠陥（`token_blacklist` アプリ未登録による `AttributeError`＝有効トークンでも常に 400）を根治するため、`core/settings.py` の INSTALLED_APPS に `rest_framework_simplejwt.token_blacklist` を追加し migrate する（追加テーブルのみ・既存データ影響なし）。これにより logout は refresh トークンを実際に失効させて 200 を返す
4. **想定外例外の応答基盤（core/exceptions.py）**: `custom_exception_handler` に非 APIException の分岐を追加し、`django.request` ロガーへスタックトレース記録 + 統一 JSON 500（`main_message='サーバーエラー'`）を返す。`DEBUG=True` 時のみ `sub_message` に例外クラス名とメッセージを含める。既存の応答フォーマット自体は変更しない
5. 既存レスポンス契約の維持範囲（FE が参照するキー・4xx の文言）と、伝播時 500 のレスポンス形式（統一 JSON・`main_message='サーバーエラー'`）を回帰テストで固定する
6. 再発防止の一般化: 「広域 except 禁止・想定外は顕在化」の規約を `rules/ultimate_django_coding_standards.md` に新規節「エラーハンドリング方針」として明文化し、同ファイルの既存コード例（サービス層 `create_article` / Celery タスク `generate_report` / `LoggingMixin.dispatch`）を規約と整合させる

FE 影響: コード変更なし。`error.main_message` / `sub_message` を参照する統一 JSON 形式が 500 でも維持されるため（`frontend/src/utils/apiError.ts`）、想定外欠陥時は表示文言が「エラーが発生しました」→「サーバーエラー」に変わり、personal 組織不在（環境異常）時は「組織の設定に失敗しました」→「サーバーエラー」に変わる。正常系・想定内 4xx の契約は不変。詳細な影響範囲は計画時に FE 消費箇所を全件確認して確定する。

## 制約・引き継ぎ情報
- DRF `EXCEPTION_HANDLER` は `core.exceptions.custom_exception_handler`（`core/settings.py:150`）。APIException 系のみ統一 JSON へ変換し、非 APIException は `exception_handler` が None を返して Django 標準 500（HTML）へ流れる。本イシューではこの None 分岐を捕まえて統一 JSON 500 + `django.request` へのスタックトレース記録に置き換える
- 本プロジェクトは Sentry 等の外部エラー監視を未導入で、例外の可観測性はロギング設定（`core/enhanced_logging.py`・`django.request` に `error_file` ハンドラ）に依存する。ハンドラ内で応答を返すと Django 標準の 500 ログ経路を通らないため、`logger.exception` による記録を必ず行う
- 登録ビューは `@ratelimit(10/5m)`（django-ratelimit）付き。テストは I131 と同様 `RATELIMIT_ENABLE=False` のファイルローカル autouse fixture で決定論化する
- I131 で validate-slug / 登録 API の正常系・既存 4xx 系はレスポンス body 完全一致で固定済み（`backend/accounts/tests/test_I131_org_id_rename.py`）。本イシューの変更でこれらが GREEN のままであることが契約維持の主要な検証になる
- 想定外例外の注入テストは monkeypatch 等のテスト都合パッチではなく、設計上検証可能な方法を計画時に検討する（例: ビュー内部メソッドの差し替え可能化よりも、テストからの例外注入点の設計を優先検討）
