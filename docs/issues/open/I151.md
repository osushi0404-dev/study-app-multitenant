### 決定の詳細

1. **django-guardian は更新せず削除する。** コードからの利用が皆無である（`backend/core/settings.py` の `INSTALLED_APPS` に 1 行あるのみ・`AUTHENTICATION_BACKENDS` 未登録・マイグレーション参照 0 件・`assign_perm` 等の呼び出し 0 件・テストコードからの参照 0 件）。本更新で最もリスクの高い「認可パッケージのメジャー 2 段更新」が不要になるため、**削除は変更量とリスクを減らす方向の判断**である。削除時に次を確認する。
   - (a) `manage.py check` が警告 0 になる（**事前実測で確認済み**。実装時に再確認する）
   - (b) **まっさらな DB に対する `migrate` が最後まで通る**（テスト DB は毎回新規作成されるため、ここが壊れると全テストが落ちる）
   - (c) `ANONYMOUS_USER_NAME` 等の guardian 専用設定が残っていない
   - (d) テストコードに guardian への参照がない
2. **DB に残る `guardian_*` テーブルは今回削除しない。** 不可逆操作であり本イシューの目的（脆弱性解消）と無関係である。「危なくない変更」と「不可逆な変更」を同一 PR に混ぜるとレビューもロールバックも難しくなる。別イシューとして起票する。
   - タイトル案: `未使用の guardian_* テーブル削除 — django-guardian 廃止（I151）で不要になった 2 テーブルをバックアップ取得のうえ削除する`
3. **バージョンは最新一括を採用する。** 最小限案との差である Django 5.2.16 / 5.2.17 はパッチ 1 つで実質同一であり、django-filter を 24 系に留めれば近いうちに同じ作業が再発する。かつ最新セットは監査 0 件・`check` 通過・マイグレーション変化なしまで実測済みであり、**検証済みの選択肢を捨てて未検証の組み合わせを選ぶ理由がない**。バージョン指定は既存に合わせ `==` の完全固定とする。
4. **`backend/requirements-dev.txt` も更新する（pytest-django 4.14.0 ＋ pytest 9.0.3）。ただし `pip-audit -r requirements-dev.txt` を CI の常設ゲートに追加してはならない。**
   - 両方更新する理由: pytest-django 4.9.0 は Django 5.2 への対応を宣言していない（5.1 まで）ため更新は必須。pytest 8.3.4 には脆弱性 1 件（PYSEC-2026-1845・修正 9.0.3）があり、pytest 9 で回帰が出ても**テストの失敗として可視化される**種類のリスクで、静かに壊れるものではない。
   - **実装は 2 段のコミットに分ける**。**(1) Django 5.2.17 ＋ 本体依存 ＋ pytest-django 4.14.0**（すべて必須の変更）→ テスト全件 pass を確認してコミット、**(2) pytest 9.0.3 のみ**（唯一の任意の変更）→ 再度確認してコミット。分割の目的は**切り離せる変更を単独コミットに隔離すること**であり、pytest-django 4.14.0 は Django 5.2 対応に必須で切り離せない以上、1 段目に含めるのが正しい。退避は「2 段目のコミットを落とす」だけで済む。
   - **`.github/workflows/ci.yml` は今回変更しない**。現行の PR ゲートは `pip-audit -r requirements.txt`（27 行目）で**本番依存のみが対象**であり、dev 依存は監査されていない。受け入れ条件に「手元で `pip-audit -r requirements-dev.txt` を実行し 0 件を記録する」を入れることと、CI の監査対象を増やすことは**別の作業**である。前者は CI ゲートの範囲を一切広げないため本イシューで実施してよい。後者（恒久対応）は許可リストと期限の仕組みが入る **I152（#268）で行う**。機構が無い状態で監査対象を広げると「外部の脆弱性公開だけで全 PR が停止する」面積が増えるためである。
5. **検証環境は Docker を使う。起動できない場合の代替はホスト venv ではなく CI とする。** 依存更新の検証は本番と同じ形で動くかを見るものであり、psycopg2 / python-magic 等は OS 側ライブラリに依存するためホスト venv の結果は保証にならない。`requirements.txt` 変更後は `docker compose build backend` によるイメージ再ビルドを行う。
   - **本ブランチは CI を代替手段として使える**。CI 停止の原因である `pip-audit` を修正しているのが本ブランチ自身であり、`requirements.txt` 修正時点でゲートが通るためである。
   - ただし **CI を回すには develop 宛の PR 作成が必要**である。`.github/workflows/ci.yml` のトリガーは `push: [develop, main]` / `pull_request: [develop, main]` であり、**feature ブランチへの push だけでは CI は起動しない**。代替手段として使う場合は先に draft PR を作成する。
   - ホスト venv は依存解決の下見・`pip-audit` の事前確認に限り使用し、**テスト合否の根拠にはしない**。
6. **認可の回帰確認は既存テストの結果記録でよい（新規テストの追加は不要）。** 意図は「更新の前後で同じ結果になること」の確認である。記録には次を含める。
   - (a) 対象とする認可・テナント境界テストの**モジュール名を列挙**する（「関連テストを実行した」では後から検証できない）
   - (b) **更新前と更新後の件数を両方記録**する（`110 件 pass → 110 件 pass` の形）
   - (c) **skip・削除・条件緩和による緑化をしていない**ことを明記する
   - (d) guardian 削除に伴い「**まっさらな DB で `migrate` が通る**」ことを記録する
7-A. **マイグレーション検証は 2 経路で担保する（第 2 回 grill・2026-08-17 の決定）。**
   - **(a) ローカル: 使い捨て DB を作って `migrate` する。** 開発データを壊さずにまっさらな状態を再現できる唯一の手段である。手順は `docker compose exec db psql -U postgres -c "CREATE DATABASE migrate_check;"` → `docker compose exec -e DB_NAME=migrate_check backend python manage.py migrate` → 確認後 `DROP DATABASE migrate_check;`。ボリューム削除（`docker compose down -v`）は破壊的なわりに得るものが同じであり採らない。
   - **(b) CI: E2E ジョブがまっさらな DB に対して `migrate` を実行している。** `.github/workflows/e2e.yml` の 17 行目 `docker compose up -d --wait db backend frontend`（GitHub ランナーは毎回新規＝ボリュームも空。`docker-compose.yml` の backend 起動コマンドに `manage.py migrate` が含まれる）と 25 行目 `docker compose exec -T backend python manage.py migrate --noinput` の 2 段で実行される。E2E は必須チェックのため、マイグレーションが壊れていれば PR はマージできない。
   - **(c) CI: Backend Lint & Security の「Check migration drift」ステップ**（`.github/workflows/ci.yml` の 29〜35 行目）が `makemigrations --check --dry-run` を実行し、モデルとマイグレーションの乖離を検出する。(a)(b) が「`migrate` が実行できるか」を見るのに対し、これは「モデル定義と既存マイグレーションがずれていないか」を見る別種のチェックである。**guardian を `INSTALLED_APPS` から外した状態＋確定セットで事前実測し `No changes detected` を確認済み**（第 3 回 grill・2026-08-17）。
   - **`backend/pytest.ini` の `--no-migrations` を見直す別イシューは起票しない。** これはテスト高速化のための意図的な設定（標準的なやり方）であり、pytest が検証しない部分は上記 (b) が実際に埋めているためである。**次に同じ疑問が出たときに調べ直さずに済むよう、テスト記録に「マイグレーション検証は (a) ローカルの使い捨て DB と (b) CI の E2E ジョブの 2 経路で担保」と明記する。**
   - 【訂正】第 2 回 grill の初回提示で「ローカルも CI もマイグレーションを一度も検証していない」と記載したが**誤り**である。`.github/workflows/ci.yml` の Backend Tests ジョブのみを見て `.github/workflows/e2e.yml` を見落としていた。検証していないのは Backend Tests（pytest）だけである。

7-B. **celery の動作確認は「実行の成功」まで見る（第 2 回 grill・2026-08-17 の決定）。** worker と beat のコンテナを起動し、**worker のログでタスクが成功したことまで**確認する（beat がタスクを投げたことの確認では不十分）。
   - 「テスト実走で確定」は成立しない。celery タスクを呼ぶアプリコードもテストも 0 件である（`.delay(` / `apply_async` / tasks の import すべて 0 件）。
   - ただし**未使用ではない**。`backend/core/celery.py` の `beat_schedule` が 30 秒ごとに `studylogs.tasks.update_daily_analytics_task` を実行しており、worker / beat 両サービスは backend と同じイメージから作られるため再ビルドの影響を受ける。30 秒待てば 1 回実行されるため確認コストは小さい。
   - **import できることだけの確認では不足**である。再ビルドで推移的依存（kombu 等）が上がって壊れる場合、それは import ではなく**実行時**に現れるためで、最も見たいものを見逃す。
   - この確認が決定 7-C のリスクへの備えを兼ねる。**実行時まで確認するなら kombu を固定しなくても十分に安全**と言える。

7-C. **固定していない推移的依存は今回触らない（第 2 回 grill・2026-08-17 の決定）。** celery 5.3.4 は据え置き、kombu の固定も行わない。celery の更新は未検証バージョンへの変更でスコープ拡大であり、kombu だけ固定しても他の推移的依存には同じ問題が残るため中途半端である。
   - 実態: `backend/requirements.txt` は celery 5.3.4 を固定するが kombu は固定していない。`docker compose build backend` で kombu が 5.6.2 に上がる（celery 5.3.4 の宣言は `kombu (<6.0,>=5.3.2)` で範囲内）。
   - **代わりに、再ビルド後の `pip freeze` の出力をテスト記録に残す。** 本当の問題は「celery が落ちたときに Django 更新のせいと誤診しやすい」ことであり、実際に入ったバージョンが記録に残っていれば後から切り分けられる。コストはコマンド 1 つで効果が大きい。
   - 根本解決（lockfile 導入による推移的依存の固定）は別軸であり急がない。別イシューとして起票する。
     - タイトル案: `backend 依存のロックファイル導入 — 推移的依存が再ビルドのたびに変動する状態を解消し、イメージビルドを再現可能にする`

7-D. **【本イシューの範囲外・別イシュー】celery beat のスケジュールが開発用のまま固定されている。** `backend/core/celery.py` の `beat_schedule` は 5 タスクすべてが開発用の短間隔（30 秒 / 60 秒 / 300 秒 / 3600 秒 / 1800 秒）で有効になっており、本番用の `crontab(...)` はすべてコメントアウトされている。このままデプロイすると日次のはずの分析更新が 30 秒ごとに走る。さらに `crontab` は import されていないため、コメントを外すだけでは `NameError` になる。**I151 では触らない。**
   - タイトル案: `celery beat のスケジュールが開発用のまま — 日次タスクが 30 秒間隔で実行される設定を環境別に切り替える`

7. **django-extensions は 4.1 へ更新する（決定 3 の最新一括に含む）。「今回行わない」のは本番依存 → 開発依存への移動のみである。** 3.2.3 は Django 4.2 までしか対応を宣言しておらず、更新は必須である。移動を今回行わない理由は、`INSTALLED_APPS` からの除外を伴い失敗すれば本番の起動に影響するためで、脆弱性解消と混ぜる種類の変更ではない。別イシューとして起票する。
   - タイトル案: `django-extensions を本番依存から開発依存へ移動 — 本番イメージから開発専用ツールを除外し INSTALLED_APPS の条件付き登録へ整理する`

## 背景/目的

**背景**: 2026-08-15 に I146 の `/code-review` を実行したところ、CI の `Backend Lint & Security` が失敗して CI ゲートで停止した。原因は I146 の変更ではなく、`pip-audit` が Django 4.2.30 に 6 件の脆弱性を検出したためである。定期監査（Dependency Audit workflow）は 2026-08-07 から連日失敗しており、#262 が自動起票済みのまま未対応で滞留していた。

**目的**: サポート対象内の Django へ更新して 6 件の CVE を解消し、`pip-audit -r requirements.txt` を exit 0 に戻す。これにより backend の PR ゲートと定期監査の双方をグリーンにし、停止している全 PR のマージ経路を回復する。

- 現在 open の他 PR（#256 等）は直近実行が CVE 公開前のため緑に見えているだけで、再 push すれば同様に失敗する。**backend を含む全 PR がマージ不能**である。

### 根本原因

Django 4.2 LTS が延長サポート期間を終えており、**4.2 系に修正リリースが出ない**。pip-audit の Fix Versions に 4.2.x が 1 つも現れないことがその証拠である。したがってパッチ更新では解消できず、サポート対象系列（5.2 LTS または 6.0）への移行が唯一の解消手段となる。

さらに現在の `requirements.txt` は Django 5.2 に非対応のパッケージ（DRF 3.15.2 / django-filter 23.4 / django-redis 5.4.0 / django-extensions 3.2.3）を含むため、Django 単独更新は成立しない。とくに DRF は 3.18.0 が `django>=5.2` を要求するため、Django と同時に上げる必要がある。

### 解決方針

**Django 5.2.17（LTS）へ更新し、Django 5.2 に非対応の依存パッケージを対応版へ同時に更新する。未使用の django-guardian は更新せず削除する。**

- **5.2 を選ぶ理由**: 5.2 は LTS であり 6.0 / 6.1 は LTS ではない。サポート期間の長い系列を選ぶことで、同種の EOL 起因の停止を最も遠ざけられる。5.2.16 以上が 6 件すべての Fix Versions を満たし、5.2 系の最新である 5.2.17 を採用する（決定 3）。
- **一括更新にする理由**: Django だけを上げても DRF・django-filter・django-redis・django-extensions が非対応で動作しない。分割すると中間状態が壊れるため、1 イシューで整合の取れた組み合わせへ移行する。
- **guardian を削除する理由**: 決定 1 のとおりコードから一切使われていない。更新すれば認可パッケージのメジャー 2 段更新という本件最大のリスクを負うことになるが、削除すればそのリスクごと消える。

## Danger Ops（有/無）
- 有
- 内容: 依存パッケージの一括メジャー更新と、`INSTALLED_APPS` からのアプリ除去（django-guardian）。**当初想定より危険度は下がっている**（guardian を更新せず削除する方針に変更したため、認可パッケージのメジャー 2 段更新が消えた）。残る要注意点は (1) DRF 3.15 → 3.18 の挙動差、(2) guardian 除去後の `migrate` 失敗、(3) pytest 9 によるテスト基盤の挙動差。
