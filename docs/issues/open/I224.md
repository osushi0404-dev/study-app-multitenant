# I224: GitHub への書き込み（イシューの書き換え・コメント・push）の回数を絞り、短い間に集中しないようにする

## 関連資料
- GitHub Issue: #413
- Draft PR: #420
- 起点: I220（retro からの起票・2026-11-05）
- 関連: I223（GitHub App への移行の記録）
- GitHub サポートへの補足で約束した再発防止（イシューの書き換え・コメントの回数を絞る、push をまとめる、同時に複数のセッションで動かさない）

## 設計確認メモ（/grill-me）
- ユーザーの指示（2026-11-07）: 「ループエンジニアリング、ハーネスエンジニアリングのベストプラクティスと開発をサクサク進めるという観点で問題ないやり方を選択して」→ 以下はすべて Claude の推奨案で確定
- 前提（grill-me で実測・2026-11-07）: I226（PR #418）の push は 21:23〜22:27 の約 1 時間に 10 回（`git reflog show refs/remotes/origin/feature/I226-revoke-check-and-g10-scope`）。最も詰まった所は 3 分半に 4 回。ほかにイシュー本文の書き換え・PR の作成／更新／Ready・起票などが 5 回前後。GitHub が公開している、作る操作の上限（1 分 80 回・1 時間 500 回ほど。grill-me の時点では調べ直していない・計画で確かめる）よりずっと少なく、停止の原因は量より「人でない新しいアカウントの自動の書き込み」の可能性もある。その対策の本筋（GitHub App への移行）は I223 で済んでいる
- Q: どこまでやるか → A: **(a) 回数をまとめるだけ**。GitHub に送る（push する）のは、要る 3 時点に絞る: ① 下書き PR を作るとき（plan-issue）② review-gate の CI 待ちの前（fix-loop の後のやり直しのたびを含む）③ close の最後の確認（`pr-base-sync.sh final`）の前。ほかの段階の記録（STAGE_DONE・自律判断の記録・テスト結果など）は手元でコミットだけし、次に送るときにまとめて送る。イシュー本文の書き換え（`gh issue edit --body-file`）は grill-me の終わりの 1 回だけにする（plan-issue での同期は、Draft PR の番号などを足す必要があるときも close のときにまとめる・詳細は計画）。書き込みの間隔を空ける仕組み（`gh` の入口で待つなど）は入れない
- Q: 目標の数字 → A: 1 本のイシューで push は **4 回以内**（fix-loop の後の review-gate のやり直し 1 回ごとに +1 を許す）。測り方はブランチへの push の履歴（`git reflog show refs/remotes/origin/<ブランチ>` の `update by push` の行数）。I224 の次に進めるイシュー 1 本で実測して達成を確かめる（I224 自身でも測って記録する）
- Q: 同時に複数のセッションで書き込まない件 → A: **決まりとして書くだけ**（仕組みで止めない）。テスト用に起こすセッションは I223 で読み取りだけの鍵なので書き込めない。残るのは、ユーザーが複数の作業フォルダ（worktree）で同時に進める場合だけ。手元の安全装置を作り込まない方針（最後の守りは GitHub）に合わせる

## 背景/目的

**背景**: 2026-10-30 に、Claude が GitHub の操作に使っていた bot アカウントが停止された。GitHub からの理由の説明は未着だが、短い間にイシューの書き換え・コメント・push が集中したことがきっかけと見ている（I193 以降、Claude が段階を自分で進めるようになり、書き込みの回数が大きく増えた）。GitHub App に移っても、同じ量と集中のしかたなら、また止められるおそれがある。
**目的**: 1 つのイシューを進めるときの GitHub への書き込みの回数を減らし、短い間に集中しないようにする。

### 現状の問題（証拠・再現手順）
- 段階ごとに「記録をコミットして push」があり、1 つのイシューで push が 10 回を超えることがある（各段階のスキルの結線・`docs/runbooks/workflow.md`。回数は見立てで未実測）
- grill-me・計画の段階で、GitHub のイシュー本文を何度も書き換える（`gh issue edit --body-file`）
- retro で既存イシューへのコメントを続けて付ける
- テスト用の `claude -p` を同時に流すと、書き込みが重なる（I220 の M-03・M-04）
- 実測の例（I220・2026-11-05・review-gate から close まで）: push 10 回。内訳は App の確かめ 2・隠れた PR のせいで無駄になった 1・改名したブランチ 1・段階ごとの記録 5（PR の作り直し・review-gate・test-gate・retro・STAGE_DONE close）・close の前の 1。GitHub に送っておく必要があるのは「review-gate の CI 待ちの前」と「close の最後の確認の前」だけで、段階ごとの 5 回は 1〜2 回にまとめられた
- ほかのイシューでの回数の実測は未特定・grill-me で確認

### 根本原因
（停止の原因が書き込みの集中だというのは推定。GitHub の説明は未着）各段階のスキルが、その段階の終わりごとに GitHub へ書き込む作りで、イシュー全体での回数と間隔を見る仕組みが無い。そうなっているのは、記録をコミットすることと GitHub へ送ることが分かれておらず（各段階の結線が「commit/push」を 1 組で書く）、review-gate が「PR の最新のコミット＝手元の HEAD」を前提に CI を待つため、と見ている。

### 解決方針
- 確定（設計確認メモ参照）:
  - push を段階ごとでなく、要る 3 時点（下書き PR の作成・review-gate の CI 待ちの前・close の最後の確認の前）にまとめる。ほかの段階は手元でコミットだけ
  - イシュー本文の同期は grill-me の終わりの 1 回だけにする
  - 書き込みの間隔を空ける仕組みは入れない
  - 同時に複数のセッションで書き込まない決まりを `docs/runbooks/workflow.md`（または `docs/runbooks/worktree.md`）に書く（仕組みでは止めない）

## 実装対象（既知のもの）
| ファイル | 変更内容 |
|---------|---------|
| `.claude/skills/`（各段階のスキルの結線・plan-issue・grill-me・retro・close など） | push の時点を 3 つにまとめる・イシュー本文の同期を grill-me の終わりだけにする |
| `docs/runbooks/workflow.md`・`docs/runbooks/worktree.md` | 書き込みの時点の決まり・同時に複数のセッションで書き込まない決まり |
| `scripts/claude/`（push を前提にする確認があれば。例: `flow-stage.sh`・`gate-check.sh`） | 手元だけのコミットでも段階の判定・確認が壊れないことを計画で確かめる（直すかは計画で決める） |

## スコープ
### 含む
- GitHub への書き込みの回数と時点の見直し（push を 3 時点に・イシュー本文の同期を grill-me の終わりだけに）
- 同時に複数のセッションで書き込まない決まり（決まりだけ。テスト用の `claude -p` は I223 で読み取りだけなので対象外）
- 測り方（ブランチへの push の履歴の行数）と目安（1 本で 4 回以内・やり直し 1 回ごとに +1）
### 含まない
- GitHub App への移行そのもの（I223）
- 書き込みの間隔を空ける仕組み（grill-me で入れないと確定）

## 関連する品質基準
- 該当なし（ハーネスの運用の仕組み）

## 受け入れ条件（Acceptance Criteria）
- [ ] 各段階のスキルが、push を 3 時点（下書き PR の作成・review-gate の CI 待ちの前・close の最後の確認の前）だけで行い、ほかの段階は手元のコミットだけにしている
- [ ] イシュー本文の書き換え（`gh issue edit --body-file`）が grill-me の終わりの 1 回だけになっている
- [ ] 1 本のイシューの push が 4 回以内（fix-loop の後の review-gate のやり直し 1 回ごとに +1）であることを、I224 の次のイシュー 1 本で実測して示す（`git reflog show refs/remotes/origin/<ブランチ>` の `update by push` の行数。I226 の実測は 10 回）
- [ ] 同時に複数のセッションで書き込まない決まりが手順書にある
- [ ] review-gate の CI 待ち（PR の最新のコミットと手元の HEAD が同じこと）など、push を前提にしている確認が壊れていない
- [ ] 既存のハーネステスト・CI がすべて pass する

## 制約・引き継ぎ情報
- GitHub の公開の上限（API の回数の上限）とは別に、自動の監視が「人らしくない操作」をどう見ているかは公開されていない。数字の目安は未定・grill-me で確認
- review-gate は PR の最新のコミットが手元の HEAD と同じであることを確かめるので、push を減らすと待ちの手順に影響する
