## 設計確認メモ（/grill-me）
- Q: ログイン画面で「パスキーでログイン」をどう出すか（ボタン／入力欄の候補〔conditional UI〕／両方） → A: **ボタンだけ**。今の ID・パスワードの欄は移行期間（#622 まで）残し、その上に「パスキーでログイン」ボタンを置く。入力欄の候補（conditional UI・`mediation: 'conditional'`・`autocomplete="username webauthn"`）は作らない。理由: #622 で欄ごと消えるため一時的な作りになる・画面を開くだけで challenge を発行する負担が無くなる。#622 の後はボタンだけの画面にする（#622 にコメント済み）
- Q: パスキーの登録・削除の前に本人か確かめるか → A: **確かめる**。登録・削除の API は、直前の本人確認（今のパスワード、または登録済みのパスキーでの確認）が無ければ拒む。パスワードを廃止した後もパスキーで確かめられる形にする。確認の持ち方（サーバー側でどう覚えるか）は計画で決める
- Q: 本人確認のあと、確かめ直さずに続けて操作できる時間は → A: **5 分**。確認から 5 分を過ぎた登録・削除は拒み、もう一度確かめてもらう
- Q: 設定画面のパスキーの一覧に何を出すか → A: **名前＋登録日＋最後に使った日**。名前は登録のときに自動で付け（例: 「Windows の Chrome」）、あとで本人が変えられる。最後に使った日はパスキーでログインに成功したときに更新する
- Q: 利用者や組織を無効にしたとき、パスキーをどうするか → A: **すべて消す**。利用者を無効にしたらその人のパスキーを、組織を無効にしたらその組織の利用者全員のパスキーを消す。有効に戻しても戻らず、登録し直し（移行期間はパスワードでログインして登録し直す。#622 の後は #620 の登録用リンクで登録し直す）
- Q: 管理者が組織の利用者のパスキーを見たり消したりできるようにするか → A: **#620 で作る**（I619 では作らない）。I619 の間は本人がパスワードでログインして自分で消せる。#620 にコメント済み
- Q: パスワードでログインした人にパスキーの登録を勧めるか → A: **勧めない**（I619 は設定画面から登録できるだけ）。移ってもらう進め方は廃止の段取りと一緒に #622 で決める。#622 にコメント済み
- （質問にせず決めたこと）最後の 1 つのパスキーも削除できる。#622 までは パスワードでも入れるため。パスワード廃止後の扱いは #622 で決める（#622 にコメント済み）

## 背景/目的

**背景**: 今のログインは「メールアドレス または ユーザーID ＋ パスワード」で、JWT を返す（`backend/accounts/views.py` の `CustomTokenObtainPairView`・`backend/accounts/backends.py` の `EmailOrUserIdBackend`）。パスワードは漏れ・使い回し・フィッシングに弱い。ユーザーはパスキーへ移り、最終的にパスワードとメールアドレスを持たない形にしたい。
**目的**: ログイン済みの利用者が自分のパスキーを登録でき、パスキーだけでログインできる。手元の開発環境（localhost）でも同じに動き、E2E で自動で確かめられる。

### 現状の問題（証拠・再現手順）
- パスキー（WebAuthn）の登録・ログインの API と画面が無い（`backend/accounts/urls.py` に該当の経路が無い）
- パスワードしか認証の手段が無い

### 根本原因
認証の手段がパスワードだけで、フィッシングに強い手段（パスキーは登録したサイトでしか使えない）が無い。

### 解決方針
- バックエンドに WebAuthn の登録（attestation）とログイン（assertion）の API を足す。使うライブラリ（例: py_webauthn・django-otp-webauthn など）は計画で調べて決める
- 1 人が複数のパスキーを持てる形にする（端末ごとに登録・一覧・名前の変更・削除）。パスキーは利用者に紐づけ、一覧・名前の変更・削除は既存のテナント分離の仕組みに合わせて本人の分だけに絞る。最後の 1 つも削除できる
- 登録・削除の前に本人の確認（今のパスワード、または登録済みのパスキー）を求め、確認の有効時間は 5 分（設計確認メモ）
- ログインのときの利用者の特定は、ユーザー名を入れない形（discoverable credential）にする（将来メールアドレスを無くすため、メールアドレスに頼らない）。ログイン画面は「パスキーでログイン」ボタンから始める（入力欄の候補〔conditional UI〕は作らない・設計確認メモ）
- ログインに成功したら、今の `CustomTokenObtainPairView` と同じ中身（組織の情報など）の JWT を返す（フロントの後の処理は変えない）
- 利用者・組織を無効にしたら、該当するパスキーをすべて消す（設計確認メモ）
- RP ID・origin は設定（環境変数）で切り替え、localhost と本番の両方で動かす。localhost は HTTPS でなくてもブラウザがパスキーを使える（安全な文脈として扱われる）ことを計画で確かめる
- 移行期間は今のパスワードのログインも残す（廃止は別イシュー）
- E2E は Playwright で仮想の認証器を付けて、登録 → ログアウト → パスキーでログインを流す

## 受け入れ条件（Acceptance Criteria）
- [ ] ログイン済みの利用者が設定画面からパスキーを登録・一覧・名前の変更・削除できる（複数登録できる・最後の 1 つも削除できる）
- [ ] 一覧に名前・登録日・最後に使った日が出る。名前は登録のときに自動で付き、本人が変えられる。最後に使った日はパスキーでのログインの成功で更新される
- [ ] 登録・削除は、直前の本人確認（パスワード または 登録済みのパスキー）が無いと拒み、確認から 5 分を過ぎても拒む（API のテストで確かめる）
- [ ] ログイン画面の「パスキーでログイン」ボタンから、登録したパスキーだけで（パスワードなしで）ログインでき、今と同じ JWT が返る
- [ ] 他人のパスキー・別の組織の利用者のパスキーの一覧・名前の変更・削除ができない（テナントの分離。API のテストで確かめる）
- [ ] challenge は使い捨てで期限があり、使い回し・期限切れを拒む（API のテストで確かめる）
- [ ] 署名回数が前回以下（0 のままの認証器を除く）のログインを拒む（API のテストで確かめる）
- [ ] 利用者を無効にするとその人のパスキーが、組織を無効にするとその組織の利用者のパスキーがすべて消え、有効に戻しても戻らない（API のテストで確かめる）
- [ ] 手元（localhost）の実際のブラウザで、人がパスキーの登録とログインをできる（人の手動テスト）
- [ ] Playwright の仮想の認証器で「登録 → ログアウト → パスキーでログイン」の E2E が CI で通る
- [ ] 今のパスワードのログインは変わらず動く

## 影響範囲（想定）
- Backend: accounts アプリに API とモデルを追加・利用者/組織の無効化の処理にパスキーの削除を足す
- Frontend: ログイン画面（`frontend/src/pages/Login.tsx`）・設定画面（`frontend/src/pages/Settings.tsx`）
- DB: パスキーのテーブルを追加（足すだけのマイグレーション）。無効化のときの削除は通常の業務の処理（一括の破壊的操作ではない）
- Config/Infra: RP ID・origin の環境変数。本番の値は本番環境ができたときに決める（今は本番環境が無い）

## 制約・引き継ぎ情報
- ログインの試行回数の制限（django-ratelimit。既存のログインは `key='ip'`）をパスキーの API にも当てるか計画で決める
- この段階では、パスキーを登録できるのはパスワードでログイン済みの人だけ。新規の利用者の初回登録・端末をなくしたとき・無効から戻したときの再登録、管理者が利用者のパスキーを見る・消す操作は #620 が担う。パスワードの廃止はその後
- 仮想の認証器は Chromium だけで使える。E2E のブラウザの設定（`e2e/playwright.config.ts`。今は `channel: 'chromium'` と `--unsafely-treat-insecure-origin-as-secure` を使っている）を確かめる
