## 背景/目的

**背景**: I179・I174・I181 では、「develop/main は GitHub 側で保護され（ブランチ保護・CODEOWNERS・承認必須。bot は PR を出すだけでマージできない）、ユーザーがマージを誤らない限り GitHub は壊れない。Claude がローカルを壊しても GitHub から復旧できる」を前提に、手元の見張りやレビューを軽くした（2026-10-21〜22 のユーザー方針）。その後の棚卸しで、この前提には穴があることが分かった。
**目的**: 「GitHub から復旧できる」が成り立たない操作を洗い出して塞ぎ、前提を正しい形（どこまでが復旧できる範囲か）にする。前提が成り立つ範囲では、確認待ちを減らして速く進められるようにする。

### 現状の問題（証拠・再現手順）
1. **秘密情報の push は取り消せない**: リポジトリは公開（`gh repo view osushi0404-dev/study-app-multitenant --json visibility` → `PUBLIC`）。bot は feature ブランチへ push できるので、秘密情報を含むコミットを push した時点で、マージしなくても全世界に公開され、取り消しも GitHub からの復旧もできない（キーの無効化・再発行が必要になる）。
2. **秘密情報の検査は飛ばせる**: 手元の守りは pre-commit（`.pre-commit-config.yaml` の detect-secrets）で、`git commit --no-verify`（`-n`）で飛ばせ、見張りも止めない（`pretooluse_guard.py` に `no-verify` の判定なし）。CI の `Backend Lint & Security` も detect-secrets を全ファイルに実行する（必須チェック）が、push の後に動くので、見つけた時点ですでに公開されている（起票時は「CI に検査が無い」と書いたが、/plan-issue で誤りと判明）。
3. **見張りが異常終了すると素通りになる**: PreToolUse フックは exit 2 以外の異常終了（例外・タイムアウト）ではコマンドを止めない。I174 で読み解き（`_analyze`）と安全網（`_safety_net`）は例外なら確認に包まれたが、ほかの判定は包まれておらず、時間切れ・メモリ不足も素通り。I179 第 10 周で、判定の処理量が爆発してメモリを使い切り、セッションごと落ちた実例がある（その判定は I179 計画変更記録 6 で廃止済み・I179 retro P3）。
4. **ワークフローの書き換えで、マージ無しに secrets に触れられる（grill で検証）**: `ci.yml`・`e2e.yml` は develop/main 宛ての `pull_request` で動き、同じリポジトリのブランチからの PR では PR 側のワークフローが secrets（`E2E_TEST_PASSWORD`）付きで動く。
5. **ワークフローを書き換えなくても、PR 側のコードが CI の中で `GITHUB_TOKEN` に触れられる（/security-review で判明）**: `ci.yml`・`e2e.yml` に `permissions:` が無く、`GITHUB_TOKEN` の権限はリポジトリの既定任せ。PR 側のテスト・`package.json` の scripts・`manage.py` のコマンドは CI の中で動くので、4. の「ワークフローの編集を確認」だけでは防げない。
6. **その他（本イシューで対応するもの）**:
   - 前提が成り立つ範囲（ローカルだけで復旧できる操作）でも、`.claude/settings.json` の ask にある `rm`・`mv`・`cp`・`chmod`・`chown` で確認待ちが出ている。
   - リモートブランチの削除が確認なしで通る。
   - `scripts/claude/tests/guard_corpus_diff.py` は、未コミットの変更が無いとき「見張りを最後に変えたコミットの直前」と比べるが、そのコミットがマージコミットだと第 1 親（取り込み前の見張り）と比べてしまい、誤って不合格になる（I179 の /close 前の取り込みで 98〜99 件。`--base origin/develop` なら 0 件）。
   - （対象外・引き継ぎのみ）起動時の「Deny rule Write(...) never matches · use Edit(...)」の警告は primary の `.claude/settings.local.json`（個人用・git 管理外）が出どころ。

### 根本原因
- 「GitHub が最後の守り」という前提を、どの操作で成り立つか（復旧できる範囲）を確かめずに一般化した。公開リポジトリで push 自体が公開になる点、feature ブランチへの push と PR の作成は bot にも許されていて、PR 側のワークフローが secrets 付きで動く点が抜けていた。
- 見張りの判定の例外・時間切れ・メモリ不足を、確認に倒す仕組みが一部にしか無い（フックの仕様では exit 2 以外は止めない）。

### 解決方針（grill で確定）
1. **秘密情報の push を止める**: GitHub の push protection を有効化（ユーザーの UI 操作）・見張りで `git commit`（`--no-verify`／`-n`）と `git push`（`--no-verify`）を停止（`DANGER_OK=1` で確認）・CI の既存の detect-secrets（`Backend Lint & Security`・必須チェック）が外されないことを決定論テストで守る・検出時の対応手順を runbook に書く。
2. **マージ無しで GitHub 側に影響が出るほかの操作**: `.github/workflows/`・`.pre-commit-config.yaml`・`.secrets.baseline` の Edit/Write を確認にする・`ci.yml`・`e2e.yml` の最上位に `permissions: contents: read` を書く・リモートブランチの削除を確認にする・イシュー/PR への書き込みとリポジトリ設定・リリースは対策しない理由を記録する。
3. **見張りの異常終了を素通りにしない**: 判定全体を包み例外なら確認・内側で時間 20 秒（`signal.alarm`）／メモリ 512MB（`RLIMIT_DATA`）の上限（超えたら確認）。決定論テストで注入して確かめる。
4. **前提が成り立つ範囲の確認待ちを減らす**: settings.json の ask から `rm`・`mv`・`cp`・`chmod`・`chown` を外して allow に移す（外すだけでは既定の権限確認が出るため）。`git rebase`・`psql` は残す。`rm -rf`・`git reset --hard` は見張りの承認制のまま。単純で安いガード（保護ブランチへの push・強制 push・MCP からのマージ・別リポジトリの PR の取り込み）は残す。
5. **小さな整理**: `guard_corpus_diff.py` のマージコミットの扱い。
6. **前提の明文化**: 結論（復旧できる範囲・できない操作と対策）を runbook に書き、I181 の「前提」の注記と、そのほかの「GitHub が最後の守り」に触れた記述（`docs/runbooks/worktree.md` ほか）を更新する。

## スコープ
### 含む
- 秘密情報の push を防ぐ仕組み（手元の見張り・CI・GitHub 側の設定）と検出時の対応手順
- マージ無しで GitHub 側に取り返しのつかない影響が出る操作の洗い出しと対策（ワークフローの書き換え・ワークフローの `GITHUB_TOKEN` の権限・リモートブランチの削除・イシュー/PR への書き込み・リポジトリ設定）

- 前提が成り立つ範囲での確認待ちの削減（settings.json の ask）
- `guard_corpus_diff.py` のマージコミットの扱い
- 前提（復旧できる範囲）の明文化と、関連する記述の更新
### 含まない
- レビュー工程の重さ・敵対的レビューの線引きや上限（I181）
- 見張りの判定ロジックの全面的な作り直し（I174 で実施済み）
- 意図的な回避（`SKIP=detect-secrets`・`core.hooksPath` の書き換え等）への対策（ガードの脅威モデルは事故）
- E2E の secrets を承認付きの environment に移すこと
- primary の `.claude/settings.local.json` の `Write(...)` の警告（個人用・git 管理外。primary のセッションで直す）

## 受け入れ条件（Acceptance Criteria）
- [ ] 「GitHub から復旧できる」が成り立たない操作の一覧（秘密情報の push・ワークフローの書き換え・リモートブランチの削除・イシュー/PR への書き込み・リポジトリ設定）と、それぞれの対策（または対策しない理由）が計画書に記録されている
- [ ] GitHub の push protection が有効になっている（ユーザーの UI 操作・`gh api` か画面で確認）
- [ ] CI の `Backend Lint & Security`（develop の必須チェック）で detect-secrets が全ファイルに走ることが決定論テストで守られ（ジョブ・pre-commit の設定から外すと不合格）、必須チェックに入っていることをユーザーが画面で確認している
- [ ] 見張りが `git commit` の `--no-verify`／`-n`（まとめた短縮形を含む）と `git push` の `--no-verify` を停止し、`DANGER_OK=1` 付きでは確認になる（決定論テストで機械検証）
- [ ] `ci.yml`・`e2e.yml` の `GITHUB_TOKEN` が読み取りだけ（最上位 `permissions: contents: read`）で、決定論テストで守られ、PR の必須チェックが緑のまま（/security-review で追加）
- [ ] 見張りが `.github/workflows/` 配下・`.pre-commit-config.yaml`・`.secrets.baseline` の Edit/Write と、リモートブランチの削除を確認にする（決定論テストで機械検証）
- [ ] 見張りの判定中の例外・時間超過（20 秒）・メモリ超過（512MB）が確認（ask）になる（注入した決定論テストで機械検証）
- [ ] settings.json の ask から `rm`・`mv`・`cp`・`chmod`・`chown` が外れて allow にあり、`git rebase`・`psql` は ask に残っている（`test_settings_permissions.sh` が合格）
- [ ] `guard_corpus_diff.py` が、見張りを最後に変えたコミットがマージコミットのときも誤って不合格にならない（決定論テスト）
- [ ] 前提（復旧できる範囲）と秘密情報を push してしまったときの対応手順が runbook に明記され、I181 の「前提」の注記・`worktree.md` の記述と整合している
- [ ] 既存の見張りの決定論テストがすべて合格する

## 影響範囲（想定）
- Backend: なし
- Frontend: なし
- DB: なし
- Config/Infra: `.claude/settings.json`・`.github/workflows/ci.yml`・`.github/workflows/e2e.yml`（最上位の `permissions` だけ）・GitHub リポジトリの設定（push protection の有効化・必須チェックの確認。ユーザーの UI 操作）
- Harness: `scripts/claude/hooks/pretooluse_guard.py`・`scripts/claude/tests/`・`docs/runbooks/danger-ops.md`・`docs/runbooks/review-rules.md`・`docs/runbooks/worktree.md`・`docs/issues/open/I181.md`
- 対象外（意図的除外）: primary の `.claude/settings.local.json`（個人用・git 管理外。primary のセッションで直す）・`docs/runbooks/branch-protection-setup.md`（必須チェックの根拠として参照するだけで変更しない）

## 制約・引き継ぎ情報
- track:harness。bot アカウントは repo の管理権限が無い（リポジトリ設定の変更 API は 404）ため、GitHub 側の設定（push protection の有効化・必須チェックの確認）はユーザーの UI 操作になる。push protection は計画の承認時（以降の push を守るため早いほどよい）、必須チェックの確認は実装の最後（手動テスト M2）に依頼する。
- 秘密情報の push と GitHub Actions に関わる変更は、「GitHub が最後の守り」の対象外。本イシュー自身のレビューは、この部分を変える範囲では敵対的レビューを 1 周・時間上限付きで回す（I181 の「前提」の注記と同じ扱い）。
- 見張りの変更は、I174 の 3 つのテスト（`test_guard_bash_oracle.sh`・`test_pretooluse_guard_matrix.sh`・`test_guard_corpus_diff.sh`）を流してからコミットする（`docs/runbooks/danger-ops.md`）。
- primary の `.claude/settings.local.json` の `Write(...)` の deny は `Edit(...)` に書き換えるか削除する（primary のセッションで実施。本イシューの対象外）。
