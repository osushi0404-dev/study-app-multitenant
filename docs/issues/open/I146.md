## 設計確認メモ（/grill-me）
- Q: fork 判定の手段は何を使うか → A: `gh pr view <番号> --json isCrossRepository -q .isCrossRepository`。実測確認済み（#257=`true`／#256=`false`）。origin の owner/name を別途引いて文字列比較する必要はない
- Q: 今回の事故で /close は実行されたか → A: されていない。#257 は別ブランチの PR のため `gh pr view`（番号省略）の自動検出には掛からない。失敗の実体は「調査中の思い込み」であり、スキル経由のゲートだけでは同じ経路を止められない
- Q: ゲートはどこに置くか（script だけで足りるか） → A: **3層に置く**。(1) script 層= `pr-base-sync.sh`（sync/final 共通・不一致は exit 1）、(2) hook 層= `pretooluse_guard.py` に `gh pr` 取り込み系サブコマンドの cross-repo 判定を追加、(3) skill 層= `/close` step 0 の既存照会に `isCrossRepository` を追加。パスに依存しない層（hook）が無いと同種の再発を止められないため
- Q: hook の遮断強度は block か ask か → A: **`gh pr merge` は block（exit 2）**（方針上ありえず不可逆・記録なしの外部コードが develop に入る）。**`gh pr ready` / `gh pr edit` / `gh pr review --approve` は ask**（理由文言に fork 由来である旨と head リポジトリ名を含める）。**read-only（view/checks/diff）と `gh pr close` / `gh pr comment` / `gh pr review --comment` は素通し**（外部 PR を断るのに必要なため塞いではならない）
- Q: hook 内の `gh` 照会が失敗したら → A: **ask に降格**（block しない）。オフライン・未認証で作業不能にしないため。既存の「動的・不透明 push 判定（ask degrade）」と同方針
- Q: 残存ギャップをどう扱うか → A: 今日と同じ経路（読み取り中心の調査での思い込み）は hook でも止まらない。hook が止めるのは「外部 PR に /close を回す・マージする」経路。残りは do 層（runbook 記載）で埋める。この限界を計画書にも明記する
- Q: CONTRIBUTING.md の言語と置き場所 → A: **リポジトリルート**に置き、**英語を先頭・日本語を後段に併記**。読み手が外部寄稿者のため英語が実効的で、`.github/` 配下よりルートの方が見つけやすい
- Q: イシュー（バグ報告・提案）は受け付けるか → A: **受け付ける**。ただし対応を約束しない旨を明記する。PR（コードの寄稿）のみ受け付けない、と書き分ける
- Q: `.github/pull_request_template.md` にも記載するか → A: **する**。PR 作成画面は外部寄稿者が最初に見る場所で do 層として最も実効的。自前 PR でも毎回表示されるため **1行**（受け付けない旨＋CONTRIBUTING.md へのリンク）に留める
- Q: 脆弱性報告の経路は → A: **GitHub の Private vulnerability reporting を有効化**（`gh api -X PUT repos/<owner>/<repo>/private-vulnerability-reporting`。現状 `{"enabled":false}` を実測確認済み・取り消し可）し、**`SECURITY.md` を新設**して誘導する。メールアドレスは記載しない。数行で済むため別イシューに切り出さず本イシューに含める

## 背景/目的

**背景**: 2026-08-04、I138(#247) の /close 作業中に PR #257 が「This branch is out-of-date with the base branch」と E2E 失敗を示した。調査の結果、#257 は自分たちが出した PR ではなく、public リポジトリの issue #247 を第三者（@Dodothereal）が運用する自律 AI エージェントが拾い、fork から出してきた未依頼の外部寄稿だった。方針コメントを付けて close 済み。issue #247 は OPEN のまま残し、I138 は自前実装する方針で確定した。

**目的**: 同種の外部寄稿が再び届いたときに、(a) 受付方針が明文化されていて寄稿者にも自分たちにも即座に判断がつく状態、(b) 自前でない PR を自分たちのクローズ／レビュー手順に載せてしまう事故が決定論的に止まる状態にする。

### 現状の問題（証拠・再現手順）

1. **自前でない PR をクローズ作業に載せた**
   PR #257（head: `Dodothereal:fix/247-i138-plan-writing-rules` / base: `develop`）を I138 のクローズ対象と誤認し、調査と GitHub Actions の実行承認まで進めた。head リポジトリが origin と異なることに気づくまで、ブランチ追従案まで検討していた。

2. **fork PR は CI が原理的にグリーンにならない**
   fork からの PR には repository secrets が渡らないため `E2E_TEST_PASSWORD` が空になり、E2E が必ず失敗する。
   ```
   Error: E2E_TEST_PASSWORD is not set. ... (e2e/global-setup.ts:14)
   ```
   （run 29983378475 attempt 2 / 2026-08-04 11:16:44Z）。`.github/workflows/e2e.yml` は `secrets.E2E_TEST_PASSWORD` を参照しており、ブランチ追従や再実行では解消しない。

3. **fork PR の Actions 承認待ちを承認してしまった**
   attempt 1 は `action_required`（fork PR の既定＝手動承認待ち）で停止していた。本来は承認しないのが正しいが、クローズ作業の一環として承認したため 2 の失敗が発生した。

4. **base 追従ゲートが head リポジトリを検証していない**
   `scripts/claude/pr-base-sync.sh` は `mergeStateStatus` のみを見て BEHIND なら `merge_base`（`git merge origin/<base>`）を実行する。fork PR に対して実行すると、push 権限のないブランチへの追従を試みることになる。head リポジトリの検証は存在しない（fail-open）。

5. **受付方針が明文化されていない**
   リポジトリルートに `CONTRIBUTING.md` が存在せず、`docs/runbooks/workflow.md` にも外部寄稿・fork PR への言及がない（`grep -n "外部\|CONTRIBUTING\|fork"` でヒット 0）。

### 根本原因

1. **public リポジトリでありながら外部寄稿の受付方針が未記載**。イシューが公開されている以上、第三者（特に自律 AI エージェント）からの PR は今後も届く。方針が無いため、届くたびに個別判断とやり取りのコストが発生する。
2. **ハーネスが「PR は自前のもの」という暗黙前提で組まれている**。head リポジトリが origin と一致するかを検証する箇所がどこにも無いため、外部 PR がそのまま自分たちの手順（/close の base 追従・CI 承認）に流れ込む。手順側の注意書きだけでは今回のように見落とす。

### 解決方針

do（手順の明文化）と gate（決定論チェック）で対応する。gate はパスに依存しない層を含めて **script / hook / skill の 3 箇所**に置く。判定は全箇所とも `gh pr view <番号> --json isCrossRepository` を単一ソースとする。

**do 層**
- ルートに `CONTRIBUTING.md` を新設し、コードの寄稿（PR）を受け付けない方針とその理由（変更ごとに計画・テスト・レビューの記録を必須とする内部ワークフローで開発しており、`docs/runbooks/` と `.claude/` はレビュー AI の判断基準そのものであること）を明記する。イシュー（バグ報告・提案）は受け付けるが対応を約束しない旨を書き分ける。英語を先頭・日本語を後段に併記する。
- `.github/pull_request_template.md` に 1 行（外部からの PR は受け付けていない旨＋`CONTRIBUTING.md` へのリンク）を追加する。
- `SECURITY.md` を新設し、GitHub の Private vulnerability reporting へ誘導する（同機能を有効化する。メールアドレスは記載しない）。
- runbook に、外部 PR を見つけたときの扱い（Actions の実行承認をしない・base 追従や CI 対応をしない・方針コメント付きで close する）を記載する。

**gate 層**
- **script**: `scripts/claude/pr-base-sync.sh` の MODE 分岐より前に cross-repo チェックを追加し、fork 由来なら STOP（exit 1）する（fail-closed）。既存の `test_pr_base_sync.sh` にケースを追加する。
- **hook**: `scripts/claude/hooks/pretooluse_guard.py` に `gh pr` サブコマンド判定を追加する。`merge` は **block（exit 2）**、`ready` / `edit` / `review --approve` は **ask**（理由文言に fork 由来と head リポジトリ名を含める）、read-only（view/checks/diff）と `close` / `comment` / `review --comment` は素通し。`gh` 照会に失敗した場合は block ではなく **ask に降格**する。
- **skill**: `.claude/skills/close/SKILL.md` step 0 の既存 `gh pr view --json baseRefName` 照会に `isCrossRepository` を加え、`true` なら STOP する手順を明記する。

**なぜ 3 層必要か**: 今回の事故で /close は実行されていない（#257 は別ブランチの PR のため PR 自動検出には掛からない）。失敗の実体は調査中の思い込みであり、スキル経由のゲートだけでは同じ経路を止められない。ハーネスを経由するあらゆる操作を捕捉できるのは hook 層のみである（CLAUDE.md §3 の二重ガード方針に沿う）。

**残存ギャップ（明示）**: 読み取り中心の調査での思い込みそのものは hook でも止まらない（read-only 操作は素通しすべきであり、外部 PR を断るには `close` / `comment` も必要なため）。hook が止めるのは「外部 PR に /close を回す・マージする」というより重大な経路である。残りは do 層（runbook 記載）で埋める。

また、問題 3（fork PR の Actions 実行を承認してしまった）には決定論ゲートを置かない。承認は GitHub UI 上の操作でハーネスを経由せず、スクリプトからも hook からも捕捉できないためである。do 層（runbook への記載）のみで防ぐ。実害も CI の失敗表示に留まる。

## 制約・引き継ぎ情報
- `pr-base-sync.sh` は fail-closed 設計（取得失敗・未知値は STOP）で統一されている。追加するチェックもこの方針に揃えること。
- 終了コードの意味は既存と揃える: 0=続行OK / 1=STOP / 2=ユーザー確認。新しい終了コードは増やさない。
- 検証コマンドは複合形（`&&`・`||`・パイプ）にせず単体形で書く（`.claude/review-agents/plan-reviewer.md` の「コマンド衛生」観点）。
- `pretooluse_guard.py` は全 Bash 実行を通る共通経路であるため、**判定対象外のコマンドに余計な処理・ネットワーク照会を持ち込まない**こと（`gh pr <対象サブコマンド>` にマッチした場合のみ `gh` 照会を行う）。コマンドのトークナイズは既存 `_segments`（shlex ベース）を使い、素朴な `str.split()` を新規に持ち込まない。
- hook のテストは実 GitHub に依存させない。`test_pr_base_sync.sh` と同方式で `gh` スタブを PATH 先頭に挿す。
- 今回の事故の経緯詳細は PR #257 のコメントと本イシューの「現状の問題」に記録済み。
- 本イシューは track:harness だが、`.github/pull_request_template.md` と `CONTRIBUTING.md` / `SECURITY.md` はリポジトリ共通のため、隣 worktree（study-app-multitenant）側の作業と衝突しないタイミングで実施する。

- ただし GitHub リポジトリ設定の変更（Private vulnerability reporting の有効化）を 1 件含むため、実施前にユーザー承認を取る。無効化に戻す手順は `gh api -X DELETE repos/<owner>/<repo>/private-vulnerability-reporting`
