## 背景/目的

**背景**: #446 で全 API を順に呼ぶ横断のテストを作る途中で、`GET /api/dashboard/analytics/` が 500 になる場合を見つけた。組織の境界とは関係がないため #446 では直さなかった。#446 のテストの下準備では、日々のまとめの解いた問題数を 1 以上にしてこの不具合を避けている。そのままでは不具合が隠れるので起票する。
**目的**: 解いた問題が 0 件の日があっても、学習統計の画面が 500 にならずに表示される。0 件の日を含む場合を回帰テストで毎回確かめる。

### 現状の問題（証拠・再現手順）
- `backend/dashboard/views.py:246-255`（`_get_performance_trends`）は、週ごとの正答率の平均を `Avg(F('total_problems_correct') * 100.0 / F('total_problems_attempted'))` で出している
- 日々のまとめ（`DailyStudySummary`）に `total_problems_attempted = 0` の日が 1 日でもあると、データベースで 0 で割ることになり、応答が 500 になる（#446 の下調べで確かめた）
- 統計の画面（`frontend/src/pages/Statistics.tsx:72`）がこの API を呼ぶので、利用者に 500 が見える
- 再現: 解いた問題数が 0 の日のまとめを持つ利用者でログインし、学習統計の画面を開く（または `GET /api/dashboard/analytics/` を呼ぶ）

### 根本原因
割り算の分母が 0 になる日を除いたり守ったりしないまま、データベースの集計で正答率を計算している。日々のまとめは学習時間だけの日（問題を解かない日）にも作られうるため、分母が 0 の行が入る。その場合を通るテストが無かったので、気づかれていなかった。0 件の行は、学習記録の終了 API（`backend/studylogs/views.py` の `_update_daily_summary`）で問題を 0 問のまま記録を終えたときに作られる（grill-me で特定）。

### 解決方針
grill-me で確定（上の「設計確認メモ」）:
- 週ごとの正答率は「週の合計の正解数 ÷ 週の合計の解いた問題数 × 100」で出す（日ごとの正答率の平均はやめる）。分母は週の合計なので、0 件の日があっても 0 で割らない
- 週の合計が 0 問のときは `0` を返す（今までどおり）
- `days` の入力を確かめ、整数でない・1 未満・365 を超える値は 400 にする（省略時は 30）
