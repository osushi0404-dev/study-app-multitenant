## 設計確認メモ（/grill-me）
- Q: DB の扱いは?（旧「SQLite ロック競合」の正確性）→ A: **【docker-compose.yml 実査により訂正】** dev DB は SQLite ではなく **Postgres コンテナ + named volume**。`COMPOSE_PROJECT_NAME`（既定＝ディレクトリ名）ごとに named volume が分かれるため、worktree ごとに DB データは**自動分離**され共有・ロック競合は起きない。`db.sqlite3`（gitignore）は起動 dev DB ではない。runbook は「dev DB は Postgres・project 単位で自動分離」と記述する（旧「SQLite ロック競合」の記述は誤りのため撤回）。
- Q: `.env`（秘密情報）等の共有/非共有の整理は? → A: 非共有リストに backend `.env`（新 worktree では手動コピー要）を追加。共有リストに `.claude/settings.json`・tracked な frontend `.env.*`（`.env.development`/`.env.production`）を明記する。
- Q: 新 worktree 作成時のセットアップ手順を runbook に含めるか? → A: 含める。**ただし本プロジェクトは Docker Compose ベース**（`docker compose up -d`。依存は image に焼き込み・`node_modules` は frontend コンテナの匿名ボリューム・dev DB は Postgres コンテナ）であり、ホストの `venv`/`pip install`/`npm install` は使わない。よってセットアップは「backend `.env`（gitignore・非共有）を既存 worktree からコピー → `docker compose up -d`（正準手順は common-commands.md 参照）」を記載する。`COMPOSE_PROJECT_NAME` 既定＝ディレクトリ名のため worktree ごとにコンテナ/ボリューム（Postgres データ含む）は自動分離される。※本 A は初回グリルの「venv/pip/npm」記述を、docker-compose.yml 実査で判明した Docker 現実に合わせて訂正したもの。
- Q: worktree を並行運用する際の衝突点は? → A: **ホスト固定ポート（5432/6379/8000/3000/80/443）が衝突する**。override 無し・`COMPOSE_PROJECT_NAME` 未設定のため、2 つの worktree で同時に `docker compose up` するとポートが衝突する。現行の人手2トラック運用では**同時に up せず 1 スタックずつ**起動する（推奨）。同時起動が必要なら worktree ごとに compose override でポートと `COMPOSE_PROJECT_NAME` を変える（override 構築は本イシュー対象外＝別イシュー）。旧「SQLite ロック競合」は誤り（dev DB は Postgres・volume は project 単位で自動分離）で、真の衝突点はポートである。
- Q: runbook の記述構成は「純粋な一般手順のみ」か「一般手順＋現構成の具体例」か? → A: **2層**。手順本文は固有名に依存しない一般形で書き、末尾に「現時点のトラック構成（参考・日付つき）」を別枠で1ブロック付す。これで AC の「一般表現」と実行者の具体性を両立させる。
- Q: アプリ開発トラックの作業ツリーは既存 `study-app-multitenant` か新設 `wt-app` か? → A: **既存の `study-app-multitenant`（primary checkout＝採番権威）をそのまま使う**。`wt-app` は新設しない。`wt-<track>` 命名ルールは追加で生やす linked worktree（例 `wt-harness`）にのみ適用する。

## 背景/目的

### 現状の問題（証拠・再現手順）
「バイブコーディングの仕組み改善」トラックと「学習アプリ開発」トラックを**並行で**進めたいが、標準手順が docs に無く属人化している。単一作業ツリーでブランチを切り替える方式には以下の問題がある:
- 片方の未コミット変更がもう片方の作業を妨げる（同じ作業ツリーを奪い合う）。
- 1つのセッションで両トラックを扱うとコンテキストが混在し、計画・成果物がぶれる。
- セッションをまたぐ引き継ぎを**チャット上の口頭メモ**で行うと、メモ漏れで受け手セッションがぶれ、記録が `docs/` に残らず憲法5「記録が残る形」に反する。

実際に本イシューの起票準備中、worktree を **`main` から**作成してしまい（`main` は初期コミット `Initialize README` で停止・実体は `develop` に集約）、テンプレート・スクリプト・runbook・アプリコードが一切無い空ツリーが生成される事故が発生した。手順が docs 化されていれば防げた。

### 根本原因
- トラック並行運用の標準手順（worktree の作り方・**ベースブランチの選択**・トラック/ブランチ設計・環境の非共有点）が未整備。
- 「セッション間の引き継ぎは口頭でなく**イシュー/計画/レビューのファイル経由（自己完結）**で行う」という原則が明文化されておらず、人（メモを書く担当）がボトルネックになる構造が放置されている。

抽象化: 「並行する作業トラックを、作業ツリーとセッションの分離＋ファイルベースの引き継ぎで無損失に扱う運用が未定義」という一般問題。

### 解決方針
`docs/runbooks/worktree.md` を新規作成し、CLAUDE.md の参照先リストに1行追加する。runbook には以下を含める:
1. トラック単位で git worktree を分離する運用（`git worktree add/list/remove`）。**ベースブランチは `develop`**（`main` は初期コミットのため使わない）を明記。
2. トラック設計: トラック単位で作業ツリー、その中でイシュー単位にブランチを切る。アプリ開発トラックは既存の primary checkout（`study-app-multitenant`＝採番権威）を使い、追加トラックは `wt-<track>` 名の linked worktree（例 `wt-harness`）として生やす。`wt-app` は新設しない。
3. 各 worktree ディレクトリで**独立した Claude セッション**を起動する手順（Cursor/VSCode での別ウィンドウの開き方を含む）。
4. 注意点: worktree 間で**共有されるもの**（`.git` 履歴・コミット済みファイル・CLAUDE.md・`docs/runbooks`・`.claude/settings.json`・tracked な frontend `.env.*`）と**共有されない/手当てが要るもの**（backend `.env`＝gitignore・要コピー、`e2e/.env.e2e`＝任意、未コミット/untracked）。依存・`node_modules` は**コンテナ管理**（image・frontend の匿名ボリューム `/app/node_modules`）でホスト共有の対象外。dev DB は **Postgres コンテナ + named volume** で `COMPOSE_PROJECT_NAME`（既定＝ディレクトリ名）ごとに自動分離される（`db.sqlite3` は gitignore 対象だが起動 dev DB ではない）。WSL 表示確認。
5. **採番の一貫性**: 起票済みイシューを untracked のまま放置すると他 worktree から不可視になり採番が食い違う。採番は権威となる作業ツリー（未コミット分が見える場所）で行うか、起票後すみやかに develop に取り込む。
6. **セッション間引き継ぎ原則**: 口頭メモを禁止し、引き継ぎはイシュー/計画/レビューのファイルに自己完結で記述する（文脈ゼロのセッションが同じ結論に到達できる状態を必須とする）。
7. **新 worktree のセットアップ手順**: backend `.env`（gitignore・非共有）を既存 worktree からコピー → `docker compose up -d`（正準手順は `common-commands.md` 参照）。ホストの `venv`/`pip install`/`npm install` は不要（依存はコンテナ管理）。E2E を行う場合は `e2e/.env.e2e` も用意。
8. **並行実行の衝突（重要）**: ホスト固定ポート（5432/6379/8000/3000/80/443）のため、2 worktree で同時に `docker compose up` するとポートが衝突する。現行運用では**同時に up せず 1 スタックずつ**起動（推奨）。同時起動が必要なら worktree ごとに compose override でポート＋`COMPOSE_PROJECT_NAME` を変える（override 構築は本イシュー対象外）。
9. **記述構成（2層）**: 手順本文は固有名に依存しない一般形で書き、末尾に「現時点のトラック構成（参考・日付つき）」を別枠で1ブロック付す（一般表現の AC と実行者の具体性を両立）。

### 含む
- `git worktree add / list / remove` の手順、ベースブランチ＝`develop` の明記、トラック/ブランチ設計（アプリ開発＝既存 primary checkout `study-app-multitenant`、追加トラック＝`wt-<track>` の linked worktree。`wt-app` は新設しない）。
- runbook の記述構成: 手順本文は一般形＋末尾に「現時点のトラック構成（参考・日付つき）」の2層。

- 新 worktree のセットアップ手順（backend `.env` コピー → `docker compose up -d`。ホストの venv/pip/npm install は不要＝依存はコンテナ管理。正準手順は common-commands.md 参照）。
- 並行実行の衝突（ホスト固定ポート 5432/6379/8000/3000/80/443 の衝突・同時 up 不可・1 スタックずつ／override は別イシュー）。
- 注意点: 共有される `.git`/コミット済みファイル/CLAUDE.md/`.claude/settings.json`/tracked な frontend `.env.*`、非共有で手当てが要る backend `.env`（コピー）・untracked、コンテナ管理（node_modules は匿名ボリューム・依存は image）、dev DB は Postgres コンテナ+named volume で COMPOSE_PROJECT_NAME 単位に自動分離、WSL 表示確認。
- 採番一貫性の注意（untracked イシューの worktree 間不可視）。
- セッション間引き継ぎ＝イシュー/計画/レビューのファイル経由（自己完結原則）の明文化。
### 含まない
- worktree ごとの compose override（ポート/`COMPOSE_PROJECT_NAME` 分離による同時 `docker compose up`）の仕組み構築（必要なら別イシュー）。
- CI・自動化・worktree 生成のスクリプト化（本イシューは手順の docs 化に限定）。
- Agent ツールの `isolation: "worktree"` 等ハーネス内 worktree 機能の運用（人間の長期並行が対象）。
