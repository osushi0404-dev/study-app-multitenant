## 設計確認メモ（/grill-me）
- Q: SQLite/DB の扱いは?（本文の「SQLite ロック競合」の正確性）→ A: `db.sqlite3` は gitignore 対象で **worktree ごとに独立**（共有されない）。本ハーネス worktree は DB を参照しない想定。よって「共有による DB ロック競合」は考慮不要とし、runbook は「DB は worktree ごとに独立・共有しない」と記述する（アンチパターン的に 1 DB を共有した場合のみ競合が起きる点は補足に留める）。
- Q: `.env`（秘密情報）等の共有/非共有の整理は? → A: 非共有リストに backend `.env`（新 worktree では手動コピー要）を追加。共有リストに `.claude/settings.json`・tracked な frontend `.env.*`（`.env.development`/`.env.production`）を明記する。
- Q: 新 worktree 作成時のセットアップ手順を runbook に含めるか? → A: 含める。venv 作成 + `pip install`、`npm install`、backend `.env` の手動コピー等の再セットアップ手順を記載する（`migrate` 等 DB 手順はアプリトラックのみ条件付き。共有機構の構築は引き続き対象外＝手順の docs 化に限定）。
- Q: runbook の記述構成は「純粋な一般手順のみ」か「一般手順＋現構成の具体例」か? → A: **2層**。手順本文は固有名に依存しない一般形で書き、末尾に「現時点のトラック構成（参考・日付つき）」を別枠で1ブロック付す。これで AC の「一般表現」と実行者の具体性を両立させる。
- Q: アプリ開発トラックの作業ツリーは既存 `study-app-multitenant` か新設 `wt-app` か? → A: **既存の `study-app-multitenant`（primary checkout＝採番権威）をそのまま使う**。`wt-app` は新設しない。`wt-<track>` 命名ルールは追加で生やす linked worktree（例 `wt-harness`）にのみ適用する。

## 背景/目的

### 現状の問題（証拠・再現手順）
「バイブコーディングの仕組み改善」トラックと「学習アプリ開発」トラックを**並行で**進めたいが、標準手順が docs に無く属人化している。単一作業ツリーでブランチを切り替える方式には以下の問題がある:
- 片方の未コミット変更がもう片方の作業を妨げる（同じ作業ツリーを奪い合う）。
- 1つのセッションで両トラックを扱うとコンテキストが混在し、計画・成果物がぶれる。
- セッションをまたぐ引き継ぎを**チャット上の口頭メモ**で行うと、メモ漏れで受け手セッションがぶれ、記録が `docs/` に残らず憲法5「記録が残る形」に反する。

実際に本イシューの起票準備中、worktree を **`main` から**作成してしまい（`main` は初期コミット `Initialize README` で停止・実体は `develop` に集約）、テンプレート・スクリプト・runbook・アプリコードが一切無い空ツリーが生成される事故が発生した。手順が docs 化されていれば防げた。

### 根本原因
- トラック並行運用の標準手順（worktree の作り方・**ベースブランチの選択**・トラック/ブランチ設計・環境の非共有点）が未整備。
- 「セッション間の引き継ぎは口頭でなく**イシュー/計画/レビューのファイル経由（自己完結）**で行う」という原則が明文化されておらず、人（メモを書く担当）がボトルネックになる構造が放置されている。

抽象化: 「並行する作業トラックを、作業ツリーとセッションの分離＋ファイルベースの引き継ぎで無損失に扱う運用が未定義」という一般問題。

### 解決方針
`docs/runbooks/worktree.md` を新規作成し、CLAUDE.md の参照先リストに1行追加する。runbook には以下を含める:
1. トラック単位で git worktree を分離する運用（`git worktree add/list/remove`）。**ベースブランチは `develop`**（`main` は初期コミットのため使わない）を明記。
2. トラック設計: トラック単位で作業ツリー、その中でイシュー単位にブランチを切る。アプリ開発トラックは既存の primary checkout（`study-app-multitenant`＝採番権威）を使い、追加トラックは `wt-<track>` 名の linked worktree（例 `wt-harness`）として生やす。`wt-app` は新設しない。
3. 各 worktree ディレクトリで**独立した Claude セッション**を起動する手順（Cursor/VSCode での別ウィンドウの開き方を含む）。
4. 注意点: worktree 間で**共有されないもの**（venv・node_modules・ビルド成果物・backend `.env`・**未コミット/untracked ファイル**）と**共有されるもの**（`.git` 履歴・コミット済みファイル・CLAUDE.md・`docs/runbooks`・`.claude/settings.json`・tracked な frontend `.env.*`）。**DB(`db.sqlite3`) は gitignore 対象で worktree ごとに独立（共有しない）ため DB ロック競合は考慮不要**（1 DB を意図的に共有した場合のみ競合が起きる旨は補足）。WSL 表示確認。
5. **採番の一貫性**: 起票済みイシューを untracked のまま放置すると他 worktree から不可視になり採番が食い違う。採番は権威となる作業ツリー（未コミット分が見える場所）で行うか、起票後すみやかに develop に取り込む。
6. **セッション間引き継ぎ原則**: 口頭メモを禁止し、引き継ぎはイシュー/計画/レビューのファイルに自己完結で記述する（文脈ゼロのセッションが同じ結論に到達できる状態を必須とする）。
7. **新 worktree のセットアップ手順**: venv 作成 + `pip install`、`npm install`、backend `.env` の手動コピー（`migrate` 等 DB 手順はアプリトラックのみ条件付き）。
8. **記述構成（2層）**: 手順本文は固有名に依存しない一般形で書き、末尾に「現時点のトラック構成（参考・日付つき）」を別枠で1ブロック付す（一般表現の AC と実行者の具体性を両立）。

## スコープ
### 含む
- `git worktree add / list / remove` の手順、ベースブランチ＝`develop` の明記、トラック/ブランチ設計（アプリ開発＝既存 primary checkout `study-app-multitenant`、追加トラック＝`wt-<track>` の linked worktree。`wt-app` は新設しない）。
- runbook の記述構成: 手順本文は一般形＋末尾に「現時点のトラック構成（参考・日付つき）」の2層。
- 各ディレクトリで独立 `claude` セッションを起動する手順、Cursor で別フォルダを別ウィンドウで開く方法（同一フォルダ再オープンは既存ウィンドウにフォーカスが戻るだけ、という落とし穴の明記を含む）。
- 新 worktree のセットアップ手順（venv 作成 + `pip install`・`npm install`・backend `.env` の手動コピー。DB マイグレーション等はアプリトラックのみ条件付き）。
- 注意点: 環境（venv/node_modules/ビルド成果物/backend `.env`/untracked ファイル）非共有、共有される `.git`/コミット済みファイル/CLAUDE.md/`.claude/settings.json`/tracked な frontend `.env.*`、DB(`db.sqlite3`) は worktree ごとに独立で共有しない（ロック競合は考慮不要）、WSL 表示確認。
- 採番一貫性の注意（untracked イシューの worktree 間不可視）。
- セッション間引き継ぎ＝イシュー/計画/レビューのファイル経由（自己完結原則）の明文化。
### 含まない
- venv・node_modules・DB を worktree 間で共有する仕組みの構築（必要なら別イシュー）。
- CI・自動化・worktree 生成のスクリプト化（本イシューは手順の docs 化に限定）。
- Agent ツールの `isolation: "worktree"` 等ハーネス内 worktree 機能の運用（人間の長期並行が対象）。
