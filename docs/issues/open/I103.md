# I103: 問題作成時の越境subject書き込みを防止（perform_create に組織検証を追加・update の SEC-1 と対称化）

## 関連資料
- GitHub Issue: #193
- 発見経緯: I102（問題管理の更新系を組織管理者権限に限定）の `/grill-me` 中に判明した、テナント境界の create 側欠落。role ベース認可（I102）とは別軸のため分離。
- 関連イシュー: I102（#192）で更新系は組織管理者（`role == 'admin'`）限定済み。本 I103 はその上で「他組織の subject への越境書き込み」を塞ぐ。

## 設計確認メモ（/grill-me）
- Q: AI生成経路（generate_ai/generate_adaptive）の同型越境穴も本イシューで塞ぐか？ → A: **含める**。`generate_ai`（views.py:373）・`generate_adaptive`（:496）も `Subject.objects.get(id=subject_id)` を**組織フィルタ無し**で取得し、その subject 配下に問題を作成する（`_save_ai_problem_to_db`→`Problem(subject=subject)`）＝`perform_create` と同一の越境穴。I102 で AI生成も admin 限定になったため脅威モデルは同一。よって**3経路（perform_create / generate_ai / generate_adaptive）**すべてで `subject.organization_id != request.user.organization_id` を拒否し、テストも3経路で越境=拒否を担保する。
- Q: 越境拒否時の HTTP status は？（当初 400 案） → A: **403 に確定**。同一 ViewSet 内で越境拒否 status が既に割れており（`upload_image`:612-616・`delete_image`:729-733＝**403** / `perform_update` SEC-1:296-299＝400）、**403 が既存多数派**。403（認可拒否）に収束させる。実装: `perform_create` は `rest_framework.exceptions.PermissionDenied('他組織の科目には問題を作成できません')`（→403）で拒否（当初 `DRFValidationError`＝400 から変更）。`generate_ai`/`generate_adaptive` は subject 取得後に org 一致チェックを追加し `Response({'error': '他組織の科目には問題を作成できません'}, status=403)` を返す。
- Q: `perform_update` の SEC-1（越境 subject 付け替え・現状400）が残ると不整合では？ → A: **SEC-1 の 400→403 統一は別イシュー**（越境拒否=403 をコードベース規約として明文化）。理由: SEC-1 の変更は `test_I073_image_update.py` の 400 アサート7箇所（:323,345,357,372,461,476,567）を巻き込むため、create 側の穴塞ぎ（本 I103）に混ぜるとスコープが濁る。**本 I103 の間は create/AI=403・update=400 の一時的不整合を許容**し、別イシュー（issue-bootstrap 候補）で収束する。
- Q: 「SEC-1 と対称化」という当初フレーミングは？ → A: **status までの対称は主張しない**（SEC-1 は当面 400）。本質は「**同一の検証ロジック**（`subject.organization_id != user.organization_id`）で create 側3経路の越境を拒否する」こと。status は 403（upload/delete と一致）。
- Q: `ProblemSerializer.subject` の queryset 組織絞り込み（二重防御）は？ → A: **本イシューでは実装しない**（当初方針を維持）。3経路の明示チェックで越境は確実に塞げるため。将来必要なら別途。
- Q: `generate_ai` の `save_to_db=False`（非永続プレビュー生成・views.py:403-414）でも org チェックを効かせるか？ → A: **効かせる**。`save_to_db` の値に関わらず、subject 取得直後（generation の前）に**無条件で** org 一致チェックを行い、越境なら生成前に 403 で弾く（DB 越境注入が無くても、他組織 subject の存在露呈＋AI クォータ消費はテナント境界逸脱のため）。`generate_adaptive` は常に永続なので元から対象。※Problem を作成する API 経路はこの3経路で全て（`upload_image` は MediaAsset 作成で org=403 検証済み・quiz 系は Problem 非作成）。

## 背景/目的

### 現状の問題（証拠・再現手順）
問題作成 API（`POST /api/problems/`）で、**組織管理者が自組織以外の科目（subject）に問題を作成できてしまう**（マルチテナント境界の越境書き込み）。

証拠:
- `backend/problems/views.py` の `perform_create`（:232〜）に **subject の組織検証が無い**。一方 `perform_update`（:277〜）には SEC-1 検証（:294-297）があり、`new_subject.organization_id != request.user.organization_id` なら `他組織の科目には変更できません` で拒否している。→ **create 側だけ非対称に無防備**。
- `backend/problems/serializers.py` の `ProblemSerializer.subject` は既定の `PrimaryKeyRelatedField`（queryset 未絞り込み）で、**全組織の Subject を受理**する。

再現:
1. 組織 A の管理者（`role='admin'`）で認証する。
2. `POST /api/problems/` に、組織 B に属する `subject`（subject_id）を指定して問題を作成する。
3. 検証が無いため作成が成功し、組織 B の科目配下に組織 A 管理者が作った問題が注入される（組織 B のユーザーがその問題を閲覧・出題される）。

### 根本原因
`perform_update` に存在する subject の組織一致検証（SEC-1）が **`perform_create` には実装されていない**。加えて `ProblemSerializer.subject` の queryset が組織で絞られていないため、シリアライザ段階でも他組織 subject を弾けない。作成・更新でテナント境界の担保に非対称がある。

### 解決方針
**問題を作成する全経路で subject の組織一致を検証**し、越境書き込みを **403** で拒否する（`perform_update` の SEC-1 と**同一の検証ロジック**）。
- **3経路すべてに org 一致チェックを追加**する（判定は `subject.organization_id != request.user.organization_id`）:
  - `perform_create`: 越境なら `PermissionDenied('他組織の科目には問題を作成できません')`（→**403**）で拒否。
  - `generate_ai`（views.py:373）: `Subject.objects.get(id=subject_id)` 取得後・生成前に org 一致チェックを追加し、越境なら（`save_to_db` の値に関わらず一律）`Response({'error': '他組織の科目には問題を作成できません'}, status=403)`。
  - `generate_adaptive`（views.py:496）: 同上。
- **status は 403**（認可拒否）。同一 ViewSet の `upload_image`/`delete_image` が既に越境=403 を返しており、それに揃える。`perform_update` SEC-1 は現状 400 だが、**その 400→403 統一は別イシュー**（越境拒否=403 の規約化）とし、本イシューの間は create/AI=403 / update=400 の一時的不整合を許容する。
- `ProblemSerializer.subject` の queryset を組織で絞る二重防御方式は **本イシューでは実装しない**（serializer への request context 受け渡しが必要でコストが増える割に、3経路の明示検証で越境は確実に塞げるため）。将来必要なら別途検討。
- 前提: 更新系・AI生成は I102 で管理者（`role == 'admin'`）限定済み。したがってこの穴を突けるのは管理者のみだが、**他組織の管理者による越境注入**を塞ぐ。

## スコープ
### 含む
- 問題作成3経路（`perform_create` / `generate_ai` / `generate_adaptive`）の subject 組織一致検証（他組織 subject への問題作成・AI生成を **403** で拒否）
- 上記の回帰テスト（3経路とも越境=403拒否 / 自組織=成功）
### 含まない
- **`perform_update` SEC-1 の 400→403 統一（越境拒否 status の規約化）＝別イシュー**（`test_I073_image_update.py` の 400 アサート7箇所を巻き込むため分離。本イシューの間は create/AI=403・update=400 の一時的不整合を許容）
- 更新系の admin 限定・FE ガード（I102 で対応済み）
- `is_correct` の表示・露出（I078）
- 画像アップロード等、subject 以外の越境検証（`upload_image`/`delete_image` は既に `problem.organization_id != request.user.organization_id` を 403 で検証済み＝対象外）
- `SubjectViewSet` 等、問題以外のリソースのテナント境界

## 関連する品質基準
- C2 プライバシー/情報露出・マルチテナント境界 — 他組織のデータ空間への書き込みを構造的に禁止する。
- C1 正確性/信頼性 — 作成と更新でテナント境界の担保を対称化し、認可の抜けをなくす。

## 受け入れ条件（Acceptance Criteria）
- [ ] 組織 A の管理者が組織 B の `subject` を指定して `POST /api/problems/` を実行すると **403**（`他組織の科目には問題を作成できません` 相当）で拒否される
- [ ] 組織 A の管理者が組織 B の `subject_id` で `generate_ai`（`save_to_db` の True/False 双方）/ `generate_adaptive` を実行すると **403** で拒否される
- [ ] 組織 A の管理者が自組織の `subject` で問題作成・AI生成すると従来どおり成功する（201 / 200）
- [ ] 3経路の検証がいずれも同一の判定（`subject.organization_id != request.user.organization_id`）で越境を拒否している
- [ ] 上記を検証する回帰テスト（3経路とも越境=403 / 自組織=成功）が追加され全て PASS する

## 影響範囲（想定）

- Frontend: なし
- DB: なし
- Config/Infra: なし

## 制約・引き継ぎ情報
- I102 の `/grill-me` で発見。role ベース認可（I102）とは別軸（テナント境界）のため分離。
- `perform_update` の SEC-1 検証は `backend/problems/views.py:296-299` に既存（越境 subject 付け替えを 400 で拒否）。本イシューは create 側3経路に**同一の検証ロジック**を追加するのが本質（status は 403＝`upload_image`/`delete_image` と一致）。
- **越境拒否 status の不整合**: 同一 ViewSet で upload/delete=403・SEC-1=400 と割れている。本イシューは create/AI を 403 で追加し、SEC-1 の 400→403 統一は**別イシュー**（`test_I073_image_update.py` の 400 アサート7箇所を巻き込むため分離。issue-bootstrap 候補）。
- 前提: 更新系・AI生成は I102 で `role == 'admin'` 限定済み。本イシューは「管理者間の越境」を塞ぐ差分。
