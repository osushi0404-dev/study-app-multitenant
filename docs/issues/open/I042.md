# I042: /implement スキルに新規実装向け TDD ガイドを追加する

## 関連資料
- GitHub Issue: #88

## 設計確認メモ（/grill-me）
- Q: TDD は「強制停止」か「ガイド案内」か → A: 強制停止（テストを先に書かなければ作業を止めて待機）
- Q: Red フェーズで Claude はテストを実際に実行するか → A: pytest / npm test を実行して失敗を確認してから Green フェーズへ進む
- Q: フロントエンド（Jest）も TDD 対象に含めるか → A: 含める（Backend・Frontend ともに対象）

## 背景/目的

**背景**: /implement スキルに TDD サイクルの回し方が明示されておらず、テストを後付けで書く習慣を防げない状態だった。
**目的**: 新規の振る舞い追加時に Red→Green→Refactor を強制する TDD ガイドを /implement に追記し、auto_test 仕様を実装前から活用する流れを標準化する。

- 現在の `/implement` スキルは実装手順のみを記載しており、新規機能実装時に TDD（Test-Driven Development）サイクルをどう回すか明示されていない
- テストを後付けで書く習慣を防ぎ、`docs/tests/open/$ARGUMENTS_auto_test.md` に記載された自動テスト仕様を実装前から活用する流れを標準化したい
- 新規の振る舞い（エンドポイント・ビジネスロジック）を追加する場合に絞って TDD サイクル（Red → Green → Refactor）の手順を `/implement` スキルに追記する

## スコープ
### 含む
- `/implement` スキルの `手順` セクションへの TDD ガイド追記（新規振る舞い追加時のステップとして）
- `$ARGUMENTS_auto_test.md` の内容を先に読んでテストを先行実装する指示
- Red（テスト先行実装 → 失敗確認）→ Green（最小実装 → テスト通過）→ Refactor（内部整理のみ）のサイクル明示
- Refactor フェーズの範囲定義：可読性改善・重複削除のみ。新機能追加や設計変更は計画書更新が必要な旨を明記
- 認証・認可・テナント境界を検証するテストを Red フェーズに含める旨の明示
- `/test` スキルとの役割分担の注記（実装中の実行 vs 最終確認）
- 既存コード変更（バグ修正・リファクタ）では TDD ガイドを任意扱いにする注記
- `/issue-bootstrap` スキルのステップ6報告テンプレートに `/grill-me` を次のステップとして追記（`workflow.md` との乖離を解消）

### 含まない
- テストテンプレートの変更
- `test` スキルの変更
- 既存イシューの実装への遡及適用

## 受け入れ条件（Acceptance Criteria）
- [ ] `/implement` スキルの手順に「新規の振る舞い追加の場合は TDD サイクルを回す」ステップが追加されている
- [ ] 「新規の振る舞い」の定義（エンドポイント・ビジネスロジックの追加）が明示されている
- [ ] Red フェーズ（テスト先行実装 → 失敗確認）・Green フェーズ（最小実装 → テスト通過）・Refactor フェーズが明記されている
- [ ] Refactor フェーズの範囲（内部整理のみ・新機能や設計変更は計画書更新が必要）が明記されている
- [ ] 認証・認可・テナント境界を検証するテストを Red フェーズに含める旨が明示されている
- [ ] `/test` スキルとの役割分担（実装中の実行 = サイクル確認、`/test` = 最終確認）が注記されている
- [ ] 既存コード変更（バグ修正・リファクタ）は TDD 必須でない旨が注記されている
- [ ] `$ARGUMENTS_auto_test.md` を参照してテストを書く流れが明示されている
- [ ] `/issue-bootstrap` スキルのステップ6報告テンプレートに `/grill-me` の案内が追加されており、`workflow.md` の「イシュー承認後」の振る舞いと一致している

- Frontend: なし
- DB: なし
