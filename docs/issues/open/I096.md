## 設計確認メモ（/grill-me）
- Q: 撤去の `docker compose down -v` ゲート方式（無条件消去の禁止・二重ガード整合） → A: **`DANGER_OK=1` 必須**。`wt-remove.sh` は内部で `$DANGER_OK` を検査し、未設定なら `down -v` を実行せず明示エラーで停止（`scripts/db_backup.sh` を案内）。既存 `pretooluse_guard.py` の `DANGER_OK=1` 契約と同一にし、Claude が `bash wt-remove.sh` 経由で無言に volume を消す抜けを塞ぐ。対話プロンプトは非対話フローを壊すため不採用。`--purge-volumes` 既定 OFF 案は §5D の volume 漏れ（消し忘れ）を再導入するため不採用。
- Q: `.env` コピー元（source）の決め方 → A: **primary checkout（`git worktree list` の先頭エントリ）の `backend/.env` を既定 source**（絶対パス直書きせず先頭から導出＝決定論的・環境非依存）。`--env-source <path>` で上書き可。source 欠落時は**ハードエラーで停止**（無言の自動検出はしない＝別 worktree の改変済み secrets 誤コピーの非決定性を避ける）。`e2e/.env.e2e` は source に在れば同様コピー・無ければ非致命。中身は読まず `cp`+`test -f` のみ。
- Q: 未 push/未コミットの worktree 撤去時の挙動 → A: **`git worktree remove` の前に (1) 未コミット変更（`git status --porcelain` 非空）(2) 未 push コミット（upstream/origin に無い commit）を検出したら明示メッセージで中止**。`--force` は使わない。git 既定は dirty を弾くが clean-but-unpushed を弾かず作業消失し得るため機械化で塞ぐ。
- Q: `docker compose up` の既定 → A: **既定 OFF・`--up` で opt-in**。§6 の同時 up ポート衝突・1 スタック運用と整合。同時起動の仕組み化は I097。
- Q: `COMPOSE_PROJECT_NAME` global export 検出の扱い → A: **警告のみ**（停止しない・軽微・同梱）。
- Q: テスト方式（Docker 非依存性） → A: 一時 git リポジトリ＋linked worktree を実生成し、基点固定・`.env` コピー/欠落停止・撤去順序（`down -v`→`remove`）・`DANGER_OK` ゲート・未 push 中止を検証。`docker` はスタブ（呼び出し順序を記録するダミー）で **Docker デーモン非依存**にする。
- Q: `wt-new` の引数フォーマットと検証 → A: `wt-new <track> <番号> <概要>`。**番号=数字のみ**（例 `096`・`I` 接頭辞はスクリプトが付与し `feature/I096-<概要>` を構成）。`track`/`概要` は **`[A-Za-z0-9._-]` のみ許可**し、空白・不正文字は**明示エラーで停止**（曖昧な slug 自動変換はしない＝決定論的・無言変換なし）。
- Q: worktree path / branch が既に存在する場合 → A: `git worktree add` の生失敗に委ねず、**事前に path 存在・branch 存在を検査して原因を明示したエラーで停止**（誤解のない fail-fast）。
- Q: worktree の base ディレクトリ → A: `/mnt/c/app` を直書きせず **primary checkout root の親（`dirname`）から導出**し `<base>/wt-<track>` とする（環境非依存・決定論的。primary は `git worktree list` 先頭）。
- Q: `COMPOSE_PROJECT_NAME` 検出方法 → A: スクリプト実行環境で当該変数が**非空にセットされていれば警告**（`${COMPOSE_PROJECT_NAME:-}` 判定）。§5C の global export 検出目的に合致。

## 背景/目的

### 現状の問題（証拠・再現手順）
worktree の作成・撤去が**手動多段**で、runbook が自ら「重大」「静かに壊れる」と警告する foot-gun が未ガードのまま人手規律に委ねられている（`worktree.md`）:
- **§3 重大**: `git worktree add` の基点を `origin/develop` にしないと（例えば `main`）、テンプレート・スクリプト・アプリコードの無い**空ツリー**ができる。
- **§5B 静かに壊れる**: backend `.env` は `env_file` の `required: false` 参照のため、コピー忘れでも `docker compose up` は**失敗せず**、`SECRET_KEY`/`DB_PASSWORD` が insecure な既定値のまま**静かに起動**する。
- **§5D volume 漏れ**: 撤去時に当該ディレクトリで `docker compose down -v` を実行してから `git worktree remove` しないと、named volume（Postgres データ含む）が残留・累積する。
- **§5C 分離崩壊**: `COMPOSE_PROJECT_NAME` を global export すると worktree ごとの分離が壊れる。

いずれも「手順書に注意書きがある」だけで、**実行時に守られたかを検証・強制する仕組みが無い**。

### 根本原因
worktree の作成〜起動〜撤去という**定型ワークフローがスクリプト化されておらず**、各 foot-gun 回避が個別の人手手順として散在している。定型作業が自動化されていないため、注意書きの見落とし一つで静かに壊れる。

### 解決方針
worktree lifecycle を束ねる**ヘルパースクリプト**を `scripts/claude/` 系に追加し、foot-gun を機械化で不可能化・自動化する:
1. **`wt-new <track> <番号> <概要>`（作成）**: 引数検証（番号=数字のみ・`track`/`概要` は `[A-Za-z0-9._-]` のみ、不正は明示エラー）→ worktree path（`<base>/wt-<track>`・base は primary checkout root の親から導出）と branch（`feature/I<番号>-<概要>`）の既存を事前検査し衝突は明示エラーで停止 → `git fetch origin` → `git worktree add <base>/wt-<track> -b feature/I<番号>-<概要> origin/develop`（**基点を origin/develop に固定**＝§3 重大の回避）→ backend `.env` を **primary checkout（`git worktree list` 先頭）の `backend/.env`** から新 worktree 配下へ `cp`（`--env-source` で上書き可）し**存在を検証**（欠落/コピー失敗なら明示エラーで停止＝§5B の回避）→ **既定では up せず、`--up` 指定時のみ** `docker compose up -d`。
2. **`wt-remove <track>`（撤去）**: 撤去前チェック（未コミット変更・未 push コミットを検出したら `--force` を使わず明示メッセージで中止）→ 当該ディレクトリで `docker compose down -v`（**`DANGER_OK=1` 必須**・未設定なら実行せず停止＝二重ガード整合／§5D）→ 元ディレクトリへ戻って `git worktree remove`。
3. **`COMPOSE_PROJECT_NAME` の global export 検出**（§5C）: スクリプト実行環境で当該変数が非空（`${COMPOSE_PROJECT_NAME:-}`）なら警告する（軽微・同梱）。

## スコープ
### 含む
- 作成スクリプト（基点 origin/develop 固定・`.env` source=primary（`git worktree list` 先頭）既定＋`--env-source` 上書き・存在検証・up は既定 OFF/`--up` opt-in）。
- 撤去スクリプト（撤去前チェックで未コミット/未 push を検出したら `--force` 不使用で中止 → `down -v`（`DANGER_OK=1` 必須ゲート）→ `remove` の順序保証）。
- `COMPOSE_PROJECT_NAME` global export の検出警告。
- `.env` 欠落/コピー失敗時に**明示エラーで停止**する検証（silent 起動の防止）。
- スクリプトの自動テスト（Docker デーモン非依存・`docker` スタブ）と runbook 更新。

### 含まない
- 同時スタック起動のためのポート/プロジェクト名 override（→ I097 で扱う）。
- Docker/Compose 以外の環境への一般化。
- Windows ネイティブ（非 WSL）シェル対応。

## 受け入れ条件（Acceptance Criteria）
- [ ] 作成スクリプトが引数検証（番号=数字・`track`/`概要` は許可文字のみ）と worktree path/branch の既存衝突検査を行い、不正時は明示エラーで停止する
- [ ] worktree の作成先は primary checkout の親ディレクトリから導出する（`/mnt/c/app` を直書きしない）
- [ ] 作成スクリプトが基点を `origin/develop` に固定し、`main` 等の誤基点で空ツリーを作れない
- [ ] 作成スクリプトが backend `.env` を primary checkout（`git worktree list` 先頭）から新 worktree 配下へコピーし、欠落/コピー失敗時は**明示エラーで停止**する（insecure 既定値での静かな起動を防ぐ）／`--env-source` で source を上書きできる
- [ ] 作成スクリプトは既定で `up` せず、`--up` 指定時のみ `docker compose up -d` する
- [ ] 撤去スクリプトが撤去前に未コミット変更・未 push コミットを検出したら `--force` を使わず中止する
- [ ] 撤去スクリプトの `docker compose down -v` は `DANGER_OK=1` 未設定時は実行されず明示エラーで停止する（設定時のみ実行）
- [ ] 撤去スクリプトが `docker compose down -v`（当該ディレクトリ）→ `git worktree remove` の順で実行する
- [ ] `COMPOSE_PROJECT_NAME` が global export されている場合に警告が出る
- [ ] 上記を検証する自動テストが `scripts/claude/tests/` に追加され PASS（Docker デーモン非依存＝`docker` スタブで検証）
- [ ] `docs/runbooks/worktree.md` §3/§5 がスクリプト利用手順に更新されている（手動手順は fallback として保持）

## 影響範囲（想定）
- Backend: なし（`.env` の**コピー**のみ・中身は変更しない）
- Frontend: なし
- DB: なし（named volume の回収は既存 danger-ops 手順に従う）
- Config/Infra: `scripts/claude/`・`docs/runbooks/worktree.md`
- 参照のみ（本イシューでは新規作成・改変しない）: `e2e/.env.e2e`（source に在れば作成スクリプトが `cp` する対象・中身は読まない）／`scripts/db_backup.sh`（撤去前の任意バックアップとして案内するのみ）

## 制約・引き継ぎ情報
- `docker compose down -v` は danger-ops（`pretooluse_guard.py` が `DANGER_OK=1` を要求）。撤去スクリプトはこの二重ガードと整合させること（スクリプト内で無条件に volume を消さない・撤去は明示操作として扱う）。
- `.env` は gitignore 対象かつ deny リスト（`Read/Edit/Write(./.env*)`）。スクリプトは**中身を読まず**にコピー（`cp`）と**存在確認**（`test -f`）のみ行い、フックの deny と衝突しない実装にすること。
- I095（横断ガード）と実装トラックが同じ（wt-harness）。スクリプトが別 worktree の `.env` を**コピー元として読む**動作は I095 の「読み取りは許可」と整合するが、**書込先は必ず新規/現 worktree 配下**に限定すること。
- ハーネス改善トラック（wt-harness 側セッション）で進める想定。

## Danger Ops（有/無）
- 有（撤去スクリプトが `docker compose down -v` で named volume を回収＝Postgres 開発データ削除を含む）
- 何を: 撤去対象 worktree の named volume。なぜ: worktree 撤去時の volume 漏れ防止。どう承認: 既存 danger-ops 枠組み（`DANGER_OK=1` + 撤去は明示コマンド）。ロールバック: 開発 DB のため復元不要（必要なら `scripts/db_backup.sh` を事前実行）。
