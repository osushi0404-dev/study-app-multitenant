# I095: 別 worktree 配下への編集を PreToolUse フックでハードブロック — トラック横断の直接編集を技術強制で不可能化（Edit/Write + Bash 書込・読み取りは許可）

## 設計確認メモ（/grill-me）
- Q: worktree 境界の判定ができないとき（git 不在・`git worktree list` 失敗等）の振る舞いは？ → A: **fail-safe（ブロック）**。境界を確定できなければ安全側に倒して書込をブロックする（「絶対に横断できない」を優先）。既存フックの fail-open 方針とは異なる **worktree ガード専用の方針** とし、git が常在する本リポジトリでは実害はほぼ無い。下記「エスケープ無し」と併用のため、git 失敗時は書込が全面停止しうる点を、明確な復旧誘導メッセージ（git 状態の修復を促す）で補う（文言は plan-issue で確定）。
- Q: 意図的な横断書込のエスケープハッチ（DANGER_OK=1 で解除）を設けるか？ → A: **エスケープ無し（真に不可能）**。横断の引き継ぎは §9 のファイル経由に限定する。正当な新 worktree 初期化は I096 スクリプト経由でフック不可視のため通るため、エスケープは不要。
- Q: Bash 書込検出の網羅範囲は？ → A: **実用重視（主要コマンドの絶対パス）**。`>` `>>` `>|` `tee` `cp` `mv` `sed -i` の宛先が別 worktree の**絶対パス**ならブロック。`cd <別worktree>` 後の相対書込・不透明ラッパー（`eval`／変数展開越し）は**既知の限界**として stderr/log に明示（silent に取りこぼさない）。Edit/Write/MultiEdit は絶対パス判定で確実にブロック。

## 背景/目的

### 現状の問題（証拠・再現手順）
worktree でトラックを分離しても、**あるトラックのセッションから別トラックの作業ツリーを直接編集することを止める技術的仕組みが無い**。抑止は `worktree.md §9`（「現セッションから他トラックの worktree を直接編集せず、引き継ぎはファイル経由」）と memory `feedback_respect_track_session_boundary` の**ソフトルールのみ**。

- 再現: `wt-harness` セッションで `Edit`/`Write` の `file_path` に絶対パス `/mnt/c/app/study-app-multitenant/backend/foo.py` を渡す、または `Bash` で `echo x > /mnt/c/app/study-app-multitenant/...` とリダイレクトすると、**何のガードもなく別 worktree を書き換えられる**（逆方向も同様）。
- 証拠: `scripts/claude/hooks/pretooluse_guard.py` に worktree 横断判定は存在しない（実装済みは push 保護ブランチ・checkout/restore の dirty 破棄・高リスクパス ask のみ）。`.claude/settings.json` の `permissions.allow` は `Edit(backend/**)` 等の**相対 glob** で、別 worktree の**絶対パス**に対する挙動は信頼できるガードにならない。
- 憲法§3 は「二重ガード（settings 権限 + PreToolUse フック）」を掲げるが、**worktree 横断はどちらの層にもガードが無い**。`git worktree list` 上に `study-app-multitenant`（primary）と `wt-harness`（linked）の 2 ツリーが同一ホスト FS に露出している。

### 根本原因
worktree 分離の副作用として**別トラックの作業ツリーが同一ホスト FS に露出**するが、書込操作を「現 worktree 配下」に限定する強制層が無い。分離はディレクトリを分けるだけで、横断書込の防止は人手規律に委ねられている。抽象化: 「トラック境界（worktree 境界）が物理的に隣接しているのに、境界越えの書込を技術強制するガードが二重ガードのどちらの層にも無い」。

### 解決方針
`scripts/claude/hooks/pretooluse_guard.py` に「**対象パスが別 worktree ルート配下なら `exit 2` でブロック**」する判定を追加する（既存二重ガードの hook 層を拡張）。

1. **現 worktree ルート** = `git rev-parse --show-toplevel`（既存 `_repo_relative` が使用済み）。**全 worktree ルート** = `git worktree list --porcelain` で列挙。
2. **判定基準**: 対象の絶対パスが「**別 worktree ルート配下**」なら block。「現 toplevel の外」では判定しない（`/tmp` スクラッチパッド・リポジトリ外の正当な編集を誤ブロックしないため）。
3. **対象操作**（grill-me 確定）:
   - **Edit/Write/MultiEdit**: `tool_input.file_path` を絶対パス正規化して判定（確実にブロック）。
   - **Bash 書込**: `>` `>>` `>|`・`tee`・`cp`・`mv`・`sed -i` の**宛先**が別 worktree の**絶対パス**なら検出しブロック。`cd <別worktree>` 後の相対書込・不透明ラッパー（`eval`／変数展開越し）は**既知の限界**として `log`/stderr で明示（no silent caps）。
4. **読み取りは許可**: §9 の趣旨は「直接編集の禁止」。`Read`/`cat`/`grep` 等の参照は対象外（採番権威 primary の確認等の正当な参照を阻害しない）。
5. **fail-safe（grill-me 確定）**: worktree 境界を確定できない場合（git 不在・`git worktree list` 失敗等）は安全側に倒して書込をブロックする。既存フックの fail-open 方針とは異なる **worktree ガード専用の方針**。git 失敗時に書込が全面停止しうるため、git 状態の修復を促す明確なメッセージを出す。
6. **エスケープ無し（grill-me 確定）**: `DANGER_OK=1` 等での横断書込の解除は設けない（真に不可能化）。横断の引き継ぎは §9 のファイル経由に限定。
7. `.claude/settings.json` は commit 済み＝全 worktree 共有のため、**双方向（harness↔app）に自動適用**される。
8. **false-green 対策**（I094 の decoy 反証・reference のアンカー一致を踏襲）: 現 worktree の類似/部分一致パスで誤ブロックしないこと、別 worktree では必ずブロックすることの両方を decoy で反証する自動テストを同梱。

## スコープ
### 含む
- `git worktree list --porcelain` による別 worktree ルート列挙。
- Edit/Write/MultiEdit の `file_path` 絶対パス正規化＋別 worktree 配下判定＋ block。
- Bash 書込の主要経路（`>` `>>` `>|`・`tee`・`cp`・`mv`・`sed -i`）の宛先が別 worktree 絶対パスの場合の判定＋ block。
- 別 worktree の**読み取り除外**（Read/参照系は通す）。
- 現 worktree 配下・リポジトリ外パス（`/tmp` 等）の**誤ブロック回避**。
- **fail-safe**（境界確定不能時はブロック）と **エスケープ無し**（DANGER_OK 解除なし）の実装。
- decoy 反証を含む自動テストの追加。
- worktree.md §9 への技術強制追記。

### 含まない
- Bash 書込経路の**完全網羅**（`cd <別worktree>` 後の相対書込・`eval`/不透明ラッパー・変数展開越しの宛先は既知の限界。`log` で明示し、必要なら別イシュー）。
- worktree 横断以外の一般的な「リポジトリ外への書込」全般のガード（本イシューは worktree 横断に限定）。
- settings.json 権限層（allow/deny glob）側での重複ガード化（hook 層で十分・二重化は別途）。
- 横断書込の解除手段（DANGER_OK 等のエスケープハッチ）の提供。

## 受け入れ条件（Acceptance Criteria）
- [ ] `wt-harness` から `/mnt/c/app/study-app-multitenant/` 配下を Edit/Write すると `exit 2` でブロックされる（逆方向＝primary から wt-harness 配下も同様）
- [ ] Bash の `echo x > <別worktree>/f`・`echo x >> <別worktree>/f`・`echo x >| <別worktree>/f`・`tee <別worktree>/f`・`cp a <別worktree>/`・`mv a <別worktree>/`・`sed -i ... <別worktree>/f` がブロックされる
- [ ] 現 worktree 配下の Edit/Write/Bash 書込は従来どおり通る（誤ブロック無し）
- [ ] `/tmp` スクラッチパッド等リポジトリ外への書込は通る（誤ブロック無し）
- [ ] 別 worktree 配下の Read/`cat`/`grep` 等の**読み取りは通る**
- [ ] worktree 境界を確定できない場合（`git worktree list` 失敗をシミュレート）に書込が **fail-safe でブロック**され、git 状態修復を促すメッセージが出る
- [ ] `DANGER_OK=1` を前置しても横断書込は**解除されない**（エスケープ無し）
- [ ] decoy 反証（現 worktree の類似パス・部分一致パスで誤ブロックしない／別 worktree で必ずブロックする）を含む自動テストが `scripts/claude/tests/` に追加され PASS
- [ ] Bash 書込の未カバー経路（`cd` 経由・不透明ラッパー）がある旨が stderr/log で利用者に明示される（silent に取りこぼさない）
- [ ] `docs/runbooks/worktree.md` §9 に技術強制済みである旨が追記されている

## 影響範囲（想定）
- Backend: なし
- Frontend: なし
- DB: なし
- Config/Infra: `scripts/claude/hooks/pretooluse_guard.py`・`scripts/claude/tests/`・`docs/runbooks/worktree.md`（`.claude/settings.json` のフック登録は既存のまま流用）

- **fail-safe ×エスケープ無しの相互作用（要注意）**: grill-me で fail-safe（境界確定不能ならブロック）とエスケープ無しを確定した。両者の併用により、`git worktree list` が失敗する状況では書込が**全面停止**しうる（解除手段が無い）。git が常在する本リポジトリでは実害はほぼ無い想定だが、plan-issue で「git 状態の修復を促す明確なメッセージ」を必須とし、恒久的に詰まらない導線を確保すること。
- 「別 worktree 配下」の判定は必ず**worktree ルートの境界一致**（末尾 `/` 付きの接頭辞一致）で行い、`study-app-multitenant` と `study-app-multitenant-foo` のような**兄弟ディレクトリ名の部分一致**で誤判定しないこと（reference `string_token_match_anchoring` の原則）。
- ハーネス改善トラック（wt-harness 側セッション）で進める想定。
