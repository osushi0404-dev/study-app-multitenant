## 背景/目的

**背景**: I200 で、見張り（`scripts/claude/hooks/pretooluse_guard.py`）の確認を (A) GitHub の破壊・(B) 復旧できない状態・(C) 秘密や個人情報の流出だけに絞った。レビューで、方針の (B)・(C) に当たるのに確認にならない形と、作りの整理の余地が残った。1〜4 はどれもコンテナの中（`docker compose exec` など）の判定で、#430 のサンドボックスは docker をその外に出す見込み（#430 の本文）。そのため見張りの役目として残る見込みが高く、#430 を待たずに着手してよい。
**目的**: #430 の後も見張りに残る役目について、取りこぼしを塞ぎ、確認の基準（手順書）と見張りの実物を一致させる。

### 現状の問題（証拠・再現手順）
1. **環境変数の表示の取りこぼし（(C)・`SECURITY=yes`）**: 引数なしの `export`・`declare`・`typeset` と、`env -0`・`env -u X` が確認にならない（台帳 F10・F12。`_container_risky` の判定は `env` の引数なし・`export`／`declare`／`typeset` の `-p`／`-x` だけを見る）
2. **コンテナ内の書き込み先の取りこぼし（(B)）**: `cp -t <dir>`・`--target-directory=`・`mv` の移動元が `/app/` の場合が、`/tmp/` 以外への書き込みとして見られない（一覧 F9・F11。`_ctr_write_targets` は最後の位置引数だけを見る）
3. **WHERE なしの UPDATE（(B) 大量更新）**: `psql -c "UPDATE users SET ..."`（WHERE なし）が、危ない語に当たらず通る疑い（敵対的レビュー 2 周目の Low）。→ /grill-me（2026-11-11）で実際に流し、コンテナ内・ホストとも既存の判定で停止になることを確かめた。テストでの固定が無いことだけが残り
4. **許可リストの二重化**: コンテナ内の「安全と確認済みの一覧」（`_container_safe`・約 110 行）は、I200 の後は「危ない語があっても通す例外」の役目だけになった。語の判定と二重の仕組みで、細かい分岐はもう結果を変えない。`ps` の e の判定も 2 か所にある
5. **手順書と見張りの写しのずれ**: `danger-ops.md` の 4. は見張りの規則を言葉で写しているため、見張りを変えると写しがずれる（I200 の手動 M-05 の NG で 1 周の延長が要った・一覧 F13）。同じ形が `docs/runbooks/worktree.md` §9 でも起きた（I219 のコードレビューの F1）

### 根本原因
- 1〜3: 見張りの規則を「確認を出す書き方の列挙」で作っているため、同じ意味の別の書き方が漏れる。I200 では脅威モデル（事故）に沿って粗い判定にとどめた
- 4: I200 で判定の主役を語の判定に替えたとき、古い仕組み（許可リスト）を片付けなかった
- 5: 規則の写しを手順書に持つ作り

### 解決方針
0. **対象の確かめ**: #430 が先に終わっていれば、その計画書の「公式だけで組んだ守りと、それで止まらない漏れの一覧」と突き合わせ、サンドボックスで止まるようになったものは対象から外す（止まることを確かめた記録があれば、見張りに足さない）。#430 がまだなら、1〜5 は今の見張りの役目として扱う
1・2. 環境変数を全部表示する形と、書き先を指定するオプション（`-t`・`--target-directory=`）・移動元を確認にする。粗い判定にとどめる（I179 の教訓）
3. `psql` の経路で WHERE なしの UPDATE・DELETE が停止になることは確かめ済み（設計確認メモ）。見張りは変えず、テストで固定する
4. 許可リストを「危ない語が当たっても通したい形」（`pytest -k delete` のようなもの）だけに縮めるか、消して語と書き込み先の判定に一本化するかを計画で決める
5. 手順書には規則の分類と代表だけを書き、細かい列挙は見張りの定数を正とする（`danger-ops.md` の 4. と `worktree.md` §9）
- 一覧の F5・F7・F8 は、計画で同梱するか決める
