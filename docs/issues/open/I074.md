## 設計確認メモ（/grill-me）
- Q: レビューは何段にするか？ → A: **3レビューの順次ゲート**にする。(1) **診断レビュー**＝修正前（根本原因・対応方針・影響調査）、(2) **実装レビュー**＝修正後・テスト前（コード修正が方針どおりか・回帰/副作用）、(3) **テストレビュー**＝テスト後（テストが修正を十分検証しているか・回帰防止・false-green でないか）。「実装の正しさ」と「テストの十分性」を別レビューに分ける。
- Q: 各レビューのタイミング（手順位置）は？ → A: 診断レビュー＝**手順3.5**（修正前）、実装レビュー＝**手順5.5**（修正後・テスト前）、テストレビュー＝**手順6.5**（テスト後）。
- Q: 順次ゲートと NG 差し戻しは？ → A: **前のレビューが OK のときのみ次へ進む**（診断OK→承認→修正→実装レビューOK→テスト→テストレビューOK）。NG 差し戻し: 診断NG→手順2（再診断）、実装レビューNG→手順5（再修正）、テストレビューNG→手順5/6（再修正・再テスト）。一気通貫では実施しない。
- Q: 実装機構は？ → A: **既存 `/plan-issue-review`・`/code-review` と同型**（`claude -p` ＋ review-agent system-prompt ＋ `--tools Read,Grep,Glob` を bash スクリプトで起動・VERDICT 解析・記録）。`scripts/claude/fix-diagnosis-review.sh`／`fix-implementation-review.sh`／`fix-test-review.sh` を新設（1スクリプトをパラメータ化でも可）。
- Q: 各レビューの入力は？ → A: 診断レビュー＝fix-loop が生成する **`docs/reviews/I###_fix_diagnosis_<ts>.md`**（章立て: 失敗分解／根本原因／対応方針＝修正箇所と方法／影響調査の実施有無と結果）。実装レビュー＝**作業ツリー差分（`git diff` ＋ `git diff --staged`）**（コミット前）。テストレビュー＝**テスト差分（追加/変更テスト）＋テスト実行結果（手順6 の出力）**。新規 `docs/fixes/` ディレクトリは作らず、fix-loop アーティファクトは既存 `docs/reviews/` に集約する。
- Q: 各レビューのエージェント定義は？ → A: **新設 `fix-diagnosis-reviewer.md`／`fix-implementation-reviewer.md`／`fix-test-reviewer.md`**（既存 `code-reviewer.md` は issue/plan/AC 前提で重いため流用せず、各々の焦点に絞った軽量エージェントにする）。読み取り専用（Read/Grep/Glob）・VERDICT 行を出力。
- Q: 各レビューの出力記録の扱いは？ → A: 既存 `plan-issue-review`/`code-review` と同型で **`docs/reviews/I###_fix_diagnosis_review_<ts>.md` / `I###_fix_implementation_review_<ts>.md` / `I###_fix_test_review_<ts>.md`** に保存し、feature ブランチで path-scoped commit（既存 `commit_review_artifact` 踏襲）。**PR コメント投稿は任意**（PR があれば投稿・無ければ skip・非ブロック）。
- Q: 適用範囲（コスト）は？ → A: **原則必須＋明示的な軽微例外**。SKILL.md に軽微条件（例: 単一ファイルのタイポ/フォーマットのみ等）を列挙し、該当時は各レビューを簡略化してよい。順次ゲート自体は維持。
- Q: `claude -p` 不可時（未認証/headless 等）の挙動は？ → A: **`issue-review.sh` と同型の非ブロック skip**（警告のみ・`exit 0`）。ただし**「レビュー未実施」を明示記録**し、診断レビュー等のゲートは skip 時に手順4（承認）でユーザーが実施可否を判断できるようにする（完全自動停止はしない＝headless でも fix-loop が回る）。
- Q: 診断レビュー（手順3.5・承認前）が評価する対象は「複数案」か「推奨1案」か？ → A: **提示した全案＋Claude 推奨案の妥当性**をレビュー対象にする（案選択そのものをレビューに含め、手順4 の承認判断に供する）。診断メモの「対応方針」欄には全案と Claude 推奨を記載する。
- Q: 順次ゲートの NG 差し戻ししきい値は？ → A: **`BLOCKER`＋`HIGH` で差し戻し**（`OK` のみ次段へ進む）。既存 `code-review` の VERDICT 3段（`BLOCKER`/`HIGH`/`OK`・`detect_code_verdict` 同型）を踏襲。`HIGH` 誤検知による過剰差し戻しはゲート連続 NG 上限で救済する。
- Q: NG 時のゲート強制形態は？ → A: **診断 NG＝ユーザー提示で停止**（直後の手順4 承認でユーザーが別案選択／再診断指示できるため）。**実装 NG／テスト NG＝Claude が VERDICT を読んで自動ループバック**（実装 NG→手順5／テスト NG→手順5/6）し、NG 内容を報告する。
- Q: ループ暴走ガードは？ → A: **各ゲート連続 NG 上限=2回**で自動ループバックを停止しユーザーへエスカレーション（報告）。上限値を SKILL.md に明記。headless の非ブロック skip・自動継続でも無限ループ／トークン浪費を防ぐ。
- Q: 3レビューを毎回全走させるか（コスト）？ → A: **3レビュー原則必須。ただし実装レビュー・テストレビューは差分が軽微例外条件に合致する場合は簡略化可**（順次ゲート自体は維持）。診断レビューは常時必須（I073 の本丸＝診断・影響調査の見落とし阻止）。
- Q: 軽微例外の適用判断は？ → A: **手順4 の承認時にユーザーが可否判断する**（Claude 単独では skip／簡略化しない）。軽微例外条件（例: 単一ファイルのタイポ／フォーマットのみ）は SKILL.md に列挙する。
- Q: テストレビュー NG（手順6.5）の差し戻し先は「手順6 のみ」か「手順5/6」か？（理想・根治で再検証） → A: **手順5/6 が最適**として確定。テスト NG の中身は必ずテストコードの不備（カバレッジ不足／false-green）で、その編集が起きるのは手順5（修正）のみ。手順6（実行）だけに戻すとテスト内容が変わらず同一 NG を反復し連続 NG 上限で無為にエスカレーションするため根治しない。根治経路＝**手順5（テスト追記/修正）→手順6（再実行）→手順6.5（再レビュー）**。修正済みテストが手順6 で RED になる場合（＝修正自体が不十分）は既存の「手順6 失敗→手順1」導線が多層で拾う。手順2（診断）までは戻さない（テスト十分性専用ゲートで、方針誤りは手順5.5 が捕捉済み）。実装 NG は手順5 のまま。※前ラウンドで「テスト NG→手順6」に狭めたのは誤りだったため訂正。
- Q: 軽微例外条件の具体的定義は？ → A: **「単一ファイルのタイポ／フォーマット／コメント修正のみ、かつロジック・制御フロー・テスト対象の振る舞いを変えない」変更**と定義（SKILL.md に明記）。変更行数しきい値は設けない（誤判定を招きやすく、最終判断は手順4 のユーザーであるため定性条件で十分）。この例外で簡略化可なのは実装/テストレビューのみ・診断レビューは常時必須・順次ゲート自体は維持。
- Q: 軽微例外の「予測判定（手順4・修正前）」と実 diff の乖離にどう対処するか？ → A: **手順5.5 で実 diff による再判定を入れる（fail-safe）**。手順4 の軽微例外承認は**「簡略化の候補」**扱いとし、手順5.5 で実 diff が軽微例外条件（単一ファイル・振る舞い不変）に**実際に合致するか自動再確認**する。合致しなければ簡略化を**撤回してフルレビュー**へ。予測に基づく簡略化が非自明変更を素通りさせるのを技術的に防ぎ、本イシューの「不十分レビュー阻止」目的に整合させる（追加コストは diff の条件判定のみ）。
- 補足: 本イシューは lint/audit/scan 出力で AC が決まる類ではない（SKILL.md / review-agent の文言追加が成果物）ため、「ツール実行による完了基準確定」は非該当。

## 背景/目的

### 現状の問題（証拠・再現手順）
現状の `/fix-loop`（`.claude/skills/fix-loop/SKILL.md`）は次の流れで、**「原因調査・対応方針の妥当性」と「修正内容の正しさ」を分けてレビューしていない**:
1. 失敗内容の分解 → 2) 根本原因調査 → 3) 対応案提示 → 4) 一括承認 → 5) 修正 → 6) テスト/lint/scan → 7) 再発防止記録

このため、**誤った原因特定・対応方針・影響調査漏れのまま実装フェーズへ進むリスク**がある。I073 ではまさに「DB 状態だけ検証してキャッシュ読み取り経路を見落とした」「`_delete_by_pattern` の同型バグが analytics 等にも存在する（影響調査の不足）」といった、**調査・方針段階での独立レビューが効くはずの見落とし**が発生した。

### 根本原因
fix-loop に「診断（原因＋方針＋影響調査）」「実装（修正差分）」「テスト（テストの十分性）」をそれぞれ**独立したサブエージェントでレビューし、前段が通って初めて次へ進む順次ゲート**を設ける仕組みが無い。レビューが実装後の1回のみ（または承認のみ）で、診断の妥当性・テストの十分性が独立検証されない。

### 解決方針
fix-loop に **3レビューのサブエージェント・レビュー**と **順次ゲート**を導入する。`/plan-issue-review`・`/code-review` が既に確立している「`claude -p` ＋ review-agent 定義」パターンを踏襲する。
- **診断レビュー（手順3.5・修正前）**: 「根本原因の調査結果」「対応方針（**提示した全案＋Claude 推奨案**をどのロジック/箇所でどう直す計画か）」「修正に関わる**影響調査**の実施有無と結果（同型バグ・他の呼び出し箇所・関連機能への波及）」を専用サブエージェントでレビュー。承認前レビューのため、案選択の妥当性を手順4 の承認判断に供する。
- **実装レビュー（手順5.5・修正後/テスト前）**: 実装した修正差分が対応方針どおりか・回帰/副作用がないかを専用サブエージェントでレビュー。
- **テストレビュー（手順6.5・テスト後）**: 追加/変更したテストが修正を十分に検証しているか・回帰防止・**false-green でないか**を専用サブエージェントでレビュー。
- **順次ゲート（しきい値と強制形態）**: 各レビューの VERDICT が **`OK` の場合のみ** 次へ進む。**`BLOCKER`＋`HIGH` は差し戻し対象**（既存 `code-review` の VERDICT 3段を踏襲）。差し戻しの実行形態は段で分ける: **診断 NG＝ユーザー提示で停止**（直後の手順4 承認でユーザーが別案選択／再診断を指示）、**実装 NG／テスト NG＝Claude が VERDICT を読んで自動ループバック**（実装 NG→手順5／テスト NG→手順5/6）＋NG 内容を報告。一気通貫では実施しない。
- **ループ暴走ガード**: 各ゲートの連続 NG が **2回**に達したら自動ループバックを停止しユーザーへエスカレーション（報告）。headless の非ブロック skip・自動継続でも無限ループ／トークン浪費を防ぐ。
- **適用範囲（コスト）**: 3レビューは原則必須。ただし**実装/テストレビューは差分が軽微例外条件に合致する場合のみ簡略化可**（順次ゲート自体は維持）。診断レビューは常時必須。軽微例外の適用可否は**手順4 の承認時にユーザーが判断**（Claude 単独では skip／簡略化しない）。**手順4 の承認は「簡略化の候補」扱いとし、手順5.5 で実 diff が軽微例外条件（単一ファイル・振る舞い不変）に実際に合致するか自動再判定する。合致しなければ簡略化を撤回してフルレビューする（fail-safe）。**

## スコープ
### 含む
- fix-loop の手順へ3レビュー（診断=手順3.5・実装=手順5.5・テスト=手順6.5）の追加
- 順次ゲート（前段 OK 時のみ次へ）・NG 差し戻し導線（診断→手順2／実装→手順5／テスト→手順5・6）・軽微例外条件・`claude -p` 不可時の非ブロック skip＋未実施記録の明記
- 診断レビューの入力＝診断メモ（`docs/reviews/I###_fix_diagnosis_<ts>.md`）を fix-loop が生成する仕組み
- 実装レビューの入力＝作業ツリー差分（コミット前）／テストレビューの入力＝**作業ツリー全差分（修正＋テスト）＋テスト実行結果**（テスト十分性・false-green を判定するには修正内容の可視化が必須のため、テスト差分単体でなく修正を含む全差分を渡す）
- 3レビュー用エージェント定義（`fix-diagnosis-reviewer.md`／`fix-implementation-reviewer.md`／`fix-test-reviewer.md`）と起動スクリプトの新設
- 3つの出力レビュー記録を `docs/reviews/` に保存・path-scoped commit（PR コメントは任意）。新規 `docs/fixes/` は作らず `docs/reviews/` に集約
### 含まない
- `/plan-issue-review`・`/code-review` 等、他スキルのレビュー機構の変更
- fix-loop 以外のワークフロー段階の改変
- `code-reviewer.md` の流用・改変（3レビューとも専用エージェントを新設）
