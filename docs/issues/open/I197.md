## 背景/目的

**背景**: I166 の /code-review（I193 マージ前の古い流れ）で、敵対的レビューの第 1 周の 3 体（裏で動くサブエージェント）が、開始 3〜4 分のコマンドで見張りの確認画面に当たり、誰も答えないまま約 11.5 分止まった。15 分の上限で止めて 3 件とも「拒否」で終わり、報告は最後に 1 回だけ書く作りのため、調べた内容はすべて失われた。それでも古い決まり（時間切れの体は指摘 0 件と数える）で「通過」になった。ユーザーの評価は「あかんやん」「問題があったのはコードレビュー」「今の状態だと採用は無理」。
**目的**: 実装の検証（レビュー）の仕組みを、今の部品の流用にこだわらずに白紙から設計し直す。①黙って止まる経路を構造的に無くす ②証拠が無いことを合格にしない ③確かめるべき項目の網羅を自己申告ではなく決定論で保証する ④開発をサクサク進められる速さと費用に収める。

### ユーザーの方針（2026-10-26）
- 確認待ちで止まって結果的に OK と評価されるのはまずい。
- サブエージェントを呼ぶ方式を続けるのが最適か（今の状態だと採用は無理）、メイン側でチェックする方式に変えるかも含めて検討したい。
- 根本的な見直し・改善にしたい。現状維持にこだわらない。現状の流用にこだわらなくてもいい。
- 確認が出ない作りにした場合に、本来実施すべきレビューが網羅できているのかが心配。
- 基準: ループエンジニアリング・ハーネスエンジニアリングのベストプラクティスと、開発をサクサク進めること。
- **留意点（変えない前提）**: 公式のツール（Claude Code の公式機能・組み込みのスキルやサブエージェント・`claude -p`・GitHub の公式機能など）をベースにするという考え方は変えない（I193 の方針）。白紙から作り直すのは「検証の仕組みの設計」であって、この土台の考え方ではない。自作は公式に無い部分だけに足し、公式を置き換える案は失うものを実証してから出す。

### 現状の問題（証拠・再現手順）
1. **第 1 周（I166・古い流れ）**: 3 体とも、開始 3〜4 分のコマンド 1 つで約 11.5 分止まっていた（各体の作業記録の集計で確定。最後のツール呼び出しの結果は 3 件とも「ユーザーが拒否」＝上限で止めた時点の扱い）。決まりで「通過」になった。
2. **第 2 周**: 1 体は Claude Code 本体のワークツリー隔離チェック（「too complex to verify」）に実験ファイルの作成（波かっこを含む heredoc）を拒否され、読んで確かめるだけになった。別の 1 体は `docker compose exec ... python /tmp/<file>.py` の形で確認画面に当たり、ユーザーの応答を待った（ユーザーが画面に気づいて答えた）。
3. **延長周（ユーザー承認）**: 「レビュー役は Read・Grep・Glob だけ・実験コードは報告に書いて返す・親がそのまま実行して結果を返す（1 体 2 往復まで）」に変えると、3 体とも 1〜2 分で報告した。範囲内の High（復習モードのテストの穴）と範囲外の High（学習記録 API の越境・I196 #331 として起票）が見つかった。ただし縛りは指示だけで、守られる保証は無い。
4. **今の develop（I193 マージ後・2026-10-26 に確認）**:
   - review-gate の敵対的レビューは「報告の無い観点を合格に数えない（1 回だけ起動し直し、それでも無ければ HIGH）」に変わっている（`.claude/skills/review-gate/SKILL.md` 3-1 の 5）。
   - しかしレビュー役（`.claude/agents/adversarial-reviewer.md`・tools に Bash・model: sonnet）を裏で起動し 15 分のタイマーで待つ形は同じ。確認画面で止まる穴は残っており、今は「止まったまま合格」ではなく「15 分×2 回待って HIGH で止まる」になっただけ（時間の無駄と人の判断待ち）。
   - 一方、コードレビュー役・計画レビュー役・イシューレビュー役・fix-loop の各レビュー役は、すでに `claude -p --agent` の独立した別プロセスで動いている（tools は Read, Grep, Glob だけ）。裏で動くサブエージェントとして起動しているのは敵対的レビュー役だけ。
5. **原因の説明が推測になった**: 時間切れの原因を、親（Claude）が作業記録を見ずに 2 回推測で説明した（「Docker の準備」「波かっこ」）。止まった体の最後のツール呼び出し・結果・待ち時間を機械的に残す仕組みが無い。

### 根本原因
- 検証する側（レビュー役）が承認を要る操作を自由に行える作りで、裏で確認待ちになっても親から気づけない（親から「子が確認待ちか」を直接知る公式の手段は見当たらない）。
- 判定が「レビュー役の自己申告（反証失敗＝指摘 0 件）」に寄っていて、何を確かめたか・確かめていないかが決定論で集計されない。報告が最後に 1 回だけなので、途中で止まると証拠がすべて消える。
- 決定論で確かめられること（テスト・注入）と LLM でしか見られないこと（脅威モデル・要件の漏れ）の分担が設計されておらず、LLM のレビュー役に実験の実行まで任せている。
- 方式は grill-me で確定（設計確認メモ）: (d) 別プロセス・読むだけ＋実験は親が実行。

### 解決方針
白紙から次の問いに答えを出す（今の部品は使っても捨ててもよい）。方式・目標値・分担は grill-me で確定済み（設計確認メモ）: **(d) `claude -p --agent` の別プロセス・tools は Read/Grep/Glob・`--permission-prompts none`・実験は親が実行（1 体 2 往復まで）＋決定論（注入など）を厚くする**。以下 1〜6 の (a)〜(f) の比較は、計画書に「採用・捨てた理由・実証結果」として残すための材料。
1. **検証の全体設計**: 何を・どの段階で・何で確かめるか。決定論で確かめられるもの（テスト・注入〔守りを壊してテストが落ちるか〕・lint・型・静的な検査・CI）と、LLM でしか見られないもの（脅威モデル・要件の漏れ・設計の筋）を分け、LLM には後者だけを任せる。実装した本人の確認と独立した目の確認をどう分けるか。
2. **独立した目の用意の仕方（方式の比較）**:
   - (a) 裏で動くサブエージェント（今の方式）: 確認画面で黙って止まる。
   - (b) 読むだけのサブエージェント＋実験は親が実行（I166 の延長周）: 止まらず速かった。定義の tools から Bash を外せば、指示ではなく仕組みで縛れるかを確かめる。
   - (c) メイン側（実装したセッション）がレビューする: 止まらないが独立性を失う（自己レビューは追認に引っぱられる、という過去の教訓）。
   - (d) 独立した別プロセス（`claude -p --agent`）: 他のレビュー役が既に使っている。承認なしの設定（`--permission-prompts none` 等）で起動すれば、承認が要る操作は自動で拒否されて出力に残るため、黙って止まらず、拒否を機械的に「未検証」にできる。敵対的レビューに使えるか（時間・費用・実験の実行・結果の受け渡し）は小さく試して確かめる（計画の未知リスク先行）。
   - (e) 公式の組み込み（`/code-review`・`/security-review` など）にどこまで任せられるか。
   - (f) GitHub 側（CI のジョブ・PR のレビュー）に独立した検証を置く。
   - 確定（grill-me）: (d) を軸に、1 の決定論（注入など）を厚くする組み合わせ。(a) は捨てる。(c) は独立性を失うので敵対的レビューの代わりにしない。(e) は今のまま併用。(f) は費用のかからない決定論の検査だけ（Claude を Actions で動かさない）。
3. **網羅の保証**: 受け入れ条件・脅威モデルから「必ず確かめる項目の一覧」を計画の段階で先に作る。検証する側は項目ごとに「実験で確認／読んで確認／未実施」を報告し、判定は一覧から決定論で出す（自己申告の「反証失敗」だけで通さない）。一覧の各項目には計画で「実験必須」か「読んで確認で可」を指定し、計画レビューで確認する。実験必須を読んで確認だけで済ませた項目・未実施・時間切れ（1 周 10 分超）・拒否は「未検証」とし、1 件でも残れば合格にしない（fail-closed）。確かめた範囲を記録に残し、後から監査できるようにする。
4. **止まり方とサクサク感の両立**: 黙って止まる経路を構造的に無くす（待ち時間の上限に頼らない）。途中の結果を残す（最後に 1 回だけ報告する作りをやめる）。人の判断で止めるのは、価値判断・取り消せない操作・上限到達だけ（I193 の「止める条件 3 つ」）。決定論の確認が済んでいれば、LLM の検証を絞れるか（I166 では「テストの見かけ合格」の観点が注入の確認と重なった一方、延長周では注入で見落としたテストの穴を見つけた。両方の事実を材料にする）。
5. **I166 の /retro からの同梱**:
   - 予防 1: 検証する側が承認を要る操作を自由に行える作りを無くす（2・4 の答えで、黙って止まる経路を構造的に無くす）。
   - 予防 2: 時間切れ・報告なし・拒否で終わった体は、最後のツール呼び出し・結果・待ち時間を決定論で集計して、検証の記録に残す。
6. **見張りとの関係**: リポジトリの見張り（`scripts/claude/hooks/pretooluse_guard.py`）と Claude Code 本体のワークツリー隔離チェックが、検証に必要な普通の実験を止めない作りにする。見張りの確認を絞るイシュー（I200 #335）との分担は grill-me で確定: 本イシューでは見張り・`.claude/settings.json` を変えず、レビュー役に実行の道具を持たせない作りで、見張りが今のままでも黙って止まらないようにする。

## 受け入れ条件（Acceptance Criteria）
- [ ] 検証の全体設計（何を・どの段階で・何で確かめるか、決定論と LLM の分担）が文書化されている
- [ ] 独立した目の方式を比較した結果（採用した方式・捨てた方式とその理由・実証の結果）が計画書に記録されている
