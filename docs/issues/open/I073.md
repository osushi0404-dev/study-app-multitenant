# I073: 問題編集時の画像更新（追加・差し替え・削除・並び替え）を実装

## 関連資料
- GitHub Issue: #150
- Draft PR: #151
- 事前調査（問題管理機能の現状調査）: 作成・一覧・削除・出題・AI生成は実装済み、編集時の画像更新のみ未実装と判明
- 関連先行イシュー: I031（MediaAsset / ProblemMediaAsset による画像管理の新方式導入）

## 設計確認メモ（/grill-me）
- Q: 編集時の画像更新APIの方式は？（既存の個別 upload/delete エンドポイントを再利用するか）
  → A: **PUT 一括差分更新**を採用。1回の multipart PUT で「最終的な画像の並び（既存＋新規）＋新規ファイル」を送り、サーバ側で `ProblemService.update_problem_with_images()` が `@transaction.atomic` 下で追加・削除・並び替えを一括処理する。既存の `upload_image`/`delete_image` は複数HTTP呼び出しで原子性を担保できず AC（途中失敗で部分更新を残さない）と矛盾するため、編集フローでは使わない。新規作成フローと同じ ProblemService 経路に統一する。
- Q: 画像並び替えのスコープとUI方式は？
  → A: **今回のスコープに含め、上下（↑/↓）ボタンで実装**。各画像サムネイルの並べ替えボタンで position を入れ替える。新規依存ライブラリ（DnD等）は追加しない。
- Q（自己解決）: 編集の権限は？ → ProblemViewSet は `IsAuthenticated`＋queryset の組織スコープ（`subject__organization == request.user.organization`）。`IsOrgAdmin` は Subject 作成のみで Problem 編集には掛からない。他組織ユーザーは queryset 上 404。
- 確定した multipart 契約（usage_kind ∈ {problem, explanation} ごと）:
  - 新規ファイル: `question_image_1..N` / `explanation_image_1..N`（作成フローの命名を踏襲）
  - 並び順＋残す指定: `question_images_order` / `explanation_images_order` = 最終並び順を表す JSON 配列。各要素は `{"existing": "<MediaAsset UUID>"}` または `{"new": "<新規ファイルのフィールドキー>"}`。
  - 削除: 暗黙指定。order 配列に現れない既存アセットは紐づけ解除（共有なしなら物理削除）。
  - 枚数上限: 結果セットで usage_kind ごと最大5枚をサーバ側で強制。
- スコープ外（フォローアップ）: 画像保存ロジックの二重実装（`ProblemService._process_images`＝`problems.utils` 経路と `upload_image`＝`StorageService` 経路の併存）の統一。本イシューでは編集を ProblemService 経路に寄せるに留め、既存 upload_image の刷新は別イシュー。

## 背景/目的

### 現状の問題（証拠・再現手順）
問題は画像付き（問題画像・解説画像 各最大5枚）で**作成**できるが、作成後に画像を**編集**できない。

- 再現: 管理画面（`frontend/src/pages/QuizManagement.tsx`）で既存問題を編集ダイアログから開き、画像を追加/差し替え/削除しても反映されない。
- バックエンド側の根拠: `backend/problems/services/problem_service.py` の `update_problem_with_images()` が画像処理を実装しておらず、`# TODO: 画像の追加・削除・並び替え機能` のコメントのみで本文の画像差分処理が無い。
- 結果として、テキスト・選択肢は更新できるが画像はサーバ側で無視される。

### 根本原因
- 作成フロー（`create_problem_with_images()`）と画像個別操作API（`POST /api/problems/{id}/images/upload/`、`DELETE /api/problems/{id}/images/delete/{asset_id}/`）は実装済みだが、**編集フロー（PUT `/api/problems/{id}/`）に画像差分処理が接続されていない**。
- 編集時に「既存画像のうちどれを残し / どれを削除し / どれを新規追加するか」を表現する差分の受け渡し仕様（フロント→API）が未定義。

### 解決方針
編集を「画像個別API」ではなく、作成と対等な **PUT の一括差分更新** で完結させる（multipart 契約は「設計確認メモ」に確定値あり）。
1. フロント（編集ダイアログ）で、既存＋新規を1つの並び替え可能リストとして扱い、最終並び順（`*_images_order`）＋新規ファイル（`*_image_i`）を multipart PUT で送信。並び替えは上下ボタン。
2. `update_problem_with_images()` を実装し、`@transaction.atomic` 配下で
   - order 配列に現れない既存 `ProblemMediaAsset` を紐づけ解除。対象アセットが他問題で共有されていなければ物理削除＋`MediaAsset` 論理削除、共有されていれば紐づけ解除のみ（アセットは保持）。
   - 新規ファイルの保存・`MediaAsset`/`ProblemMediaAsset` 作成（作成フローと同じ枚数上限・SHA256・ストレージキー規約を再利用）
   - order 配列の順に `position` を再採番して並び替えを反映
   を行う。
3. 既存の作成フローのバリデーション・ストレージ規約・テストパターンを最大限再利用し、ロジック重複を避ける。

## スコープ
### 含む
- 既存問題への画像の追加
- 既存画像の差し替え（削除＋追加の組み合わせで実現）
- 既存画像の削除
- 画像の並び替え（position 再採番）
- 問題画像・解説画像（usage_kind = problem / explanation）の両方
- 上記の決定論テスト追加

### 含まない
- テキスト問題タイプの回答判定の実運用化（別イシュー）
- 分野（Field）管理UI / アクセス権限管理UI（別イシュー）
- 問題のインポート/エクスポート・一括削除（別イシュー）
- 画像のトリミング・編集（クロップ等）機能

## 関連する品質基準
- C1 正確性/信頼性 — 編集の画像差分はトランザクションで一貫性を担保し、途中失敗で孤児アセットや二重削除が起きないこと。
- C7 保守性 — 作成フローのバリデーション・ストレージ規約を再利用し、画像処理ロジックの重複・乖離を作らない。

## 受け入れ条件（Acceptance Criteria）
- [ ] 既存問題に画像を追加でき、保存後の再取得で反映される
- [ ] 既存画像を削除でき、共有されていない場合はストレージ実体も削除される（共有時は紐づけのみ解除）
- [ ] 既存画像を差し替えでき（削除＋追加）、結果が正しく反映される
- [ ] 画像の並び順を変更でき、`position` が再採番されて表示順に反映される
- [ ] 問題画像・解説画像それぞれで上記が機能する
- [ ] 枚数上限（各5枚）を編集時も超過できない（超過時はバリデーションエラー）
- [ ] 編集処理はトランザクションで、途中失敗時に部分更新が残らない
- [ ] 他組織ユーザーは対象問題を編集できない（queryset スコープにより 404）
- [ ] 上記を検証する決定論テストが追加され全て PASS する（追加・削除・差し替え・並び替え・枚数上限・共有画像・他組織不可の各ケース）

## 影響範囲（想定）
- Backend: `problems` の serializers / views / services（画像差分処理の追加）
- Frontend: 問題管理画面の編集ダイアログ・`ImageUploadArea`（既存画像対応）・quiz.service の更新API
- DB: スキーマ変更なし（既存 `MediaAsset` / `ProblemMediaAsset` を使用）
- Config/Infra: なし

## 制約・引き継ぎ情報
- 画像ストレージキー規約: `/org/{org.slug}/subjects/{subject.slug}/{usage_kind}/{uuid}.ext`（作成フロー準拠）。
- 削除時は他問題での共有有無を確認してから物理削除すること（既存 delete_image / delete_problem の挙動を踏襲）。
- 編集後はキャッシュ（`cache_service` の problems キャッシュ）を無効化すること。

## Danger Ops（有/無）
- 無
- 画像ファイルの物理削除を伴うが、対象は「当該問題に紐づき他で共有されていないアセット」に限定され、論理削除・共有チェック・トランザクションで保護されるため破壊的一括操作には該当しない。
