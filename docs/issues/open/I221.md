## 背景/目的

**背景**: イシューは「GitHub のイシュー」と「手元の `docs/issues/open/I###.md`」の 2 か所にあり、番号も「GitHub の番号」と「自前の I###」の 2 つがある。このため、次の自前の仕組みと手作業が要っている。
- 全ワークツリーをまたぐ採番のスクリプト（`next-issue-num.sh`）。それでも同時に起票すると番号がぶつかる（I189・未解決）
- 手元のファイルを「未コミットのまま置く」決まり（コミットすると `/plan-issue` の最初のコミットが空になり失敗する。I062・I067 の事故）
- 手元のファイルを直すたびに `gh issue edit --body-file` で GitHub に同期する手作業（2026-10-29〜30 の I200・I213 の作業だけで 10 回を超えた）。同期を忘れると 2 つがずれる
- ワークツリーをまたいでイシューファイルを手で持ち運ぶ作業（app-1 から harness-1 へ）
**目的**: 「公式の道具を土台にし、自作は公式に無い部分だけ足す」方針（I193）に沿って、イシューの正を GitHub に一本化できるかを検討する。できるなら、起票のスキル・採番のスクリプト・手元のイシューファイルを薄くするか無くし、同期と持ち運びの手作業と番号の衝突を無くす。

### 現状の問題（証拠・再現手順）
- 同時起票の番号の衝突（I189 #321 に記録。2026-10-24 に harness-1 と harness-2 で同じ番号）
- 本文の同期の手作業: I200 の grill-me・plan-review・retro のたびに `gh issue edit` を流した（`docs/reviews/closed/I200_review.md` の流れ）
- ワークツリーをまたぐ持ち運び: ハーネスのイシュー（I200・I212 など）のファイルが app-1 に未追跡で置かれ、harness-1 で始めるには手で持ってくる必要がある
- 2026-10-30 に Claude が起票のスキルを通さずに起票したとき、スキルの手順（テンプレートのコピー）を省いた。手順が多いほど、通さないと漏れる

### 根本原因
イシューの内容と番号を、GitHub と手元のファイルの 2 か所に持つ作り（I193 の組み直しでも残した部分）。手元のファイルを持っている元の理由は、①イシューの本文の変更を PR の差分としてレビュー・記録に残せる（計画・テスト・レビューの記録と同じ場所で、同じ版で読める）②ネットワークに頼らずスクリプトが本文を読める ③close で open → closed に移して「完了」を git の履歴に残せる、の 3 つ。案 1 では、これらを失うか別の方法で補う必要がある

### 解決方針（設計確認メモで案 1 に決定）
- GitHub のイシューを唯一の正にする。新しいイシューは手元のイシューファイルを作らない。GitHub 画面用のイシューフォームは作らない（設計確認メモ）。起票は薄くした `/issue-bootstrap` が `gh issue create` で行い、本文のひな形・自己完結度のレビュー・公開リポジトリの決まり・ラベルはスキルに残す
- `/plan-issue`・`/grill-me`・自己完結度のレビュー・close・確かめのスクリプトなど、手元のイシューファイルを読むものを、`gh issue view` で GitHub の本文を読む形に更新する。既存のイシューファイルがあるイシューは、移行中も今の流れで動くようにする
- 番号: 新しいイシューは「I＋GitHub の番号」（#403 → I403・設計確認メモ）。記録のファイル名・ゲートのスクリプトの I### の形はそのまま使う。自前の採番（`next-issue-num.sh`）は新しいイシューでは使わない（スクリプトを消すか残すかは計画で決める）
- `/plan-issue` が計画を始めるときに GitHub のイシュー本文を 1 回だけ手元に書き写し、計画書と一緒にコミットする（設計確認メモ・2026-11-08。GitHub で見えなくなったときの備えと、根本原因 ① の補いを兼ねる。写しは同期しない）。失うもの（根本原因の ①〜③）を補う方法の残り（②③）は、スパイクで確かめてから決める
- I189（採番の衝突）は吸収して取り下げる見込み（計画で確定）
- I220（#400・起票は Claude が実行する決まり）は、I221 で起票の流れが変わるので、合わせて見直す
