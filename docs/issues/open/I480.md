## 背景/目的

**背景**: retro の手順 4-0 は、コードレビューの台帳の残りを `code-review.sh --route` で「後続イシュー」と「軽い指摘の一覧」に振り分ける。今の決まりでは `SECURITY=yes` の指摘は重さと再現に関係なく後続イシューになり、さらに「次のハーネスの作業で最優先」と書く。見張り（`scripts/claude/hooks/pretooluse_guard.py`）の直しでは、レビュー役が読んで見つけた軽い読み漏れが毎回 `SECURITY=yes` で付き、I444 → I454 → I463 → I469 → #477 と最優先の後続が途切れずに続いた。
**目的**: 重さが Low で再現の無い指摘は、`SECURITY=yes` でも軽い指摘の一覧（`docs/reviews/backlog/`）に回し、最優先の後続イシューの連鎖を止める。再現のあるもの・Medium 以上の秘密情報の指摘は今までどおり後続イシューにする。

### 現状の問題（証拠・再現手順）
- `route_reasons()` は `sec == "yes"` だけで後続イシューの理由を足す（重さ・再現を見ない）
- 例: I469 のコードレビュー 1647 の F1〜F3 は 3 件とも `SEV=Low REPRO=no SECURITY=yes`。どれも変更前からある形で、一部はわざと抜ける書き方に近い。それでも後続イシュー #477 になり、本文に「最優先」と書かれた
- 列挙で塞ぐ方式の見張りでは、レビューのたびに新しい読み漏れが見つかるので、この決まりのままだと最優先の後続が終わらない（レビューが収束しない）

### 根本原因
- 振り分けの決まり（I208）が、`SECURITY=yes` を「重さに関係なく後続イシュー」と決めている。秘密情報に関わる指摘を取りこぼさないための安全側の決まりだったが、軽くて再現の無い指摘まで最優先に上がる

### 解決方針
- `route_reasons()` の `SECURITY=yes` の条件を、「`SECURITY=yes` かつ（再現あり または Medium 以上）」に絞る。`SEV=Low` かつ `REPRO=no` は一覧に回す
- retro の手順 4-0 の説明（「`SECURITY=yes`（重さに関係なく）」）と「次のハーネスの作業で最優先と書く」の条件を同じに直す
- GitHub から復旧できない例外（秘密情報の push など）に当たる指摘は、止める判定（`blocking()`）で別に止まるので、この変更で緩まないことを確かめる
- 細部は計画で決める（未定・grill-me で確認してもよいが、方針は上で合意済み）
