# I157: celery beat のスケジュールが開発用のまま — 日次タスク 5 件が 30 秒〜1 時間間隔で実行される設定を環境別に切り替える

## 関連資料
- GitHub Issue: #274
- I151（Django 5.2 LTS 更新。決定 7-D で発見・範囲外として本イシューへ分離）
- `backend/core/celery.py`（対象ファイル）

## 背景/目的

**背景**: I151 の依存調査で celery の設定を確認したところ、`beat_schedule` の 5 タスクすべてが**開発用の短い間隔で固定**されており、本番用の設定はコメントアウトされたままだった。I151（脆弱性解消）とは無関係のため、範囲外として分離した。

**目的**: 環境に応じて実行間隔が切り替わるようにし、本番デプロイ時に日次タスクが 30 秒ごとに走る事故を防ぐ。

### 現状の問題（証拠・再現手順）

`backend/core/celery.py` の 21〜56 行目。5 タスクすべてが同じ形になっている。

| タスク | 本来の意図（コメント） | 現在有効な設定 |
|---|---|---|
| `update-daily-analytics` | 毎日午前 2 時 | **30 秒ごと** |
| `send-study-reminders` | 毎日午前 7 時 | **60 秒ごと** |
| `analyze-mistake-patterns` | 毎週月曜午前 3 時 | **300 秒（5 分）ごと** |
| `cleanup-expired-suggestions` | 毎時 0 分 | 3600 秒（1 時間）ごと |
| `cache-maintenance` | 30 分ごと | 1800 秒（30 分）ごと |

コードの形（`update-daily-analytics` の例・24〜27 行目）:
```python
'update-daily-analytics': {
    'task': 'studylogs.tasks.update_daily_analytics_task',
    'schedule': 30.0,  # 30秒ごと（開発環境用）
    # 'schedule': crontab(hour=2, minute=0),  # 本番環境では毎日午前2時
},
```

実際に 30 秒間隔で実行されていることは稼働中のログで確認済み（2026-08-22）:
```
celery-1 | Task studylogs.tasks.update_daily_analytics_task[...] succeeded in 0.0103s
celery-1 | Task studylogs.tasks.update_daily_analytics_task[...] succeeded in 0.0115s   ← 30 秒後
```

**影響**:
- このままデプロイすると、日次のはずの分析更新が **1 日 2880 回**走る。DB 負荷とタスクキューの浪費になる
- `send-study-reminders` はメール送信を伴う。本番で 60 秒ごとに走ると**利用者へのリマインダーが大量送信されうる**（現在は対象 0 件のため顕在化していない）
- コメントを外すだけでは直らない。**`crontab` が import されていない**ため、コメントアウトを解除すると `NameError` になる

```python
# backend/core/celery.py:7-8
import os
from celery import Celery
# crontab の import が無い
```

### 根本原因

開発時に「とりあえず短い間隔で動作確認できるように」した設定が、**環境ごとに切り替える仕組みを持たないまま**コミットされた。本番設定はコメントとして残されたが、コメントは実行されないため、切り替えは手作業に依存している。設定を環境変数から読む他の箇所（`RATELIMIT_ENABLE` / `DEBUG` / `ALLOWED_HOSTS` 等）と一貫していない。

### 解決方針

**`DEBUG` または専用の環境変数で開発用スケジュールと本番用スケジュールを切り替える。**

実装方針は計画時に確定するが、既存コードとの一貫性を重視すると次の形になる。

```python
from celery.schedules import crontab   # <- 追加（現状 import されていない）
from django.conf import settings

# 開発用の短間隔スケジュールを使うかどうか（既定は本番用）
CELERY_BEAT_DEV_SCHEDULE = os.getenv('CELERY_BEAT_DEV_SCHEDULE', 'False').lower() == 'true'

if CELERY_BEAT_DEV_SCHEDULE:
    schedules = {'update-daily-analytics': 30.0, ...}
else:
    schedules = {'update-daily-analytics': crontab(hour=2, minute=0), ...}
```

**決めるべき点**:
1. **既定をどちらにするか** — 「開発が既定」だと本番で事故る。**「本番が既定・開発は明示的に有効化」を推奨**（`RATELIMIT_ENABLE` が「既定 True・E2E CI でのみ無効化」としているのと同じ考え方）
2. **切り替えのキー** — `DEBUG` を流用するか専用の環境変数を作るか
3. **`docker-compose.yml` での指定** — 開発環境で短間隔を使うなら、compose 側で環境変数を設定する
4. **タイムゾーン** — `app.conf.timezone = 'Asia/Tokyo'`（58 行目）が設定済み。`crontab` の時刻はこれに従う

## スコープ
### 含む
- `crontab` の import 追加（コメント解除だけでは `NameError` になる問題の是正）
- 5 タスクすべての環境別切り替え
- 既定を本番用にする（開発は明示的に有効化）
- 切り替えを検証するテスト

### 含まない
- **タスクの実行内容の変更**（`studylogs/tasks.py` / `core/tasks.py` のロジック）
- **スケジュール時刻そのものの見直し**（コメントに書かれた意図をそのまま採用する。時刻の妥当性の検討は別）
- **celery / kombu のバージョン更新** — I156（ロックファイル導入）の領域
- **タスクが 1 箇所からも呼ばれていない件**（beat 以外に呼び出し元がない。これは設計上の別論点）

## 関連する品質基準
- C7 フェールセーフ/可観測性 — 設定ミスが本番でだけ顕在化する状態を解消する。既定値が安全側（本番用）になっていること
- C2 プライバシー — `send-study-reminders` はメール送信を伴う。意図しない高頻度送信は利用者への迷惑行為になりうる

## 制約・引き継ぎ情報
- I151 の実測で確認済み: beat は実際に 30 秒間隔でタスクを投げており、worker は成功で完了している（設定が「効いていない」のではなく「開発用の設定が効いている」状態）。
- `docker-compose.yml` の `celery-beat` は `celery -A core beat -l info` で起動し、スケジュール状態を `backend/celerybeat-schedule` に保存する。切り替え後にこのファイルが古いスケジュールを保持しないか確認する。
- トラック: `track:app`（変更対象は `backend/`）。

## Danger Ops（有/無）
- 有
- 内容: 定期実行の間隔を変更する。既定を本番用にするため、**開発環境で環境変数を設定し忘れると、これまで 30 秒ごとに動いていたタスクが日次になる**（開発中の動作確認がしにくくなる）。逆に本番で開発用が有効になると高頻度実行の事故になる。
- 承認: 既定値・切り替えキー・compose での指定内容を計画書で確定し、ユーザー承認を得てから実装する。
- ロールバック: `backend/core/celery.py` と `docker-compose.yml` を変更前へ戻す。`backend/celerybeat-schedule` に古い状態が残る場合は削除して beat を再起動する。
