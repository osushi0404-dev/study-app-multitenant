## 背景/目的

**背景**: I620（組織の管理者の登録用リンク・メンバー管理）のレビューで、止めるほどではない重さの指摘（Low・再現なし）と、敵対的レビューの Medium 2 件（上限の 2 周の中で直さなかったもの）が残った。test-gate では、確かめ用の運営と本人ひとりの組織の利用者が初期データに無く、開発の DB に手で作った（承認が要った）。E2E では、ログイン直後の通知がユーザーメニューに重なってログアウトを押せず、時間しだいで落ちることがあった。
**目的**: 残った指摘を直し、確かめの道具（初期データ）とテストを安定させる。

### 現状の問題（証拠・再現手順）
敵対的レビュー（優先）:
- M1: パスキー削除の URL の `passkey_id` は正規表現 `[0-9a-f-]{36}` を通れば UUID でなくても通る（例: `-` 36 個）。`backend/accounts/registration_links.py` の `delete_passkey_of` の `Passkey.objects.filter(pk=…)` が `ValidationError` で 500 になるおそれ（404 ではなく）
- M2: 期限切れ・失効・無効の利用者・無効の組織のリンクを、`complete` の側で確かめるテストが無い（`test_I620_registration_links.py` は `options` の側だけ）。`complete_link_registration` の鍵つきの引き直しを外しても落ちない
- L: `test_tc07_concurrent_complete_only_once` の 2 本の実行順が決まらず、行の鍵を外しても通る順がありうる
コードレビューの台帳（すべて Low・アプリ本体）:
- F4: 同じユーザー ID を同時に作成すると `exists()` の後の INSERT で IntegrityError → 500（`backend/accounts/views.py` の `MemberViewSet.create`）
- F5: メニュー（`frontend/src/components/Layout.tsx`）は `role=admin` かつ本人ひとりの組織でないときに出すが、裏側（`IsOrgMemberManager`）は無効な組織・共有の personal 組織も 403 にする。メニューが出るのに開けない管理者がいる
- F6: `MemberCreateSerializer` の `user_id` の `max_length`・`required` のエラー文が DRF の既定の英語（`backend/accounts/serializers.py`）
- F7: 登録画面で押したときの options の取り直しが 4xx（期限切れ・失効）だと、「使えないリンク」ではなく一般の登録の失敗の文が出る（`frontend/src/pages/PasskeySetup.tsx`）。押してから WebAuthn を呼ぶまでに通信を挟むので Safari・iOS で操作の扱いが切れるおそれがある点は、#637 で実機で確かめる
- F8: リンクのダイアログを閉じるアニメーションの間、見出しが『』になる。追加の流れの発行は行の発行と別の処理で、二度押しの防止が効かない（`frontend/src/pages/MemberManagement.tsx`）
- F9: 設定の読み込みのテスト（`test_tc13_empty_origins_do_not_break_settings_loading`）が `.env` の `REGISTRATION_LINK_BASE_URL` の影響を受け、土台の値も確かめていない
- F10: E2E が MUI の内部のクラス名 `.MuiTableContainer-root` で表の枠を探している（`e2e/tests/registration-link.spec.ts`）
- F11: 360px のボタンの高さの確かめが、ボタン 2 つの行だけ（［リンクを取り消す］を含む 3 つの行を見ていない）
- F12: 表の `'& td:first-of-type'` の `minWidth` は効かないブラウザがある。`'& td:last-of-type > div'` は `MemberCredentialActions` の内部の構造に頼る（`frontend/src/pages/MemberManagement.tsx`）
確かめの道具・テストの安定:
- 確かめ用の運営（`is_staff`）と本人ひとりの組織の利用者が `backend/accounts/management/commands/seed_e2e.py` に無い。I620 の test-gate では開発の DB に手で作った（コンテナの中のコマンドに「password」が入り、承認が要った）
- ログイン直後・登録直後の通知（react-hot-toast・`frontend/src/App.tsx` の `Toaster` の `position="top-right"`）が右上のユーザーメニューの「ログアウト」に重なり、通知の上にマウスがあると通知が消えないので押せない。E2E（`registration-link.spec.ts`）は通知が消えるのを待つ形で避けたが、画面の重なり自体は残る
- `e2e/tests/settings.spec.ts` の TC-28（目標時間を保存して再読み込み）が、E2E 全体を並行で流したときだけ 1 回落ちた（単独では通る。TC-28 と `dashboard-layout.spec.ts` の TC-27 が同じ利用者 `e2e_user_c` を使う）

### 根本原因
- 経緯: レビューの止める基準（Medium 以上・再現あり・差分の中）に当たらない指摘と、敵対的レビューの上限（2 周）の後に残った Medium を、I620 の中では直さなかった
- 項目ごとの技術的な原因: M1 は URL の正規表現が UUID の形を保証せず、`get_object` と違って削除の引き当てに形の誤りを 404 にする処理が無い／M2・L はテストが options の側だけで、同時使用のテストが実行の順に頼る／F4 は存在の確認と作成が別の問い合わせ（原子的でない）／F5 は画面のメニューの判定と裏側の `IsOrgMemberManager` が別に書かれている／F6 はシリアライザの既定のエラー文を上書きしていない／F7 は押したときの取り直しの失敗を一般の登録の失敗と同じ文にしている／F8 はダイアログの値を閉じた瞬間に捨てる・追加の流れの発行に送信中の印が無い／F9 はテストが別のプロセスに今の環境変数を渡している／F10〜F12 は MUI の内部の構造（クラス名・要素の入れ子）に頼った書き方
- 初期データ（`seed_e2e`）に、運営と本人ひとりの組織の利用者が無かった（I620 で初めて要った）
- 通知の置き場所（右上）とユーザーメニューの位置が重なる（既存の作り。I619 の E2E でも同じ待ちが要った可能性）
- settings.spec の不安定さの原因は未特定。計画で調べる（同じ利用者 `e2e_user_c` を並行で使う spec どうしの干渉が第一の候補）

### 解決方針
- M1: 削除の action で `passkey_id` を `uuid.UUID` に直してから引き（形が違えば 404）、テストを足す
- M2・L: `complete` の側に、期限切れ・失効・無効の利用者・無効の組織の parametrize のテストを足す。同時使用のテストは、1 本目が鍵を持っている間に 2 本目が待つ形を作る（順序に頼らない）か、鍵を外したときに必ず落ちる形にする（方式は計画で決める）
- F4: 作成を `IntegrityError` で受けて 400（重複と同じ文）にする
- F5: メニューを出す条件を裏側と同じにする（`UserSerializer` に裏側の判定の結果〔例: メンバーを管理できるか〕を出す形を推奨。方式は計画で決める）
- F6: `user_id` のエラー文を日本語にそろえる
- F7: 押したときの options が 4xx なら「使えないリンク」の案内に切り替える。押すたびに取り直す今の作りは変えない（Safari・iOS の実機の確かめと、出なかったときの直しは #637）
- F8: 閉じるアニメーションの間も見出しを保つ。追加の流れの発行の二度押しを止める
- F9: テストで `REGISTRATION_LINK_BASE_URL` を消した環境を作り、土台の値（`FRONTEND_URL`）も確かめる
- F10・F11: E2E を `getByRole('table', { name: 'メンバーの一覧' })` から辿る形にし、3 つのボタンの行も確かめる
- F12: 列の幅の指定をセルの部品の `sx` に移し、操作の部品に「横に並べる」指定を props で渡す
- 初期データ: `seed_e2e` に確かめ用の運営と本人ひとりの組織の利用者を足し、`docs/runbooks/frontend-verify.md` §5 のアカウントの表に足す
- 通知の重なり: `frontend/src/App.tsx` の `Toaster` の `position` を `top-center` に変える（右上のユーザーメニューと右下のクイズ管理の［＋］ボタンに重ならない）。E2E の「通知が消えるのを待つ」回避は外せるなら外す
- settings.spec: 原因を計画で調べて直す（利用者の干渉なら、spec ごとに別の利用者にする・直列にするなど。方式は計画で決める）
- 着手の順: 敵対的レビューの M1・M2・L を先に、その後 F4〜F12・初期データ・通知・settings.spec
