## 背景/目的

**背景**: I151 の自動テスト・手動テスト・マージ後確認で、pytest / ruff / pip-audit / npm audit / 読み取り専用の `manage.py shell` など、**読み取り・テストだけの操作**で承認待ちが繰り返し発生し、作業が大きく滞った。ユーザーから「絶対に必須な確認か？もっとサクサク進めてほしい」と指摘があった。
**目的**: 本当に危険な操作（`docs/runbooks/danger-ops.md` の定義）だけが確認・ブロックされ、それ以外の操作は auto mode の判断で止まらずに進む状態にする。安全性は落とさない（危険操作の捕捉と人の承認は、決定論的な見張りで担保する）。

### 現状の問題（証拠・再現手順）
1. `.claude/settings.json` の `permissions.ask` に `Bash(docker compose exec *)` が一律で入っており、auto mode が安全と判断できる操作でも毎回プロンプトが出る（画面表示: `Ask rule Bash(docker compose exec *) overrides auto mode for this command.`）。
2. 過去 51 セッションの記録を集計した結果（2026-10-16・scratchpad の集計スクリプト）、ask 対象コマンドの実行は計 125 回で、うち **`docker compose exec` が 120 回（約 96%）**。中身は pytest・ruff・pip-audit・npm audit・`manage.py shell -c`（読み取りや APIClient での疎通確認）が大半だった。
3. `permissions.allow` の 68〜77 行目（`docker compose exec backend pytest *` 等 10 行）は**一度も効いていない**。理由は (a) ask が allow より優先されること、(b) 実際のコマンドには `-T` が付いていてパターンに一致しないこと。
4. ask のうち、次の項目は危険な形だけを見張りが既にブロックしており、ask は二重で冗長:
   - `git reset *` → 危険なのは `--hard` のみ（guard 483 行目でブロック済み）
   - `docker compose down *` / `docker-compose down *` → 危険なのは `-v/--volumes` のみ（guard 487 行目でブロック済み）
5. `git merge *` / `git cherry-pick *` は手元のブランチにしか影響せず、取り消しもできる（develop/main への push は deny ＋ guard でブロック済み）。danger-ops.md の定義にも含まれない。
6. 既存 guard の破壊的 SQL 判定が、SQL 文の先頭にある `DROP` / `TRUNCATE` / `DELETE FROM` と単一引用符の `-c '...'` を見逃す（設計確認メモ 2 項目目）。
7. 既存 guard の hard-block が、絶対パスの `rm -rf` をすべて解除不能で止める（設計確認メモ 4 項目目）。
8. `manage.py flush` / `migrate <app> zero` / `dropdb` / `psql ... < dump.sql` / shell 内の `.delete()` は、どれも guard を素通りする（2026-10-16 にフックへ直接入力して exit 0 を確認）。

### 根本原因
権限設定が「コマンドの種類」で一律に確認をかけており、「その操作が危険かどうか」で判定していない。コンテナ内で何を実行するかは見ていないため、テスト実行と DB の全削除を区別できず、安全側に倒して全部止めている。一方で、guard はコンテナ内の危険操作をほとんど捕捉できず（問題 6・8）、`DANGER_OK=1` 付きの操作に人の承認をかける役目も ask ルールに頼っていた。そのため ask を外せなかった。

### 解決方針
1. **見張りを先に強化する**（`pretooluse_guard.py`）:
   - (a) **破壊的 SQL 判定の是正**: 判定語を単語境界で照合し（先頭一致を含む）、`-c "..."` と `-c '...'` の両方を対象にする。対象は `DROP` / `TRUNCATE` / `ALTER TABLE` / WHERE なしの `UPDATE` と `DELETE`。ホストの psql とコンテナ内の psql の両方に効く。
   - (b) **コンテナ内の危険操作の追加**（判定は書き出しに依存させず、中のコマンドがどこにあっても当てる。ホストで直接実行・`docker exec`・`docker compose exec/run`・`docker-compose exec/run`・`-T` / `--rm` / `-e` / `--user` などのオプション付き・`bash -c` / `sh -c` で包んだ形のどれでも同じ結果にする）:
     - `manage.py flush` / `sqlflush` / `reset_db` などの DB 全消去
     - `manage.py migrate` に位置引数が 2 つあるもの（`migrate <app> zero` や `migrate <app> <マイグレーション名>` の巻き戻し）
     - `dropdb` / `pg_restore --clean` / `psql ... < ファイル` / `psql -f <ファイル>`（ダンプ・SQL ファイルの流し込み）
     - `manage.py loaddata`（既存の行の上書き）
     - `redis-cli FLUSHALL` / `FLUSHDB`（ログイン状態・celery の待ち行列・レート制限カウンタの全消去）
     - `manage.py shell -c "..."` 内のデータ削除・一括更新（設計確認メモの 5 種のパターン）
   - (b2) **コンテナ経由の外部送信（メール・OpenAI）の確認**: 設計確認メモの 5 種の兆候（4 種目の `bash -c` / `sh -c` で包んだ形は 5 種目にも適用）があれば `permissionDecision=ask` を返す（exit 2 ではない）
   - (b3) **実行されるファイルの中身の判定**: `manage.py shell < ファイル`・`python ファイル.py`・コンテナ内の `bash` / `sh ファイル` で実行されるファイル（ホストの bash スクリプトと `scripts/claude/` 配下は対象外）を特定できるときは、その中身にも (a)(b)(b2) の判定をかける。コンテナ内のパスは compose のマウント（`/app/docs/` → `docs/`・`/app/` → `backend/`）で読み替える。読めなければ判定を飛ばし、標準エラーにその旨を出す
   - (c) **`rm -rf` hard-block の是正**: ルート `/` そのものだけを解除不能で止める。それ以外の `rm -rf` は通常の危険操作として扱う。
   - (d) **`DANGER_OK=1` の扱いの是正**: `DANGER_OK=1` 付きでも危険操作に該当すれば、素通しせず `permissionDecision=ask` を返して人の承認を求める。すべての解除経路に一律で適用する。
2. **ask から外す**: `docker compose exec *` / `run *` / `down *`（`docker-compose` 表記も含む）、`git reset *`、`git merge *`、`git cherry-pick *`。
3. **効いていない allow を整理する**: 68〜77 行目の 10 行を削除する（ask を外すと auto mode の判断に任せるため不要。残すと誤解を招く）。あわせて、効いていない `Write(...)` ルール（allow 5 行・deny 5 行）を削除する。Claude Code 起動時に「`Write(docs/**) is not matched by file permission checks — only Edit(path) rules are`」と警告が出ており、同じ範囲は既存の `Edit(...)` ルールが既にカバーしている（deny の `.env` / `secrets` / `*.pem` / `*.key` も `Edit(...)` 側で拒否済み）。
4. **残すもの（変更しない）**: `rm *` / `mv *` / `cp *`（未コミットの記録ファイルが多く、削除・上書きは戻せない）・`psql *`（ホスト上で直接実行する psql。`-f` や標準入力経由の SQL を guard で判定しきれないため ask を残す）・`git rebase *`（danger-ops に「大規模 rebase」と明記）・`chmod *` / `chown *`（使用 0 回・負担なし）。
5. 依存ファイル・マイグレーション編集時の guard の ask（`HIGH_RISK_EDIT_PATTERNS`）は、価値判断が要る変更のため**維持する**。
