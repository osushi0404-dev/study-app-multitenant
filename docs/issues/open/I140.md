# I140: 登録APIの personal 組織自動作成が category 未指定で IntegrityError — フォールバックパスの修正

## 設計確認メモ（/grill-me）
- Q: フォールバックパスの修正方式は (a) 既定カテゴリを解決して自動作成を継続 / (b) 自動作成を廃止 のどちらか → A: **(b) を採用**。フォールバックの `Organization.objects.create()` を削除し、personal 組織不在時は None を返して既存の 400 分岐（`views.py:78-84`・「組織の設定に失敗しました」）に載せる。理由: personal 組織は migration 0014/0017/0018 で常に存在する設計が正であり、未認証の登録 API が組織（＋カテゴリ）を作る隠れた書き込みパスは環境の壊れを隠すため廃止する
- Q: (b) の応答文言とログの扱い → A: ユーザーへの応答は既存 400 応答を形式変更なしで流用。サーバーログは現行の `logger.warning("Personal organization was missing, created new one")` を、personal 組織不在＝環境異常を明示する `logger.error` に置き換える
- Q: personal 不在を 400 で返すのは意味論上は理想（サーバー起因＝500）と差分があるがどうするか → A: 500 化には広域 `except Exception` の撤去が前提のため、本イシューでは既存 400 契約を維持。500 への再分類は受け皿イシュー I142（#253）の本文に「slug 指定の組織不在=400 維持 / slug なし personal 不在=500 へ再分類」を追記して引き継ぐ（2026-07-19 追記済み）

## 背景/目的

### 現状の問題（証拠・再現手順）
- `UserRegistrationView._get_organization()`（`backend/accounts/views.py:154-161`）は、slug なし登録で personal 組織（`type='personal'`・`is_active=True`）が 1 件も存在しない場合のフォールバックとして `Organization.objects.create(name='個人利用', slug='personal', type='personal', is_active=True)` を実行するが、**`category` を渡していない**。
- `Organization.category` は **NOT NULL の FK**（`backend/accounts/models.py:51-56`・`null=True` なし・`on_delete=PROTECT`）のため、このフォールバックパスに入ると `IntegrityError` になる（I131 code-review で静的に確認・モデル定義との突き合わせで裏取り済み）。
- 発現条件: dev/本番 DB では personal 組織が migration 0014 で作成済みのため通常は発現しない。**personal 組織が存在しない/非アクティブ化された環境**（新規環境の初期化不備・データ初期化後など）で、slug なし登録（`POST /api/auth/register/`）が失敗する。
- ビュー全体は `except Exception` で 400 に丸めるため（views.py:121-129）、発現時はユーザーに「エラーが発生しました」とだけ表示され原因が露見しない（I131 と同じ丸め問題の影響下にある）。

### 根本原因
フォールバックの `Organization.objects.create()` が、モデルの必須 FK `category` を指定していない実装漏れ。migration 0014 で personal 組織が常に存在する前提が置かれ、このパスが実行・テストされたことがない（自動テスト不在）。

### 解決方針
（grill-me で (b) に確定・2026-07-19。詳細は「設計確認メモ」参照）
- フォールバックの `Organization.objects.create()` を廃止し、personal 組織不在時は None を返して既存の 400 分岐（`views.py:78-84`・「組織の設定に失敗しました」）に載せる。応答形式の変更なし
- 現行の `logger.warning` は、personal 組織不在＝環境異常を明示する `logger.error` に置き換える
- 再発防止テスト（personal 組織不在状態での slug なし登録が 400 になり、組織が新規作成されないこと）を追加する
- 400/500 の意味論: personal 不在は本来サーバー起因（500 相当）だが、広域 `except Exception` の撤去を含む例外設計見直しは I142（#253）で実施するため、本イシューでは既存 400 契約を維持し、500 への再分類は I142 へ引き継ぐ
