## 設計確認メモ（/grill-me）

### 基本方針（2026-10-19 確定・ユーザー指示）
- 公式（Claude Code）が提供する機能はなるべくそのまま使い、自作は「公式に無い部分」だけを公式の上に足す。公式の処理を置き換える・無効化する案は採らない。

### 事前調査（コード・公式・スパイクで自己解決）
- 内蔵ワークツリー機能（`claude --worktree`・サブエージェント `isolation: worktree`・`EnterWorktree` ツール）はハーネス内で未使用（`.claude/`・`scripts/claude/`・`docs/runbooks/` を grep して該当なし）。ただし Claude のツール一覧に `EnterWorktree` があり、Claude が依頼に応じて使い得る。
- 内蔵機能の基点: `worktree.baseRef` 既定 `"fresh"`＝リモートの既定ブランチ。本リポジトリの既定ブランチは `develop`（`gh repo view --json defaultBranchRef` で確認）なので空ツリー（main 基点）の問題は起きない。**（2026-10-21 訂正・敵対的レビュー）** 公式は既定ブランチを GitHub ではなく手元の `refs/remotes/origin/HEAD` で決める。実物の primary では clone 時のまま `origin/main` を指しており、そのままでは空ツリーになる。`worktree.md` §2 の「作る前の確認」で `git remote set-head origin --auto` により `origin/develop` に合わせる。
- Docker のビルドコンテキストは `./backend`・`./frontend` のみ（`docker-compose.yml`）。リポジトリ直下の `.claude/worktrees/` はイメージに入らない。
- スパイク（2026-10-19・使い捨てリポジトリで `claude -p` 2.1.302 を実行。手順と結果の要約は「## 制約・引き継ぎ情報」）:
  - S1: WorktreeCreate フックは `--worktree`・サブエージェント `isolation: worktree`・`EnterWorktree` の 3 経路すべてで発火する（入力は共通項目＋ `name`。サブエージェントの `name` は `agent-<id>`）。
  - S2: WorktreeCreate フックを登録すると、変更なしのサブエージェント用ワークツリーが自動削除されず残り、`ExitWorktree`（remove）も「状態を確認できない」として拒否される。フック未登録なら両方とも正常に削除される。→ 置き換え型フックは公式の自動片付けを壊す。
  - S3: `.worktreeinclude` は入れ子パス（例 `sub/.env`）の gitignore 済みファイルも新ワークツリーにコピーし、コピーされたファイルがあっても自動片付けは正常に働く。
  - S4: WorktreeRemove フックは単独登録（WorktreeCreate なし）では発火しない（サブエージェントの自動削除時に呼ばれなかった）。→ 公式の片付けに Docker の後始末を足すことはできない。
  - S5: サブエージェントのツール実行時、PreToolUse フックのプロセス cwd はサブエージェントのワークツリー（入力 `cwd` も同じ）。`CLAUDE_PROJECT_DIR` は親リポジトリ。
  - S6: 現行の横断書込ガード（`_cross_worktree`）は、入れ子ワークツリー（`.claude/worktrees/<name>/`）の中から自分自身のファイルを編集しようとすると、親ワークツリー配下と誤判定してブロックする（exit 2）。親→入れ子・入れ子→親の書込ブロックは正しく働く。原因: 判定が「cur 以外のいずれかの root の配下か」で、パスを含む最も内側の root を見ていない。
- (C) 共有物の注意は追記のみで設計判断なし（質問省略）。
- 本イシューは lint/audit 等のツール出力で完了基準が決まるイシューではないため、ツール実走による AC 確定は対象外。

### 確定事項
- Q: 人が長く使うワークツリー（例: ハーネス改善の 2 つ目）の作り方は？ → A: 公式の `claude --worktree <track>-<連番>`（例: `claude --worktree harness-2`）に切り替える。必ず primary（`study-app-multitenant`）から作る（作成元フォルダの中に作られるため。primary は撤去対象外なので巻き込み削除が起きない）。配置は `<primary>/.claude/worktrees/<track>-<連番>/`、初期ブランチは公式の `worktree-<name>`（作業ブランチは `/plan-issue` が作る。不要になった `worktree-<name>` は手元から削除してよい）。`scripts/claude/wt-new.sh` は廃止し、公式に無いポート割当だけを新スクリプト `scripts/claude/wt-ports.sh` に切り出す。
  - 撤回: 1 回目の grill-me で決めた命名 `wt-<track>-<連番>`（primary と並ぶ場所への wt-new.sh 作成）は、この確定で置き換える。
- Q: 既存の `wt-harness`（`/mnt/c/app/wt-harness`・旧方式）はどうするか？ → A: 今そこで進めているイシュー（I178・I179）が完了・クローズした後に、`wt-remove.sh` で撤去し、必要なら公式方式で作り直す。I179 は `wt-harness` 上で進めるため、I179 の中では移行手順を `worktree.md` に書くまでとし、実際の移行は I179 の完了記録に「残作業」として残す。primary はワークツリーの親なので移行しない。
- Q: primary（`study-app-multitenant`）の「アプリ開発専用」をどうするか？ → A: 専用指定を廃止し、どのトラックでも使ってよい。採番は `next-issue-num.sh` がどのワークツリーからでも大域一意を返すため、primary を採番権威として特別扱いする理由はない。primary の役割は「ワークツリーの作成元（親）」として残る。トラックは GitHub ラベル（`track:harness` / `track:app`）で区別し、ワークツリーは作業場所として複数可。
- Q: 同一ワークツリーで次イシューに移る手順は？ → A: 切替用スクリプトは作らない。新ブランチは `/plan-issue` が作成する。`worktree.md` には「未コミット変更を片付けてから `/plan-issue` を実行する」とだけ書く。
- Q: （grill 中に判明）`/plan-issue` が `git checkout develop` を経由するため、別ワークツリーが develop をチェックアウト中だと失敗する。どうするか？ → A: 本イシューで直す。`git fetch origin` ＋ `git checkout -b feature/I<番号>-<概要> origin/develop` の形にし、develop をチェックアウトしない。同じ手順を載せている `docs/runbooks/issue-flow.md` ステップ5 も同時に更新する。
- Q: §10 の手書きトラック構成表をどうするか？ → A: 表を削除し、「現在の状態は `git worktree list` で確認する」の案内と、トラック⇔ラベル対応（`track:harness`／`track:app`）だけを残す。
- Q: 設定ファイル（`backend/.env`・`e2e/.env.e2e`）のコピーは？ → A: 公式の `.worktreeinclude`（リポジトリ直下・新規）に `backend/.env` と `e2e/.env.e2e` を書く。これで `--worktree`・サブエージェント・`EnterWorktree` のすべてでコピーされ、公式の自動片付けも保たれる（S3）。WorktreeCreate / WorktreeRemove フックは使わない（S2・S4）。
  - 撤回: 1〜2 回目の grill-me で決めた「WorktreeCreate / WorktreeRemove フックから wt-new.sh / wt-remove.sh の中核を呼ぶ」「EnterWorktree 経路の作成後検査」は、S1・S2 の結果と基本方針により撤回。
- Q: ポートの割当は？ → A: 作成時には割り当てない。Docker を起動するワークツリーでだけ、起動前に `scripts/claude/wt-ports.sh` を bash で 1 回実行し、直下 `.env` に `DB_PORT`/`REDIS_PORT`/`BACKEND_PORT`/`FRONTEND_PORT` を生成する（割当規則は現行 wt-new.sh の I097 ロジック＝STEP 10・既存ワークツリーを走査して空きオフセット・衝突時 fail をそのまま移す）。実行し忘れてもポート衝突は Docker がエラーで止めるため気づける（静かな誤動作にならない）。
- Q: Docker のデータ（コンテナ・named volume）の片付けは？ → A: Docker を起動したワークツリーは `wt-remove.sh` で撤去する（`docker compose down -v` → `git worktree remove`）。Docker を起動していないワークツリー（サブエージェント用など）は公式の自動片付けに任せる。公式の片付けで消してしまった場合に備え、残ったコンテナ・データ置き場を見つけて消す手順（`docker compose ls -a` で一覧）を `worktree.md` に書く。
- Q: wt-remove.sh の `DANGER_OK=1` 必須をどうするか？ → A: 当該ワークツリーの Compose プロジェクト（既定＝ディレクトリ名）に属するコンテナ・named volume が 1 つも無い場合は `DANGER_OK` なしで `git worktree remove` まで進める（`down -v` は実行しない）。1 つでもある場合と、判定に失敗した場合（docker 不在・コマンド失敗）は従来どおり `DANGER_OK=1` 必須（fail-safe）。撤去後のブランチは削除せず残す。（**2026-10-21 改訂・敵対的レビュー**: データありは `DANGER_OK=1` で `docker compose -p <既定名> down -v`。消す相手を確定できない＝名前の指定・コンテナの作業フォルダが別・同名の別ワークツリーは `DANGER_OK=1` でも停止。docker が使えない場合は停止し、`KEEP_DATA=1`（`DANGER_OK` とは別の合図）のときだけ `down -v` をせずに撤去。詳細は計画書 4-6・Danger Ops）あわせて、公式方式の配置（`<primary>/.claude/worktrees/<name>/`）のワークツリーも撤去対象として指定できるようにする（現行は `<base>/wt-<track>` 固定）。
- Q: 横断書込ガードの入れ子誤判定（S6）は？ → A: 本イシューで直す（入れ子ワークツリーを使う前提のため必須）。対象パスを含む最も内側（最長一致）のワークツリー root を求め、それが現ワークツリーでなければ「別ワークツリー」と判定する。親→入れ子・入れ子→親のブロック、fail-safe、`DANGER_OK` 非解除は維持。I174 が同じファイルを大きく改修中のため、I174 が先にマージされた場合は develop を取り込み直して衝突を解消する。
- Q: 入れ子配置で本体の検索結果が重複する懸念は？ → A: `.gitignore` に `.claude/worktrees/` を追加する（Cursor の検索・Claude の検索ツールは gitignore を尊重）。`grep -r` 等の gitignore を見ないコマンドでは混ざる旨を `worktree.md` に注意として書く。

## 背景/目的

**背景**: 2026-10-18、ハーネス改善トラック用に 2 つ目のワークツリーを作ろうとした際、`docs/runbooks/worktree.md` を確認したところ「1 トラック＝1 ワークツリー」前提で同一トラックの 2 つ目が定義されていなかった。これを機にルール全体を Anthropic 公式のワークツリー機能・ベストプラクティスと比較評価し、複数の不整合・欠落が見つかった。grill-me（3 回）とスパイクで対応範囲と方式を確定し、本イシュー内で実施する。
**目的**: (1) ワークツリーの作成・片付けを公式機能（`claude --worktree`・`.worktreeinclude`・自動片付け）に寄せ、自作は公式に無い部分（ポート割当・Docker の後始末・横断書込ガード・採番）だけにする。(2) 運用ルールを現在の実際の使い方（同一トラック複数ワークツリー・ワークツリーの複数イシュー使い回し）に合わせる。

### 現状の問題（証拠・再現手順）
評価で判明した問題（A〜H。G は grill-me 中、H はスパイクで判明）:

- **(A) 同一トラック複数ワークツリーが未定義**: `worktree.md` §2「トラック単位で作業ツリー」・§10「トラック = 1 作業ツリー」。ハーネス改善用の 2 つ目を作る運用が書かれていない。また primary（アプリ開発用と定義）で harness の I174 を「例外」として実施中であり、定義と実態がずれている。
- **(B) ワークツリーを複数イシューで使い回す切替手順が無い**: 実際は `wt-harness` が I146 → I178 → I179 と使い回されている（`git worktree list` で確認）が、次イシューへの移り方が未記載。
- **(C) 全ワークツリー共有物の注意が不足**: §7 に git stash スタック・git config（hooks 含む）が全ワークツリー共有である点が無い。素の `git stash pop` で他セッションの退避分を取り出す危険がある。
- **(D) §10 のトラック構成が陳腐化**: 「2026-07 時点」のスナップショットのまま、実態と一致しない。手書きスナップショットは構造的に古くなる。
- **(E) wt-remove.sh の使い勝手**: Docker を使っていないワークツリーでも `DANGER_OK=1`（`docker compose down -v`）必須で撤去できない。撤去後のブランチの扱いも未記載。撤去対象が `<base>/wt-<track>` 固定。
- **(F) 作成が自作スクリプト中心で公式機能と二重になっている**: 公式の `claude --worktree`／サブエージェントの `isolation: worktree`／`EnterWorktree` は `.claude/worktrees/<name>/` に作成し、`wt-new.sh` の安全策（`backend/.env` コピー・ポート割当）を通らない。一方 `wt-new.sh` は公式の `.worktreeinclude`・自動片付けと役割が重なる。
- **(G) `/plan-issue` のブランチ作成が複数ワークツリーで失敗し得る**: `.claude/skills/plan-issue/SKILL.md`（23〜25 行目）と `docs/runbooks/issue-flow.md` ステップ5（219〜221 行目）が `git checkout develop` → `git pull` → `git checkout -b` の順。git は同じブランチを複数ワークツリーで同時にチェックアウトできないため、別ワークツリーが develop をチェックアウト中だと失敗する。
- **(H) 横断書込ガードが入れ子ワークツリー自身の書込を誤ってブロックする**: スパイク S6。`pretooluse_guard.py` の `_cross_worktree`（263〜279 行目）・`_block_cross_worktree`（371〜386 行目）。公式方式（`.claude/worktrees/` 配下）を使うと、そのワークツリーの中から自分のファイルを編集できない。

評価で確認した強み（維持対象）: セッション分離・ポート分離・Docker volume 分離・採番単一化・横断書込ガードは公式ガイダンス（ポート/DB 等の共有資源に言及なし）より手厚い。

### 根本原因
- A/B/D/G: ルール・手順が作成当時（2 トラック・各 1 ワークツリー・単一作業ツリーでのブランチ切替）の構成を前提に書かれ、その後の運用変化に追従していない。
- C/E: 作成時の検討範囲外（共有物の洗い出し・Docker 非使用ケース）。
- F/H: 自作スクリプトが Claude Code 側に後から入った公式ワークツリー機能より前に作られ、公式機能（入れ子配置・自動コピー・自動片付け）を前提にしていない。

### 解決方針
設計確認メモの確定事項に従い、A〜H をすべて本イシューで対応する（見送りなし）。
- A/F: 人が使うワークツリーは primary から `claude --worktree <track>-<連番>` で作る。`.worktreeinclude` で `backend/.env`・`e2e/.env.e2e` をコピー。`wt-new.sh` は廃止し、ポート割当を `wt-ports.sh` に切り出す。WorktreeCreate / WorktreeRemove フックは使わない。primary の「アプリ開発専用」「採番権威」の特別扱いを廃止。既存 `wt-harness` の移行手順を書き、実移行は I178・I179 完了後の残作業とする。
- B: `worktree.md` に「未コミット変更を片付けてから `/plan-issue` を実行する」を追記。
- C: `worktree.md` §7 に stash・git config 共有の注意（素の `git stash` / `git stash pop` 禁止・`git stash push -u -m <タグ>` ＋ SHA 指定 `apply`）を追記。
- D: §10 の手書き構成表を削除し、`git worktree list` 案内とトラック⇔ラベル対応のみ残す。
- E: `wt-remove.sh` を、Compose のコンテナ・named volume が無ければ `DANGER_OK` 不要、あれば（または判定失敗なら）必須に変更（**2026-10-21 改訂・敵対的レビュー**: データありは `DANGER_OK=1` で `docker compose -p <既定名> down -v`。消す相手を確定できない＝名前の指定・コンテナの作業フォルダが別・同名の別ワークツリーは `DANGER_OK=1` でも停止。docker が使えない場合は停止し、`KEEP_DATA=1`（`DANGER_OK` とは別の合図）のときだけ `down -v` をせずに撤去。詳細は計画書 4-6・Danger Ops）。公式配置のワークツリーも撤去対象にできるようにする。ブランチは残す。Docker を起動したワークツリーの撤去は `wt-remove.sh`、それ以外は公式の自動片付け。取り残しの発見・削除手順を書く。
- G: `git fetch origin` ＋ `git checkout -b feature/I<番号>-<概要> origin/develop` に変更し、develop をチェックアウトしない。
- H: 横断書込ガードを「対象パスを含む最も内側のワークツリー root」で判定するよう修正。
- `.gitignore` に `.claude/worktrees/` を追加し、gitignore を見ない検索コマンドで結果が混ざる注意を書く。
