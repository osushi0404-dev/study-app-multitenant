## 背景/目的

**背景**: 開発の流れ（/plan-issue → /implement → /code-review → /test → /retro → /close）は、retro の個別対処で自作のスキル・スクリプトを積み上げて作ってきた。I185 で「公式機能をなるべくそのまま使う」方針を掲げて点検したが、点検は今の自作を 1 つずつ「公式で置き換えられるか」で判定した。そのため、置き換えると失うものがある自作はほとんど「残す」になり、公式の道具を土台にした流れは描かれなかった。
**目的**: 計画からクローズまでの流れを、公式の道具だけで組んだ形を土台にする。自作は、公式だけでは止まらない漏れを止める部分に限り、公式の上に差分として載せる。

### 現状の問題（証拠・再現手順）
- I185 の報告書 §4 は「自作の仕組み → 置き換えられる公式機能 → 失うもの → 判定」の形で、出発点が自作になっている。自作の `/code-review`・危険操作の見張り・採番などは「残す」、レビュー役の定義は「一部だけ」と判定された
- 公式の `/simplify`（重複・無駄の整理）と `/verify`（アプリを動かして確かめる）は、§4 の表に載っていない。今のスキル（`.claude/skills/`）・レビュー役（`.claude/review-agents/`）・スクリプト（`scripts/claude/`）・runbook（`docs/runbooks/`）・CLAUDE.md・`.github/` のどこからも呼んでいない（2026-10-24 に grep で確認）
- 自作の `/code-review`・`/security-review` は公式と同じ名前で、打つと自作が動く。公式の版は使えない状態になっている（I185 報告書 §4・I188）
- 自作の `/code-review` は公式の `/code-review` を呼ばず、`scripts/claude/code-review.sh` から自作のレビュー役（`.claude/review-agents/code-reviewer.md`）に `claude -p` で頼んでいる

### 根本原因
自作を足すとき・見直すときの出発点が、いつも「今ある自作」だった。I185 も同じ形で点検したため、「公式だけで組むとどうなるか」を一度も描いていない（I179 でも、自作スクリプトを活かす前提で発想して手戻りした）。

### 解決方針
①公式の道具だけで組んだ計画からクローズまでの流れを先に描く（公式文書を出典に、各工程でどの公式の道具を使うか）→ ②その流れで止まらなくなる漏れを 1 つずつ挙げる（I185 報告書 §4 の「失うもの」を候補にし、今の自作のゲートが実際に止めた記録で裏を取る）→ ③挙げた漏れのうち、GitHub の CI・ブランチ保護などでも止まらないものだけを、自作の差分として公式の上に載せる。手間や便利さだけの理由では自作を残さない → ④公式の道具を流れに入れたときに失うもの・増える手間（費用・時間・誤検知）は、実際に動かして確かめてから採用する
- 決定済み（2026-10-24・ユーザー回答）:
  - I188・I192 は無いものとして扱い、必要なことは本イシューでもれなく行う（両イシューは本イシューが終わるまで着手せず、結果次第で取り下げる）
  - 対象の工程は、実装・確かめ・レビューに加え、計画・振り返り・クローズも含める
  - 費用は無料の範囲内に限る。有料の公式の道具（`/code-review ultra`〔無料 3 回の後は有料〕・GitHub Actions の Claude 連携〔API の利用料〕）は候補に入れない
  - プルリクエストは 1 本にする
- 公式の道具ごとの採否（`/code-review`・`/security-review`・`/simplify`・`/verify`・サブエージェント定義・フック）は、/plan-issue で実際に動かして確かめ、上記③の基準で Claude が決める

## スコープ
### 含む
- 公式の道具だけで組んだ流れの設計と、自作で載せる差分の決定
- 公式の道具を流れに入れたときの実証（失うもの・増える手間・誤検知）
- 決めた流れへのスキル・スクリプト・runbook の組み直し
- ユーザーの確認を「人がやる手動テスト」と「マージ」だけにする変更と、それに合わせた CLAUDE.md の絶対ルール（承認なしにコード変更を開始しない）の書き換え
- 公式の道具を、流れの中で Claude が自動で動かす形にすること（工程のコマンドはユーザーが打つ）
- `/plan-issue` から手動テストの手前まで続けて進む形にすること（`/implement`・`/code-review`・`/test` を個別に打つ必要をなくす。確かめの工程の中身〔CI と重複する手元のテストの流し直し・`/fix-loop` の戻り先・人の手動テストの位置〕も含めて整える）
- 公式と同じ名前の自作スキル（`/code-review`・`/security-review`）の重なりの解消と、レビュー役（`.claude/review-agents/`＋`claude -p` のスクリプト）の公式のサブエージェント定義への移し替え（必要な場合）
- 止めてユーザーに聞く条件を、設計確認メモの 3 つに絞ること
- 振り返りの改善案の採否と起票（既存イシューへの同梱・新規起票）を Claude が自動で行い、マージの前に一覧で報告する形にすること
- 本イシューの /close で、I188・I192 に残る作業があるかを確かめ、無ければ取り下げを提案すること
### 含まない
- 有料の公式の道具（`/code-review ultra`・GitHub Actions の Claude 連携）の導入
- アプリ（backend/frontend）の変更
- レビューの上限・打ち切り条件そのものの変更（I181 の範囲）
- 定期見直しの仕組みづくり（I186 の範囲）
