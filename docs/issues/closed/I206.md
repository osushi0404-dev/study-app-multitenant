## 背景/目的

**背景**: I202 で、止めない指摘も「台帳の残り」として差分のレビューの入力に出し、直ったら resolved と書けるようにした（台帳の限界の直し）。I202 自身の review-gate（3 周）で、実物のレビュー役が台帳の残りを直していないのに `STATUS=open` で書き直した。その結果、振り直した番号がレビュー役の付けた新しい番号と合流し、合流しなかった 5 件が中身の無い open の指摘（F15〜F19）として台帳に残った。どちらも 1 周目に止めない指摘（F1・F8）として予測されていたもので、止める判定を見逃す向きではないが、台帳の質が周ごとに落ちる。
**目的**: 判定の仕組み（`scripts/claude/code-review.sh` の台帳の更新）を決定論で直し、台帳の番号が合流しない・中身の無い指摘が増えない状態にする。あわせて I202 の台帳の残りを片付ける。I202 で決めた「確かめる 2 点」は、I196（#331）の retro で測るよう引き継ぐ（設計確認メモ）。

### 現状の問題（証拠・再現手順）
- 番号の合流（I202 台帳 F1・Medium）: `scripts/claude/code-review.sh` の `_LEDGER_PY` の `update` で、振り直し先の番号を `next_id`（前の台帳の最大の次）から振る。レビュー役は同じ周に新しい指摘を「入力の最大の番号の次」から付けるので、振り直し先と重なり、`seen` で同じ指摘として合流する。I202 の 2 周目（`_1630.md`）で、台帳の残り F1・F3〜F5 の書き直しの振り直し先が、新しい指摘 F11〜F14 と合流した
- 中身の無い指摘の増え方（I202 台帳 F8・Low）: 台帳の残りを `STATUS=open` で書き直すと、I197-F1 の守り（前の SCOPE を引き継がない）のために毎回新しい番号に振り直す。レビュー役が「今回の差分では直していない」と書き直すたびに、中身の無い open の指摘が増える（`_1630.md` の F15〜F19 は F6〜F10 の書き直し）
- そのほかの台帳の残り（要約。詳細と再現は上の記録の FINDING 行）:
  - adversarial-review.sh: F3（flock の範囲の外の `check_worktree` が、ほかの観点の実験の途中の状態を拾いうる）・F4（読めないログが 1 つで周全体が HIGH）・F5（鍵を取った後の締め切りの確認が鍵の前より緩い）・F10（`flock` の存在確認が無い）
  - code-review.sh: F6（`RISK=up` を種類・計画の判定を見ずに YES にする）・F7（「なし（理由）」のような書き方は再現ありになる）・F9（目印で YES になっても同じ周の `/security-review` は走らない）・F12（`changed_outside_records` が git の失敗を検知しない）・F13（develop の取り込みだけの周でもレビュー役を呼ぶ）・F14（一時ファイルの後片付け）・F20（入力の見出しの表記）・F21（取り消しの一覧の作成の失敗を握りつぶす）・F22（100KB で切ると後ろの取り消しの差分が落ちうる）
  - テスト: F23（`mixed()` の push の失敗を隠す）
  - F15〜F19: F6〜F10 の書き直しの重複（中身なし。直すのではなく台帳の扱いを決める）
- I202 で決めた確かめる 2 点（`docs/reviews/open/I202_review.md` の自律判断の記録）:
  - `RISK=up` の付けすぎ（一度付くと戻らないので、誤って付くとそのイシューは毎回敵対的レビューになる）。次のアプリのイシュー（I196 など）の記録で、付いた件数と理由を見る
  - 実験役を `flock` で 1 本ずつにしたことで、敵対的レビューの締め切り（「実行していない（締め切り）」）による未検証が増えていないか。次に敵対的レビューが走ったイシューの記録で件数を見る

### 根本原因
- 台帳の更新（`update`）の番号の決め方が、「前の台帳」だけを見て、今回のレビューの中の番号を見ていない（振り直し先の番号の範囲が、レビュー役の新しい番号の範囲と重なる）
- 台帳の残りの「open での書き直し」に、受け付ける（前の SCOPE を引き継ぐ＝I197-F1 の穴）か振り直す（中身の無い指摘が増える）かの 2 択しかなく、「何もしない（前の行をそのまま残す）」の扱いが無い
- 残りの指摘は、I202 の止める基準（ハーネスは止める条件の一覧に当たるものだけ）で止めずに台帳に残したもの（意図どおり。片付ける先が要る）

### 解決方針
- 最優先: 番号の合流と中身の無い指摘の増え方を、`code-review.sh` の台帳の更新で決定論に直す（手順・観点は足さない）。直し方（例: 振り直し先を「前の台帳と今回のレビューの番号の最大の次」から振る・台帳の残りの open の書き直しは前の行を変えずに捨てる、など）は計画で Claude が決める。I197-F1 の守り（見せた番号の使い回しで、差分の中の新しい指摘が止まらなくなることを防ぐ）を弱めないこと
- I202 の台帳の F15〜F19（中身の無い重複）の扱い（台帳から除く手段を用意するか、そのまま残すか）は計画で決める
- 残りの指摘は、まとめて採否を計画で決める（直すことで新しいコードを大きく足すものは粗い形を優先・I197 の教訓）
- 確かめる 2 点は I206 では測らない。I196（#331）の retro で件数を見て、設計確認メモの基準（どちらも 1 件でもあれば直す／起票する）に当たれば直す。I206 では引き継ぎを I196 のイシューに書くだけ
