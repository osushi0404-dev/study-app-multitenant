## 設計確認メモ（/grill-me）
- 判断基準（ユーザー指示）: ループ／ハーネスエンジニアリングのベストプラクティスと「開発がサクサク進むか」の観点で問題ないやり方にする。フロントの調査・確認・テストはなるべく自動化し、最低限のエビデンスを残す
- Q: 画面を動かす仕組み → A: Playwright MCP（`@playwright/mcp`・バージョン固定・画面なし〔headless〕）。E2E と同じ Playwright で WSL でも安定し、Claude が 1 手ずつ画面を見て判断できる。Claude in Chrome は WSL での動作が未確認で、ユーザーのブラウザに依存するため採らない。使い捨てスクリプトは MCP で足りない場合だけ
- Q: アプリの起動方法 → A: docker compose で frontend も起動する。ワークツリーごとのポートは `wt-ports.sh` の割り当て（`.env` の `FRONTEND_PORT`）に従い、`localhost:3000` 固定にしない
- Q: ログインに使うアカウント → A: E2E 用の `e2e_user_a`／`b`／`c`@example.com を使い回す（管理者と一般ユーザーの両方がいて権限の確認もできる）。パスワードは `e2e/.env.e2e`。ユーザーがいない場合だけ `seed_e2e` を流す（E2E 用ユーザーだけを作り直す）
- Q: Claude が画面確認をするタイミング → A: `/test` の手動テストで Claude が自分で確かめられる項目は Claude がやる。`/implement` の途中でも必要なら使ってよい。人に頼むのは、Claude では観測できない項目だけ
- Q: 画面の動きを変えたときのテスト → A: 手で確かめるだけで終わらせず、E2E か単体テストを追加・更新する（以後は CI が毎回自動で確かめる）。テストにしにくい見た目の確認だけ、画面キャプチャで確かめる。これは `/code-review` の観点（判断が要るため）とする
- Q: エビデンスを git に入れるか → A: **画像は git に入れない**。理由: ①公開リポジトリなので誰でも見られる ②git は履歴から消せず、リポジトリが重くなり続ける ③画面確認の目的は Claude が自分で確かめることで、長く残す証拠は「CI で毎回動くテスト」と「文章の記録」で足りる。**文章の記録だけコミットする**（既存のテスト記録 `docs/tests/` に「画面確認」の行を足すだけで、新しいファイルは作らない）。1 行の中身: 画面・操作の手順・使ったアカウント・期待した結果と実際の結果・日時・コミット番号・画像のファイル名
- Q: 画像の保存先と削除のタイミング → A: ワークツリー直下の `.evidence/I###/`（`.gitignore` に追加）。PR マージ後のワークツリーの片付けで一緒に消える（削除のための手順を増やさない）。`/close` 後、Approve & Merge の前にユーザーが見られるよう、`/close` では消さない。primary で作業した場合は次のイシューの `/plan-issue` で前のイシューの `.evidence/` を消す
- Q: 確認のし忘れを防ぐ仕組み → A: 決まった判定（スクリプト）にする。`frontend/src` を変えたイシューでは、`/test` でテスト記録に「画面確認」の行が 1 件以上あり、書いた画像が `.evidence/I###/` に実在することを確かめ、無ければ不合格。確認できない理由がある場合は、その理由を書いた行で代えられる
- Q: E2E が失敗したときの記録 → A: 手元は `screenshot: 'only-on-failure'`・`trace: 'retain-on-failure'`（git に入らない `e2e/test-results/`）。CI は失敗時に**画面キャプチャだけ**を Actions のアーティファクトとして 14 日保存する。trace は CI では上げない（ログイン画面で入力したパスワードが trace に記録され、公開リポジトリのアーティファクトは誰でも取れるため）
- Q: 型チェック・lint のコマンド → A: `frontend/package.json` に `typecheck`（`tsc --noEmit`）と `lint`（`eslint src/ --ext .ts,.tsx --max-warnings 0`）を足し、CI もこのコマンドを呼ぶ形にして、手元と CI のずれをなくす
- Q: CRA から Vite への移行 → A: 本イシューで起動・単体テストの所要時間を測り、その数字を付けて別イシューのタイトル案を出す（移行そのものはしない）
- Q: 点検の時間 → A: フロントの開発設定の点検は 30 分を上限とし、結果は計画書に書く（報告書は作らない）
- Q（2 回目の /grill-me・Claude が自己解決）: Playwright MCP で開ける先を絞るか → A: 絞る。開けるのは手元のアプリ（`localhost` / `127.0.0.1`）だけにする（`--allowed-origins`）。ブラウザの状態はセッションごとに使い捨て（`--isolated`）、画像の保存先は `.evidence/`（`--output-dir`）。外部サイトを開けると、画面上の文章に紛れた指示を読む・ログイン情報を外へ送るといった危険が増えるため。各オプションの名前は採用するバージョンの公式ドキュメントで計画時に確かめる
- 型チェック・lint・単体テストの現状（ツール実行で確認）: develop の最新コミット 2be339b で CI（`npx tsc --noEmit`・`npx eslint src/ --ext .ts,.tsx --max-warnings 0`・`CI=true npm test`）が合格している（2026-10-24 の CI 実行結果）。エラー・警告は 0 件なので、「`npm run typecheck`・`npm run lint` で CI が合格する」という受け入れ条件は今の状態で満たせる
- 必須確認: 価値 → Claude が画面を自分で確かめられず、人に頼むか使い捨てスクリプトを書いている現状を解消するため価値あり。コスト → 追加は MCP 1 つ・npm コマンド 2 つ・判定スクリプト 1 つで、保守は小さい。既存方針 → 「公式をなるべくそのまま使う」「手動テストは Claude が自分でできるものは自分でやる」と一致

## 背景/目的

**背景**: 2026-10-24 の会話で「Claude Code はデバッグ実行した画面を見たり、入力・画面遷移・画面キャプチャをしたりできるか」を確認した。Playwright は `e2e/` にすでに入っているので、スクリプトを書けば操作とキャプチャはできる。ただし、Claude が 1 手ずつ画面を見ながら操作する手段（Playwright MCP など）は用意されておらず、フロントの変更を確かめるやり方も、確かめた証拠の残し方も決まっていない。型チェックと lint は CI では動いているが、手元で同じものをすぐ実行するコマンドがない。そのため、Claude が「変更→自分で確かめる→直す」を素早く回しにくい。
**目的**: Claude がフロントの変更を、人に頼まず自分で画面を見て確かめられるようにする（起動・ログイン・入力・画面遷移・画面キャプチャ・コンソールエラーの確認まで）。確かめた証拠は最低限（文章の記録）だけ残し、確認のし忘れは決まった判定で止める。あわせてフロントの開発設定を見直し、確認 1 回あたりの待ち時間と手間を減らす。

### 現状の問題（証拠・再現手順）
- `.mcp.json` には GitHub の MCP しかなく、Claude が画面を見ながら 1 手ずつ操作する手段がない（今できるのは、使い捨てのスクリプトを書いて実行し、保存した画像を読むことだけ）
- フロントの画面確認の手順（起動方法・ワークツリーごとのポート・どのアカウントでログインするか・キャプチャの保存先）と、エビデンスの残し方が決まっておらず、毎回その場で組み立てている
- 型チェック（`npx tsc --noEmit`）と lint（`npx eslint src/ --ext .ts,.tsx --max-warnings 0`）は `.github/workflows/ci.yml` にだけ書かれていて、`frontend/package.json` の scripts は `start`・`build`・`test`・`eject` だけ。手元で CI と同じ確認をするには CI の定義を見てコマンドを組み立てる必要がある
- フロントは CRA（`react-scripts` 5.0.1・TypeScript 4.9 系）で、起動とテストが遅くなりやすい（Vite への移行は未起票）
- E2E は `trace: 'on-first-retry'` だけで、失敗したときに画面キャプチャが残らない
- フロントを変えても、画面で確かめたかどうかを止める仕組みがない
- （I158 で発見）E2E コンテナで 1 ファイルだけ流す `docker compose --profile e2e run --rm e2e npx playwright test tests/<file>.spec.ts --retries=0` は、見張り（`scripts/claude/hooks/pretooluse_guard.py`）の安全一覧に無いため毎回承認画面が出る。一方、標準の起動（`docker compose --profile e2e run --rm e2e`＝コンテナ内で `npm install && npm test`）は確認なしで通る。1 ファイルだけ流す方が、全件を流す標準の起動より危険度は同じか低い。Claude が自分で「直す→流す」を回すときの詰まりになっている
- （I158 で発見）E2E の落とし穴:
  - ホストで `npx playwright test` を動かすと、chromium の起動に要るライブラリがホストに無く失敗する（ブラウザ本体は `~/.cache/ms-playwright/` にあるが、それだけでは動かない）
  - 短い間に続けて流すと、ログインのレート制限（django-ratelimit・403）に当たり global-setup が落ちる。解除まで 5 分待つ必要がある
  - e2e コンテナは `http://frontend:3000` で画面を開くため、ブラウザの「安全なコンテキスト」にならない（`crypto.randomUUID` などが使えない）。CI は `localhost` で開くので、手元のコンテナと CI で動きが違う
  - 開発サーバーに型エラーがあると、webpack のエラー表示（オーバーレイ）が画面を覆い、クリックを遮る

### 根本原因
これまでのハーネス改善は、工程・レビュー・権限の側が中心だった。「Claude がフロントの結果を自分の目で確かめる手段」「確かめた証拠の残し方」「その確認を速く回すためのフロントの設定」は、まとめて決めたことがない

### 解決方針
①Playwright MCP（`@playwright/mcp`・バージョン固定・headless・開ける先は `localhost`／`127.0.0.1` だけ・ブラウザの状態は使い捨て・画像は `.evidence/` に保存）を `.mcp.json` に追加し、`.claude/settings.json` で操作を許可する → ②画面確認の手順（docker compose で起動・`FRONTEND_PORT` に合わせた URL・E2E 用アカウントでのログイン・`.evidence/I###/` への保存・コンソールエラーの確認・テスト記録への 1 行）を `docs/runbooks/frontend-verify.md` にまとめ、公式 `/run` スキルからも使える形にする → ③`frontend/package.json` に `typecheck`・`lint` を足し、CI もそれを呼ぶ → ④E2E の失敗時の記録（手元は画面キャプチャ＋trace、CI は画面キャプチャだけを 14 日保存）を設定する → ⑤`frontend/src` を変えたイシューで画面確認の行と画像の実在を確かめる判定スクリプトを作り、`/test` に組み込む → ⑤' 見張りの安全一覧に、e2e コンテナ内の `npx playwright test`（ファイル指定・`--retries`・`--reporter`・`--grep` など、実行の範囲や表示だけを変える選択肢）を加え、見張りのテストに「通る例」と「通らない例」を足す → ⑤'' I158 で見つかった落とし穴 4 件の対策を計画の調査で決め、`docs/runbooks/frontend-verify.md` に書く → ⑥フロントの開発設定を 30 分上限で点検し、起動・単体テストの所要時間を測る。Vite への移行など大きな改善は数字つきのタイトル案で別イシューにする

## 制約・引き継ぎ情報
- 公式機能をなるべくそのまま使う。置き換える場合は失うものを実証してから決める
- 公開リポジトリなので、画像・trace・パスワードを git や CI のアーティファクトに出さない（trace にはログイン時に入力したパスワードが記録される）
- WSL2 上で動かすため、ブラウザは headless 前提。chromium の本体はこのマシンに取得済み（`~/.cache/ms-playwright/chromium-1217`）だが、**I158 で、ホストには起動に要るライブラリが無く失敗すると分かった**。Playwright MCP もホストで chromium を起動するため、同じ問題に当たる見込みが高い。計画の調査で、①ホストにライブラリを入れる（`sudo npx playwright install-deps chromium`・sudo が要るのでユーザーが `!` で実行）②Playwright MCP をコンテナで動かす、のどちらにするかを決める。①なら `localhost` で開けるので安全なコンテキストになり、CI と同じ動きになる
- I158 の落とし穴への対策の方向（計画の調査で確定する）:
  - レート制限: ログインは global-setup の storageState を使い回し、連続実行でログインし直さない。開発環境だけで制限を緩める案は、本番の設定と食い違わないかを確かめてから決める
  - 安全なコンテキスト: 画面確認は `localhost` で開く（上の①）。e2e コンテナの URL の扱いは計画で決める
  - 型エラーのオーバーレイ: 画面確認の前に `npm run typecheck` を通すことを手順にする
- 見張りの安全一覧は「ローカルの安全装置は GitHub が最後の守り前提で最小限に」に従い、文字列の判定を作り込まない。足すのは e2e コンテナ内の `npx playwright test` に限る
- MCP の追加は外部パッケージを取り込むことになるため、バージョンを固定する（`.mcp.json` の GitHub MCP と同じく `@x.y.z` 指定）
- `.github/workflows/` の変更を含むため、計画のあと `/security-review` を通す
- ワークツリーの片付け（`git worktree remove`）で `.evidence/` が消えることを、計画時に実際に確かめる
