- Draft PR: #139
- 起点: I062 のクローズ後監査（「整備済みのはずの規定コマンドが実行時に破綻/不適用で、別手段に逃げていた」ケースの洗い出し）
- 関連: I066（同監査由来のスクリプト/close 側の整合化。本イシューはスキル文言側）

## 設計確認メモ（/grill-me）
- **Q1（1a）→ A: invariant 明文化 ＋ ハンドオフ是正（plan-issue 本体ロジックは原則変更なし）**
  - 確定した正しい流れ: イシューファイルは issue-bootstrap で**ローカル作成（未コミット）**し、**どのコンテキストでも develop に事前コミットしない**。`/plan-issue` が feature ブランチで**初コミット**する。同一ファイルシステムのため context clear をまたいでも untracked ファイルは残り、別コンテキストの plan-issue が拾える（＝develop 事前コミットもハンドオフ PR も不要）。
  - 現行 plan-issue は「ローカル未コミット」の場合は既に正常動作（`git add issue`→`commit`→`push`→`gh pr create` が成立）。よって **plan-issue 本体のロジック変更は原則不要**。
  - 真因（本文1の現象）: I062 は I064 のクローズで I062/I063 のバックログ issue ファイルを **develop へ事前コミット**したため、plan-issue の `commit` が no-op 化し PR が空コミットで失敗した。
  - 修正対象: ① `plan-issue/SKILL.md` に invariant（イシューは feature ブランチで初コミット／develop へ事前コミット禁止）を明記。② **retro/close のハンドオフで新規イシューファイルを develop にコミットしない**（close の一括 `git add` が未コミットの backlog issue ファイルを巻き込まない・retro バックログはローカル作成に留める）。③（任意）plan-issue に防御注記（万一すでにコミット済みなら計画docsコミットで draft PR を作る）。
- **Q2（1b）→ B: /test を plan 駆動にする**。`auto_test.md`（計画書のテスト計画）が指定する自動テストを正として実行し、**指定が無い場合のみ**既定の pytest/jest/e2e にフォールバック。app/非app を区別する分岐は不要。`test/SKILL.md` の手順と `description` を更新。
- スコープ補足: 命名規約 runbook（plan-writing-rules.md / review-rules.md / issue-flow.md）は触らない（I064 棲み分け）。**対象スキルは `.claude/skills/{plan-issue, test, retro, close}/SKILL.md`**（retro/close は 1a ハンドオフ是正分の追加）。本文「想定する反映先」は本メモで plan-issue/test に retro/close を追加する形に更新する。

## 背景/目的

### 現状の問題（証拠・再現手順）

1. **plan-issue スキルの branch→issueコミット→draft PR 規定が「イシュー未コミット」前提で破綻する**
   - 規定（`.claude/skills/plan-issue/SKILL.md`）: `git checkout develop` → `git add docs/issues/open/I###.md` → `git commit -m "docs: create issue I###"` → `git push` → `gh pr create --draft`。
   - 破綻: イシューファイルが既にベースブランチ（develop）にコミット済みの場合、`git commit` は**no-op**（変更なし）になり、その後の `gh pr create` は**「No commits between develop and feature/…」でエラー**になる。
   - 証拠（I062）: `I062.md` は `f0d2c4b close(I064)` で既に develop へコミット済みだった。`git log --all | grep "create issue I062"` = **該当なし**（規定の commit ステップは一度も成立していない）。実運用では計画書 docs を先にコミットしてから draft PR を作る**別手順で回避**した（スキルにこの分岐の記載なし）。

2. **/test スキルが app 変更前提で、非app（スクリプト/ドキュメント/エージェント定義）変更時の自動テスト指定が無い**
   - 規定（`.claude/skills/test/SKILL.md`）: env 判定後に backend `pytest` / frontend `jest` / `playwright e2e` を実行する手順のみ。
   - 破綻: Backend/Frontend 変更が無いイシューでは規定テストが無関係。「何を正の自動テストとするか」がスキルに無い。
   - 証拠（I062）: Backend/Frontend 変更ゼロ、`python -m pytest` ローカル不可。規定テストは未実行のまま「非該当」と宣言し、スキル未記載の `bash scripts/claude/tests/test_review_verdict.sh` を**独自に正として採用**した。放置すると (a) 無関係な pytest 結果を当該イシューのテストと誤認、または (b) 実行者ごとに代替手段がバラつき検証の再現性が失われる。

### 根本原因
- スキルが**典型ケース（イシューは新規・未コミット／変更は app コード）のみを想定**し、前提が崩れるケースの分岐が文書化されていない。結果、実行時に規定コマンドが破綻/不適用となり、その場の判断で別手順に逃げる（＝整備済みワークフローが機能していない）。

### 解決方針（詳細文言は grill-me/plan-issue で確定）
1. `plan-issue/SKILL.md` に分岐を明記: 「イシューファイルが既にベースブランチにコミット済みの場合は、`docs: create issue` コミットをスキップし、最初の計画書 docs コミットを基に draft PR を作成する」。あわせて「イシューファイルは plan-issue の feature ブランチで初コミットするのが原則（ベースに事前コミットしない）」を前提として明記。
2. `test/SKILL.md` に分岐を明記: 「Backend/Frontend に変更が無いイシュー（スクリプト/ドキュメント/エージェント定義のみ）では、計画書が指定する専用自動テスト（例: 専用テストスクリプトの `bash` 実行）を正とし、pytest/jest/e2e は『非該当』と明示記録する」。

### 想定する反映先（既知のもの）
| ファイル | 変更内容 |

| `.claude/skills/test/SKILL.md` | 計画駆動化（auto_test.md を正・指定/欠損時のみ既定にフォールバック・pytest等は非該当明記）＋停止条件に計画書指定テストの失敗を追加 |
