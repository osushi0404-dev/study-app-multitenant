- Draft PR: #219
- 発見経緯: I107 クローズ時の実証事象（2026-07-15・PR #202）。/close 完了・マージ依頼後に base（develop）へ別 PR（#201/I103）がマージされ、PR #202 が「This branch is out-of-date with the base branch」となり、ユーザー報告を受けて手動で origin/develop マージ→push→CI 再確認を実施した

## 設計確認メモ（/grill-me）
- Q: step 0 で BEHIND 検知時、push＋CI 確認まで行うか → A: 行わない。step 0 は fetch → merge まで（コンフリクト時 STOP）。push は step 3 の close コミット push に相乗りさせ、CI 実行を1回にまとめる。これにより CI が確認する対象＝実際にマージされる最終の中身が一致する
- Q: 最終チェック（Ready 化直後）の合格条件 → A: 「CLEAN」ではなく「**BEHIND / DIRTY でない ＋ CI 全グリーン**」。本リポジトリはユーザーの Approve がマージ条件のため、承認前の正常な最終状態は BLOCKED（CI 全緑・承認待ちのみ）。CLEAN を待つ設計は正常系で永遠に合格しない
- Q: 実装形態（SKILL.md 記載のみか、スクリプト新設か） → A: スクリプト新設（根治案）。scripts/claude/pr-base-sync.sh を新設（code-review.sh の CI 待機ループを流用）し、SKILL.md からは呼び出すだけにする。scripts/claude/tests/test_pr_base_sync.sh に決定論テストも追加
- Q: UNKNOWN リトライと CI 待機の具体値 → A: UNKNOWN リトライは 5 秒間隔×6回（計30秒）・上限到達時は値を報告して続行可否をユーザーに確認。CI 待機は code-review.sh と同じ 15 秒間隔・上限 600 秒
- Q: イシュー未列挙の3値（DRAFT / HAS_HOOKS / UNSTABLE）の扱い → A: HAS_HOOKS＝CLEAN 同等で続行。UNSTABLE＝`gh pr checks` 併読（pending は待機・fail は STOP 報告）。DRAFT＝step 0 では正常（続行）・Ready 化直後は反映ラグの可能性があるため UNKNOWN と同様に数回リトライし、それでも DRAFT なら STOP 報告
- Q: mergeStateStatus の照会方法 → A: 一覧照会（`gh pr list --json mergeStateStatus`）では計算が走らず UNKNOWN のままになる（2026-07-16 実測）。PR 番号指定の個別照会（`gh pr view <番号> --json mergeStateStatus`）を使う。draft PR でも遅れていれば BEHIND が返ることを PR #218 で実測確認済み

## 背景/目的

### 現状の問題（証拠・再現手順）
- /close スキルは「CI グリーンの確認 → docs 移動 → PR 説明更新 → Ready 化 → マージ依頼」と進むが、**base ブランチ（develop）が close 作業中〜マージ依頼後に進んだ場合の検知・追従手順がない**。
- 実証（2026-07-15・I107）: /close 完了時点で PR #202 は CI 全グリーンだったが、直後に PR #201（I103）が develop にマージされ、ブランチ保護（up-to-date 要求）により PR #202 がマージ不能（out-of-date）になった。検知はユーザーの GitHub 画面目視で、追従（fetch→merge→push→CI 再確認）は依頼ベースの手動対応だった。
- 並行トラック運用（wt-harness / study-app-multitenant の2 worktree 同時進行）では、close 前後に他トラックの PR が base へマージされる事象は構造的に再発する（今回も I103=app トラックと I107=harness トラックの並行完了が原因）。

### 根本原因
- /close スキルに base ブランチの鮮度（PR が base の最新を含むか）を確認するステップがなく、確認タイミングも定義されていない。CI グリーン確認と Approve & Merge 依頼の間に base が進むと、検知が人間の目視頼み（fail-open）になる。

### 解決方針
- GitHub が判定した状態を直接見る決定論的チェックを /close に組み込む（時刻・コミット数の推測に依存しない）:
  - **チェック方法**: `gh pr view <PR番号> --json mergeStateStatus -q .mergeStateStatus`（**PR 番号指定の個別照会**。一覧照会 `gh pr list` では計算が走らず UNKNOWN のままになるため使わない＝2026-07-16 実測）
  - チェック本体は **scripts/claude/pr-base-sync.sh に新設**し（code-review.sh の CI 待機ループを流用）、SKILL.md からは呼び出すだけにする（手続き文書の実行漏れ・承諾プロンプト多発を回避する根治案）
  - マージコンフリクト発生時は自動で進めず **STOP してユーザーに報告**する（fail-closed。自動解決しない）
- **挿入位置は2箇所（実行範囲が異なる）**:
  1. **step 0（開始時）＝取り込みのみ**: `BEHIND` なら `git fetch origin develop` → `git merge origin/develop --no-edit` まで。**push と CI 確認はしない**（push は step 3 の close コミット push に相乗り）。これにより close コミットと base 追従マージが同じ CI 実行にまとまり、CI が確認する対象＝実際にマージされる最終の中身が一致する
  2. **step 5 直後（`gh pr ready` 後・マージ依頼の直前）＝フルチェック**: 最終防衛線。`BEHIND` なら fetch → merge → push → CI グリーン確認（`gh pr checks` の pending 待機 15 秒間隔・上限 600 秒・fail 時 STOP）。**合格条件は「CLEAN」ではなく「BEHIND / DIRTY でない ＋ CI 全グリーン」**（ユーザー Approve がマージ条件のため、承認前の正常な最終状態は BLOCKED＝CI 全緑・承認待ちのみ。CLEAN 待ちは正常系で永遠に合格しない）
- mergeStateStatus 全8値の分岐（GitHub GraphQL docs の MergeStateStatus と照合済み）:
  - `CLEAN` / `HAS_HOOKS`（マージ可・CI 通過）→ 続行
  - `BEHIND` → 上記の追従処理（挿入位置により取り込みのみ / フル）
  - `BLOCKED` → `gh pr checks` を併読して切り分け（CI 全緑なら承認待ちの正常状態として続行。CI fail は STOP・pending は待機）
  - `UNSTABLE`（マージ可だが CI 未通過あり）→ `gh pr checks` 併読（pending は待機・fail は STOP 報告）
  - `DIRTY`（コンフリクト）→ STOP してユーザー報告
  - `UNKNOWN`（GitHub 計算中）→ 5 秒間隔×6回（計30秒）リトライ。上限到達時は値を報告して続行可否をユーザーに確認
  - `DRAFT` → step 0 では正常（続行。draft でも遅れていれば BEHIND が返ることを PR #218 で実測確認済み）。Ready 化直後は反映ラグの可能性があるため UNKNOWN と同様にリトライし、それでも DRAFT なら STOP 報告
