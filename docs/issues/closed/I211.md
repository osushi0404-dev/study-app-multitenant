- Q: 手元で指定の版を入れる手段 → A: uv を手元に 1 回だけ入れる（ユーザーの作業）。python 本体と PyYAML・pre-commit を固定した版で、1 コマンドで作り直せる。OS の python（3.12）は入れ替えない。CI も公式の `astral-sh/setup-uv`・`actions/setup-python` が同じ版のファイルを読む
- Q: 今後 python の版を上げるとき、アプリと一緒に上げるか → A: このイシューはハーネスのテストだけを対象にする。アプリの python を上げるときは、そのとき別イシューにする
- Q: 版上げを Dependabot の PR で受け取る仕組みを入れるか → A: 別イシュー（Dependabot の点検と直し。調べたところ `.github/dependabot.yml` は I028 で入ったが、Dependabot の PR がこれまで 0 件。起票はユーザーが行う）

## 背景/目的

**背景**: I204 でハーネスのテストが頼る道具を一覧（`required-tools.txt`）にまとめ、CI と手元が一覧を通して揃う形にした。ただし I204 は「下限」だけを確かめる。そのため python は手元 3.12・CI 3.11 とずれたままで、PyYAML・pre-commit も手元と CI で入る版が違いうる。ユーザーは I204 の grill-me で「版をぴったり揃えたいが別イシューで」と決めた。
**目的**:
1. python・PyYAML・pre-commit の版が、手元と CI で同じ 1 つの版に揃う。
2. 今後版を上げるときも揃ったままになる。版を上げる流れは「版を書いた 1 か所を書き換える → 手元で入れ直してハーネスのテストを流す → push すると CI が同じ版で流れる」になり、片方だけ上がったら機械的に止まる（ユーザーの要望: 以降バージョンアップがあってもそろうようにしたい）。

### 現状の問題（証拠・再現手順）
- python: CI は `.github/workflows/ci.yml` の harness-tests ジョブ（`ci.yml:158-160`）で `python-version: '3.11'`。手元（WSL の Ubuntu）は `check-tools.sh` の実行で `python3 3.12.3`。一覧も `required-tools.txt:6` で「3.11 以上・ぴったり揃えるのは後続のイシュー」と書いている。
- PyYAML: 一覧は `PyYAML>=6.0`（`required-tools.txt:7`）。CI は `check-tools.sh --pip-specs` の出力を `pip install -r` で入れるので、その日の最新が入る。手元は `apt install python3-yaml` で入った 6.0.1。版は固定されていない。
- pre-commit: 一覧は `pre-commit>=4.0`（`required-tools.txt:10`）。CI はその日の最新、手元は `pipx install pre-commit` で入った 4.5.1。こちらも固定されていない。
- `check-tools.sh` は下限（`sort -V -C`、`check-tools.sh:67`）だけを見るので、手元と CI の版がずれても通る。

### 根本原因
- 一覧が「下限」しか持たず、ぴったりの版を書く場所が無い。
- CI は「下限以上の最新」を入れ、手元は OS のパッケージ（apt）や pipx で入った版を使うので、両者が同じ版を参照していない。
- 版を上げる手順（どこを書き換え、手元でどう入れ直し、何で揃ったことを確かめるか）が決まっていない。

### 解決方針
- 版を書く場所を 1 か所にする（例: 一覧の列を「下限」から「ぴったりの版」に変える／`.python-version` などの公式の仕組みを使う）。CI（`actions/setup-python` の `python-version` か `python-version-file`、`pip install`）と手元の確かめ（`check-tools.sh`）の両方がそこを読む。
- `check-tools.sh` は版がぴったり一致しなければ止める。`test_i204_tool_sync.sh` は CI と一覧の版が食い違えば止める。
- 版は 3.11 に揃える（手元を CI・アプリに合わせる）。手元は uv で python 3.11 と PyYAML・pre-commit を固定した版で入れ、1 コマンドで作り直せるようにする（今の apt の PyYAML・pipx の pre-commit には頼らない）。uv の環境の置き場所・ロックファイルの形・既存の pre-commit の hooks への影響は計画で決める。公式の仕組み（`python-version-file`・`astral-sh/setup-uv` など）をなるべくそのまま使う。
- 版を上げる手順を runbook に書く（手元で入れ直す → ハーネスのテストを流す → push → CI が同じ版で緑）。

## スコープ
### 含む
- ハーネスのテスト（harness-tests ジョブと `run-all.sh`）が頼る python・PyYAML・pre-commit の版を手元と CI で揃える
- 版を書く場所を 1 か所にし、版を上げた後も揃ったままにする仕組み（片方だけ上がったら機械的に止まる）
- 版を上げる手順の runbook
- I204 の敵対的レビューの Medium（`ci_check` の install 検出の漏れ）と `check-tools.sh` の空行の見た目
### 含まない
- アプリ本体（backend の CI ジョブ・`backend/requirements*.txt`・Docker イメージ）の python の版（いまは harness-tests 以外の `ci.yml:19-21`・`ci.yml:72-74`・`dependency-audit.yml:35-37` も 3.11 で揃っている。アプリの python を上げるときは別イシュー）
- git・docker の版を揃えること（一覧の下限のまま）
- 版上げを自動で受け取る仕組み（Dependabot。別イシュー「Dependabot の点検と直し」で扱う）

## 制約・引き継ぎ情報
- I204 で「一覧が正」「CI は一覧を通して揃える」「install は一覧を読む 1 つだけ」の形にした。この形は崩さない。
- 手元の python 3.12.3 は Ubuntu の OS の python。OS の python は入れ替えず、uv で 3.11 を入れる（grill-me で確定）。
- `.github/workflows/` の変更は push・Actions の変更に当たるので、ローカルの安全装置の対象外（GitHub の保護が最後の守り）。
- 版を上げる流れはユーザーの想定どおり「手元で動作確認 → CI へ上げる」順にする。
