## 背景/目的

**背景**: I166 のレビューで、普通の実験のコマンド（コンテナの中で Python のファイルを動かす等）に見張りの確認画面が出て、裏で動くレビュー役が誰にも気づかれずに止まった。ユーザーが「その確認は必須か」と問い、Claude が調べた結果は「不要」だった。そのコマンドは、コンテナに `.git` も GitHub の認証情報も無いため GitHub を壊せない。壊せるのは未コミットの `backend/`・`docs/` の変更と使い捨ての dev DB だけで、確認なしで通る `manage.py shell -c "..."` と同じことしかできない。
**ユーザーの方針（2026-10-25）**: 「GitHub の破壊行為になるもの・復旧できない状態を実現できるもの・個人情報の流出などセキュリティ的にハイリスクなもの以外は OK（確認なし）にしたい。それ以外にどうしても確認ありにした方がいいものがあるなら残していい」
**目的**: 確認画面を、上の 3 種類（＋どうしても残すと決めたもの）だけに絞る。普通の開発・検証の操作で人の確認が要らないようにして、開発をサクサク進める。

### 現状の問題（証拠・再現手順）
- 見張りが確認を出す 7 種類（`pretooluse_guard.py` の `main()`）:
  1. `DANGER_OK=1` 付きの危険操作
  2. 外部への送信・秘密情報の表示を伴う操作
  3. **コンテナ内の操作を安全と確認できない**（許可リストにない・流し込み・読めない書き方）
  4. 未コミットの変更を消すかもしれない git の操作
  5. GitHub から戻せないことがある操作
  6. 動的・不透明な宛先の push
  7. **見張りがコマンドを読みきれない**（読み落としかけた書き方を含む）
- 許可の設定で確認が出る 16 件（`.claude/settings.json` の `ask`）: `git rebase`・`psql`、編集の `.github/workflows/**`・`.pre-commit-config.yaml`・`.secrets.baseline`・各 Dockerfile・`frontend/nginx.conf`・`backend/requirements*.txt`・`backend/pyproject.toml`・`frontend/package.json`・`frontend/package-lock.json`・`**/migrations/*.py`・`backend/init-db.sql`
- 実測（2026-10-25・`scripts/claude/check-permission-prompt.sh`・通常モード）: 次はすべて承認画面が出る判定だった。
  - `docker compose cp <scratchpad のファイル> backend:/tmp/x.py`
  - `docker compose exec -T backend python manage.py shell -c "exec(open('/tmp/x.py').read())"`
  - `docker compose exec -T -e PYTHONPATH=/tmp backend python -m pytest ... -p <プラグイン>`
  - I166 のレビュー役は `docker compose exec ... python /tmp/<file>.py` の形で確認画面に当たった。
  - 一方、親のセッション（自動承認モード）では同じコマンドが確認なしで通っていた。
- 上の 3（コンテナ内）と 7（読みきれない）は、ユーザーの方針の 3 種類のどれにも当たらない操作でも確認を出している。
- 確認を出した層: I166 の第 2 周でユーザーが見た確認画面は「Hook PreToolUse:Bash requires confirmation: コンテナ内の操作を安全と確認できませんでした（許可リストにない・流し込み・読めない書き方）。確認してください: python /tmp/fg_1.py ...」で、見張りの 3 が出したもの（設定の `ask` ではない）。他の 3 つの形（`docker compose cp`・`manage.py shell -c "exec(...)"`・`pytest -p`）がどの層（見張りの 3・7 か、設定の allow に無いことによる通常の確認か）で確認になるかは、未特定・計画の最初に `check-permission-prompt.sh` の出力（見張りの文言の有無）で確定する。

### 根本原因
見張りが「危ないと分かった操作だけを止める」のではなく、「安全と確認できない操作はすべて人に聞く」（fail-safe）作りになっている（3・7）。経緯: I174 で、`docker compose exec` などの一律の確認をやめて見張りの判定に置き換えた。そのとき、コンテナ内の操作は「許可リストに入るものだけ素通しにし、それ以外は人の確認＝fail-safe」とした（`pretooluse_guard.py` の 3 の分岐のコメント「I174: コンテナ内の操作は、許可リストに入るものだけ素通しにする（それ以外は人の確認＝fail-safe）」）。何を安全とみなすかが許可リスト（`_container_safe()` の列挙）で決まるため、列挙に無い普通の書き方は、守る対象（GitHub・取り消せない状態・秘密）に関係なく確認になる。7（読みきれない）も同じく、読めないことそのものを理由に確認を出す。設定の `ask` も、git や GitHub から戻せる編集（Dockerfile・依存・マイグレーションのファイル）を含んでいる。どの許可リストのどの条件に外れて I166 の各コマンドが確認になったかの詳細は、未特定・計画で確定。

### 解決方針
- 確認を出す基準を、ユーザーの方針の 3 種類に置き直す:
  - (A) GitHub の破壊（force push・develop/main への push・リモートのブランチ／タグの削除・外部〔fork〕由来の PR への操作・リポジトリ設定の変更など）
  - (B) 復旧できない状態（未コミットの変更を消す git 操作・未コミットのファイルの削除・dev DB のデータを消す操作〔`down -v`・volume の削除・破壊的な SQL〕など）
  - (C) 秘密・個人情報の流出（秘密ファイルの読み取り・表示・外部への送信・個人情報を含むデータを外へ出すこと）
- (A)〜(C) は、今ある見張りの検出と設定でカバーされている。新しい検出は足さない（作り込まない）:
  - (A) GitHub の破壊 → 見張りの 5（GitHub から戻せないことがある操作）・6（動的・不透明な宛先の push）と、設定の `deny`（`git push origin develop/main`・`--force` など）
  - (B) 復旧できない状態 → 見張りの 4（未コミットの変更を消すかもしれない git の操作）と 1（`DANGER_OK=1` 付きの危険操作＝`docs/runbooks/danger-ops.md` の `down -v`・volume の削除・破壊的な SQL など）
  - (C) 秘密・個人情報の流出 → 見張りの 2（外部への送信・秘密情報の表示）と、設定の `deny`（`.env`・鍵ファイルの読み書き・`curl`・`wget`・`ssh` など）
  - 実装時に、各代表の操作がこの対応どおりに止まることを確かめる（受け入れ条件 2）。抜けがあった場合だけ、既存の検出の分岐に足す。
- 見張りの 3（コンテナ内）・7（読みきれない）の一律の確認をやめる。コンテナ内の操作も、上の 1・2・4・5・6 の検出（コンテナの中で `rm -rf` や破壊的な SQL を実行するなど）には今までどおり当たるようにする。読みきれないときは、(A)〜(C) につながる危ない語が含まれるときだけ確認し、含まれなければ通す（設計確認メモで確定・語の一覧は計画で確定）。
- 設定の `ask` は、秘密検査の設定（`.pre-commit-config.yaml`・`.secrets.baseline` の編集）の 2 件だけを残し（この 2 件も、秘密の検査を弱めうる書き換えだけに絞るかを計画で判断）、残りの 13 件と `.github/workflows/**` を外す。`.github/workflows/**` の編集は、見張りが書き足す中身を見て、秘密情報・個人情報が外に出うる書き換え（設計確認メモの 2026-10-29 の一覧）のときだけ確認する（設計確認メモで確定）。外した操作のうち危ないもの（データを消す SQL など）は、見張りの 1 の判定で止まることを確かめる。
- 「GitHub が最後の守り」の前提（I179・I182）に沿い、ローカルの見張りを作り込まない（文字列でシェルを読む精密な判定を増やさない）。公式の許可の仕組み（`.claude/settings.json` の allow/ask/deny・権限モード）を優先し、自作の見張りは公式で表せない部分だけにする（I193 の方針）。
- 確かめ方: 外した確認が本当に出なくなったこと、残した確認が出ることを `scripts/claude/check-permission-prompt.sh`（通常モードの判定）で固定する（ハーネステスト）。

## スコープ
### 含む
- 見張り（`pretooluse_guard.py`）と許可の設定（`.claude/settings.json`）の確認の基準の見直しと実装
- 見直した結果のハーネステスト（通常モードの判定で固定）
- 基準を書いた runbook の更新

### 含まない
- 検証する側（レビュー役）が確認画面で止まらない作り（I197 #332 で扱う。本イシューで確認を絞っても、検証の仕組みは確認に頼らずに止まらない作りにする）
- Claude Code 本体のワークツリー隔離チェック（パイプでの流し込み・波かっこを含む heredoc・PowerShell の拒否など。リポジトリのフック・設定では変えられない。避け方は I197 で扱う）
- 時間切れを合格にしない決まり（I193 で導入済み）

## 関連する品質基準
- C8 セキュリティ — 確認を絞っても、GitHub の破壊・取り消せない状態・秘密や個人情報の流出の 3 種類は必ず止まる状態を保つ
- C2 プライバシー・コンプライアンス — 個人情報を含むデータを外へ出す操作は確認を残す

## 受け入れ条件（Acceptance Criteria）
- [ ] 確認を出す基準（(A) GitHub の破壊・(B) 復旧できない状態・(C) 秘密や個人情報の流出、＋ユーザーが残すと決めたもの）が `docs/runbooks/` に書かれている
- [ ] (A)〜(C) と残すと決めたものに当たる操作は、通常モードで確認が出る（または止まる）ことを、代表の操作ごとにハーネステストで固定している（危ない操作は、同じ規則に当たり実行されても困らない代わりの操作で確かめる）
- [ ] I166 で確認が出た普通の操作（`docker compose cp`・`docker compose exec ... manage.py shell -c "exec(...)"`・`docker compose exec ... python /tmp/x.py`・`docker compose exec ... pytest ... -p <プラグイン>`）が、通常モードで確認なしで通ることを、ハーネステストで固定している
- [ ] `.github/workflows/**` の編集は、秘密情報・個人情報が外に出うる書き換え（`secrets.` の新しい参照・権限を広げる `permissions:`・`pull_request_target`/`workflow_run`・外部への送信・`github.event.` の `run:` への直の埋め込み）のときだけ確認になり、それ以外（action の版の書き換えなど）は確認なしで通ることを、ハーネステストで固定している
- [ ] 設定の `ask` が、`.pre-commit-config.yaml`・`.secrets.baseline` の編集の 2 件（計画で絞るならその形）だけになっている。外した 13 件のうち `psql` のデータを消す SQL など危ない使い方は、見張りの判定で止まることをハーネステストで固定している
- [ ] 見張りが読みきれないコマンドは、(A)〜(C) につながる危ない語（計画で確定した一覧）を含むときだけ確認になり、含まないときは通ることを、ハーネステストで固定している
- [ ] セッションの開始時に、primary が develop にいて追跡済みファイルに未コミットの変更が無ければ `origin/develop` へ早送りされ、条件に合わないとき・失敗したときはそろえずに理由と手で行うコマンドを出して、セッションの開始を止めないことを、ハーネステストで固定している（失敗注入: 未コミットの変更あり・develop 以外のブランチ・早送りできない〔primary に develop に無いコミットがある〕）。未追跡のファイルが消えないことも確かめる
- [ ] 既存のハーネステスト（`bash scripts/claude/tests/run-all.sh`）・CI がすべて pass する

## 影響範囲（想定）
- Backend: なし
- Frontend: なし
- DB: なし

## 制約・引き継ぎ情報
- 見張りと設定の変更は、安全装置そのものの変更（CLAUDE.md「止めて聞く条件」2）で、高リスクの例外ファイルに当たる（`scripts/claude/code-review.sh` の `path_risk_trigger()`）。計画レビュー・敵対的レビューの対象になる。
- worktree でも許可の判定は元のリポジトリの設定で行われる（ブランチで足した allow はマージまで効かない）。確かめは `check-permission-prompt.sh`（ブランチの設定ファイルを読ませる）で行い、稼働中のセッションで「確認なしで通った」ことを合格扱いにしない。
- 自動承認モードのセッションでは、確認が自動の判断になり、通常モードと結果が違う（I166 で実測）。判定は通常モードで行う。
- 過去の教訓: 文字列からシェルの動きを読む精密な見張りは作り込まない（I179 で 11 周回して廃止）。例外は秘密情報の push（公開リポジトリでマージ無しでも取り消せない）・push・Actions の変更。
