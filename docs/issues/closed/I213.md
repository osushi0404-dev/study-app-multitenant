### 計画での読み替え（/plan-issue・2026-10-29・詳細は docs/plans/open/plan_I213.md の 9）
- ハーネスの uv は Dependabot で見張らない: Dependabot の uv（0.13.5）と I211 の `required-version = "==0.13.6"` がぶつかり、ロックファイルの作り直しが毎回失敗する（写しで exit 2 を確認）。版を上げる手順は I211 の runbook のまま
- 土台イメージを「タグ＋指紋（`@sha256:`）」で固定する: タグだけでは同じ版の中の更新を Dependabot が PR にできない（Q4 の実現）。これで手元の `--pull` は要らない
- Playwright の 2 つの版を同じ PR で上げる設定は使わず、手元の e2e のコンテナが起動時にその版のブラウザを入れる（CI と同じ方法。版がずれても動くことを確認）
- `target-branch` を消す（書くとセキュリティの修正の PR に設定が効かない。既定のブランチは develop なので宛先は同じ）
- 書き間違いを pre-commit の `check-dependabot`（check-jsonschema）で止める

## 背景/目的

**背景**: I211 で、ハーネスのテストの道具の版を 1 か所に固定し、手で版を上げる手順を決めた。BP では、新しい版の通知と版上げの PR は Dependabot などに任せ、人は CI が緑の PR をマージするだけにする。調べたところ、このリポジトリには `.github/dependabot.yml` があるのに、Dependabot が作った PR はこれまで 1 件も無い（`dependabot/` で始まるブランチの PR が 0 件。2026-10-28 に `gh pr list` で確認）。何か月も新しい版が出ていないとは考えにくく、動いていない可能性が高い。
**目的**: Dependabot が実際に動き、アプリ・e2e・Docker イメージ・GitHub Actions・pre-commit・ハーネスの道具の新しい版を、扱いやすい量の PR で届ける。セキュリティの修正は待たずに届き、出たばかりの版（乗っ取られた版の恐れ）は数日待つ。届いた PR をこのリポジトリの流れでどう通すかが決まっている。

### 現状の問題（証拠・再現手順）
- Dependabot の PR が 0 件（上記）。`.github/dependabot.yml` の書き方（`version: 2`・`target-branch: develop`）に明らかな誤りは見当たらない。既定ブランチは develop
- 脆弱性アラートは無効（`repos/.../vulnerability-alerts` は 404 で区別できなかったが、`repos/.../dependabot/alerts` が 403「Dependabot alerts are disabled for this repository」を返した。2026-10-29）
- 見張っていないもの: `e2e/package.json`・Docker イメージ（`backend/Dockerfile`・`frontend/Dockerfile`・`frontend/Dockerfile.dev`・`docker-compose.yml`）・`.pre-commit-config.yaml` のフック・`scripts/claude/tests/uv.lock`（I211）
- 小さい版上げをまとめる設定（groups）・出たばかりの版を待つ設定（cooldown）が無い。このリポジトリは PR ごとのレビューが重いので、PR が大量に来ると負担が大きい

### 根本原因
- PR が 0 件の原因（確定・設計確認メモ Q1）: リポジトリの設定で Dependabot の機能が無効だった。2026-10-29 09:03（日本時間）にユーザーが Settings → Advanced Security で有効にした直後、版上げのジョブが初めて動き、PR が 14 件届いた
- 見張りの漏れ・まとめ方が無いのは、I028 で最小の設定だけを入れ、その後に増えた対象（e2e・ハーネスの道具など）を足していないため

### 解決方針
- PR が来ない原因は特定・有効化済み（設計確認メモ Q1）。Malware alerts も On にした（Q8・2026-10-29）。残るリポジトリ設定の UI 操作は無い
- 有効化の直後に届いた 14 件（#360〜#373）は I213 のマージまでマージせず、マージ後に新しい設定へ寄せて整理する（Q7）
- `.github/dependabot.yml` に見張りの漏れを足す（npm の `/e2e`・docker・pre-commit〔Dependabot の対応状況を計画で確認。無ければ別の手段〕・uv〔`/scripts/claude/tests`〕）
- minor・patch を見張りの対象ごとに `groups` でまとめ、`cooldown` で minor・patch は 7 日・major は 14 日待つ。セキュリティの修正は security updates で待たずに受け取る（設定はユーザーの UI 操作）
- Docker の土台イメージは、動かす環境の版を変える版上げ（python の major・minor、node・postgres・redis の major）を `ignore` で出させない。playwright のイメージは e2e の `@playwright/test` と一緒に上げる
- すべての action をコミットの SHA で固定し、横に版を書く（Dependabot が SHA のまま上げる）
- Dependabot の PR の通し方: minor・patch のまとめ PR と security updates は流れを通さず CI が緑ならユーザーがマージ。CI が赤い PR と major の PR はマージせず、イシューを立てて通常の流れで扱う。ラベルは `dependencies`＋`track:app`／`track:harness` を自動で付ける。自動マージは使わない
- `dependency-audit.yml`（毎日の監査）との役割分担を決める（監査は「今入っている版に穴がある」を見つけ、Dependabot は「直した版を PR で届ける」）
- 版を上げる手順そのもの（I211 の runbook）は変えない

- Dependabot が動かない原因の特定と、動くようにすること
- 見張りの対象の追加・PR のまとめ方・待つ日数・セキュリティ修正の受け取り
- Dependabot の PR の受け取り方の決まり・runbook
- 取り込んだ版上げを手元（Docker の backend・frontend）に反映する仕組み（標準の起動コマンドで毎回作り直す）
- すべての action のコミットの SHA での固定
- Dependabot の PR でも CI（E2E）が動くようにすること（E2E のテスト用パスワードを毎回作る）
### 含まない
- 版を上げる手順そのもの（I211 の担当）
- 届いた版上げの PR の中身の対応（それぞれの PR で扱う）
- アプリの python の版上げ（3.11 → 3.12 など。別イシュー）
- Docker の土台イメージの環境の版上げ（`node:18` → 新しい版など。別イシュー）
