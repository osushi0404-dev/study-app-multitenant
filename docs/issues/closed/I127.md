# I127: API レート制限の導入（DRF スロットルで未認証公開エンドポイントの列挙・スクレイピングを減速）

## 関連資料
- GitHub Issue: #232
- Draft PR: #236
- 発生元: I115（#213・PR #228）の security-review 残余リスク Low（2026-07-18・`docs/plans/open/plan_I115.md` の「セキュリティレビュー結果」参照）
- 関連イシュー: I115（`SubjectViewSet.public` の未認証 200 復旧。公開エンドポイント自体は既存設計意図）

## 設計確認メモ（/grill-me）
- Q: レート値は？ → A: anon `60/min`（IP ごと）・user `300/min`（ユーザーごと）で確定。
- Q: 適用範囲は全体一律か公開エンドポイント個別（ScopedRateThrottle）か？ → A: 本イシューは全体一律（`AnonRateThrottle` / `UserRateThrottle` のみ）。高コスト API（AI 問題生成・画像アップロード等）の個別制限・インフラ層防御・Retry-After 対応は別イシューで詳細調査（I129・#235 として起票済み。auth の DRF 一本化・403→429 是正も同イシューに統合）。
- Q: 既存 django-ratelimit（`backend/accounts/views.py` の認証系 IP 制限 5/5m 等）との関係は？ → A: 併存維持。auth 側の django-ratelimit はそのまま残し、DRF スロットルを API 全体に重ねる。一本化（auth の DRF 移行）は I127 ではせず、後続の I129（#235）で実施する。
- Q: テスト・無効化方式は？ → A: DRF スロットルも既存 `RATELIMIT_ENABLE=false`（`backend/core/settings.py:288`・E2E CI で使用中）に連動して無効化する。スロットル回帰テスト（429）は `override_settings` で LocMemCache＋低レートに差し替えて決定論的に検証し、その他の単体テストはスロットル無効で実行する。リスク（実 Redis 経路・Redis 断フェイルオープンが自動テスト対象外／スイッチ名が django-ratelimit 専用に見える）は軽微と評価し、settings コメントで連動を明記して許容。
- Q: 429 受信時のフロント表示は？ → A: 本イシューに含める。`frontend/src/services/api.ts` のエラー分岐に 429 を追加し「リクエストが多すぎます。しばらく待ってから再試行してください」をトースト表示する。
- 補足（調査による訂正）: 認証エンドポイント（ログイン等）は既に django-ratelimit で IP ベース制限済み。本イシューのギャップは「それ以外の DRF API 全般（特に未認証公開エンドポイント）」である。

## 背景/目的

### 現状の問題（証拠・再現手順）
DRF に `DEFAULT_THROTTLE_CLASSES` / `DEFAULT_THROTTLE_RATES` が未設定（`backend/core/settings.py:142-157` の `REST_FRAMEWORK` に該当キーなし・2026-07-18 確認）のため、**API 全体にレート制限が存在しない**。

特に未認証で到達できる公開エンドポイント（`GET /api/subjects/public/`・`GET /api/organizations/subjects/public/`、I115 で復旧）は、組織 slug の総当たりによる「有効な組織の存在確認＋科目カタログの収集（スクレイピング）」を減速する仕組みがない。露出データは科目の id/name/description のみ（個人情報なし）で重大度は Low。なお認証エンドポイント（ログイン等）は既に django-ratelimit の IP ベース制限（`backend/accounts/views.py` の `@ratelimit`・5/5m 等）で保護済みであり、本イシューのギャップは「それ以外の DRF API 全般（特に未認証公開エンドポイント）に構造的な減速が無い」点である。

### 根本原因
DRF の既定ではスロットルは無効であり、プロジェクト初期設定時にレート制限の設計判断が行われないまま現在に至っている（I115 以前からの既存構成。I115 の security-review で顕在化）。

### 解決方針
DRF 標準のスロットル機構を導入する（新規依存なし・キャッシュバックエンドは既存 Redis を利用）:
- `REST_FRAMEWORK` に `DEFAULT_THROTTLE_CLASSES`（`AnonRateThrottle` / `UserRateThrottle`）と `DEFAULT_THROTTLE_RATES` を設定する
- レート値は anon `60/min`（IP ごと）・user `300/min`（ユーザーごと）で確定（設計確認メモ参照）。適用範囲は全体一律とし、高コスト API の個別制限（`ScopedRateThrottle`）は別イシューで検討する
- 既存の django-ratelimit（認証エンドポイントの IP 制限）は併存維持し、一本化はしない
- DRF スロットルは既存 `RATELIMIT_ENABLE` 設定（E2E CI で `false`）に連動して無効化できるようにする（settings コメントで両機構への連動を明記）。スロットル回帰テストは `override_settings` で LocMemCache＋低レートに差し替えて決定論的に検証し、その他の単体テストはスロットル無効で実行する
- 429 受信時はフロント（`frontend/src/services/api.ts`）のエラー分岐にトースト表示を追加する
- 既存の正常利用（登録画面の科目取得・クイズ回答・E2E テスト）を阻害しないレート設計とし、回帰テストで担保する

## 実装対象（既知のもの）
| ファイル | 変更内容 |
|---------|---------|
| `backend/core/settings.py` | `REST_FRAMEWORK` に `DEFAULT_THROTTLE_CLASSES` / `DEFAULT_THROTTLE_RATES`（anon `60/min`・user `300/min`）を追加し、`RATELIMIT_ENABLE` に連動して無効化できるようにする |
| `backend/core/tests/`（新規） | スロットル超過で 429 が返る回帰テスト（`override_settings` で LocMemCache＋低レート）＋通常利用レンジで 429 にならないことの検証（横断設定のため `core/tests/` に配置） |
| `frontend/src/services/api.ts` | エラー分岐に 429 を追加し「リクエストが多すぎます。しばらく待ってから再試行してください」をトースト表示 |

## スコープ
### 含む
- DRF スロットルの導入（anon `60/min`・user `300/min` の全体一律）と回帰テスト
- E2E・既存自動テストがレート制限に抵触しないことの確認（`RATELIMIT_ENABLE` 連動での無効化・テスト用キャッシュ差し替えの設計を含む）
- 429 受信時のフロント表示（`frontend/src/services/api.ts` にトースト追加）
### 含まない
- WAF・インフラ層のレート制限（nginx/CDN 等）の導入
- 高コスト API（AI 問題生成・画像アップロード等）の個別レート制限（`ScopedRateThrottle`）・Retry-After 対応（I129・#235 で調査。設計確認メモ参照）
- 既存 django-ratelimit（認証エンドポイント）の変更・DRF への一本化（I129・#235 で実施）
- 公開エンドポイントの返却内容・認可の変更（I115 で確定済み）

## 関連する品質基準
- C2 プライバシー/情報露出 — 公開カタログの大量収集・組織 slug 列挙を減速し、露出面の悪用コストを上げる。
- C1 正確性/信頼性 — 大量リクエストによるサービス劣化（可用性）への基本防御。正常利用を阻害しないレート設計を検証で担保する。

## 受け入れ条件（Acceptance Criteria）
- [ ] 未認証リクエストが設定レートを超過すると 429 を返す（回帰テストで固定）
- [ ] 通常利用（登録画面の科目取得・ログイン・クイズ回答のフロー）がレート制限に抵触しない（既存自動テスト・E2E が引き続き全 PASS）
- [ ] レート値（anon `60/min`・user `300/min`）が全体一律で適用され、設定値がハードコードでなく settings に集約されている
- [ ] DRF スロットルが `RATELIMIT_ENABLE=false` で無効化される（E2E CI の既存スイッチに連動）
- [ ] テスト実行環境でスロットルがテストを不安定化させない（回帰テストは LocMemCache＋低レートへ差し替え・その他テストはスロットル無効）
- [ ] 429 受信時にフロントで「リクエストが多すぎます。しばらく待ってから再試行してください」のトーストが表示される

## 影響範囲（想定）
- Backend: `backend/core/settings.py`（REST_FRAMEWORK）・`backend/core/tests/` のスロットル回帰テスト。DRF スロットルはキャッシュ（既存 Redis・`IGNORE_EXCEPTIONS: True` のため Redis 断時はフェイルオープン）を使用。`backend/accounts/views.py` の django-ratelimit は変更なし（併存維持の参照のみ）
- Frontend: `frontend/src/services/api.ts` に 429 トースト追加
- DB: なし
- Config/Infra: なし（新規依存なし・既存 Redis 利用）

## 制約・引き継ぎ情報
- I115 の security-review で「設計 Low-2 / シナリオ Low-2（スロットル未設定での列挙・スクレイピング）」として記録済み。処遇＝本イシューで根治。
- 露出データは科目メタデータのみで緊急性は低（Low）。優先度はユーザー判断。
- DRF スロットルはプロセス内/キャッシュベースの簡易制御であり、分散環境での厳密性・インフラ層防御は本イシューの対象外（含まないに明記）。

## Danger Ops（有/無）
- 無
- 設定追加のみ。ただしレート値を誤ると正常利用が 429 になり得るため、通常利用フローの回帰（E2E 含む）を AC で担保する。
