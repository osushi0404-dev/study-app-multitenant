# I132: FEテストの axios 内部構造依存を解消 — モックライブラリ導入で api.test.ts のインターセプタ直接参照を置き換え

- 発見経緯: I127 コードレビュー Low 指摘（docs/reviews/I127_code_review_20260719_1149.md）

## 設計確認メモ（/grill-me）

- Q: テストケースの範囲 → A: TC-FE-01/02（429/500 トースト）の維持に加え、**`/auth/` URL でトーストを出さないスキップ分岐の 1 ケースを追加**（実経路化で新たにテストの通り道に入る分岐のため）。401 トークンリフレッシュ分岐のテストは含めない（別イシュー候補・タイトル案: 「401 トークンリフレッシュ分岐の FE 回帰テスト追加 — I132 で導入した DI + axios-mock-adapter パターンの適用」）

- Q: npm audit の AC 基準 → A: 実測ベースライン **18 件**（low 9 / moderate 4 / high 5・すべて react-scripts 系の開発時依存）から**増えないこと**を AC とする（2026-07-19 実測）

## 背景/目的

**背景**: I127（DRF API レート制限導入）で FE に 429 エラー時のトースト表示を追加した際、その回帰テスト（TC-FE-01/02）を書く必要があったが、FE に HTTP モックライブラリが未導入だったため、axios の内部構造を直接参照してインターセプタのエラーハンドラを呼び出す暫定方式を採用した（plan_I127 に意図的な妥協として記録済み）。この暫定方式が I127 コードレビューで Low 指摘を受け、本イシューを起票した。

**目的**: テストの axios 内部実装への依存を排除し、実際のリクエスト経路（モックされた HTTP 応答）でトースト表示を検証する方式に置き換える。これにより axios のバージョンアップやインターセプタの変更でテストが実装と無関係に壊れる・false-green になるリスクをなくすとともに、FE における HTTP モックテストの標準パターンを確立する。

### 現状の問題（証拠・再現手順）
`frontend/src/services/__tests__/api.test.ts:18` が axios の**内部構造**に直接アクセスしている:

```typescript
const rejected = (apiClient as any).instance.interceptors.response.handlers[0]
  .rejected as (error: unknown) => Promise<never>;
```

- `interceptors.response.handlers[0]` は axios の公開 API ではなく内部実装（配列順序・プロパティ名）への依存。axios のバージョンアップや api.ts のインターセプタ追加/並び替えで**テストが実装と無関係に壊れる**（あるいは別のハンドラを掴んで false-green になる）リスクがある。
- `as any` でのプライベートプロパティ（`instance`）参照は型安全性も損なう。

### 根本原因
FE に HTTP モックライブラリ（axios-mock-adapter / msw 等）が未導入のため、I127 実装時にインターセプタの rejected ハンドラを直接呼ぶ方式を暫定採用した（plan_I127「設計判断の明示」に記録済みの意図的な妥協。新規依存の追加を I127 のスコープ外としたため）。

### 解決方針
dev 依存として **axios-mock-adapter** を導入する（2.1.0・peer: axios >= 0.17.0 で本体 axios ^1.17.0 と互換実測済み。msw は CRA の Jest 27/jsdom 16 でポリフィル追加が多数必要なため不採用 — 比較記録は計画書に残す）。

あわせて `api.ts` に**最小の DI 変更**を入れる: `ApiClient` クラスを export し、コンストラクタを `constructor(instance?: AxiosInstance)` に変更（未指定時は現行と同じ設定で内部生成し、シングルトン `apiClient` の挙動は不変）。テストは `axios.create()` したインスタンスにモックアダプタを装着し、それを注入した `new ApiClient(instance)` で「実際にリクエストを発行し、モックされた 429/500 応答を返させ、トースト呼び出しを assert する」方式へ書き換える。インターセプタ連鎖（401 リフレッシュ分岐 → handleApiError）を実経路で通すため、現行方式より検証の忠実度も上がる。
