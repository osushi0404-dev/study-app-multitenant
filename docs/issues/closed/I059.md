# I059: スキル強化: イシューファイルの自己完結度向上（テンプレート拡充・完結チェック追加）

## 関連資料
- 起点: I058 振り返り（2026-05-03）— フォローアップイシューの自己完結度不足が課題として浮上
- GitHub Issue: #121
- Draft PR: #123

## 設計確認メモ（/grill-me）
- Q: 変更対象は retro スキルか issue-bootstrap か → A: issue-bootstrap（とテンプレート）。retro は問題発見の起点という文脈のみで、本体は改修しない（スコープ外のまま）
- Q: retro のフォローアップ起票は issue-bootstrap 経由か → A: 経由する。よって本強化は retro 起票分にも自動的に波及し、retro 側の追加改修は不要。狙いは「retro で得た根本原因・証拠をその場でファイルに転記し、イシュー単位でコンテキストを分離／クリアして新規会話で着手できる状態」を作ること（AC #6 の検証状態と一致）
- Q: 自己完結度チェックの強制レベルは → A: (a) ソフト警告型。未記入の重要セクションを一覧提示して補足を促すが続行（コミット）は可能。「未特定・grill-me で確認」等のプレースホルダが明記されていれば未記入扱いにしない（理由: テンプレートが未確定を正規に許容／bootstrap は情報が薄い瞬間に走る／後続 grill-me が空欄を埋める分業／機械判定の誤検知回避／本来目的は「情報があるのに取りこぼす」防止）
- Q: 最終報告メッセージで grill-me スキップ可否をどう示すか → A: (a) 動的分岐。「未特定/未定」プレースホルダが残る場合は `/grill-me` を推奨、全項目が具体記入済みなら `/plan-issue` 直行を推奨、と報告文を出し分ける
- Q: AC #6 の検証用イシューの扱いは → A: (b) 検証専用イシューを新規採番して作成し、コンテキストクリア後に `/plan-issue` へ入れることを確認したうえで削除する（git 履歴に番号が残る点は許容）。GitHub Issue は削除不可のため後始末はローカルファイル削除＋GitHub Issue クローズで行う
- Q: 自己完結度チェックを（既存レビュー基盤に倣い）サブエージェント化するか → A: する。ただし「記入有無のみ」なら grep で十分・サブエージェントは過剰。**イシュー内容のレビューまで含める**前提なら、改訂後テンプレートでイシューが実質的な設計アーティファクトになるため、第三者目線のサブエージェントレビューが筋が良い（自己レビューバイアスの解消＝AC#6 の「文脈ゼロの読者が着手できるか」を直接再現／最上流で手戻りを防ぐ）。よって `issue-bootstrap` の自己完結度チェックを **issue-review サブエージェント（内容レビュー込み）** として新設し I059 で対応する（スコープ拡張）
- Q: 既存 `plan-issue-review` サブエージェントと重複しないか → A: 役割を分けて重複を回避する。issue-review = 「生まれたてのイシューが自己完結しているか」（作成直後・最上流ゲート）、plan-issue-review = 「プラン込みで実装着手できるか」（実装直前ゲート）。イシューファイルは両者の間で変化する（grill-me が設計確認メモを追記等）ため二度見ではなく補完
- Q: issue-review の起動タイミング・ブロック方針・出力先は → A: タイミング=ファイル作成後・GitHub 登録前（step 3.5）／ブロック方針=ソフト（非ブロック。Q1=a を踏襲し findings は助言として提示、続行可）／出力先=`docs/reviews/` に保存しコンソール提示（この時点で PR 未作成のため PR コメントはしない）／モデル=既存レビュアーに合わせ claude-sonnet-4-6／ツール=Read,Grep,Glob の読み取り専用

## 背景/目的

### 現状の問題（証拠・再現手順）
I058 の retro でフォローアップイシュー（C2/P1〜P5）を起票することになったが、
現行の `issue_template.md` と `issue-bootstrap` スキルで作成したイシューファイルには以下が欠けており、
コンテキストをクリアした新規会話でそのままイシューに着手できない:

- 「なぜ今このイシューが存在するか」しか書かれておらず、**具体的な症状・エラー・対象コード箇所**が記載されない
- retro で特定した**根本原因**が会話コンテキストに留まり、イシューファイルに移されない
- **解決方針**（どのアプローチをなぜ選ぶか）が未記載
- **変更対象ファイル・コード箇所**が既知でもイシューファイルに書かれない
- **制約・引き継ぎ情報**（親イシューで判明した設計制約・試みた解決策）が記録されない
- イシューファイル作成後に**自己完結度チェック**がなく、空欄のまま先に進める

### 根本原因
`issue_template.md` のセクション設計が「問題の宣言」止まりで「実装に必要な詳細情報のキャプチャ」を要求していない。
また `issue-bootstrap` スキルに「記入内容の品質ゲート」がないため、空欄でもコミット・完了となる。

### 解決方針
1. `issue_template.md` に構造化セクションを追加し、具体的な証拠・根本原因・解決方針・実装対象・制約を記載する欄を設ける
2. `issue-bootstrap` スキルの自己完結度チェックを **issue-review サブエージェント（内容レビュー込み）** として実装する。既存レビュー基盤（`plan-issue-review`/`code-review` = 薄いスキル → `scripts/claude/*.sh` → `claude -p` + `.claude/review-agents/*-reviewer.md`）に倣い、`.claude/review-agents/issue-reviewer.md`（第三者・読み取り専用・インジェクション対策）と `scripts/claude/issue-review.sh` を新設する。`issue-bootstrap` はファイル作成後・GitHub 登録前にこのレビューを起動する（ソフト・非ブロック）
3. 完了ガイドを更新し「イシューが自己完結していれば `/grill-me` をスキップして直接 `/plan-issue` に進める」旨を明記する（issue-review の判定で出し分け）

## スコープ
### 含む
- `docs/issues/templates/issue_template.md` の改訂（セクション追加・構造化）
- `.claude/review-agents/issue-reviewer.md` の新設（イシュー内容を第三者レビューするサブエージェント指示・読み取り専用・インジェクション対策）
- `scripts/claude/issue-review.sh` の新設（issue-reviewer を `claude -p` で起動し結果を `docs/reviews/` に保存・ソフト判定）
- `.claude/skills/issue-bootstrap/SKILL.md` の改訂（ファイル作成後・GitHub 登録前に issue-review を起動／完了ガイドを判定で動的分岐）
- `docs/runbooks/issue-flow.md`・`docs/runbooks/workflow.md` の同期改訂（C1・retro 是正: issue-bootstrap のフロー変更を、フローを記述するランブックに反映）

### 含まない
- `grill-me`・`plan-issue`・`plan-issue-review`・`code-review` 等の既存スキル／既存サブエージェントの変更
- 既存イシューファイルの遡及的な更新
