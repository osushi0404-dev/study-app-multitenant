## 背景/目的

### 現状の問題（証拠・再現手順）
- 依存の既知脆弱性チェック（`pip-audit -r requirements.txt`・CI の Backend Lint & Security ジョブ）は **PR 時の CI でのみ**実行される。
- 依存ピンに対する新規 CVE は**リポジトリ無変更でも時間経過で発生**する（環境ドリフト）。このため検知が「誰かが PR を出した時」まで遅延し、そのタイミングで**全 PR の CI が一斉に fail** して無関係イシューの作業をブロックする。
- 実証: develop の最終 CI（2026-07-09）はグリーンだったが、2026-07-14 の PR #202（I107・Pillow と無関係の差分）で Pillow 12.2.0 の CVE 5件が初検知され、I107 が完了間際でブロックされた。緊急イシュー I108 の割り込み対応が必要になった。
- Frontend 側（npm audit / Frontend Lint & Security ジョブ）にも同じ構造のリスクがある。

### 根本原因
- 依存監査が「変更をゲートする」目的でのみ CI に組み込まれており、「リポジトリ無変更でも時間経過で fail し得るチェックのドリフトを事前検知する」目的の定期実行の仕組みが存在しない（I108 retro の 5 Whys で特定）。

### 解決方針
**案a（GitHub Actions scheduled workflow）で確定**（/grill-me 2026-07-15。設計確認メモ参照）:
- GitHub Actions の `schedule`（cron: `0 22 * * *` UTC = JST 朝 7:00 毎日）で develop（`checkout ref: develop` 明示）に対し、PR ゲートと同一条件の `pip-audit -r requirements.txt` / `npm audit --audit-level=critical --omit=dev` を定期実行する。
- fail 時に `gh issue create` で GitHub イシューを自動起票する（ラベル `dependency-audit`。監査種別ごとに open 最大 1 本・既存があればコメント追記）。
- **前提作業**: default branch を main → develop に変更する（オーナーがブラウザで実施。`schedule` は default branch 上の workflow 定義しか発火しないため。main は現在 README.md のみ）。
- 案b（Dependabot security updates）は見送り（判定ソース不一致・有効化に admin 手作業が必要）。なお default branch の develop 化により、既存の `.github/dependabot.yml`（I028 で追加・現在は default branch 外のため不活性）の weekly version updates が有効化される副作用がある（I028 の本来意図の回復。ノイズが問題なら計画時に設定調整を検討）。

## スコープ
### 含む
- 依存脆弱性ドリフトの定期検知の仕組み（backend: pip-audit 相当 / frontend: npm audit 相当）
- 検知時の自動アクション（自動起票または自動 PR）と重複防止
- 検知時運用の runbook 追記
### 含まない
- 検知された個別 CVE への対応（都度、通常のイシューフローで対応する）
- PR 時 CI の pip-audit / npm audit ゲート自体の仕様変更
- セキュリティ以外の依存更新の自動化（メジャーバージョン追従等）

## 関連する品質基準
- C2 プライバシー/セキュリティ — 既知 CVE のある依存を検知するまでの時間（露出期間）を短縮し、未成年含むユーザーのデータを扱うアプリの依存を継続的に監査する。
