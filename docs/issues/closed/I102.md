# I102: 問題管理を組織管理者権限に限定（非admin の問題 CRUD・参照を admin 限定・FE/BE 二重ガード）

## 関連資料
- GitHub Issue: #192
- Draft PR: #195
- 発見経緯: I078（問題管理画面での正解表示・is_correct write_only 見直し）の `/grill-me` 中に判明した、is_correct とは独立した既存の認可欠陥。
- 関連イシュー: I078（read 経路の is_correct 出し分け・表示）。本 I102 は I078 の前提となる認可是正を担当し、is_correct 露出そのものは扱わない。

## 設計確認メモ（/grill-me）
- Q: FE ガードの「管理者」判定は何を使うか？（FE/BE 不一致の解消） → A: **FE も `user.role === 'admin'` で判定する role ベースの新ガード（`OrgAdminRoute`）を追加**し、BE `IsOrgAdmin`（`views.py:31`＝`role == 'admin'`）と同一の「組織管理者」概念に統一する。**既存 `AdminRoute`（`AdminRoute.tsx:25`＝`is_staff || is_superuser` 判定）は流用しない**。理由: `role` と `is_staff` は独立フィールド（`accounts/serializers.py` で `role` と `is_admin`(=is_staff) を別項目として設定・`create_user` は is_admin 未指定なら is_staff=False）。既存 `AdminRoute`（プラットフォーム staff 用。`accounts/AdminUserViewSet` の `IsAdminUser` と対）を流用すると、org admin（`role='admin'` かつ `is_staff=False`）が BE では許可されるのに FE で弾かれ、正当な管理者がロックアウトされる。`user.role` は既に FE に露出済み（`services/types.ts:22`）。
- Q: create 時の越境（org-A admin が org-B の subject に問題作成）も本イシューで塞ぐか？ → A: **本イシュー対象外。別イシューで対応する。** `IsOrgAdmin` は `has_permission` で role のみ判定し組織スコープを持たない。参照・更新・削除・画像は `get_queryset` の org 絞り込み（`views.py:161`→`get_object` 404）＋更新の SEC-1（`views.py:296`）で越境を防いでいるが、**create（`perform_create`）だけ subject の org 検証が無く越境書き込みの穴が残る**（serializer の `subject` は全 Subject を受理）。この穴は is_correct/role 認可とは別軸のため I102 に含めず別イシューへ切り出す。I102 は「非admin=403（参照含む全経路）」の role ベース認可に限定する。
- Q: 認可回帰テストのレベルは？ → A: 既存 `backend/problems/tests/` の流儀に合わせ、**DRF テストクライアントで role 別（user／admin）に各エンドポイントを叩く結合テスト**で検証する（非admin=**全経路 403（参照含む）**／admin=200-201）。
- Q: 「問題管理」ナビメニュー項目も非admin から隠すか？ → A: **隠す**。`frontend/src/components/Layout.tsx:74` の「問題管理」項目を、既存の `isOrgAdmin`（`user?.role === 'admin'`、:70 で定義済み）条件付き表示に移す（:75-77 の「科目管理」と同じパターン）。route ガード（`OrgAdminRoute`）だけだと非admin にはデッドリンク（クリック→権限エラー画面）になるため、メニュー自体を出さない。→ **`frontend/src/components/Layout.tsx` を実装対象に追加**。補足: `Layout.tsx` が既に `role === 'admin'` を org-admin ナビ判定に使っている事実が、Q1 の「FE も role で判定」決定（既存 is_staff ベース `AdminRoute` は流用しない）を裏付ける。
- Q: `OrgAdminRoute` の非admin フォールバック挙動は？ → A: 既存 `AdminRoute` と**同一パターン**（`user` 無し＝未認証時のみ `/login` リダイレクト、認証済み非admin はインライン権限エラー Alert「このページにアクセスする権限がありません。管理者権限が必要です。」を表示）。判定条件のみ `is_staff||is_superuser` → `role === 'admin'` に差し替える。
- Q: `role='user'`（個人/自己登録）ユーザーが自分用の問題を作る用途は想定するか？ → A: **想定しない**。自己登録ユーザーは全員 `role='user'`（`UserRegistrationSerializer` は role 未設定＝モデル既定 `user`。`role='admin'` 付与は superuser 作成・`AdminUserViewSet` 明示・E2E シードのみ）。利用モデルは「**開発者/組織が用意した科目・問題を `role='user'` ユーザーが解いて学習する消費者型**」。問題オーサリングは org-admin 専用で確定。
- Q: 参照（`list`/`retrieve`）も admin 限定にするか？（read+write=admin の採否） → A: **採用（Option B）。`ProblemViewSet` 全体を `[IsAuthenticated, IsOrgAdmin]` で admin 限定にする（read も 403）。** 理由: 確定利用モデルでは `/api/problems/` の read consumer は `QuizManagement`（本イシューで admin 化）のみで、**非admin の参照利用者は実在しない**（`role='user'` は `quiz/next_problem` 経由で出題を消費し `/api/problems/` を叩かない。`quiz.service.getProblems` は呼び出し 0 の未使用コード。frontend 全体で `/api/problems/` を GET するのは QuizManagement だけ＝確認済み）。「参照は全ユーザー」に開くのは使われない防御にすぎず、代わりに I078 に「open read 経由の答え漏洩」リスクと `get_serializer_class` ロール出し分け機構を抱え込む。read も admin 限定にすれば **BE は分岐不要（viewset 一律）**、**I078 は is_correct を無条件露出でよくなり漏洩経路が構造的に消滅**する。後方互換の破壊なし（read の非admin 実利用者ゼロ）。**重複・非効率は増えない**（`ProblemAdminSerializer` は結果経路 `QuizAnswerDetailSerializer.problem` と共有の `ProblemSerializer` を継承し `choices` 1 フィールドのみ上書き＝ロジック重複ゼロ。B は `get_serializer_class` のロール分岐を1つ削減する純減）。トレードオフ: 「参照は全ユーザー」原則を撤回（将来 非admin 読み取り専用ブラウザが必要になれば read を再オープン＝YAGNI）。
- Q: I078 との順序依存は？ → A: **B では I102 を I078 より先に（または同時に）マージすることが必須**。I078 は `ProblemViewSet.serializer_class` を is_correct 露出版に切り替えるが、その安全性は「read が admin 限定」に依存する。逆順でマージすると is_correct 無条件露出が open read（`IsAuthenticated` のまま）に漏れる。既定の実装順（I102→I078）と一致。
- Q: I102 による既存テストへの波及は？ → A: `/api/problems` を叩く既存テストは **`test_I073_image_update.py` のみ**（fixture `role="user"`）で、I102 で 403 化するため **fixture を admin 化する**（`env["user"]`→org1 admin、`env["user2"]`→org2 admin＝`test_other_org_cannot_edit`/`test_cross_org_subject_rejected` の越境意図を保持）。他は破壊なし＝検証済み: `test_views.py` は quiz エンドポイントのみ／E2E 3本（auth・quiz-session・tenant-isolation）は問題管理を触らない／FE は `QuizManagement` のみ（`quiz.service.ts` は `updateProblem` 以外死コード）。`middleware` の `/api/problems` 参照はアクティビティ名ログのみで非アクセス制御。
- Q: I102 に追加する自動テストは？（権限チェック以外・E2E 含む） → A: (1) **BE authz 回帰テスト**（非admin=`GET/POST/PUT/PATCH/DELETE`・AI生成・画像の全経路 403 / admin=200-201）、(2) **`test_I073_image_update.py` fixture の admin 化**（既存テスト整合）、(3) **E2E authz スモーク**を `e2e/tests/` に 1 spec 追加（非admin: 「問題管理」メニュー非表示＋`/quiz-management` 遮断／admin: 到達可）。**delete/validate_choices/list フィルタ/基本 create/総合 admin CRUD E2E などの既存カバレッジ負債は I102 に含めない**（I102/I078/I103 の変更が原因でない既存負債。**別イシューで対応＝ユーザーが振り返りで起票予定**）。
- Q: E2E authz スモークの「非admin 遮断」を検証する identity はあるか？ → A: **無いので E2E インフラを拡張する（option A）**。`seed_e2e.py` の E2E ユーザーは `e2e_user_a`・`e2e_user_b` とも `role='admin'`（:69, :85）で**非admin が存在しない**。`global-setup.ts` は user A・B の storageState のみ生成、`playwright.config.ts` も user_a/user_b のみ。→ 以下を追加する: (1) `seed_e2e.py` に**非admin ユーザー `e2e_user_c@example.com`（`role='user'`・org_a 所属）**を追加、(2) `e2e/global-setup.ts` で `e2e_user_c` の storageState（`.auth/user_c.json`）を生成、(3) `e2e/playwright.config.ts` に非admin storageState を使うプロジェクト（または spec 内 `test.use`）を追加、(4) `e2e/tests/problem-management-authz.spec.ts` で非admin=メニュー非表示＋`/quiz-management` 遮断／admin（既存 `user_a`）=到達を検証。非admin identity は I104（総合 CRUD E2E）・I078（表示 E2E）でも再利用可能な基盤投資。

## 背景/目的

### 現状の問題（証拠・再現手順）
問題管理 API（`ProblemViewSet`）と管理画面（`QuizManagement`）が、**組織管理者でない一般ユーザー（学生ロール）にも更新系操作を許してしまっている**。

証拠:
- `backend/problems/views.py:150` — `ProblemViewSet.permission_classes = [permissions.IsAuthenticated]` のみ。`create`/`update`/`partial_update`/`destroy` および `generate_ai`/`generate_adaptive`/`upload_image`/`delete_image` の各アクションに管理者限定の認可がない。
- `frontend/src/App.tsx:78` — `<Route path="quiz-management" element={<QuizManagement />} />` が `<AdminRoute>` で保護されていない（`admin/users` 系は :87-89 で `<AdminRoute>` 済みなのと非対称）。

再現:
1. 学生ロール（`role != 'admin'`）のユーザーで認証する。
2. `POST /api/problems/`（または `PUT`/`DELETE /api/problems/{id}/`、`POST /api/problems/generate_ai/` 等）を直接叩く。
3. 200/201 で問題の作成・編集・削除・AI生成が成功してしまう（本来は組織管理者のみが行うべき操作）。
4. フロントでも `/quiz-management` に直接遷移すると学生でも管理画面が開き、作成・編集・削除 UI が操作できる。

### 根本原因
`ProblemViewSet` の権限が「認証済みか否か」だけ（`permission_classes = [IsAuthenticated]`）で判定され、**問題管理（オーサリング）が組織管理者の機能であるにもかかわらず、非admin（`role='user'`）にも作成・編集・削除・AI生成・画像操作を許している**。参照（list/retrieve）も全認証ユーザーに開いているが、確定した利用モデル（`role='user'` は開発者/組織提供のコンテンツを quiz 経由で消費する学習者）では **`/api/problems/` の参照を必要とする非admin は存在しない**（read consumer は管理画面 `QuizManagement` のみ）。フロントも管理画面ルートを admin ガードしていないため、UI レベルの防御もない。

### 解決方針
**問題管理 API・画面を組織管理者（`role == 'admin'`）限定にする（参照・更新系の両方＝read+write）**。**FE・BE の二重ガード**で担保する。
- バックエンド: `ProblemViewSet.permission_classes = [permissions.IsAuthenticated, IsOrgAdmin]` を **viewset 全体に一律適用**（read/write すべて admin 限定・アクション別分岐は不要）。`IsOrgAdmin` は `views.py:23` に既存（`role == 'admin'` 判定）。→ 非admin は list/retrieve/create/update/destroy/generate_ai/generate_adaptive/upload_image/delete_image のすべてで 403。
- フロント: **role ベースの新ガード `OrgAdminRoute`（`user.role === 'admin'` 判定・非admin 時のフォールバックは既存 `AdminRoute` と同一パターン）を新設**し、`frontend/src/App.tsx` の `quiz-management` ルートをそれでラップして非admin は管理画面に到達できないようにする。**既存 `AdminRoute`（is_staff 判定）は流用しない**（BE `IsOrgAdmin` の `role == 'admin'` と概念を統一し、org admin が is_staff=False でロックアウトされるのを防ぐ）。加えて **`frontend/src/components/Layout.tsx` の「問題管理」ナビ項目を既存 `isOrgAdmin`（`role === 'admin'`）条件付き表示に移し**、非admin にはメニュー自体を出さない（デッドリンク回避・多層防御）。
- テスト: 非admin が **参照を含む全エンドポイント**で **403** を受けること・admin は 200/201 で操作できることを検証する認可回帰テストを追加。
- 補足（採否理由）: read も admin 限定にするのは、確定利用モデルで read の非admin 利用者が実在せず、開いたままだと I078 が「open read 経由の答え漏洩」防止のためロール出し分け機構を恒常的に抱える必要があるため。read を閉じることで BE は分岐不要・I078 は is_correct 無条件露出で安全になる（後方互換の破壊なし）。

- `Layout.tsx` の「問題管理」ナビ項目を org-admin 限定表示に変更（非admin にはメニュー非表示）

### 含まない

- **問題管理のテストカバレッジ負債（problem delete・validate_choices・list フィルタ・基本 create・総合 admin CRUD E2E）＝ 別イシューで対応（ユーザーが振り返りで起票予定）。** I102/I078/I103 の変更が原因でない既存負債のため本イシューに含めない
- `is_correct` の表示・露出（read 経路の serializer 出し分け）＝ **I078 の担当**
- 正解マーク表示・編集ダイアログの初期選択などの UI 改修（I078）
- `SubjectViewSet` / `QuizSessionViewSet` 等、問題管理以外の ViewSet の認可（本イシューの対象外）
- 既存 `AdminRoute`（is_staff 判定）の改修・置換（本イシューは role ベースの新ガードを追加するのみ）
- 新しいロール・権限モデルの導入（既存 `role == 'admin'` を使う）

## 関連する品質基準
- C1 正確性/信頼性 — 権限のない操作を構造的に禁止し、問題データの意図しない改変・削除を防ぐ。

## 制約・引き継ぎ情報
- I078 の `/grill-me` で発見された、is_correct とは独立した既存の認可欠陥。I078 に同梱せず本イシューに分離（根本原因・再発防止テストが別のため）。
- **順序依存（必須）: I102 を I078 より先に（または同時に）マージすること。** I078 は `ProblemViewSet.serializer_class` を is_correct 露出版（`ProblemAdminSerializer`）に切り替えるが、その安全性は本イシューの「read も admin 限定」に依存する。逆順でマージすると is_correct 無条件露出が open read（`IsAuthenticated` のまま）に漏れる。
- `IsOrgAdmin` は `backend/problems/views.py:23` に既存（`request.user.role == 'admin'`）。新規の BE 権限クラスは不要。
- **FE/BE の管理者定義を `role == 'admin'` に統一する**。既存 `AdminRoute`（`is_staff`／`is_superuser` 判定）はプラットフォーム staff 用（`accounts/AdminUserViewSet` の `IsAdminUser` と対）であり本イシューでは流用しない。`role` と `is_staff` は独立フィールドのため、is_staff ベースの流用は org admin のロックアウトを招く。
- **参照（read）も admin 限定にする**（read+write=admin）。理由: 確定利用モデルでは `/api/problems/` の read consumer は管理画面（`QuizManagement`）のみで、`role='user'` は `quiz/next_problem` 経由で出題を消費し `/api/problems/` を叩かない（`quiz.service.getProblems` は未使用・呼び出し 0）。read を開く「参照は全ユーザー」原則は使われない防御にすぎず、I078 の答え漏洩リスクとロール出し分け機構を不要化するため read も閉じる。将来 非admin 向け読み取り専用ブラウザが必要になれば、その時点で read を再オープンする（YAGNI）。非admin 向けの読み取り専用管理 UI は提供しない。
- **create 時の越境 subject 検証（`perform_create` の org チェック欠落）は I103（#193）で対応する。** 本イシューは role ベース認可に限定。
