## 設計確認メモ（/grill-me）
- Q: アプリ本体の「指摘 0」に、Low の好みの改善提案まで含めるか？ → A: 含めない（ユーザー決定 2026-10-27）。アプリ本体で止めるのは、イシューに関係する（直した差分の中の）Blocker・High・Medium。Low（code-reviewer の重大度定義で「改善提案」）は止めず、台帳に残して retro で扱う
- Q: 敵対的レビュー（高リスク時）の止め方を同じ形に揃えるか？ → A: 揃えない（2026-10-27 ユーザーと合意）。敵対的レビューで周を進める理由は今のまま Critical・High・未検証だけ。アプリ本体でイシューに関係する Medium が出たときは、そのイシューの中で直すが、敵対的レビューの周は増やさず、基本レビューの差分のレビューで確かめる（過去の記録: アプリの I166 は敵対的レビュー 3 周すべて OK で、ループはハーネスでだけ起きていた）
- Q: ハーネスの Medium（そのイシュー特有ではなく、ほかでも起こりうるもの）は別イシューで対応するか？ → A: する（ユーザー提案 2026-10-27）。ただし「特有か・ほかでも起こりうるか」の見分けは AI の判断でぶれるので分けず、ハーネスで止めない指摘はすべて後続へ回す。1 件ずつ起票せず、retro がそのイシューの残りを 1 件の後続イシューにまとめる（I202 と同じ形）か、合う既存イシューに同梱する。判定の仕組みの穴・セキュリティに関わるものが入っていれば、その後続イシューを次のハーネスの作業で最優先にする
- Q: レビュー役がハーネスの完璧な状態を目指して指摘を上げ続ける状態を、どう根本から防ぐか？（Medium を含めるかは直接の原因ではない・ユーザー指摘 2026-10-27） → A: 根本の原因は ① レビュー役への問いが「問題を探せ」で終わりの基準が無い ② 止めるかをレビュー役の感覚の重大度で決めている ③ 直したコードがまた見る対象になる、の 3 つ（I197 の台帳・差分のレビューは ③ の一部だけを防ぐ）。対策は、指摘を出す側・止めるかを決める側・直す側の決まりを揃えること: (1) ハーネスのレビュー役には「止める条件の一覧のどれかに当たるか」を判定させる（閉じた問い） (2) 止める指摘には具体的な再現（この入力・この手順でこう壊れる）を必須にし、書けない指摘は止めない側に回す (3) 止めるかはスクリプトが機械で決め、直す側（実装者）は決めない（自分に甘くなる・念のため全部直して周が回る、の両方を防ぐ）。守る条件: 判定の仕組みを大きく作り込まない（スクリプトが見るのは「どの止める条件か」と「再現の欄があるか」だけで、再現の正しさは機械で確かめない）・後続イシューを必ず片付ける・アプリ本体は止める条件の一覧で絞らない（アプリと共通にするのは行単位の範囲と再現の欄だけ）。この形で周が減るかは、I205 の後のハーネスのイシューで周の数を記録して確かめる（ループエンジニアリング・ハーネスエンジニアリングのベストプラクティスと開発の速さの観点での評価を経てユーザーが合意）
- Q: それ以外のハーネスで止める条件の一覧は何か？ → A: 次の 4 つで確定（ユーザー合意 2026-10-27・ループ／ハーネスエンジニアリングのベストプラクティスと「develop・main が壊されず、ローカルは GitHub から復旧でき、個人情報が出ないなら穴も許容」の基準で評価済み。止めるのは取り返しがつかないこと・気づかないうちに起きることに絞る）: ① 流れが動かなくなる（スキル・スクリプトがエラーで止まり次の段階に進めない） ② 秘密情報・個人情報が外に出る ③ develop・main を直接壊す（直 push・強制 push・ブランチ保護を外す等）、または GitHub から戻せない設定を壊す ④ イシューの受け入れ条件を満たしていない（どの受け入れ条件かの番号の記載を必須にする。何でも④に押し込む抜け道を防ぐ）。「判定をすり抜けられる穴（関所の穴）」は一覧に入れない（止めずに後続イシューへ回し、次のハーネスの作業で最優先にする。CI とユーザーのマージ前確認が最後に残るため・入れると毎回挙がって周が回るため）
- Q: アプリ本体の「イシューに関係する指摘」の範囲は？ → A: 次の 2 つ（ユーザー合意 2026-10-27）: (i) このブランチで変えた行（と前後数行）への指摘（1 周目の全体レビューでも、ブランチで触っていない古いコードの指摘は止めずに後続へ回す） (ii) 受け入れ条件・計画を満たしていないという指摘（行に関係なく止める。古いコードが原因でイシューの機能が動かない場合はこちらで止まる）
- Q: 敵対的レビューが OK でも、アプリ本体のイシューに関係する Medium が出たときはどうするか？（2 問目の「周は増やさない」と、gate-check.sh の「敵対的レビューの OK の後の変更を通さない」が食い違う・/plan-issue で判明） → A: 関所（gate-check.sh）は変えない（ユーザー決定 2026-10-27）。上限（通算 2 周）が残っていれば直して基本レビューの差分のレビューを通し、次の周で確かめる（直した差分だけを見るので短い）。上限が残っていなければ直さずに台帳に残し、retro が最優先の後続にする。2 問目の「敵対的レビューの周は増やさない」は、上限を増やさない・Medium だけで上限を超えて回さない、の意味に読み替える
- Q: 差分の外のセキュリティに関わる Blocker はどうするか？ → A: 今のまま止める（アプリ本体・ハーネスとも。ユーザー合意 2026-10-27）。個人情報の流出（他組織のデータが見える等）はユーザーが最も避けたいもので、出現はまれなので進みを遅くしない

## 背景/目的

**背景**: I197 で基本レビューを「台帳＋直した差分だけのやり直し＋止めるのは Blocker・High」にした。しかし ① 止める基準がアプリとハーネスで同じで、GitHub から復旧できるハーネスの変更でも High で止まり、直すとまた差分が出て周が回る（I197 自身がこの形で周を重ねた。最後は回数の上限〔5 回目で止める〕に頼る形） ② 「差分の中か外か」をファイル単位で決めているため、1 行直しただけのファイルでも全体が「差分の中」になり、レビュー役が昔からある穴を新しい High として書くと止まる（完璧を目指す形で周が回る抜け道） ③ 一方でアプリ本体（学習アプリ）は、Medium・Low を止めずに後回しにしているが、ユーザーの方針は「対応イシューに関連するものなら指摘 0 を目指す」。
**目的**: 止める基準を「壊れたときに GitHub から復旧できるか」と「アプリ本体か」で分け、ハーネスは完璧を目指さずに進め、アプリ本体はイシューに関係する指摘を残さない。あわせて、直していない古いコードの指摘で周が回らないようにする。回数の上限は、ほかで止まらなかったときの最後の安全網にとどめる。

### 現状の問題（証拠・再現手順）
- 止める基準: `scripts/claude/code-review.sh` の `_LEDGER_PY` の `blocking()` が、変更の種類によらず「open の Blocker・High（範囲の中）」を止める
- 範囲の判定: `delta_files`（ファイル単位）と `scope_of`（FILE が範囲のファイルにあれば delta）。行の情報を使っていない
- 繰り返しの上限: `.claude/skills/review-gate/SKILL.md` §2「5 回目になるときは、fix-loop へ回さずに止める」に、ハーネスの変更の収束を頼っている

### 根本原因
- 「GitHub が最後の守りなので、手元のハーネスは作り込まない」という方針（I181・I182）が、レビューで止める基準に反映されていなかった
- 差分のレビューの範囲が「直した行」ではなく「直したファイル」だった

### 解決方針
- (a) 止める基準を変更の種類で分ける（変更の種類は、指摘の FILE のパスでスクリプトが決める）:
  | 変更の種類 | 止めるもの |
  |---|---|
  | アプリ本体（`backend/`・`frontend/`・`e2e/` など。ハーネスの場所の一覧に無いものはすべてこちら＝厳しい側） | イシューに関係する Blocker・High・Medium（指摘 0 を目指す。Low の改善提案は数えない・設計確認メモ）。「イシューに関係する」= このブランチで変えた行（と前後数行）への指摘、または受け入れ条件・計画を満たしていないという指摘（行に関係なく）。1 周目の全体レビューでも、ブランチで触っていない古いコードの指摘は止めずに台帳から後続のイシューへ |
  | ハーネスのうち GitHub から復旧できない例外（`path_risk_trigger()` の一覧: `.github/*`・`.pre-commit-config.yaml`・`.secrets.baseline`・見張り・settings） | Blocker・High（今のまま） |
  | それ以外のハーネス（スキル・スクリプト・テスト・手順書など） | 止める条件の一覧に当たり、再現が書かれた指摘だけ。一覧（設計確認メモで確定）: ① 流れが動かなくなる ② 秘密情報・個人情報が外に出る ③ develop・main を直接壊す、または GitHub から戻せない設定を壊す ④ イシューの受け入れ条件を満たしていない（条件の番号が必須）。関所の穴は一覧に入れない。それ以外は台帳に残して後続のイシューへ |
- 共通の例外: 差分の外でも、セキュリティに関わる Blocker は止める（今のまま・設計確認メモ）
- (a2) 止める指摘の書き方と判定（設計確認メモ）: レビュー役は、止める指摘に「当たる止める条件」と「再現（入力・手順・壊れ方）」を書く。スクリプトは、その欄があるかだけを見て止めるかを決める（再現の正しさは機械で確かめない）。再現の欄が無い指摘は止めない側（アプリ本体でも同じ。ただしアプリ本体は止める条件の一覧で絞らない）。直す側は、止めると判定された指摘だけを直す
- (b) 「差分の中か外か」を行で決める: 直した差分の塊（とその前後の数行）に入る指摘だけを「差分の中」にする。FINDING 行に行番号（または行の範囲）を書かせ、スクリプトが差分の塊と照合する（書き方・前後の行数は計画で決める）。行が読めない指摘は「差分の中」（止める側）
- 差分の外の指摘・止めない指摘の受け渡し: 台帳に残った指摘は、そのイシューの retro 段階が拾い、1 件の後続イシューにまとめて起票するか、合う既存のイシューに同梱する（1 件ずつは起票しない。I197 では I202 に回した）。判定の仕組みの穴・セキュリティに関わるものが入っていれば、その後続イシューを次のハーネスの作業で最優先にする。アプリ本体の差分の外の指摘が埋もれないよう、retro がアプリ本体の残りを必ず振り分けることを手順に足すか、台帳の残りを retro に機械的に渡すかは計画で決める
- (c) 回数の上限は最後の安全網として残す（上限に当たったら、止め方の見直しの兆しとして止めて聞く）
- アプリ本体の「指摘 0」に数える範囲は Blocker・High・Medium（Low の改善提案は含めない。LLM のレビュー役はほぼ必ず何か提案を出すので、含めると収束しないため・設計確認メモ）
- 敵対的レビュー（高リスク時）の止め方は揃えない（設計確認メモ）。アプリ本体でイシューに関係する Medium が出たら、上限（通算 2 周）が残っていれば直して基本レビューの差分のレビューを通し、次の周で確かめる。上限が残っていなければ直さずに台帳に残し、retro が最優先の後続にする（gate-check.sh は変えない・上限は増やさない）
