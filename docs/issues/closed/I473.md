## 背景/目的

**背景**: ダッシュボード画面の数値（今日の学習時間・連続学習日数・解答問題数・正答率・週次グラフ・科目別の進み具合・おすすめ）がほぼすべて 0 または空のまま表示されている。2026-08-06 の検討資料で原因を調査済み。その後、組織の境界（I431・I455）と今日の復習（I452）の変更は入ったが、数値が 0 になる原因（集計元と画面と API の受け渡し形式）は変わっていない（2026-11-12 の develop で確認）。
**目的**: クイズを解いた結果が、ダッシュボードの数値・グラフ・科目別の進み具合・おすすめに正しく反映される状態にする。画面と API の受け渡し形式（API 契約）を 1 本に確定し、テストで固定して再発を防ぐ。

### 現状の問題（証拠・再現手順）
- 再現: dev 環境でログインしてクイズを数問解く → ダッシュボードを開く → 今日の学習時間 0 分・連続学習日数 0 日・解答問題数 0・正答率 0%・週次グラフ空・正答率のドーナツグラフが「不正解 100%」の赤一色（I452 の画面確認〔2026-11-12〕でも同じ表示を確認）
- dev DB の件数（2026-10-24・読み取りのみ）: `StudyLog` 0 件・`DailyStudySummary` 0 件、`QuizSession` 124 件・`QuizAnswer` 44 件
- 画面と API のキーが 1 つも一致していない（検討資料 §2.1）: 画面は `stats` / `weekly_progress` / `recommendations` / `recent_sessions` / `subject_progress` を読むが（`frontend/src/pages/Dashboard.tsx:130-146`）、API（`GET /api/dashboard/overview/`・`backend/dashboard/views.py:74-100`）は `today` / `study_streak` / `weekly_summary` / `recent_quizzes` / `subject_progress` / `upcoming_goals` を返す。`subject_progress` は名前だけ一致し、中身のキー名と正答率の単位（画面 0〜1・API 0〜100）が違う（`Dashboard.tsx:463` の `accuracy < 0.7` 判定が壊れている）
- 科目セレクタが効かない: 画面は `subject_id` を送るが、`DashboardOverviewView.get` は `query_params` を読まない（検討資料 §2.3）。なお I452 で足した「今日の復習」のカード（`frontend/src/components/TodayReviewCard.tsx`）は科目の選択に合わせて動く
- おすすめが画面に届かない: `SubjectRecommendationView`（`/api/dashboard/recommendations/`・`backend/dashboard/views.py:263-`）は実装済みだが画面は呼ばず、存在しない `overview.recommendations` を読んでいる（検討資料 §2.4）。画面側の `getRecommendations`（`frontend/src/services/dashboard.service.ts:17-`）はどこからも呼ばれていない
- テストが無い: `backend/dashboard/` にテストが無く、`Dashboard.test.tsx` も E2E も無い（検討資料 §2.6 Q1）。組織の境界は #446 の横断テスト（`backend/core/tests/test_I446_cross_api_tenant_isolation.py`）が overview・analytics・recommendations の 3 経路を見ている

### 根本原因
1. **集計元の表に書き込む経路が無い**: ダッシュボードは `StudyLog` / `DailyStudySummary` から集計しているが、これを作る画面の経路が無い（I452 で、存在しないアドレスを指していた画面側の関数は消した）。実際の学習データはクイズ記録（`QuizSession` / `QuizAnswer`）と、I452 から作られる復習記録（`SpacedRepetitionReview`）にある
2. **画面と API が別々の仕様で作られ、照合する仕組みが無い**: 画面の型（`frontend/src/services/types.ts`）と API が独立に書かれ、画面側の防御的な既定値（`data?.stats || {…0}`）が不一致をエラーにせず 0 で埋めて隠した。契約テスト・型の単一ソースも無い

### 解決方針
検討資料 §4 の**案C（実データ基準で再設計）**を採る。案A（画面を API に合わせる）・案B（API を画面に合わせる）はどちらも集計元が空のままなので数値は 0 のままになり、症状が変わらないため採らない。
- 集計元を `QuizSession` / `QuizAnswer` に統一する（初手では日次サマリ等の非正規化は入れない）
- API 契約を 1 本に確定する（検討資料 §5.2 の形を叩き台にする: 単位をキー名に含める `_seconds` / `_days` / `_rate`・比率は 0〜1・「0」と「データ無し」を区別する `has_data`・おすすめを `overview` に統合）
- 科目フィルタ（`subject_id`）を正式にサポートし、不正な値は 400（I452 の `review_summary` と同じ扱い・`OrgSubjectField`）
- 1 回の表示あたりのクエリ数を定数本に抑え、テストで固定する（現状は連続日数が 1 日 1 クエリ・科目別が科目ごとに 3 クエリ）
- 画面の防御的既定値を廃止し、欠損は欠損（エラー状態）として扱う
- I452 の「今日の復習」のカード（ダッシュボードのいちばん上・科目の選択の下）は壊さない
- 学習時間・連続日数・週の推移・間違いやすい分野・おすすめの決まりは「設計確認メモ」のとおり。「今日」は `timezone.localdate()` で出す（#481 の決まりを先取りする）
- `StudyLog` / `DailyStudySummary` / `StudyGoal` はダッシュボードの集計から外すだけで、モデル・テーブルは残す
- おすすめは `overview` に統合し、`/api/dashboard/recommendations/` と画面の `getRecommendations` は消す
- 統計画面は別イシュー（#487 の次）
