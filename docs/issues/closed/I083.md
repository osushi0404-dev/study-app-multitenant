## 設計確認メモ（/grill-me）
- Q: 静的に確定できない動的宛先 push（`$(...)`/`$VAR`/エイリアス/`eval`・`sh -c` ラッパー）をどう扱うか → A: **(a) allowlist／fail-safe**。宛先トークンが**単純な静的ブランチ名**と確認できる push のみ従来どおり静的判定（feature 通過・protected は exit 2 block）。少しでも動的・不透明な push は安全と断言できないため **ask（確認プロンプト）に degrade**。理由: 既知イディオムを解決する (b) はシェル表現を追うパーサ依存＝I080 の穴（網羅漏れ）の再来。安全機構は「網羅的賢さ」でなく「単純さ＋曖昧なら安全側」が理想。block＋DANGER_OK 強制の (c) は「危険と確定」用の escape hatch を「危険か不明」に流用する意味のすり替えのため不採用。
- Q: AC「誤検知ゼロ」に ask を含むか → A: **hard block（exit 2）しない＝誤検知ゼロ。ask（exit 0＋確認プロンプト）は許容**（誤検知に含めない）。(a) では正当な動的 feature push も ask になるため、この定義でないと AC が達成不能。
- Q: `allow: Bash(git push *)` をどこまで絞るか → A: **維持（絞らない）**。settings の glob では `$(`/`$VAR` の判定が困難。判定はフック側に集約し「静的安全なら無確認通過／それ以外 ask」を一手に担う（I080 で確立した broad allow＋フックが番人の単一モデルを踏襲）。
- Q: 不透明ラッパー（`eval`/`sh -c`/`bash -c`/`git -c alias.`）の ask トリガ条件は → A: **ラッパー痕跡が存在し、かつコマンドに `git` と `push` の両トークンが現れる場合に ask**（visible-intent 限定案）。理由: 本ガードの脅威モデルは「**事故**による protected/force push」であり、事故では push 意図が必ずテキストに可視化される（`git push origin $(git rev-parse --abbrev-ref HEAD)` を develop 上で実行する等）。push トークンを完全隠蔽する `eval "$VAR"` 形は事故ではなく**意図的偽装＝脅威モデル外**、かつ `DANGER_OK=1` で別途解除可。全 `sh -c`/`eval` を無差別 ask にする最大 fail-safe 案は**アラーム疲労**を生み一律承認の習慣化でガードの実効性をむしろ損なうため不採用。残余（`eval "$VAR"` 等の push トークン完全隠蔽形）は脅威モデル外として `docs/claude-code-structure.md` に既知の限界として明記する。
- Q: 直接 `git push`（ラッパー無）で動的文字（`$`/`` ` ``/`{`/`(`）を見る範囲は → A: **`push` 以降の引数領域全体**（remote/dest/refspec を問わず）に動的メタ文字が一つでもあれば ask（宛先限定にしない）。理由: コマンド置換 `$(...)` は内部に空白を含み shlex トークナイズを破壊する（`$(echo develop)` → `$(echo`/`develop)` に分裂）ため、宛先トークンだけを健全に分離できない＝「宛先限定」案は再びパーサ依存（I080 の失敗様式）に陥る。引数領域に動的文字があれば静的判定を信用せず ask に倒すのが唯一健全。副作用 `git push $REMOTE feature`（remote だけ動的・宛先は静的安全）の false-ask は稀かつ無害（確認1回）として許容（AC「誤検知＝hard block」の定義上これは誤検知に含まれない）。
- Q: force 判定の方式は部分一致 `re.search` か `_segments` ベースか → A: **pure `_segments` ベースに確定**（本文の「`re.search` 化」表現は破棄）。push を含むセグメントの `push` 以降トークンに force 系フラグ（`--force`／`--force-with-lease[=...]`／`--force-if-includes`／単一ダッシュの短縮クラスタで `f` を含む `-f`/`-uf`/`-fu` 等）があれば block。理由: 部分一致 `re.search(r"git\s+push\b.*--force")` は (i) **現行コードの潜在誤 block を温存**する（`git push origin feature; echo "use --force"` を実測で誤 block＝`re.match`/`.*` が後続トークンの `--force` まで貪欲に伸びる）。(ii) `--push-option=force` のような非 force 用法や `rm -f x && git push ...` の `rm -f` を誤検知し得る。`_segments` は push セグメントのトークン単位で判定するため AC の4 force 形（`-f`/`--force-with-lease`/`cd foo && --force`/`true; --force`）を全て block しつつ上記誤検知を原理的に排除。実測で全件検証済み（「網羅的賢さでなく単純さ＋健全性」と一貫）。
- Q: ラッパー隠蔽 force（`eval "git push --force ..."`）と config フラグ判定の扱いは → A: **(i) ラッパー隠蔽 force は `_segments` で捕捉されず ask に degrade（block しない）**。Q1（不透明ラッパー）の脅威モデル＝事故では intent が可視・意図的偽装は対象外・`DANGER_OK=1` 解除可、と整合（block より弱いが脅威モデル外の偽装に hard block を当てない一貫方針）。**(ii) ラッパー ask の config 判定は `-c alias.` 限定**（`git -c user.name=x push origin feature` のような非 alias の `-c` config override は ask しない＝誤 ask 回避。alias 間接参照のみが push サブコマンドを隠蔽するため）。
- Q: ラッパーマーカー（`eval`/`sh -c`/`bash -c`/`-c alias.`）の検出は部分一致か構造的か → A: **構造的（`_segments` のセグメント先頭トークン）検出に確定**。各セグメントについて、先頭トークンが `eval`／`sh`・`bash`・`dash`・`zsh` ＋ 同セグメントに `-c`／`git` の `-c` 値が `alias.` で始まる、のいずれかをラッパー痕跡とする。理由: 部分一致 `\b(eval|sh|bash)\b` は `git push origin bash-feature`・`sh-fix`・`eval-remote` のような**ブランチ/リモート名**に偶然含まれる文字列で誤発火し、AC「静的に安全な push は無確認通過」に違反する（実測で確認）。構造的検出はコマンド位置のトークンのみを見るため branch/remote 名の偶然一致を原理的に排除し、既存 `_segments` 基盤を再利用できる（force/動的判定と同じ「単純さ＋健全性」方針で一貫）。回帰 TC（`git push origin bash-feature`・`sh-fix`・`eval-remote` が無確認 pass）を追加。

## 背景/目的

本イシューは I080 の push ガードに残った**2つの回避経路**を塞ぐ（いずれも I080 実装後レビュー／再レビューで発見・実機実証）。

### 欠陥1: 動的宛先の静的解析すり抜け（R5）
I080 で導入した PreToolUse フック（`pretooluse_guard.py` の `_push_protected_target` /
`_norm_push_dest` / `_segments`）は、**シェル展開前の生コマンド文字列**を静的に正規化して
protected ブランチ（develop/main）宛ての push を判定する。このため、実行時にしか宛先が
確定しない形は捕捉できず、protected push が無確認で実行到達する。

develop ブランチの temp git repo を立て、実フックへ stdin JSON を投入して再現確認済み
（リテラルは exit 2 で遮断されるが、以下は全て **exit 0（素通り）**）:

| コマンド形 | 実 exit | 回避種別 |
|---|:---:|---|
| `git push origin develop`（リテラル・対照） | 2 | — 正しく遮断 |
| `git push origin $(echo develop)` | 0 | コマンド置換 |
| `git push origin $(git rev-parse --abbrev-ref HEAD)` | 0 | コマンド置換（**自然なイディオム**・事故耐性なし） |
| `D=develop; git push origin $D` | 0 | 変数展開 |
| `git -c alias.p="push origin develop" p` | 0 | エイリアス間接参照（`push` トークンが消える） |
| `eval "git push origin develop"` | 0 | ラッパー（`git` トークンが消える） |
| `sh -c "git push origin develop"` | 0 | ラッパー |

さらに `.claude/settings.json` の `allow: Bash(git push *)` により、これらは
**プロンプトなしで自動実行**される。deny の完全一致 glob（`Bash(git push origin develop)`）も
文字列不一致で空振りする。

### 欠陥2: force push danger-op の取りこぼし（R6 / F1・High）
フックの force 判定 `re.match(r"git\s+push\b.*--force", cmd, re.I)`（`pretooluse_guard.py:243`）が
**先頭アンカー（`re.match`）かつ `--force` 文字列限定**のため、以下が danger-op を回避する
（feature/x ブランチの temp repo＋実フックで実測）:

| コマンド形 | 実 exit | 回避種別 |
|---|:---:|---|
| `git push --force origin x`（対照） | 2 | — 正しく遮断 |
| `git push -f origin x` | 0 | **`-f` 短縮形（単体ですり抜け）** |
| `cd foo && git push --force origin x` | 0 | 複合コマンド（先頭アンカー外れ） |
| `true; git push --force origin x` | 0 | 複合コマンド |

deny glob `Bash(git push * --force*)` も先頭一致せず空振りし、**非保護ブランチへの force push が無防備**。
他の danger-op（rm-rf/reset --hard/--all/--repo 等）は `re.search` を使い複合コマンドに強いのに、
**force 判定だけ `re.match` で一貫性を欠く**。保護ブランチ宛の force は `_push_protected_target`
（`_segments` 分割）が捕捉するため、漏れは**非保護宛**に限定される。

### 根本原因
- **欠陥1**: 静的トークン照合では、シェルのコマンド置換 `$(...)` / バッククォート / 変数展開 `$VAR`・`${...}` /
  git エイリアス間接参照（`-c alias.x=...`）/ `eval`・`sh -c`・`bash -c` ラッパーを原理的に追跡できない。
  `HEAD` リテラルは解決するのに、同じ意図のシェル展開（`$(git rev-parse ...)`）は素通しする非対称が残る。
- **欠陥2**: force 判定だけが `re.match`（先頭アンカー）かつ `--force` 文字列限定で、`-f`/`--force-with-lease`
  短縮形・複合コマンドを取りこぼす（他の danger-op との実装一貫性の欠如）。

### 解決方針
ブラックリスト（既知の宛先形を列挙）や展開の解決ではシェル表現を追い切れず穴が再発する
（I080 の網羅漏れと同じ失敗）。そこで **allowlist／fail-safe 方式**へ倒す:

- `not danger_ok` の git push のうち、宛先トークンが**単純な静的ブランチ名**（`$`・`` ` ``・`{`・
  `(` を含まず、かつコマンドが `eval`/`sh -c`/`bash -c`/`-c alias.` でラップされていない）と
  確認できるものだけ、従来どおり静的判定する（feature は無確認通過・protected は exit 2 block＝I080 の挙動を維持）。
- 少しでも**動的・不透明**な push（`$(...)`/`$VAR`/`${...}`/エイリアス/`eval`・`sh -c`・`bash -c` ラッパー等）は、
  宛先を安全と断言できないため **ask（確認プロンプト）に degrade** する（hard block ではなく ask。
  「確認できない」に対する正しい応答は人へ委ねること。block＋DANGER_OK 強制は escape hatch の意味の
  すり替えになるため不採用）。develop/main 上でも ask により silent 実行を防ぐ。
- **ask トリガの判定範囲（設計確認で確定）**: (i) 直接 `git push` は `push` 以降の引数領域全体に動的メタ文字
  （`$`/`` ` ``/`{`/`(`）が一つでもあれば ask（宛先トークンの分離に依存しない＝`$(...)` の空白で shlex が
  壊れてもすり抜けない）。(ii) `eval`/`sh -c`/`bash -c`/`git -c alias.` の不透明ラッパーは、ラッパー痕跡が存在し
  かつ `git` と `push` の両トークンが可視のとき ask（脅威モデル＝事故では push 意図が必ずテキストに現れる）。
  ラッパー痕跡の検出は**構造的**に行う＝`_segments` の各セグメント先頭トークンが `eval`／`sh`・`bash`・`dash`・`zsh`＋`-c`／
  `git` の `-c` 値が `alias.` 始まり、のいずれか。部分一致は `git push origin bash-feature` 等のブランチ/リモート名で
  誤 ask するため不採用（branch/remote 名の偶然一致を原理的に排除）。
  push トークンを完全隠蔽する `eval "$VAR"` 形は事故ではなく意図的偽装＝**脅威モデル外**として対象外
  （`docs/claude-code-structure.md` に既知の限界として明記。`DANGER_OK=1` で別途解除可）。
- `allow: Bash(git push *)` は**維持**（settings の glob では `$(`/`$VAR` 判定が困難）。判定はフック側に
  集約し「静的安全なら無確認通過／それ以外 ask」を一手に担う。

**欠陥2（force 取りこぼし）の修正**: force 判定を **pure `_segments` ベース**に確定する（設計確認で確定。
部分一致 `re.search` は不採用）。push を含むセグメントの `push` 以降トークンに force 系フラグ
（`--force`／`--force-with-lease[=...]`／`--force-if-includes`／単一ダッシュ短縮クラスタで `f` を含む
`-f`/`-uf`/`-fu` 等）があるかで判定する（複合コマンド・短縮形に頑健）。これにより
`git push -f origin x`・`cd foo && git push --force origin x` でも DANGER_OK ゲートが効く
（`DANGER_OK=1` 前置で従来どおり解除可）。同時に、現行 `re.match(r"git\s+push\b.*--force")` が
抱える**潜在誤 block**（`git push origin feature; echo "use --force"` を後続トークンの `--force` まで
貪欲一致して誤 block する／`--push-option=force`・`rm -f x && git push ...` の誤検知）を根治する。
なおラッパー隠蔽 force（`eval "git push --force ..."`）は `_segments` で捕捉されず ask に degrade する
（Q1 の脅威モデル＝意図的偽装は hard block 対象外・`DANGER_OK=1` 解除可、と一貫）。

回帰用に、動的回避形の負例 TC（ask 化）・force 取りこぼし形の負例 TC（block 化）・正当な静的/動的 push の
挙動 TC を追加する。

> なお `DANGER_OK=1` 前置時は従来どおり escape（release/hotfix 経路）を維持する。

## スコープ
### 含む
- 【欠陥1】動的・不透明な宛先（コマンド置換/変数展開/エイリアス/`eval`・`sh -c`・`bash -c` ラッパー）経由の push を **ask に degrade**して silent 実行を阻止
- 【欠陥2/F1】force push 判定の取りこぼし修正（`re.search` 化＋`-f`/`--force-with-lease`/短縮結合形・複合コマンド対応）
- 判定のフック集約（`allow: Bash(git push *)` は維持・settings は絞らない）
- 上記の回帰 TC（動的形→ask・force 取りこぼし→block の負例・正当 push の挙動・DANGER_OK escape 維持・false-green 注入）
### 含まない
- 静的形（リテラル名・refspec・`+`・`refs/heads/`・`HEAD`・`--all`/`--mirror`・`--repo`）の保護（I080 で実装・検証済み）
- push 以外の danger-op（reset/checkout/rm 等）の見直し
- **push トークンを完全隠蔽する偽装形**（例 `eval "$VAR"`／`sh -c "$CMD"` で push がコマンド文字列に一切現れない）の検知（事故ではなく意図的偽装＝脅威モデル外。`docs/claude-code-structure.md` に既知の限界として明記し、`DANGER_OK=1` 解除に委ねる）

## 受け入れ条件（Acceptance Criteria）
- [ ] 上記6回避形（`$(...)`・`$(git rev-parse ...)`・`$VAR`・`-c alias.`・`eval`・`sh -c`）が `not danger_ok` で全て **ask 応答**（`hookSpecificOutput.permissionDecision=ask`＋exit 0）を返す決定論 TC が PASS（hard block ではなく ask。develop/main 上でも ask で silent 実行を防止）
