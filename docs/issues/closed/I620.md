- Q: 組織の管理者が利用者を作るときの入力 → A: **ユーザー ID（`User.user_id`）だけ**。メールアドレス・パスワード・名前の欄は作らない（名前の扱いは #621、メールとパスワードの廃止は #622）。作ったら続けて登録用リンクを発行する

- Q: リンクの期限 → A: **1 時間**。1 人につき有効なリンクは 1 つだけで、出し直すと前のリンクは使えなくなる。切れたら管理者が出し直す（BP・Claude が決めた・ユーザー一任）
- Q: 発行の前の本人確認 → A: 発行・失効・パスキーの削除の前に、管理者本人の直前（5 分以内）の本人確認を求める（#619 の `HasRecentReauth` と同じ）（BP・Claude が決めた）
- Q: 組織の管理者自身が端末をなくしたとき → A: **同じ組織のほかの組織の管理者、または運営用の管理者（`is_staff`）が発行する**。自分あてには発行できない。運営用のアカウント（`is_staff`・`is_superuser`）あてには画面・API からは発行できず、サーバーで動かす管理コマンドだけで発行する（BP・Claude が決めた・ユーザー一任）
- Q: 運営用の管理者の発行の範囲 → A: 今の `/admin/users`（運営用）から、どの組織の一般の利用者・組織の管理者にも発行できる。ただし本人ひとりの組織（`Organization.is_individual`）の利用者には発行しない（下の項目）
- Q: 個人利用の人（本人ひとりの組織で管理者が本人だけ）が端末をなくしたとき → A: **運営による復旧はしない**（メールが無く、運営は連絡してきた人が本人か確かめられず、なりすましの入口になるため）。このイシューでは、パスキーの登録の画面で「2 台以上の端末で使えるようにしてください（iCloud キーチェーン・Google パスワード マネージャーなど、端末どうしで同期されるパスキーを推奨）」と案内する。**復旧用のコード**（登録のときに一度だけ見せ、本人が控える）は #633 で、#622 より前に行う（BP・Claude が決めた・ユーザー一任）
- Q: 個人利用の人の最初の登録（今はパスワードの自己登録）→ A: このイシューでは扱わない（#622 でパスキーの自己登録に替える）

- （同上）利用者・組織を無効にするとパスキーはすべて消え、有効に戻しても戻らない（I619）。有効に戻した利用者の登録し直しは、このイシューの登録用リンクで行う
- Q: 本人ひとりの組織の利用者（I539 で自分の組織の `role='admin'`）にも新しい画面を出すか → A: **出さない**。本人ひとりの組織（`Organization.is_individual=True`）の管理者には「メンバー管理」のメニューを出さず、API も拒む（ひとりの組織に人を足せないように）（コードを読んで Claude が決めた・2 回目の grill-me）

## 背景/目的

**背景**: パスワードとメールアドレスをやめると、(1) 新しい利用者の最初のパスキーの登録 (2) 端末をなくした利用者の再登録 (3) 無効から有効に戻した利用者の登録し直し を、メールを使わずに行う手段が要る。ユーザーは「組織の管理者が再登録する」形を選んだ。
**目的**: 組織の管理者が、その組織の利用者向けに 1 回だけ使える登録用リンクを発行でき、利用者はそのリンクからパスキーを登録してログインできる。管理者は組織の利用者のパスキーを見て消せる。

### 現状の問題（証拠・再現手順）
- 利用者の登録はメールアドレスとパスワードでの自己登録（`backend/accounts/urls.py` の `auth/register/`）と本人確認メール（`auth/verify-email/`）、忘れたときはパスワード再設定メール（`auth/password-reset/`）に頼っている
- メールを使わずに登録・再登録する手段が無い
- 利用者を作る画面（`frontend/src/pages/UserManagement.tsx`・`UserCreate.tsx`、API は `backend/accounts/views.py` の `AdminUserViewSet`）は運営用の管理者（`IsAdminUser`＝`is_staff`）だけが使え、組織で絞っていない。組織の管理者（`role='admin'`）が自分の組織の利用者を管理する画面・API は無い
- 管理者がほかの利用者のパスキーを見る・消す手段が無い（#619 の `PasskeyViewSet` は本人のものだけ）

### 根本原因
本人確認と復旧の手段がメールの到達だけに頼っていて、アプリの中で管理者が本人であることを確かめて復旧させる経路が無い。

### 解決方針
- 組織の管理者（`role='admin'`）向けに「メンバー管理」の画面と API を新しく作る。できるのは、自分の組織の利用者の一覧・作成（ユーザー ID だけ）・登録用リンクの発行・失効・パスキーの一覧と削除だけ（ほかの組織の利用者・運営用のアカウント・自分自身には発行できない）。役割の変更と無効化は運営用の管理者だけ
- 本人ひとりの組織（`Organization.is_individual=True`）の管理者には、メニューを出さず API も拒む
- 運営用の管理者（`is_staff`）は今の `/admin/users` から、どの組織の利用者にも発行でき、パスキーを見て消せる（本人ひとりの組織の利用者・運営用のアカウントを除く）。運営用のアカウントあては管理コマンドだけ
- 登録用リンクは推測できない乱数・1 回だけ・期限 1 時間・1 人につき有効なものは 1 つ（出し直すと前のものは失効）。管理者はリンクを自分で利用者に渡す（アプリはメールを送らない）
- リンクの値はハッシュで保存し、元の値は発行した画面で一度だけ見せる（リンクの文字・コピーのボタン・QR コード・閉じると二度と見られない旨）
- 発行・失効・パスキーの削除の前に、管理者本人の直前（5 分以内）の本人確認を求める（#619 の `HasRecentReauth`）
- 発行した時点で、その利用者の古いパスキーをすべて消し、ログイン中の状態（refresh トークン）も使えなくする
- 無効から有効に戻した利用者（パスキーは無い）にも同じリンクで登録し直してもらう
- 利用者はリンクを開いてパスキーを登録し、ログインする
- パスキーの登録の画面に「2 台以上の端末で使えるように（同期されるパスキーを推奨）」の案内を出す
- 発行・使用・失効・管理者によるパスキーの削除をサーバーのログに残す（リンクの値は出さない）

## スコープ
### 含む
- 組織の管理者の「メンバー管理」の画面（一覧・ユーザー ID だけでの作成・登録用リンクの発行・失効・パスキーの一覧と削除）
- 発行した直後のリンクの表示（文字・コピー・QR コード）
- 運営用の管理者による登録用リンクの発行とパスキーの一覧・削除（画面）と、運営用のアカウントあての発行（管理コマンド）
- リンクからのパスキー登録（新規の初回・端末をなくしたときの再登録・無効から戻した人の登録し直し）
- 複数端末でパスキーを使うことの案内
### 含まない
- 組織の管理者による役割の変更・利用者の無効化（今までどおり運営用の管理者だけ）
- パスキーそのものの登録・ログインの仕組み（#619）
- 個人利用の人（本人ひとりの組織）の復旧（#633・運営による復旧はしない）
- 個人利用の人の最初の登録をパスキーにすること（#622）
- 名前の欄・パスワード・メールアドレスの廃止（#621・#622）
