# I620 修正の診断（fix-loop・2026-11-26 14:30）

起点: `docs/reviews/I620_code_review_20261126_1409.md` の止める指摘 F1〜F3（いずれも Medium・delta・再現あり）

## 失敗分解

### F1 追加したメンバーが今のページに無いと、登録用リンクが発行されない
- 再現: 組織のメンバーが 20 人を超え、管理者が 1 ページ目を見ている。［メンバーを追加］で `zzz_user` を追加する（並びはユーザー ID 順なので 2 ページ目に載る）
- 期待: 追加の後に本人確認 → 登録用リンクのダイアログが出る（ボタンの文言「追加してリンクを発行」）
- 実際: 「メンバーを追加しました」だけが出て、リンクは発行されず、何の案内も無い。`justAdded` も残ったまま
- ログ: なし（画面の部品が描かれないので発行の処理が動かない）

### F2 登録画面を開いて 5 分を過ぎてから押すと、1 回目の登録が失敗する
- 再現: リンクを開き、6 分後に［パスキーを登録］→ 端末の確認を終える
- 期待: 登録できる
- 実際: 開いたときに取った challenge（期限 `WEBAUTHN_CHALLENGE_TTL_SECONDS` = 300 秒）を使うので、`consume_challenge` が期限切れで拒み「パスキーを登録できませんでした」。2 回目は通る。ファイルの冒頭の説明「押すたびに取り直す」とも食い違う
- ログ: `passkey register failed … reason=challenge` 相当（期限切れ）

### F3 パスキーの origin の一覧が空だと、設定の読み込みで起動できない
- 再現: `WEBAUTHN_ALLOWED_ORIGINS=`（空）かつ `REGISTRATION_LINK_BASE_URL` 未設定で `manage.py check`
- 期待: システムチェック `accounts.E001`（origin が空）で止まる（I619 の決まり）
- 実際: `settings.py` の読み込みで `WEBAUTHN_ALLOWED_ORIGINS[0]` が `IndexError` になり、どのコマンドも動かない

## 根本原因
- F1: 「追加の後の発行」を、一覧の行の部品（`MemberCredentialActions` の `autoIssue`）が描かれたときに動かす形にした。行が今のページに無いと描かれないので発行が動かない。発行の起点を、描画の結果（どの行が見えているか）に結び付けたのが原因
- F2: /simplify の効率の指摘（開いたときの challenge が使われない）に対し、1 回目は開いたときの challenge を使う形に変えた。challenge には 5 分の期限があり、ページを開いてから押すまでの時間は利用者次第なので、期限切れになりうる
- F3: 既定値を、設定の読み込み時に空でありうるリストの先頭から取った。空の場合の扱い（I619 はシステムチェックで報告）を考えていなかった
- セキュリティ: どれも認証・認可・機密データの露出には当たらない（F1 は発行されないだけ・F2 は失敗するだけ・F3 は起動しないだけ）。F2 の challenge の期限は守られている（期限切れで拒んでいる）

## 対応方針（全案＋推奨）

### F1
- 案 A（推奨）: 追加の後の発行を画面（`MemberManagement`）の `handleAdd` で直接行う。作成 → 本人確認 → `credentialApi(MEMBERS_BASE).issueLink` → 画面の 1 つの `RegistrationLinkDialog` で出す。行の部品の `autoIssue` と `justAdded` を消す
  - 良い: 発行がどのページにいても動く。描画と発行が分かれ、仕組みが単純になる（足すより消すほうが多い）
  - 悪い: 発行の処理が行の部品と画面の 2 か所から呼ばれる（どちらも同じ `credentialApi` の関数で、失敗の文も同じ定数を使う）
- 案 B: 追加の後に、そのメンバーが載るページへ移ってから行の部品に発行させる
  - 悪い: 何ページ目かをサーバーに聞く必要があり、描画に結び付いたまま。複雑
- 案 C: 追加の後は発行せず「行から発行してください」と案内する
  - 悪い: 画面の文言・流れ（「追加してリンクを発行」）が変わる＝ユーザーが了承した案から外れる

### F2
- 案 A（推奨）: 押すたびに options を取り直す（/simplify の前の形に戻す）。開いたときの options はリンクが使えるかの確かめと表示だけに使う
  - 良い: 期限切れが起きない。冒頭の説明と一致する
  - 悪い: 開いたときの challenge の行が 1 つ使われずに残る（期限 5 分で、次に challenge を作るときに消える・I619 の片付け）。認証なしで作れる行はスクロットルで抑えている
- 案 B: 開いたときの options の取得時刻を覚え、期限の内なら使い、外なら取り直す
  - 悪い: 端末の時計に頼る・状態が増える。得るものが小さい
- 案 C: 開いたときは challenge を作らない軽い確かめの API を足す
  - 悪い: API が増える（範囲が広がる）

### F3
- 案 A（推奨）: 既定値を「一覧の先頭、空なら `FRONTEND_URL`」にする（`(WEBAUTHN_ALLOWED_ORIGINS or [FRONTEND_URL])[0]`）。空の一覧は I619 の E001 がこれまでどおり報告する
  - 良い: 1 行で直り、設定の読み込みで落ちない。E001 の決まりを保つ
- 案 B: 既定値を `FRONTEND_URL` にする
  - 悪い: ワークツリーのように `FRONTEND_URL` と画面の origin がずれる環境で、リンクから登録できない（implement で実際に起きた）

## 影響調査
- F1: `autoIssue` を使うのは `MemberManagement` だけ（`StaffCredentialsCard` は使っていない）。消しても他に影響しない。Jest の TC-22（追加 → 本人確認 → 発行 → リンクの表示）を、追加したメンバーが一覧に無い場合で確かめる形に直す
- F2: `PasskeySetup` だけ。Jest の TC-24 の「options の呼ばれる回数」を 2 回（開いたとき＋押したとき）に戻す
- F3: `settings.py` の 1 行。同じ形（空でありうるリストの先頭を読み込み時に取る）を `grep` で探したが、`WEBAUTHN_ALLOWED_ORIGINS` を作る行は空の要素を除くだけで先頭を取らない。ほかに無い。再現のテストは、空の一覧で設定を読み直すと落ちる形を決定論で作りにくいので、既定値を作る小さな関数（`default_link_base(origins, frontend_url)`）に切り出して、空・空でないの 2 つを pytest で確かめる
