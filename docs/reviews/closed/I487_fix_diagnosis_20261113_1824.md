# I487 修正の診断（コードレビュー F7・React Query への置き換えの後）

## 失敗分解
- 出どころ: `docs/reviews/I487_code_review_20261113_1811.md` の止める指摘 F7（Medium・`frontend/src/pages/Settings.tsx:192-193`）
- 再現手順: 目標 30 分・今日 45 分学習・目標達成のお知らせはまだ出ていない状態で、設定画面で目標を 60 分にして保存し、ダッシュボードへ戻る
- 期待値: 目標は 60 分なので、目標達成のお知らせは出ない（45 < 60）。60 分に届いたときに出る
- 実際値: 保存のときは `invalidateQueries` だけなので、ダッシュボードに戻ると、設定のキャッシュ（古い 30 分）が「成功」のまま返り、取り直しが終わるまでの間に `useDashboardAchievements` が 30 分で判定する。45 ≥ 30 で目標達成のお知らせが出て、`dailyGoalDate` に今日が記録される。新しい 60 分に届いたときには出ない
- ログ: なし

## 根本原因
- `invalidateQueries` はキャッシュを「古い」と印を付けるだけで、次に読むまで古い値を返し続ける（React Query の stale-while-revalidate）。保存した値（PATCH の応答）が手元にあるのに、キャッシュに入れていなかった
- 達成の判定は「目標の取得が終わった（成功）」ことだけを見ていて、その値が古いかどうかを見ていない
- セキュリティ: 該当なし（端末の表示用の記録だけ）

## 対応方針（全案＋推奨）
### 案 A（推奨）: 保存の応答で設定のキャッシュを書き換える（`setQueryData`）
- `Settings.tsx` の保存の成功時に、PATCH の応答（`updatedSettings`・裏側が保存した値）を `queryClient.setQueryData(userSettingsKey(user.id), updatedSettings)` で入れる。ダッシュボードに戻ったときは、最初から新しい目標で判定・表示する
- React Query の公式の推奨（Updates from Mutation Responses）。取り直しの通信も要らない
- セキュリティ影響: なし。BP: 公式の推奨の形。保守性: 1 行の置き換え
- リスク: `user` が無いときは書けない（設定画面はログインした利用者だけが開く画面なので、その場合は `invalidateQueries` に倒す）
### 案 B: 保存のときにキャッシュを消す（`removeQueries`）
- 次にダッシュボードを開くと設定を取り直し、その間は目標の表示を隠す（読み込み中）
- 短所: 取り直しの通信が要り、目標の 1 行が一瞬消える。手元にある新しい値を使わない
### 案 C: 達成の判定を、目標の取得が終わって取り直し中でもないときだけにする（`isFetching` を見る）
- 長所: 別のタブで設定を変えたときなど、ほかの古いキャッシュの道筋も防ぐ
- 短所: 判定の条件が増え、`useDailyStudyGoal` の状態の形も変わる。今回の再現（この画面で保存した直後）は案 A で根から消える
### 推奨: 案 A（粗く確実・公式の推奨・最小）。TC-10d を「保存の後、設定のキャッシュが保存した値になっている（古い値を返さない）」に変える

## 影響調査
- 同型のバグ: 設定のキャッシュを使うのは `useDailyStudyGoal` だけ（`grep -rn "user-settings\|userSettingsKey" frontend/src`）。数字（overview）・科目の一覧は、この画面から書き換えないので同じ問題は無い
- 他の呼び出し: `NotificationContext` は設定をキャッシュを通さずに取る（今のまま）
- テスト: TC-10d を書き換える（保存の前は 45、保存の後は 50 がキャッシュに入る・取り直しを待たない）
