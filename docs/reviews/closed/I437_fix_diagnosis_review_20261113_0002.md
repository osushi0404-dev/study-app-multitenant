# 診断レビュー [I437]

## 指摘一覧
| 重大度 | 観点 | 指摘内容 | 該当箇所 |
|--------|------|---------|---------|
| Info | 根本原因 | 根本原因は成立している。「欄名の完全一致の一覧」という方式のため、別名の欄が増えると漏れる。コードで確認できた（`enhanced_logging.py:16-24, 239-241`）。`FieldValidationView` の `value` という同型の漏れも、`views.py:551-552` の実在を確認した。 | enhanced_logging.py |
| Info | 対応方針 | 案Bは妥当。残る点が2つある。(1) `_safe_body` は `dict(request.data)` で、トップレベルのキーしか見ない。JSON のネスト（例: `{"data": {"password": ..}}`）は伏せられない。今回のエンドポイントはどれもフラットなので現状の実害はない。ただし範囲外として台帳に残す、またはテストで「ネストは対象外」と明記するとよい。(2) `key` が文字列でない場合に備え、`str(key).lower()` にする。例外時は `None` を返すので漏れはしない。 | `_safe_body` |
| Info | 対応方針 | 語の一覧に `refresh` を入れると、`refresh_interval` のような無害な欄も伏せる。記録の手がかりが減るだけで、安全側の挙動なので許容できる。ただし、`user_id` などの個人情報を完全一致のまま残す理由（R4）が、計画書に反映されていることを確認すること。 | 案B |
| Info | 影響調査 | `value` は完全一致で足す案だが、DRF の `request.data` で `value` という欄を持つ別 API が将来増えると、その欄が過剰に伏せられる。実害は小さい。 | PERSONAL_BODY_FIELDS |

## 影響調査の網羅性評価
- **同型バグ**: serializer の秘密欄と、ビューが `request.data` から直接読む欄を全件確認している。私の grep でも、直接読む欄は `refresh`・`field`・`value`・`subject_id` ほかで、記載と一致した。`value` 以外に、一覧から漏れる秘密や個人情報の欄は見つからなかった。
- **呼び出し箇所**: `_safe_body` の呼び出しは `ErrorContextMiddleware` だけである。参照は `enhanced_logging.py` 内に限られ、`REDACTED_BODY_FIELDS` を他ファイルから使う箇所は無いことを確認した。`mask_sensitive_data` は未使用で、範囲外とする判断も妥当。
- **波及**: ログの内容だけが変わり、API の応答・画面・DB には影響しない。
- **計画との整合**: 案Bは計画の方式（完全一致）を秘密欄について変える。診断メモは、計画書を直して計画レビューを通すことを明記しており、プロセス上も適切。
