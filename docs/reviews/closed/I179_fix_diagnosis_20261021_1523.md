## 1. 失敗分解

再現の共通手順: 使い捨て git repo に primary、入れ子 `.claude/worktrees/nest`（未コミットのファイルあり）、兄弟 `../sib` を作り、cwd=primary で `{"tool_name":"Bash","tool_input":{"command":"<入力>"}}` をガードに渡す。期待値はすべて exit 2（`DANGER_OK=1` でも止める）。

### F1（High・第 7 周の修正の後退）sed のスクリプト除外の取りこぼし
- 入力: `sed -i -es/a/b/ .claude/worktrees/nest/f`・`sed -i -e's/.*//' …`・`sed -i -nes/a/b/p …`・`sed -i -f/tmp/s.sed …`・`sed -i -es/a/b/ ../sib/f`

## 2. 根本原因
- **F1・F5（第 2〜3・5〜6 周と同じ構図）**: 誤ブロックを減らすための精密化（sed のスクリプトを除く・前置きの種類を区別する）が、再現しきれない書き方を抜け道にした。
- **F2・F4 の多く（作業フォルダの追跡の再現漏れ・3 回目）**: 作業フォルダを「コマンドの順番どおりに追う」方式は、bash の意味（サブシェル＝括弧・パイプ・`&`・`$( )`、シェル内／別プロセスの前置き、`cd -`・`pushd`/`popd` のスタック）を正しく再現しないと穴になる。第 6 周の括弧、第 7 周の前置き、第 8 周のパイプ・`&` と、再現する範囲を広げるたびに次の漏れが見つかっている。区別する処理が増えるほど、それぞれを固定する TC も必要になり、テスト不足の指摘（F4）も増える。
- **F3**: 移動元を位置で決める（最後が宛先）という前提が `-t` で崩れる。位置の意味を再現している点で同じ種類。
- **共通の根**: 「シェルの意味を再現して正確に判定する」方向の設計。安全装置としては「再現しない・分からないものは止める側に寄せる（和集合で判定する）」べきだった。
- **セキュリティ観点**: 承認（`DANGER_OK=1` でも解けない）なしに他のワークツリーの未コミット作業を消せる経路（OWASP A01 相当）。アプリの認証・認可・XSS・インジェクションには該当しない。機密データの露出も無い。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨）: 作業フォルダを順に追わず、コマンド中のすべての移動先を「基準の候補」として和集合で判定する
- **基準の候補**: セッションの作業フォルダに加え、コマンド全体（順番・括弧・パイプ・`&` に関係なく）に出てくる移動先をすべて集める: `cd`・`pushd` の引数、`-C`・`--chdir[=]`・`-C<dir>`・`-D`（前置きの値）、`GIT_WORK_TREE=`・`GIT_DIR=`、`git -C`・`--work-tree`・`--git-dir` の値。`cd -`・`popd`・`~-` は「どれかの候補」なのですべての候補を含める（追加の候補は不要）。`~+` は全候補に置き換えて判定する。固定でない移動先（変数・置換を含む）は候補にしない（計画の「対象外」どおり。既存の警告のみ）。
- **対象の判定**: 書込・削除・破棄の対象パス（相対）は、**すべての候補を基準に**絶対パスにして判定し、どれか 1 つでも別ワークツリーのもの（または中に別ワークツリーを含む）なら止める。git の読み取り以外の操作は、すべての候補（と `-C` 等）を対象フォルダとして判定する。
- **コマンドの読み方**: 前置き（`command`・`builtin`・`time`・`env`・`sudo`・`timeout`・`exec`・`nice`・`nohup`・`stdbuf`・`ionice`・`doas`）はすべて「後ろに現れる既知のコマンド名の位置をすべて候補にする」方式にそろえる（シェル内／別プロセスの区別をやめる）。`cd` かどうかで作業フォルダを変える処理自体が無くなるので、前置きの種類を区別する必要もない。
- **sed**: スクリプトの除外をやめ、オプション以外の引数をすべてパスとして見る（第 7 周の前の挙動）。
- **mv**: 位置引数と `-t`/`--target-directory` の値をすべて移動元として見る（中身も見る）。cp の宛先は従来どおり（`-t` の値と最後の位置引数。展開を含めば中身も見る）。
- **括弧・スタックの処理**: 不要になるので消す（`_loose_segments` の括弧の目印・`st`・`stack`・`sub_stack`）。
- **誤ブロック（受容）**: (1) 1 つのコマンドの中で別ワークツリーへ `cd` し、その後に自分側の相対パスを消す・書く形（例: `(cd .claude/worktrees/nest && git status) ; rm -r build`）は止まる（まれ。コマンドを分ければ通る）。(2) sed のスクリプトに展開文字を含む形（`sed -i '2{s/a/b/}' f` 等）が、primary（中に入れ子がある場所）で止まる（第 7 周で解消した誤ブロックが戻る。回避: スクリプトを `-e` の後ろに置いても同じなので、スクリプトファイル（`-f`）に書く・サブフォルダで実行する）。§9 に書く。
- セキュリティ: 順番・括弧・パイプ・`&`・前置きの種類を再現しないので、この種類の抜け道が構造的に無くなる（どの候補でも別ワークツリーに当たれば止まる＝和集合）。ベストプラクティス: 安全装置は「分からないものは止める側」。保守性: 処理が減る（括弧・スタック・前置きの区別・sed の除外を削除）。テスト: 区別する処理が無くなるので、F4 の TC 不足の多くは対象ごと消える。リスク: 上の誤ブロック 2 種。

### 案 B: 公式のサンドボックス（`sandbox.filesystem.denyWrite`）で OS レベルで止める
- 調査（claude-code-guide・公式文書 sandboxing / settings-reference / permissions / worktrees / sub-agents）: primary から `.claude/worktrees` への Bash の書込・削除を OS レベルで止めることはできる。ただし書込には「禁止した中の一部だけ許可する」設定が無く、primary の設定が入れ子のセッションと `isolation: worktree` のサブエージェントにも届くと、自分のワークツリーに書けなくなる可能性が高い（未検証）。`git worktree remove`・`wt-remove.sh` の撤去も止まる。Linux/WSL2 では bubblewrap・socat の導入が要る。hooks・MCP・`!` は対象外。
- セキュリティ: 文字列の解析に頼らない点で最も強いが、公式配置（入れ子）と両立しない恐れが大きい。保守性: 設定は少ないが、撤去・サブエージェントの手順を作り直す必要がある。リスク: 高い（未検証の前提が多い）。→ 本イシューでは採らない。将来、公式が「入れ子の自分だけ許可」に対応した時点で再検討する候補として §9 に 1 行残す。

### 案 C: 個別に塞ぐ（sed の続けて書く形・パイプ/`&` のサブシェル・`mv -t`・TC 追加）
- セキュリティ: 今回の入力は止まるが、再現する範囲を広げるたびに次の漏れが見つかる構図が続く（第 6〜8 周の実績）。ユーザー指示（同種の繰り返しは設計を粗く）に反する。→ 採らない。

### 推奨: 案 A
理由: 同じ種類の抜け道（シェルの意味の再現漏れ）を構造的に無くせる唯一の案で、処理とテストも減る。誤ブロックは「1 つのコマンドで別ワークツリーへ cd してから自分側を消す」「展開文字を含む sed のスクリプト」に限られ、回避手順で解ける。
