## 指摘一覧（助言）
| 重大度 | 観点 | 指摘内容 | 該当箇所 |
|--------|------|---------|---------|
| Warning | 根本原因 | 根本原因は「各段階が終わりごとに書き込む作りで、全体の回数と間隔を見る仕組みが無い」という内容です。これは現状の問題（段階ごとに push する、本文を何度も書き換える）の言い換えに近いです。「なぜ段階ごとに書き込む設計になったか」には触れていません。たとえば、記録の永続化と GitHub への同期が分離されていない、push が review-gate の前提になっている、といった構造的な原因です。また、停止の原因が書き込みの集中だというのは、背景に書かれているとおり推測です。根本原因の節でも「推定」と明示すると、原因の確度が分かりやすくなります。 | 根本原因 / 背景 |
| Warning | 自己完結度 | 現状の問題の数値が根拠なしです。「push が 10 回以上」とありますが、実測値や出典がありません。他の項目（本文の書き換え、コメント）には回数がまったくありません。ベースラインが無いので、受け入れ条件の「今より減った」を検証できません。 | 現状の問題 / AC1 |
| Warning | スコープ・受け入れ条件 | AC1 の測り方が未定で、AC2 の「集中しない」にも基準がありません（たとえば N 分に M 回まで）。どちらも検証可能な形になっていません。「未定」の明示はありますが、計画着手前に少なくとも測定方法（ログ集計、`gh` ラッパーの記録など）の案が必要です。 | 受け入れ条件 AC1・AC2 / 制約 |
| Info | 解決方針 | 候補が 4 つ並んでいるだけで、優先順位や採否の基準がありません。push をまとめる案は、review-gate の CI 待ち（制約に記載）と衝突しうるので、トレードオフを事前に書いておくと計画しやすくなります。「同時に複数のセッションで書き込まない決まり」は、強制するのか運用ルールだけなのかも不明です。 | 解決方針 / 制約 |
| Info | 実装対象 | `.claude/skills/` は対象スキルが特定されていません。`scripts/claude/` も「未特定」と明示されています。どの段階のスキルが push やイシュー編集をしているかは、grep で洗い出せる既知の範囲です。計画時に一覧化すると具体的になります。review-gate の確認を含む変更範囲も列挙に入っていません。 | 実装対象 |
| Info | スコープ | 「同時に複数セッションで動かさない」は、サポートへ約束した再発防止なのに、スコープの「含む」に明示されていません。また、`claude -p` のテストの並列実行（I220 M-03・M-04）の扱いが、含む・含まないのどちらにも書かれていません。 | スコープ / 関連資料 |

## 次のアクションの推奨
未確定箇所（回数の実測、集中の基準、採用する方針）を埋めるため、`/grill-me` を推奨します。特に先に決めたいのは次の 3 点です。
1. 現状の書き込み回数の測り方（ベースライン）
2. 「集中しない」の数値の目安
3. 4 つの候補のうち採用するもの

根本原因は、設計上の理由まで書き足しておくと、計画の精度が上がります。
