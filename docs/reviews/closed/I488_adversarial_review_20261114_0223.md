1. **他組織の問題への答えが集計に混ざる経路。**
   - `build_analytics` が `QuizAnswer` を読むのは `_answers(user)` だけです。これは `scope_to_user_org(..., subject_path='problem__subject')` を通ります。
   - `has_data`、`scoped`、`subject_breakdown`、`_between` はすべて、この土台の queryset から派生しています。他組織の科目名や数字が出る別経路はありません。
   - 自分の答えだけを数えるのは `session__user=user` の絞り込みです。他人の答えが入る経路はありません。
   - 組織なしの利用者は、土台が空になるため 0 件になります。
2. **`subject_id` の検証の抜け道。**
   - `OrgSubjectField` は `available_subjects(request.user)` の範囲だけを受け付けます。これはリクエストの利用者を使う実装です。
   - 数字でない値、他組織、全体共有、存在しない ID はいずれもフィールドの `subject_id` エラーになります。ビューは `days` のエラーでなければ固定の 1 種類の 400 を返すので、body は同一です。
   - `days` と `subject_id` が両方不正な場合は、`days` の 400 を先に返します。これは計画どおりで、存在の推測にはつながりません。
   - 空文字の `subject_id` も、フィールドのエラーとして同じ科目の 400 になります。
3. **科目の絞り込みが内訳に漏れる経路。**
   - `subject_breakdown` は意図どおり全科目ですが、元は `_answers` なので境界は保たれています。
