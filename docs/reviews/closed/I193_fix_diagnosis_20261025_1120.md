- 再現手順: 設計書 `docs/proposals/I193_official_base_flow.md` の §7（自作で残すスキル・レビュー役）と、計画 §5.9 で組み込んだ自作の判定スクリプトを、§3 の漏れの行（L1〜L14）と 1 つずつ突き合わせる
- 期待値: 自作で残すものが、すべて §3 のどれかの行（公式だけでは止まらない漏れ）に対応している（受け入れ条件 3）
- 実際値: 次の 2 つが §3 のどの行にも対応していない
  1. fix-loop の 3 つのレビュー役（`fix-diagnosis-reviewer`・`fix-implementation-reviewer`・`fix-test-reviewer`）。§7 では「レビュー役 7 本」の行に含まれ、置き場所と道具の制限（L7・L8）だけが書かれていて、残す理由（どの漏れを止めるか）が無い
  2. I187 の判定スクリプト 3 本（`check-frontend-evidence.sh`・`check-manual-test-executor.sh`・`check-permission-prompt.sh`）。計画変更記録 5 で流れに組み込んだが、設計書の §3・§7 に無い
- ログ: 手動テスト No.8 の実結果

## 根本原因
- 1: 設計書の §3 を「人の承認を外すと止まらなくなる漏れ」と「公式に置き換えるもの」から書き、fix-loop の中のゲート（I165 などで作った直しの診断・テストの十分性の確認）を「今あるものを残す」扱いにして、漏れとして書き出さなかった
- 2: 計画変更記録 5（範囲の追加）で計画書・スキルは直したが、設計書（設計の根拠）を同じ変更で直さなかった（計画を変えたら、根拠の文書も一緒に直す決まり〔plan-writing-rules.md「ルール変更時に関連ファイルを同時更新する」〕の漏れ）
- セキュリティ観点: 文書の欠けで、動きの穴ではない。認証・注入・秘密情報には当たらない

## 対応方針
- 案 A（推奨）: 設計書 §3 に 2 行足す
  - L15: 直しの診断の誤り・直した後のテストの空振り（公式に「直しの前後をレビューする」仕組みは無い。GitHub は CI のテストだけを見る）→ 載せる: fix-loop の 3 つのレビュー役（診断・実装・テストの順のゲート）
  - L16: 画面の動きを人が見ないまま進む・Claude で確かめられる確認を人に振る・承認画面が出るかを人に聞く（Playwright MCP・`claude -p` は確かめる手段で、記録の有無や振り分けは判定しない。GitHub は止めない）→ 載せる: I187 の判定スクリプト 3 本（I187 の「公式と自作の分担」）
  - あわせて §7 の test-gate の行に I187 の判定スクリプトを、レビュー役の行に「fix 系 3 本は L15」を書く。TC-01 D2 を L1〜L16 にする（FG は今の L13 を消す形のまま）
  - セキュリティ影響なし・BP 適合（根拠を 1 か所に保つ）・保守性よし・リスク小（文書とテストの期待値だけ）
- 案 B: fix-loop のレビュー役を消す（自作を減らす）
  - 直しの診断・テストの空振りを止める場所が無くなる（I193 でもテストレビューが 2 回、正しい差し戻しをした）。漏れが止まらなくなるので採らない
- 案 C: 受け入れ条件 3 の対象を §7 の「スキル」だけに狭める
  - 受け入れ条件を緩める変更で、計画レビューのやり直しが要る。根拠を書かずに残すことになるので採らない
