# I205 修正の診断（F11・2026-10-27）

## 失敗分解
- 出典: `docs/reviews/I205_code_review_20261027_1307.md`（台帳 2 周目）の止める指摘 F11（`STOP=flow`・再現あり）
- 再現手順: 一時の git リポジトリで `docs/foo bar.md`（空白を含むパス）の 3 行目を変えたブランチを作り、`code-review.sh` を関数だけ読み込んで `delta_hunks develop ""` を実行する（scratchpad の f11.sh で実行済み）
- 期待値: `docs/foo bar.md<TAB>3<TAB>3` の 1 行（3 列）
- 実際値: `docs/foo bar.md<TAB>1<TAB>999999999` と `docs/foo bar.md<TAB><TAB>3<TAB>3`（4 列）の 2 行
- ログ: `git diff -U0` の出力が `+++ b/docs/foo bar.md<TAB>`（行末にタブ）。4 列の行を `ledger_update` が `p, s, e = l.split("\t")` で読むと ValueError で落ち、本体はこれを「FINDING 行の形が崩れている」として BLOCKER にする。空白を含むファイルを変えたイシューでは、レビューが毎回 BLOCKER になり先へ進めない（止める条件 ① 流れが動かなくなる）

## 根本原因
- git は、パスに空白があると `---`・`+++` の見出しの行末にタブを付ける（パスの終わりを示すため）。`_HUNKS_PY` は `+++ b/` の後ろを行末までそのままパスにしており、このタブを取り除いていない
- `ledger_update` は塊の行を「ちょうど 3 列」と決めつけて読んでいる（パスにタブが入ると崩れる）
- 計画 4.11 で見出しの読み方を直したときに、空白を含むパスを確かめるテストが無かった
- セキュリティ: 認証・認可・インジェクション・秘密情報には関係しない（読み取りの崩れで流れが止まるだけ。止まる向きなので見逃しにはならない）

## 対応方針（全案＋推奨）
- 案 A: `_HUNKS_PY` で `+++ b/` の後ろの行末のタブを 1 つ取り除く（`rstrip("\t")`）
  - 良い点: 原因そのものを直す。1 行
  - 悪い点: パスの末尾が本当にタブのファイル（実際には無い）は区別できない
- 案 B: `ledger_update` の塊の行の読み方を `rsplit("\t", 2)`（後ろから 2 つの数字の列を取る）にして、パスにタブが入っても落ちないようにする
  - 良い点: 読み取りが崩れても流れが止まらない
  - 悪い点: 単独では、タブ付きのキーが残り範囲の比較に一致しない（ただし計画 4.11 の F2 の処理で、そのファイルはファイル全体の塊にもなるので、止める側に倒れる）
- 案 C: `git diff -z` などで機械向けの出力に変える
  - 悪い点: `-U0` の塊の読み方を作り直すことになり、新しいコードが大きくなる（I197 の教訓に反する）
- **推奨: 案 A ＋ 案 B**。A で原因を直し、B で同じ種類の崩れ（列の数のずれ）があっても流れを止めない。どちらも 1 行で、新しいコードはほとんど増えない。テスト H10（空白を含むパスで 3 列の 1 行が出て、台帳が作れる）と FG（A を外すと不合格）を足す

## 影響調査
- 同じ型の読み取り: `_HUNKS_PY` の `diff --git` の行の `rsplit(" b/", 1)` は、行末にタブが付かない（git の仕様。見出し `diff --git` には付かない）ので影響なし。`--- a/` の行は読んでいない
- 他の呼び出し: 塊の一覧を読むのは `ledger_update` だけ（`grep -n 'split("\\t")'`）。`kinds`・`blocking`・`verdict` は塊を読まない
- gate-check.sh・adversarial-review.sh は塊を使わない（変更なし）
