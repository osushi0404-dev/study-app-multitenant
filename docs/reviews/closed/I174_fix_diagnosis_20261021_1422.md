# I174 fix-loop 診断メモ（5 回目の fix-loop・/security-review の Blocker への対応）

- 起点: `docs/plans/open/plan_I174.md` 末尾「セキュリティレビュー結果」（2026-10-21・Blocker 1 件）
- 範囲: Blocker の 1 件だけ（High・Medium・Low は既知・受け入れ済み・または記録済みで、この fix-loop では扱わない。I181 の観点で変更を小さく保つ）

## 1. 失敗分解

| 再現手順（mktemp -d の一時リポジトリ） | 期待値 | 実際値 | ログ |
|---|---|---|---|
| `git -c core.fsmonitor='touch PWNED' checkout -- f`（f は変更あり）を見張りに判定させる | 判定だけで何も実行されない | PWNED が作られた（判定は 2） | `rc=2 pwned1=YES` |
| `core.fsmonitor` を設定した別のリポジトリへ `cd … && git checkout -- g` を判定させる | 同上 | PWNED が作られた | `rc=2 pwned2=YES` |

## 2. 根本原因

計画 0-14 で入れた `_git_loc`／`_git_run` は、判定対象のコマンドの `-c key=val`・`-C`・`--git-dir`・`--work-tree`・`GIT_DIR=`・cd の先をそのまま使って、見張り自身が `git rev-parse`／`git status` を実行する。git は設定（`core.fsmonitor`・clean フィルタ等）や、実行した場所のリポジトリの `.git/config` によって任意のコマンドを実行するため、**人の承認より前に、見張りがコマンドを実行する**。I174 以前は、見張りの作業ディレクトリ（このリポジトリ）でだけ git を実行していた。

セキュリティ観点: コマンドインジェクション（OWASP A03）に当たる。入口はモデルが書くコマンドと、取り込んだ外部リポジトリの設定。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨）: 信頼できる場所でだけ git を実行し、コマンド由来の設定は渡さない
- `_git_run` は、判定対象のコマンドの `-c` を渡さない（場所の指定 `-C`・`--git-dir`・`--work-tree`・`GIT_DIR`／`GIT_WORK_TREE` だけを使う）。`-c core.fsmonitor=false` を付ける。
- 実行してよい場所は、見張りの作業ディレクトリで `git worktree list --porcelain` から得た「このリポジトリとその worktree」の配下だけ（realpath で比較。`-C`・cd の先・`--git-dir`・`--work-tree`・`GIT_DIR` のすべて）。それ以外では git を実行しない。
- 信頼できない場所での、場所に依存する判定（未コミット変更の取り消し・今のブランチで宛先が決まる push）は、0-15 と同じく**確認**にする（推測で通さない）。
- セキュリティ影響: 見張りが外部の設定でコマンドを実行する経路が無くなる。信頼する場所の `.git/config` は、このリポジトリの利用者が管理するので信頼してよい（I174 以前と同じ前提）。
- ベストプラクティス: 判定器（フック）は副作用を持たず、信頼できない入力でコードを実行しない。読めないものは人に委ねる（0-13・0-15 と同じ方針）。
- 保守性: 場所の判定は `_git_run` の 1 か所に集まる。
- リスク・副作用: 一時ディレクトリや別のリポジトリでの git の書き換え（`cd /tmp/x && git checkout -- f`）が、精密判定から確認に変わる。作業記録の再判定で増え方を確かめる（上限 1%）。

### 案 B: git に無害化のオプション（`-c core.fsmonitor=false`・`core.hooksPath` 等）だけを付けて、場所は今のまま
- 実行される設定の種類（フィルタ・`core.sshCommand` 等）を列挙しきれず、列挙漏れが残る。不採用。

### 案 C: 見張りが git を実行するのをやめ、場所に依存する判定をすべて確認にする
- 安全だが、このリポジトリでの普段の `git checkout -- <file>`・`git push` の精密判定（停止）が無くなり、確認が増える（I174 の目的に反する）。不採用。

### Claude 推奨: 案 A

## 4. 影響調査（実施済み）

- 同型: 見張りが subprocess で外部コマンドを実行する箇所は、`_git_run`（`_current_branch`・`_worktree_dirty` から）と、作業ディレクトリでだけ動く既存の git 呼び出し（`git worktree list` 等・コマンド由来の設定を使わない）。コマンド由来の値を使うのは `_git_run` だけ。
- 他の呼び出し箇所: `_current_branch`（push の宛先）・`_worktree_dirty`（取り消し）。どちらも `_git_run` を通るので、`_git_run` の修正で両方に効く。
- 関連機能: worktree 横断書き込みのブロック（`_cross_worktree`）は git を実行しない（パスの比較のみ）ので影響なし。
- テスト: 上の 2 形で PWNED が作られないこと・判定が確認か停止になること、このリポジトリ内（worktree を含む）の精密判定が後退しないことを自動テストにする。

## 5. 改訂（代替の診断レビュー `I174_fix_diagnosis_review_20261021_1430.md`・HIGH 2 件への対応）

案 A を次のとおり具体化する（案の選択は変えない）。

### A-1. 信頼する場所は「配下」ではなく「一致」で決める
- 信頼する場所: 見張りの作業ディレクトリで `git worktree list --porcelain` から得た各 worktree の最上位（realpath）と、その git-dir（各最上位で `git rev-parse --absolute-git-dir`。どちらも見張りの作業ディレクトリ側の信頼できる情報だけで得る）。
- 判定する場所（cd の先・`-C` の連結）が、ある最上位 R の配下でも、R との間に別の `.git`（ディレクトリかファイル）がある＝**入れ子のリポジトリ**なら信頼しない。
- コマンドの `--git-dir`・`--work-tree`・`GIT_DIR`・`GIT_WORK_TREE` は、信頼する git-dir・最上位と**完全に一致**するときだけ受け入れる（リポジトリの中に新しく作った偽の git-dir は一致しないので信頼しない）。
- 見張りが実行する git には、信頼する git-dir と最上位を `--git-dir=<信頼する git-dir> --work-tree=<R>` として**明示して**渡し、git 自身の探索（近い `.git` を探す）を使わない。作業ディレクトリは判定する場所（`cwd`）にする（パスの指定はそこからの相対で解決される）。
- 信頼しない場所では git を実行せず、場所に依存する判定は確認にする（0-15 と同じ）。

### A-2. セキュリティレビューの必須条件との対応

| 必須条件（計画書・Blocker 行） | 案 A での扱い |
|---|---|
| コマンド由来の `-c`・`--config-env` を渡さない | 渡さない。見張りが組み立てる引数だけで git を実行する |
| コマンド由来の `GIT_*` 環境変数・設定ファイルの指定を渡さない | 渡さない。さらに見張りの環境からも `GIT_` で始まる変数を除いて実行する（Claude の環境に紛れ込んだ値の影響も受けない） |
| 実行してよい場所は、このリポジトリと worktree だけ | A-1（一致・入れ子の除外・明示の git-dir） |
| `-c core.fsmonitor=false`・`-c core.hooksPath=/dev/null` 等の無害化 | 付ける（`core.fsmonitor=false`・`core.hooksPath=/dev/null`） |
| `status` に `--no-renames`・`status.showUntrackedFiles=no` | 付ける（`--no-renames`・`--untracked-files=no`。未追跡のファイルは判定に使っていない） |
| フィルタの実行は信頼できる場所だけ | A-1 により、フィルタの設定が効くのは信頼する git-dir の設定だけ（本物の git も同じ設定で動く） |

### A-3. 「信頼しないので実行しない」と「git の失敗」を区別する
- `_git_loc_trusted(loc)` を新設し、場所に依存する判定（`_git_revert_check`・`_analyze` の push_dynamic）が先に呼ぶ。信頼しない場合は確認にする（`_git_run` が None を返して素通しになる経路を作らない）。信頼する場所での git の失敗は、今までどおり（I174 以前からの fail-open）。

### 残余リスク（記録）
- 信頼するこのリポジトリの `.git/config` を、それより前のコマンド（`git config core.fsmonitor …`）で書き換えた場合は、見張りの git でも設定が効く。ただし I174 以前から同じで、本物の git も同じ設定で動くため、この fix-loop の範囲外とする（計画書の残余リスクに記す）。
