# 敵対的レビュー [I473] ── 観点: 2. テストの false-green・tautology

## findings
反証失敗（新規指摘なし）。探索した仮説:
- TC-12（V3）が、片方だけ数える形や、データが少ないと常に通る形になっていないか。
- TC-22（V4）が、正常な応答でも通る形、または別の理由で偶然通る形になっていないか。
- 数える側の `_count_queries` が、キャッシュの有無で結果を変えていないか。

各仮説の結果は次のとおり。実験は返していない。

- **V3（TC-12 `test_query_count_is_constant`）**
  - 同じ `_count_queries` を、答え 1 件の状態（small）と、科目 3 つ・各 20 日分の答えを足した状態（large）の両方で呼んでいる。
  - `assert small == large` で両者を比べ、さらに `large == 9` と実数も固定している。片方だけを数える形ではない。
  - 数える前にキャッシュを毎回消している。そのため、キャッシュが当たった側だけ本数が減る、という偏りは出ない。
  - large 側では、正答率が約 33% の科目が 3 つできる。小さい側では `weak_subjects` が空なので、データの量で分岐する経路を両方通る。
  - 実装は、候補の集計を件数が足りていても省かない作りになっている（`selectors._recommendations`）。そのため、データが増えて本数が増える退行が起きれば、このテストは落ちる。
- **V4（TC-22）**
  - `last_7_days` を欠いた応答と、`totals` を欠いた応答を、`it.each` で別々に流している。
  - どちらも `role="alert"` に「ダッシュボードの数字を読み込めませんでした」が出ることを見ている。
  - あわせて、「0分」「0日」「0%」と `stat-answered-count` が出ないことも見ている。正常な応答だけで通る形ではない。
  - 自動テスト文書によると、`totals` だけを欠く形は、確かめを外しても別の例外で偶然通る false-green だった。
  - そのため `last_7_days` を欠く形が足してある。文書には、確かめを外すと落ちることを実測した記録がある。
  - 補足として、`last_7_days` を欠く応答でもコンポーネントは落ちずに描ける。この形が `isDashboardOverview` を固定する本命の経路になっている。
