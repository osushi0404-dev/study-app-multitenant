## 2. 根本原因
- **F1・F2（共通の根）**: 第 2 周で、ガードの「生の文字列への正規表現」を「シェルを模したトークン判定」に**置き換えた**。トークン判定は誤ブロックを減らせる一方、シェルの文法（空白なしの区切り・前置コマンドのオプション・`-lc` のような結合オプション・`$( )`・予約語・関数・ヒアドキュメント）を部分的にしか再現しないため、正規表現が持っていた「どこに書かれていても止める」性質を失った。安全装置の判定方式を変えるときに「旧方式で止まっていた入力は新方式でも止まる」（後退しない）を検証する差分テスト（新旧比較）を用意していなかった。ヒアドキュメント除外は、誤ブロック（データとしての文字列）を減らす目的で入れたが、境界の判定が不完全なため、実行されるコマンドを隠す経路になった。
- **F3**: 敵対的レビューの対応で設計（Danger Ops の契約）を変えた際に、消費箇所（イシュー・計画の冒頭/表・runbook の別節・danger-ops.md）の全件更新を行わなかった（plan-writing-rules の「消費箇所の全件更新」の不履行）。
- **F4**: 「確定できなければ止める」（fail-closed）を優先した結果、止めた後に人が安全に進める手順（持ち主を確かめたうえで手で片付ける・バックアップが実際に取れたことの確認）を設計していなかった。
- **F5**: TC が「その機能を壊したら落ちるか」（変異）ではなく「代表的な入力で通るか」で書かれていた。
- **セキュリティ観点**: 本件はハーネスの安全装置（破壊的操作の承認ゲート）の不備。F1・F2 は「承認なしで開発 DB の volume を消せる」経路で、OWASP の分類では A01（アクセス制御の不備）に相当する。アプリの認証・認可・XSS・インジェクションには該当しない。機密データの露出も無い。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨）: 正規表現を元に戻し、トークン判定は「追加の検出」として重ねる
- ガード: develop の正規表現（`docker compose … down … -v`）を生の文字列に対して維持し、第 1 周で足した形（compose と down の間のオプション）・短縮結合（`-vt`）・`docker volume rm/remove/prune`・`docker system prune … --volumes` も**生の文字列への正規表現**で止める。そのうえで、正規表現が取りこぼす形（`docker --context x compose …`・クォートした `"down"`）だけをトークン判定で**追加**検出する（どちらかが一致したらブロック＝和集合）。ヒアドキュメント除外は撤回する。
- 後退の防止: 新旧比較 TC（develop のガードで exit 2 の入力が新ガードでも exit 2）を追加し、第 3 周の再現入力（F1・F2 の全形）を TC にする。
- 誤ブロック: コミットメッセージ・grep の引数中の文字列で止まる性質は develop と同じに戻る（受容。既知の種類で、`DANGER_OK=1` 前置または文言の言い換えで回避できる）。トークン判定の `down` はサブコマンドの位置だけを見る（`pytest -k down -v` を誤ブロックしない）。
- セキュリティ: 後退が無くなり、第 1・2 周の追加分だけ強くなる（最も安全）。ベストプラクティス: 安全装置は「疑わしきは止める」が原則で、誤ブロックは承認で解ける。保守性: 判定が 2 系統になるが、それぞれ単純。リスク: 誤ブロックが develop 並みに残る。
### 案 B: トークン判定のまま、シェル文法の再現を強化する
- 空白なしの区切りの分割・前置コマンドのオプション読み飛ばし・`-lc` 等の結合・`$( )`・バッククォート・予約語・関数・ヒアドキュメントの正しい境界を実装する。
- セキュリティ: 網羅できれば誤ブロックも減るが、シェル文法は広く、取りこぼしが再発しやすい（今回と同じ種類の失敗）。保守性: 低い（複雑）。リスク: 高い。
### 案 C: develop の正規表現に戻し、第 1 周の追加（`-p` 等）だけを正規表現で残す（トークン判定を撤回）
- セキュリティ: 後退は無いが、`docker --context x compose …`・クォート・`-vt` の取りこぼし（第 2 周 Medium）が戻る。保守性: 最も単純。リスク: 低いが、既知の穴を残す。

### F3〜F5 の対応（どの案でも共通）
- F3: イシュー（受け入れ条件・Danger Ops・関連箇所）・計画 4-6 冒頭/設計判断表・`worktree.md` §5(C)・`danger-ops.md`（Docker の例に volume 削除を追加）を新しい契約に揃え、GitHub のイシュー本文も同期する。
- F4: (1) 作業フォルダ不一致・同名で止まった場合の手順を §4 に書く（`docker ps -a --filter label=… --format …` で持ち主を確かめ、撤去対象のものと確認できたら、承認を得て primary から `DANGER_OK=1 docker compose -p <名前> down -v` を実行し、その後に `wt-remove.sh` を再実行する。§4 の取り残し手順の「フォルダ名と違うこと」の条件は「持ち主を確かめていない名前を指定しない」に改める）。スクリプトに「持ち主を無視して消す」抜け道は足さない（消す前に人が確認する手順を明示する）。(2) バックアップ案内: コンテナが無い場合は `docker compose -p <名前> up -d db` で起動してからダンプする案内にし、ダンプ後に `test -s <ファイル>`（空でないこと）を確かめる手順を加える。ファイル名の直後の全角括弧をやめる。再実行の案内を `bash <スクリプト>` の形にする。(3) §11: コピーしない untracked は wt-harness のセッションで削除してから撤去／未 push の入れ子は、必要なら push（不要なら wt-harness のセッションでブランチと作業を確認のうえ、入れ子の中で `git reset` 等はせず、入れ子を残したまま外側の撤去を見送る）と書く。
- F5: R21 を作業フォルダ 2 行（撤去対象と別の場所）に・スタブで空ラベルも作れるように・P15 を変数ごとの TC に分ける（`export` だけ・クォートだけ・`BACKEND_PORT2` を先に置く）・`_CMD_PREFIXES`/`eval`/`&` の TC を追加・`pytest -k down -v` の許可 TC。`xargs`/`find -exec`/`docker.exe` は案 A なら正規表現（`\bdocker(\.exe)?\s+volume\s+(rm|remove|prune)\b` を生の文字列に）で止まる。

### 推奨: 案 A ＋ F3〜F5 の共通対応
理由: 安全装置の変更は「後退しない」が最優先。案 A は develop 以上の強さを構造的に保証でき（和集合）、新旧比較 TC で将来の後退も決定論で捕まえられる。案 B は今回の失敗と同じ種類の取りこぼしを再生産しやすく、案 C は既知の穴を残す。

## 4. 影響調査
- 同型バグ: ガードの他の規則（`git push`・`rm -rf`・`git reset --hard`・SQL）は、すべて develop のまま生の文字列への正規表現と `_segments` ベースの判定で、今回の置き換えの影響を受けていない（第 2 周で変更したのは Docker の volume 削除の判定だけ）。既存のガードのテスト（adversarial_trigger 40・checkout 14・gh_pr 245・push 87）は全件 PASS。
