## 根本原因
`code-review.sh` の機械判定 2 系統に対し、I134_auto_test.md の文書構成が不適合だった:
1. **omission_lint（code-review.sh:209-220）**: 「`## 決定論ゲート（自動実走）` セクションの**外**にある fenced ```bash ブロック内に allowlist ゲートパターン（`grep -q`/`grep -L` 等）があれば HIGH」を返す。plan-review Warning 対応で TC-03〜06 のスクリプト**全文**を auto_test に fenced ブロックで掲載した際、スクリプト内部の `grep -q` 行がこのパターンに一致した（ゲート隠蔽ではなくスクリプト参照掲載だが、lint は区別しない仕様）。
2. **run_declared_gates（同 :181-205）**: formal セクションが無いため「決定論ゲート宣言なし」となり、ALLOW 分類で自動実走可能な TC-01 の grep 2 本がハーネス実走されていない（宣言していれば毎回 exit code が証跡注入される）。

セキュリティ観点: 該当なし（テスト文書の構成問題。認証・認可・入力処理・機密データに関与しない）。

## 対応方針（全案＋推奨）

### 案 A（推奨）: formal gate 宣言＋スクリプト全文の計画書移設＋将来制約コメント
- auto_test.md に `## 決定論ゲート（自動実走）` セクションを新設し、TC-01 の grep 2 本（ALLOW・現に exit 0）を宣言する。
- TC-03〜06 のスクリプト全文を計画書 `plan_I134.md` の新設節「検証スクリプト全文（scratchpad 実行用）」へ移設し、auto_test の各 TC は同節への参照とする（omission_lint は AUTO_TEST_FILE のみを検査するため解消。スクリプト本文の記録要求＝plan-review Warning「計画書・テスト文書のいずれにも残っていない」は計画書側で満たし続ける）。
- Medium 対応: `check-issue-background.sh` 冒頭コメントに「formal gate 化する場合は `scripts/claude/tests/` へ移動が必要（classify_gate allowlist は `bash scripts/claude/tests/*.sh` のみ ALLOW）」の 1 行を追記する。
- メリット: lint の意図（自動実走可能なゲートは宣言し毎回実走させる）へ正面から適合。TC-01 が以後のレビューで常時機械実走される。セキュリティ影響なし・保守性良（置き場の分散は相互参照で緩和）。
- デメリット/リスク: スクリプト全文の置き場が計画書側へ移る（auto_test 単体では全文が見えない。参照明記で緩和）。

### 案 B（不採用推奨）: スクリプト内の `grep -q` を `grep --quiet` 等へ書き換えて lint を回避
- メリット: 変更が最小。
- デメリット: 検知器の意図を欺く偽装であり、ベストプラクティスに反する（lint は同義オプションを追うたびに軍拡競争になる）。将来 lint 強化で再発。セキュリティ影響はないが筋が悪い。

### 案 C（不採用推奨）: TC-03〜06 を `scripts/claude/tests/` に常設し formal gate 宣言
- メリット: 全 TC が機械実走される理想形に見える。
- デメリット: TC-03 はネットワーク依存（gh で 41 件走査）・TC-05/06 は実行時にしか存在しないスナップショット/退避ディレクトリ引数が必要で、code-review のたびに自動実走されると FAIL（fail-closed で BLOCKER 化）または長時間化する。環境依存ゲートの常設は false-red を生み、比例性を欠く。
