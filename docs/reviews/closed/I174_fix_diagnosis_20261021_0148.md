## 2. 根本原因

**git の判定が 2 つの経路に分かれ、経路ごとに「git の見つけ方・オプションの読み方・実行場所の扱い」が違う。**

| 判定 | 経路 A: 最上位の文字列（`_segments`） | 経路 B: 読み解いた単純コマンド（`_parse`→`_cmd_danger`） |
|---|---|---|
| 保護ブランチへの push | `_push_protected_target`（`_danger_reasons`） | `_cmd_danger` が同じ関数を単純コマンドごとに呼ぶ（0-13 で追加） |
| force push | `_push_has_force` | 同上 |
| 宛先の読めない push | `_push_is_dynamic`（main・**経路 A だけ**） | なし → H2 |
| `--all`・`--mirror`・`--repo` | `_danger_reasons` の正規表現（**A だけ**） | なし |
| 未コミット変更の checkout/restore | `_git_revert_target_on_dirty`（**A だけ**・`git` の直後の語しか見ない・見張りの cwd で status） | なし → H1 |
| reset --hard・clean -f | なし | `_cmd_danger`（`_git_sub` で -C 等を飛ばす） |

- 経路 A は入れ子のシェル（`bash -c`・`bash -lc`・ヒアドキュメント・`eval`・xargs/parallel/watch の中）を見ない。経路 B は入れ子を `_parse` が展開するので見える。
- `git` の見つけ方: A は `"git" in toks` の完全一致（第 2 周で push 3 関数だけ basename に直した）、B は先頭の basename。
- オプション: A の checkout/restore は `rest[0]` が checkout/restore のときだけ（`-C`・`-c`・`--work-tree` が入ると外れる）。B は `_git_sub` で飛ばす。
- 実行場所: 第 2 周で push だけ `-C` と `cd` を追うようにしたが、checkout/restore（`_worktree_dirty`）は見張りの cwd のまま。`cd` の読み取りも `len(toks)==2` だけ（`cd -- X`・`cd -P X` を外す）。`--git-dir`・`--work-tree`・`GIT_DIR=` は未対応。

このため、第 2 周 #2（push の実行場所）を直すと第 3 周 H1（checkout の実行場所）が、0-13（入れ子の push の宛先・force）を直すと第 3 周 H2（入れ子の push の動的宛先）が残った。**個別の書き方を潰す修正を続ける限り、もう一方の経路に同じ穴が残り、周回が収束しない。**

H3（テスト）の原因: 経路 A と B の両方が同じ形を止めるため、片方を外しても他方が止め、テストが「どちらの経路で止めたか」を区別しない。git.exe は差分テストの DANGERS にも無い。

M6（誤確認）の原因: 第 2 周で、経路 A の (ii)(iii) を「語のどこかに push」という文字列の一致に広げた。引用符の中の検索語も push と数える。

M5 の原因: `_wrap_skip` の値を取るオプションの一覧が短い形だけで、長い形（`--arg-file`）や parallel の主要オプション（`-a`・`--halt`・`--colsep`・`-I`）が無い。

M7〜M10・L12 の原因: danger-ops.md の「未コミット変更の取り消し」「rm -rf / find -delete」を、名前（`checkout/restore`・`-r` と `-f` の両方）で列挙しており、同じ結果になる別の操作（ステージ済み・`--pathspec-from-file`・`git rm -r`・`rm -r`・`find -exec rm`・`clean.requireForce=false`・push 設定の変更）が抜ける。

### セキュリティ観点
- 影響は「意図しないデータ消失（未コミット・ステージ済みの変更、作業ファイル）」と「保護ブランチへの意図しない push」。認証・認可・インジェクション・XSS・機密データ露出には該当しない（見張りは開発者のローカル環境の事故防止で、外部入力を受けない）。
- 見張りは `subprocess.run` に引数の配列を渡しており（`shell=False`）、判定対象のコマンド文字列がシェルとして実行されることはない。今回追加する `git -C <path> status` も同じ方式にする。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨）: git の判定を経路 B の 1 か所にまとめ、実行場所を 1 つの「git の文脈」で追う
- `_git_ctx(c)` を新設する。入力は単純コマンド（入れ子を展開済み）。返すのは、サブコマンドとその引数、実行場所（`cd`/`pushd` の引き継ぎ〔`cd --`・`cd -P`・`~` 対応〕＋ `-C` の連結＋ `--work-tree`／`--git-dir`／`GIT_DIR=`・`GIT_WORK_TREE=`）、`-c key=val` の一覧、場所が読めない（変数・置換を含む）か、xargs/parallel から展開されたか（`_expand` で印を付ける）。
- push・checkout/restore・reset・clean・`git rm`・`git config` の判定を、すべて `_cmd_danger` の中で `_git_ctx` を使って行う。経路 A の `_push_protected_target(cmd)`・`_push_has_force(cmd)`・`_git_revert_target_on_dirty(cmd)`・`--all/--mirror/--repo` の正規表現は `_danger_reasons` から外す（関数は単純コマンド用に作り直す）。
- 「宛先の読めない push」（`$`・`` ` ``・`{`・`*` を含まない動的宛先・xargs/parallel 由来・`git -c alias.*push`・場所が読めない）は、単純コマンドごとに判定して `_analyze` の結果に `push_dynamic` として返す。main はそれを確認にする。最上位の文字列一致の (ii)(iii) は廃止する（→ M6 の誤確認も消える）。
- 未コミット変更の判定は、実行場所で `git -C <場所> status --porcelain -- <path>` を行う。ステージ済み（1 文字目）も変更ありに数える（M7）。`--pathspec-from-file` は確認、`git rm -r`（`--cached` なし）は変更ありなら停止（M9）。
- 判定の追加: `-c remote.*.push=`・`git config remote.*.push`・`git config push.default`（matching）を危険操作に（M8）。`git -c clean.requireForce=false clean` を停止に（L12）。`rm -r`/`-R`（`-f` なし）・`find -exec/-execdir rm`・`xargs rm` を `rm -rf` と同じ扱いに（M10。作業記録の再判定で新規停止が 1% 以内か確かめる）。
- `_wrap_skip` の値を取るオプションに、xargs の長い形と parallel の主要オプションを足す（M5）。
- テスト: 差分テスト（oracle）の git の印を出す関数を、実行場所を解決するものにする。一時リポジトリ（feature/x＋develop の worktree＋未コミット変更のあるファイル）を 1 回だけ作り、`-C`・`cd`・`--work-tree` で場所を変える書き方 × 入れ子の包み方 × git の呼び方（`git`・`/usr/bin/git`・`git.exe` 相当の関数）を総当たりする。push テスト・container テストに H1〜L13 のケースを足し、S28・S29 を一時ディレクトリにする（M11）。pushd・`~` のケース（L13）。
- **セキュリティ影響**: 判定を 1 か所にまとめることで、入れ子・場所の変更・git の呼び方で判定が変わる穴がまとめて消える。外部入力やインジェクションのリスクは増えない（subprocess は配列渡し）。
- **ベストプラクティス適合**: 1 つの読み取り結果に判定を当てる形（構文を読む処理と判定の分離）。0-13 で入れたエントリでの正規化と同じ方針。
- **保守性・拡張性**: git の判定を足すときは `_git_ctx` の結果に条件を 1 つ足すだけ。経路が 1 つなので、テストで「どちらの経路が止めたか」を考える必要がなくなる（H3 の根因の解消）。
- **リスク・副作用**: 変更は大きい（push 関数群の作り直し・main の順序の変更）。既存テスト 747＋114＋301 件と作業記録の再判定（新規の確認・停止 1% 以内）・差分テストで回帰を確かめる。git status を場所ごとに呼ぶので、1 回の判定の時間がわずかに増える（`git` を含むコマンドだけ）。

### 案 B: 指摘ごとの局所修正（これまでの周回と同じやり方）
- `_git_revert_target_on_dirty` に `-C`・cd を足す、(ii) を `-lc`・`-ec` に広げる、などを指摘ごとに足す。
- セキュリティ影響: 指摘された形は塞がるが、経路が 2 つのままなので同型の穴が残る。
- ベストプラクティス: 不適合（同じ規則が 2 か所に分かれたまま）。
- 保守性: 低い。第 1〜3 周と同じく周回が収束しない見込み。
- リスク・副作用: 1 回の変更は小さいが、レビューの周回と時間が増え続ける（ユーザー指摘「レビューに時間がかかりすぎ」に反する）。

### 案 C: 場所を変える git と入れ子の push は、まとめて確認にする（保守的な単純化）
- `-C`・`--git-dir`・`--work-tree`・`GIT_DIR=` を持つ git の書き込み系と、`cd` を含むコマンドの中の checkout/restore/push、入れ子の中の push は、中身を判定せず確認（ASK）にする。
- セキュリティ影響: 穴は塞がる（確認止まり＝人の判断に頼る）。
- ベストプラクティス: 中程度（読めないものを確認に回す fail-safe）。
- 保守性: 中程度（経路は 2 つのまま。新しい git の判定を足すたびに同じ問題が起こりうる）。
- リスク・副作用: `cd <repo> && git push` のような普段の作業が確認になり、I174 の目的（承認待ちの削減）に反する。H3（テスト）・M5〜M10 は別途必要。

### Claude 推奨: 案 A
根因（判定の経路が 2 つ）を直接取り除く唯一の案。案 B はこれまでの 3 回の周回で収束しなかったやり方の繰り返し、案 C は I174 の目的に反する。
