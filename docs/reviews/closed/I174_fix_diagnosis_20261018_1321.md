## 2. 根本原因

### 2-1. bash の文法を読む処理が複数あり、規則がばらばら
- 引用符・コメント・ヒアドキュメント・継続を読む処理が少なくとも 6 か所に分かれ、それぞれが自前の規則を持つ: `_scan_quotes` / `_strip_comments`（引用符とコメント）・`_cut_heredocs`（ヒアドキュメント。`<<<` を含む行ではその行のヒアドキュメントを全部無視する）・`_cut_substitutions`（`$( )`）・`_join_continuations`（継続。コメントの直前の文字の集合が `_is_comment_start` と違い `\n` を含む）・shlex（`_segments`・`_raw_commands`・`_safety_net` の 3 か所）。`$'…'` はどこも扱っていない。
- 1 か所を直すと、ほかの処理との食い違いが新しい穴になる（第 1 周で継続を足す → 第 2 周でコメント・本文と食い違う → 第 3 周で入れ子・`<<<` と食い違う）。

### 2-2. 「bash と同じに読めているか」を確かめる仕組みがない
- テストは具体例（入力と期待値）だけで、見張りの読み方が bash の実際の動作と一致しているかは確かめていない。例を足すたびに、例の外側の形（別の文脈の組み合わせ）で食い違いが残る。テストの観点の指摘（分岐を外しても合格）もこれが原因。

### 2-3. 読みきれない形を素通しにする
- 引用符が閉じない（`$'it\'s'` の読み違いを含む）・ヒアドキュメントが閉じない形で、shlex の代替経路（`text.split()` で 1 つのコマンドにまとめる）に落ち、後ろの行の危険なコマンドが引数として扱われて素通しになる。

### 2-4. セキュリティ観点
- 開発ハーネスの見張り（人の承認なしにデータ消失・保護ブランチへの push・秘密情報の表示を起こさない）の穴で、CLAUDE.md 絶対ルール 4 に関わる。アプリの認証・認可・入力処理は変えない。OWASP では A01（承認の迂回）に相当。

## 3. 対応方針（全案＋推奨）

### 案 A: これまでどおり、指摘の形ごとに直してテストを足す
- 内容: 第 3 周のテストの抜け（T1〜T6）と Medium（`$'…'`・`$(( << ))`・`#` の誤認）を個別に直してテストを足す。
- セキュリティ: 今回の形は塞がるが、2-1・2-2 が残るので次の組み合わせでまた食い違う（実績: 3 周連続で同じ種類）。
- ベストプラクティス: 自前の字句解析を場当たりで広げる形。
- 保守性: 処理が 6 か所のまま。
- リスク・副作用: 速いが収束の見込みがない。

### 案 B: bash 本体を「正解」にした差分テスト＋読みきれない形は確認（推奨）
1. **bash との差分テスト**（新規 `scripts/claude/tests/test_guard_bash_oracle.sh`）: 危険なコマンド（`git reset --hard`・`git push --force`・`rm -rf`）を、前置きの文脈（引用符の中の `#`・`'…'`・`"…"`・`$'…'`・コメントの末尾の `\`・`<<'EOF'` / `<<EOF` / `<<-EOF` / `<<'EOF-PR'`・`<<<`・`$(( << ))`・`bash -c '…'`・`bash <<'EOF'`）と書き方（1 行・継続で折る位置 2 通り・前の行と `&&` / `;` / 改行でつなぐ）の組み合わせで自動生成する。各スクリプトを、mktemp -d の中で本物の bash に実行させる（`git` と `rm` は「危険な引数で呼ばれたら印を出すだけ」のシェル関数に置き換えて `export -f` する。ほかは echo・cat・wc・tr など無害なものだけを使う）。**bash が危険なコマンドを実行した形では見張りが 2 であること**を確かめ、合わなければ不合格。bash が実行しない形（本文・引用符の中）で見張りが止めたら件数を表示する（余計な停止）。
2. **読みきれない形は確認**: 引用符・ヒアドキュメントが閉じない（shlex の代替経路に落ちる）・`$'…'` を含む、のどれかなら、精密判定が何も返さなくても確認（ask）にする（2-3 の fail-open をなくす）。
3. **差分テストで見つかった食い違いを直す**: 文法を読む処理のうち食い違いの出たものを、`_scan_quotes` の 1 つの状態機械（引用符・`$'…'`・コメント）にそろえる（`_strip_comments`・`_cut_heredocs`・`_join_continuations` が同じ判定を使う）。第 3 周の T1〜T6 と Medium（`$'…'`・`$(( << ))`・`#` の誤認・`<<<` の行のヒアドキュメント）は、差分テストの生成の範囲に入れて確かめる。
- セキュリティ: 「bash が実行するのに見張りが見ない」形を、例を書かずに組み合わせで機械的に見つけられる。読みきれない形は確認になるので、残った食い違いも素通しにならない。
- ベストプラクティス: 自前の構文解析器は、本物の処理系と突き合わせる差分テスト（differential testing）で正しさを確かめるのが定石。字句解析の規則を 1 か所にまとめるのも定石。
- 保守性: 文脈・書き方を 1 行足すと差分テストが広がる。処理の規則が 1 か所にそろう。
- リスク・副作用: 差分テストは bash を実際に実行するので、生成するスクリプトは無害なコマンドと置き換えた関数だけに限る（書き込みは mktemp -d の中だけ）。実行時間（数百件 × bash の起動）はゲートの 1 行 120 秒に収める（件数を調整）。読みきれない形の確認が増えすぎないかは、作業記録のゲート（`test_guard_corpus_diff.sh`）で測る。

### 案 C: bash の構文解析ライブラリ（bashlex 等）に置き換える
- 0-12 の診断と同じ理由（依存の同梱・全面書き換えの後退リスク・bashlex にもヒアドキュメント等の未対応がある）で見送る。案 B の差分テストは、将来どの読み方に変えても使える。

### 推奨: 案 B
- 2-2（正解との突き合わせが無い）を差分テストで、2-3（読みきれない形の素通し）を確認で、2-1（規則のばらつき）を 1 つの状態機械へのそろえで直す。手順 4 の承認の後、計画書 0-13 に記録してから実装する。

## 4. 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
- 同型バグ: 文法を読む 6 か所すべてが対象（2-1 の一覧）。push・checkout の判定（`_segments`）も shlex を使うので、差分テストに `git push --force` を入れて確かめる。
- 他の呼び出し箇所: guard は Bash の PreToolUse だけ。Edit/Write の判定は変えない。
- 関連機能: 総当たりの表（`test_pretooluse_guard_matrix.sh`）は「操作 × 書き方」、差分テストは「文脈 × 書き方」で、役割を分ける。I146 の gh pr ガードの `_safety_text` は別の前処理なので影響しない（ステップ 6 の取り込みで差分テストに `gh pr` を足すかを決める）。
- 承認待ちへの影響: 「読みきれない形は確認」で増える確認は、作業記録のゲートで 1% 以内を確かめる（`$'…'` は作業記録に少ない見込み）。
