# 診断レビュー [I636]

## 指摘一覧
| 重大度 | 観点 | 指摘内容 | 該当箇所 |
|--------|------|---------|---------|
| HIGH | 影響調査 | 「MUI の `Snackbar` は使っていない・`grep` で確認」は事実と違う。`UserCreate.tsx`、`UserEdit.tsx`、`UserManagement.tsx` が `Snackbar` を使っている。既定位置は下の左側なので上のバーと重なる可能性は低い。ただ、調査結果が誤っているため、同型調査を信用できない。この 3 画面について、`Snackbar` と react-hot-toast が併存する前提で、重なりや二重表示がないかを書き直す必要がある。 | 影響調査 1 |
| HIGH | 影響調査 | 通知を `top: 72` に出すと、同じ縦位置にあるアクセシビリティ設定パネルと重なる。パネルは `AccessibilityProvider.tsx:212` で `top: 72`・`right: 16`・幅 320 に出る（上のバーのボタンから開いたとき）。360px 幅だと、通知（350px の既定幅）がパネルの上端を覆う。react-hot-toast の z-index（9999）は、パネルの 1001 より高い。パネルは通知が出ている間に開かれやすく、直接の原因になった「通知がボタンを塞ぐ」と同型の問題が新たに生じる。案 A のリスクにこの点がなく、影響調査にもない。 | 対応方針 案 A／影響調査 2 |
| Info | 対応方針 | 案 A は「上のバーと縦に分ける」という方針として妥当。ただし 72px は上のバーの高さ（56px／64px）とパネルの `top: 72` を直書きで合わせた値。上のバーの高さが変わると壊れる。定数の共有か、コメントで根拠を残すとよい。 | 案 A |
| Info | 根本原因 | 根本原因は、ボタン数の数え違いと、E2E の確認対象がユーザーメニューのボタンだけだったこと。コードと画像の証拠があり、成立している。 | 根本原因 |
| Info | 対応方針 | 確かめ方に「直す前に落ちることを確認する」と「上のバー全体（`banner`）を対象にする」が入っているのは良い。パネルを開いた状態での重なりの確認も加えること。 | 確かめ方 |

## 影響調査の網羅性評価
- **同型バグ**: 上のバーや右下の［＋］と重なる一時的な表示の調査は、一部が誤っていて、一部が漏れている。
  - `Snackbar` の使用箇所が 3 画面あるのに、「使っていない」と書かれている。
  - 同じ上端付近に出るアクセシビリティ設定パネルを調べていない。
- **波及**: 全画面の通知位置が 16px から 72px に変わる点は調べてある。ログイン画面と登録用リンク画面は、上のバーがなくても同じ位置に出る点も調べてある。
- **計画との関係**: AC12 を強める方針と、敵対的レビューの周回の扱いは妥当。
- 上の 2 件の HIGH を診断メモで補えば、案 A で進んでよい。補うのは、`Snackbar` 使用箇所の再調査と、パネルとの重なりの評価（対策、または許容する理由）。

VERDICT: HIGH
