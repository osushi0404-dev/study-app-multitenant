## 主要な学び（根本原因分析）

### 事象
auto_test の TC-11a / TC-11b が **false-green**（検証対象が壊れても OK を返す）状態で計画段階に提出された。
- TC-11a: `grep -q 'VERDICT: <BLOCKER\|HIGHRISK\|OK>'` は BRE で `\|` が OR となり「HIGHRISK」部分一致で常に通過。
- TC-11b: `for ...; do ... || { echo NG; break; }; done; echo OK` は break 後も末尾 `echo OK` が無条件実行され、見出しが消えても OK。
→ plan-reviewer が指摘（私の自己ゲートでは検出できなかった）。

### 理想 vs 実際
| ステージ | 理想 | 実際 |
|---------|------|------|
| plan-issue（文書品質ゲート） | 否定・回帰系 TC を「失敗条件を注入して NG が出る」ことまで確認してから提出 | 正常系で OK を返すことのみ確認し提出 |
| plan-issue-review | 「合否判定 TC が false-green でないか」をチェック項目として保持 | 一般推論で偶発的に検出（チェック項目化されていない） |

### 5 Whys: 否定・回帰系 TC の false-green
- Why1: なぜ壊れても OK を返す TC を提出したか？ → 「正常時に OK」だけ確認し「異常時に NG」を確認しなかった。
- Why2: なぜ異常時を確認しなかったか？ → 文書品質ゲートが回帰・不在・否定アサーションの TC に対し「失敗条件で不合格になること」の検証を要求していない。
- Why3: なぜ要求がないか？ → 既存ゲートは「lint / 静的解析ツールの**異常系**を実際に実行し非ゼロ終了を確認」という**特定ケース**にのみ異常系実行を求め、grep / 存在否定 / 無改変確認など**一般の決定論 TC** へ一般化されていない。
- 根本原因（抽象化済み）: **決定論的な合否判定 TC（特に否定・不在・回帰アサーション）について、失敗条件を注入して実際に不合格を出すことを検証する、という要求がゲートに一般化された形で存在しない。**
- 抽象化テスト: I071 固有語（grep・P9・TC-11）を除いても「否定・回帰系の合否判定ロジックは失敗条件で実際に不合格を出すことを検証してから採用する」で成立 → 一般化可能。
- 分類: **予防処置**（TC を持つ全イシュー・決定論ゲート全般で再発し得る）。ユーザーの目標運用モデル「検証は①手続き<②決定論ゲート<③敵対的検証」において、false-green は**見かけ上のゲートだが実体は手続き未満**であり、ゲート品質を担保する仕組みが必要。

| # | カテゴリ | 根本原因 | 予防策（do+gate 2層） | 対象ファイル |
