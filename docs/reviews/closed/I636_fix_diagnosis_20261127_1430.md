# I636 fix-loop 診断メモ（2026-11-27 14:30）

起点: fix-loop（通知を上のバーの下へ・パネルを手前に）の後の差分のレビュー `docs/reviews/I636_code_review_20261127_0952.md` の止める指摘 F5・F6。

## 失敗分解
- F5
  - 再現手順: 幅 360px で、パスキーの登録の直後（通知「パスキーを登録しました」が出ている間）に、上のバーのユーザーメニューを開く
  - 期待値: メニューの「設定」「ログアウト」を押せる
  - 実際値: 通知（上から 72px・`z-index: 9999`・幅は既定の最大 350px）が、メニュー（`Layout.tsx` の `Menu`・ユーザーメニューのボタンの下に開く・項目は y≈40〜140・`z-index: 1300`）の項目より手前に来て、「ログアウト」の左側を覆う。押すと通知に当たる。E2E は Playwright が覆いの消えるまで待って押すので通っていた
- F6
  - 再現手順: アクセシビリティ設定のパネルを開いたまま、ユーザーメニューやダイアログを開く
  - 期待値: メニュー・ダイアログが手前に出て操作できる
  - 実際値: パネル（`zIndex: 10000`）が MUI の `Menu`・`Dialog`（1300）・`Tooltip`（1500）より手前になり、「設定」「ログアウト」を覆う
- ログ: コードレビューの台帳 F5・F6（再現あり・Medium）

## 根本原因
- 「通知が操作を塞ぐ」問題を、置き場所（右上 → 上の中央 → 上のバーの下）と重なり順（パネルを手前に）で避けようとした。画面には、上のバーのボタン・そこから開くメニュー・パネル・ダイアログ・右下の［＋］など、通知と同じ場所に出うる操作が多く、置き場所と重なり順の組み合わせで全部を避けることはできない（1 つを避けると別のものに重なる）
- 塞ぐ仕組みそのものは、通知が押せる要素（クリックを受け取る）で、マウスを乗せると消えなくなる（react-hot-toast の一時停止）こと。通知には押す操作が無い（閉じるボタン・リンクを持たない）ので、クリックを受け取る必要が無い
- セキュリティの観点: 該当なし（表示の重なり）

## 対応方針（全案＋推奨）
### 案 A（推奨・ユーザーが選んだ）: 通知をクリックを受け取らない表示にする
- `Toaster` の `toastOptions` の `success`・`error`・`loading` の種類の `style` に `pointerEvents: 'none'`。通知の上を押すと、下にあるボタン・メニュー・パネルに届く。マウスを乗せても一時停止しない（4 秒で消える）
- 種類を絞る理由: 押す操作を持つ通知が 2 つある（`frontend/src/contexts/AuthContext.tsx:116` のセッションの期限の警告〔`toast((t) => …)`・［セッション延長］のボタン〕と、`frontend/src/hooks/useAutoLogout.tsx:43` の同じ警告〔`toast.custom`〕）。どちらも `success`・`error`・`loading` の種類でないので、ボタンは今までどおり押せる（`toast.custom` は `toastOptions.style` を使わず、react-hot-toast がその子に `pointer-events: auto` を付ける）。押す操作を持たない普通の通知はすべて `toast.success`・`toast.error`（と `showSuccessToast` などの包み）で出している
- 置き場所は上のバーのすぐ下（`BELOW_APP_BAR_TOP`）のまま（上のバーのボタンの見た目を隠さないため）
- パネルを通知より手前にした変更（`ABOVE_TOASTS_Z_INDEX`）は戻す（`zIndex: 1001`。メニュー・ダイアログより後ろに戻り F6 が消える。通知はクリックを受け取らないので、パネルを手前にする理由が無くなる）
- セキュリティ影響: なし
- BP 適合: 操作を持たない一時的な表示が、ほかの操作を塞がない（WCAG 2.2 の 2.4.11 フォーカスが隠れないの考え方）。通知の読み上げは `role="status"`・`aria-live="polite"` のまま変わらない
- 保守性: 画面にどんな操作が増えても、通知が塞ぐことはない（置き場所・重なり順の組み合わせに頼らない）
- リスク・副作用: マウスを乗せて通知を止めて読むことはできなくなる（ユーザーが選択の時点で受け入れた）。通知は見た目の上では、出ている 4 秒の間、下のメニュー・パネルの一部に重なる（押すのは下のもの）
- 確かめ方: E2E（TC-30）で、通知が出ている間にユーザーメニューを開き、通知と「ログアウト」の項目が重なる（幅 360px）ことを確かめてから、その重なりの中の点の一番手前の押せる要素（`elementFromPoint`。クリックを受け取らない要素は返さない）が「ログアウト」の項目の中にあることを確かめる。直す前（`pointer-events` の指定なし）で落ちることを確かめる。パネルの確かめ（パネルの上端の点がパネルの中）は残す（パネルを通知より手前にしなくても、通知がクリックを受け取らないので通る）。上のバーとの重なりの確かめも残す

### 案 B: 通知を画面の下の中央に出す
- 幅 360px でクイズ管理の右下の［＋］に重なる。ユーザーが選ばなかった

### 案 C: 通知の重なり順をメニュー・パネルより後ろにする
- ダイアログの中で出す通知（「リンクをコピーしました」など）がダイアログの後ろに隠れる。ユーザーが選ばなかった

## 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
1. 同型: 通知（react-hot-toast）は `App.tsx` の `Toaster` 1 か所で、すべての画面の通知に効く。押す操作を持つ通知は `AuthContext.tsx:116`（`toast((t) => …)`）と `useAutoLogout.tsx:43`（`toast.custom`）のセッションの期限の警告だけ（`grep` で確かめた）。どちらも種類が `success`・`error`・`loading` でないので、今回の指定の外で、ボタンは押せるまま。`ErrorToast.tsx:63` の `showWarningToast`（`toast((t) => …)`・押す操作なし）も種類の外なので、クリックを受け取るまま（警告は今の呼び出しが少なく、押す操作の有無で種類を分けるほうが単純なので、ここは変えない）。MUI の `Snackbar`（`UserCreate.tsx`・`UserEdit.tsx`・`UserManagement.tsx`・下の左）は別の仕組みで変えない
2. 関連機能: パネルの重なり順を 1001 に戻すので、I636 の前と同じ（メニュー・ダイアログより後ろ）。`ABOVE_TOASTS_Z_INDEX` の定数は使わなくなるので消す。`BELOW_APP_BAR_TOP` はパネルと通知の 2 か所で使い続ける
3. 計画との関係: `frontend/src/App.tsx`・`frontend/src/components/AccessibilityProvider.tsx`・`frontend/src/constants/layout.ts`・`e2e/tests/registration-link.spec.ts` は、前の計画変更で実装対象に入っている。受け入れ条件 AC12 は「上のバーのどのボタンも、上のバーから開くメニュー・パネルの操作も塞がない」に言い直す（計画変更記録）
4. 敵対的レビュー: 通算 2 周を使い切っている。ユーザーの判断（「マージの前にこの PR で直す」・1 周の延長を含む）で、直した後に `--round-limit 3` で 1 周だけ流す
