## 2. 根本原因

**bash がどの場所で git を実行するか、どのファイルを渡すかを、見張りが推測で決めている。推測が外れたときに、通す側にも止める側にも倒れる。**

- 実行場所は `cd` の順序だけでなく、`( … )`・パイプ・`&`（サブシェル）、`cd -`・`$OLDPWD`・`~-`（元へ戻る）、失敗する cd（留まる）、読めない cd の先（変数・`$(…)`）で変わる。静的にすべてを正しく再現することはできない。
- 第 1 周は「分からないときは通った場所すべてで調べて止める」（止めすぎ＝第 2 周の Medium 2 件）、第 2 周は「`( … )`・popd が無ければ cd の先だけ」（緩めすぎ＝第 3 周 H1・H3）と、推測の方向を変えるたびに逆側の穴が出た。
- 対象のファイル（`$(…)`・xargs・find・中かっこ）も同じ。第 1 周は「変更があれば止める」（`git checkout "$BR"` まで止める）、第 2 周は「一覧のコマンド以外は切り替えとして通す」（第 3 周 H2）と往復した。
- H4・L8 はテストの不足（判定 1 つにつき、外したら落ちるケースが無い）。L6・L7 は新しく足した判定の止めすぎ。

### セキュリティ観点
- 影響は開発者のローカル環境での事故（未コミット変更の消失・保護ブランチへの push）。認証・認可・インジェクション・XSS・機密データ露出には該当しない。
- 見張りの git 呼び出しは引数の配列（`shell=False`）で、判定対象の文字列をシェルとして実行しない（変更なし）。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨・ユーザーが選択した方針）: 場所・対象が 1 つに決まらない git の書き換えは「確認」にする
- **場所の判定を 2 つに分ける**:
  - 一意に決まる: コマンドに cd / pushd / popd が無い、または cd がすべて文字どおりの既存のディレクトリで、`( … )`・パイプ・`&` の中に無く、`cd -`・`~-`・`$OLDPWD` を使わない → 最後の cd の先（と `-C` 等）で精密に判定する（今と同じ。停止は停止）。
  - 一意に決まらない（上のどれかに当たる）→ 場所を推測せず、**場所に依存する判定（未コミット変更の取り消し・宛先を書かない／HEAD 宛ての push）は確認（ASK）**。場所に依存しない判定（`git push origin main`・`--force`・`reset --hard` など）は今までどおり停止。
- **対象の判定**: 戻す対象が読めない（`$(…)`・変数・xargs・find・中かっこ・`--` の無い checkout の読めない引数）ときは、その場所に変更が 1 つでもあれば**確認**、変更が無ければ通す（消えるものが無い）。`--pathspec-from-file` も同じ扱いにそろえる（今は停止）。
- 実装: `_analyze` が単純コマンドを順に見ながら「場所が一意か」を持つ（`c["loc_ambiguous"]`）。`_cmd_danger` は場所に依存する判定を、一意なら精密判定、一意でなければ `_analyze` の新しい結果 `"git_unsure"` に入れて main が確認にする。最上位の文字列経路（`_danger_reasons` の `_git_revert_target_on_dirty(cmd)`・`_push_protected_target(cmd)`）も同じ関数で「一意でなければ場所に依存する判定をしない」。安全網（`_sn_judge` の cd 引き継ぎ）も同じ判定を通る。`_CD_HERE_RE` と「通った場所すべてを候補にする」処理（cds）は廃止。
- その他: checkout-index の `-a` のテスト（H4）、read-tree は `--reset` だけを対象（L7）、`git mv -f` の移動先がディレクトリならその中の同名ファイル（L6）、danger-ops.md の更新（L9）。
- **セキュリティ影響**: 推測で通す経路が無くなる（一意でなければ必ず人の確認）。止めるべきもの（場所に依存しない危険操作）は停止のまま。
- **ベストプラクティス適合**: 読み切れないものは人に判断を委ねる（fail-safe）。0-13 の「読みきれない形は確認」と同じ考え方で、方針が 1 つにそろう。
- **保守性・拡張性**: 推測の分岐（`_CD_HERE_RE`・cds・`_scoped` の細かい条件）が減る。新しい書き方は「一意か・一意でないか」のどちらかに入るだけで、往復が起きにくい。
- **リスク・副作用**: cd を含む git の書き換えの一部が確認になる。作業記録（3,701 件）の checkout / restore は 26 件で、cd・変数・xargs と組み合わせた実作業は見つかっていない（第 2 周 ロジック観点の調査）。作業記録の再判定（TC-15・新しく確認・停止 1% 以内）で確かめる。

### 案 B: 指摘ごとの修正を続ける（`cd -` を元の場所として扱う・失敗する cd を検出する 等）
- セキュリティ影響: 指摘された形は塞がるが、推測の分岐が増え、次の周で逆側の穴が出る見込みが高い（この /code-review の 3 周で実証済み）。
- 保守性: 低い。リスク: レビューの周回が終わらない。

### 案 C: 残りを別イシューにして /test へ進む
- セキュリティ影響: `cd -` 等で変更が消える・develop に push できる穴が残ったままマージされる。
- 保守性: 変化なし。リスク: 事故が実際に起こりうる形（`cd -` は普段書く形）を残す。

### Claude 推奨: 案 A
推測をやめることで往復の原因そのものを取り除く。ユーザーもエスカレーション時にこの方針を選択済み。
