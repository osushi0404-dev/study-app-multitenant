前回診断（20260706_0114）は VERDICT: HIGH で差し戻し。指摘①前回NG解消の機構未設計 ②TC-21 競合未確認 ③分類の主体未明記 を本 v2 で解消する。

## 失敗分解

- 期待値: 実装/テストゲートが REMAND を返したとき、その修正の「原因調査結果・修正方針・修正内容・テスト結果（既存 OK 箇所への無影響=回帰を含む）」が既存ゲートと同レベル以上でレビューされる。
- 実際値: REMAND は「自動で手順5（テストは手順5/6）へ戻り再修正＋NG報告」のみ。NGの原因調査/方針が未ゲート、再レビューが「前回NG解消」「回帰」を明示要求しない。
- 該当箇所: SKILL.md 共通ルール／手順5.5・6.5 REMAND 分岐。

## 根本原因
REMAND を「新たな失敗として扱い、深さに応じてゲートを再通過させる」構造がない。具体的欠落は 3 点: (1) NG修正の原因調査/方針を審査する経路が無い、(2) 再レビューが「前回NG指摘の解消」を検証する機構（前回NG内容の伝達）を持たない、(3)「実行の不備」と「方針の誤り」を分類せず一律手順5へ直行するため方針ミスを空転させる。

## 対応方針（全案＋Claude 推奨）

### 案1（Claude 推奨・採用）: 分類駆動ルーティング ＋ 前回NGの明示 fail-closed 検証
REMAND を受けたら Claude が NG を分解し **「実行の不備」/「方針の誤り」を分類**（手順2 相当）。深さを分ける:
- **実行の不備**（承認済み方針は正・実装/テスト実行のみ誤り）: 手順5 で再修正 → 手順6（**全スイート再走＝回帰**）→ **手順5.5/6.5 で再レビュー**。原因/方針は自明のため手順3.5 は省略（outcome を 5.5/6.5 が審査）。ユーザー承認(手順4)不要＝自動（headless 維持）。
- **方針の誤り**（診断・アプローチ自体が不適）: **手順2→3→3.5（診断レビュー）→4（ユーザー承認・新案のため）→ 手順5…**。新方針の原因調査/方針を手順3.5 が審査。
- **前回NGの明示検証（fail-closed）**: 実装/テスト再レビューには**前回NGレビュー記録を context に渡し**、reviewer が各前回指摘の diff 上の解消を検証。確認できなければ未解消として REMAND。
- **誤分類対策**: 実装/テスト reviewer に「実行の不備か方針の誤りか」を出力させ、方針の誤りと判明したら 2 回上限を待たず即エスカレーション（手順2 へ）。
- **回帰（無影響）**: 手順6 の全スイート再走（決定論）＋既存 reviewer の回帰観点で担保（新機構不要・SKILL に明示）。
- 連続NG上限(2) はバックストップとして維持。

### 案2（不採用）: 全 REMAND を一律手順1へ環流し常に全ゲート再通過
些細な実行不備にも毎回フル診断レビュー(claude -p)が走り過剰・高コスト。分類しないため深さが過剰。

### 案3（不採用）: NG専用レビューを別途新設
ゲート二重化・保守負荷増・既存と粒度乖離。

セキュリティ: レビュー機構の指示ファイル/スクリプト変更のみ。認証・認可・インジェクション・機密露出の新規リスクなし。前回NG context は自リポジトリの diff/レビュー記録で外部送信なし。

### ① 前回NG解消の伝達経路（前回 HIGH 指摘の解消）
reviewer はステートレスで context = diff＋結果のみ、という指摘は妥当。機構を確定した: **entrypoint が前回NGレビュー記録パス（オプション引数）を受け取り context に節として付加**、reviewer は fail-closed で解消を検証。`run_fix_review` は context を受け取るだけなので signature 不変・lib 非改修。診断ルート（方針の誤り）は Claude が再診断メモに前回NG理由を記述するため diagnosis entrypoint の引数追加は不要。→ 伝達経路を確定し空振り(false-green)を排除。
