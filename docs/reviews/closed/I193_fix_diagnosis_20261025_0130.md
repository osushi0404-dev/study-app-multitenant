## 根本原因
- H1: 「段階が進んだか」を、記録の中で他の節の書き込みでも変わる値（行番号）で見分けた
- H2: 「レビューの後の変更」を 2 点間の差（REVIEWED_COMMIT と HEAD）で取り、ブランチ自身の変更と、取り込んだ相手側の変更を分けていない
- M1: 上限を使い切った後の戻り方を、手順の分岐に書いていない
- M2: 記録の場所を「フォルダ」で決め、その中にあるコマンドの正（決定論ゲートの節）とテンプレートを区別していない
- M3: 機械が読む出力を、引用の規則がある形式（porcelain の行）で読んだ
- M5・L1・L2: 実装の細部の見落とし（失敗の握りつぶし・パイプの終わり方・上限）
- M4: 指摘の前提を確かめる。1 回目の review-gate で code-review.sh を背景で実行したとき、CI 待ちが 330 秒あり、組み込みとレビュー役を含めて 10 分を超えたが、完了の通知で正常に結果を受け取れた（背景の実行は 10 分で止まらない）。前提が成り立たないので、指摘は採らない

## 対応方針（全案＋推奨）
- H1: 案 A（推奨）`flow-stage.sh` が `STAGE_COUNT:`（STAGE_DONE 行の数）を出し、proceed はその増減で見分ける。案 B 最後の STAGE_DONE 行の中身を比べる（同じ段階を 2 回続けて書く正常な場合と区別しにくい）
- H2: 案 A（推奨）レビューした時点と今で「ブランチ自身の変更」（比べる相手との merge-base からの差・記録の場所を除く）をファイルごとに比べる。行番号と index 行は除く。取り込みのときに食い違いを直した場合は、ブランチ自身の変更が変わるので数える。案 B `--first-parent --no-merges` のコミットだけを見る（取り込みのコミットでの直しを見落とす）
- M1: 案 A（推奨）上限を使い切った後のコードの変更は「上限到達」と同じに止める（止める条件 3・ユーザーの承認で 1 周延長）と review-gate に書く
- M2: 案 A（推奨）記録の場所を `docs/(tests|plans)/(open|closed)/`・`docs/reviews/`・`docs/issues/` に絞る（テンプレートを外す）。auto_test.md の決定論ゲートの節は、レビューした時点と今で抜き出したコマンドを比べ、違えば数える
- M3: `git status --porcelain=v1 -z` で読む
- M4: 採らない（上の根本原因に実測を書いた）
- M5: ジョブ名を読めないときは `CI_WAIT: NO_JOBS` で exit 1。review-gate は原因を直して 1 回やり直し、直せなければ止める
- L1: here-string で渡す
- L2: 60,000 文字を超えるときは、組み込みの出力の前までと記録への参照だけを投稿する

## 影響調査
- `LAST_LINE` を見分けに使う箇所: proceed だけ（flow-stage.sh は出力を残す）
- `diff_outside_records` を使う箇所: gate-check の check_record（コードレビュー・敵対的レビューの両方）
- `RECORD_RE` を使う箇所: gate-check の作業ツリーの確認と差分の確認
- テスト: TC-01 の G 系は、一時リポジトリを main から切った feature ブランチにした（実際の使い方と同じ。main の上で直接コミットすると「ブランチ自身の変更」が常に空になるため）。G14（取り込み）・G15（決定論ゲートの節）・G16（テンプレート）・G17（空白を含む名前）・F11（STAGE_COUNT）・S13・C10b を足した。修正前の版でこれらが不合格になることは、テストレビューの前に確かめる
