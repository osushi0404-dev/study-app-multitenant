## 失敗分解
- F1（High）: `bash scripts/claude/a.sh>/dev/null`（`a.sh` は新規）。期待: 中で動く。実際: 区切りの記号に `<>` が無く、語が `scripts/claude/a.sh>/dev/null` になり一覧に当たらず書き換えない
- F2（High）: `scripts/claude/evil.tmp`（`.gitignore` が無視する名前）を書き `bash scripts/claude/evil.tmp`。期待: 中で動く。実際: 無視されるファイルは `ls-files --exclude-standard` にも `diff` にも出ない。変更が他に無ければ `_check` は `if not changed: return res` で `_reach` を呼ばずに終わり、変更があっても `_reach` は「一覧に無い」として読み飛ばす
- F4（Medium）: `bash scripts/claude/test-session.sh 'x' --permission-mode bypassPermissions`。期待: 承認。実際: `--permission-mode`・`--setting-sources` の値を見ない

## 根本原因
- F1・F2: 「実在するのに git の一覧（追跡＋追跡していない新規）に無いファイル」を、レビュー済みと同じ扱いにしていた。その状態に入る道は 3 つある: ① 出発点（`bash` の直後のスクリプト・引数のファイル）が一覧に無い（F2 の典型・F1 の語の取り違え）② 変更が無いと早期の return で出発点を調べずに終わる ③ 追跡済みのスクリプトが、無視されるファイルを名前で呼ぶ（`by_name` は一覧からしか作らないので辺にならない）
- F4: 許可の表を引数の名前だけで作り、値が子のセッションの守り（許可のモード・プロジェクトの設定を読むか）を外せることを見ていなかった
- セキュリティ: 3 つとも、レビュー前の中身・守りの無い子をサンドボックスの外で動かせる穴（C8）

## 対応方針（全案＋推奨）
- F1・F2:
  - 案 A（推奨）: 規則「実在するのに一覧に無いファイルに届いたら、レビュー前（当たり）」を 3 つの道すべてに当てる
    1. `_segments` の区切りに `<>` を足す（`set(t) <= set(";&|()<>")` も合わせる）。`2>/dev/null`・`2>&1`・`< in` の形を回帰の TC にする
    2. `_check` は、`_files()` の後・`if not changed` の前に、出発点のうち「実在し、一覧に無い」ものがあれば当たりにして返す（早期の return より先に調べる）
    3. `_reach` で読んだファイルの語は、一覧の名前で引くのに加えて、そのファイルと同じフォルダの `<語のファイル名>` と、語が `scripts/claude/` で始まるならそのパスを見て、実在し一覧に無ければ当たりにする（同じフォルダ・リポジトリからの相対パスで呼ぶ形を拾う。別のフォルダのファイル名だけで呼ぶ形は残る＝わざと避ける形として受け入れ R3 に足す）
  - 案 B: `git ls-files --ignored --others` も読む。`scripts/claude/tests/.venv` の数千のファイルで上限に当たり、毎回中で動く
  - 案 C: 無視されるファイルを止める（block）。中で動かせば足り、止めると正当な作業も止まる
- F4:
  - 案 A（推奨）: `--permission-mode` の値は `default`・`manual`・`plan`・`acceptEdits`・`auto` だけ。`--setting-sources` はカンマ区切りの値に `project` を含むとき、または中身がレビュー済みの `--settings` を一緒に渡すときだけ通す。空の値・表に無い値は承認。`=` の形も同じに扱う
  - 案 B: 2 つを表から外し常に承認。敵対的レビューの実験の起こし方（`.claude/agents/adversarial-reviewer.md:69` の `--permission-mode <manual|auto> --setting-sources user --settings .claude/settings.json`）が毎回止まる
- 新しい安全装置の対象: 手元の秘密（`.env`・鍵の控え）とサンドボックスの外の書き込み（GitHub からは戻せない）。最後の守りは許可の設定と auto モードの判定役。判定はパス・値の照合だけで、シェルの動きを読む精密な判定は足さない
