# I609 修正の診断メモ（手動テスト No.7 の NG）

## 失敗分解
- 再現手順: 開発の環境で、管理者 `e2e_user_a` が `/quiz-management` を一度開く（一覧の応答がキャッシュされる）→ `docker compose exec backend python manage.py import_problems --file /tmp/i609_import.md --subject-id 20 --created-by e2e_user_a@example.com`（3 問）→ `/quiz-management` を開き直す
- 期待値: 問題管理の一覧に取り込んだ 3 問が出る（手動テスト No.7）
- 実際値: 一覧に出ない。DB には 3 問がある（解説・出典・組織は期待どおり。`Problem` の id 111〜113）
- ログ: `import_problems` の出力は「✅ 成功: 3問」。エラーなし

## 根本原因
- 問題管理の一覧（`ProblemViewSet.list`・`backend/problems/views.py:183-230`）は、応答を利用者ごとに `cache_service.set_problems_cache` で 1 時間（`CACHE_TIMEOUTS['problem_list'] = 3600`）キャッシュする
- 画面・API からの作成・更新・削除・画像の変更は、どれも `cache_service.invalidate_problems_cache` を呼んでキャッシュを消す（`views.py:283,352,361,415,439,527,623,640`）
- `import_problems`（`backend/problems/management/commands/import_problems.py`）は `Problem.objects.create` で直接作り、キャッシュを消さない。I609 より前は `points=10` で 1 問も登録できなかったため、この抜けが表に出なかった
- セキュリティ: 認証・認可・テナントの境界には関係しない（キャッシュは利用者ごとのキーで、古い一覧が出るだけ。他組織のデータは混ざらない）

## 対応方針（全案＋推奨）
### 案 A（推奨）: 取り込みの最後に、1 問でも登録したら `cache_service.invalidate_problems_cache(subject.id)` を呼ぶ
- セキュリティ: 影響なし（消すだけ）
- BP: API の作成の経路（`views.py:283`）と同じ消し方にそろえる。消すのはループの後の 1 回だけ（`delete_pattern` を問題ごとに呼ばない）
- 保守性: 1 行。試し実行・0 問のときは呼ばない
- リスク: 取り込みが途中の問題で失敗しても、登録できた分があれば消す（正しい）。キャッシュの消去が失敗しても `_delete_by_pattern` が例外を握って続ける（今の API と同じ）

### 案 B: `Problem` の `post_save`・`post_delete` のシグナルでキャッシュを消す
- 利点: どの経路で作っても消える（根本の深さ）
- 欠点: 取り込みで問題ごとに `delete_pattern`（Redis の走査）が走る。今の API の経路の明示の消去と二重になる。シグナルは処理の流れが見えにくく、規約の「業務の処理はサービスに書く」から外れる。計画の範囲を大きく超える

### 案 C: 取り込みの後にキャッシュの消し方を手順に書く（コードは変えない）
- 欠点: 毎回の手作業で忘れる。I586 の利用者が取り込みの後に一覧で確かめられない

推奨: 案 A。作成の経路を `ProblemService` にまとめる直し（案 B より正しい根本）は計画の範囲を超えるので、retro の候補（/simplify の指摘と同じ）

## 影響調査
- 同型の抜け: 問題を作る経路は、API（`perform_create`・消している）・AI 生成（`views.py:415,439,527`・消している）・`import_problems`（消していない・今回直す）・`generate_ai_problems` コマンド（`backend/problems/management/commands/generate_ai_problems.py`・消していない。I609 の範囲外で、今は動いていない経路〔`_save_ai_problem_to_db` と同じく古い項目を使う〕。retro で扱う）
- 科目の問題の数（`problem_count`）はキャッシュせず毎回数える（`backend/core/subject_service.py:78,86`）ので、取り込みの後もクイズの開始・学ぶ科目の画面は正しい
- クイズの出題は DB を直接読むので、取り込んだ問題はすぐ出題される
- テスト: TC-15 を足す（管理者が一覧を開いてキャッシュを作る → 取り込み → 一覧を開き直すと 3 問が入っている）。直す前に落ちることを確かめる
