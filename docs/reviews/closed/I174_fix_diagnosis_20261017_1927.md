# I174 fix-loop 診断メモ（敵対的レビューやり直し第 3 周・上限到達への対応）

- 対象: ブランチ `feature/I174-guard-based-permission-review`（head fe64a73。第 3 周の指摘はすべて修正済み・テスト合格）
- 入力: `docs/reviews/I174_adversarial_review_20261017_1443.md`（やり直し第 1 周）・`_20261017_1911.md`（第 2 周・Critical 1・High 9）・`_20261017_1926.md`（第 3 周・Critical 1・High 4・上限到達）
- 計画書: `docs/plans/open/plan_I174.md`（0-10・0-11）

## 1. 失敗分解（再現手順 / 期待値 / 実際値 / ログ）

個々の指摘はすべて修正済み（fe64a73 の guard で期待値どおり）。fix-loop の対象は「周を回すたびに新しい Critical/High が出て収束しない」こと。各周の Critical/High を、出どころで分けた（ログ＝各周の記録の findings 表）。

| 周 | Critical/High | うち、直前の周の修正が生んだ後退 | うち、シェルの文法の読み落とし | うち、名前・書き方の列挙の漏れ | うち、テストの覆い隠し・余計な確認 |
|---|---|---|---|---|---|
| やり直し 第 1 周 | 不明（原文消失。復元 9 件） | — | 1（語にくっついた `;`） | 7（別名・キーワード・秘密の設定の形） | 1 |
| 第 2 周 | 10 | 3（`python - 引数`・`.env` の文字列・構文木化でのタスク名） | 1（書き換え直後の実行＝コマンド内の順序） | 3（`git clean -f`・`.env*`・`.apply()`） | 3（`dd` の語・許可リストが狭い・S61） |
| 第 3 周 | 5 | 3（`dd` の名前判定 → `if` の中・`.env` glob が広すぎ／狭すぎ） | 1（`if/then`・`for/do` の本体） | 1（`python - < f`） | 0 |

代表的な再現（第 3 周・fe64a73 の前の guard）:
- `if [ -d backend/media ]; then rm -rf backend/media; fi` → 期待 2 ／ 実際 0
- `for f in backend/*.sqlite3; do shred -u $f; done` → 期待 2 ／ 実際 0（第 2 周の前は 2＝後退）
- `cat e2e/.env.e2*` → 期待 ASK ／ 実際 0（第 2 周の前は ASK＝後退）
- `grep -n I174 docs/reviews/*` → 期待 0 ／ 実際 ASK（第 2 周の修正が生んだ誤判定・作業記録で +23 件）
- `python3 - < f.py`（f.py は flush）→ 期待 2 ／ 実際 0

## 2. 根本原因

### 2-1. シェルの文法を部分的にしか読まず、読めない形を「安全」と扱っている（fail-open）
- `_raw_commands` / `_parse` は shlex でトークンに分け、区切り記号で単純コマンドに分ける自前の読み取り（Python のコードだけは 0-10 で構文木 `ast` にしたが、シェルの部分は shlex のまま）。bash の文法を網羅していない。読み落とした形は、先頭が知らない語のコマンドになり、どの判定にも当たらず**素通し**になる。
- 第 3 周の Critical（`if…then rm -rf`）は I174 の前からある穴で、3 周＋やり直し 2 周のあいだ見つからなかった。fe64a73 で `if/then/elif/else/while/until/do` は個別に足したが、**同じ種類の穴が fe64a73 でも残っている**（2026-10-17 実測。コマンドは実行していない）:

  | コマンド | 期待 | fe64a73 |
  |---|---|---|
  | `function f { git reset --hard origin/develop; }; f` | 2 | 0 |
  | `diff <(rm -rf backend/media) x`（プロセス置換） | 2 | 0 |
  | `coproc rm -rf backend/media` | 2 | 0 |
  | 参考: `case x in x) rm -rf …;; esac`・`f() { rm -rf …; }`・`[[ ]] &&`・`until/do`・`select/do`・`time { }` | 2 | 2（たまたま当たる） |

- 「読めない形は確認に回す」という fail-safe が、コンテナの中（compose の許可リスト）にはあるが、**ホストのコマンドにはない**。予約語を 1 つずつ足す直し方では、次の未対応の語（`function`・`coproc`・`<( )`）でまた素通しになる。

### 2-2. 修正が局所的で、変更の影響を網羅的に測る仕組みがない（後退が毎周出る）
- 各周の修正は、指摘の再現コマンドだけをテストに足している。同じ判定が他の書き方（包むコマンド・制御構文・パイプ・`$( )`・ヒアドキュメント）の中でどう振る舞うかは確かめていない。そのため `dd` をコマンド名の判定に変えたら `if` の中で外れる、という後退が起きた。
- 誤判定（余計な確認）も、作業記録 3,373 件の再判定を、毎周サブエージェントがその場で手作りして測っている。決定論のゲートになっていないので、修正した本人がコミットの前に気づけない。

### 2-3. 判定の対象を「名前の固定リスト」で持っている
- `.env` の候補（`.env`・`.env.local`・`.env.prod`）、秘密を読むコマンド、外部送信のルート名・タスク名などを固定のリストで持つため、リストの外の書き方は漏れる（`.env.e2e`・`python - < f`）。漏れの多くは、計画 0-10 の脅威モデル（事故）の範囲で「普段書く形」として指摘されている。

### 2-4. セキュリティ観点
- 本イシューは開発ハーネスの見張り（データ消失・外部送信・秘密情報の表示を人の承認なしに起こさない）で、アプリの認証・認可・入力処理は変えない。2-1 の穴は「人の承認なしに取り消せない削除が起きる」（CLAUDE.md 絶対ルール 4）、2-3 の穴は秘密情報の露出（OWASP A02 相当）、承認の迂回は A01 相当。

## 3. 対応方針（全案＋推奨）

### 案 A: これまでどおり、指摘ごとに直して敵対的レビューを回し続ける
- セキュリティ: 指摘された穴は塞がるが、2-1・2-2 が残るので同じ種類の穴と後退が毎周出る（実績: 6 周連続で Critical/High）。
- ベストプラクティス: 自前の文法の読み取りを場当たりで広げる形。
- 保守性: 判定が増えるほど後退の範囲が広がる。
- リスク・副作用: 時間がかかる（ユーザーから「レビューに時間がかかりすぎ」と指摘あり・2026-10-17）。収束の見込みがない。

### 案 B: 安全網（読めない形・危険語の取りこぼしは確認）＋組み合わせのテストの表＋作業記録の再判定を決定論のゲートにする（推奨）
**位置づけ: 0-10（Python のコードの構文木判定）と 0-11（各周の修正）は残したまま、その上に重ねる追加の変更**。精密判定（`_analyze`・`_CodeVisitor`・`_WRITTEN`・`_resolve_marks`・push/checkout の `_segments` の判定）は置き換えない。安全網は、精密判定が 0（素通し）を返すときだけ働く最後の層で、精密判定の 2 や ASK は変えない。
1. **ホストにも fail-safe の安全網を入れる**（I146 の「精密判定＋安全網 2 層」と同じ考え方）: 精密判定（今の `_analyze`）が何も見つけなかったコマンドでも、
   - 読み取りが対応していない文法（`function`・`coproc`・プロセス置換 `<( )` `>( )`・`case`・`f() { }` の関数定義・`[[ ]]`・算術 `(( ))` 等。対応している形の一覧を持ち、それ以外の予約語・記号が出たら対象）を含むとき、または
   - コマンド全体のトークンに危険なコマンド名（`rm` に `-r`+`-f`・`git reset --hard`・`git clean -f`・`dd`・`shred`・`mkfs`・`flush`・`DROP`/`TRUNCATE` 等）が「コマンドの位置になり得る場所」（区切り・予約語・包むコマンドの直後）に現れるときは、
   止めずに**確認（ask）**にする。引数の中の語（`grep "dd"`・`YYYY-MM-DD`）はコマンドの位置ではないので反応しない。精密判定で 2 になるものは今までどおり 2。
2. **組み合わせのテストの表を作る**: 危険な操作の代表（rm -rf・git reset --hard・git clean -f・dd・shred・flush・DROP・cat .env・printenv・send_mail）× 書き方（そのまま・`&&`・`;`・`|`・`( )`・`{ }`・`if/then`・`else`・`for/do`・`while/do`・`$( )`・`bash -c`・`sh -c`・`xargs`・`find -exec`・`sudo`・`timeout`・`nohup`・`docker compose exec`・`docker exec`）を総当たりで生成し、どれも 2 か ASK になる（素通しにならない）ことを確かめるテストを足す。新しい判定や書き方を足したら表が自動で広がる。
3. **作業記録の再判定を決定論のゲートにする**: 第 2・3 周で使った作業記録 3,373 件の再判定を、記録から抜き出したコマンドの一覧と前回の判定結果を保存したテストにし、「素通し→停止」の変化があれば不合格、「素通し→確認」の増加は件数を表示する。修正した本人がコミットの前に余計な確認・誤停止に気づける。
   - 秘密を含むコマンドの除外（リポジトリに入れるため）: (1) detect-secrets（pre-commit で使用中）で検出されたもの (2) 正規表現 `(KEY|SECRET|PASSWORD|TOKEN)\s*[=:]\s*\S{8,}`・`sk-[A-Za-z0-9]{20,}`・`SG\.[A-Za-z0-9_-]{20,}`・メールアドレス（example.com 以外）に当たるもの (3) `.env` の中身を表示した出力ではなくコマンド文字列だけを保存する。除外した件数は記録する。
   - 余計な確認の増加の目安: 作業記録の 1%（約 34 件）以内。根拠: I174 の前の確認＋停止は約 289 件（8.6%）で、目的（承認待ちを減らす）に対して今は 150〜190 件（4.4〜5.6%）。1% の増加は、ここまでの削減幅（約 3〜4 ポイント）の 4 分の 1 程度で、それを超えると削減の効果を目に見えて打ち消す。
- セキュリティ: 読めない形・取りこぼしが確認になるので、2-1 の fail-open がなくなる。止める（exit 2）範囲は精密判定のままなので、誤停止は増えない。
- ベストプラクティス: 見張り（ガード）の定石は「精密判定で分かるものは判定し、分からないものは安全側に倒す」（このリポジトリでも I146 で採用済み）。組み合わせのテストは、ケースの書き漏れを構造的に防ぐ。
- 保守性: 危険な操作や書き方を 1 か所に足せば、テストの表が広がる。作業記録のゲートで余計な確認の増加も見える。
- リスク・副作用: 安全網の確認が普段のコマンドで出すぎないか（作業記録のゲートで測り、増加が作業記録の 1% を超えるなら条件を絞る）。作業記録の一覧はリポジトリに入れるので、秘密（キー・パスワード・メールアドレス）を含むコマンドは除く。

### 案 C: bash の構文解析ライブラリ（bashlex 等）に置き換える
- セキュリティ: 文法の網羅性は上がる（予約語・リダイレクト・置換を構文木で扱える）。ただし bashlex もヒアドキュメントの一部や `[[ ]]`・算術式に未対応があり、読めない形の扱い（fail-safe）は結局必要。
- ベストプラクティス: 構文は構文解析器で扱うのが定石。
- 保守性: フックは素の python3 で動くので、ライブラリを同梱する必要がある（依存・ライセンス・更新の管理が増える。依存監査〔dependency-audit〕の対象外のコードが増える）。
- リスク・副作用: 読み取りの全面的な書き換えになり、これまでの 682 件の判定の後退を一度に招きやすい。時間がかかる。

### 推奨: 案 B
- 2-1 は安全網で fail-safe にし、2-2 は組み合わせの表と作業記録のゲートで後退と余計な確認をコミット前に見えるようにする。2-3（名前の固定リスト）は、安全網が確認に回すので「漏れても素通しにならない」形で吸収する。
- 案 C の網羅性の利点は大きいが、依存の追加と全面書き換えの後退リスクに見合わない。案 B の安全網が働いていれば、読み取りの網羅性の不足は「確認が出る」だけで済む。
- 手順 4 の承認の後、安全網の条件・組み合わせの表・作業記録のゲートを計画書 0-12 に記録してから実装する。

## 4. 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
- 同型バグ: 予約語の読み落としは `_raw_commands` を通るすべての判定（危険操作・外部送信・秘密情報・コンテナの許可リスト）に共通（上の 2-1 の表）。push・checkout の判定は `_segments` という別の読み取りで、fe64a73 で実測した（2026-10-17）: `if true; then git push -f origin main; fi`・`for b in main; do git push -f origin $b; done`・`while true; do git push -f origin main; break; done`・`for f in a; do git checkout -- <変更のあるファイル>; done`・`if true; then git checkout -- <変更のあるファイル>; fi` はすべて 2。`_segments` 側は予約語に依存しない判定（トークン列に `git push` / `git checkout --` があるか）なので同型の穴はなく、安全網は `_segments` に当てない（実装範囲は広がらない）。
- 0-10・0-11 の仕組みとの関係: `_WRITTEN`（同じコマンド内で書くファイル）・`_resolve_marks`（`$( )` の中身の復元）・`_CodeVisitor`（Python の構文木）は精密判定の一部としてそのまま使う。安全網は `_analyze` の結果が空のときに、同じトークン列（ヒアドキュメントの本文は除く）を見るだけなので、これらの仕組みの判定を変えない。
- 他の呼び出し箇所: guard は Bash の PreToolUse でだけ使われる（`.claude/settings.json` の hooks）。Edit/Write の判定と worktree の判定は変えない。
- 関連機能: I146（PR #261）の gh pr ガードの安全網（`_safety_text`）と考え方が同じなので、I146 のマージ後のステップ 6 の取り込みで、二重の安全網にならないよう整理する。
- 承認待ちへの影響: 安全網の確認が増える分は、作業記録のゲートで件数を測って計画書に記録する（I174 の目的は承認待ちを減らすことなので、増加は 1% 以内を目安にする）。
