# I160: code-review.sh の CI ゲートに相互依存イシューの通過経路を追加 — 合流 PR の全チェック SUCCESS と既知の失敗ステップ指定を根拠に通過させ記録へ注入する

## 関連資料
- GitHub Issue: #278
- 発見元: I159（#276・PR #277）の `/code-review`（2026-10-15）と `/retro I159` の予防処置 P1
- 相互依存の実例: I151（#267・PR #269）× I159（#276・PR #277）
- 実際の回避手順（今回の手作業）: PR を持たない一時ブランチ `review-tmp/I159` で code-review.sh を実行 → 記録コミットを `--ff-only` で本ブランチへ移送 → `gh pr review 277 --comment` を手動投稿（docs/reviews/open/I159_review.md「code-review 指摘への対応」に記録）
- 関連: I152（#268・依存監査の PR ゲート許可リスト化）
- 同梱: `/retro I183`（2026-10-24）の予防処置 P1 — CI 待機のタイムアウトを fail-closed にする（下記「同梱: CI 待機のタイムアウト」）

## 背景/目的

**背景**: I151（Django 更新）と I159（frontend の npm audit critical 解消）は CI 上で相互に待ち合っていた。I159 の PR #277 単体では develop に残る Django の CVE で Backend Lint & Security（pip-audit）が必ず落ち、I151 の PR #269 単体では frontend の critical で Frontend Lint & Security が落ちる。I159 を I151 ブランチへ取り込んだ合流状態（PR #269）では 6 チェックすべて SUCCESS で、I159 の受け入れ条件（AC-4）もこの合流状態を正と定義していた。にもかかわらず `/code-review I159` は code-review.sh の CI ゲートで停止し、ユーザーに進め方の確認が必要になった。ユーザーからは「別々のイシューがそろわないときれいにならない場合は、確認なしで進めてほしい」と指示があった。
**目的**: 相互依存イシューで、単体 PR の失敗が「相方イシューで解消する既知の失敗」に限られ、かつ合流 PR が全チェック SUCCESS の場合に、code-review.sh が手作業の回避なしに通過し、その根拠をレビュー記録に残す状態にする。

### 現状の問題（証拠・再現手順）
- `scripts/claude/code-review.sh:267-291` は現在のブランチの PR の `gh pr checks` に `fail` が 1 つでもあれば「⛔ CI が失敗しています」で `exit 1` する。既知・想定どおりの失敗かどうかを区別する手段がない。
- 再現: I159 ブランチ（PR #277）で `bash scripts/claude/code-review.sh I159` → Backend Lint & Security（失敗ステップ `pip-audit` のみ）で停止（2026-10-15）。
- 結果として「PR を持たない一時ブランチで実行し CI 確認自体を飛ばす」手作業が必要になった。この回避は CI 確認を丸ごと外すため、想定外の失敗も素通りする。

### 根本原因
- code-review.sh の CI ゲートが「PR 単体の全チェック合格」を唯一の通過条件にしており、相互依存イシュー（合流しないと CI が通らない組）を想定していない。
- 「どの失敗が既知か」「合流 PR はどれか」を宣言する場所がない。

### 解決方針
- 相互依存の宣言を 1 か所に置く（例: 計画書に `## 相互依存 CI` 節を設け、合流 PR 番号と既知の失敗〔ジョブ名／ステップ名〕を機械可読な行で書く）。宣言の置き場所と書式は grill-me で確定する。
- code-review.sh は CI に失敗があるとき、宣言がある場合に限り次の 3 点をすべて満たせば通過する。1 つでも満たさなければ従来どおり `exit 1`。
  1. 単体 PR の失敗ステップが、宣言した既知の失敗ステップに**完全に含まれる**（ステップ単位で照合し、想定外のステップの失敗は通さない）
  2. 合流 PR の全チェックが SUCCESS
  3. 合流 PR のヘッドに現在のブランチの HEAD が含まれる（取り込みが古いままの合流 PR を根拠にしない）
- 通過した場合は、根拠（合流 PR 番号・ヘッド SHA・単体の失敗ステップ一覧）をレビュー記録の決定論ゲート証跡へ注入する。
- 宣言がない場合の挙動は変えない（無回帰）。

### 同梱: CI 待機のタイムアウト（/retro I183 の予防処置 P1）
- **現状の問題**: `scripts/claude/code-review.sh:267-291` の CI 待機は 600 秒で打ち切り、`⚠️ CI タイムアウト` を出すだけで、`fail` の文字が無ければそのままレビューへ進む。pending が残った（結果が分からない）まま `FINAL_VERDICT: OK` を出せる fail-open。
- **証拠**: I183（PR #310・2026-10-23）で E2E Tests (Playwright) が 10m55s かかり、600 秒で時間切れ → CI 未完了のまま `FINAL_VERDICT: OK`。CI 全緑は事後に `gh pr checks 310` で手動確認した（`docs/reviews/open/I183_review.md`）。E2E は現在 10〜11 分かかるため、アプリ変更の PR ではほぼ毎回起きる。
- **根本原因**: 外部の非同期結果を待つゲートが、タイムアウト（結果不明）を「失敗なし」と同じに扱っている。所要時間が延びたときに待機上限を見直す仕組みも無い。
- **解決方針**: タイムアウト時に pending が残っていれば非ゼロ終了で停止し（「CI 未完了」と再実行の案内を出す）、レビューへ進まない（fail-closed）。待機上限は現行の最長ジョブ（E2E 約 11 分）を上回る値にし、定数として一か所で定義する。

## 受け入れ条件（Acceptance Criteria）
- [ ] 相互依存の宣言があり、単体 PR の失敗ステップが既知の失敗ステップに完全に含まれ、合流 PR が全チェック SUCCESS で、合流 PR のヘッドに現在の HEAD が含まれるとき、code-review.sh が CI ゲートを通過してレビューへ進む
- [ ] 上記のどれか 1 つでも満たさない場合（宣言外ステップの失敗・合流 PR に失敗がある・取り込みが古い）は従来どおり `exit 1` で停止する
- [ ] 宣言がない場合の挙動が従来と同一（無回帰）
- [ ] 通過時、レビュー記録の決定論ゲート証跡に合流 PR 番号・ヘッド SHA・単体の失敗ステップ一覧が記録される
- [ ] CI 待機が上限に達したとき pending のチェックが残っていれば、code-review.sh が非ゼロ終了で停止し、レビュー（`FINAL_VERDICT`）を出力しない
- [ ] CI 待機の上限が現行の最長ジョブ（E2E 約 11 分）を上回る値で、定数として一か所で定義されている
- [ ] 各経路を検証するテストが scripts/claude/tests/ にあり、失敗注入で不合格になることを確認済み

## 制約・引き継ぎ情報
- `gh pr checks` はジョブ単位、失敗ステップの特定は `gh run view <run> --json jobs`（`.jobs[].steps[] | select(.conclusion=="failure")`）で取得できる（I159 で実測）
- 一時ブランチ方式の手作業回避は CI 確認を丸ごと外すため、本イシュー完了後は使わない
- ユーザー方針（memory: 相互依存イシューは既知失敗で止まらず自律で進める）を仕組み側で実現するもの
