# I193 fix-loop 診断メモ 5（2026-10-25 03:45）

対象: 基本レビュー 5 回目 `I193_code_review_20261025_0326.md`（FINAL_VERDICT: HIGH）。review-gate の繰り返しの上限（4 回目以降）に従い、直すのは High 1 件と、それに直結する Medium 1 件だけ（自律判断の記録）。

## 失敗分解

### H1: close が gate-check の後に develop を取り込み、きれいに取り込めたときはレビューを通り直さない
- 再現手順: ブランチが変えたファイル（例 `scripts/a.sh`）を develop 側も変え、自動マージが通る状態で close 段階を実行する
- 期待値: 取り込んだ後の中身が「レビュー済みの HEAD」と食い違うなら、review-gate に戻す
- 実際値: close は ①`gate-check.sh`（取り込み前の HEAD を見て合格）→ ②`pr-base-sync.sh sync`（exit 0）→ 続行、の順。exit 0 のときは review-gate に戻す指示が無く、合成後の中身のまま push してマージを依頼する
- ログ: `.claude/skills/close/SKILL.md` 14〜39 行（事前チェックの gate-check が step 0 の前にある。step 0 の exit 0 は「続行」だけ）

### M1（H1 に直結）: 繰り返しの上限が、計画のやり直しより前の周まで数える
- 再現手順: review-gate ⇄ fix-loop が 4 回続いた後に、範囲を変えて plan-review → implement をやり直し、その後の最初の review-gate が HIGH になる
- 期待値: 実装をやり直した後は、新しい実装に対する 1 回目として数える
- 実際値: 「途中に `review-gate NEXT: test-gate` を挟まずに数える」だけなので、やり直し前の 4 回も数え、いきなり 5 回目（止める）になる。今回の延長（ユーザーの判断）は、この数え方のずれが原因の一つ
- ログ: `.claude/skills/review-gate/SKILL.md` 35 行・`docs/reviews/open/I193_review.md` の `STAGE_DONE:` 行

## 根本原因
- H1: 「レビュー済みの HEAD か」を確かめる場所（gate-check）が、HEAD を動かす操作（base 追従）より前にある。確かめた後に HEAD が変わるので、確かめた結果が意味を失う（I185 の種類 B「確かめた後の変更がレビューを通らない」と同じ形）。gate-check 自体には「develop が同じファイルを変えていた取り込みは止める」判定（G19）があるのに、順番のせいで使われていない
- M1: 数え始めの区切りに「実装のやり直し（`STAGE_DONE: implement`）」が入っていない
- セキュリティ観点: H1 はレビューを通っていない合成後のコードがマージ依頼に進む（レビューの迂回）。ただし最後の守りとして、GitHub のブランチ保護（CI 必須・Code Owners の承認）は残っている。M1 は止まりすぎる側（安全側）のずれで、セキュリティの穴ではない

## 対応方針

### H1
- 案 A（推奨）: close の順番を入れ替え、base 追従（step 0）を先に、gate-check を後にする。取り込みで HEAD が変わっても、gate-check がその HEAD を見る。develop だけの変更（別の PR でレビュー済み）は gate-check の「ブランチ自身の変更」の比べ方で数えないので通り、ブランチのファイルに develop が触れていれば G19 の判定で落ちて review-gate に戻る
  - セキュリティ: レビューの迂回を塞ぐ。新しい判定を足さず、今ある決定論の判定を正しい場所で使う
  - BP 適合: 「確かめるのは、変える操作の後」。ゲートを 1 か所にまとめる
  - 保守性: 手順の並べ替えだけ。スクリプトの変更なし
  - リスク: step 0 の exit 1（食い違いの解決）の後も gate-check を通るので、今の「記録の場所の外を直したら review-gate へ」の文は gate-check と重なる（害は無い。文は残す）
- 案 B: 順番はそのままにして、step 0 の後に「HEAD が変わったら gate-check をやり直す」を足す
  - 手順が 1 つ増え、「変わったか」の見分けを Claude が行う（忘れうる）。案 A のほうが単純で確実
- 案 C: pr-base-sync.sh の中で gate-check を呼ぶ
  - スクリプトの役割が混ざり、pr-base-sync.sh は古い流れのイシューでも使われる。範囲が広がる

### M1
- 案 A（推奨）: 数え方の区切りに「`STAGE_DONE: implement` の行」を足す（`review-gate NEXT: test-gate` か `implement` の行の後から数える）。手順書の文 1 か所
- 案 B: 区切りを `plan-review` の行にする — plan-review の後は必ず implement を通るので結果は同じだが、実装をやり直したことを直接表す implement のほうがわかりやすい

## 影響調査
- 同型のバグ: 「gate-check の後に HEAD を動かす」段階を探した。test-gate は gate-check の後に記録の場所（`docs/`・`.evidence/`）だけを書く（記録の場所は gate-check が数えない）ので同型ではない。close の step 5.5 の `pr-base-sync.sh final` は取り込まない（確かめるだけ）ので同型ではない。close の step 3 は記録の移動だけ
- 呼び出し箇所: close の手順の並べ替えは close/SKILL.md だけ。`docs/runbooks/workflow.md` のフローの 5（close: `gate-check.sh` → 記録を closed へ → … → base 追従）も同じ順番を書いているので合わせて直す
- 関連機能: gate-check の G19（develop も同じファイルを変えていた取り込みで止まる）は TC-01 で確かめ済み。新しいテストは、close の手順で base 追従が gate-check より前にあること（S22）と、上限の区切りの文（S19 に足す）
