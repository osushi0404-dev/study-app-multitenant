# I636 fix-loop 診断メモ（2026-11-27 14:00・再診断）

起点: close の後のユーザーの確認の依頼で見直して見つかった、手動テスト No.7 の NG。前の診断メモ（`docs/reviews/I636_fix_diagnosis_20261127_1340.md`）は診断レビューで差し戻された（`docs/reviews/I636_fix_diagnosis_review_20261127_0941.md`・HIGH 2 件: `Snackbar` の使用箇所の調べの誤り・アクセシビリティ設定のパネルとの重なりの見落とし）。この版で補う。

## 失敗分解
- 再現手順: 幅 360px でログインする（`e2e_user_a`）。ログイン直後の通知「ログインしました」が出ている間に、上のバーの右側のボタンを見る
- 期待値: 通知が上のバーのどのボタン（左のメニュー・アクセシビリティ設定・テーマの切り替え・ユーザーメニュー）も塞がない。アクセシビリティ設定のパネルを開いたときも、パネルの操作が塞がれない
- 実際値: 通知（x=96〜264・y=16〜61）が「アクセシビリティ設定」のボタン（x≈224〜248）に重なる。通知の上にマウスがあると通知は消えないので、そのボタンを 4 秒以上押せないことがある（I636 が直した「ユーザーメニューを押せない」と同じ種類の問題が、別のボタンで残っている）
- ログ: 画面確認の画像 `.evidence/I636/01_login_toast_360.png`・`02_members_360_region_focus.png`。E2E の TC-30 は、通知の枠とユーザーメニューのボタンの枠の重なりだけを確かめていた

## 根本原因
- 通知の置き場所（`frontend/src/App.tsx` の `Toaster`）を「上の中央・左右 64px を空ける」にしたとき、上のバーの右側のボタンを 1 つ（ユーザーメニュー）と数えた。実際は 3 つ（`frontend/src/components/Layout.tsx` の `Toolbar` の `AccessibilityToggleButton`・テーマの切り替え・ユーザーメニュー）あり、幅 360px では通知の幅の中に入る
- 通知は上のバー（`AppBar`・`position="fixed"`）と同じ高さに出るので、横の幅をどう抑えても、ボタンの数と幅の組み合わせしだいで重なる（作りとして壊れやすい）
- 確かめ（E2E の TC-30・手動テスト No.3）の相手がユーザーメニューのボタンだけで、上のバーの全体と、上のバーから開くパネルを見ていなかった
- セキュリティの観点: 該当なし（表示の重なり）

## 対応方針（全案＋推奨）
### 案 A（推奨）: 通知を上のバーのすぐ下に出し、アクセシビリティ設定のパネルを通知より手前に重ねる
- `Toaster` の `containerStyle={{ top: BELOW_APP_BAR_TOP }}`（72px。上のバーの高さ 56px〔幅 600px 未満〕・64px〔それ以上〕より下に 8px 以上の余白）。位置は上の中央のまま（ユーザーが選んだ「上の中央」を保つ）。最大幅の指定（`min(350px, calc(100vw - 128px))`）は外し、react-hot-toast の既定（350px）に戻す
- アクセシビリティ設定のパネル（`frontend/src/components/AccessibilityProvider.tsx` の `AccessibilityPanel`・上のバーから開いたときは `top: 72`・`right: 16`・幅 320・`zIndex: 1001`）は、同じ高さに出るので通知と重なる。react-hot-toast の通知の重なり順（`z-index: 9999`）はパネル（1001）より手前なので、通知がパネルの上端の操作を塞ぐ。パネルの `zIndex` を通知より手前（`ABOVE_TOASTS_Z_INDEX` = 10000）にし、両方が出たときはパネルが手前になる（通知は一部が隠れるが、操作は塞がれない）
- 72px は今、パネル（`top: 72`）と通知の 2 か所で使うので、`frontend/src/constants/layout.ts` に `BELOW_APP_BAR_TOP = 72`（根拠のコメントつき）と `ABOVE_TOASTS_Z_INDEX = 10000` を置き、両方から読む（直書きの数を合わせない・診断レビューの Info）
- 通知の重なり順は下げない: MUI の `Dialog`（`z-index: 1300`）より手前のままにしないと、ダイアログの中で出す通知（例: リンクのダイアログの「リンクをコピーしました」）がダイアログの後ろに隠れる
- セキュリティ影響: なし
- BP 適合: 固定の上のバーの操作と、そこから開くパネルの操作を、一時的な表示で塞がない（WCAG 2.2 の 2.4.11 フォーカスが隠れないの考え方にも沿う）
- 保守性: 上のバーにボタンが増えても重ならない（幅の計算に頼らない）。72px と重なり順の値は定数 1 か所
- リスク・副作用:
  - 通知が各画面の一番上の中身（見出しなど）に 4 秒ほど重なる。各画面の一番上の操作（例: メンバー管理の［メンバーを追加］は幅 360px で y≈146〜190）には届かない高さ（72〜117px 程度）
  - ログインの画面・登録用リンクの画面（上のバーが無い）でも、上から 72px に出る
  - パネルは開いている間、ダイアログ（1300）より手前になる（パネルを開いたままダイアログを開いた場合）。パネルは利用者が自分で開閉する補助の操作で、手前にあるほうが使いやすい
- 確かめ方:
  - E2E（TC-30）で、通知の枠の上端が上のバー（`getByRole('banner')`）の下端以上であることを確かめる（個々のボタンでなく上のバー全体）。直す前（今の位置）で落ちることを確かめる
  - E2E で、通知が出ている間に上のバーの「アクセシビリティ設定」を押してパネルを開き、パネルの上端の近く（パネルの中央の x・上端から 10px）の一番手前の要素がパネルの中にあることを確かめる（`elementFromPoint`）。直す前（パネルの `zIndex` 1001）で落ちることを確かめる
  - 手動テスト No.7 を 360px と 1280px で行う

### 案 B: 最大幅を右側の 3 つのボタンを避ける幅にする
- 幅 360px では通知の幅が 60px 程度になり読めない。ボタンが増えるたびに計算し直しになる。採らない

### 案 C: 通知を下の中央に出す
- クイズ管理の右下の［＋］（`QuizManagement.tsx` の `position: fixed; bottom: 16; right: 16`）と、上のバーの無い画面のアクセシビリティ設定の浮いたボタン（`bottom: 80; right: 16`）に、幅 360px で重なる。ユーザーが grill-me で「上の中央」を選んだ判断（右下は［＋］と重なるので選ばない）とも合わない。採らない

### 案 D: 通知を押せないようにする（`pointer-events: none`）
- 通知の上を押すと下のボタンに届くので塞がない。ただし、上のバーのボタンが見えないまま押せる（見た目と操作が食い違う）。マウスを乗せて止める（読むための一時停止）もできなくなる。採らない

### 推奨
案 A。上のバーと縦に分けるので、幅やボタンの数に左右されない。上のバーから開くパネルとの重なりは、パネルを手前にして操作を守る。「上の中央」というユーザーの決定も保つ。

## 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
1. 同型（画面の固定の要素と重なりうる一時的な表示・浮いた表示）:
   - react-hot-toast の `Toaster`（`App.tsx`）: 今回直す
   - MUI の `Snackbar`: `UserCreate.tsx:302`・`UserEdit.tsx:404`・`UserManagement.tsx:334` の 3 画面で使う（前の版で「使っていない」と書いたのは誤り）。どれも `anchorOrigin` を指定しないので既定の下の左に出る。上のバー・上のバーから開くパネル・通知（上）とは重ならない。3 画面のファイルは `toast.` を直接呼ばない（`grep` で 0 件）。ただし `UserEdit.tsx` の中の運営の欄（`StaffCredentialsCard` → `MemberCredentialActions`）は react-hot-toast で通知を出すので、この画面では両方が並ぶ。出す操作が違い（`Snackbar` は利用者の情報の保存、通知は登録用リンク・パスキーの操作）、出る場所（上と下の左）も違うので、重ならず、同じ操作で二重にも出ない。下の左は、上のバーの無い画面のアクセシビリティの浮いたボタン（右下）とも重ならない
   - アクセシビリティ設定のパネル（`AccessibilityProvider.tsx:208-225`）: 上のバーから開くと `top: 72`・`right: 16`。今回の案 A で通知と同じ高さになるので、重なり順で守る（上）
   - アクセシビリティの浮いたボタン（`AccessibilityProvider.tsx:170-182`・上のバーの無い画面だけ・`bottom: 80`）・クイズ管理の［＋］（右下）: 通知（上）とは重ならない
2. 関連機能: すべての画面の通知の位置が 16px → 72px 下がる。ログインの画面・登録用リンクの画面（上のバーが無い）も同じ位置に出る。ダイアログの中の通知（コピーなど）は、重なり順を変えないのでダイアログより手前のまま
3. 計画との関係: `frontend/src/App.tsx` と `e2e/tests/registration-link.spec.ts` は計画の実装対象の中。`frontend/src/components/AccessibilityProvider.tsx` と新しい `frontend/src/constants/layout.ts` は計画の外なので、計画変更記録に書いて計画レビューを通してから直す。受け入れ条件 AC12（「…ユーザーメニューのボタンに重ならず…」）は、上のバーのどのボタンも、上のバーから開くパネルの操作も塞がない形に強める
