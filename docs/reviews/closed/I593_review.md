- 審査の入口とレビュー役の定義・レビューの決まりを、ブランチが分かれた時点の写しの版で動かす。写しで動かせない判定の部品を変えた PR は必ず高リスク。テストを弱める差分を決定論で拾ってレビュー役に必ず見せる

## 振り返り

### I593 振り返り（かんたんなまとめ）

#### 良かった点
- 受け入れ条件 6 つをすべて満たした。審査の入口とレビュー役の定義は、マージ後は変更前の写しの版で自動で動く（理由: 公式ブログの「判定の基準は変更前の版から読む」に合わせ、毎回の `!` の手間も無くせる）
- 新しい仕組みがこの PR の中ですでに効いた。`!` で流したレビューの記録に「審査の版: 作業ツリー → 高リスク」とテストを弱めうる差分の一覧が載り、敵対的レビューまで自動で進んだ（理由: 決定論の判定にしたので、確かめが毎回同じに動く）
- コードレビューが、テストを弱める指摘が行の位置で止まらない穴（F1）を見つけ、1 回の修正で直った（理由: 新しい判定にも、既存の台帳の仕組みがそのまま効いた）

#### 今回の問題への直接の対処
- テストを弱める指摘が、消した行の位置によっては「差分の外」になり止まらなかった。止める種類を足したとき、その前にある「差分の中か外か」の判定を見落としていた。→ その判定でも受け入れ条件の未達と同じ扱いにして直し、テストを実在するファイルで確かめる形に強めた（直し済み）
- この PR ではレビューを流すたびに `!` を 4 回お願いした。レビューの仕組みそのものを変える PR なので、マージ前の写しにはまだ新しい仕組みが無かったため。→ このイシューのマージで解消する（次からは自動で流れる）。マージ後の最初のハーネスの PR で実測する（#547 にコメント）

#### 同じ問題を次回から防ぐ改善
- 整理で出た「直す深さ」の提案 3 つ（ほかの手順書も写しから読む・計画レビューの高リスクの付け方・gate-check の読み方）は、範囲を広げるので見送り、指示とレビュー役の見直し（#547）で判断する
- 新しいルールは足さない。今回の手戻りはどれも流れの中で捕まり（コードレビュー・shellcheck・pre-commit）、手戻りも小さかったため
