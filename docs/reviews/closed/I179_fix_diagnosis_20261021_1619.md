## 1. 失敗分解

再現の共通手順: 使い捨て git repo に primary、入れ子 `.claude/worktrees/nest`（未コミットの変更あり）、兄弟 `../sib` を作り、ガードに `{"tool_name":"Bash","tool_input":{"command":"<入力>"}}` を渡す。

### F1（High・止めすぎ）入れ子のセッションで自分の中を移動して戻る形が止まる
- 入力（cwd=入れ子）: `cd backend && cd .. && git add -A`・`cd backend && cd ../frontend && rm -r build`・`cd docs && cd .. && echo a > x.txt`
- 期待値: exit 0（自分のワークツリーから出ていない）／実際値: exit 2（`DANGER_OK=1` でも解けない）
- 原因箇所: 移動先を集めるループが、`..` を含む相対の移動先もすべての候補（セッションの作業フォルダ＝入れ子を含む）に当てるため、`<入れ子>/..`（primary の中）が候補に入る。

### F2（High・普通の書き方の取りこぼし）cp/mv の宛先指定の書き方
- 入力（cwd=primary）: `cp --target-directory <入れ子>/src f`（空白区切り）・`cp -t<入れ子>/src f`（連結）・`cp -vt <入れ子>/src f`（短いオプションの結合）・`cp --target=…`・`mv --target=…`
- 期待値: exit 2 ／ 実際値: exit 0（実測で入れ子の未コミット変更が上書き）

### F3（High・普通の書き方の取りこぼし）移動先の `~+`
- 入力: `cd ~+/.claude/worktrees/nest; rm -r src`・`git -C ~+/.claude/worktrees/nest checkout -- .` → exit 0（実測で消失）

### F4（High ×2・テスト不足）`git --work-tree <dir>`（空白区切り）の止める側 TC が無い／候補を 2 回まわす処理の 2 回目を確かめる TC が無い

### F5（Medium・文書）§9 の回避「`cd docs && mv *.md …`」が 1 コマンドでは止まる（別の Bash 呼び出しに分ける必要があるのに書いていない）

### 対象外とするもの（ユーザー判断＝意図的な回避の書き方。§9 の「止められないもの」に明記する）
- `CDPATH=`・`export CDPATH`・`HOME=…; cd`（引数以外で行き先が決まる cd）、`coproc`、同じコマンドの中で作ったシンボリックリンク経由、GNU の長いオプションの省略形（`rm --rec`・`env --chd=`・`--target=` 以外の省略）、逆順の相対移動を繰り返すループ。
- 同じコマンドに別ワークツリーの読み取り（`git -C <別> log`）と自分側の git の変更を並べる形が止まる（Medium・止めすぎ）: 第 8 周で受容した「1 つのコマンドで別ワークツリーへ移動してから自分側を変更する形」と同じ扱い（コマンドを分ければ通る）。

## 2. 根本原因
- **F1**: 第 8 周の「すべての移動先を全候補に当てる（和集合）」は抜け道を無くすために粗くしたが、`..` を全候補に当てると「入って戻る」だけの移動が親（primary）を候補に入れてしまう。和集合の粗さが、入れ子が標準になった配置と噛み合わなかった。
- **F2・F3**: 守る範囲を決めないまま「どんな書き方でも止める」を目指したため、普通の書き方（`-t<dir>`・`--target-directory <dir>`・`-vt`）と意図的な回避の書き方（`CDPATH`・`coproc`・省略形）を区別せずに追い続け、普通の書き方の一部も取りこぼしていた。
- **共通の根**: 文字列を解析するガードの脅威モデル（何を守るか）を計画に書かずに、敵対的レビューの「全部の抜け道」に応じ続けた。文字列の解析ではシェルの意味を完全には再現できないので、守る範囲を「普通の書き方の事故」に絞って明記する必要があった（公式文書も Bash の deny ルールは best-effort、強い境界はサンドボックスとしている）。
- **セキュリティ観点**: 過失による他ワークツリーの作業消失（OWASP A01 相当）の防止。意図的な回避は、Claude が敵対者ではない前提で対象外とし、強い境界が必要なら OS レベル（サンドボックス）で別途扱う。アプリの認証・認可・XSS・インジェクション・機密データの露出には該当しない。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨・ユーザー承認済みの案 1）: 守る範囲を「普通の書き方による事故」と明記し、その範囲の 4 点だけ直す
1. **F1**: 移動先のうち、`..` を含む相対の移動先は「書いた順に追った直前の位置」だけを基準にする。`..` を含まない相対の移動先は従来どおりすべての候補を基準にする（第 8 周の抜け道＝パイプ・`&`・括弧の `cd` は止めたまま）。候補集めは「増えなくなるまで」まわす（上限 8 回。逆順の連鎖も拾う）。
2. **F2**: cp/mv で宛先指定のオプション（`-t` を含む短いオプションの塊・`--t` で始まる長いオプション）があれば、位置引数と連結された値（`-t<dir>`・`--target=<dir>`・`--target-directory=<dir>`）をすべて宛先として見る（どれが宛先かを解析しない＝粗く止める）。
3. **F3**: 移動先の `~+`・`~-` を、すべての候補に置き換えて集める。
4. **F4**: `git --work-tree <dir>` の止める側 TC と、後ろの移動が手前の相対の移動の基準になる形（2 回目のまわり）の TC を足す。
- 文書: §9 の冒頭に脅威モデル（守る範囲＝普通の書き方による事故・対象外＝意図的な回避）を書き、「止められないもの」に上の対象外を追加。回避手順は「別の Bash 呼び出しに分ける」と明記（F5）。計画変更記録 5 に脅威モデルを追記し、敵対的レビューのプロンプトにもこの範囲を渡す。
- セキュリティ: 普通の書き方の事故は引き続き止まり、F1 の止めすぎが無くなる。意図的な回避は対象外と明記（受容）。保守性: 変更は小さい。リスク: 対象外の回避形は止まらない（文書化済み）。
