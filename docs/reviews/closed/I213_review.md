# I213 レビュー: Dependabot を点検し、動いて役に立つ形に直す

## 変更概要
Dependabot が動かなかった原因（リポジトリの設定で無効）を記録し、設定を「8 つの対象を見張る・小さい版上げはまとめる・出たばかりの版は待つ・セキュリティの修正にも設定が効く」形に書き直した。Dependabot の PR を CI だけで判定できるよう、CI から秘密情報を無くし（E2E のパスワードをジョブごとに作る）、action を SHA・土台イメージを指紋で固定した。手元は標準の起動コマンドで毎回作り直す形にし、受け取り方を runbook に書いた。決定論テストの選び方をルール化した。

## 変更点
（計画書 `docs/plans/closed/plan_I213.md` の 4 と対応）
- 4-1 `.github/dependabot.yml`: 8 対象（pip・npm /frontend・npm /e2e・docker /backend・docker /frontend・docker-compose・github-actions・pre-commit）・groups（version と security の両方で minor・patch をまとめる）・cooldown 7 日（pip・npm の major 14 日）・ignore（環境の版）・ラベル・`target-branch` を消した
- 4-2 ワークフロー 3 つの全 action を SHA＋版のコメントで固定

- 4-5 compose の e2e: 起動時に `npx playwright install chromium`

- 4-7 新規 `scripts/claude/tests/test_i213_dependabot.sh`（6 項目・FG 付き）／4-8 `test_i204_tool_sync.sh` の setup-uv の書き方の確かめを W1 に一本化

## 振り返り

### I213 振り返り（かんたんなまとめ）

#### 良かった点
- PR が来ない原因を、推測でなく GitHub の記録（Dependabot の実行記録が 0 件・警告の機能が無効）で先に絞れた。ユーザーが設定を有効にした直後に PR が届き、原因が確定した（理由: 画面の確認を頼む前に、bot で読める記録を全部読んだ）
- 設計の段階で小さな試し（スパイク）を 3 つ行い、そのままでは失敗する設計を実装の前に外せた。ハーネスの uv を Dependabot に任せると毎回失敗すること／Playwright の 2 つの版をそろえる仕組みが試せないこと／設定の書き間違いを公式の検証で止められること（理由: 外の仕組みの動きに頼る所を、計画の前に実物で確かめた）
- 届いた 14 件の CI を全部見て、Dependabot の PR では E2E が必ず落ちる（秘密情報が渡らない）ことを実装の前に見つけ、秘密情報を使わない形に直せた。PR の CI でも手元でも E2E が通った
- ユーザーの「テストは過剰では？」を受け、テストを 15 項目から 6 項目に絞り、選び方をルールとレビュー役に反映した

#### 今回の問題への直接の対処
- `node:18`（サポート終了）の版上げは、設計確認で「別のイシューにする」と決めたのに起票していなかった（クリップボードへのコマンドの貼り付けが失敗し、そのままになった）。→ I214（#375）として起票し、台帳の残りの 1 件（手元の e2e のコンテナで OS の部品を入れていない）も同梱した

#### 同じ問題を次回から防ぐ改善
- レビューのやり直しが、前の回の確かめの結果を正しく扱わない穴が 2 つ出た。1 つ目: 組み込みのセキュリティのレビューは実際には動いて「問題なし」と書いていたのに、書き方が決まった形でなかったため「読めていない」と判定された。そのうえ、やり直しは中身を見ずに通った（起票済みの I212 の穴そのもの）。2 つ目: 敵対的レビューの 2 周目は文言の差分だけを見たため、1 周目に実験で確かめた項目を「未検証」とし、あなたに延長の判断をお願いすることになった。→ どちらも判定のスクリプトの直しが要るので、起票済みの I212（#358）にまとめて書き足した（判定は決まった 1 行だけで読む／中身のファイルが変わっていなければ前の周の確認を引き継ぐ）。次のハーネスの作業で最優先
- テストの作りすぎ（設定の写しや、意図的な変更でしか壊れないものまで確かめる）→ このイシューの中で、テストの選び方をルール（`docs/runbooks/plan-writing-rules.md`）と計画レビュー役・コードレビュー役に足した

### I213 振り返り（詳細）

#### 良かった点
- 原因の特定を bot で読める記録（動的ワークフロー・alerts の API）から先に行い、設定画面の確認を最小にした
- スパイク 3 つ（uv の版の衝突・Playwright の起動時の導入・スキーマ検証の FG）で、実装前に設計を確定した
- 2 回目以降の grill-me で 14 件の CI を全件見て、E2E の secrets 依存を実装前に見つけた
- ユーザーの指摘を受けて決定論テストを 6 項目に絞り、基準をルール化した（I213 の中で完結）

| P1 | スキル・規約（判定の仕組み） | 差分だけのやり直しが、前の回の確かめの結果を正しく扱わない（組み込みのレビューの「指摘なし」を文章の形で読む／範囲 0 本で OK／敵対的レビューで中身の変わらない実験必須の項目を判定し直す） | I212（#358）に同梱: 組み込みのレビューに機械判定の 1 行を出させてそれだけで読む／前の周に実験で確認済みの項目は、記録の場所の外のファイルが変わっていなければ引き継ぐ（決定論） | `scripts/claude/code-review.sh`・`scripts/claude/adversarial-review.sh`・`docs/runbooks/review-rules.md` |

#### 5 Whys: P1（やり直しが前の回の確かめを正しく扱わない）
- Why 1: 敵対的レビューの 2 周目が、1 周目に確かめた項目を未検証にした → 2 周目は前の周の後の差分だけを見て、その範囲に無い項目を実験しなかった
- Why 2: なぜ実験しない項目が未検証になるか → 判定は周ごとに「必ず確かめる項目」を全部判定し直し、前の周の結果を使わない
- Why 3: なぜ前の周の結果を使わないか → 差分のレビュー（I197・I202）を入れたとき、「見る範囲を狭める」と「確かめた結果を引き継ぐ」を組で設計しなかった
- 抽象化: 「範囲を狭めたやり直しは、範囲の外の確認結果の引き継ぎ（とその条件）を同時に決めないと、確認が抜けるか、確認済みのものを未検証にする」。I213 に固有でない
- 分類: 予防処置

#### 見送り（理由）
- Write ツールが会話の途中で使えなくなった: 環境の許可の話で、Bash で 1 行作って Edit で置き換える回避で手戻りなし
- 計画レビューの実行中に e2e の 2 ファイルが元の文言に戻った: 原因不明。変更の通知でその場で捕まり、直し直して git の差分で確かめた（手戻りわずか）。同じことが続けば調べる
- 承認画面の多さ: I200（#335）で扱うとユーザーが決定済み（I213 マージ直後）
- 実装中に範囲が 3 回変わった（テストの絞り込み・ルールへの反映・承認画面）: どれもユーザーの指示で、計画変更記録と計画レビューのやり直しで扱えた
- 指示ファイルのメンテナンス: このイシューでレビュー役 2 つに観点を足した（ほかに足す観点は無い）
