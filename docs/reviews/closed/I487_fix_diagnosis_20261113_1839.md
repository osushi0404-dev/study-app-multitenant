# I487 修正の診断（コードレビュー F10・F7 の直しの後）

## 失敗分解
- 出どころ: `docs/reviews/I487_code_review_20261113_1828.md` の止める指摘 F10（Medium・`frontend/src/pages/Settings.tsx:195`・再現あり）
- 再現手順: ダッシュボードを開き、設定の取得（`GET /api/settings/`）が遅いうちに設定画面へ移る。目標を 60 分にして保存する。保存の前に始まった GET が、保存の後に古い 30 分を返す
- 期待値: 設定のキャッシュは保存した 60 分のまま
- 実際値: 遅れて届いた古い GET の応答（30 分）がキャッシュを上書きし、F7 の直し（保存の応答でキャッシュを書き換える）が崩れる
- ログ: なし

## 根本原因
- `setQueryData` の前に、同じキーの進行中の取得を止めていない。React Query は、進行中の取得が終わるとその結果でキャッシュを書くので、保存の後に届いた古い応答が勝つ
- React Query の公式の手順（mutation の応答・楽観的な更新でキャッシュを書くときは、先に `cancelQueries` で同じキーの取得を止める）を F7 の直しで入れていなかった
- セキュリティ: 該当なし

## 対応方針（全案＋推奨）
### 案 A（推奨）: `setQueryData` の前に `await queryClient.cancelQueries({ queryKey: userSettingsKey(user.id) })`
- 公式の手順そのもの。進行中の取得を止め、その古い応答はキャッシュに書かれない
- セキュリティ影響: なし。BP: 公式の推奨。保守性: 1 行
- リスク: 止めた取得を待っていた画面は、書き換えたキャッシュ（新しい値）を読むので問題ない
### 案 B: 保存の後に `invalidateQueries` も呼んで、もう一度取り直す
- 長所: 最後は必ずサーバーの値になる
- 短所: 取り直しが終わるまでは古い応答で上書きされうる時間が残る（F7 と同じ形の短い窓）。通信も増える
### 推奨: 案 A

## 影響調査
- 同型のバグ: キャッシュを手で書き換えているのはこの 1 か所だけ（`grep -rn "setQueryData" frontend/src` は `Settings.tsx` とテストだけ）
- テスト: TC-10d に「保存の前に始まった設定の取得が保存の後に古い値を返しても、キャッシュは保存した値のまま」を足す（進行中の取得を `queryClient.fetchQuery` で作り、応答を保存の後に返す）
