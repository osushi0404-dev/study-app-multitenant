## 振り返り

### かんたんなまとめ
**良かった点**
- 計画を書く前に、app-1 で読むだけの試しを 2 つ流しました（DB のコンテナだけで SQL を流す・backend の起動の処理を通らずに 1 つのコマンドを流す）。これで、手順書のコマンドが「移行が途中で止まった後」には動かないことを、事前に見つけられました。
- primary の作業を、計画書の手順だけを頼りに別のセッションへ渡せました。結果は GitHub #605 のコメントで受け取り、primary の状態が計画の想定と違ったところ（移行がもっと古かった・ほかのアプリの移行も流れた）も、そのつど承認を取って進められました。
- 計画レビューで「ほかのアプリの移行も一緒に流れる」と指摘され、事前の一覧（`migrate --plan`）を手順に足していました。primary では実際に、ほかのアプリの移行 3 本が見つかりました。

**今回の問題への直接の対処**
- 手順書の残りの細かい点が 3 つ見つかりました（消える行の候補の数え方・移行の後の DB で SELECT が失敗する・古いイメージだと動かない）。どれも軽いので、軽い指摘の一覧に回しました。次に手順書を直すイシューで扱います。

**同じ問題を次回から防ぐ改善**
- 今回の片付けが必要になった元は、「アプリを起動するたびに、DB の移行が自動で流れる」仕組みです。ワークツリーごとに DB が別なので、ほかのワークツリーでは、次に起動したときに承認も控えも無く危ない移行が流れてしまいます。この仕組みは #579 で直す予定なので、「ほかのワークツリーの初めての起動でも止まるようにする」ことを #579 にコメントで足しました。手順書に「気をつける」と書くより、仕組みで止めるほうが確かだからです。

**足さなかったもの（理由つき）**
- 「保存先を移すときは全部のワークツリーを片付ける」という決まりを手順書に足す案は、見送りました。心がけでは止まらず、#579 が直れば仕組みで止まるからです。
- コミットのときに、関係の無い古い記録 11 本を巻き込みかけました。送る前に気づいて作り直したので、決まりは足していません。
- primary の問題 186 の画像は、ほかのワークツリーに写しがありました。それでも、ユーザーが写しのあることを知ったうえで消すと決めたので、そのままにしました。

#### 5 Whys: ほかのワークツリーが移行の前のまま残った

- Why 2: ワークツリーごとに DB とファイルが別なことを、片付けの範囲に入れていなかった（R6 で「未確認」のまま受け入れた）
- Why 3: マージすれば済むと見えるが、DB の移行はそのワークツリーで起動したときに流れ、承認と控えはその場では取られない
- 根本原因: 危険な移行が「次に起動したとき」に、どのワークツリーでも承認の外で流れる仕組み（#579）。固有の名前を除いても成立する
