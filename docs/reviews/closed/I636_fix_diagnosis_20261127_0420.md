# I636 fix-loop 診断メモ（2026-11-27 04:20）

起点: test-gate の手動テスト No.2（AC13: E2E 全体を並行・`--retries=0` で 3 回流して TC-28 が 3 回とも通る）の NG。

## 失敗分解
- 再現手順: e2e コンテナで `npx playwright test --retries=0 --repeat-each=3`（§8 の上書きを重ねる）。同じ実行の中で TC-28（`e2e/tests/settings.spec.ts`）を 3 本並行に流す
- 期待値: TC-28 の保存（`PATCH /api/settings/`）の応答の `daily_study_goal_minutes` が、入力欄に入れた値（`next`）と同じ
- 実際値: `Expected: 45`・`Received: 50`（`e2e/tests/settings.spec.ts:28`。入力欄に 45 を入れて［保存］を押したのに、送られた値が 50）
- ログ: 63 件中 62 件が通過・TC-28 の 1 件が落ちた（repeat2）。同じ実行の 1 回目（別の実行）では TC-30 が 1 件落ちた（下の「影響調査」の 3）

## 根本原因
- 設定画面（`frontend/src/pages/Settings.tsx:159-175`）は、`useEffect` の中で `dashboardService.getUserSettings()` を呼び、応答で `resetSettingsForm(settingsData)`（React Hook Form の `reset`）を呼ぶ。効果の後片付け（古い応答を捨てる処理）が無い
- 開発のビルドでは `React.StrictMode`（`frontend/src/index.tsx:11`）が効果を 2 回走らせるので、設定の取得が 2 回出る。フォームは 1 回目の応答で描かれ（`loading` が偽になる）、利用者（E2E）が入力した後に 2 回目の応答が届くと、`reset` が入力欄を保存済みの値に戻す。そのまま［保存］を押すと、戻った値（50）が送られる
- 2 回目の応答が入力より後に届くのは、裏側が混んでいるとき（並行の E2E）だけなので、たまにしか落ちない（I620 の「並行で 1 回だけ落ちた」と同じ形。単独では通る）
- E2E は開発のサーバー（StrictMode あり）に対して流すので、この形で落ちる。本番のビルドは効果が 1 回なので同じ形では起きないが、効果に後片付けが無いことは React の推奨（https://react.dev/learn/synchronizing-with-effects#fetching-data）に反する。画面を離れてすぐ戻ったときなどに、古い応答が新しい入力を上書きしうる
- セキュリティの観点: 認証・認可・入力の検証・機密の扱いには関わらない（利用者自身の設定の値が、本人の入力でなく保存済みの値で送られるだけ）。該当なし

## 対応方針（全案＋推奨）
### 案 A（推奨）: 効果に後片付けを付け、古い応答を捨てる
- `useEffect` の中に `let ignore = false;`、後片付けで `ignore = true`。応答を受けた後、`ignore` なら `setSettings`・`resetSettingsForm`・`toast.error`・`setLoading` をしない
- セキュリティ影響: なし
- BP 適合: React の公式の「効果でデータを取るときの後片付け」の形そのもの（規約 §5 は取得を TanStack Query に寄せるが、この画面の移行は別の作業）
- 保守性: 3〜5 行。既存の作りを変えない
- リスク・副作用: StrictMode の 1 回目の取得の結果を捨てるだけ。2 回目の取得の応答で描くので、表示までの時間は今と同じ
- 確かめ方: Jest で「1 回目の取得が後片付けされた後に解決しても、フォームの値を戻さない」を再現（StrictMode で描き、1 回目の取得を遅らせる）。直しを外すと落ちることを確かめる。E2E は全体を 3 回、順に流す

### 案 B: 設定の取得を TanStack Query に移す（規約 §5）
- キャッシュ・取り直し・古い応答の扱いを Query に任せる。`reset` は最初の 1 回だけにする（`values` の同期などの作りが要る）
- セキュリティ影響: なし
- BP 適合: 規約 §5 に最も合う
- 保守性: 長い目では良いが、設定画面は 300 行を超え、通知・テーマ・パスワード・パスキー・学ぶ科目の欄が同居している。移行は I636 の範囲（レビューの残り）を大きく超える
- リスク・副作用: 保存の後のキャッシュの扱い（I487 F7・F10 の手順）と二重になる。新しいコードが大きく、それ自体が次の周の指摘の元になる

### 案 C: E2E の側で、2 回目の取得の応答を待ってから入力する
- テストだけ直す。画面の作り（古い応答が入力を戻す）は残る
- BP 適合: 原因を直さない（症状を隠す）。採らない

### 案 D: StrictMode を外す
- 開発で副作用の誤りを見つける仕組みを捨てる。採らない

### 推奨
案 A。原因（効果の後片付けが無い）を最小の変更で直し、React の公式の形に合う。案 B は規約の方向として正しいが、範囲が大きいので別の作業（規約 §16 の移行の流れ）に任せる。

## 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
1. 同型: `useEffect` の中の取得の応答でフォームを `reset` する画面を探した（`grep` で `useEffect` と `reset(` を使い、後片付け〔`ignore`・`cancelled`・`AbortController`〕の無いファイル）。`QuizManagement.tsx`・`SubjectManagement.tsx` は一覧の取得だけで、取得の応答でフォームを戻さない（`reset` はダイアログを開くときだけ）。`AddMemberDialog.tsx`・`PasskeyRenameDialog.tsx` は開いたときに空や固定の値へ戻すだけで、取得を待たない。同型は `Settings.tsx` だけ
2. 関連機能: `Settings.tsx` の保存の後のキャッシュの書き換え（I487 F7・F10）は保存の処理で、読み込みの効果は触らない。通知の予約（`useNotifications`）・テーマは読み込みの効果と別
3. 別の落ち方（TC-30）: 1 回目の実行で、管理者のページがログイン直後の 401 でログイン画面に戻った。画面の更新の宛先 `frontend/src/services/api.ts:142` の `/api/auth/token/refresh/` が、裏側（`backend/accounts/urls.py:31` の `auth/refresh/`）と食い違って 404 になり、ログアウトする。I636 の変更ではなく前からある食い違い。直すと認証の作り（トークンの更新）に触れ、I636 の範囲を超えるので、retro で別のイシューにする（この fix-loop では直さない）
4. 計画との関係: `Settings.tsx` は計画の実装対象に無い。計画 §4-13 の「ここに無いファイルが要るときは、計画変更記録に書いて計画レビューを通し直す」に従い、直す前に計画書を直して plan-review を通す
