## 2. 根本原因

- **H1**: 「I151 の完了後に起票する」というユーザーの指示を守ることを優先した。その結果、制約の置き場所を、版管理の外にあるローカルファイルにしてしまった。GitHub のイシュー本文は外部への書き込みなので、起票の時期と一緒に後回しにした。しかし既存のイシュー本文の同期は「起票」ではなく、指示とぶつからない。判断を誤った。
- **H2**: 判定 1b を足すときに、「ログの行がある＝成功した」と仮定した。Celery の beat がログを出す時点（送信の前）を確かめなかった。beat 側の失敗はログにしか出ないのに、そのログの ERROR を見る判定を作らなかった。
- **M1**: 実メールの危険を「probe が足す実行」の問題としてだけ捉え、beat が常に同じタスクを SMTP 設定の worker へ送っていることを見落とした。根本は開発環境の常設設定（worker の EMAIL_BACKEND が SMTP 固定・SendGrid のキーあり）で、I151 の範囲外の既存の問題である。
- **M2**: 条件付きの承認を、承認を記録する各所に転記するときに、条件の部分を落とした。
- **M3 / M4 / M5 / L**: 是正の波及を sweep する範囲が狭かった（特に review.md §7）。M4 は、レビューアが既存の不具合を新たに見つけた。

### セキュリティ観点

- M1 は、第三者（実在のアドレス）へ意図しないメールが届きうるという、プライバシーと信頼の問題である。I151 の依存更新が原因ではなく、開発環境の常設設定の問題。I151 の中では、TC の手順で危険を増やさないことと、危険の存在を記録に正しく書くことにとどめる。根治（開発環境では明示しない限り送信しない設定）は別イシューで行う。
- 認証・認可・入力検証・インジェクションに関わる変更は無い。

## 3. 対応方針（全案＋推奨）

### 案 1（推奨・前回エスカレーションで示した最終案を、理想の基準で詰めたもの）

- **H1**: GitHub #266（I150）と #274（I157）の本文を、ローカルの注記入りの版へ同期する。差分は注記とリンク行だけであることを確認済み（ほかの人の変更は上書きしない）。新しいイシューは作らないので、「起票は I151 の後で」という指示とはぶつからない。手動 No.8・review.md の根拠を「GitHub 本文への反映」に改める。
- **H2**: 判定 2c・2d（beat のログの ERROR / Traceback が 0 件）を加える。beat 側には既知のエラーが無いので、除外は無い。加えて判定 1c（worker のログで、`update_daily_analytics_task` の succeeded が 2 件以上）を加える。probe が足す実行は 1 回だけなので、2 件以上なら少なくとも 1 件は beat が送ったものになる。これで beat → broker → worker の経路を、端から端まで確かめられる。失敗を注入して検証する。
- **M1**: 計画書・I151.md・auto_test の「実メールを送らない」を、「probe が足す実行分だけ。beat の定期実行は開発環境の常設設定のまま」と正確に書き直す。TC と手動テストの手順に「復習カードがある状態で celery を動かさない（メールが送られうる）」という注意を書く。根治は、I151 の完了後に起票するイシューの候補に入れる（記憶メモと計画書ステップ 4 に記録済み）。
- **M2**: 承認の記録を、全箇所で「条件付きの承認。条件（理想の基準で問題ないこと）を満たしたかの判定は Claude が行い、その後の敵対的レビューで検証した」に揃える。
- **M3**: 計画書ステップ 5（記録の完成）に、「`/close` で PR 本文の『後続タスク』に、I151 の完了後に起票するイシューを必ず列挙する」を加える。手動 No.8 の確認項目にも入れる。
- **M4**: 既存の不具合として計画書 §2-8 に記録し、別イシューの候補に入れる。「TC-AUTO-03 が担う」を訂正する。
- **M5・L**: review.md §7 を現行の判定に揃える。3s の説明を「件数」に弱める。0926 は review.md の結果節で「旧判定 3 を評価した記録」と注記する。除外を外すときの手順の書きぶりを揃える。冒頭注記の見出しを改める。「同じイメージ」を「同じ依存の版」に訂正する。probe に開発環境のガード（`settings.DEBUG` が False なら実行せずに NG を出す）を加える。

### 案 2（不採用）: H1 を、ローカルの I150.md を I151 ブランチにコミットして解決する

- I150.md は他のイシューと同じく「未コミットで扱う」運用になっている（起票済みイシューのローカルファイルは invariant として未コミット）。I151 の PR に I150 の本文が混ざると、I150 の正本が 2 か所に分かれる。GitHub 本文の同期のほうが、正本（GitHub）に直接届くので優れている。

### 案 3（不採用）: H2 を、beat のログの ERROR だけで是正する

- 送信が成功したと beat が思っても、broker や worker 側で落ちる経路（キューの不一致など）は捕まえられない。worker 側の受信・成功の件数も見る案 1 のほうが、端から端まで確かめられる。
