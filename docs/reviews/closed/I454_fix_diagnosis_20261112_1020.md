## 根本原因
- 見張りは、どの文字が値を取るかを知らない。まとめ書き（`-tAcX`・`-lcX`・`-nesX`・`-vtX`・`-hlocalhost`）の中で、どこから後ろが値かは決められない。implement は「多く読む」側、fix-loop 1 は「少なく読む」側に 1 つの規則で寄せたため、呼び出し元によってどちらかが止める側の後退になった（同じ種類の指摘が 2 周続いた）
- どちらが安全側かは呼び出し元で決まる:
  - 多く読むほど止める側に倒れる: sh／su／flock／python／manage.py shell の `-c`（中を多く検査する）・sed の `-e`（式が見つかれば位置引数をすべて書き先にする）・cp などの `-t`（書き先が増える）・psql の `-c`（ただし今は `-c` が見つかるとヒアドキュメントを見ないので、偽の `-c` で見落とす＝F1）
  - 多く読むと誤って止める: psql の `-f`（DANGER_OK が要る停止・F2）・grep の `-e`／`-f`・`-f`／`--format`・`-o`／`-L`／`-f`
- セキュリティ観点: 守る対象は F10 が DB のデータ（手元の開発 DB）、F11 が develop への強制 push（GitHub の保護が最後の守り）、F12 が別ワークツリーの未コミットの作業（GitHub から戻せない）。守るのは普通の書き方の事故

## 対応方針（全案＋推奨）
- **案 A（推奨）: 読み方を 2 段にし、呼び出し元が選ぶ（粗い fail-closed）**
  - `_opt_values(toks, names, loose=False)`: 既定は変更前とまったく同じ 2 形（先頭の文字＝`-cX`・英字だけの並びの最後の文字＝`-tAc X`）。`loose=True` のときだけ、英字だけの並びの後にある該当の文字の後ろを、候補として**すべて**足す（`-tAcDELETE` → `DELETE`、`-hlocalhost` → `alhost` も候補）
  - `loose=True` にするのは、多く読むほど止める側に倒れる呼び出し元だけ: sh／su／flock の `-c`・python／manage.py shell の `-c`・psql の `-c`・sed の `-e`／`-f`・cp などの `-t`
  - psql の `-c`（`_sql_of`）は、`-c` の値とヒアドキュメント・here-string を**合わせて**見る（偽の `-c` があってもヒアドキュメントの DELETE を見落とさない・F1 の根本）
  - `-t` は、まとめ書きの途中から読んだ値（推測）があるときは、最後の位置引数も書き先に残す（推測が外れても本当の書き先を落とさない）
  - psql の `-f`・grep・`--format`・`-o` は変更前のまま（F2 の誤停止も変更前に戻る）
  - セキュリティ: 上の表のすべての行が止める側か変更前と同じになる。BP: 規則は英字かどうかだけで、値を取る文字の一覧は持たない。保守性: 関数は 1 つのまま、呼び出し元に 1 語足すだけ。リスク: 多く読む側は誤った確認が増えうる → corpus diff で件数を見る
- 案 B: コマンドごとに値を取る文字の表を持ち、getopt と同じに読む（F14 の提案）
  - 精密だが、表の保守が要り、粗い判定の方針（I179 retro P1・memory「fix-loop を過剰にしない」）に反する。同じ種類が 2 周続いたら精密化をやめる決まりにも反する。採らない
- 案 C: implement の形（1 つ目の候補だけを多く読む）に戻し、`_sql_of` だけヒアドキュメントを合わせて見る
  - F1 は直るが、F2（`-dprofile_db` で DANGER_OK が要る誤停止）が残り、普通の作業を止める。採らない
