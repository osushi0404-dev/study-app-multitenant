# I151 fix-loop 診断メモ（2026-10-16）

- 起点: `/test I151` で TC-AUTO-10 判定 2 が不合格（2026-10-16 08:26 台のログ）
- 対象: `docs/tests/closed/I151_auto_test.md` TC-AUTO-10（AC-15「celery worker のタスクが成功する」）

## 1. 失敗分解

| 項目 | 内容 |
|---|---|
| 再現手順 | ① `docker compose build backend celery celery-beat` → `docker compose up -d --wait`（ユーザー指示による 2026-10-16 の作り直し）。② 起動後に `docker compose logs celery --since 3m > /tmp/i151_celery.log 2>&1`。③ 判定 2 `! grep -qE 'ERROR\|Traceback' /tmp/i151_celery.log` |
| 期待値 | 判定 1（成功ログあり）・判定 2（`ERROR` / `Traceback` なし）とも exit 0 |
| 実際値 | 判定 1 は exit 0（`studylogs.tasks.*` が 3 件 succeeded）。判定 2 は exit 1（ERROR 1 行・Traceback 1 回） |
| ログ | `ERROR/MainProcess] Received unregistered task of type 'core.tasks.cache_maintenance_task'. The message has been ignored and discarded.` に続いて `Traceback ... celery/worker/consumer/consumer.py, line 658, in on_task_received ... KeyError: 'core.tasks.cache_maintenance_task'`。同じ秒（08:26:19）に `studylogs` の 3 タスクも受信されている。コンテナを作り直している間に beat が Redis に積んだメッセージが、起動直後にまとめて配送されたもの |

## 2. 根本原因

**I151 以前（2026-03-20 の I004）からある既存の不具合で、依存更新が原因ではない。**

1. `backend/core/celery.py:52` の beat スケジュールが、30 分ごとに `core.tasks.cache_maintenance_task` を送っている。
2. worker は `app.autodiscover_tasks()`（引数なし）でタスクを登録する。この関数は `INSTALLED_APPS` の各アプリの `tasks` モジュールしか探さない。`settings.py` の `LOCAL_APPS` は `accounts` / `problems` / `studylogs` / `dashboard` だけで、`core` は入っていない。また `core.tasks` を明示的に import している箇所も無い（`git grep` で確認）。
3. このため worker は `core.tasks.*` を 1 つも登録していない。`celery -A core inspect registered` の結果は `core.celery.debug_task` と `studylogs.tasks.*` 8 件だけだった。届いたメッセージは「未登録」として捨てられ、ERROR と Traceback が出る。
4. これまでの TC-AUTO-10（2026-08-24 / 2026-10-14）が合格していたのは、30 分に 1 回の送信が判定窓の 3 分に入らなかったからである。今回は作り直しの間に溜まったメッセージが起動時に一斉に届いたため、窓に入った。**TC-AUTO-10 は 30 分周期の既存エラーを、タイミング次第でしか検出できない設計だった**（判定式の盲点）。

**I151 起因でないことの根拠**: I151 の `settings.py` の差分は `django_extensions` と `guardian` の 2 行削除だけ（`git diff origin/develop HEAD -- backend/core/settings.py backend/core/celery.py backend/core/tasks.py`）。`celery.py` / `tasks.py` は変わっておらず、celery 5.3.4・kombu 5.6.2 も据え置きである。登録の仕組み（`autodiscover_tasks` が `INSTALLED_APPS` を見る）は celery 側の挙動で、Django の版に依存しない。

**登録しても直らないことの確認**: 試しに `core.tasks.cache_maintenance_task` を backend コンテナで 1 回直接実行した（`t.apply()`。読み取りのみ）。結果は `succeeded` だった。しかし中で呼ぶ `cache_service.get_cache_stats()`（`core/cache_service.py:321`）は、`'RedisCache' object has no attribute '_cache'` で失敗して `{'error': ...}` を返していた。統計の取得後の処理も `pass` だけである。つまりこのタスクは、登録しても実質何もしない。この `_cache` の不具合は、敵対的レビュー第 2 周で既知（新旧の django-redis どちらにも `_cache` が無い）。

### セキュリティ観点

認証・認可・入力検証・機密データの露出のいずれにも該当しない。捨てられているのはキャッシュ統計を取るだけの保守タスクで、引数は空。ログに機密情報は含まれない（メッセージ本文は `[[], {}, {...}]`）。

## 3. 対応方針（全案＋推奨）

### 案 A（推奨）: 既存不具合として別イシューで根治し、I151 では TC-AUTO-10 を「既知の 1 種だけを厳密に除外し、それ以外は必ず落とす」判定へ改める

- I151 での変更（docs のみ。コードは変えない）:
  - TC-AUTO-10 の判定 2 を、次の件数一致の 2 行に置き換える。
    - 判定 2a: `ERROR` を含む行の数 ＝ `Received unregistered task of type 'core.tasks.cache_maintenance_task'` を含む行の数（`test "$(grep -c 'ERROR' log)" -eq "$(grep -c "unregistered task of type 'core.tasks.cache_maintenance_task'" log)"`）
    - 判定 2b: `Traceback` の数 ＝ `KeyError: 'core.tasks.cache_maintenance_task'` の数
  - 既知の 1 種以外の ERROR / Traceback が 1 行でも混ざれば、件数がずれて不合格になる。既知の 1 種が 0 件のときも 0 = 0 で合格する（タイミング依存は残らない）。
  - 判定 3 を新設する。`celery -A core inspect registered` の出力に、beat スケジュールの `studylogs.tasks.*` 4 件がすべてあること。これで、依存更新で登録そのものが壊れる退行を、タイミングに関係なく検出する。
  - 除外は**別イシューのマージまでの暫定**と明記する。別イシューの AC に「TC-AUTO-10 相当の判定から除外を外しても合格すること」を入れる。
  - 失敗注入で検証する（既知エラーだけのログ → 合格、別の ERROR を 1 行足したログ → 不合格、Traceback を 1 つ足したログ → 不合格）。
- 別イシュー（起票案）: 「celery の core.tasks が未登録で cache_maintenance_task が 30 分ごとに破棄される問題を修正（`cache._cache` 不在で統計も取れない）」。登録方式（`INSTALLED_APPS` へ追加するか、`app.conf.imports` で読み込むか）と、何もしていないタスクを残すか消すかは、そちらで決める。
- セキュリティ影響: なし（判定の厳しさは、既知の 1 種を除いて現状以上）。
- ベストプラクティス: 計画外の実装を禁止する I151 の憲法（計画書に無い実装はしない）に沿う。依存更新の PR に無関係な挙動変更を混ぜない。
- 保守性: 暫定の除外が残り続ける危険がある。別イシューの AC に「除外を外す」を入れて歯止めにする。
- リスク・副作用: 除外のパターンを広くしすぎると別のエラーを隠す。そこで ERROR と Traceback をそれぞれ件数一致にし、タスク名まで完全に指定して最小にする。

### 案 B: I151 の中で根治する（`core.tasks` を登録する）

- 例: `celery.py` に `app.conf.imports = ('core.tasks',)` を足す。または `LOCAL_APPS` に `'core'` を足す。
- メリット: TC-AUTO-10 を変えずに済み、ERROR は止まる。
- デメリット: 計画書に無い実装になる（計画の更新と再承認が要る）。依存更新の PR に、無関係な挙動の変更（タスクが 30 分ごとに実際に動き始める）が混ざる。しかも登録しても、`_cache` の不具合で中身は空振りする（上の実測）。直したように見えて、実際には何も直らない。`'core'` を `INSTALLED_APPS` に足す方式は、モデルやテストの探索範囲も変わるので影響が広い。
- セキュリティ影響: なし。

### 案 C: beat スケジュールから `cache-maintenance` を外す

- メリット: ERROR は止まり、何もしていないタスクも動かなくなる。
- デメリット: 案 B と同じく計画外の変更。タスクを残すか消すかという設計判断を、依存更新の PR で先取りしてしまう。

### 案 D（不採用）: 時間をずらして TC-AUTO-10 を取り直す

- 30 分周期の窓を外して再実行すれば合格する。しかし既存エラーを知りながら見えない時刻を選ぶことになり、判定の盲点（タイミング依存）も残る。採らない。

### 推奨

**案 A**。原因は I151 の前からあり、根治（登録方式の決定と、空振りしているタスクの扱い）は依存更新とは別の設計判断なので、別イシューで行うのが理想の形である。I151 の側では、TC-AUTO-10 を「タイミングで見逃す」状態から「既知の 1 種以外は必ず落とす＋登録の退行はタイミングに関係なく検出する」状態へ改める。結果として、判定は現状より厳しくなる。

## 4. 影響調査（実施有無と結果）

- **同型バグ（スケジュールされているのに未登録のタスク）**: beat スケジュール 5 件のうち、`studylogs.tasks.*` の 4 件はすべて登録済み（`inspect registered` で確認）。未登録なのは `core.tasks.cache_maintenance_task` の 1 件だけ。
- **他の呼び出し箇所**: `core/tasks.py` の 4 タスク（`cache_maintenance_task` / `cleanup_old_sessions_task` / `system_health_check_task` / `generate_system_report_task`）を参照しているのは `core/celery.py:52` だけ。`.delay()` などの呼び出しは無い（`git grep`）。ほかの 3 タスクはどこからも使われていない。
- **関連機能への波及**: 捨てられるのはこの 1 種だけで、同時に届いた `studylogs` の 3 タスクは正常に成功している。ユーザー向けの機能への影響は無い。
- **I151 の他の TC への波及**: TC-AUTO-10 以外の `/test` の結果（TC-00〜09・11A/11B・15〜17）はすべて合格。TC-12 / 13 / 14 は停止のため未実行。
- **記録の波及**: 計画書の AC-15 は「タスクの成功が確認できる」だけで、エラーが無いことは条件にしていない（`plan_I151.md:171`）。手動 No.3 の期待結果は「`ERROR` / `Traceback` が無い」なので（`I151_manual_test.md:25`）、案 A を採る場合は TC-AUTO-10 と同じ書きぶりへ揃える。

## 5. 訂正（2026-10-16・fix-loop 後の敵対的レビュー第 1 周で判明）

本メモはレビュー済みの記録なので、本文は書き換えず、ここに訂正を記録する。

1. **失敗分解「ログ」欄と根本原因 4 の経緯は誤り**: 「コンテナを作り直している間に beat が Redis に積んだメッセージが、起動直後にまとめて配送された」と書いたが、誤りだった。celery / celery-beat は 2026-10-16 01:44 JST に起動したまま動き続けており（`docker inspect` の StartedAt＝2026-10-15T16:44:36Z）、08:26 の時点で作り直してはいない。実際は、worker と beat のログが 08:00:32〜08:26:19 に途切れていた（ホストのスリープからの復帰とみられる）。08:26:19 に、beat が期限を過ぎた予定（cache-maintenance を含む）をまとめて送った。また beat の予定ファイル（`backend/celerybeat-schedule`。ホスト側に残る）のため、beat を再起動すると cache-maintenance がすぐに送られる（01:44:38 に実例あり）。そのため「再作成から 1 分後」に実行する TC-AUTO-10 では、既知のエラーはほぼ毎回窓に入る。結論（I151 起因ではない）は変わらない（レビューアが celery 5.3.4 の Django 連携部と develop の設定を確認）。
2. **推奨の「判定は現状より厳しくなる」は不正確**: 判定 2a・2b は、既知の 1 種について、旧判定 2 なら不合格になるログを合格にする。**この 1 種については判定を緩める変更**である。別の軸（登録の確認）で厳しくした部分はあるが、全体として「厳しくなる」とは言えない。
3. **判定 3（固定の 4 タスク名）の効果は過大評価だった**: 固定リストの登録確認では、周期の長いタスクの実行時の失敗（例外を捕まえて `{'error': ...}` を返し、succeeded と記録される）、スケジュールへのタスク追加、別 worker の混入を検出できなかった。`docs/tests/closed/I151_celery_probe.py` を使う判定 3s・3a・3b・4a・4b（スケジュールから導いた全タスクの登録と実行結果）に置き換えた（`I151_auto_test.md` TC-AUTO-10）。
4. **影響調査の漏れ**: `core.tasks` の登録に依存する未着手イシュー（I150: `core/tasks.py` に失効トークン削除タスクを追加）と、cache-maintenance の扱いを先に決めてしまう起票済みイシュー（I157: beat 5 件の crontab 化）を見ていなかった。実施順の制約を、計画書ステップ 4 に追記した。
5. **ファイル名の時刻**: 本メモのファイル名 `_1740` は作成時刻と合っていない（実際の作成は 08:3x 台）。参照箇所が多いため、名前は変えずにここに記録する。
