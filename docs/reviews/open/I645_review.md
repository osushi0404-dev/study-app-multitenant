## 振り返り

### I645 振り返り（かんたんなまとめ）

#### 良かった点
- 本物のブラウザで動くテスト（E2E）を先に足したおかげで、計画で見立てた原因（押せなくした選択肢の灰色の強さ）の裏にあった本当の原因（選んだ選択肢と API の id の比べ方が、文字と数字で合っていなかった）を、マージの前に見つけられた（理由: 部品のテストは型に合わせて id を文字で作っていたので、それだけでは気づけなかった）
- ダークモードの色を目で見るだけでなく、色を測って明るさの比を計算した（理由: 見た目では読めそうでも、赤の比が決まりの 4.5:1 に届いていないと数字で分かった）
- 失敗の注入（印を消す・色を消す）で、テストが本当に落ちることを毎回確かめた（理由: 書き換えのたびに、テストが何も見ていない状態になっていないかを確かめられた）

#### 今回の問題への直接の対処
- ダークモードで、クイズの解説の枠が明るい灰色のままで読みにくく、赤い文字も明るさの比が足りなかった。画面が明るいモード向けの色を直接書いていて、テーマもダークモードの色を確かめていなかったため。→ I649（#649）を起票した。テーマでダークモードの色を決め直し、今回クイズの選択肢だけに入れた手当てもテーマに戻す
- レビューで、答えた後の正誤が読み上げでは選択肢ごとに分からない（アイコンは飾りで読まない）と指摘された。止めるほどではない小さな指摘。→ 同じ画面の読み上げを直す #536 に入れた
- レビューで、プレビューのテストの並びの確かめが記号の位置だけを見ていると指摘された。→ 選択肢の並びを扱う #647 でテストを足すときにそろえるよう入れた

#### 同じ問題を次回から防ぐ改善
- 選んだ誤答に印が出なかった本当の原因は、画面が手で書いた API の型（id は文字）が、実際の API（id は数字）と食い違っていたこと。型が嘘をついているので、型チェックもテストも気づけなかった。→ 手で書いた型を API の定義から作った型に置き換えるイシュー #496 に入れた。置き換えれば、同じ種類の食い違いを型チェックが機械で止める

#### 見送ったこと（理由つき）
- 計画のときに実機で再現せず、コードを読んで原因を推測した → 実装の E2E がその場で本当の原因を捕まえ、手戻りは小さかったので、新しい手順は足さない
- 書き換えでファイルの改行コードが変わった・コミットの時のリントで 2 回止まった・手元の E2E がログインの回数の制限で落ちた → どれも、整理の点検・コミットの前の検査・手順書の既存の避け方がその場で捕まえたので、新しい手順は足さない

#### なぜを繰り返す原因分析（P1）
- Why 1: なぜ選んだ誤答に印が出なかったか → 選んだ id（文字）と API の id（数字）を `includes` で比べて外れた
- Why 2: なぜ文字と数字が混ざったか → ラジオの値は文字になり、画面の型は id を文字と書いていたので、型チェックが食い違いを見なかった
- Why 3: なぜ型が実際と違ったか → 画面の型が API の定義から作られず手書きで、API の実際の形と同期する仕組みが無い
- 抽象化: 「画面が使う API の型が、API の定義から作られていないと、実際の応答との食い違いを型チェックもテストも見逃す」。I645 に固有でない → 予防処置（#496 の範囲）

#### 理想の状態との差
- 計画（plan-issue）: 理想は、利用者に見える症状の原因を計画の前に実機で再現して確かめていた。実際はコードを読んで推測した。ただし実装の最初の E2E が捕まえたので、見送り（2.7 の問 2）
- 実装: 理想どおり、E2E を早く流して見つけた
