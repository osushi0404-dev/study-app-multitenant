## 背景/目的

**背景**: 2026-08-15、I146 の `/code-review` が CI ゲートで停止した。原因は I146 の変更ではなく、第三者が公開した Django の新規 CVE を `pip-audit` が検出したことだった（I151 として起票）。この停止は I146 に限らず、backend を含む**全 PR** に及ぶ。実際 2026-08-07 の CVE 公開から 8 日間、定期監査は毎晩失敗し続け、その間に push された PR はすべてマージ不能だった。

**目的**: リポジトリ外の出来事（第三者による advisory 公開）だけで、無関係な変更のマージ経路が全面停止する状態を解消する。PR ゲートは「その PR が状況を悪化させたか」を判定し、リポジトリ全体の既存負債は定期監査＋追跡イシュー＋期限で管理する、という役割分担へ移す。

### 現状の問題（証拠・再現手順）

現行の PR ゲートはリポジトリの**現在状態**を判定している:

```yaml
# .github/workflows/ci.yml
- name: pip-audit
  run: pip-audit -r requirements.txt          # 検出 0 件でなければ fail
- name: npm audit
  run: npm audit --audit-level=critical --omit=dev
```

この判定は「この PR が何を変えたか」を一切見ない。結果として:

1. **PR が触っていない依存の CVE が公開された瞬間、その PR は落ちる。** 2026-08-15 時点で PR #261（I146・変更内容は文書とハーネスのみで `requirements.txt` 未変更）の `Backend Lint & Security` が FAILURE。
2. **停止は全面的。** 現在 open の他 PR（#256 等）が緑に見えているのは直近実行が CVE 公開前だからであり、再 push すれば同様に落ちる。
3. **定期監査と仕事が重複している。** リポジトリ現在状態の監視は `dependency-audit.yml` が毎晩実施し、fail 時は GitHub イシューを自動起票する（#262 が該当・2026-08-07 起票）。PR ゲートは同じ判定を再実行したうえ、全作業停止という副作用だけを追加している。
4. **停止が長期化しうる。** 今回の解消には Django 5.2 への移行（I151）が必要であり、即日では終わらない。その間ずっと全 PR が止まる。

### 根本原因

**PR ゲートの判定対象が「変更の影響」ではなく「リポジトリの現在状態」になっている。**

CI の各ゲートは本来「この変更が既存の品質を下げていないか」を見る回帰防止装置である。しかし依存監査だけは、変更と無関係な外部データベース（advisory DB）の時間変化を判定に取り込んでおり、**リポジトリを一切変更しなくても、ある日突然 fail に転じる**。この性質を持つ判定をマージ必須チェックに置いたことが原因である。

なお現行 runbook は「定期監査グリーンなら PR もグリーン」という一貫性を保つよう定めており（docs/runbooks/dependency-audit.md）、両者が同一条件であること自体は決定論ゲート `test_i109_dependency_audit.sh` のペア検証で担保されている。つまり本問題は実装の不具合ではなく、**意図どおりに実装された設計の帰結**である。したがって設計判断のやり直しとして扱う。

### 解決方針

**許可リスト（期限・追跡イシュー必須）方式を採用する。**

- PR ゲートは、許可リストに載っていない検出があれば fail する。載っている検出は通す。
- 許可リストの各エントリには **対象 ID・パッケージ・理由・追跡イシュー番号・失効日** を必須とし、**失効日を過ぎたエントリがあればゲートは fail する**。
- 定期監査（`dependency-audit.yml`）は**許可リストを適用しない**。リポジトリの真の現在状態を毎晩監視し、これまでどおり自動起票する（現行動作を維持）。
- 判定は shell スクリプト（例: `scripts/claude/audit-gate.sh`）に集約し、ci.yml からはそれを呼ぶ。backend（pip-audit）/ frontend（npm audit）で同じ枠組みを使う。

ゲートが fail する条件（いずれか）:
1. 許可リストにない検出がある（＝この PR による新規混入、または未承認の既存分）
2. 失効日を過ぎたエントリがある（＝期限内に直さなかった）
3. 必須項目（追跡イシュー・失効日・理由）を欠くエントリがある
4. 実際には検出されなくなった古いエントリが残っている（＝許可リストの衛生。取り除き忘れの放置防止）

**この方式を選ぶ理由**: 既存分を通すこと自体は他方式でも実現できるが、本方式は「誰が・なぜ・いつまでに直すか」を**人間が明示的に書かない限り通らない**。放置すると期限切れで再び全面停止するため、直す力（forcing function）が保たれる。

**採用しなかった案**: develop をベースラインに差分判定する方式（PR head と base の検出 ID を比較し、増分のみで fail）。維持コストは低いが、既存分が**記録も期限もないまま無期限に免除**される。develop へ直接入った脆弱性が誰にも意識されず残り続けるため、「気づける」という定期監査の価値を実質的に損なう。今回の停止の再発は防げても、別の失敗（放置の常態化）に置き換わるだけであり採用しない。

**この変更は「チェックを甘くする」ものではない**という点を計画・レビューで明確にすること。既存分を無条件に素通しするのではなく、明示的な承認・追跡・期限を課したうえで通す。判定の厳しさは維持し、停止の巻き添え範囲だけを絞る。

## 関連する品質基準
- C8 セキュリティ — 脆弱性検知の実効性を落とさずに、停止の巻き添え範囲だけを絞る。許可リストが「無期限の免罪符」にならないことをテストで担保する
