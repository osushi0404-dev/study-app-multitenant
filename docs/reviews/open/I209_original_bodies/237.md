# I130: code-review.sh ゲート分類器のクォート考慮化 — 引用符内パイプの誤 BLOCKER を是正し、ゲート実走可能な判定コマンド形を plan-writing-rules に明文化（同梱: 計画変更時の旧値 sweep チェック・issue-bootstrap の GitHub 本文再同期・plan-issue のイシューファイル自動復元）

## 関連資料
- GitHub Issue: #237
- 起点: I122 retro（2026-07-18）予防処置 P1〜P3 の同梱起票（軽微 2 件は個別イシュー過剰のため主題に同梱）
- 追加同梱（P4）の起点: 2026-08-15 の I151（#267）起票時。track:app のイシューを wt-harness 側で起票したため、着手先の app worktree からローカルファイルが見えず、手動復元が必要になった（P3 と同じ「GitHub 本文が正」の前提に立つ自動化）
- 実例（P1）: docs/reviews/I122_code_review_20260718_1303.md — TC-04 `grep -qF '| 合否基準が合格時に非ゼロ終了する' ...` が「⚠️ 実走対象外（allowlist 不一致/チェーン系・fail-closed）」→ FINAL VERDICT: BLOCKER。LLM レビュー本文は全 AC 実装済み・指摘 Low のみだったため、分類器の誤判定が単独で差し戻し 1 往復を生んだ
- 是正の実例（P1 暫定対処）: docs/reviews/I122_code_review_20260718_1310.md — TC-04 をパイプ文字なしの一意フレーズ判定に変更して OK 化（回避であり根治ではない）
- 対象スクリプト: scripts/claude/code-review.sh（ゲート分類ロジック）
- 対象ルール: docs/runbooks/plan-writing-rules.md「否定・回帰系の決定論テストの自己検証（false-green 禁止）」節（I122 で追加した合否判定インターフェース統一 bullet の周辺）

## 背景/目的

**背景**: code-review.sh のゲート分類器が引用符内の `|` をパイプチェーンと誤判定し、I122 の code-review で LLM レビュー全 AC 実装済みにも関わらず誤 BLOCKER→差し戻し 1 往復が発生した（I122 retro 予防処置 P1〜P3 の同梱起票・2026-07-18）。
**目的**: 分類器をクォート考慮のトークン単位判定に精緻化して受理形を plan-writing-rules に明文化し（P1）、計画変更時の旧値 sweep チェック（P2）・issue-bootstrap の GitHub 本文再同期（P3）・plan-issue のイシューファイル自動復元（P4）を併せて追加する。

### 現状の問題（証拠・再現手順）
- **P1（主題）**: code-review.sh のゲート分類器は、auto_test.md の決定論ゲートコマンドを allowlist（`grep -q` 等）と照合する際にクォート文脈を考慮しない。このため**引用符内の固定文字列に `|` を含むだけ**の単一コマンド（例: `grep -qF '| 表セル文言' file`）をパイプチェーンと誤判定し、「実走対象外（fail-closed）」→ 合成判定 BLOCKER にする。再現: I122 の code-review 初回（20260718_1303）。テーブル行アンカー等、`|` を含む固定文字列判定は今後も需要があるが、現状は書けない制約が暗黙に存在し、どのルールにも明文化されていない。
- **P2（同梱）**: 計画作成中にスコープ・対象数を変更した場合（I122 では 3→4 ファイル）、変更に関連するセクションは更新しても、数量の旧値表記が他セクションに残る（I122 plan review 20260718_1238 Warning: 「3 ファイル」が 5 箇所残存）。旧値を grep して残存ゼロを機械確認する手順が文書品質ゲートにない。
- **P3（同梱）**: issue-bootstrap は GitHub Issue 番号をローカルのイシューファイルへ追記する（step 5）が、その後 GitHub 本文を再同期するステップがない。worktree 間ハンドオフは「GitHub 本文が正」を前提に `gh issue view --json body` で取り込むため、GitHub# 行が取り込み先で毎回欠落する（I122 の harness 側取り込みで実発生・手動追記で対処）。

- **P4（同梱）**: イシューファイル（`docs/issues/open/I###.md`）は起票した worktree の untracked ファイルとして存在し、**別 worktree からは見えない**（worktree.md §8）。しかしイシューのトラック（`track:app` / `track:harness`）と起票した worktree は一致するとは限らない。着手先の worktree に到達する手段が `gh issue view <GitHub#> --json body -q .body > docs/issues/open/I###.md` の**手動実行のみ**で、どのスキルにも組み込まれていない。実発生 2 件: (a) 2026-08-15、I151（#267・track:app）を wt-harness で起票 → app worktree に不在（`ls` で確認）、(b) I134 完了時に「隣 worktree へのローカル反映が未実施」のまま残置。手順を知らない／忘れたセッションは、イシューファイルが無い状態で `/plan-issue` に入り、参照先不在のまま進むか停止する。なお他 worktree への直接書き込みは PreToolUse フックで技術ブロックされているため（worktree.md §9・I095）、起票側からコピーして解消することはできない。

### 根本原因
- P1: 分類器が文字列一致ベースでクォートを解釈しない実装（導入時は単純コマンドのみ想定）。かつ「ゲートで実走可能な判定コマンドの形」の制約がどのルールにも明文化されておらず、TC 作成側が制限を知る手段がない（I122 retro 5 Whys）。
- P2: 「消費箇所の全件更新」ルールは概念・パスを対象としており、数量・件数表記のスコープ変更を対象として明文化していない。
- P3: step 5（ローカル追記）が GitHub 本文への伝播を前提にしていない（取り込み手順の前提と不整合）。
- P4: worktree 間ハンドオフの正本が GitHub 本文であることは runbook・イシュー本文（本ファイル §制約 の取り込みコマンド）に**記述としては存在する**が、実行はセッションの人手規律に委ねられている。イシューファイルを必要とするスキル（`/plan-issue`）が、その不在を検知して自力で復元する構造になっていない。

### 解決方針
- **P1-do（根治）**: code-review.sh のゲート分類ロジックをクォート考慮のトークン単位判定に精緻化する。シングル/ダブルクォート内の `|`・`;`・`&&` 等はチェーン記号として扱わない。**fail-closed 原則は維持**する（クォート外にチェーン記号がある・allowlist 不一致の形は引き続き実走対象外）。分類の決定論テストを scripts/claude/tests/ に追加する（①引用符内 `|` を含む allowlist コマンド → 実走対象、②実際のパイプチェーン `cmd | cmd` → 対象外、③クォート不整合等の不明形 → 対象外、の 3 方向＋失敗注入）。
- **P1-gate（明文化）**: plan-writing-rules の合否判定インターフェース統一 bullet の周辺に「決定論ゲートの判定コマンドは分類器が実走可能な形で書く（単一コマンド・チェーン記号を含めない。引用符内も分類器の対応範囲を確認する）」を追記し、分類器の受理形を利用者から見える仕様にする。
- **P2（同梱）**: plan-issue SKILL の文書品質ゲートに「計画作成中にスコープ・対象数を変更した場合、旧値（旧ファイル数・旧 TC 数等）を計画書・テスト文書に grep して残存ゼロを確認したか」のチェック項目を 1 件追加する。
- **P3（同梱）**: issue-bootstrap SKILL の step 5 に「GitHub# 追記後、`gh issue edit <GitHub#> --body-file docs/issues/open/I###.md` で GitHub 本文を再同期する（`gh` 不可なら skip・非ブロック）」を追記する。
- **P4（同梱）**: plan-issue SKILL の冒頭に「ローカルの `docs/issues/open/I###.md` が存在しない場合、GitHub イシュー本文から復元してから続行する」手順を追加する。人手規律ではなく**スキルの標準手順**として組み込むことで、起票 worktree と着手 worktree の不一致を意識せずに済む状態にする。
  - 復元元の特定: `gh issue list --state all --search "I### in:title" --json number -q '.[0].number'` で GitHub# を引き、`gh issue view <GitHub#> --json body -q .body > docs/issues/open/I###.md` で書き出す。
  - **fail-closed**: `gh` 不可・該当イシュー不在・本文が空のいずれかなら復元せず停止する（空ファイルを作って続行しない）。P3 が入れば GitHub 本文にローカルと同じ内容が載っているため、この復元で情報欠落は生じない（P3 と P4 はセットで意味を持つ）。
  - 既にローカルファイルが存在する場合は**何もしない**（GitHub 本文で上書きしない。ローカルでの編集途中を壊さないため）。

## 受け入れ条件（Acceptance Criteria）
