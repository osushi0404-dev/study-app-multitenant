# I186: 開発環境の見直し・改善を定期的に回す仕組みを作る — 公式機能（/insights・/doctor・/skill-doctor・/fewer-permission-prompts・定期実行）を土台にし、足りない部分（承認の回数・周回の数え方、ベストプラクティスとの差分確認）だけを足して I185 の手順を繰り返せるようにする

## 関連資料
- GitHub Issue: #316
- 前提イシュー: I185（#315・開発環境の総点検と改善）。本イシューは I185 でやった見直し・改善を繰り返し回せるようにする
- 関連: I181（#304・レビュー工程の見直し）・I174（承認待ちの集計の実例）
- 既存スキル: `.claude/skills/retro/`（イシュー単位の振り返り。本イシューは複数イシューにまたがる見直し）
- 公式機能の調査（2026-10-24・claude-code-guide で確認）:
  - `/insights`: このマシンの最近のセッション（最大 200）を分析し、使い方・うまくいかなかった点・試すとよい機能を HTML レポートにする（https://code.claude.com/docs/en/costs.md#analyze-your-usage-patterns）。サブエージェント記録・worktree ごとの記録を含むかは公式に記載なし
  - `/usage`: スキル・サブエージェント・MCP 別の利用量の割合（承認の回数・待ち時間は出ない）
  - `/fewer-permission-prompts`: 記録から読み取り専用のコマンドを拾い、`.claude/settings.json` の許可リストに追加する（https://code.claude.com/docs/en/commands.md）
  - `/doctor`: 設定・CLAUDE.md・権限・利用量を診断し修正案を出す
  - `/skill-doctor`: スキルごとのコンテキスト消費と利用回数、使われていないスキルを表示（https://code.claude.com/docs/en/skills.md#find-unused-skills）
  - 定期実行: 手元の記録やワークツリーを読めるのは Desktop scheduled tasks か、開いたままのセッションでの `/loop`。クラウドの `/schedule` は毎回リポジトリを新しく取得するため手元の記録を読めない（https://code.claude.com/docs/en/scheduled-tasks.md）
  - 記録（`~/.claude/projects/<project>/<session-id>.jsonl`）の形式は内部仕様で変わりうるため、直接読む自作スクリプトは壊れうる。公式のおすすめは `/export`・`claude -p --resume`・フックの `transcript_path`・Agent SDK（https://code.claude.com/docs/en/sessions.md）

## 背景/目的

**背景**: これまで、改善は retro（イシュー 1 件ごとの振り返り）から生まれていた。そのため、イシューをまたいで繰り返す詰まりや、工程が重くなっていくことには気づきにくかった。I185 で一度見直して改善するが、一度きりではまた同じ状態に戻る。公式にも記録の分析（`/insights`）・設定の診断（`/doctor`）・スキルの棚卸し（`/skill-doctor`）・承認の削減（`/fewer-permission-prompts`）・定期実行の機能があり、多くはそのまま使える。
**目的**: I185 でやった「見直し→改善」を、定期的に繰り返し回せるようにする。公式機能をなるべくそのまま使い、自作するのは公式に無い部分だけにする。

### 現状の問題（証拠・再現手順）
- retro はイシュー単位なので、イシューをまたいで繰り返す詰まりを拾えない（例: 承認待ちが多い問題は I174 で全記録を集計して初めて量が分かった）
- ベストプラクティスや公式機能は更新され続けるが、それに照らして開発環境を見直す工程がない
- 公式機能に無い部分がある: ①承認待ちの回数・時間を数える指標、②レビュー・修正の周回数（このリポジトリ独自の工程なので公式には無い）、③`/insights` がサブエージェント記録・ワークツリーを含むかは未確認、④公式ドキュメントの更新とこちらの設定の差分を確かめる手順

### 根本原因
イシューをまたいで工程全体を定期的に見直す仕組みがない（改善が retro 起点の個別対処だけになっている）

### 解決方針
未定・grill-me で確認（案: ①公式機能〔`/insights`・`/doctor`・`/skill-doctor`・`/fewer-permission-prompts`〕を決まった順で回す手順を作る → ②公式に無い部分〔承認の回数・周回の数・ベストプラクティスとの差分〕だけを足す → ③定期実行は Desktop scheduled tasks か `/loop` を使う → ④出てきた改善案はユーザーが採否を選び、採用分はイシューにして進める）
- 仕組みの形（runbook の手順だけで足りるか、スキルにするか）: 未定・grill-me で確認（I185 の結果と、公式機能でどこまで足りるかを見て決める）
- 承認の回数・周回の数え方: 未定・grill-me で確認（記録を直接読むと形式の変更で壊れうるため、フックの `transcript_path` や `claude -p --resume` など公式の読み方を優先して検討する。I185 で使った数え方を土台にする）
- 実行の頻度ときっかけ（一定のイシュー数ごと・定期実行・手動）: 未定・grill-me で確認
- 「詰まりの上位」とする基準・改善案を出すしきい値: 未定・grill-me で確認（I185 の結果を見て決める）

## スコープ
### 含む
- 公式機能を土台にした見直し・改善の手順づくり
- 公式に無い部分（承認の回数・周回の数え方・ベストプラクティスとの差分確認）の追加
- 実行するタイミングの決定と、定期実行の設定（公式の定期実行機能を使う）
### 含まない
- I185 の総点検と改善そのもの
- 見直しで出た改善案の実装（そのたびに別イシュー）
- 既存の起票済みイシューの棚卸し・統廃合
- 公式機能でできることの作り直し

## 受け入れ条件（Acceptance Criteria）
- [ ] 見直しの手順に、使う公式機能と順番が書かれ、各公式機能で足りない部分が何かが明記されている
- [ ] 自作した部分はすべて「公式に無い」ことが根拠つきで書かれている
- [ ] 手順を実行すると、承認の回数とレビュー・修正の周回数が、全ワークツリー＋サブエージェントの記録を対象に数えられる（`/insights` が含まない範囲は補う）
- [ ] 手順を実行すると、詰まりの上位とそれぞれの改善案（まとめる・やめる・置き換えるを含む）が出る
- [ ] 起票などの外部操作は提案までで、ユーザー承認なしには実行されない
- [ ] 実行のタイミングが workflow.md に書かれ、定期実行にする場合は公式の定期実行機能で設定されている

## 制約・引き継ぎ情報
- I185 の完了後に着手する（見直しの観点と数え方を I185 の結果から取る）
- 公式機能をなるべくそのまま使う。置き換える場合は、失うものを実証してから決める
- 回数の集計は全ワークツリー＋サブエージェントの記録まで見る（I174 の教訓）
- 定期実行はクラウドの `/schedule` では手元の記録を読めないため、Desktop scheduled tasks か `/loop` を候補にする
- 改善案は「足す」より「まとめる・やめる・置き換える」を優先して検討する。工程の削減は、回数・費用だけでなく、止めている漏れの種類と上流原因で判断する
