## レビュー観点（計画に対応）

### 1. 不変条件（1 ユーザー 1 有効セッション）
- [ ] 部分ユニーク制約 `uniq_active_quizsession_per_user` がモデルとマイグレーション `0021` にある（TC-09・TC-20）
- [ ] 開始処理が `transaction.atomic` 内でユーザー行を `select_for_update` してから、キー照合 → 既存終了 → 新規作成を行う（TC-07・TC-08・false-green 注入済み）
- [ ] `IntegrityError` が 409 に変換され、500 にならない（TC-10）

### 2. 冪等性（Idempotency-Key）
- [ ] 同じキーは 200 で同じセッション、異なるキーは後勝ちで 201、キー無しも受け付ける（TC-01〜TC-04）
- [ ] UUID でないキー（空文字含む）は 400、同じキーで科目が違えば 422、終了済みでもそのまま返す（TC-05・TC-06・TC-15）
- [ ] キーの照合が必ず `user` で絞られ、他人のセッションを返さない（TC-16）
- [ ] キーの値が応答・ログに出ない

### 3. API の締め
- [ ] `http_method_names = ['get', 'post', 'head', 'options']` で PUT/PATCH/DELETE が 405（TC-11）
- [ ] `is_active`・`started_at` が読み取り専用（TC-12）
- [ ] `permission_classes = [permissions.IsAuthenticated]`・`get_queryset` が不変更（TC-17）
- [ ] CORS 許可ヘッダに `idempotency-key` があり、許可オリジンは不変更（TC-13）

### 4. マイグレーション
- [ ] 列追加・データ・制約の 3 本に分かれ、`0020` の逆方向が noop（ロールバックは `migrate problems 0018`）
- [ ] まっさらな DB で通る（TC-21）・dev DB で通り重複が 0 件（手動 No.1〜3）
- [ ] データマイグレーションが「最新以外」だけを終了扱いにし、削除しない・終了済みの行の `ended_at` を変えない（TC-14）

### 5. フロント
- [ ] StrictMode でも開始 POST が 1 回・`Idempotency-Key` 付き（TC-30・TC-40・false-green 注入済み）
- [ ] `crypto.randomUUID` が無い環境ではヘッダ無しで送る（例外にならない）
- [ ] エラー時の挙動が現行どおり（TC-31）・既存の読み込み経路に退行なし（TC-32）
- [ ] `react-hooks/exhaustive-deps` 違反なし・型チェック合格（TC-33）

### 6. 設計品質・計画との一致

## 敵対的レビュー観点（独立サブエージェント向け・「合格を反証せよ」）
- 「同一ユーザーで有効セッションが 2 件になる経路は無い」を反証せよ: `create` 以外に `is_active=True` の行を作る・戻す経路（admin・`end` 以外のアクション・シリアライザの書き込み・シェル・シード）が残っていないか。制約違反が 500 として漏れる経路が無いか。
- 「同じキーの再送は必ず同じセッションを返す」を反証せよ: 401 後の自動再送・ヘッダの大文字小文字・UUID の別表記（波括弧・ハイフン無し）で別セッションが作られないか。ロック前の照合で取りこぼす時間差が無いか。
- 「他人に影響しない」を反証せよ: 他ユーザーのキーで 200 が返る・他ユーザーの行がロックされ続ける・他ユーザーの有効セッションが終了されるケースが無いか。
- 「マイグレーションは安全」を反証せよ: 同じ `started_at` の重複・`ended_at` が既にある有効行・ユーザー削除済みの行で、`0020` が「最新」を誤選択しないか。`0021` が dev／本番データで失敗し得る条件が残っていないか。
- 「StrictMode でも 1 回」を反証せよ: 科目の切り替え・`id` 付き URL との行き来・アンマウント中の応答で、送信漏れ（開始されない）や二重送信が起きないか。
