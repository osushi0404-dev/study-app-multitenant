# I487 修正の診断（コードレビュー F1）

## 失敗分解
- 出どころ: `docs/reviews/I487_code_review_20261113_1708.md` の止める指摘 F1（Medium・受け入れ条件 11・再現あり）
- 再現手順: 連続 7 日に届いた日 D にダッシュボードを開く（7 日の節目のお知らせが出て、記録 `streakRuns['7']` に開始日 D-6 が入る）→ 翌日 D+1、まだ解答せずにダッシュボードを開く
- 期待値: 同じ連続（D-6〜D）なので、7 日の節目のお知らせは出ない（受け入れ条件 11「連続日数は同じ連続の間に 1 回」）
- 実際値: API は `streak.current_days = 7`（今日まだ解答が無いので昨日までを数える）を返し、画面は開始日を `D+1 - 6 = D-5` と計算する。記録の D-6 と違うので、同じ連続なのにもう一度出る
- ログ: なし（判定は純粋な関数 `decideAchievements`・`frontend/src/utils/dashboardAchievements.ts`）

## 根本原因
- 裏側の連続日数（`backend/dashboard/selectors.py:97-111` の `_current_streak`）は、「今日に答えがあれば今日まで、無ければ昨日まで」の連続を数える（`:106`）
- 画面の判定は、連続の終わりを常に「今日」と決め打ちして開始日を出していた（`daysBefore(today, days - 1)`）。裏側の数え方（終わりの日が今日か昨日か）を読まずに、片方だけの前提で計算したため
- セキュリティ: 該当なし（端末の localStorage の表示用の記録だけ。認証・認可・入力・表示の逃がしに関わらない）

## 対応方針（全案＋推奨）
### 案 A（推奨）: 連続の終わりの日を、同じ応答の「今日の答えの数」で決める
- `overview.today.answered_count > 0` なら終わり = 今日、0 なら終わり = 昨日。開始日 = 終わり - (days - 1)
- 判定に使うのは「すべて」の応答（I473 F2）で、`today` も `streak` も同じ範囲（全科目）で数えた値なので、裏側の `_current_streak` と同じ規則になる
- セキュリティ影響: なし
- BP: 裏側の規則を同じ応答の値から写すだけで、API を変えない。純粋な関数のまま
- 保守性: 裏側の規則（今日が無ければ昨日）をコメントで指し示す。規則が変われば同じ関数を直す
- リスク: 端末の日付と裏側の「今日」がずれると（日付の境目・#481 の範囲）まだ 1 日ずれうる。これは日付の統一（#481）で直す範囲で、今回の指摘（同じ日付の前提での誤り）とは別
### 案 B: 開始日の比較に 1 日の幅を持たせる（記録の開始日と計算した開始日の差が 1 日以内なら同じ連続とみなす）
- 長所: 端末と裏側の日付のずれにも強い
- 短所: 「途切れてすぐ同じ節目に届いた」場合（例: 連続 7 で途切れ、1 日空けて再び 7 日）を同じ連続と取り違えうる。あいまいな規則で、次の指摘の元になる
### 案 C: API に連続の終わりの日（`streak.last_day` など）を足す
- 長所: 裏側の値をそのまま使える
- 短所: 契約（`OverviewSerializer`・`openapi.yaml`・型）を変える。本イシューの影響範囲（裏側は設定の契約の追加だけ）を広げる。案 A で同じ規則を得られるので割に合わない
### 推奨: 案 A（粗く確実・API を変えない・裏側の規則と一致）

## 影響調査
- 同型のバグ: 開始日の計算は `decideAchievements` の 1 か所だけ（`grep -n daysBefore frontend/src` で他に無い）
- 他の呼び出し: `useDashboardAchievements` だけ（「すべて」の応答を渡す）。渡す値は変えない
- 関連機能: 解答数・正答率・目標達成の判定は日付の開始日を使わないので影響なし
- テスト: TC-14 に「今日まだ解答が無い翌日」の場合を足す（今は全ケースで終わり = 今日の前提。ひな形の `today.answered_count` は 0 なので、今の TC-14 の値は終わり = 昨日として計算し直す必要がある → TC-14 のひな形で今日の答えの数を明示する）
