# I211 fix-loop 診断メモ（CI の Harness Tests の失敗）

## 失敗分解
- 再現手順: PR #357 に c5a6e875 を push → CI（run 40713387394）の Harness Tests ジョブ
- 期待値: `astral-sh/setup-uv@v10` が uv 0.13.6 を入れ、`bash scripts/claude/tests/run-all.sh` が流れる
- 実際値: ジョブが 3 秒で失敗。step は 1 つも動いていない
- ログ（要約）: 「Prepare all required actions」で `Unable to resolve action astral-sh/setup-uv@v10, unable to find version v10`

## 根本原因
- `astral-sh/setup-uv` は大きな版の目印（`v10` のような動くタグ）を出していない。`git/matching-refs/tags/v10` を見ると `v10.0.0`〜`v10.3.3` の細かい版のタグだけがある
- 計画（4-7）は既存の `actions/checkout@v4` と同じ書き方を前提にした。スパイク 8 は `action.yml` を `v10.3.2` のタグで読んだが、`v10` というタグがあるかどうかは確かめていなかった
- テスト（`test_i204_tool_sync.sh` の `ci_check`）は `uses` の名前（`@` の前）だけを見るので、存在しない版でも合格した
- セキュリティ観点: 認証・認可・インジェクション・秘密情報の露出には当たらない。動くタグが無いことは、むしろ取り込みの安全性に有利（設計レビューの Medium〔浮動タグの差し替え〕の対象が小さくなる）

## 対応方針（全案＋推奨）
| 案 | 内容 | セキュリティ | BP | 保守性 | リスク・副作用 |
|---|---|---|---|---|---|
| A（推奨） | `astral-sh/setup-uv@v10.3.3`（今の最新の細かい版のタグ）に変える。`ci_check` に「setup-uv の版は `vX.Y.Z` の細かい版」を足し、写しの `ci.yml` で `@v10` を不合格にする失敗注入を付ける | 動くタグより差し替えの余地が小さい | 配布元が出している版の付け方に合わせる。Dependabot の github-actions（既存の設定）が細かい版も上げられる | 1 行の変更とテスト 1 項目 | 小さい。版を上げるときは手で書き換える（Dependabot の後続イシューで自動化の対象） |
| B | コミットの SHA に固定（`@<40 桁>` ＋版のコメント） | いちばん強い | GitHub の推奨 | リポジトリのほかの action（`@v4`）と書き方が違う | SHA を読み違えると同じ失敗。全体の方針（SHA 固定）は design-security-review で別扱いにした |
| C | setup-uv をやめ、`pip install uv==0.13.6` を CI に書く | PyPI から版指定 | 公式の action を使わない | `required-version` と CI の版が 2 か所になる | install を 0 個にする決まり（AC5）と食い違う |

推奨は A。粗く確実で、配布元の版の付け方どおり。SHA 固定（B）はリポジトリ全体の方針として残余リスクのまま retro で扱う。

## 影響調査
- 同型のバグ: リポジトリのほかの `uses`（`.github/workflows/*.yml`）は `actions/*@v4`・`actions/setup-python@v5`・`pre-commit/action@v3.0.1` で、どれも今日まで CI が動いている（動くタグがある・細かい版を書いている）。今回足した `astral-sh/setup-uv` だけが対象
- ほかの呼び出し箇所: 計画書 4-7・runbook には `@v10` を書いていない（計画書 4-7 のコード例だけ）。計画書のコード例も直す
- 関連機能への波及: なし（ほかのジョブは変えていない）
