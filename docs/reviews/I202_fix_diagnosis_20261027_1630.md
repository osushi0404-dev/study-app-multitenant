# I202 fix-loop 診断メモ（review-gate 1 周目の止める指摘 F2）

- 対象の記録: `docs/reviews/I202_code_review_20261027_1615.md`（REVIEWED_COMMIT 05b2dce）
- 止める指摘: F2（High・harness・STOP=flow・再現あり）。ほかの F1・F3〜F10 は止めない指摘（台帳に残り retro が後続へ回す。ここでは直さない）

## 失敗分解
- 再現手順: 1 周目でアプリのファイル `backend/x.py` に再現つきの High が付く。fix-loop が、その変更を取り消して `backend/x.py` を origin/develop と同じ中身に戻し、コミットする。review-gate の 2 周目（差分のレビュー）を流す
- 期待値: レビュー役が呼ばれ、戻した差分を見て F1 を resolved と書ける。台帳の F1 が resolved になり、OK に進める
- 実際値: `branch_own_files`（merge-base から HEAD でブランチが変えたファイル）から `backend/x.py` が外れる。そのため `delta_files`（ブランチが変えたファイル ∩ 起点の後に変わったファイル）が空になる。I202 で足した `NO_DELTA=1`（範囲が空ならレビュー役を呼ばない）に当たり、台帳がそのまま引き継がれる。F1 は open のまま残って HIGH になり、何度やり直しても同じ（流れが進まない）
- ログ: 記録の F2 の再現の欄のとおり（`scripts/claude/code-review.sh:877` 付近の NO_DELTA の判定）

## 根本原因
`NO_DELTA` の判定に、「レビューの対象の範囲」（`delta_files`）をそのまま使った。`delta_files` は、ブランチが変えた行の範囲を決めるための集合で、「起点の後に直したものがあるか」を表していない。変更を取り消す直し・ファイルを消す直しは、ブランチが変えたファイルから外れるので、直したのに範囲が空に見える。

I202 より前は、範囲が空でもレビュー役を呼んでいた。そのため、取り消しの直しでもレビュー役がファイルを読んで resolved と書けた（GIT_DIFF は「変えたファイルは無い」になる不便は前からある）。I202 の変更で、この経路が塞がれた（後退）。

セキュリティの観点: 認証・認可・機密データには関係しない（ハーネスの流れの判定）。止める側への崩れ（止まり続ける）で、見逃しの向きではない。

## 対応方針（全案＋推奨）
- 案 A（推奨）: `NO_DELTA` の判定を「起点から HEAD までに、記録の場所の外のファイルが 1 つも変わっていない」に変える（既にある `changed_outside_records "$SINCE" HEAD` をそのまま使う。0 なら NO_DELTA）。取り消し・削除の直しは記録の場所の外の変更なので、レビュー役が呼ばれる。あわせて、範囲（`delta_files`）が空でも記録の場所の外が変わっているときは、レビュー役への `git diff` に、その変わったファイルの起点からの差分を載せる（取り消しの差分を見せる。前からの不便も同時に解消）
  - セキュリティ影響: なし。BP: 既にある関数の再利用で、新しい判定を足さない
  - 保守性: NO_DELTA の意味が「直したものが無い」と一致する
  - リスク・副作用: 数行の変更。範囲の集合（行の塊・台帳の SCOPE）には触れないので、止める判定は変わらない
- 案 B: NO_DELTA（空の範囲でレビュー役を呼ばない）をやめて、I202 の前の形に戻す
  - メリット: いちばん小さい・確実
  - デメリット: 計画 4.0 で「直す」とした共通化の 3 つ目（空の範囲で claude を呼ばない）を取り下げることになる。取り消しの差分がレビュー役に見えない不便も残る
- 案 C: `delta_files` に「ブランチが変えたファイルから外れたもの（起点の後に変わり、今は develop と同じ）」を足す
  - デメリット: 範囲の集合を変えるので、行の塊・SCOPE の判定に波及する。新しい判定のコードが増える

推奨は案 A。理由: 既にある関数で NO_DELTA の意味を正し、範囲の判定に触れずに済む。取り消しの差分もレビュー役に見えるようになる。

## 影響調査
- 同型のバグ: `delta_files` を「直したものがあるか」の意味で使っている箇所を探した。NO_DELTA の判定（`code-review.sh:877`）と、GIT_DIFF の組み立て（`code-review.sh:868-873`、範囲が空なら「変えたファイルは無い」と書く）の 2 か所。どちらも案 A で直す
- ほかの呼び出し箇所: `delta_files` は `delta_hunks` の対象のファイル（行の塊）にも使う。取り消したファイルには、ブランチが変えた行が無いので、塊に入らないのが正しい（変えない）
- 関連機能: `gate-check.sh` の「レビューの後の変更」の判定は、REVIEWED_COMMIT と HEAD の中身の比較で、`delta_files` を使っていない（影響なし）
- テスト: `test_i202_ledger_cleanup.sh` の W4（記録の場所だけを変えた→呼ばない）は案 A でも同じ結果。取り消しの直しで呼ばれることを確かめる項目（W4b）と、その失敗注入を足す
