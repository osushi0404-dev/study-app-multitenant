# I179 fix-loop 診断メモ（2026-10-21・5 回目）

起点: 6 回目の `/code-review I179` の敵対的レビュー第 10 周（`docs/reviews/I179_adversarial_review_20261021_1719.md`）。第 10 周の途中でセッションが落ち、再開後に原因が I179 のガード自身だと特定した。作業フォルダの扱いで同じ種類の指摘が 5 回目のため、「同種の指摘が繰り返されたら粗い fail-closed に倒す」方針（精密化をやめる）で根治する。対象コミット 9b0b947（実装は 4e7b815）。

## 1. 失敗分解

再現の共通手順: ガードに `{"tool_name":"Bash","tool_input":{"command":"<入力>"},"cwd":"<作業フォルダ>"}` を stdin で渡す（判定だけでコマンドは実行されない）。①は使い捨て repo（primary `P`・入れ子 `P/.claude/worktrees/{nest,nest2}`・兄弟 `SIB`）で実測。

### C1（Critical）移動先の数に対して処理量が指数的に増え、異常終了で全検査が素通りになる
- 再現: cwd=/mnt/c/app/wt-harness、`ulimit -v 1048576`・`timeout 20` を付けて、入力 `cd d1; …; cd dN; rm -r x`
- 期待値: N によらず 1 秒未満で判定（exit 0 か 2）
- 実際値: N=1 で 0.69 秒、N=2 で 20 秒の打ち切り、N≥3 で `MemoryError`（`_bash_destroy_targets` → `tgt` → `_abs_in` → `normpath`、`pretooluse_guard.py:645`）。上限なしでは WSL のメモリを使い切る。第 10 周②のエージェントが N=6 で強制終了（exit 137）し、セッションごと落ちた。
- 二次被害: 公式の仕様では、PreToolUse フックは exit 2 だけがブロックで、それ以外の異常終了（例外の exit 1・タイムアウト）は**ブロックしない**。`main()` はこの検査（:1605）の後で、強制 push・保護ブランチへの push・`git reset --hard`・`rm -rf`・Docker のデータ削除・危険な SQL を検査している。そのため `cd a && cd b && cd c && git push --force` のような形では、それらの検査がすべて素通りになる。
- 影響範囲: 問題のコードは I179 のブランチにだけあり、develop/main には無い（`git grep _bash_destroy_targets origin/develop` が空）。今回の被害は、セッションが落ちたことだけ（作業ツリー・コミットは無事）。

### H1（High・fix-loop 4 回目の後退）`..` を含む移動先の基準がずれて別ワークツリーへの破棄が通る
- 入力（cwd=nest）: `cd backend && pytest; cd -; cd ../nest2 && git checkout -- .`・`pushd backend && pytest && popd && cd ../nest2 && git checkout -- .`・`git -C backend log -1 && cd ../nest2 && rm -r src`。（cwd=primary）: `git -C backend status && cd ../SIB && git checkout -- .`・`cd frontend && npm run build && cd ~- && cd ../SIB && git checkout -- .`
- 期待値: exit 2（4e7b815^ では 2）／ 実際値: exit 0。実際に実行し、nest2 の未コミット変更が消えることを確認済み（①）。再開前のセッションでも同じ 3 形を再現した。

### M1（Medium・止めすぎ）・L1（Low・止めすぎ）
- M1: `cp -t backend .claude/worktrees/nest/backend/a`（別ワークツリーから自分へのコピー）が止まる（`-t` なしなら通る）。
- L1: 入れ子のセッションで `cd ~+/backend && cd .. && git add -A` が止まる。

## 2. 根本原因

- **C1**: fix-loop 3 回目（78985fe）で、作業フォルダを順に追う方式をやめた。代わりに「すべての移動先をすべての候補に当て、候補が増えなくなるまでまわす（上限 8 回）」和集合の方式にした。ところが `..` を含まない相対の移動先は、自分が作った候補にも当たり続ける（`d1` → `d1/d1` → …）。そのため候補は増え続けて止まらず、移動先の数が増えると組み合わせで爆発する。候補の数と処理時間の上限が無く、ガード全体を例外から守る仕組みも無かった（異常終了は「止めない」側に倒れる）。テストは短いコマンドだけで、移動先が多い入力の処理時間を確かめる TC が無かった。
- **H1**: fix-loop 4 回目（4e7b815）で、`..` の止めすぎ（第 9 周 F1）を直した。そのとき、「書いた順に追った直前の位置」（`lin`）という、シェルの動きの部分的な再現を足した。しかし `cd -`・`popd`・`~-`・`-C` 系を正しく追えず、再現漏れの抜け道になった。`..` の解釈は書いた順に依存する（`cd backend && cd ..` と `cd .. && cd backend` は行き先が違う）。一方、`_loose_segments` は区切り（`&&`・`;`・`|`・`&`・括弧）を捨てていて、順番を正しく再現する材料が無い。
- **共通の根**: 第 1 周から続く「コマンドの文字列からシェルの作業フォルダの動きを再現する」方式の限界。5 回目の同じ種類の指摘であり、精密化を重ねるほど抜け道（H1）か副作用（C1）が出る。
- **セキュリティ観点**: C1 は防御機構の可用性の欠陥（異常終了で fail-open。OWASP A04 安全でない設計／A05 設定の不備に相当）。巨大な入力でガードを落とせば、危険操作の検査をまとめて外せる。H1 は過失による他ワークツリーの作業消失（A01 相当）。アプリの認証・認可・XSS・インジェクション・機密データの露出には該当しない。

## 3. 対応方針（全案＋推奨）

すべての案に共通: **ガードの例外を fail-closed にする**。`main()` の `_bash_destroy_targets` 以降の判定で例外が出たら、exit 2 で止める（理由を表示する）。

### 案 A（推奨）: 移動の連鎖は解釈しない。判定できない形は「分けて実行」で止める（粗い fail-closed）
1. 基準の候補は「セッションの作業フォルダ」と「各移動先をセッションの作業フォルダ基準で 1 回だけ解いたもの」に限る。重ねがけはせず、増えなくなるまでまわすループと `lin` は削除する。候補の数は移動先の数＋1 以下になる（処理量は線形）。
2. 次のどれかに当たるコマンドを「作業フォルダを判定できない」とする。
   - 移動先が 2 つ以上あり、そのうち 1 つでも相対パスがある（`cd a && cd b`・`git -C backend … && cd ../x` 等）
   - `cd -`・`popd`・引数なしの `pushd` を含む
   - 移動先か対象のパスに `~+`・`~-` を含む

   このときは、相対パスの削除・書込と、読み取り以外の git 操作をすべて止める。メッセージは「`cd` 等を複数含むコマンドでは宛先を判定できない。Bash 呼び出しを分けるか、絶対パスで書く」。絶対パスの対象は従来どおり判定する。`DANGER_OK=1` でも解除しない（既存の別ワークツリー判定と同じ）。
3. 移動先が 1 つ（`cd backend && rm -r build`・`cd ../nest2 && rm -r src`・`git -C <入れ子> reset --hard`）や移動先が絶対パスだけの形は、従来どおり正確に判定する（止める／通すは変わらない）。

- 効果: C1・H1・L1 が同時に消える（シェルの動きを再現しないので再現漏れが無く、処理量の上限が構造的に決まる）。
- 副作用（止めすぎ）: 移動を 2 回以上含むコマンドの中の、相対パスの削除・書込・git の変更が止まる。これには第 9 周 F1 で通すようにした `cd backend && cd .. && git add -A` も含む（入れ子のセッション）。回避は、Bash 呼び出しを分けること（Bash の作業フォルダは呼び出しをまたいで保たれる）か、絶対パスで書くこと。メッセージで案内し、§9 に明記する。読み取りやテスト（`cd backend && cd .. && pytest`）は止まらない。
- セキュリティ: 普通の書き方の事故はすべて止まる側に倒れる（fail-closed）。異常終了でも止まる。ベストプラクティス: 公式の Bash 権限ルールの考え方（複合コマンドは粗く扱い、確実な境界は別の仕組み）と整合。保守性: コードが減る（ループ・`lin`・`~±` の置換を削除）。リスク: 上の止めすぎだけ（回避が容易）。

### 案 B: 区切りを保つように `_loose_segments` を作り直し、作業フォルダを書いた順に正確にたどる
- `&&`・`;` で確定、`||`・`|`・`&`・括弧では「動いたかもしれない」として和集合をとる。`cd -`・`pushd`/`popd` のスタックも再現する。
- 止めすぎは最も少ない。ただし第 8 周で順を追う方式をやめた理由（再現漏れ）そのものに戻る。5 回目の同じ種類の指摘で、精密化を重ねると次の抜け道が見つかる構図が続く（fix-loop を過剰にしない運用）。→ 採らない。

### 案 C: 今の和集合を残し、上限（候補 64 件・各移動先は 1 本の連鎖で 1 回まで）を付け、`..` は 4e7b815 より前と同じく全候補に当てる
- C1・H1 は直る。ただし第 9 周 F1 の止めすぎは案 A と同じく戻る。そのうえ、移動先の組み合わせを数える分だけ案 A より複雑で、上限を超えたときの扱いも別に必要になる。→ 採らない（同じ止めすぎで、案 A より複雑）。

### 案 D: 相対パス・`cd` 越しの判定を I179 から外す（develop と同じく絶対パスだけを見る）
- 単純で確実。ただし、公式の配置では別ワークツリーが primary の中（入れ子）にある。そのため `rm -r .claude/worktrees/x`・`git clean -ffdx` のような普通の事故を防げず、計画変更記録 5 の目的を失う。→ 採らない。

### 推奨: 案 A（＋共通の例外 fail-closed）

### 対応範囲
- 対応: C1（Critical）・H1（High）。L1 は案 A で同時に解消する。
- 見送り: M1（Medium・`cp -t` で移動元も宛先とみなす止めすぎ）。fix-loop 4 回目に「どれが宛先かを解析しない」と決めた粗さの結果で、回避（`-t` を使わない）が容易。直結する High が無いため対象外とし、§9 の既知の止めすぎに追記する。

### NG の分類と再承認
- **C1: (b) 方針の誤り**（和集合の候補集めに上限が無い設計）。**H1: (b) 方針の誤り**（順を追う部分的な再現）。いずれも新方針のため、手順4 でユーザー承認を得る。

## 4. 影響調査

- **同型バグ**（上限の無い処理・異常終了で素通り）:
  - `_bash_destroy_targets` の候補集め（:619）が唯一の「増えなくなるまでまわす」処理。
  - `_docker_volume_wipe_tokens` は `depth` 引数で再帰に上限がある（:245）。
  - gh の解析は `_GH_SCAN_MAX=200` で上限がある（:890）。
  - 例外の素通りはガード全体の問題だが、ほかの判定には入力の大きさで爆発する処理が無い。そのため、例外の fail-closed は `_bash_destroy_targets` 以降の判定を対象にする。`main()` 全体を包む案は、develop にある既存の判定の挙動（読み込み失敗時など）まで変えるため、I179 の範囲外とする。
- **他の呼び出し箇所**: `_bash_destroy_targets` は `main()` の 1 か所だけ。`_moves_in`・`_head_candidates` は `_bash_destroy_targets` からだけ呼ばれる。
- **関連機能への波及**:
  - 正規の手順は、移動先が 1 つか、移動を含まない。具体的には `/close` の `git mv`・sed、`/issue-bootstrap` の cp、§11 の cp、`git worktree add/prune/repair`、`wt-remove.sh`、`cd backend && …`。そのため止まらない（実装後に既存の TC で確かめる）。
  - 第 9 周 F1 の TC（`cd backend && cd .. && git add -A` 等を通す側）は、止める側に変わる（案 A の副作用として TC を書き換える）。
  - 第 10 周①の 5 形と、移動先を 10 個並べた入力の処理時間（1 秒未満）、例外時の exit 2 を、止める側・処理量の TC として足す。
- **既存の I179 以外のガード**（`_bash_write_targets`・push・reset・Docker 等）のコードは変えない。
