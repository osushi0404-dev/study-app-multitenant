## 2. 根本原因

### 3-1（および Medium「合格 = exit 0 原則との食い違い」）
第 2 周で TC-AUTO-06/07 の合否方式を「`!` 付きで exit 0＝合格」から「exit 1 のみ合格」へ反転させた。だが、その方式を参照する記述（冒頭の原則 7〜8 行、TC 一覧、TC 本文の false-green 根拠、2026-08-24 の実施記録、手動 No.1 の期待結果、計画書 §7・テスト方針）を**横断して掃き出さず、局所的に書き換えた**。合否方式が文書中の各所に散らばって書かれていて、**唯一の正（SSOT）が無い**ことが構造的な原因である。第 1・2 周の High（revert 記述の取り残し・7→9 モジュールの取り残し）も同じ型で、是正のたびに取り残しが新たな指摘を生んでいた。

### 3-2
`docker compose --profile e2e run --rm e2e` は、依存サービス `e2e-init` のイメージが既にあれば作り直さない。`e2e-init` は `./backend` をボリュームでマウントするため**コードは最新**になるが、**インストール済みのライブラリはイメージ作成時のまま**（Django 4.2.7）になる。TC-AUTO-13 にはビルド手順も、イメージの中身を確かめる判定も無かった。さらに `e2e-init` は既定の DB 名（開発用 DB `learning_app`）へ migrate するので、TC 本文の「まっさらな DB への migrate を同時に担保」は **CI（毎回新しいランナー）でだけ**成り立つ。記録上の合格は CI 実行（毎回ビルド）であり、CI ログ（run 32651105381）で `7 passed`・flaky 0 件・retry 0 件を確認済みのため、**実害は無い**。

### Medium 群
- E2E `retries: 2`: Playwright は再試行で通ったテストを flaky とし、既定では exit 0 にする。TC は exit 0 しか見ていない。
- TC-AUTO-16: 「2 段目＝pytest 単独」を照合する判定が無い（判定 2 は件名だけを見る）。
- I155: AnonymousUser の削除で `UserSettings` 1 行・`StudyStreak` 1 行が CASCADE で連鎖削除される（Collector による読み取り専用の試算で確認）。バックアップ・AC・Danger Ops・ロールバックは 2 テーブル前提のまま。
- §8 の branch protection 一時解除: 元へ戻す手順・期限・復元確認が無い。なお、`gh api repos/.../branches/develop` で**保護の要約（必須チェック 5 件・`enforcement_level: everyone`）は bot でも読める**ことを確認した（設定変更 API は admin 権限が要るが、読み取りは可能）。

### セキュリティ観点
変更対象は記録文書（テスト記録・計画書・イシュー本文）だけで、アプリコード・設定・依存には触れない。認証・認可・インジェクション・XSS・機密データ露出のいずれにも該当しない。§8 の保護一時解除に「元へ戻す手順と機械確認」を足すのは、防御（必須チェック・管理者への適用）を外したまま放置される事態を防ぐもので、セキュリティを強める方向である。I155 の範囲是正は、不可逆な削除の対象をバックアップ・承認の範囲と一致させるもの。

## 3. 対応方針（全案＋推奨）

### 案 1（推奨）: 合否方式を SSOT 化して横断是正＋各 Medium を根治
1. **SSOT 化**: auto_test の TC 一覧に「合格条件」列を追加し、TC ごとに「exit 0」か「exit 1」かを 1 か所で定義する。冒頭の原則 7〜8 行を「合格条件は TC 一覧の『合格条件』列に従う（既定 exit 0・TC-06/07 のみ exit 1）」へ改める。
2. **横断掃き出し**: `grep -n 'exit 0\|exit 1\|非ゼロ'` で TC-06/07 に関わる全記述（TC 本文 181・194 行、実施記録 2026-08-24 行、false-green 表、手動 No.1、計画書 §7・テスト方針）を洗い出して一括で直す。是正後にもう一度 grep し、取り残しが 0 件であることを確かめる。
3. **TC-AUTO-13**: 準備に `docker compose --profile e2e build e2e-init` を加え、判定 0（`e2e-init` イメージの Django が 5.2.17）を追加する。「まっさらな DB への migrate」は CI の場合に限ると明記する。flaky 対策として、ローカル実行に `npx playwright test --fail-on-flaky-tests` を使い、CI 記録の判定として「flaky 0・retry 0」を CI ログから確かめる手順を加える（CI 設定 `e2e.yml` は I151 の範囲外のため変えない）。
4. **TC-AUTO-16**: 2 段目のコミットの変更ファイルと差分行を照合する判定を追加する（変更ファイルは `requirements-dev.txt` だけ／変更行は `-pytest==8.3.4` と `+pytest==9.0.3` の 2 行だけ）。
5. **I155**: 削除対象に `UserSettings` 1・`StudyStreak` 1 を明記し、バックアップ・AC・影響範囲・Danger Ops・ロールバックを「2 テーブル＋残置データ一式」へ広げる。GitHub #272 の本文を同期する。
6. **§8**: 一時解除の範囲（`Backend Lint & Security` の必須指定のみ）、期限（当該 PR のマージ直後）、復元確認（`gh api .../branches/develop` で必須チェック 5 件・`enforcement_level: everyone` を確認）を明記する。
7. **Low**: イシュー本文のロールバック項に I152 依存を追記（#267 も同期）。TC-15 注記の参照先消失を修正。PBKDF2 反復回数の引き上げ（次回ログイン時の再ハッシュ）をリスク表に記載する。

- メリット: 取り残しの構造的原因（SSOT 不在）を断つ。第 3 周の High・Medium をすべて解消する。
- デメリット: 変更箇所が多い。ただし対象は記録文書だけ。
- セキュリティ影響: なし（§8・I155 は防御を強める方向）。
- ベストプラクティス: テスト仕様の合否基準を 1 か所で定義するのは、テスト設計の標準的な形。
- リスク: 書き換えで新たな取り残しが生じる → 是正後の横断 grep を手順 6 の確認に含める。

### 案 2: 指摘された行だけを局所修正する
- メリット: 変更が最小。
- デメリット: 第 1〜3 周で毎回同じ型（局所修正による取り残し）の High を再生産した原因そのもの。不採用。

### 案 3: TC-06/07 を「exit 0＝合格」の方式へ戻す（`!` を復活）
- メリット: 例外が無くなり、原則が単純になる。
- デメリット: 第 2 周で実証した欠陥（実行エラーの exit 128 が `!` で合格に反転する）が戻る。代わりに `test -z "$(git grep ...)"` 形式にしても、エラー時は出力が空になり合格する。不採用。

### 推奨
