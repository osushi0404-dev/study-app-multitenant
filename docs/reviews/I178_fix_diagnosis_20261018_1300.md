## 2. 根本原因

**原因の概要**: 「文書の正しさ」を、文書の一部を拾って確かめるテストで守ろうとしたため、拾っていない部分が毎周の穴になった。加えて、I178 専用の確認手順（承認後・マージ前に行う確認）を、汎用の /close の流れ（承認とマージを一度に依頼する）に後から差し込んだため、両者の順番の約束がどこにも書かれていなかった。

**詳細**:

1. **H1（部分検証の繰り返し）**: 第 1 周は「文言がどこかにある」、第 2 周は「行が節内にある」、第 3 周は「5 つの節が全文一致する」と、毎回検証する範囲を広げてきた。しかし runbook の中で人が読んで操作する部分（概要・§1.5・§3 の全ステップ・§4〜§6）は、どれも設定を誤らせ得る。範囲を列挙する方式である限り、列挙から漏れた節・同じ見出しの重複・節の外の矛盾が、次の周の穴になる。runbook は「レビューで内容が確定した設定の契約書」なので、守るべきは「確定した内容から黙って変わらないこと」であり、部分の列挙ではない。
2. **H2・M1・M3（流れの約束の欠落）**: 第 2 周で No.8（記録コミットで承認取り消しを確かめる）を足したとき、「No.5 では承認だけを押し、マージは No.8 の後」という順番の約束を、手動テスト文書・runbook・/close のどこにも書かなかった。/close step 6 は「Approve & Merge を依頼」と書かれており、test_i178 がその文言を固定しているので、I178 の流れの側からも変えられない状態だった。失敗した場合の分岐（No.6 が成功してしまう・マージ後の確認が NG）も同じく未定義だった。
3. **M2**: No.6 の対象 PR（#298・develop 宛て）と、見直す設定画面（No.1＝develop）の対応を取り違えた記述ミス。

### セキュリティ観点

- H1 は、runbook が誤った設定手順に書き換えられても検知できないこと。人が runbook どおりに設定すると、承認者の限定や push 制限が外れ、bot・外部 PR のマージを GitHub が止めない状態に戻り得る（認可の後退）。
- H2 は、bot のマージ拒否（攻撃シナリオ 1）と承認取り消し（攻撃シナリオ 3）の実地確認が行われないまま完了すること。設定ミスがあっても気づけない。
- L5 の宛先ブランチ変更は、Dismiss stale の効かない経路があり得るという設計上の残余で、実機確認が必要。マージは `oshui0404` の操作であるため既知 (4)（差分を見ない承認）に近い。

## 3. 対応方針（全案＋推奨）

### H1 の案

#### 案 A（推奨）: runbook 全体を「確定版」として固定し、変更を検知する＋既存の節の全文比較を残す

- test_i178 に、runbook 全体の SHA-256 を期待値として持たせ、一致しなければ NG にする。NG 時は「runbook が変わった。内容をレビューし、計画書 5-5 と test_i178 の節の期待値を確かめてから、ハッシュを更新すること」と表示する。
- 既存の 5 節の全文比較は残す（どの節が変わったかの差分表示と、設定値の意味の確認のため）。あわせて、節の開始見出しがファイル内に 1 回だけであることを確かめる（同じ見出しの重複を検知）。
- close SKILL は他のイシューでも頻繁に変わるため、ファイル全体の固定はしない。step 5.5〜6 の全文比較に加え、step 6 の見出し行が 1 回だけであることを確かめる。
- メリット: runbook のどこを変えても必ず検知され、範囲の列挙漏れが原理的に無くなる（第 3 周の F・G・A と Medium の B・D・H がすべて NG になる）。仕組みが単純。
- デメリット: runbook を正当に直すたびにハッシュの更新が要る（保守の手間が 1 行分増える）。ハッシュの一致は「レビュー済みの内容から変わっていない」ことの確認で、内容の正しさそのものは、更新時のレビューと節の全文比較が担う。
- セキュリティ: 認可設定の手順書が黙って緩められる経路を塞ぐ。OWASP の「セキュリティ設定ミス」への予防として妥当。
- 保守性: 期待値は 1 か所（ハッシュ値）。誰がいつ変えたかは git の履歴に残る。

#### 案 B: 比較する節を増やす（ステップ 1〜5・概要・§1.5・§4〜§6）＋見出しの重複検知

- メリット: どの節のどこが変わったかを差分で示せる。
- デメリット: 実質的に runbook のほぼ全文を期待値としてスクリプトに二重に持つことになり、保守の手間は案 A より大きい。列挙方式のため、新しい節を足したときの漏れが再発し得る（今回の根本原因そのもの）。

#### 案 C: runbook の設定部分を 1 つの設定ファイル（YAML 等）から生成する

- メリット: 設定の正本が 1 つになり、文書とテストの二重管理が無くなる。
- デメリット: 文書生成の仕組みを新たに作ることになり、要件規模に対して過剰。I178 の範囲を大きく超える。

### H2・M1〜M4・Low の対応（案は 1 つ・ほかに妥当な選択肢が無いもの）

- **H2**:
  - 手動テスト No.5 と「実施の順番」に「No.5 では **Approve だけを押し、Merge は押さない**。マージは No.8 の後の再承認の後」と明記する。
  - runbook 確認 6 の手順 3 にある「その後 oshui0404 がマージする」を、「マージは手動テストの流れ（承認取り消しの確認の後）に従う」へ変える。
  - /close step 6 に一般的な一文を足す: 「手動テスト文書に、承認の後・マージの前に行う確認がある場合は、まず承認だけを依頼し、その確認を終えてからマージを依頼する」。test_i178 の close step 6 の期待値も同時に更新する。
- **M1**: No.6 の備考に分岐を追加する。マージが成功してしまった場合は、develop の設定（No.1）を直す。No.4〜6 の記録と No.8 の代わりの確認（別の確認用 PR で承認後に push して取り消しを確かめる）は、マージ後の記録用 PR で行う。
- **M2**: No.6 の備考の「No.2 を見直す」を「No.1（develop）を見直す」に直す。
- **M3**: 記録用 PR（`docs(I178): マージ後確認の記録`）の対象に No.8 の結果を加える。#298 には No.4〜No.6 の結果だけをコミットする（それが No.8 の操作になる）。
- **M4**: 記録用 PR の対象に、レビュー文書の AC 判定表（AC-2・AC-4・AC-5）を加える。No.7 または TC-17 が NG の場合は、Issue #297 を開き直し、原因を調べて修正する（設定の誤りならユーザーが設定画面で直す。文書の誤りなら新しい PR で直す）。これを手動テスト文書と計画書ステップ 5 に書く。
- **L1**: 手動テストの前提を「TC-01〜TC-19（マージ後に行う TC-17 を除く）」に直す。runbook 確認 5 の close を `gh pr close <PR番号> --delete-branch` にそろえる。

- **L3**: runbook 確認 6 の手順 2 に「実行前に `oshui0404` の了承を得る」を加える。
- **L4**: 合否判定は、`message` から URL（`http` で始まる部分）を除いてから行い、HTTP ステータスも一緒に記録する。
- **L5（宛先ブランチ変更で承認が残る可能性）**: 実機確認が必要で、マージはユーザーの操作のため、**/retro へ送る**（I178 では runbook §1.5 の Dismiss stale の説明に「宛先ブランチの変更では取り消されない可能性がある（未確認）」と 1 行だけ書く）。
- **Medium（close SKILL の step 5.5〜6 の外に矛盾する文を足す・第 3 周 E）**: close SKILL は他のイシューでも変わるため全体は固定しない。step 6 の見出しが 1 回だけであることの確認で一部を補い、残りは残余として記録する。

### 推奨

H1 は **案 A**。H2・M1〜M4・L1〜L4 は上の対応をそのまま行い、L5 は /retro へ送る。

理由: 案 A は、今回の根本原因（範囲の列挙による漏れ）を構造的に無くす唯一の案で、仕組みも最も単純。保守の手間（ハッシュ更新）は、runbook が「認可設定の契約書」である以上、変更時のレビューを強制する効果として妥当。
