# I223 fix 診断メモ（20261105_1420）

## 失敗分解
- 対象: review-gate の記録 `docs/reviews/I223_code_review_20261105_1353.md` の「止める指摘」F1（SEV=Medium・STOP=ac:8・REPRO=yes・SECURITY=yes・FILE=scripts/claude/tui-capture.sh）
- 再現手順: `bash scripts/claude/tui-capture.sh '<入力>' '{Enter}'` で起こした対話のセッション（tmux の中の `claude --permission-mode manual`）が `gh issue comment …` などを Bash で実行する
- 期待値: テスト用のセッションなので、GitHub へは読み取りだけの鍵（`GH_APP_READONLY=1`）が渡り、書き込みは GitHub が拒否する（受け入れ条件 6）
- 実際値: `tui-capture.sh:44` の `tmux new-session -d -s "$S" -x 200 -y 50 -c "$ROOT" "claude --permission-mode manual"` は指定を付けないので、中の `gh` は書き込みの鍵を受け取る。tmux のセッションは tmux サーバーの環境で起きるので、呼び出し側で前置きしても、サーバーが先に起きていると届かない
- ログ: 記録の FINDING F1 の行。静的なテスト G6 は `claude -p` の形しか見ないので、この起動を見落とした

## 根本原因
- 計画の調査（「テスト用のセッションを起こす所」）と計画変更記録 3 の grep が、`claude -p` の形だけを数えていた。対話の画面を確かめるため tmux の中で `claude` を起こす入口（I195 の `tui-capture.sh`）も、テスト用のセッションを起こす所だった
- G6 の検査の対象も `claude -p` の形だけだった
- セキュリティ観点: 書き込みの鍵がテスト用のセッションに渡る＝作り話の入力で本物の書き込みが起きうる（受け入れ条件 6 の未達）。認証・インジェクション・XSS の話ではない。最後の守りは GitHub の権限（App は develop・main に push・マージできない）

## 対応方針（全案＋推奨）
- **案 A（推奨）: `tmux new-session` に `-e GH_APP_READONLY=1` を付ける**（tmux 3.0 から。手元は 3.4。CI の Harness Tests は偽の tmux で起動のログを見る）
  - セキュリティ: 新しいセッションの環境に必ず入る（サーバーの環境に関係なく、tmux が子のプロセスに渡す）
  - BP: tmux の公式の指定。起動のコマンドの文字列（`"claude --permission-mode manual"`）は変わらないので、`test_tui_capture.sh` の失敗の注入（148 行目・その文字列を書き換える）はそのまま効く
  - 保守性: 1 か所の変更。`test_tui_capture.sh:68` の期待する起動の行（偽の tmux の記録）に `-e GH_APP_READONLY=1` を足す
  - リスク: tmux が 3.0 より古いと `-e` を知らずに起動に失敗する（失敗は「起動できない」で止まる側＝fail-closed）
- 案 B: 起動のコマンドを `"env GH_APP_READONLY=1 claude --permission-mode manual"` にする
  - セキュリティ: A と同じく確実
  - BP・保守性: 起動のコマンドの文字列が変わり、`test_tui_capture.sh` の 68 行目・148 行目（失敗の注入の書き換え前の文字列）・122〜123 行目の確かめを作り直すことになる
- 案 C: `tui-capture.sh` の冒頭で `export GH_APP_READONLY=1` するだけ
  - tmux サーバーが先に起きていると、サーバーの環境で起きるので届かない（tmux は `update-environment` に無い変数を新しいセッションに渡さない）。不確実なので採らない
- G6 の広げ方（どの案でも）: `tmux new-session` の行に `claude` があるとき、同じ論理行に `GH_APP_READONLY=1` を要求する（今の `claude -p` の検査と同じ粗い規則。精密なシェルの解析はしない）。FG: `tui-capture.sh` の写しから `-e GH_APP_READONLY=1 ` を消すと G6 が不合格
- 推奨: **案 A＋G6 の広げ方**

## 影響調査の実施有無と結果
- 実施した。テスト用・検証用のセッションを起こす所を、`claude -p` 以外の形も含めて探した: `grep -rnE '(^|[^-])\bclaude\b +(--|-p|"|$)|new-session' scripts/claude --include=*.sh`（コメントとテストを除く）
  - `scripts/claude/tui-capture.sh:44`（今回）だけが、`claude -p` の形でない起動
  - ほかの起動はすべて `claude -p`（計画変更記録 3 で 6 か所に付けた・G6 が見ている）
  - `scripts/claude/hooks/` は claude を起こさない
- 他の呼び出し箇所: `tui-capture.sh` を使う手順（`plan-writing-rules.md` の「対話画面の判定」・`frontend-verify.md` 以外の手順書）は、スクリプトを通して使うので、スクリプトを直せば全部に効く
- 関連機能: `test_tui_capture.sh` の起動の行の照合（68 行目）を直す。122〜123 行目（`claude --permission-mode manual` を含む）と 148 行目（失敗の注入）は案 A では変わらない
