## 2. 根本原因

### 2-1. Python コードを正規表現で判定していること（#1〜#5・#9・#11 の大半）
- `manage.py shell` / `python -c` / ヒアドキュメント / 実行ファイルの Python コードを、`_CODE_DANGER` / `_CODE_EXTERNAL` の正規表現で判定している。正規表現は、改行・空白・変数名・呼び出しの形（チェーン、関連マネージャ、ループ、キーワード引数）の揺れに弱く、誤検知を避けるために条件を絞ると見逃しが出て、広げると誤検知が出る（第 2 周の `[^;\n]*?` の修正が #3 を生んだのが典型）。
- さらに、compose の許可リストでは「危険・外部送信の列挙に当たらなければコードは安全」としていたため、列挙の漏れがそのまま素通しになる（許可リストの中に列挙方式が残っていた＝fail-safe になっていない）。
- ホストの Python は「Django らしい語がコードの文字列に含まれるか」（`_DJANGO_CTX_RE`）で判定の要否を決めていた。語の有無はコードの意味と関係がなく、`manage.py shell`（定義上 Django のコード）に当てて見逃し（#2）、記録を書き換える文字列に当てて誤停止（#6）を起こした。

### 2-2. `$(...)` の中身をコードとして扱っていないこと（#1）
- `_cut_substitutions` は `$(...)` を別のコマンドとして判定するが、`-c "$(...)"` の値は `__SUBST__` という文字列になり、`_python_code` / `_sql_of` は「見えているコード」として扱っていた。`$(cat <<'EOF' ... EOF)` の本文は `cat` のデータ扱いでどこからも判定されない。

### 2-3. その他（個別の不具合）
- ホスト側のリダイレクトの印（`writes`）が、`_expand` でコンテナ内のコマンドに引き継がれる（#11）。
- パイプで受ける psql / manage.py shell を、素の docker exec とホストでは判定しない（#10）。
- deny の `Edit(**/.env.*)` が `.env.example` 等の編集まで拒否する（#13）。
- ホストの秘密情報の判定がコンテナ内だけ（`echo $KEY`）・`gh auth status -t`・`git diff` の `.env`（#14）。
- push の判定がヒアドキュメント本文に反応する・`docker compose config --services` まで確認・frontend の `/app` を backend に読み替える（#16）。
- AC-13 の文面が方針（0-9）に追随していない（#12）。
- テストの抜け（#7・#8・#15）。

### 2-4. セキュリティ観点
- 本イシューの guard は、Claude の事故（データ消失・外部送信・秘密情報の表示）を防ぐ開発ハーネスのゲートで、アプリの認証・認可・入力の扱いは変えない。#1〜#5 は「人の承認なしにデータ消失が起きうる」穴（CLAUDE.md 絶対ルール 4）、#14 は秘密情報の露出の穴で、どちらもこの fix-loop で塞ぐ対象。OWASP の観点では、A01（権限の不備＝承認の迂回）と A02（秘密情報の露出）に相当する。

## 3. 対応方針（全案＋推奨）

すべての案で、2-2（`$(...)` の解決）・2-3（個別の不具合）・テストの抜けは直す。違いは 2-1（Python コードの判定）の直し方。

### 案 A: 正規表現のまま、見つかった形を個別に足す
- 内容: `.update(` の改行・関連マネージャ、`cache.clear`、ループの `.save()`、`call_command` の各形などを正規表現に追加。誤検知は除外パターンで対応。
- セキュリティ: 今回の再現は塞がるが、同じ種類の揺れ（別の書き方）が次も出る。許可リストの中に列挙方式が残るので fail-safe にならない。
- ベストプラクティス: Python のコードを正規表現で解析するのは脆い（ソースの構造を扱うなら構文木を使うのが定石）。
- 保守性: パターンが増え続け、誤検知と見逃しのトレードオフが続く（第 2 周→第 3 周で実際に起きた）。
- リスク・副作用: 小さい修正で済むが、敵対的レビューを回すたびに新しい穴が見つかる構造が残る。

### 案 B: compose の中の Python コード（manage.py shell・python -c・python ファイル）は常に確認にする
- 内容: compose の許可リストから Python コードを外す（危険・外部送信の列挙は引き続きホスト・素の docker にも当てる）。
- セキュリティ: compose 側は確実に fail-safe になる。ホスト・素の docker の見逃し（#2 等）は列挙のまま残る。
- 保守性: 単純。
- リスク・副作用: **承認待ちの削減がほぼ消える**。作業記録では compose exec/run 243 件のうち 118 件（約 49%）が Python コードを渡す操作（manage.py shell 92・python -c 25・python ファイル 1）で、手動テストの読み取り確認の大半がここに入る。I174 の目的（承認待ちの削減）に反する。

### 案 C（推奨）: Python コードを構文木（標準ライブラリ `ast`）で読み、compose では「安全と分かる呼び出しだけ」を通す
- 内容:
  1. コードを `ast.parse` で構文木にし、呼び出し（`Call`）・import・属性の参照・ループを、書き方の揺れ（改行・空白・括弧・変数名）に関係なく取り出す。構文として読めないコードは、compose では確認にし、ホスト・素の docker では従来の正規表現の判定に戻す。
  2. **危険操作の判定（ホスト・素の docker・compose 共通）**: `.delete()` / `_raw_delete()`（`cache.delete` は除く）・QuerySet 系の `.update()`（呼び出しのチェーン・`objects` を含む属性の連鎖・`*_set` / 関連マネージャ〔2 段以上の属性〕・`qs` 等の名前。単独の変数名 `d.update()` は除く）・`.bulk_update()`・`cache.clear()` / `.flushall()` / `.flushdb()`・ループや内包表記の中の `.save()` / `.delete()`・`call_command` の第 1 引数とキーワード引数（`flush` / `sqlflush` / `reset_db` / `loaddata` / `seed_e2e` の `flush=True` / `--flush`・`migrate` の位置引数 2 つ以上）・`shutil.rmtree` / `os.remove` 等・`cursor().execute()` の破壊的 SQL のリテラル
  3. **外部送信・秘密情報の判定（共通）**: import（`smtplib`・`socket`・`requests`・`urllib`・`httpx`・`http.client`・`subprocess`・`django.core.mail`）・呼び出し（`send_mail` 等・`.delay()` / `.apply_async()`・`*_task()`・`email_user`・`send_verification_email`・`PasswordResetForm`・`os.system` / `os.popen`）・文字列の API パス（登録・パスワード再設定・AI 生成）・`reverse('register')` 等・秘密情報（`os.environ` の読み出し〔`setdefault` での書き込みは除く〕・`getenv`・`.env` を含むパスの `open`・`settings.SECRET_KEY` 等）
  4. **compose の許可リスト（compose の中だけ）**: 2・3 に当たらず、かつ、すべての呼び出しが「安全な呼び出しの一覧」（表示・組み込みの変換、ORM の読み取り〔`get` / `filter` / `exclude` / `all` / `count` / `exists` / `values` / `values_list` / `first` / `last` / `order_by` / `select_related` / `prefetch_related` / `annotate` / `aggregate` 等〕、集計関数、1 件の `save()` / `create()` / `set_password()` / `refresh_from_db()`、テスト用クライアント〔`APIClient` / `Client` / `force_authenticate` / `get` / `post` 等〕、`cache.get` / `cache.delete`、`reverse`〔登録等以外〕、`timezone.now`、`json.dumps` 等）に入り、import も一覧（`django.*`・アプリのモジュール・`rest_framework.*`・`json`・`datetime` 等）に入るときだけ素通し。一覧外の呼び出しが 1 つでもあれば確認。
  5. **ホストの Python の判定の要否**: `manage.py shell` / `django-admin shell` に渡すコードは常に判定する。素の `python` のコードは、import にアプリ（`django`・`problems` 等）が含まれるときに危険操作を判定し、秘密情報と外部送信（API パス・`.env` の読み出し）はいつも判定する。文字列の中の語では決めない（#6・#11 の誤判定をなくす）。書き込みモードの `open(` は危険操作から外す（ホストのファイル編集は通常の作業。compose では一覧外の呼び出しとして確認になる）。
- セキュリティ: compose の Python コードが「一覧に入るときだけ素通し」になり、fail-safe になる。書き方の揺れで判定が外れる構造がなくなる。ホスト・素の docker の危険操作の判定も、構文木で揺れに強くなる。
- ベストプラクティス: ソースコードの構造の判定は構文木で行うのが定石。Python 標準の `ast` だけで実現でき、依存を増やさない。
- 保守性: 判定が「呼び出しの名前と形」の表になり、正規表現の組み合わせより読みやすい。一覧に足すだけで安全な呼び出しを増やせる。
- リスク・副作用: 実装量は案 A より大きい（guard の Python コード判定の部分を書き直す）。一覧にない読み取りの呼び出しを使う手動テストでは確認が出る（安全側）。正規表現のフォールバックは構文として読めないコードに限られる。

### 推奨: 案 C
- 理由: 案 A は第 2 周→第 3 周で起きた「直すと別の穴が出る」構造を残す。案 B は I174 の目的（承認待ちの削減）をほぼ失う。案 C は compose の Python コードを fail-safe にしたまま、手動テストのふだんの読み取り確認（作業記録の約半分）を素通しのまま保てる。

## 4. 影響調査（同型バグ・他の呼び出し箇所・関連機能への波及）
- 同型バグの調査: 「正規表現でソースや SQL を判定する」箇所は、Python コード（`_CODE_DANGER` / `_CODE_EXTERNAL` / `_DJANGO_CTX_RE`）と SQL（`_sql_is_destructive` / `_sql_is_safe_read`）。SQL は psql の文を対象にしていて、第 3 周で新しい見逃しは出ていない（`-c "$(...)"` の経路は 2-2 で直す）ので、今回は Python コードだけを構文木に置き換える。
- 呼び出し箇所: `_python_code` / `_python_code_raw` / `_code_reasons` を使うのは `_cmd_danger`・`_cmd_external`・`_container_safe`。この 3 か所を新しい判定に切り替える。
- 関連機能への波及: guard は全セッションの Bash に効く。ホストの Python の判定を「import で決める」に変えると、記録を書き換えるスクリプト・検証スクリプトの誤停止（#6・#11）がなくなる。既存の push / checkout / worktree のテストと、container テスト 418 件・settings テストへの影響は手順 6 で全件を再実行して確かめる。
- I146（#260）との統合（計画書ステップ 6）への影響は無い（判定の入口 `_danger_reasons` / `_analyze` の形は変えない）。
