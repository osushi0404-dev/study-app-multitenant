# I524 診断メモ（fix-loop・2026-11-16 10:35・ユーザーの BP の確認）

起点: マージ依頼の後、ユーザーの「念のための確認だが、今回対応した内容はBPの観点で評価して問題ないか？」に、Claude が規約（`rules/ultimate_django_coding_standards.md` §14「アンチパターン」のエラーの握りつぶし・「防御的プログラミング」「ログ出力: 適切なレベルで記録」）と照らして 4 点を報告し、ユーザーが「1と2をこのPRで直して」と決めた。直すのはこの 2 点だけ（3: テストの準備の重複・4: compose の設定の写しは今のまま）。

## 失敗分解
### 1. `--soft-stop` が異常まで正常終了にする（台帳の F2・#508 に同梱済みのもの）
- 再現手順: 確かめ用の利用者のメール `verify_i487@example.com` の利用者が、ほかの組織（`verify-i487-org` 以外）にいる DB で、`python manage.py seed_dashboard_verify --password-env E2E_TEST_PASSWORD --soft-stop` を流す（開発の起動の `dashboard-verify-seed` と同じ形）
- 期待値: 起きてはいけない状態なので、データを作らずに失敗で終わる（終了コード 非 0）。想定内の止まり方（`DEBUG` が偽・パスワードが空）だけが、作らずに正常に終わる
- 実際値: 標準出力に `確かめ用のデータは作りませんでした: verify_i487@example.com が確かめ用の組織（verify-i487-org）にいないため、何もしません` を出して終了コード 0。起動のログを読まない限り気づけず、古いデータのまま起動のたびに同じ 1 行が出続ける
- ログ・根拠: `backend/dashboard/management/commands/seed_dashboard_verify.py:43-46`（`except VerifyDataError` で `options['soft_stop']` なら `return`）。`VerifyDataError` は 3 か所で投げる（`backend/dashboard/verify_data.py` の `ensure_debug`〔DEBUG が偽〕・`_ensure_user`〔ほかの組織〕・`seed_verify_data`〔パスワードが空〕）

### 2. 「作りませんでした」の案内を標準出力に普通の文で出している
- 期待値: 作らなかったことは注意の知らせなので、Django の管理コマンドの慣例どおり `self.stderr.write(self.style.WARNING(...))` で標準エラーに出す
- 実際値: `self.stdout.write(...)`（`seed_dashboard_verify.py:45`）。成功の出力（種・期待値）と区別がつかない
- 影響: 動作には影響しない（`docker compose logs` は標準出力・標準エラーの両方を出す）

## 根本原因
- 計画 4-2・9 は「`--soft-stop` は `VerifyDataError` のとき正常に終わる」と、例外の型 1 つで決めた。`VerifyDataError` は「想定内で作れない（環境が整っていない）」と「起きてはいけない状態（データの食い違い）」の 2 種類の止まり方を 1 つの型にまとめていて、計画はその違いを分けなかった。イシュー・受け入れ条件 AC9 が求めていたのは前者（パスワードが無い・`DEBUG` が偽）だけ
- 案内の出し先は、計画で決めておらず、既存の出力（期待値の行）と同じ書き方に合わせた
- セキュリティ: 認証・認可・入力・秘密の露出には当たらない（案内の文にパスワードの値は入らない）。異常が見えなくなるのは、運用の見える化（規約のエラーの握りつぶし）の問題

## 対応方針（全案＋推奨）
### 案 A（推奨）: 想定内の止まり方を `VerifyDataError` の下の型に分け、`--soft-stop` はその型だけを正常終了にする
- `verify_data.py` に `class VerifyDataUnavailable(VerifyDataError)`（docstring: 作れる環境にないとき〔DEBUG が偽・パスワードが空〕。開発の起動の処理からは、作らずに正常に終わってよい）を足す。`ensure_debug` とパスワードが空のときにこれを投げる。ほかの組織の場合は今どおり `VerifyDataError`
- コマンドは `except VerifyDataUnavailable` を先に置き、`soft_stop` なら `self.stderr.write(self.style.WARNING(f'確かめ用のデータは作りませんでした: {error}'))` で `return`。`except VerifyDataError` は今どおり `CommandError`（`--soft-stop` があっても）
- セキュリティ影響: なし（止まる条件・順番は同じ。異常が失敗として見えるようになる）
- BP: 例外の型で意味を分けるのは Python の標準の形（`except` の具体的な型で受ける・規約 §14 の良い例）。処理側の例外を処理の言葉で分け、コマンドの層の例外に依らない（I513 の BP の直しと同じ向き）
- 保守性: 呼び出し側（I513 のテスト・コマンド）の `VerifyDataError` は、下の型も受けるので今のまま動く
- リスク・副作用: 異常のとき `dashboard-verify-seed` のコンテナが終了コード 1 で終わる。どのサービスもこれに依存しないので起動は止まらない（計画 R2 のまま）。名前を指定しない `--wait` は使わない（R3 のまま）

### 案 B: `VerifyDataError` に属性（例: `expected: bool`）を持たせ、コマンドが属性を見て分ける
- BP: 型で分けられるものを属性の if で分けるのは、型で受ける慣例より読みにくい。投げる側が属性を付け忘れると黙って正常終了・異常の扱いが入れ替わる
- 不採用

### 案 C: `--soft-stop` を外し、compose の command にシェルで「パスワードが無ければ案内を出して `exit 0`」を書く
- `DEBUG` が偽の判定はシェルからはできず、コマンドの中の判定と二重になる。計画 9 で「シェルで `|| true` などを書かない」と決めた理由（想定外の失敗を失敗のまま見せる）とも合わない
- 不採用

### 2 の直し（どの案でも同じ）
- 案内は `self.stderr.write(self.style.WARNING(...))`。成功の出力（種・期待値）は今どおり標準出力

## 影響調査
- 同型: `VerifyDataError` を受けているのは `seed_dashboard_verify.py` の 1 か所だけ（`grep -rn VerifyDataError backend`）。テストでは `test_I513_seed_dashboard_verify.py` の TC-45（DEBUG が偽で `VerifyDataError` を待つ）・TC-47（ほかの組織で `VerifyDataError` を待つ）・`test_I524_dashboard_verify_volume.py` の TC-04・TC-05（`--soft-stop` の出力を標準出力で見ている）・TC-07（`--soft-stop` なしのほかの組織で `CommandError`）
  - TC-45・TC-47: 下の型も `VerifyDataError` なので、そのまま通る
  - TC-04・TC-05: 出力の場所を標準エラーに直す
  - 足す: `--soft-stop` があっても、ほかの組織なら `CommandError` で、その利用者のデータが変わらない（TC-08）。失敗の注入: `except VerifyDataUnavailable` を `except VerifyDataError` に戻すと TC-08 が落ちる（FG-7）
- 関連機能: compose の `dashboard-verify-seed` の command・コメント（「パスワードが無い・DEBUG が偽なら、作らずに案内を出して正常に終わる」）は変わらず正しい。手順書 §11 に「ほかの組織に同じメールの利用者がいるなど、起きてはいけない状態ではエラーで終わる（ログに理由）」を 1 行足す
- 計画: 4-2・9・必ず確かめる項目 V1 の「`VerifyDataError` のとき正常終了」を「`VerifyDataUnavailable` のとき」に直す。受け入れ条件 AC9（パスワードが無い・`DEBUG` が偽で作らず起動も止めない）は変わらない。範囲は変わらない
