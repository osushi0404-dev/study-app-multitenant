## 失敗分解
- 再現手順: PR #521 の CI（Actions run 43664045176・ジョブ Backend Tests）。手元では `docker compose exec backend python -m pytest studylogs/tests/test_I455_org_scoped_querysets.py::test_unscoped_reads_have_reason_comment`
- 期待値: `studylogs`・`dashboard` のテスト以外のコードで、組織で絞る取り出し方を持つ 8 モデル（`QuizSession` を含む）を `objects.for_user(user)` 以外で読む行には、その行か直前の行に `# 組織で絞らない: <理由>` がある（I455 の決まり・TC-06）
- 実際値: `AssertionError: 8 モデルを組織で絞らずに読んでいます。… ['dashboard/verify_data.py:286', 'dashboard/verify_data.py:301']`（1 failed, 494 passed）
- ログ: `QuizSession.objects.bulk_update(sessions, ['started_at'])`（286 行）と `QuizSession.objects.filter(user=user).delete()`（301 行）に理由のコメントが無い

## 根本原因
- I513 で `backend/dashboard/verify_data.py` を足したとき、`dashboard` アプリのコードに I455 の決まり（絞らずに読むなら理由を書く）が掛かることを見落とした。決まりのテストは `studylogs/tests/` にあり、実装の段階では関係するテスト（`dashboard/tests/` の 2 ファイル）だけを手元で流したので、CI で初めて当たった
- 2 行とも、確かめ用の利用者 1 人に限った書き込み（解答の時刻を直す・その利用者のセッションを消す）で、組織をまたいで読み出して返す処理ではない。漏れの実害は無い（中身を外に返さない・開発の DB だけ・`DEBUG` が偽で止まる）
- セキュリティ: 認可・入力・データの露出は変わらない。消す範囲は `user=user`（確かめ用の組織にいることを先に確かめた利用者）で、TC-44・TC-47 が固定している

## 対応方針（全案＋推奨）
- 案 A（推奨）: 2 行の直前に `# 組織で絞らない: <理由>` を書く（例: `# 組織で絞らない: 確かめ用の利用者（確かめ用の組織にいることを確かめ済み）が今作ったセッションの時刻を直すだけ`）
  - セキュリティ: 変化なし。BP: I455 の決まりそのままの書き方（`studylogs/services.py` と同じ）。保守性: 理由が行に残る。リスク・副作用: コメントだけで動作は変わらない
- 案 B: `QuizSession.objects.for_user(user)` で絞ってから消す・直す
  - セキュリティ: 同じ（利用者は確かめ用の組織の人なので結果は変わらない）。BP: 決まりの第一の書き方。保守性: `bulk_update` は QuerySet の取り出しではないので `for_user` を挟めず、286 行は結局コメントが要る。削除だけ `for_user` にすると、`subject` が null のセッション（`allow_null`）の扱いの読み解きが要る。リスク: 動作が少し変わる（作り直しで消えるセッションの範囲が狭まりうる）
- 案 C: 決まりのテストの対象から `dashboard/verify_data.py` を外す
  - 安全装置を弱める変更で、開発専用でも例外を足すのは決まりの趣旨に反する。採らない
- 推奨: 案 A（動作を変えず、決まりどおり。粗く確実）
