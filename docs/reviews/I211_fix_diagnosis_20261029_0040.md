# I211 fix-loop 診断メモ 2（CI の Harness Tests の FG-K2 の失敗）

## 失敗分解
- 再現手順: PR #357 に fa791b32 を push → CI（run 40715048373）の Harness Tests
- 期待値: `test_i211_version_pin.sh` の FG-K2（`pyproject.toml` から PyYAML を消した写しで `uv lock --check --offline`）が非ゼロで、出力に `update`
- 実際値: 非ゼロだが、出力に `update` が無い（`expected=[yes yes] got=[yes no]`）。ほかの 47 本と FG-K2 以外の 21 項目は合格。手元では合格していた
- ログ（要約）: `FAIL FG-K2 pyproject.toml と uv.lock がずれれば不合格 expected=[yes yes] got=[yes no]`

## 根本原因
- /simplify の整理で、FG-K2 の `uv lock --check` に `--offline` を付けた（計画変更記録 3）。CI の runner は新しいキャッシュで、`uv run` が入れたパッケージ本体はあるが、解決し直しに要る索引の情報が無い。そのため `--offline` だと「ネットワークを使えない」という別の理由で失敗し、`update` の文言が出なかった
- テストは「失敗の理由がロックのずれであること（`update`）」まで確かめていたので、別の理由の失敗を合格にしなかった（偽の合格を防ぐ作りが働いた）
- 手元で通ったのは、手元のキャッシュに索引の情報が残っていたため（環境の差）
- セキュリティ観点: 該当なし（テストの書き方の問題）

## 対応方針（全案＋推奨）
| 案 | 内容 | セキュリティ | BP | 保守性 | リスク・副作用 |
|---|---|---|---|---|---|
| A（推奨） | FG-K2 だけ `--offline` を外す（K2 の正の確認は CI で `--offline` のまま通ったので残す） | 影響なし | 確かめたい失敗（ロックのずれ）を確実に起こす | 1 語の変更 | FG-K2 はネットワークが要る（pre-commit の shellcheck・uv の初回と同じ前提〔計画 R5〕） |
| B | FG-K2 の判定から `update` を外し、非ゼロだけで合格にする | 影響なし | 別の理由の失敗でも合格になり、偽の合格を招く | 簡単 | 否定のテストの質が下がる（採らない） |
| C | FG-K2 の前にキャッシュを温める（`uv lock` を一度流す） | 影響なし | 回り道 | 手順が増える | 温めの成否に依存する |

推奨は A。

## 影響調査
- 同型のバグ: `--offline` を付けたのは K2 と FG-K2 の 2 か所だけ。K2（正のロックの確認）は CI でも合格した（ロックが合っていれば索引の情報が要らない）
- ほかの呼び出し箇所: runbook・CI には `--offline` を書いていない
- 関連機能への波及: なし
