# I545 fix-loop 診断メモ（2026-11-17 03:52）

起点: review-gate の記録 `docs/reviews/I545_code_review_20261117_0342.md` の「止める指摘」F1・F2（直すのはこの 2 件だけ）。

## 失敗分解

### F1（High・STOP=ac:8）旧規約が消えたことを見る決定論ゲートが実走で FAIL
- 再現手順: `scripts/claude/code-review.sh` がゲートの `! grep -qs "" rules/backend-django-coding-standards.md` などの 8 行（auto_test の 3〜10 行目）を `run_one_gate()` で実走する
- 期待値: ファイルが無いので合格（exit 0）
- 実際値: 8 行とも exit=1（FAIL）。`run_one_gate()`（`scripts/claude/code-review.sh:417-425`）は `! grep` の行を、内側の grep の exit が 1（一致なし）のときだけ合格にし、2 以上（ファイルが無いなどのエラー）は fail-closed にする。ファイルが無いと grep は 2 を返すので不合格になる
- ログ: レビューの記録の FINDING F1。あわせて「0 バイトのファイルが残っても合格になる」との指摘

### F2（Medium・STOP=ac:7）UX の決まりと React 規約のフォームの例が食い違う
- 再現手順: `docs/runbooks/ux-rules.md` §3 は「誤りは送信の前に分かる（入力欄を離れたときに確かめる）」。`rules/react-coding-standards-integrated.md` §8 の例は `useForm({ resolver: zodResolver(schema) })` で `mode` を書いておらず、React Hook Form の既定（`onSubmit`）になる
- 期待値: 規約どおりに書いたフォームが UX の決まりを満たす（AC7: 同じことを違う内容で書いた箇所が無い）
- 実際値: 規約の例どおりだと送信を押すまで誤りが出ない

## 根本原因
- F1: 「ファイルが無い」ことを、ファイルを名指しした `! grep` で確かめようとした。ゲートの実走は `! grep` のエラー（exit 2）を不合格にする（不在の判定がエラーで偽の合格にならないための作り・I084）ので、名指ししたファイルの不在はこの形では確かめられない。計画の時点の失敗の注入（FG）は、手元の `bash -c` で `!` をそのまま評価して確かめたため、実走の作りとの違いに気づかなかった
- F2: §8 の例を書いたときに、ux-rules §3 の「確かめる時機」を例のコードに落とさなかった（`mode` の指定漏れ）
- セキュリティ観点: どちらも文書と文書のテストで、認証・認可・インジェクション・機密データには当たらない

## 対応方針（全案＋推奨）

### F1
- 案 A（推奨）: 8 行を 1 行にまとめ、`rules/` フォルダ全体を、正の 2 本を除いて中身のある行が無いかで確かめる: `! grep -rq --exclude=ultimate_django_coding_standards.md --exclude=react-coding-standards-integrated.md "" rules`
  - 内側の grep は、正の 2 本のほかにファイル（`rules/bk/` の下を含む）があれば exit 0（不合格）、無ければ exit 1（合格）。`rules/` が無いときは exit 2（不合格・fail-closed）
  - 名指しの漏れが無くなる（古い 4 本・控えの 4 本に限らず、正でないファイルが何であっても捕まえる。AC8「`rules/` の直下に正の 2 本以外の規約が無い」をそのまま表す）
  - 失敗の注入: 今の状態で内側 exit 1（合格）、`rules/bk/react-coding-standards.md` を置いた写しで内側 exit 0（不合格）を確認済み
  - 残る弱み: 0 バイトのファイルは grep で捕まえられない（行が無いので一致しない）。中身の無いファイルは規約として読まれず、計画・レビューを誤らせないので、受け入れる（AC8 の目的は「正でない規約を読む余地を無くす」こと）
- 案 B: `scripts/claude/tests/` に `test -e` で不在を確かめるテストのスクリプトを足す
  - 0 バイトも捕まえられる。一方で、意図的な変更でしか壊れない決まりに恒久のテストを足すことになり、plan-writing-rules「決定論テストの対象の選び方」に反する。ハーネスのテストの数も増える
- 案 C: 不在の確かめをゲートから外し、手動テストだけにする
  - AC8 を決定論で示せなくなる（指摘そのものが残る）
- 推奨: 案 A（粗く確実な形・規則が単純・恒久のテストを足さない）

### F2
- 案 A（推奨）: React 規約 §8 に「検証の時機は `mode: 'onTouched'`（最初に欄を離れたときに確かめ、その後は入力のたびに確かめ直す）」を決まりとして書き、例の `useForm` に `mode: 'onTouched'` を足す。ux-rules §3 の「入力欄を離れたときに確かめる」と同じ意味になる
- 案 B: `mode: 'onBlur'`
  - 欄を離れたときだけ確かめ、直している最中は誤りが消えない。onTouched のほうが直した瞬間に誤りが消えて使い勝手がよい
- 案 C: ux-rules §3 を「送信のときに確かめる」に直す
  - 送信まで誤りが分からず、ux-rules §3 の「送信の前に分かる」という原則を下げる
- 推奨: 案 A。出典: React Hook Form の `useForm` の `mode`（https://react-hook-form.com/docs/useform#mode ）
