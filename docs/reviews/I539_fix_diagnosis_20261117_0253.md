# I539 fix-loop 診断メモ（2026-11-17 02:53・AC13 の後の CI）

## 失敗分解
- 再現手順: PR #544 の CI（run 43922117608・E2E Tests）。`e2e/tests/quiz-session.spec.ts` の 3 本（`:4`・`:37`・`:57`）が、利用者 A（`chromium-authed`）で `/dashboard` の「クイズを始める」を押す
- 期待値（テストの前提）: 科目を選ぶダイアログ（`[role="dialog"]`）が出て、「E2E Quiz Subject」を選ぶ
- 実際値: ダイアログが出ない（`element(s) not found`）。3 本とも同じ所で落ちる（再試行も同じ）
- ログ: `expect(locator('[role="dialog"]')).toBeVisible()` が失敗。ほかの 15 本は合格

## 根本原因
- E2E のデータ（`backend/accounts/management/commands/seed_e2e.py:107-151`）では、利用者 A の学ぶ科目は「E2E Quiz Subject」（問題 1 問）と「E2E Subject A」（問題 0 問）の 2 つ
- AC13 で、ダッシュボードは問題のある科目だけをクイズの対象にした（`StartQuizCard.tsx` の `quizTargets`）。対象は「E2E Quiz Subject」の 1 件だけになり、「すべて」でも 1 件ならダイアログを出さずにその科目へ進む（計画 4-7・TC-47 と同じ）
- テストは「学ぶ科目が 2 件だから必ずダイアログが出る」（spec の 10〜14 行目の説明）を前提にしていた。AC13 の前は、ダイアログで「E2E Subject A」を選ぶと問題が無くエラーの通知で戻される状態で、テストはそれを避けて「E2E Quiz Subject」を選んでいた
- つまりアプリの不具合ではなく、テストの前提（科目の件数でダイアログが出る）が AC13 の仕様と合わなくなった。計画の影響範囲で、学ぶ科目の件数に頼る既存の E2E を探していなかった
- セキュリティ: 関係なし（画面の遷移の前提だけ。認証・認可・入力の扱いは変えない）

## 対応方針（全案＋推奨）
- 案 A（推奨）: 3 本を新しい仕様に合わせる。「問題のある科目は E2E Quiz Subject だけなので、ダイアログを出さずにその科目のクイズへ進む」を確かめる（`/quiz?subject=` に移り、選択肢が出る・ダイアログが出ない）。説明のコメントも直す
  - 良い点: AC13（問題の無い科目を対象にしない）を、実際のデータで E2E が毎回確かめるようになる。データを変えないので、ほかの spec（`tenant_isolation` が「E2E Subject A」を使う）に影響しない
  - 悪い点: ダイアログを通る流れは E2E から消える（ダイアログは Jest の TC-04a・TC-47 が確かめる）
- 案 B: E2E のデータで「E2E Subject A」にも問題を足し、ダイアログが出る前提を保つ
  - 良い点: テストはそのまま
  - 悪い点: `tenant_isolation` などほかの spec が「E2E Subject A」の中身に頼っていないかの確認が要る。シードは本番に近い開発の DB にも流れうる（`e2e-init`）ので、変える範囲が広い。AC13 の動きは E2E で確かめられないまま
- 案 C: ダイアログが出たら選び、出なければそのまま進む、と分岐する
  - 悪い点: テストの中の分岐は、どちらの動きでも通る（偽の合格）。採らない

推奨: 案 A。仕様どおりの動きを確かめる形にし、データは変えない。

## 影響調査
- 同じ前提の箇所: `grep -rn 'role="dialog"' e2e/tests` で、ダッシュボードの「クイズを始める」の後にダイアログを待つのは `quiz-session.spec.ts` の 3 本だけ（`auth.spec.ts` の I539 の流れは、問題のある科目 1 件でダイアログなしを既に確かめている）
