## 2. 根本原因

`scripts/claude/code-review.sh:209-220` の `omission_lint` は、`docs/tests/open/I151_auto_test.md` のうち **`## 決定論ゲート（自動実走）` セクション外の fenced コードブロック**に、allowlist のゲートパターン（`grep -q` / `grep -L` / `bash scripts/claude/tests/*.sh` 等）が 1 つでもあれば HIGH を返す。テンプレート（`docs/tests/templates/auto_test_template.md:15-17, 25-35`）は「ゲート系コマンドは必ず同セクションに書く。セクション外の fenced ブロックに書くと omission-lint が宣言漏れとして HIGH を出す」と定めている。

I151 の `auto_test.md` は **同セクションを持たず**、各 TC の判定コマンドを fenced ```bash ブロックに書いている。該当行は 47 行（例: 99 行目 `grep -qE '^94 passed' /tmp/i151_pytest.log`、132 行目 `! grep -qi guardian ...`、256〜261 行目 `grep -qx ... backend/requirements.txt` 等）。

該当行は性質で 2 種類に分かれる:

| 種別 | 該当 TC | code-review での実走可否 |
|---|---|---|
| **(A) リポジトリ内ファイルだけを見る静的判定** | TC-AUTO-05 判定 1・2 / TC-AUTO-11A 判定 A-1（6 行）/ TC-AUTO-11B 判定 B-1 / TC-AUTO-15 判定 1・2 | 可能（`grep` / `! grep` は allowlist ALLOW。いずれも現時点で exit 0 を実測済み） |
| **(B) 実行時の一時ファイル（`/tmp/i151_*`）または `git grep` を見る判定** | TC-AUTO-03・06・07・10・11A A-2・11B B-2・12・16 判定 1・2・17 | 不可能。`/tmp` は Docker 実行（heavy・/test 委譲）の産物で code-review 時点に存在しない（存在しても古い証跡）。`! git grep ...` は `classify_gate` の allowlist（`grep *` / `! grep *` の前方一致）に合わず UNSAFE＝BLOCKER になる |

つまり (A) は**本来セクションに宣言すべきだった宣言漏れ**（テンプレート規約違反・実害は「code-review で静的事実が再検証されていない」こと）。(B) は宣言できない判定だが、lint が fenced ブロック内の `grep -q` を種別を問わず検出するため巻き込まれている（lint 側の検出範囲の広さ＝harness 側の課題）。

補足（追加で判明した制約）:
- TC-AUTO-15 判定 2 `! grep -qE 'django-(guardian|extensions)==' ...` は正規表現中の `|` が `classify_gate` のチェーン文字ガード（`*'|'*` → UNSAFE）に掛かる。そのまま宣言すると BLOCKER になるため、パッケージごとに 2 行へ分割が必要。
- `run_one_gate` は `! grep` を「grep の exit 1 のみ合格・exit ≥2（ファイル不在等）は不合格」と扱うため、宣言しても false-green にならない。

### セキュリティ観点
アプリコード・設定・依存の変更は無い（変更は記録ドキュメントのみ）。認証・認可・インジェクション・XSS・機密データ露出のいずれにも該当しない。(A) を宣言化すると「guardian / django-extensions の再混入」「固定バージョンの意図しない変更」が code-review のたびに機械検出されるようになり、依存監査上はむしろ強化になる。

## 3. 対応方針（全案＋推奨）

### 案 1（推奨）: (A) を決定論ゲート欄へ宣言し、(B) を inline code 表記に改める
- `I151_auto_test.md` に `## 決定論ゲート（自動実走）` セクションを新設し、(A) の 12 行（TC-AUTO-15 判定 2 を 2 行に分割するため 11→12 行）を単一 ```bash ブロックに 1 行 1 コマンドで宣言する。
- 各 TC 本文の (A) 判定は「決定論ゲート欄で宣言（code-review が毎回実走）」と参照に置き換え、判定内容（パターン・対象ファイル）は不変。
- (B) の判定は fenced ブロックから外し、箇条書きの inline code（`` `grep -qE '^94 passed' /tmp/i151_pytest.log` ``）に改める。テンプレート／lint 実装が inline backtick を非検出と明記している（`code-review.sh:207-208` の W4）正規の書き方。判定式・合否基準・実施記録は一字も変えない。
- メリット: テンプレート規約どおりの構造になる。(A) が code-review で毎回再検証され記録が強くなる（静的事実の回帰を検出）。テスト・アプリコードに一切触れない。
- デメリット: (B) は依然 code-review で再実走されない（これは /test・実施記録で担保する設計どおり）。inline 化で見た目のコピペ性がやや落ちる。
- セキュリティ影響: なし（OWASP 該当なし）。依存再混入の検出が強化される。
- ベストプラクティス: テンプレート `auto_test_template.md` の規約に完全準拠。
- リスク: 宣言した (A) が UNSAFE/FAIL に分類されれば BLOCKER になる → 全 12 行を `classify_gate` 相当で ALLOW 判定・実走 exit 0 を事前確認して防ぐ。

### 案 2: (B) を含め全部 inline code にし、ゲート欄は作らない（宣言 0 件）
- メリット: 変更が機械的・最小。lint は OK になる。
- デメリット: 本来宣言すべき (A) まで宣言しないまま lint を黙らせる形になり、テンプレートの意図（宣言漏れ防止）に反する。code-review での静的事実の再検証が得られない。**lint 回避目的の書き換え**と同型で不採用。

### 案 3: harness 側（`omission_lint`）を直して (B) を検出対象外にする
- メリット: 根治。今後のイシューで同じ巻き込みが起きない。
- デメリット: `scripts/claude/` は track:harness の領域で、I151（track:app）のブランチで変更するとトラック境界違反・計画書外の実装になる（CLAUDE.md 絶対ルール 1）。また (A) の宣言漏れは harness を直しても残る（＝ I151 側の是正は案 1 で必要）。
- 扱い: 本 fix-loop では採らず、別イシュー（track:harness）として起票を提案する。タイトル案:「code-review の書き漏れ判定が、実行時の一時ファイルや git grep による確認まで HIGH にする問題を是正」

### 推奨
**案 1**。(A) の宣言漏れという I151 側の本当の欠落を正しく埋め、(B) はテンプレートが認める表記で残す。lint 側の過検出（(B) の巻き込み）は案 3 として harness トラックで根治する。
