# I587 修正の診断メモ（fix-loop・2026-11-19 18:37）

対象: `docs/reviews/I587_code_review_20261119_1825.md` の「## 止める指摘」の F1・F2（それ以外の台帳の指摘 F3〜F5 は直さない・retro へ）

## 失敗分解

### F1（`backend/problems/views.py` の `delete_image`・共有の判定）
- 再現手順: 画像 A を問題 P1・P2 で共有する → P1 を `DELETE /api/problems/<P1>/`（`delete_problem` が紐づけを論理削除）→ `DELETE /api/problems/<P2>/images/delete/<A>/`
- 期待値: ほかに有効な紐づけが無いので、A は論理削除され、中身（`MediaAssetContent`）も消え、`GET /api/media/<A>/` は 404
- 実際値: `ProblemMediaAsset.objects.filter(asset=media_asset).exists()` が P1 の論理削除済みの紐づけを数えるので `_discard_asset` が呼ばれない。A は `is_deleted=False` のまま中身が残り、200 で配信され続ける
- ログ: レビュー役の FINDING F1（REPRO=yes）。組み込みの `/code-review` も同じ指摘（`pre_existing`）

### F2（`backend/media/` の見本のファイルの削除と 0025 の順番）
- 再現手順: ほかのワークツリー（primary など）で I587 の後の develop を取り込む → git が `backend/media/` の追跡ファイル（PNG 6 枚）を消す → backend の起動の `migrate` で 0025 が流れる
- 期待値: その環境の DB に、見本のファイルを指す `MediaAsset` があれば、中身が DB に移る
- 実際値: ファイルが先に消えているので、0025 はその行を「ファイル無し」と判定し、行と紐づけを消す。問題の画像が失われる（試しも承認も無い）
- ログ: レビュー役の FINDING F2（REPRO=yes・ACCEPTED=R6）。組み込みの `/code-review` も `important` で同じ指摘

## 根本原因

- F1: 「ほかの問題が使っているか」の判定が 3 か所（`_reconcile_images`・`delete_problem`・`delete_image`）に別々に書かれていて、`delete_image` だけが論理削除の紐づけを除いていない。`delete_image` の判定は I587 の前からのもの（ファイルの削除が中身の削除に変わっただけ）だが、I587 で「中身が残ると配信され続ける」に変わり、影響が大きくなった
- F2: 追跡ファイルの削除（git の取り込み）と、そのファイルを読む移行（起動の `migrate`）を同じ変更に入れたので、ほかの環境では「消える → 読む」の順になる。app-1 では見本のファイルを指す行が 0 件だったので現れなかった。計画の R6 は「開発のデータなので受け入れる」としたが、その判断はイシューの制約に Claude が書いたもので、ユーザーが grill-me で選んだのは「見本のファイルを移さずに消す」（app-1 で、どの行からも使われていない前提）と「ファイルの無い行は消す」の 2 つ。ほかの環境で見本のファイルが使われている場合の扱いは、ユーザーに確かめていない
- セキュリティの観点: F1 は、消したつもりの画像が同じ組織の利用者に配信され続ける（組織の境界は越えない）。F2 はデータの損失で、セキュリティの欠陥ではない

## 対応方針（全案＋推奨）

### F1
- 案 F1-a（推奨）: `delete_image` の判定を `ProblemMediaAsset.objects.filter(asset=media_asset, is_deleted=False).exists()` にし、`_reconcile_images` とそろえる。再現のテスト（共有の相手が論理削除済みのとき中身が消える）を TC-10 に足す
  - セキュリティ: 消した画像が配信されなくなる（改善）。規約: 変わらない。保守: 1 行。リスク: 有効な紐づけが残る画像は今までどおり残す
- 案 F1-b: 共有の判定をサービスの関数 1 つにまとめ、3 か所から呼ぶ（台帳の F4〔ビューからサービスの非公開の関数を呼ぶ〕も一緒に直す）
  - 保守性は上がるが、止める指摘でない F4 まで直すことになり、差分が広がる（fix-loop は止める指摘だけを直す）。retro で F4 と一緒に扱う

### F2
- 案 F2-a（推奨）: この PR では `backend/media/` の見本のファイルを消さない（`git rm` を戻す。`.gitignore` の `!backend/media/` も戻す）。0025 はファイルのある行を中身ごと DB に移すので、ほかのワークツリーが取り込んだときも見本の画像は DB に移る。見本のファイルの削除は、各ワークツリーで I587 を取り込んだ後の別のイシューにする
  - データ: 失われない。リスク: 受け入れ条件 AC9（見本のファイルを消した記録）をこの PR の外に出すので、ユーザーの判断が要る（止める条件 1）
- 案 F2-b: このまま進める（計画の R6 の受け入れ）。ほかの環境で見本のファイルを指す行は画像なしになる
  - データ: 失われうる（開発のデータ）。ユーザーが明示に受け入れていないので、Claude だけでは選ばない
- 案 F2-c: 0025 の「ファイルの無い行は消す」をやめ、行を残す（中身が無いので配信は 404・画面は「読み込めませんでした」）
  - grill-me でユーザーが選んだ「ファイルの無い行は消す」を変えるので採らない
- 推奨: F2-a。ユーザーに確かめてから直す（止める条件 1）

## 影響調査

- 同型のバグ（共有の判定）: `_reconcile_images`（`is_deleted=False` あり）・`delete_problem`（`is_deleted=False` あり・自分の問題を除く）・`delete_image`（無し）。`delete_image` だけを直す
- ほかの呼び出し: `ProblemService._discard_asset` は 3 か所から呼ばれ、中身の削除はそこに 1 つ。変えない
- F2 の波及: `backend/media/` を戻すと、`LEGACY_MEDIA_ROOT`（`BASE_DIR/media`）に見本のファイルがまた置かれる。app-1 の DB にそれを指す行は無い（M1・M3）ので、app-1 では何も変わらない。決定論のゲート（TC-20〜TC-22）は `backend/media` を見ないので影響なし
