# I513 fix-loop 診断メモ（2026-11-15 11:43）

対象: マージ依頼の後のユーザーの BP の確認（「念のための確認だが、今回対応した内容はBPの観点で評価して問題ないか？」→ Claude が規約との小さなずれ 3 点を報告 →「直す」）

## 失敗分解
### 1. 新しく書いた部品に `React.FC`
- 再現: `frontend/src/components/dashboard/DashboardStatCards.tsx:36` の `const GoalFooter: React.FC<GoalProgress> = …`
- 期待値: 規約 `rules/react-coding-standards-integrated.md:293`「関数コンポーネント + TypeScript（React.FC は使用しない）」
- 実際値: I513 で新しく足した `GoalFooter` が `React.FC` を使っている（同じファイルの既存の部品に合わせた）
### 2. 型の置き場所
- 再現: `GoalProgress` が `DashboardStatCards.tsx:51` で export され、`frontend/src/pages/Dashboard.tsx:17` が表示部品から型を import している
- 期待値: 規約 `rules/react-coding-standards-integrated.md:1578`「型定義は types/ または features/<feature>/types.ts に配置」。既存の例は `frontend/src/types/quiz.ts`
- 実際値: 画面と部品が共有する型が、表示部品のファイルにある
### 3. 確かめ用データの処理が管理コマンドの例外を直接投げる
- 再現: `backend/dashboard/verify_data.py:21,215,237,302` が `django.core.management.base.CommandError` を投げる
- 期待値: 規約 `rules/ultimate_django_coding_standards.md` の層の分け方（処理のモジュールは呼び出し元〔コマンド・ビュー〕に依らない。コマンドは薄く、入出力と例外の変換だけ）
- 実際値: 処理のモジュールが管理コマンドの層の例外に依っている（テストも処理を直接呼んで `CommandError` を待っている）

## 根本原因
- 1: 既存のファイルの書き方（`React.FC`）に合わせ、規約の節を実装の前に照らし合わせなかった。リポジトリ全体の置き換えとリントは #510 の範囲で、今はリントが止めない
- 2: 型を使う場所が 2 つ（画面と部品）になったとき、型のファイルに移す判断をしなかった
- 3: コマンドから呼ぶ前提で書き、処理のモジュールを呼び出し元から切り離す形にしなかった
- セキュリティ: どれも認可・入力・露出に関わらない。3 の止まり方（`DEBUG` が偽・パスワードが空・ほかの組織の同じメール）は変えない

## 対応方針（全案＋推奨）
### 1
- 案 A（推奨）: `GoalFooter` を `const GoalFooter = ({ todayMinutes, goalMinutes }: GoalProgress) => { … }` にする（I513 で新しく書いた部品だけ。既存の部品の置き換えは #510 がリントと一緒に行う）
- 案 B: ファイルの既存の部品も全部置き換える — #510 の範囲に踏み込み、差分が広がる
### 2
- 案 A（推奨）: `frontend/src/types/dashboard.ts` を新しく作り `GoalProgress` を置く。`DashboardStatCards.tsx`・`Dashboard.tsx` はそこから import する（既存の `types/quiz.ts` と同じ置き方）
- 案 B: `features/` を作る — このリポジトリに `features/` は無く、置き方を増やす
### 3
- 案 A（推奨）: `verify_data.py` に `class VerifyDataError(Exception)` を作って投げ、管理コマンドが `CommandError` に変える。テストは、処理を直接呼ぶところは `VerifyDataError`、コマンドを呼ぶところは `CommandError` を待つ
  - 保守性: 処理が管理コマンドの層に依らない。止まり方・文言は同じ
- 案 B: 書き込みを `dashboard/services.py` に移す — 開発の DB だけの確かめ用データを、本番の業務の書き込みと同じ場所に置くことになり、取り違えやすい（規約の services は業務ロジック）。採らない
- 案 C: 処理をすべて管理コマンドのファイルに入れる — コマンドが太り、純粋な関数（計画・期待値）のテストが管理コマンドを読み込むことになる。採らない

## 影響調査
- 1: `GoalFooter` はこのファイルの中だけで使う
- 2: `GoalProgress` を使うのは `Dashboard.tsx` と `DashboardStatCards.tsx` だけ（`grep -rn GoalProgress frontend/src`）
- 3: `CommandError` を投げるのは `verify_data.py` の 3 か所。処理を直接呼ぶテストは TC-45（空の DB）・TC-47。コマンドを呼ぶテスト（TC-45 の 2 つ目・TC-46）は `CommandError` のまま。手順書・計画書（4-3 の「`CommandError`」）の記述も直す
- どれも動作は変えない（表示・止まり方・出力は同じ）。計画は 4-1・4-3 の記述を直して計画変更記録に書く（受け入れ条件・方式・範囲は変えないので計画レビューは通り直さない）
