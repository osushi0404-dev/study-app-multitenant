# I193 fix-loop 診断メモ 7（2026-10-25 11:35）

対象: 基本レビュー 7 回目 `I193_code_review_20261025_1121.md`（FINAL_VERDICT: HIGH・High 2・Medium 5・Low 2）。test-gate を一度通った後なので、繰り返しの上限の数え方では 1 回目。直すのは High 2 件（Medium は High に直結しないので retro へ。自律判断の記録）

## 失敗分解

### H1: 敵対的レビューの上限到達で「残りを受け入れて進む」を選んでも、gate-check が通さない
- 再現手順: 敵対的レビューが通算 2 周で High を残して上限到達 → review-gate が止まってユーザーに選択肢を出す → ユーザーが 3（受け入れて進む）を選ぶ → test-gate の gate-check
- 期待値: ユーザーが受け入れた後は test-gate へ進める（受け入れの判断はユーザーがしたことが記録に残る）
- 実際値: gate-check は最新の敵対的レビュー記録の `VERDICT:` が OK でないと必ず落とす。受け入れた記録の書き方が決まっていないので、`VERDICT: HIGH` のまま詰まる（止まる側なので穴ではないが、選択肢 3 が実際には選べない）
- ログ: `.claude/skills/review-gate/SKILL.md` 3-2「上限到達」・`scripts/claude/gate-check.sh` の敵対的レビュー記録の判定

### H2: 高リスクのときの組み込み /security-review が実行できなくても、判定に影響しない
- 再現手順: パス判定 YES の変更で、組み込みの `/security-review` が時間切れ・失敗・読めない出力になる
- 期待値: 高リスクの変更で公式のセキュリティレビューが動かなかったときは、OK にしない（止まる側に倒す）
- 実際値: 記録に「(実行できず: …)」「(注意: … 判定の根拠にしない)」が書かれるだけで、`FINAL_VERDICT` は自作のレビュー役と決定論ゲートだけで決まる。公式のセキュリティレビューが 1 本も動かないまま OK になりうる
- ログ: `scripts/claude/code-review.sh` `run_official_review`（122〜137 行）・`FINAL_VERDICT=$(combine_verdict …)`（600 行）

## 根本原因
- H1: 上限到達の選択肢を決めたとき、選んだ後の記録の形（gate-check が読む形）を決めていなかった。止める側（gate-check）と選ぶ側（review-gate）の約束が 1 つ欠けている
- H2: 計画 §11 で「組み込みは参考、判定は自作」としたが、高リスクのときは公式の /security-review が多層防御の 1 枚であり、それが動かないことを判定に入れていなかった（fail-open）
- セキュリティ観点: H2 は高リスクの変更でセキュリティレビューが抜けうる穴（止まらない側）。H1 は止まりすぎる側でセキュリティの穴ではないが、「受け入れ」の記録を Claude が自分で書けると迂回になるので、書けるのはユーザーが選んだときだけ、と決める必要がある

## 対応方針

### H1
- 案 A（推奨）: review-gate 3-2 の選択肢 3 に、選んだ後の記録の形を書く。ユーザーが 3 を選んだときだけ、ユーザーの言葉・日時・受け入れた指摘を書いた敵対的レビューの記録を新しく作り、`REVIEWED_COMMIT:` を受け入れた時点の HEAD、`ROUNDS: 0`（周回に数えない）、`VERDICT: OK` にする。Claude が自分で受け入れを書くことはしない（止める条件 3 の「受け入れて進む判断は Claude だけではしない」と同じ）。gate-check は今のまま（最新の記録の VERDICT と REVIEWED_COMMIT を読む）
  - 決定論を足さず、今の gate-check の読み方に合わせるだけ。周回の数え方（`ROUNDS:` の合計）にも影響しない
- 案 B: gate-check に「USER_ACCEPTED: 行があれば通す」を足す — 新しい判定と書式が増え、Claude が誤って書いたときに迂回になる。案 A と同じ守り（ユーザーが選んだときだけ書く）を文で書く点は同じなので、単純な案 A を採る
- 案 C: 選択肢 3 を消して「止める」だけにする — ユーザーの判断の幅を狭める（I185・I187 でユーザーが実際に受け入れを選んだ）。採らない

### H2
- 案 A（推奨）: パス判定 YES のときに、組み込みの `/security-review` の出力が「実行できず」か「読めていない」なら、決定論で HIGH にする。判定は関数 `official_security_verdict <RISK_PATH> <出力>`（OK / HIGH）に切り出し、`FINAL_VERDICT` の合成に入れる。stdout に `OFFICIAL_SECURITY: FAILED` を出し、review-gate は、この行があるときは直すものが無い基盤の失敗なので fix-loop へ回さずに 1 回だけ実行し直す（2 回続けば止める条件 3）
  - 止まる側に倒す。関数にするので一時の値で振る舞いを確かめられる
- 案 B: 失敗を記録に書き、自律判断の記録で「敵対的レビューで補う」と理由を書く — 敵対的レビューは範囲を例外ファイルに絞っており、セキュリティレビューの代わりにならない。採らない

## 影響調査
- 同型: 組み込みの `/code-review` の失敗も判定に入っていない。こちらは自作のレビュー役（同じ差分の正しさを見る）が判定の正なので、計画 §11 のまま参考扱いにする（高リスクのセキュリティの層とは役割が違う）
- 呼び出し箇所: `combine_verdict` の呼び出しは 1 か所（600 行）。`neutralize_machine_lines` に `OFFICIAL_SECURITY` を足す（組み込みの出力の中の同じ文字の行を、機械の行と取り違えないように）
- 関連: review-gate の「終了コードの扱い」に `OFFICIAL_SECURITY: FAILED` の行を足す。テストは C 系に `official_security_verdict` の単体（YES＋失敗→HIGH・YES＋読めた→OK・NO＋何でも→OK）と、FINAL の合成にその結果が入っていること、S 系に review-gate の選択肢 3 の記録の形と `OFFICIAL_SECURITY: FAILED` の扱い
