## 失敗分解
- 再現手順: PR #397（HEAD は STAGE_DONE implement の後）の CI「Harness Tests」（`bash scripts/claude/tests/run-all.sh`）。手元では、ブランチを I200 のコミットにした状態で `bash scripts/claude/tests/test_i197_adversarial_process.sh`
- 期待値: run-all がすべて pass
- 実際値: `run-all: pass=49 fail=1`。不合格は `scripts/claude/tests/test_i197_adversarial_process.sh` の 1 件だけ
- ログ: `FAIL S6 見張りと settings.json を変えていない expected=0 got=1`（Actions の run 40882143298 の Harness Tests）。ほかの CI（Backend・Frontend・E2E）はすべて pass

## 根本原因
- `test_i197_adversarial_process.sh:395-399` の S6 は「比べる相手（origin/develop）との merge-base から HEAD までに、`scripts/claude/hooks/pretooluse_guard.py` と `.claude/settings.json` を変えていない」ことを確かめる。これは I197（検証の仕組みの作り直し）の**ブランチの範囲**（I197 では見張りと設定を変えない）を守るための確かめで、I197 のマージ後も run-all に残り、**後のどのブランチにも同じ制約をかけている**
- I200 は見張りと設定を変えるのが本題なので、S6 は必ず落ちる。テストの対象（イシューの範囲の決まり）が、そのイシューの間だけ有効なものだった
- 実装の段階で手元の run-all が通ったのは、見張りと設定の変更が**未コミット**のまま流したため（S6 はコミットの差分だけを見る）。コミットした後の CI で初めて出た
- セキュリティ観点: 認証・認可・インジェクション・秘密の露出には当たらない（テストの範囲の誤り）。見張りと設定の変更そのものの安全性は、`test_i200_guard_narrowing.sh`・`test_settings_permissions.sh`・`test_pretooluse_container_guard.sh` などが確かめており、S6 はそれを確かめるものではない

|---|---|---|---|---|---|
| A（推奨） | S6 と FG-S6 を消す（イシューの範囲の確かめは、そのイシューの間だけのもの。I197 はマージ済み） | 影響なし（見張りと設定の正しさは別のテストが確かめる） | plan-writing-rules.md「決定論テストの対象の選び方」: 意図的な変更でしか壊れないもの（イシューの範囲）はテストにしない | 後のイシューが見張り・設定を変えるたびに同じ失敗が起きなくなる | 消すだけで新しいコードを足さない |
