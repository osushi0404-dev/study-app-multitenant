# I455 修正の診断（fix-loop・2026-11-12 10:10）

対象: コードレビュー `docs/reviews/I455_code_review_20261112_1006.md` の止める指摘 F6（Medium・REPRO=yes）だけ。F7〜F9 は Low で止める指摘ではないので直さない（台帳に残り retro）。

## 失敗分解
- 再現手順: 次の 2 行を `backend/studylogs/` のテスト以外のファイルに書き、`docker compose exec -T backend python -m pytest studylogs/tests/test_I455_org_scoped_querysets.py -k reason_comment` を流す
  ```python
  a = StudyLog.objects.filter(user=u).count()  # 組織で絞らない: 件数だけ
  b = StudyLog.objects.filter(user=u).values()
  ```
- 期待値: 2 行目（理由なしの読み出し）が付け忘れとして報告され、テストが落ちる
- 実際値: 2 行目の窓（直前の 1 行と同じ行）に 1 行目の行末コメントが入るので、理由ありと判定され、テストが通る
- ログ: `_missing_reasons`（`backend/studylogs/tests/test_I455_org_scoped_querysets.py:229-232`）の `window = lines[max(0, node.lineno - 2):node.lineno]` と `any(REASON_MARK in line for line in window)`

## 根本原因
窓の判定が「直前の行の、どこかに印の文字がある」だけで、その印が**直前の行だけを占めるコメント**（次の行の呼び出しの理由）なのか、**直前の行の呼び出しの行末コメント**（その行自身の理由）なのかを区別していない。敵対的レビュー 1 周目で「直前 3 行」を「直前 1 行」に狭めたが、行末コメントの場合の共有が残った。docstring の「離れたコメントを別の呼び出しと共有させない」と食い違う。

セキュリティの観点: 静的テストは付け忘れを見つける補助（普通の書き方の事故が対象・R5）。この穴で他組織のデータが直接漏れるわけではないが、付け忘れが CI を通りうる（OWASP A01 の再発防止の作りが弱まる）。

## 対応方針（全案＋推奨）
- 案 A（推奨）: 理由を認める場所を 2 つに限る。(1) 直前の行が**コメントだけの行**（前後の空白を除いて `#` で始まる）で印を含む (2) **同じ行**のコメントに印を含む。行末コメントは同じ行の呼び出しの理由としてだけ認める。コメントの判定は `tokenize` の COMMENT トークンで行う（文字列の中の印を拾わない）
  - セキュリティ: 付け忘れの見逃しが減る。新しいリスクなし
  - BP: Python 標準の `tokenize` で、コメントを文字列と区別する定石
  - 保守性: 判定が「コメントの行の番号の集合」2 つになり、窓の計算より読みやすい
  - リスク: 括弧で包んだ代入（`x = (` の次の行に呼び出し）では、理由を `x = (` の上に書くと窓から外れて落ちる（F7〔Low〕と同じ。今のコードには無い形で、落ちる側＝安全側に倒れる）
- 案 B: 文字列のまま「直前の行が `#` で始まる」だけを足す（tokenize を使わない）
  - 案 A より小さいが、同じ行の判定が文字列の部分一致のまま（文字列リテラルの中の印で通る・F7）
- 案 C: 窓をやめて、各呼び出しを含む文（statement）の直前の行だけを見る（AST の親の文の `lineno` を使う）
  - 括弧で包んだ代入にも強いが、親をたどる処理が要り、新しいコードが大きくなる（次の周の指摘の元になりやすい）

推奨: 案 A。粗く確実で、F6 の共有を塞ぎ、文字列の中の印も拾わない。
