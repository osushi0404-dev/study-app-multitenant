# I223 fix 診断メモ（20261105_1450）

## 失敗分解
- 対象: test-gate の手動テスト M-02 の NG（`docs/tests/open/I223_manual_test.md`）
- 再現手順: `docs/runbooks/github-app-setup.md`「5. 確かめる」どおりに、App の鍵で `gh auth status` を流す
- 期待値: 名義が `osushi0404-claude[bot]`（`GH_TOKEN`）であることが分かり、鍵の値は画面に出ない
- 実際値: `- Token: ghs_5613515_eyJ…`（App の新しい形式の長い鍵の大部分）が画面に出た。`gh` は鍵の最後の部分しか伏せない
- ログ: test-gate の M-02 の実結果。出た鍵は `gh api -X DELETE installation/token` で失効させ（その後の読み取りが `401 Bad credentials`）、控え `~/.cache/github-app/token` を消して取り直した

## 根本原因
- 手順書（`github-app-setup.md:46`）と手動テスト M-02 が、確かめ方として `gh auth status` を指示していた。`gh auth status` の伏せ字は昔の短い鍵（`gho_…`・`ghp_…`）向けで、App の新しい形式の鍵（`ghs_<番号>_<長い文字列>`）では大部分が見える。計画の段階で、この確かめ方が鍵を出すかを確かめていなかった
- 同型: `docs/runbooks/harness-audit.md:29` も、本物の `gh` に保存されたログインの確かめ方として `/usr/bin/gh auth status` を指示している（今の保存されたログインは無効の bot のもので鍵は出ないが、bot が戻って有効になれば同じ形で出うる）
- セキュリティ観点: 書き込みのできる 1 時間の App の鍵が、端末の画面と会話の記録に出る（秘密情報の露出・OWASP A02 相当）。出た鍵は失効させ済みで、残りの影響は無い。見張りは `gh auth status -t`・`gh auth token` を確認にしているが、`-t` なしの `gh auth status` が鍵の大部分を出すことは見ていない（見張りは安全装置なので、このイシューでは変えない）

## 対応方針（全案＋推奨）
- **案 A（推奨）: 確かめ方を `gh auth status --json hosts --jq '.hosts["github.com"][] | select(.active) | .login + " " + .tokenSource + " " + .state'` にする**（`--json` で名義・鍵の出どころ・状態の欄だけを取り出し、鍵の欄を出さない。2026-11-05 に手元で `osushi0404-claude[bot] GH_TOKEN success` を確認）
  - セキュリティ: 鍵の値の欄を取り出さないので画面に出ない。gh の公式の `--json` の欄の指定
  - BP: 表示の伏せ字に頼らず、要る欄だけを取り出す
  - 保守性: 手順書 2 か所（`github-app-setup.md:46`・`harness-audit.md:29`）・手動テスト M-02・計画書 4-8 の 5. を直す
  - リスク: `gh` が古いと `--json` が無い（エラーで止まるだけで鍵は出ない＝安全側）
- 案 B: `gh auth status 2>&1 | grep -v 'Token:'` で鍵の行を消す
  - 表示の形（`Token:` の行）に頼る。形が変わると出る（fail-open）
- 案 C: 名義は確かめず、`gh api repos/osushi0404-dev/study-app-multitenant --jq .full_name` で動くことだけを見る
  - 鍵は出ないが、どの名義で動いているか（App か、保存されたログインか）が分からない
- 案 D: 見張り（`pretooluse_guard.py`）で `gh auth status` を確認にする
  - 安全装置の変更で、このイシューの範囲外（止めて聞く条件 2）。手順書を直せば、ふつうの書き方の事故は止まる。retro で扱う
- 推奨: **案 A**（M-02 は直した確かめ方でやり直す）
