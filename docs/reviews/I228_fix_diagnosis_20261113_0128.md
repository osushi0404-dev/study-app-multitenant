# I228 診断メモ（fix-loop・手動テスト No.3 の NG）

## 失敗分解
- 再現手順: `bash scripts/claude/check-permission-prompt.sh bash 'docker compose ps --status running --services'`
- 期待値: exit 0（承認なしで実行される。review-gate §3-1 で、敵対的レビューの起動の前に Claude が流す手順のため）
- 実際値: exit 10「承認画面が出る」
- ログ: `docs/tests/open/I228_manual_test.md` No.3 の備考。基本レビューの台帳 F4（`docs/reviews/I228_code_review_20261113_0112.md`）が同じ疑いを出していた

## 根本原因
- `.claude/settings.json` の allow は `Bash(docker compose ps)`（引数なしの完全一致）だけで、`--status running --services` を付けた形は当たらない。I228 で `.claude/skills/review-gate/SKILL.md` §3-1 に足した手順が、allow の形を確かめずに引数つきのコマンドを書いた
- セキュリティ観点: 承認画面が出るのは止まる向き（危ない操作が通る向きではない）。認証・インジェクション・機密データの露出には当たらない。流れ（review-gate）が承認待ちで止まる「流れが動かなくなる」問題

## 対応方針（全案＋推奨）
- 案 A: 確かめのコマンドを allow 済みの `docker compose ps`（引数なし。既定で動いているコンテナだけを出す）に変え、出力の SERVICE 列に `backend` が無ければ `docker compose up -d backend` を流す
  - 利点: 設定を変えない。副作用の無い確かめが残る
  - 欠点: 表の出力を目で読む手順が 1 つ増える（判定が Claude の読みに依存する）
- 案 B: `.claude/settings.json` の allow に `Bash(docker compose ps *)` を足す
  - 欠点: `.claude/settings.json` は GitHub から復旧できない例外の集合（`path_risk_trigger()`）で、変えると高リスク判定・敵対的レビューが要る。範囲（計画の「変更しない」）も変わる。重すぎる
- 案 C（推奨）: 確かめを省き、アプリ（`backend/`）を変えたイシューでは起動の前に常に `docker compose up -d backend` を流す（動いていれば何もしない＝冪等）
  - 利点: コマンド 1 つで、表を読む判断が要らない（粗く確実）。allow の `Bash(docker compose up *)` に当たる。設定を変えない
  - 欠点: 初回はイメージの作成で時間がかかりうる（アプリのイシューではふだんコンテナを使っているので、多くは何もしないで終わる）
  - 確かめ: allow の同じ規則（`Bash(docker compose up *)`）に当たり副作用の無い `docker compose up --help` で、承認画面が出ないことを `check-permission-prompt.sh` で確かめる（実際に `up -d` を流すとハーネスのワークツリーでコンテナが立ち上がるため、代わりの操作で確かめる・`docs/runbooks/plan-writing-rules.md`「実施者の区別」の決まり）。手動テスト No.3 を、この確かめに置き換える

## 影響調査
- 同型: I228 で足した手順のうち、Claude が流すコマンドは §3-1 のこの 2 つだけ。`docker compose exec -T backend …`（実験役の案内）は手動 No.1 で承認なしを確認済み
- 他の呼び出し箇所: `docker compose ps --status` を使う手順はほかに無い（`grep -rn "compose ps --status" .claude docs/runbooks scripts` で I228 の §3-1 だけ）
- 関連機能: 計画書 4-3 と 9.（自律判断）の記述を案 C に合わせる。方式（コンテナを起こしてから起動する）・範囲・受け入れ条件は変えないので計画レビューは通り直さない
