# I074 fix-loop 診断メモ（手順3.5 入力）— No5: SKILL.md の記録・レビュー明示の欠落

対象: fix-loop/SKILL.md の手順1/2/3 が成果物の記録先を明示せず、各成果物のレビュー対応も表になっていない問題（手動テスト No5 で Human 検出）。

## 失敗分解
- 再現手順: `.claude/skills/fix-loop/SKILL.md` の手順1/2/3（L27–34）を文脈ゼロで読む。
- 期待値: (i) 手順1（失敗分解）・手順2（根本原因）・手順3（対応方針＝全案）の成果物が**ドキュメントに記録される**旨が本文から自明。(ii) 「報告書（原因調査）／修正方針／修正内容／テスト」の**どれがどのゲートでレビューされるか**が一目で分かる。
- 実際値: 手順1/2/3 は「分解して報告」「調査・分析して報告」「複数案提示」止まりで、**記録先（手順3.5 の診断メモ）への言及がない**。また「診断／実装／テストレビュー」ラベルがユーザー語「報告書／修正方針／修正内容」に対応づかず、レビューが「自動テストのみ」と誤読され得る。
- 該当箇所: SKILL.md L27–34（手順1–3）、冒頭説明（L11–13）にレビュー対応表なし。

## 根本原因
成果物→ドキュメント→レビューの導線は設計上存在する（手順3.5 の診断メモ章立て＝失敗分解／根本原因／対応方針を fix-diagnosis-reviewer が審査、手順5.5 が修正内容、手順6.5 がテスト）。しかし **手順1/2/3 本文にその記録先が書かれておらず**、口頭報告と誤読して記録を残さないリスクがある。加えてレビュー対応が本文に散在し表になっていないため網羅が読み取れない。**レビュー機構・記録機構は既存で充足しており、欠落は記述の明示のみ**。

## 対応方針（全案＋Claude 推奨）
- **案1（Claude 推奨・採用）**: 記述明確化のみ。
  1. **手順1/2/3 の各末尾に記録先を明示**: 「→ 手順3.5 の診断メモ（`docs/reviews/I###_fix_diagnosis_<ts>.md`）の『失敗分解／根本原因／対応方針』に記録する」。口頭でなくドキュメント化を強制。
  2. **冒頭にレビュー対応表を追加**: 「原因調査結果＋修正方針→手順3.5 診断レビュー／修正内容→手順5.5 実装レビュー／テスト結果→手順6.5 テストレビュー」を明記し、3成果物すべてが審査対象と一目で分かるようにする（「自動テストのみ」の誤読を排除）。
  3. **回帰 TC 追加**: `test_fix_review.sh` に「SKILL.md が手順1/2/3 の診断メモ記録と3成果物のレビュー対応を含む」検査＋false-green 反証を追加し、記述の後退を検知する。
- **案2（不採用）**: 手順1/2/3 を手順3.5 にマージし1ステップ化 → 手順番号がずれ、既存 TC（TC-19 の 3.5/5.5/6.5 検査等）・plan/AC・他参照に波及。既存構造を壊す過剰変更。
- **案3（不採用）**: 現状維持 → No5 NG のまま。
- セキュリティ: 指示ファイルの記述追記のみ。認証・認可・インジェクション・機密露出の新規リスクなし。
