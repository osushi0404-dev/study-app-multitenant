# I202 fix-loop 診断メモ（review-gate 2 周目の止める指摘 F11）

- 対象の記録: `docs/reviews/I202_code_review_20261027_1630.md`
- 止める指摘: F11（High・harness・STOP=flow・再現あり）。ほかの open の指摘（F1・F3〜F10・F12〜F14）は止めない指摘で、ここでは直さない

## 失敗分解
- 再現手順: 1 周目で `a.py` に再現つきの High（F1）が付く。fix-loop が `a.py` を develop の中身に戻し、同じコミットで `b.sh` も直す。2 周目の差分のレビューを流す
- 期待値: レビュー役の入力の git diff に、`a.py` の取り消しの差分が入り、F1 を resolved と書ける
- 実際値: 範囲（`SCOPE_FILE`＝`delta_files`）は `b.sh` だけになる（`a.py` はブランチが変えたファイルから外れる）。`code-review.sh:887` の分岐は範囲が 1 件でもあれば範囲のファイルの差分だけを見せるので、`a.py` の取り消しが見えない。F1 は open のまま HIGH で、周が収束しない
- ログ: 記録の F11 の再現の欄のとおり

## 根本原因
前の直し（F2）で、取り消しの差分を見せるのを「範囲が空のとき」だけにした。取り消し・削除で範囲から外れたファイルは、範囲が空かどうかに関係なく見せる必要がある。つまり、レビュー役に見せるファイルの一覧が「範囲（ブランチが今も変えているファイル）」だけで、「起点の時点ではブランチが変えていて、その後に develop の中身に戻した・消したファイル」が入っていない。

セキュリティの観点: 関係しない（止まり続ける向きの崩れ）。

## 対応方針（全案＋推奨）
- 案 A（推奨）: レビュー役に見せるファイルの一覧を「範囲 ∪ 取り消したファイル」にする。取り消したファイル＝「起点の時点でブランチが変えていたファイル（`branch_own_files origin/develop "$SINCE"`。F2 の共通化で rev を渡せる）」のうち、起点の後に変わり（`OUTSIDE_SINCE_FILE`）、今は範囲に無いもの。この一覧を git diff と入力の「範囲のファイル」「変更の種類」に使う。行の塊（`delta_hunks`）と台帳の SCOPE は変えない
  - セキュリティ影響: なし。BP: 既にある関数の組み合わせ
  - リスク・副作用: develop の取り込みだけで変わったファイル（ブランチが起点の時点で変えていなかったもの）は入らないので、無関係な差分は増えない（2 周目 F13 の心配を広げない）。数行
- 案 B: 範囲が空かどうかに関係なく、起点の後に記録の場所の外で変わったファイルすべて（`OUTSIDE_SINCE_FILE`）の差分を見せる
  - メリット: 1 行で済む
  - デメリット: develop の取り込みで入った無関係な差分も見せる（入力の 100KB を食い、レビュー役が無関係な指摘を書く）
- 案 C: 取り消しの直しを fix-loop の決まりで禁止する
  - デメリット: 正しい直し方を封じる。決まりを増やす

推奨は案 A（無関係な差分を増やさずに、取り消し・削除だけを確実に見せる）。

## 影響調査
- 同型のバグ: レビュー役に見せるファイルの一覧（`SCOPE_FILE`）を使う箇所は、git diff（887 行）・入力の「差分のレビューの範囲のファイル」（930 行付近）・「変更の種類」（`ledger_kinds "$SCOPE_FILE"`）・「変更ファイル一覧」（`FILES_NOTE` の節）の 4 か所。案 A でまとめて「範囲 ∪ 取り消したファイル」の一覧（`SHOWN_FILES_FILE`）に替える。`SCOPE_FILE` 自体（範囲の数の表示・`delta_files` の結果）は変えない
- 関連機能: 行の塊・台帳の SCOPE・gate-check は `SCOPE_FILE` を使わない（影響なし）
- 前の直し（F2）の「範囲が空で外が変わったとき」の分岐は、案 A の一覧に含まれるので 1 つにまとめる
- テスト: W4b に「取り消しと同時に別のファイルも直す」混在の項目（W4c）と失敗注入を足す
