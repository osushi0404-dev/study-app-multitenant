# I586 修正の診断メモ（MT-14 の NG）

## 失敗分解
- 再現手順: 本人の利用者で http://localhost:<FRONTEND_PORT> にログイン → クイズを始める → 問17 を表示する（ユーザーの画面 2 枚・2026-11-27）
- 期待値: 問番号・選択肢の記号（ア〜エ）と本文の区切りがはっきり分かり、読みやすい（MT-14）
- 実際値: 見出しが「問17 スタースキーマで…」、選択肢が「ア ディメンションテーブル」で、記号と本文の間が半角スペース 1 つだけなので、記号が本文の一部のように見える。ユーザーの言葉: 「UIがよくない。「問17」と問題文、アイウエと選択肢が隣接しすぎてないか？」
- ログ: なし（表示の問題）

## 根本原因
- データの書き方: 計画書 9（`plan_I586.md:147`）で、画面が選択肢の記号を出さない（`QuizSession` は `choice.text` だけを出す）ため、選択肢の本文の先頭に「ア 」を付けると決めた。区切りを半角スペースにしたので、本文と見分けにくい。問題文の先頭の「問N 」も同じ（作業の記録で、問題冊子どおり付けると決めた）。問番号は出典の欄（問題文のすぐ下）にもあり、重なっている
- アプリの側: 画面に記号の表示の仕組みが無い（選択肢は本文だけ・問題文は見出しのまま）。過去問のように記号で指す問題では、データに記号を書くしかない
- セキュリティ: 該当なし（表示する文字の並びだけ。入力は管理者の import と画面の編集で、React がエスケープして出す）

## 対応方針＝全案＋推奨
- 案 A（データで区切る・推奨・ユーザーが選んだ）: 25 問の問題文の先頭の「問N 」を外す（問番号は出典の欄に残る）。選択肢の先頭を「ア 」から「ア．」（全角のピリオド）に変える。Markdown と DB の両方を直す（DB は import の `--skip-duplicates` では上書きされないので、`manage.py shell` で 25 問の問題文と 100 個の選択肢の本文だけを置き換え、一覧の一時保存を消す）。手順書 §11 と計画書 9 の書き方も直す
  - よい点: コードを変えずに今すぐ直る。元に戻すのも同じ置き換えで済む
  - よくない点: 記号を文字で持つ形は変わらない（ほかの科目でも同じ書き方が要る）。「（一部改変）」には当たらない（問番号は出典にあり、記号の後の区切りは表記の体裁で、問題冊子の文や記号は変えない）
- 案 B（アプリで記号を本文と分けて出す）: 画面の選択肢に記号の欄を足し、見出しと本文を分けて表示する。コード・API・既存データの変更が要り、I586 の範囲（データの登録と手順書）を超える。ユーザーの選択どおり別のイシューに起票する
- 案 C（何もしない）: ユーザーの NG が残る。採らない
- 推奨: 案 A を今行い、案 B は起票する（ユーザーの選択・2026-11-27）

## 影響調査の実施有無と結果
- 実施: 25 問すべての問題文が「問N 」で始まり、選択肢は「ア 」「イ 」「ウ 」「エ 」で始まる（MT-10 で確かめた形）。置き換えは先頭だけに限り、本文の途中の「ア」などは変えない
- 同型の問題: 画像の選択肢（問3・6・9・14）は「ア（画像のア）」で、区切りの空白は無い。これは「ア．（画像のア）」ではなく「ア．画像のア」にそろえる
- 波及: 照らし合わせのスクリプト（MT-10）は「問N 」で問番号を取っているので、出典の欄から取るように直して流し直す。管理画面のプレビューは「A. ア．…」と出る（記号が 2 つ並ぶ件は使いにくさの候補にあり、案 B で扱う）
- 答えた後に自分の誤答に印が出ない件（使いにくさの候補）も、アプリ側の話なので案 B のイシューに入れる
