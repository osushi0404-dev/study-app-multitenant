# I437 fix-loop 診断メモ（20261113_0002）

対象: `docs/reviews/I437_code_review_20261112_2349.md` の「止める指摘」F1（Medium・SECURITY=yes・STOP=ac:4）

## 失敗分解
- 再現手順: ログイン済みの利用者が `POST /api/auth/change-password/` をフォーム形式で `current_password=誤り&new_password=X&confirm_password=X` で送る → 400 → `ErrorContextMiddleware._log_error_response` → `_safe_body` が本文を記録する
- 期待値: パスワードを持つ欄はすべて `[REDACTED]`
- 実際値: `current_password`・`new_password` は伏せられるが、`confirm_password`（`backend/accounts/serializers.py:275`・`ChangePasswordSerializer`）は一覧に無く、新しいパスワード X が `django.request` のログ（`errors.jsonl` など）に平文で残る
- ログ: レビュー役の再現（コードを読んだもの）。伏せる一覧は `backend/core/enhanced_logging.py:16-24`

## 根本原因
- 伏せる欄を「欄の名前の完全一致の一覧」で持っているので、同じ意味の欄が別の名前（`confirm_password` と既存の `password_confirm`）で増えると漏れる。計画（R4）は個人情報の欄について完全一致を選んだが、秘密の欄も同じ方式のままにしていた
- 同型の調査（影響調査）で、もう 1 つ見つかった: `backend/accounts/views.py:544-584`（`FieldValidationView`・`POST /api/auth/validate-field/` 相当）は `field`（`email`・`user_id`・`password`）と `value`（その値）で送る。`value` は一覧に無い。この API は検証の失敗を 200 で返すが、`field`／`value` が無い・未対応の欄のときの 400 と、`AppAnonRateThrottle` の 429 は 4xx なので本文が記録され、`value` にパスワード・メールアドレスが平文で残る
- 調べた範囲: `backend/` の serializer の秘密の欄の名前（`password`・`password_confirm`・`token`・`new_password`・`current_password`・`confirm_password`）と、ビューが `request.data` から直接読む欄の名前（`refresh`・`field`・`value`・`subject_id` など）を全件 grep（2026-11-13）。上の 2 つのほかに漏れる欄は無い
- セキュリティ観点: OWASP A09／A02（ログへの機密データの露出）。認証・認可・入力検証には関係しない

## 対応方針（全案＋推奨）
### 案 A: 完全一致の一覧に `confirm_password` と `value` を足す
- セキュリティ: 今の 2 つの漏れは止まる。今後 `password2`・`new_password_confirm` のような名前が増えるとまた漏れる
- BP・保守: 計画どおりの方式のまま。一覧を足すだけ
- リスク: 小さい。差分 1 行

### 案 B: 秘密は「名前の一部に `password`・`token`・`secret`・`refresh`・`api_key` を含む欄」で伏せ、個人情報（`email`・`first_name`・`last_name`・`user_id`）と `value` は完全一致のまま
- セキュリティ: 秘密の欄の名前の揺れ（`confirm_password`・`password2`・`refresh_token`・`old_password`）を今後も止める。粗く確実な形（fail-closed 側）
- BP・保守: 秘密の一覧と個人情報の一覧で照らし方が分かれるが、どちらも短い。`logging_decorators.mask_sensitive_data`（使われていない）と同じ「名前の一部」の考え方
- リスク: 名前に `token` などを含む秘密でない欄（例: 今は無い）まで伏せる。原因調べの手がかりが減るだけで漏れは起きない。個人情報は R4 の理由（`subject_ids` などを巻き込まない）で完全一致のまま
- 計画の方式（4-5「今までと同じく欄の名前の完全一致で伏せる」）を秘密の欄について変えるので、計画書を直して計画レビューを通す

### 案 C: 許可リスト（記録してよい欄だけを残す）
- セキュリティ: 最も強い
- BP・保守: API ごとに残す欄を持つ必要があり、本イシューの範囲（伏せる欄を足す）を大きく外れる。設計確認メモの決定（「個人情報の欄だけ伏せる・ほかの入力は残す」）とも合わない
- リスク: 大きい

### 推奨: 案 B
- 秘密の欄はパスワードそのものが漏れる被害が大きく、名前の揺れで漏れたのが今回の原因。名前の一部で止めると、同じ型の漏れを根本から止められる。個人情報は計画の R4 のとおり完全一致にし、`value` は `FieldValidationView` の値（パスワード・メールアドレスが入る）なので完全一致で足す
- 直し方: `SENSITIVE_BODY_FIELDS` を「名前の一部」の語の一覧（`password`・`token`・`secret`・`refresh`・`api_key`）に、`PERSONAL_BODY_FIELDS` に `value` を足し（名前は完全一致の欄の一覧）、`_safe_body` を `any(word in key.lower() for word in SENSITIVE_BODY_WORDS) or key in PERSONAL_BODY_FIELDS` で伏せる形にする
- テスト: TC-07 に `confirm_password`・`value`・`refresh_token` を足す（直す前のコードで落ちることを確かめる）

## 影響調査の実施有無と結果
- 実施した。同型（一覧に無い名前の秘密・個人情報の欄）: `FieldValidationView` の `value`（上）。ほかに無し（serializer・`request.data` の欄の名前を全件 grep）
- 他の呼び出し箇所: `_safe_body` を呼ぶのは `ErrorContextMiddleware._log_error_response` だけ。`logging_decorators.mask_sensitive_data` は使われていない（範囲外・台帳 F5）
- 関連機能への波及: ログの中身だけ。API の応答・画面・DB は変わらない
