# I444 診断メモ（fix-loop 1）

対象: `docs/reviews/I444_code_review_20261111_1847.md` の止める指摘 F1（SEV=High・STOP=ac:6・REPRO=yes）。ほかの台帳の指摘（F2〜F7）は止める指摘ではないので直さない（retro へ）。

## 失敗分解
- 再現手順: review-gate の決定論ゲートが `docs/tests/open/I444_auto_test.md` の「決定論ゲート（自動実走）」の各行を `timeout "${GATE_TIMEOUT:-120}"`（`scripts/claude/code-review.sh` 409〜420 行）で流す。その中の `bash scripts/claude/tests/test_guard_corpus_diff.sh`
- 期待値: exit 0
- 実際値: exit 124（120 秒の時間切れ）
- ログ: 記録の 8 行目「`bash scripts/claude/tests/test_guard_corpus_diff.sh` → exit=124 ❌ FAIL」。同じスクリプトを implement で手で流したとき（`--rebuild`・上限なし）は完走して OK（作業記録 15419 件・新しく確認 3 件）。所要は数分（作業記録の各コマンドを、基準と作業ツリーの 2 つの見張りに 1 件ずつ別プロセスで渡す・12 並列）

## 根本原因
- corpus diff は「過去の作業記録のすべてのコマンドを 2 つの見張りで判定し直す」重い確かめで、所要は記録の件数に比例する（primary だけの 3701 件でも数分）。決定論ゲートの 1 行あたりの上限 120 秒には、もともと収まらない
- これまでワークツリーでは、作業記録のフォルダ名の作り方の誤り（`.` を `-` にしない）で SKIP（exit 0）になり、ゲートでは数秒で「通って」いた。5-6 でその誤りを直したので、本当に走るようになり、時間切れが表に出た。つまり「ゲートに置いた corpus diff」は以前から実際には何も確かめていなかった（偽の合格）
- 計画の誤り: auto_test の決定論ゲートに `test_guard_corpus_diff.sh` を入れた（手順書 `danger-ops.md` は「見張りを直したら、コミットの前に流す」重い確かめとしており、ゲートの時間の上限を考えていなかった）
- セキュリティ観点: 認証・インジェクション・機密データの露出には当たらない。corpus diff の作業記録・キャッシュの扱い（本人だけが読める権限）は変えない

## 対応方針（全案＋推奨）
### 案 A（推奨）: corpus diff を決定論ゲートから外し、TC-06 として implement・test-gate で手で流して結果を記録する
- 内容: `I444_auto_test.md` の決定論ゲートの行から `bash scripts/claude/tests/test_guard_corpus_diff.sh` を消す。TC-06 に「implement の後と test-gate で `bash scripts/claude/tests/test_guard_corpus_diff.sh --rebuild` を上限なしで流し、OK（新しく確認・停止が 1% 以内・異常終了 0）と件数を記録する」と書く。計画書 6. の表・計画変更記録に 1 行
- セキュリティ影響: なし（確かめの置き場所を変えるだけ。見張りの判定は変えない）
- ベストプラクティス: 手順書の位置づけ（コミットの前に流す重い確かめ）と一致する。ゲートは速い決定論の確かめだけにする
- 保守性: コードの変更なし。他の見張りのイシューの auto_test も同じ形にそろえられる
- リスク・副作用: ゲートで自動で流れなくなる。ただし以前もワークツリーでは SKIP で実際には流れておらず、確かめが減るわけではない。test-gate の記録で人に見える
- 新しい安全装置: 足さない
### 案 B: corpus diff を速くする（同じコマンドの重複を除く・見張りを 1 プロセスで何件も判定する）
- 内容: `guard_corpus_diff.py` で重複を除き、見張りを import して関数を直接呼ぶ
- リスク: 重複除去だけでは 120 秒に収まる保証が無い（記録は増え続ける）。見張りの import 呼び出しは、`_WRITTEN` などの大域の状態が判定の間で残り、別プロセスでの判定と結果が変わりうる（偽の差分）。新しいコードが大きく、次の周の指摘の元になる
### 案 C: ゲートの上限（`GATE_TIMEOUT`）をこの行だけ延ばす
- 内容: `code-review.sh` に行ごとの上限の指定を足す
- リスク: 共有の仕組み（code-review.sh・その決定論テスト）を変える。範囲を越える。記録が増えれば再び時間切れ
### 推奨: 案 A
