# I223 fix 診断メモ（20261105_1348）

## 失敗分解
- 再現手順: PR #414 の CI（run 41968150448・job Harness Tests）で `bash scripts/claude/tests/run-all.sh` を流す。手元では `bash scripts/claude/tests/test_i223_gh_app.sh` を、git が記録した実行権（644）のままの写しで流すと同じになる
- 期待値: `test_i223_gh_app.sh` が pass=16 fail=0
- 実際値: `FAIL G4 リポジトリの版で合格（期待: G4 OK / 実際: G4 NG）`・`pass=15 fail=1`（ほかのテスト 50 本は合格。手元〔/mnt/c〕では 16/16 合格）
- ログ: `gh run view 41968150448 --job 127049895975 --log-failed` の該当行は上のとおり

## 根本原因
- この端末のリポジトリは `/mnt/c`（NTFS）にあり、`git config core.filemode` が `false`。`chmod +x` しても git は実行権を記録せず、新しいファイルは `100644` で入った（`git ls-files -s scripts/claude/gh-app/` で確認: `gh`・`gh-app-token`・`install.sh`・`test-session.sh` がすべて 100644）
- `scripts/claude/gh-app/gh`（入口）は、同じフォルダの `gh-app-token` を `"$dir/gh-app-token"` と**直接実行**している。CI の checkout では実行権が無いので `Permission denied` で失敗し、入口は `gh-app-token: 鍵を受け取れませんでした` で exit 1 → G4 の 1 つ目（読み取りだけの鍵が渡る）が NG
- G1〜G3 は `bash "$S/gh-app/gh-app-token"` と bash に渡して起動するので、実行権に関係なく通る。手元（/mnt/c）はすべてのファイルが実行できるように見えるので、手元では起きない
- 本番（`~/.local/bin/` に入れたもの）は `install -m 755` で入れるので実行できる。ただし、リポジトリのファイルを直接使う（新しい端末で `install.sh` の前に試す・別の方法で写す）と同じ失敗になる。実行権に頼る作りそのものが原因
- セキュリティ観点: 失敗は「鍵を受け取れない」側（書き込みの鍵も読み取りだけの鍵も渡らない＝fail-closed）で、秘密の漏れ・権限の取り違えにはならない。認証・認可・インジェクションに関わる変更ではない

## 対応方針（全案＋推奨）
- **案 A（推奨）: 入口が `gh-app-token` を `bash "$dir/gh-app-token"` で起こす（実行権に頼らない）**
  - セキュリティ: 変わらない（起こすファイル・渡す環境変数は同じ）
  - BP: リポジトリの他のスクリプトの呼び方（`bash scripts/claude/<名前>.sh`）と同じ。実行権を記録しないファイルシステムでも動く
  - 保守性: 1 行の変更。リポジトリから直接使っても、写しても動く
  - リスク・副作用: bash を 1 つ起こすのは今と同じ（今も `#!/usr/bin/env bash` で bash が起きる）。`env` を探す分だけ軽くなる
- 案 B: `git update-index --chmod=+x` で 4 本の実行権を git に記録する
  - セキュリティ: 変わらない
  - BP: 実行するファイルに実行権を付けるのはふつう。ただし、このリポジトリの他のスクリプトは 100644 で `bash` に渡す決まりで、それと揃わない
  - 保守性: core.filemode=false の端末で、写す・作り直すたびに実行権が落ちる（気づきにくい）
  - リスク: CI は直るが、実行権に頼る作りは残る
- 案 C: A と B の両方
  - A だけで実行権に頼らなくなるので、B を足す理由が無い（足すと「実行権が要る」と誤解される）
- 推奨: **案 A**。G4 は今のまま（写しを 100644 で作る CI と同じ条件で、入口が動くことを見ている）。加えて、テストの写しで実行権を落とす（`chmod 644`）ことで、手元（/mnt/c）でも CI と同じ条件になり、同じ見落としを手元で捕まえられるようにする（失敗注入: 入口の `bash ` を消すと、手元でも G4 が NG になることを確かめる）

## 影響調査の実施有無と結果
- 実施した。同型（リポジトリのファイルを、`bash` に渡さずに直接実行する所）を `grep -rnE '"\$[A-Za-z_]+/[A-Za-z_.-]+"( |$)|exec "\$' scripts/claude/gh-app scripts/claude/test-session.sh` と読みで探した:
  - `scripts/claude/gh-app/gh`: `"$dir/gh-app-token"`（今回の原因）・`exec "$REAL_GH"`（本物の `/usr/bin/gh`。リポジトリのファイルではない）
  - `scripts/claude/test-session.sh`: `exec "${CLAUDE_BIN:-claude}"`（`claude` 本体。リポジトリのファイルではない）
  - `scripts/claude/gh-app/install.sh`: `"$BIN/gh"`（`install -m 755` で入れた後の `~/.local/bin/gh`。実行権あり）
  - 手順書（`github-app-setup.md`・`plan-writing-rules.md`）は `bash scripts/claude/...` で呼ぶ形だけ
- 他の呼び出し箇所: git の credential helper は `~/.local/bin/gh`（入れた後の版）を呼ぶので影響なし。テストの G4 の FG（`[ -n "${GH_APP_READONLY:-}" ] ||` を消す）は直す行と別の行なので影響なし
- 関連機能: この端末の `~/.local/bin/` は `install -m 755` で入れたので、今の push・`gh` は動いている（M-02 の前提は変わらない）。直した後に `install.sh` で入れ直す
