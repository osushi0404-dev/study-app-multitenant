## 背景/目的

I043（停止条件・重大度・高リスク判定）・I044（/security-review 新設）でレビューの「構造」を整備した。
次ステップとして `review_perspective_framework.md` が定義する8観点フレームワークへの整合を進める。

現行の `/plan-issue-review` および `/code-review` は以下の3観点がゼロカバーである:
- **P3（データ整合性・変更安全性）**: DB制約・トランザクション・マイグレーション安全性
- **P5（運用性・障害対応性）**: 構造化ログ・タイムアウト・フォールバック・Feature Flag
- **P8（コスト・保守負荷）**: インフラコスト・属人化リスク・維持コスト

本イシューで両スキルに P3・P5・P8 の確認セクションを追加し、設計・実装段階でこれらの問題を検出できるようにする。

## 変更点一覧

### 変更A: `.claude/skills/plan-issue-review/SKILL.md`

「Claude Code ベストプラクティス」セクションの直後・「レビュー指摘一覧」の直前に以下の3セクションを追加する。

**P3. データ整合性・変更安全性**（設計段階の確認）:
- DB制約（NOT NULL・UNIQUE・FK・CHECK）の設計方針が計画書に含まれているか
- アプリ側バリデーションとDB制約の責務分担が明確か
- トランザクション境界が計画書に明示されているか
- 冪等性が必要な処理に二重送信対策の設計があるか
- 同時更新・競合更新・排他制御の設計方針があるか
- マイグレーション手順が安全か（ロールバック可能か）
- 後方互換性を壊す変更になっていないか
- API/DB/イベント変更の影響範囲が把握されているか
- ForeignKey 削除時の挙動（CASCADE/PROTECT/SET_NULL）が計画書に明記されているか
- インデックス設計の適切性（必要なインデックスがあるか、過剰・不足がないか）

**P5. 運用性・障害対応性**（設計段階の確認）:
- ログが構造化され原因追跡に必要な情報を持つ設計か（request_id・user_id・tenant_id）
- タイムアウト・リトライ・フォールバックの方針が計画書に含まれているか
- 外部API・非同期ジョブ・バッチ失敗時の扱いが設計されているか
- Feature Flag や段階リリースが必要な変更ではないか（大規模なUI変更・外部公開API追加等の場合に検討）
- 切り戻ししやすい設計か
- Runbook・管理者向け導線が必要な箇所で不足していないか
- 新機能で追加する監視項目・アラートの定義が計画書に含まれているか

**P8. コスト・保守負荷**（設計段階の確認）:
- インフラ・DB・外部API・ジョブ実行のコストが妥当か
- 運用者の手作業が増えすぎないか
- 将来の機能追加・修正時に変更箇所が増えすぎないか
- 要件規模に対して過剰な構成を採用していないか
- 長期保守で属人化しやすい構造になっていないか
- 監視・テスト・デプロイ・リリース運用の維持コストが現実的か
- ドキュメント保守コスト（README・APIドキュメント・Runbookの更新要否）

### 変更B: `.claude/skills/code-review/SKILL.md`

「モダンなウェブアプリ開発」セクションの直後・「指摘の重大度に基づいて判定する（step 7）」の直前に以下の3セクションを追加する。

**P3. データ整合性・変更安全性**（実装段階の確認）:
- DB制約（NOT NULL・UNIQUE・FK・CHECK）が実装に反映されているか
- アプリ側バリデーションとDB制約の責務分担が計画書の設計方針通りか
- トランザクション境界が適切に実装されているか
- 冪等性が必要な処理に二重送信対策が実装されているか
- 同時更新・競合更新・排他制御が考慮されているか
- マイグレーション手順が安全か（ロールバック可能か）
- 後方互換性を壊す変更になっていないか
- ForeignKey 削除時の挙動（CASCADE/PROTECT/SET_NULL）が意図と一致しているか
- インデックス設計が適切か（必要なインデックスがあるか、過剰・不足がないか）

**P5. 運用性・障害対応性**（実装段階の確認）:
- ログが構造化され原因追跡に必要な情報を持っているか（request_id・user_id・tenant_id）
- タイムアウト・リトライ・フォールバックが計画書の方針通りに実装されているか
- 外部API・非同期ジョブ・バッチ失敗時の扱いが実装されているか
- 切り戻ししやすい実装になっているか
- Runbook・管理者向け導線が必要な箇所で実装されているか
- 新機能の監視項目・アラートが定義通りに実装されているか

**P8. コスト・保守負荷**（実装段階の確認）:
- 要件規模に対して過剰な構成を採用していないか
- 長期保守で属人化しやすい実装になっていないか（複雑すぎる処理・マジックナンバー等）
- 監視・テスト・デプロイ・リリース運用の維持コストが増加していないか
- ドキュメント（README・APIドキュメント・Runbook）の更新が必要な箇所で更新されているか
