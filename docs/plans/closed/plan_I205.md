## 1. 背景/目的
I197 で基本レビューを「台帳＋直した差分だけのやり直し＋止めるのは Blocker・High」にした。しかし次の 3 つが残っている。
- ① 止める基準がアプリ本体とハーネスで同じ。GitHub から復旧できるハーネスの変更でも High で止まり、直すとまた差分ができて周が回る。
- ② 差分の中か外かをファイル単位で決めている。そのため、レビュー役が昔からある穴を新しい High として書くと止まる。
- ③ アプリ本体は Medium を止めていないが、ユーザーの方針は「イシューに関係するものは指摘 0」。

目的は次の 3 つ。
- 止める基準を変更の種類で分ける（アプリ本体／GitHub から復旧できないハーネス／それ以外のハーネス）。
- 止めるかどうかを、レビュー役の感覚の重大度ではなく、FINDING 行の欄（当たる止める条件・再現）からスクリプトが決める。
- 差分の中か外かを行で決める。

## 4. 変更点一覧（具体）

### 修正アプローチ
次の 3 つを揃える。
- **指摘を出す側（code-reviewer）**: 止める指摘には「当たる止める条件」と「再現」を書く。ハーネスは止める条件の一覧に当たるかを答える（閉じた問い）。
- **止めるかを決める側（code-review.sh）**: FINDING 行の欄（FILE・LINE・STOP・再現・SEV・SECURITY）と変更の種類・行の範囲だけで決める。LLM の VERDICT 行は合否に使わない。
- **直す側（fix-loop）**: スクリプトが「止める」と出した指摘だけを直す。

判定のコードは小さく保つ。スクリプトが見るのは欄があるかと値の形だけで、再現の正しさは確かめない。

### 4.1 FINDING 行と台帳の行の形（`.claude/agents/code-reviewer.md`・`scripts/claude/code-review.sh`）
修正方針: 止めるかを決めるのに要る欄を FINDING 行に足し、台帳にも残す。

FINDING 行（レビュー役が書く）:
```
FINDING: F<n> SEV=<Blocker|High|Medium|Low> STATUS=<open|resolved> FILE=<パス|-> LINE=<n|n-m|-> SECURITY=<yes|no> STOP=<flow|leak|github|ac:<番号>|-> | <要約> | 再現: <入力・手順・壊れ方>
```
- `LINE`: HEAD でのそのファイルの行番号か、その範囲。結びつかないときは `-`。
- `STOP`: 当たる止める条件。`flow`＝① 流れが動かなくなる、`leak`＝② 秘密情報・個人情報が外に出る、`github`＝③ develop・main を直接壊す、または GitHub から戻せない設定を壊す、`ac:<番号>`＝④ 受け入れ条件の未達（番号はイシューの受け入れ条件の上からの順番）。当たらなければ `-`。
- `| 再現: …`: 止める指摘に必須。止めない指摘には書かなくてよい。

読み方（スクリプト）:
- 正規表現: `FINDING: (F[0-9]+) SEV=(Blocker|High|Medium|Low) STATUS=(open|resolved) FILE=(\S+) LINE=(\S+) SECURITY=(yes|no) STOP=(\S+)(?: \| (.*))?`。合わない `FINDING:` 行が 1 行でもあれば、今と同じく台帳を作らない（BLOCKER）。
- `LINE` が `^[0-9]+(-[0-9]+)?$` に合わない（`-` を含む）→ 行が読めない → 差分の中（止める側）。
- `STOP` が `flow`・`leak`・`github`・`ac:[0-9]+` のどれでもない → `-` として扱う（`ac` だけで番号が無いものも `-`）。
- 再現あり＝要約の後ろに `| 再現:` があり、その後に空白以外の文字がある（`re.search(r"\| 再現:\s*\S", rest)`）。

台帳の行（スクリプトが書く）:
```
LEDGER: F<n> SEV=… STATUS=… SCOPE=<delta|outside> KIND=<app|harness|guard> STOP=<…> REPRO=<yes|no> SECURITY=<yes|no> | <要約>
```
- 前の形（KIND・STOP・REPRO の無い I197 の形）の台帳の行も読む。足りない欄は、止める側の既定値で埋める（`KIND=app`・`STOP=-`・`REPRO=yes`）。I205 のマージの時点でレビューの途中だったイシューの台帳が、黙って消えないようにするため。

### 4.2 変更の種類（AC1）
修正方針: 指摘の FILE のパスだけで種類を決める。種類の一覧はスクリプトの中に 1 か所だけ置く（Python の `kind_of()`）。

| 種類 | パス（先に当たったもの） |
|---|---|
| `guard`（GitHub から復旧できない例外） | `.github/*`・`.pre-commit-config.yaml`・`.secrets.baseline`・`scripts/claude/hooks/pretooluse_guard.py`・`.claude/settings.json`・`.claude/settings.local.json`（`path_risk_trigger()` と同じ集合） |
| `harness` | `.claude/`・`scripts/claude/`・`docs/`・`rules/` で始まるもの、`CLAUDE.md`・`.mcp.json`・`.worktreeinclude` |
| `app` | 上のどれでもないもの（`backend/`・`frontend/`・`e2e/`・`docker-compose.yml`・`nginx/`・`scripts/db_*.sh`・`README.md` など。知らない場所は厳しい側） |

- パスは今の `scope_of()` と同じ形にそろえる（`:行番号` を除く・リポジトリのルートからの相対パス）。比べるときは `casefold()` する（F16 と同じ理由）。
- `FILE=-` の指摘は、ブランチが変えたファイルの種類から決める。`guard` があれば guard、無くて `app` があれば app、それも無ければ harness。
- `guard` の集合は `path_risk_trigger()` と同じでなければならない。2 か所に書くことになるので、テスト（R-K2）で一致を固定する。`path_risk_trigger()` 自体は変えない（安全装置の判定なので触らない）。
- 差分のレビューの入力に「変更の種類（スクリプトが決めた）」の節を足し、範囲のファイルごとに種類を出す（Python の `kinds` モードで出す）。レビュー役が、ハーネスのファイルに閉じた問いを使えるようにするため。

### 4.3 行で決める範囲（AC6）
修正方針: 範囲を「ファイル」から「ファイルと行の塊」に変える。1 周目（全体のレビュー）も、ブランチが変えた行だけを範囲にする（設計確認メモ: 古いコードの指摘は 1 周目でも止めない）。

- 新しい関数 `delta_hunks <比べる相手> <起点の SHA|"">`: `git -c core.quotePath=false diff -U0 --no-renames --no-color <A> HEAD -- <ファイル…>` の `+++ b/<パス>` と `@@ -a,b +c,d @@` を読み、`<パス>\t<始め>\t<終わり>` を出す。
  - 全体のレビュー（起点なし）: `A` は `merge-base <比べる相手> HEAD`。ファイルはブランチが変えたファイル（記録の場所を除く）。
  - 差分のレビュー: diff を 2 本取る。A＝`merge-base <比べる相手> HEAD` から HEAD（ブランチ自身が変えた行）、B＝起点の SHA から HEAD（起点の後に変わった行）。両方とも HEAD の行番号なので、重なる行だけを塊にする（develop の取り込みで入った行は A に無いので入らない）。ファイルは今の `delta_files` の結果（ブランチが変えたファイルのうち、起点の後に変わったもの）。
  - git が失敗した（古い git で知らないオプションなど）ときは `delta_hunks` が 2 を返し、本体は「⛔ 差分の行の塊を取れません」で止まる（止める側。手元の git 2.43.0 と CI で H7 を確かめる）。
  - `d` が無い → 1 行、`d=0`（消しただけ）→ `c` の 1 行（`c=0` なら 1）。
  - ファイルは変わったのに塊が 1 つも無いもの（バイナリ・モードの変更）→ そのファイルは行に関係なく範囲の中（`<パス>\t1\t999999999`）。
- 前後の行数 `HUNK_MARGIN=3`（git の既定の前後の行数と同じ）。指摘の行 `[a,b]` が塊 `[始め-3, 終わり+3]` と重なれば差分の中。
- `scope_of(path, line, stop)`:
  - `STOP=ac:<番号>` → 行に関係なく差分の中（受け入れ条件・計画の未達は行に関係なく止める。設計確認メモ）
  - `FILE=-`、または行が読めない → 差分の中（止める側）
  - パスを今と同じくそろえる（`:行番号` を除いた相対パス）。リポジトリの外（`..`）・実在しないファイル → 差分の中（止める側。今と同じ）。実在の確認（`os.path.isfile`）は、そろえたパス（大文字・小文字は書かれたまま）に対して行う。範囲と比べるときだけ、両方を `casefold()` する。大文字・小文字を区別するファイルシステムで別名の 2 ファイル（`a.sh` と `A.sh`）があると取り違えうるが、取り違えは「差分の中」になる向きだけ（止める側）なので許容する
  - そろえたパスが範囲にあり、行がどれかの塊と重なる → 差分の中。それ以外 → 差分の外
- 既にある指摘（前の周の台帳にある番号）の SCOPE は、今と同じく前の値のまま。
- `ledger_update` の 4 番目の引数は、ファイル一覧から塊の一覧（`delta_hunks` の出力）に変える。全体のレビューでも塊の一覧を渡す。
- 差分のレビューの入力の「差分のレビューの範囲のファイル」は今のまま（塊の一覧はレビュー役に見せない。行は git diff で分かるため）。

### 4.4 止める基準（AC1〜AC5）
修正方針: `blocking()` を種類ごとに分ける。重大度のラベルは、アプリ本体と guard でだけ使う。ハーネスは止める条件の一覧と再現で決め、重大度を見ない（ラベルを 1 段下げて関所を通す抜け道を、ハーネスでは閉じる。I197 の独立した評価）。

```python
STOP_RE = re.compile(r"(flow|leak|github|ac:[0-9]+)")
def blocking(e):
    sev, st, scope, kind, stop, repro, sec = ...
    if st != "open":
        return False
    sec_blocker = sev == "Blocker" and sec == "yes"
    if kind == "guard":                       # GitHub から復旧できない例外: 今のまま（再現は問わない）
        return RANK[sev] >= 2 and (scope == "delta" or sec_blocker)
    if repro != "yes":                        # 再現の無い指摘は止めない（アプリ本体・ハーネス共通）
        return False
    if sec_blocker:                           # 差分の外でもセキュリティの Blocker は止める（共通・設計確認メモ）
        return True
    if scope != "delta":
        return False
    if kind == "app":                         # アプリ本体: Blocker・High・Medium（Low は止めない）。受け入れ条件の未達（ac:<番号>）は重大度に関係なく止める
        return RANK[sev] >= 1 or stop.startswith("ac:")
    return bool(STOP_RE.fullmatch(stop))       # それ以外のハーネス: 止める条件の一覧に当たるものだけ
```
- `STOP=ac:<番号>` の番号が、イシューの受け入れ条件の数の範囲かはスクリプトで確かめない（`ac:99` も ④ に当たる扱い）。番号の取り違えは止める側に倒れるだけで、緩める向きの抜け道にならないため（計画レビューの Warning への対応）。
- `ledger_verdict`: 止める指摘に Blocker があれば BLOCKER、Blocker 以外の止める指摘があれば HIGH、無ければ OK（Medium・Low のラベルでも、止める指摘なら HIGH）。
- 既にある指摘の書き直し（今の「重大度は下げない」と同じ考え方で、止める側の値を残す）: SEV は上げるだけ。SECURITY は yes が残る。REPRO は yes が残る。STOP は前が一覧に当たっていれば前の値を残す。
- 止める指摘の一覧を記録に残す: 台帳の節の後ろに `## 止める指摘（スクリプトが決めた・fix-loop が直すのはこれだけ）` の節を足し、`ledger_blocking` の出力を書く（AC5。直す側が自分で選び直さない）。

### 4.5 LLM の VERDICT 行を合否に使わない（AC5・I202 F11）
修正方針: 全体のレビューでも、差分のレビューと同じく code-reviewer の VERDICT 行は「あるか」と「NG なのに FINDING 行が無い」の食い違いの検査にだけ使う。
- `code-review.sh:848-858` の `if [ "$REVIEW_KIND" = "delta" ]` の分岐をやめ、両方とも今の delta 側の処理にする（`VERDICT_NOTE` も「合否に使わない」に一本化）。
- F11（表の中にだけ書いた指摘が台帳に入らない）: code-reviewer の出力フォーマットから「## コード品質・セキュリティ指摘」の表を外し、指摘は FINDING 行にだけ書く形にする。受け入れ条件の照合の表からも重大度の列を外す（未達は FINDING 行に `STOP=ac:<番号>` で書く）。表の中にだけ書いたものは、形のうえで指摘ではなくなる。

## 7. ロールバック
ハーネスのファイルだけの変更なので、PR を revert すれば戻る（GitHub が最後の守り）。注意点が 1 つある。前のスクリプトは新しい形の台帳の行（KIND などの欄がある）を読めないので、レビューの途中のイシューでは、前の周の止める指摘を拾えなくなる。戻した直後にそういうイシューがあれば、review-gate をやり直す前に、新しい形で書かれたコードレビューの記録の名前を `_code_review_` を含まない名前に変えて退避する（消さない）。そうすると前のスクリプトはその記録を拾わず、全体のレビューからやり直す。退避したことは自律判断の記録に書く。

## 9. 確定事項と自律判断
### イシューに明記されていること（設計確認メモ）
- 止める基準を変更の種類で分ける。アプリ本体は Blocker・High・Medium、Low は止めない
- ハーネスの止める条件の一覧 ①〜④（④は番号必須）。関所の穴は一覧に入れない
- 再現の欄が無い指摘は止めない（アプリ本体でも同じ）。止めるかはスクリプトが決める
- アプリ本体の「イシューに関係する」＝変えた行（と前後数行）か、受け入れ条件・計画の未達。1 周目でも古いコードは止めない
- 差分の外でもセキュリティの Blocker は止める
- 敵対的レビューの止め方は揃えない
- 上限は最後の安全網として残す。retro が台帳の残りを 1 件の後続か既存に振り分ける

### Claude が技術的に決めたこと（理由）
- FINDING 行の欄の書き方（`LINE=`・`STOP=`・`| 再現:`）: 1 行で機械が読める形を保つため。今の正規表現を足すだけで済む
- 前後の行数は 3: git の既定の前後の行数と同じで、レビュー役が見る差分の見た目と合うため
- ハーネスの場所の一覧（4.2）: 一覧に無いものはアプリ本体（厳しい側）。知らない場所で甘くならないため
- `FILE=-` の種類はブランチが変えたファイルから（guard＞app＞harness）: ファイルに結びつかない指摘でも、厳しい側に倒すため
- guard は再現を問わない: GitHub から戻せない変更は今の強さのまま（ここを緩める理由が無い）
- ハーネスは重大度を見ない: 重大度のラベルを下げて関所を通す抜け道を閉じるため（I197 の独立した評価）
- 前の形の台帳を止める側の既定値で読む: 途中のイシューの止める指摘が黙って消えないため
- F11・F16 は I205 で直す（4.10）
- `path_risk_trigger()` と `gate-check.sh` は変えない: 安全装置の判定を変えないため（止めて聞く条件 2 に当たらないようにする）
- テストは新設の `test_i205_stop_criteria.sh` と、`test_i197_review_ledger.sh` の形の付け替え: I205 の判定を 1 本にまとめ、I197 のテストは意味を変えずに残すため

### ユーザーに確認した価値判断
- **Q1（2026-10-27 確定: 案 B・関所は変えない。イシューの設計確認メモに追記済み）**: 敵対的レビュー（高リスク時）で、アプリ本体のイシューに関係する Medium が出て、その周の判定が OK だったとき。設計確認メモは「直す・敵対的レビューの周は増やさない・基本レビューの差分のレビューで確かめる」。しかし今の `gate-check.sh` は、敵対的レビューの OK の後に足した変更を通さない（`gate-check.sh:9,141`）。メモのとおりにするには、関所を緩める必要がある。
  - 案 A: `gate-check.sh` を変え、敵対的レビューの OK の後の変更でも、その後の基本レビューが OK なら通す（メモのとおり。ただし高リスクのアプリの変更で、敵対的レビューを通らない差分が残りうる）

  - → 案 B に決定（ユーザー）
