追加 P6 ブロック（P4 チェックの後に配置）:
```markdown
**性能・UX設計チェック（該当する場合）**

- フロントエンド変更がある場合: 破壊的操作（削除等）の確認導線の設計があるか
- パフォーマンス懸念（N+1・キャッシュ・ページネーション等）が計画書で考慮されているか（大量データ・外部API連携がある場合）

該当なし（コード変更なし・UIなし・データ量や外部API懸念なし等）の場合は「P6 影響なし」と明記する。
```

追加 P7 ブロック（P6 チェックの後に配置）:
```markdown
**設計品質チェック（必須）**

- 旧来のアンチパターン（Django: Fat View・Raw SQL 乱用、React: Props drilling・巨大コンポーネント等）を踏襲しない設計か
- null / undefined / 空値の扱い方針が設計で統一されているか（複雑なデータ処理がある場合）
- 例外処理・エラーハンドリングの方針が計画書に含まれているか（外部API・複雑な処理がある場合）
- 設定値・定数がハードコードされない方針になっているか
```

### ステップ4: `implement/SKILL.md` の変更

**修正対象**: 既存「P3・P5 実装確認チェック」ブロックを拡張して P1・P6・P7 を追加:

変更後のブロック全体:
```markdown
**P1・P3・P5・P6・P7 実装確認チェック（該当する場合）**
要件適合性確認（P1）:
- 実装が受け入れ条件の範囲を超えた仕様追加・機能追加を含んでいないか
- マルチテナント・組織スコープの閲覧範囲・操作範囲の制約が実装で正しく確保されているか（該当する場合）
- ステータス遷移・承認条件・更新可否条件が実装で正しく制御されているか（該当する場合）

DB変更がある場合（P3）:
- ForeignKey の on_delete 設定が計画書の方針通りか（CASCADE/PROTECT/SET_NULL）
- インデックスが必要な箇所に設定されているか
- トランザクション境界が計画書の設計通りか（atomic ブロック等）
- 冪等性が必要な処理に二重送信・重複実行対策があるか

外部API・非同期処理・バッチがある場合（P5）:
- 構造化ログに request_id・user_id・tenant_id が含まれているか
- 外部API呼び出しにタイムアウトが設定されているか
- 失敗時のフォールバック・エラーハンドリングが計画書の方針通りか

フロントエンド変更または大量データ・外部API連携がある場合（P6）:
- ローディング・空状態・エラー状態の表示が実装されているか（フロントエンド変更がある場合）
- 破壊的操作（削除等）に確認導線が実装されているか（フロントエンド変更がある場合）
- N+1 クエリ・不要な全件取得が発生していないか

設計品質確認（P7）:
- 旧来のアンチパターン（Fat View・Raw SQL 乱用・Props drilling 等）が実装で踏襲されていないか
- null / undefined / 空値の扱いが実装で一貫しているか
- 設定値・定数がハードコードされていないか

該当なし（DB変更なし・外部API/非同期処理なし・フロントエンド変更なし・データ量懸念なし等）の場合は対象外項目をスキップしてよい。
```
