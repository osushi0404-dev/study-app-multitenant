## 5. 実装手順（ステップ）

> 本イシューはドキュメント（ワークフロー定義）の文言追加が中心で、レイヤー貫通（DB→API→UI）の概念は非該当。各ステップは独立適用可能な単位で切る。**未知リスク先行原則**に従い、唯一の振る舞い検証ゲート（item1 のシェル挙動）を最初に置く。検証コマンドはステップ本文に書かず、すべて自動テスト文書の TC に集約する（→ docs/tests/open/I063_auto_test.md）。

### ステップ1: implement 完了検証（item1・失敗時ハード STOP）
- **修正方針**: `implement/SKILL.md` の手順3（commit/push）と手順4（完了案内）の間に、完了案内を出す**前の必須ゲート**を挿入する。意図した変更ファイルが `git diff origin/develop...HEAD --name-only` に現れることを確認し、現れない場合は**完了案内（push 完了・/code-review 案内）を出さず**、「未コミット/未 push の可能性」を報告して停止する。
- **一般化**: I060 等の固有名に依存しない表現にする。「意図した変更ファイル」は計画書の実装対象に対応する。
- 依存: なし。→ 振る舞いスモークは TC-S1 参照。

### ステップ2: plan-writing-rules「事前調査」強化（item2/C1検証手順 + P1 do層 item6）
- **修正方針**: 「計画書作成前の事前調査（必須）」セクション（既存の「環境前提確認」「lint/audit/scan 副作用事前調査」と同じ並び）に、2つの小節を追加する:
  - (a) **参照先実在性の全件機械検証**: ドキュメント整合・棚卸し系の計画では、文書内のパス/ファイル/ディレクトリ参照を抽出し `test -f`/`ls` で実在性を全件検証する。**既存のデッドリンクも検出対象に含め、検出時は是正する**（C1）。
  - (b) **規約是正時の消費箇所全件列挙（P1 do層）**: 規約・命名・フォーマットを是正するイシューでは、旧パターンを repo 全体に grep し、**宣言箇所だけでなく消費箇所（グロブ・ループ・相互参照・スクリプト）も是正対象に全件列挙**する。
- **一般化**: ツール名・固有イシュー番号に依存しない原則表現にする。
- 依存: なし。→ 振る舞いスモークは TC-S2 参照。

### ステップ3: review-rules.md デッドリンク是正（item7・C1 同梱）
- **修正方針**: `review-rules.md:110` の「詳細な運用方法は `docs/reviews/README.md` を参照すること。」を**削除**する。理由（調査結果）: 参照先 `docs/reviews/README.md` は実在せず、運用方法本体は review-rules.md 自身に記述済みのため当該文は循環/冗長。差し替え先の実在ファイルが存在しないため削除が最小で正しい。
- 依存: ステップ2 の検証手順が本デッドリンクを検出できることの確認材料になる（TC-S2 で同時確認可）。

### ステップ4: grill-me 3点追加（item3/4/5）
- **修正方針**:
  - (item3) 「必須確認（全イシュー）」に「**scope/AC が lint/audit/scan/型チェック等ツールの出力で決まるイシューでは、概算でなく対象ツールを実際に実行して全件分類し、達成可能な完了基準を確定してから AC を記録する**」観点を追加。**（plan-review W2 反映）** 当ブロック冒頭には「コードベースを読んで自己解決できる場合は質問を省略してよい」前置きがあるため、本項目には「**この項目はコード読解で代替できず、ツール実行の省略は不可**」を明記し、省略容認の前置きに巻き込まれない書き方にする（または前置きの外に別立てで記述する）。
  - (item4) 手順4（設計確認メモの追記）に「**追記した決定値と矛盾する既存セクション（解決方針・スコープ・実装対象・受け入れ条件）を同じ決定値に整合更新する**」小節を追加。
