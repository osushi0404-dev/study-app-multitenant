## 背景/目的

I045・I046 でレビュースキル（`/plan-issue-review`・`/code-review`）を8観点フレームワークに整合させた。
しかし上流スキル（`/grill-me`・`/plan-issue`・`/implement`）は更新されていないため、
「作る段階では意識されない → レビューで多発修正」という非対称が生まれている。

本イシューでは上流スキルに P3（データ整合性）・P5（運用性）・P8（コスト・保守）の観点を組み込み、
問題をレビュー前の段階で防止して fix-loop の発生を減らす。

### 1. `.claude/skills/grill-me/SKILL.md`

**変更箇所 A: 「必須確認」に P8 を統合**

現行:
```
- 実装する価値があるか（類似機能・代替手段がないか・コストに見合う価値があるか）
```

変更後:
```
- 実装する価値があるか（類似機能・代替手段がないか・コストに見合う価値があるか）
- コスト・保守負荷が妥当か（インフラコスト・運用者の手作業増加・属人化リスク・長期維持コストが現実的か・要件規模に対して過剰な構成でないか）
```

**変更箇所 B: 「質問の観点（該当する場合のみ）」に P3・P5 を追加**

追加:
```
- データ整合性設計（DB変更がある場合）: トランザクション境界・冪等性・同時更新の扱い・マイグレーション安全性
- 運用設計（外部API・非同期処理・バッチがある場合）: 構造化ログ方針・タイムアウト・リトライ・Feature Flag・段階リリースの要否
```

### 2. `docs/runbooks/plan-writing-rules.md`

**変更箇所: 計画書テンプレートの必須セクション一覧に P3・P5・P8 の条件付きセクションを追加**

現行（セクション 1〜9）の後に追加:
```
10) データ整合性設計（DB変更がある場合のみ）
    - DB制約（NOT NULL・UNIQUE・FK・CHECK）の設計方針
    - トランザクション境界・冪等性・同時更新の扱い
    - マイグレーション手順（安全性・ロールバック可能か・後方互換性）

11) 運用設計（外部API・非同期処理・バッチがある場合のみ）
    - 構造化ログ方針（request_id・user_id・tenant_id の付与等）
    - タイムアウト・リトライ・フォールバックの方針
    - Feature Flag・段階リリース・切り戻し設計の要否

12) コスト・保守見積もり（新規インフラリソース・外部サービス追加・大規模設計変更がある場合のみ）
    - インフラ・DB・外部API・ジョブ実行のコスト妥当性
    - 運用者の手作業増加見積もり
    - 属人化リスク・長期維持コストの現実性確認
```

### 3. `.claude/skills/plan-issue/SKILL.md`

**変更箇所: 「セキュリティ・ベストプラクティスチェック」の後に P3・P5・P8 チェックを追加**

- DB変更がある場合: データ整合性設計（セクション10）が計画書に含まれているか
- 外部API・非同期処理・バッチがある場合: 運用設計（セクション11）が計画書に含まれているか
- 新規インフラリソース・外部サービス追加・大規模設計変更がある場合: コスト・保守見積もり（セクション12）が計画書に含まれているか
該当なし（コード変更なし・既存パターンの踏襲のみ等）の場合は「P3/P5/P8 影響なし」と明記する。
```

- 構造化ログに request_id・user_id・tenant_id が含まれているか
- 外部API呼び出しにタイムアウトが設定されているか
- 失敗時のフォールバック・エラーハンドリングが計画書の方針通りか

該当なし（コード変更なし・既存パターンの踏襲のみ等）の場合はスキップしてよい。
```

| リスク | 対策 |
|--------|------|
| 追加した観点が既存の確認項目と重複する | 各スキルファイルの既存内容と照合し、重複する場合は既存を統合・拡張する形を取る |
