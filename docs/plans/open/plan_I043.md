## 実装手順

ステップ間に依存関係はない。すべて並行実施可能。

### ステップ1: `/plan-issue-review/SKILL.md` の変更

**変更方針**: 3箇所を変更する。

**変更A — 手順2) の出力形式を重大度テーブルに変更**

各観点（ベストプラクティス・セキュリティ・モダン開発・Claude Codeベストプラクティス）のチェック後に、
発見した指摘をまとめて以下のテーブル形式で出力するよう手順を追加する。

```
## レビュー指摘一覧
| 重大度 | 観点 | 指摘内容 | 該当箇所 | 対応 |
|--------|------|---------|---------|------|
| Blocker | セキュリティ | 認可チェックが計画書に明示されていない | API設計 | 実装前に修正必須 |
| High | BP | Fat View になる設計 | ... | 当該PRで修正推奨 |
| Medium | モダン | ページネーション未考慮 | ... | チケット化推奨 |
| Low | BP | 変数名の微妙なズレ | ... | 改善提案 |
```

重大度の定義:
- **Blocker**: 次工程へ進めない（認可漏れ・要件未達・設計上の重大リスク等）
- **High**: 原則として修正してから進める（運用事故・重大不具合の高リスク）
- **Medium**: 当該PRでの修正推奨（難しければチケット化して期限を切る）
- **Low**: 改善提案（今回見送りの場合は理由を残す）

問題がなければ「指摘なし」と記載する。

**変更B — 高リスク判定セクションを追加**

手順2)の最後（観点チェック完了後）に以下を追加する。

```
**高リスク判定**:
以下の条件に1つでも直接該当する場合、高リスク: Yes と判定する。
- 認証・認可・ロール変更
- マルチテナント境界変更
- 管理画面追加・変更
- ファイルアップロード/ダウンロード
- 外部公開API追加・変更
- Webhook・外部API連携
- 個人情報・機微情報の新規取り扱い
- DBスキーマ重要変更
- 既存事故の再発リスクが高い変更
- 画面制御していてもAPI直叩きで事故りうる変更

判定結果を以下の形式で出力する:
## 高リスク判定
判定: Yes / No
該当条件: [リスト、なければ「なし」]
推奨: （Yes の場合）`/implement` 前に `/security-review $ARGUMENTS` を実行してください。
     （No の場合）そのまま `/implement $ARGUMENTS` へ進めてください。
```

**変更C — 手順3) の停止条件を追加**

現行:
```
- OK: 「✅ プランレビュー完了。`/implement $ARGUMENTS` を実行してください。」
- NG の場合は以下を判断する: ...
```

変更後:
```
レビュー指摘一覧の重大度に基づいて判定する:

- **Blocker あり**: ⛔ STOP。以下を出力して停止する。
  「Blocker が残っています。修正後に `/plan-issue-review $ARGUMENTS` を再実行してください。」
  → `/implement` は案内しない。

- **Blocker なし・High あり**: ❌ レビュー NG。High 以上の指摘を修正することを推奨する。
  修正可能なものは自分で修正してレビューを再実行する（現行ルール維持）。
  設計判断が必要なものはユーザーに確認する（現行ルール維持）。

- **Blocker・High なし**: ✅ プランレビュー完了。
  「`/implement $ARGUMENTS` を実行してください。」
  （高リスク判定 Yes の場合は先に `/security-review $ARGUMENTS` を実行するよう案内する）
```

### ステップ2: `/code-review/SKILL.md` の変更

**変更A — 手順4) の受け入れ条件テーブルに重大度列を追加**

現行:
```
| # | 受け入れ条件 | 実装状況 | 備考 |
```

変更後:
```
| # | 受け入れ条件 | 実装状況 | 重大度 | 備考 |
```

- 実装状況が ✅ の場合、重大度列は「-」
- ⚠️ や ❌ の場合、重大度（Blocker/High/Medium/Low）を記載

**変更B — 手順5)・6) の品質・セキュリティ指摘にも重大度を付与**

コード品質・セキュリティ観点の指摘も同じ重大度定義で分類して出力する。

**変更C — 手順7) の停止条件を追加**

現行:
```
- OK: 「✅ コードレビュー完了。`/test $ARGUMENTS` を実行してください。」
- NG: 「❌ レビュー NG。`/fix-loop $ARGUMENTS` を実行してください。...」
```

変更後:
```
- **Blocker あり**: ⛔ STOP。
  「Blocker が残っています。`/fix-loop $ARGUMENTS` で修正後、`/code-review $ARGUMENTS` を再実行してください。」
  → `/test` は案内しない。

- **Blocker なし・High あり**: ❌ レビュー NG。
  「`/fix-loop $ARGUMENTS` を実行してください。fix-loop 完了後は `/code-review $ARGUMENTS` に戻ってください。」

- **Blocker・High なし**: ✅ コードレビュー完了。
  「`/test $ARGUMENTS` を実行してください。」
```

### ステップ3: `/test/SKILL.md` の変更（停止条件の明文化）

現行ロジックはすでに正しく実装されているが、停止条件が明文化されていない。
スキルの冒頭（前提の直後）に以下を追加する。

```
## 停止条件
- 自動テスト（pytest / Jest）が1件でも失敗した場合: STOP。`/fix-loop` を案内し、`/retro` および `/close` は案内しない。
- 手動テスト確認でユーザーが NG を返した場合: STOP。`/fix-loop` を案内し、`/retro` および `/close` は案内しない。
```

### ステップ4: `/grill-me/SKILL.md` の変更

**変更箇所**: 「質問の観点（該当する場合のみ）」セクションの末尾に2項目追加する。

追加する項目:
```
- 実装する価値があるか（類似機能・代替手段がないか・コストに見合う価値があるか）
- 既存方針との衝突がないか（既存アーキテクチャ・設計指針・運用ルールに反していないか）
```

## 承認ポイント

**セキュリティ影響**: なし（スキルファイル変更のみ）

**設計判断の確認**:

| 判断事項 | 根拠 | 区分 |
|---|---|---|
| Blocker のみ STOP、High は NG 推奨（強制ではない） | 運用柔軟性を保つため。High を強制停止にすると摩擦が大きい | イシューに方針明記あり |
| 高リスク条件は「1つでも直接該当したら Yes」 | 安全側の判断。スキップはユーザー明示承認のみ | 提案資料（7-3）で決定済み |
| code-review の重大度は受け入れ条件テーブルと品質・セキュリティ指摘の両方に付与 | 全指摘に重みを持たせるため | イシューに明記あり |
| grill-me の2項目は「該当する場合のみ」扱い | 毎回強制質問にすると摩擦が大きい | 仮定で決定（要確認） |

**確認が必要な仮定**: grill-me の追加2項目を「該当する場合のみ」の任意質問とする方針。毎回必須質問にすべきか？
