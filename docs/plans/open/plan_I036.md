## 1. 背景/目的

`docs/runbooks/workflow.md` において、`/retro` スキルが「任意」扱いとなっている。
テスト OK 後に振り返りを省略されるケースがあり得るため、問題が蓄積し同じ失敗が繰り返されるリスクがある。

アジャイル・モダン開発のベストプラクティス（Scrum レトロスペクティブ、Google SRE ポストモーテム文化等）では振り返りは「推奨」ではなく**必須のセレモニー**として定義されている。
「必須（テスト OK 後は必ず実施）」に変更して継続的改善サイクルを確立する。

## 4. 調査結果

### 対象ファイルの現状確認

`docs/runbooks/workflow.md` の `/retro` に関する記載箇所を特定した。

#### 変更箇所 1（行 31）— フロー一覧の「step 7」

```
7. OK の場合 /retro I###（任意）または /close I###（open→closed へ移動、PR説明を整備、マージ依頼）
```
→ `（任意）` と明記されており、省略を容認している。

#### 変更箇所 2（行 60）— スキル呼び出しルールの表

```
| test OK 後 | 「`/retro I###` または `/close I###` を入力してください」と案内 |
```
→ `/retro` と `/close` が並列で案内されており、どちらを先に実行すべきかが不明確。

#### CLAUDE.md の `/retro` 箇所

CLAUDE.md では `docs/runbooks/workflow.md` の「使うスキル」セクションを参照する旨のみ記載しており、`/retro` を直接説明する記述はない。変更不要と判断。

### ベストプラクティス観点での根拠

| 観点 | 根拠 |
|------|------|
| Agile/Scrum | スプリントレトロスペクティブは必須セレモニー（Scrum Guide） |
| Google SRE | ポストモーテムは義務化が標準（学習サイクルの担保） |
| 継続的改善（Kaizen） | 振り返りが定着しない限り改善サイクルは機能不全になりやすい |
| 心理的安全性 | 「推奨」だと省略が暗黙的に許容され、振り返り文化が育ちにくい |
