## 背景/目的

現在の `/implement` スキルは実装手順しか持たず、新規の振る舞い（エンドポイント・ビジネスロジック）追加時に TDD（Red → Green → Refactor）サイクルを回す仕組みがない。テストが後付けになりやすい構造を解消するため、スキルに TDD ガイドを組み込む。

あわせて、`/issue-bootstrap` のステップ6報告テンプレートが `workflow.md` の「イシュー承認後は `/grill-me` を案内する」ルールと乖離していたため、同イシュー内で修正する。

## 実装手順

### ステップ1: `implement/SKILL.md` に TDD ガイドを追記する

**ステップ間の依存**: ステップ1とステップ2は独立して実施可能。

**変更箇所**: 現在の「手順:」セクションの冒頭に、条件分岐ブロックとして独立して挿入する。既存の 1)〜4) の番号は変えない。

**設計方針**:
- TDD 内側ループ（Red→Green）はローカルで高速実行する。`docker compose exec` を毎サイクル挟むと TDD の「高速フィードバック」原則に反する。
- 環境パリティ（Docker vs Local）の保証は最終確認（`/test` スキル）に委任する。これが正しい役割分担。
- 強制停止の要件があるため、条件分岐ブロックを手順の冒頭に独立配置して見落としを防ぐ。

**追記内容（「手順:」直後に挿入）**:

```markdown
手順:
━━ 【新規の振る舞いを追加する場合】新しいエンドポイント・ビジネスロジック・コンポーネントの追加が対象 ━━
先に TDD サイクルを完了してから 1) へ進む（強制。テストを書かずに 1) を開始した場合は STOP）。

[Red フェーズ]
- `docs/tests/open/$ARGUMENTS_auto_test.md` を読み、対象の振る舞いに対応するテストコードを先に実装する
- 認証・認可・テナント境界を検証するテストも必ずこの時点で実装する
- Backend（ローカル）: `python -m pytest <対象テストファイル> --tb=short` を実行し、テストが失敗することを確認する
- Frontend（ローカル）: `npm test -- --watchAll=false --testPathPattern=<対象テスト>` を実行し、テストが失敗することを確認する
- テストが失敗しない場合は STOP → ユーザーに報告してテスト内容を確認する

[Green フェーズ]
- テストを通過させる最小限の実装を行う
- 同じコマンドでテストが通過することを確認してから Refactor へ進む

[Refactor フェーズ]
- 可読性改善・重複削除など内部整理のみ行う
- 新機能追加・設計変更は計画書更新が必要（STOP → 提案 → 承認 → 計画書更新）

**注**: TDD サイクル中のテスト実行は「高速フィードバック確認」が目的でローカル実行で十分。
     `/test` スキルは「環境パリティを含む最終確認」が目的であり役割が異なる。

━━ 【それ以外（バグ修正・リファクタ・既存コード変更）】TDD は任意。1) から開始する ━━

1) 計画どおり実装
...
```

**挿入後の「手順:」セクション全体の構成**:

```
手順:
━━ 【新規の振る舞いを追加する場合】... ━━（条件分岐ブロック・上記）
━━ 【それ以外】TDD は任意。1) から開始する ━━
1) 計画どおり実装（既存）
2) ビルド・型チェック・リント・セキュリティスキャン（既存）
3) commit/push して PR を更新（既存）
4) 停止し案内（既存）
```

| リスク | 対策 |
|--------|------|
