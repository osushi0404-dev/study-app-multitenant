# 画面の使い勝手（UX）の決まり

画面を作る・直すときの使い勝手の原則。計画を書くときと、画面を確かめるときに使う。

- コードの書き方（4 つの状態の出し分け・フォーム・アクセシビリティの属性など）は `rules/react-coding-standards-integrated.md` が正。ここは「利用者から見てどうあるべきか」だけを書く
- 計画書に書く UX の節（性能・UX 設計）の項目は `docs/runbooks/plan-writing-rules.md` の 13) が正
- 画面の確かめ方（アプリの起動・Playwright MCP）は `docs/runbooks/frontend-verify.md`
- 目標の水準: WCAG 2.2 の AA（https://www.w3.org/TR/WCAG22/）

## 1. エラーのとき
- 利用者の作業の文脈を失わせない。別の画面（404 の画面など）に飛ばさず、同じ画面の中で何が起きたかを出す
  - ❌ 読み込みに失敗したら 404 の画面へ移る
  - ✅ 同じ画面に「読み込めませんでした」と再読み込みのボタンを出す
- 次にすることを必ず出す（やり直しのボタン・直し方・別の道）。「エラーが発生しました」だけにしない
- 入力した内容はエラーのときも消さない

## 2. 待つとき
- 処理中であることを必ず見せる。中身の形が分かる画面は、形だけ先に出す（スケルトン）
- 時間のかかる処理（AI の問題の生成など）は、進み具合か、終わるまでの目安を出す。必要なら止められるようにする

## 3. 入力するとき
- 誤りは送信の前に分かるようにする（入力欄を離れたときに確かめる）。何が誤りで、どう直せばよいかを具体的に書く
- 送信の成功ははっきり知らせる（トーストなど）。送信中であることが分かり、二重に送れない（コードは React 規約 §8）

## 4. 画面を移るとき
- 道筋（URL）は意味が分かり、予想できる形にする。ブラウザの戻る・進むが期待どおりに動くようにする
- 再読み込みしても、見ていた状態（絞り込み・ページ）を URL から戻せるようにする
- 保存していない入力があるときに画面を離れようとしたら、確かめる

## 5. データが無いとき
- 「何も無い」だけにせず、次にすることへの導線を出す（例: 科目が無いときは科目の設定へ。I487）

## 6. スマホと、だれでも使えること
- スマホの幅（360px）で横にはみ出さない
- タッチで押す的は 44×44px 以上にする（WCAG 2.2 の 2.5.5 の水準。AA の最低は 2.5.8 の 24×24px）
- キーボードだけで操作できる（Tab で移り、Enter で決め、Esc でダイアログを閉じる）。フォーカスの位置が見える
- 色だけで意味を伝えない（正誤は色に加えて文字・アイコンでも示す）。文字と背景の明るさの比は 4.5:1 以上（大きな文字は 3:1）
- 書き方（ラベル・`aria-*`・MUI の部品）は React 規約 §13

## 7. 確かめること（画面を作り終えたとき）
§1〜§6 と、React 規約 §7（4 つの状態）を満たすかを、`docs/runbooks/frontend-verify.md` の手順で画面を動かして確かめる。
