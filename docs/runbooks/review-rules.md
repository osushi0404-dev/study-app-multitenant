## 文書間の関係性記載ルール

### 計画書ヘッダの必須記載（初期作成）
計画書ヘッダ「## 基本情報」の項目・命名の正本は `plan-writing-rules.md`「計画書ヘッダー（文書間の関係性）」に従う。要点のみ再掲する:

- **計画書ID**: `plan_I###`（再作成時 `plan_I###_N`）
- **関連イシュー**: `#XXX`
- **Draft PR**: `#XX`
- **作成根拠資料**: この計画書の起点となった分析資料・イシューのパスを明記（例: `docs/issues/open/I010.md`）。「関連レビュー」という曖昧な表現は使用禁止
- **実装後評価**: この計画書の実装結果を評価するレビュー（`docs/reviews/open/I###_review.md`）。未作成時は `（未作成）`

### 実装後評価の記録先（新系統）
実装結果の評価は、**`/plan-issue` が作成する `I###_review.md`（ライフサイクルレビュー）** に集約する。具体的には同ファイルの「テスト結果」「計画との差分」セクションに記録する。実装後評価を別ファイルとして新規作成する手順（旧来の通し番号付き別ファイル方式）は廃止し、`I###_review.md` への追記で一本化する。

## レビューファイルの命名・状態管理（正準規約）

### 命名規則（新系統・issue 単位で一意）
レビュー関連ファイルは issue 番号で一意に識別する（旧来のグローバル通し番号方式は廃止）:

| 種別 | 命名 | 生成者 | 保存先・ライフサイクル |
|------|------|--------|----------------------|
| ライフサイクルレビュー | `I###_review.md` | `/plan-issue` | `docs/reviews/open/` → `docs/reviews/closed/`（close 段階が移動） |
| コードレビュー監査記録 | `I###_code_review_<timestamp>.md` | `scripts/claude/code-review.sh` | issue が open の間は `docs/reviews/` 直下に時系列で蓄積。close 段階で当該 issue 分を `closed/` へ回収（I065） |
| プランレビュー監査記録 | `I###_plan_review_<timestamp>.md` | `scripts/claude/plan-issue-review.sh` | 同上 |
| イシューレビュー監査記録 | `I###_issue_review_<timestamp>.md` | `scripts/claude/issue-review.sh` | 同上 |
| 敵対的レビュー監査記録 | `I###_adversarial_review_<timestamp>.md` | review-gate 段階（敵対ステージ） | 同上 |

- `<timestamp>` は `YYYYMMDD_HHMM` 形式。
- 旧形式 `review001〜003`（旧通し番号方式）は**廃止・履歴**。`docs/reviews/closed/` にそのまま残す（**リネーム不要**）。新規作成しない。

### 状態管理（open / closed の2系統）
状態は `open` / `closed` の2つのみ（旧来の3状態管理は廃止）。

- `I###_review.md`: `docs/reviews/open/` で作成し、issue クローズ時に close 段階が `docs/reviews/closed/` へ移動する。
- timestamped 監査記録（`I###_{code,plan,issue}_review_<timestamp>.md`）: issue が open の間は `docs/reviews/` 直下に蓄積し、close 段階が当該 issue 分を `closed/` へ回収する（スクリプトの保存先は直下のまま・移動は close 段階が担当）。

## 検証の全体設計（I197）

何を・どの段階で・何で確かめるか。LLM に任せるのは「読んで判断すること」だけにし、実行したかどうか・合否は決定論で出す。

| 層 | 何を確かめる | 何で | いつ（段階） | 止まり方 |
|---|---|---|---|---|
| 1 決定論 | テスト（pytest・Jest・E2E・ハーネステスト）・lint・型・注入（守りを壊すとテストが落ちるか）・計画が宣言した決定論ゲート・レビュー後の変更の有無 | CI・`code-review.sh` の決定論ゲート実走・`gate-check.sh` | implement の後・review-gate・test-gate・close | 失敗＝不合格（exit code） |
| 2 基本レビュー（独立した目） | 受け入れ条件・計画との照合・BP・セキュリティの見落とし | 組み込み `/code-review`（パスの判定が YES のときは `/security-review`。台帳の目印・計画レビューで高リスクになった分は敵対的レビューが受け持つ）・`code-reviewer`。どちらも別プロセスの `claude -p`・読むだけ・承認なし | review-gate 1 | 時間切れ・失敗・空は BLOCKER |
| 3 敵対的レビュー（高リスク時・独立した目） | 「合格」の反証。脅威モデル・要件の漏れ・設計の筋と、計画の「## 必ず確かめる項目」の各項目 | `scripts/claude/adversarial-review.sh`: 読むだけのレビュー役 3 観点を別プロセスで並列に起動し、実験案は実験役（別プロセス・自動承認モード・承認なし）が実行して `--resume` で結果を返す。判定は一覧からスクリプトが出す | review-gate 3 | 未検証・報告なし・時間切れ・拒否・作業ツリーの変更は合格にしない |
| 4 人 | 価値判断・操作感 | 手動テスト（Human の行）・マージ | test-gate・close | 人の返事 |

- **黙って止まらない**: 検証する側の `claude -p` はすべて `--permission-prompts none` で起動する（承認が要る操作は待たずに拒否され、出力の `permission_denials` に残る）。親の会話の中で裏で動くサブエージェントに検証を任せない（確認待ちになっても親から気づけない。I166）。
- **周が収束する（I197・2026-10-27）**: 基本レビューは 1 回目だけブランチ全体を見て、指摘を台帳（番号・重大度・状態）にする。やり直しは、前の記録の `REVIEWED_COMMIT` からの直した差分と、台帳の止める指摘が直ったかだけを見る（全体を探し直すと、新しいコードが大きいほど毎回新しい指摘が出て減らない。I179・I193・I197 で実測）。fix-loop の中の実装・テストのレビューはやめ、診断だけを残す（同じ差分を重ねて見ない）。高リスク（敵対的レビューを走らせるか）は計画レビューの判定・パスの判定・台帳の目印（`RISK=up`・I202）で決め、一度 YES になったら戻さない。
- **止める基準は変更の種類で分ける（I205・2026-10-27）**: 合否はスクリプト（`code-review.sh` の `blocking()`）が、code-reviewer の FINDING 行の欄（FILE・LINE・STOP・再現）から決定論で出す。code-reviewer の VERDICT 行・直す側の判断は使わない。種類は指摘の FILE のパスで決まる。

  | 変更の種類 | 止めるもの |
  |---|---|
  | アプリ本体（`app`。下の 2 つ以外すべて＝知らない場所は厳しい側） | イシューに関係する（ブランチで変えた行と前後 3 行、または受け入れ条件の未達 `STOP=ac:<番号>`）、再現のある Blocker・High・Medium（指摘 0 を目指す。Low の改善提案は止めない） |
  | GitHub から復旧できない例外（`guard`。`path_risk_trigger()` の集合） | Blocker・High（再現を問わない・I197 のまま） |
  | それ以外のハーネス（`harness`。`.claude/`・`scripts/claude/`・`docs/`・`rules/`・`CLAUDE.md` など） | 止める条件の一覧に当たり、再現のある指摘だけ（重大度は見ない）: ① 流れが動かなくなる（`flow`）② 秘密情報・個人情報が外に出る（`leak`）③ develop・main を直接壊す／GitHub から戻せない設定を壊す（`github`）④ 受け入れ条件の未達（`ac:<番号>`・番号必須） |

  - 共通: 再現（`| 再現: 入力・手順・壊れ方`）の無い指摘は止めない（guard を除く）。差分の外でも、セキュリティの Blocker（再現あり）は止める。差分の中か外かは行で決める（行が読めない・ファイルが無いときは止める側）。
  - 関所の穴（判定をすり抜けられる穴）は一覧に入れない。止めずに台帳に残す（後続のイシューに回ったときは最優先にする）。ハーネスは完璧を目指さない（GitHub が最後の守り）。
  - 止めない指摘は台帳に残り、retro が重さで振り分ける（`.claude/skills/retro/SKILL.md` 4-0・I207）: 再現のある Medium 以上・`SECURITY=yes`・アプリ本体（`KIND=app`）は 1 件の後続のイシューにまとめるか既存のイシューに同梱し、それ以外（Low、または再現なし）は軽い指摘の一覧（`docs/reviews/backlog/`）に追記する。一覧は計画（`/plan-issue`）で実装対象のファイルに当たる行を見る。
  - review-gate ⇄ fix-loop の回数の上限（5 回目で止める）は最後の安全網。当たったら止め方の見直しの兆しとして止めて聞く。
- **自己申告で通さない**: レビュー役の「実験した」は、実験役の記録（実行したコマンド・拒否・結果）で確かめる。報告の無い観点・項目の行の無い項目は未検証。
- **網羅は計画の段階で決める**: 高リスクに当たりうる計画は「## 必ず確かめる項目」（項目ごとに `実験必須`／`読んで可`）を持つ。決定論の TC で覆える項目は TC を先に考え、層 3 では「その TC が本当にその項目を確かめているか」を読む。
- **実装した本人と独立した目の分け方**: 実装セッションは段取りを呼ぶだけで、判定に自分の読みを混ぜない（自己認証の非権威化）。
- 方式の比較（裏のサブエージェント・メイン側・別プロセス・組み込み・GitHub 側）と採否の理由は `docs/plans/closed/plan_I197.md` §4.2。

## 高リスク変更の敵対的レビューステージ（自己認証の非権威化・I086／対象と上限・I181）

- **前提（GitHub が最後の守り）**: develop/main は GitHub 側で保護され（ブランチ保護・CODEOWNERS・承認必須）、bot はマージできない。手元のハーネスが壊れても GitHub から復旧できるので、手元のハーネスの変更は決定論ゲートと基本レビューで先へ進む。例外（GitHub から復旧できない操作）は `docs/runbooks/danger-ops.md`「GitHub から復旧できる範囲（I182）」。
- **対象**: 高リスク判定 YES の変更は、敵対的レビューステージ（反証マンデート×多観点サブエージェント・対応後再レビュー）の通過を合格条件とする（review-gate 段階が自動起動する）。高リスク判定 YES になるのは次のどれか:
  - (a) アプリの高リスク条件（`.claude/agents/code-reviewer.md`「高リスク判定の条件」）に当たる変更（計画レビューが判定する）
  - (b) ハーネスでは、例外に関わるファイルの変更だけ: `.github/*`・`.pre-commit-config.yaml`・`.secrets.baseline`・`scripts/claude/hooks/pretooluse_guard.py`・`.claude/settings.json`・`.claude/settings.local.json`（正は `scripts/claude/code-review.sh` の `path_risk_trigger()`）
  - (c) 台帳の目印: 計画レビューが No でも、基本レビューの code-reviewer が (a) に当たる変更を差分に見つけて FINDING 行に `RISK=up` を付けたとき（I202。一度 YES になったら戻らない）
- **実装者（実装セッション）が書く実装後レビュー・自己レビューは判定根拠にしない**（自己認証の非権威化）。合否は独立ステージ（基本 code-review＋敵対ステージ）の結論を正とする。
- 通常（高リスク判定 NO）の変更は従来の単発 code-review のまま（比例性）。
- **上限**: 1 周 10 分（`scripts/claude/adversarial-review.sh` が締め切る）・攻め筋 3 本・実験の往復は 1 観点 2 回まで・1 周 3 観点・イシュー全体で 2 周（review-gate のやり直しで数え直さない。報告の無い観点がある周は `ROUNDS: 0` で数えない）。2 周目は記録の `REVIEWED_COMMIT` からの差分だけ。判定は計画の「## 必ず確かめる項目」から決定論で出し、未検証が 1 件でも残れば合格にしない（I197）。ガード・見張りは「普通の書き方による事故」までを Critical/High にする。手順の正は `.claude/skills/review-gate/SKILL.md` §3。
- **上限到達**: 自動 OK にせず、FINAL VERDICT HIGH 以上で停止してユーザーにエスカレーションする（`docs/runbooks/workflow.md`「止めて聞く条件」3。セキュリティにかかわる指摘を受け入れて進む判断は Claude だけではしない）。残った指摘と過去の周の指摘を種類ごとに集計し、同じ種類が 2 周続いていれば「止める場所・方式の見直し」を選択肢の先頭に置く（I176 から移管）。
- **計画レビューのやり直しは、計画の方式・範囲・受け入れ条件を変えたときだけ**: findings への対応を計画変更記録に足しただけ（方式・範囲・受け入れ条件は変えない）なら plan-review 段階を通り直さずに次の工程へ進む。どちらに当たるかは計画変更記録に 1 行で書く（I181 の棚卸し: I179 は 11 回、I151 は 8 回、敵対的レビューの周ごとに挟んでいた）。

## GitHub から復旧できない変更のレビュー観点（I182）

公開リポジトリでは、次の変更は**マージしなくても PR を出した（push した）時点で**影響が出る。PR を出す前に確かめる（一覧と理由は `docs/runbooks/danger-ops.md`「GitHub から復旧できる範囲」）。

- **ワークフロー（`.github/workflows/`）の変更**: PR 側のワークフローが secrets 付きで動く。secrets を出力・外部へ送信していないか、`pull_request_target` を足していないか、`permissions` を広げていないか（最上位は `contents: read`）、pre-commit の `SKIP` に `detect-secrets` を足していないかを見る。
- **秘密情報の検査設定（`.pre-commit-config.yaml`・`.secrets.baseline`）の変更**: detect-secrets を外していないか、新しい秘密情報を baseline に足していないか（行番号の更新だけか）を見る。
- **コミットに秘密情報が入っていないか**: push protection は既知の形式の鍵しか拾わないので、`.env` の値・パスワード・トークンらしい文字列が差分に無いかを見る。

## レビュー作成の必須ルール

### 基本方針
**全ての対応完了後は必ずレビューを残し、品質向上と継続的改善を実現する。** イシュー対応は `I###_review.md`（/plan-issue が作成）に実装後評価を記録し、review-gate 等が生成する監査記録（timestamped）と併せて完了の証跡とする。

### レビュー実施タイミング
- **イシュー対応完了後**: 必須（`I###_review.md` に実装後評価を記録）
- **アドホック修正完了後**: テキスト指示による修正等も記録を残す
- **定期レビュー**: システム全体の品質確認時

### 記載の必須要件
- **対象計画書へのリンク必須**: 実装後評価では対象計画書（`docs/plans/open/plan_I###.md`）を明記する
- **重複記載の回避**: 計画書に記載済みの内容をレビューに再記載しない
- **客観的な評価**: 良い点・改善点を公正に記録する
- **イシューとの相互参照**:
  - レビュー側: 「関連イシュー: #XXX」を記載
  - イシュー側: 対応履歴にレビューリンクを追加
    ```markdown
    ## 対応履歴
    - **YYYY-MM-DD**: [対応内容]
      - レビュー: [#XXX](../reviews/open/I###_review.md)
    ```

### レビュー内容の必須要素

#### A. 対応品質評価
- 問題特定の正確性
- 修正内容の適切性
- 影響範囲の考慮
- テスト・検証の充実度

#### B. プロセス評価
- ワークフロー遵守状況
- 計画書・承認プロセス
- ドキュメント品質
- コミュニケーション

#### C. 技術的評価
- コード品質
- アーキテクチャ適合性
- パフォーマンス影響
- セキュリティ考慮

#### D. 改善提案
- **短期改善**: すぐに対応可能な改善点
- **中長期改善**: 構造的・システム的改善
- **予防策**: 同様問題の再発防止

## レビュー活用方法

### 継続的改善
- 定期的なアクションアイテム確認
- パターン分析による予防策実装
- 品質指標の継続的モニタリング

### 知識共有
- 類似問題の解決策参照
- ベストプラクティスの蓄積
- 技術的知見の共有

### 重要な注意事項
- **レビュー作成は対応者の責任**: 対応完了と同時にレビュー記録を残す
- **客観的な評価**: 良い点・改善点を公正に記録
- **具体的なアクション**: 実行可能な改善提案を記載
- **継続的フォロー**: アクションアイテムの実施状況を追跡

## スキルファイル変更時の Claude Code ベストプラクティス準拠（必須）

`.claude/skills/` 配下のファイルを変更するイシューでは、
変更内容が以下の Claude Code 公式ベストプラクティスに準拠していることを確認する。

### チェックリスト

| # | チェック項目 | 観点 |
|---|---|---|
| 1 | 使えるツールを絞る必要があるスキルは `disallowed-tools` で制限しているか。`allowed-tools` は「確認なしで使ってよい」事前許可で制限にはならないので、付けるなら本当に事前許可が要るものだけに絞っているか（素の `Bash` を事前許可していないか）（I185 P4） | セキュリティ |
| 2 | 副作用のある操作（commit・push・デプロイ等）に `disable-model-invocation: true` が設定されているか | 安全性 |
| 3 | `argument-hint` が記載されているか | 発見性 |
| 4 | `description` に「いつ使うか」が含まれているか（250文字以内） | 発見性 |
| 5 | 指示文に明確な停止条件・完了条件が記載されているか | 明確性 |
| 6 | `$ARGUMENTS` 等の変数が一貫して使われているか | 一貫性 |
| 7 | SKILL.md が 500行以内か（超える場合は supporting files への分割を推奨） | コンテキスト効率 |

このチェックは計画レビュー（plan-review 段階・`.claude/agents/plan-reviewer.md`）のレビュー観点に組み込まれている。
