# 計画書の書き方

計画書（`docs/plans/open/plan_I###.md`）の形の正はひな形 `docs/plans/templates/plan_template.md`。この文書は、各節に何を書くかと、計画を書く前に調べること・計画と実装を一致させる決まり・手動テスト文書の書き方を決める。

## 計画書の節（形はひな形）

1) **背景/目的**: 下に `### 調査結果` を置く。まず原因の概要を平易に 1〜2 文（非技術者でも分かる言葉）、次に詳細（起きる流れ・技術的な背景・なぜ起きたか・問題の箇所を ファイル:行 で）
2) **受け入れ条件**: 何ができたら OK か。手段（見る範囲・触るファイル）でなく結果（どの場合でも〜しない・〜が表示される）で書く。手段で書くと、レビュー役が「AC の文言どおり」で止まり、目的の穴が通る（I486）
3) **影響範囲**（Backend/Frontend/DB/Config）
4) **変更点一覧**: 下に `### 修正アプローチ`（全体の方針を日本語で）を置き、項目ごとに「何を達成するか」を言葉で書いてから、ファイル・関数・コード例を書く
5) **実装手順**（ステップ）
   - ファイル削除・サービス停止を伴うときは「実装後にサービス再起動が必要」と書く
   - **垂直スライス**: 特定のレイヤー（DB だけ・API だけ）を横に広げず、DB → API → 画面を薄く縦に貫く単位でステップを切る（例: 「モデル追加 + API 1 本 + 画面への表示」。このプロジェクトでは model / viewset / React component）
   - **未知リスク先行**: 実現できるか不確かなもの（新しい外部サービス・初めて使うライブラリ）を最初のステップに置く
   - **依存関係の明示**: ステップ間のブロッキング関係を書く（「ステップ 3 はステップ 1 の後」「ステップ 2 と 3 は並行してよい」）
   - セキュリティ制御（認証・認可・入力の検証）は、守る対象の機能と分けてマージしない
   - **検証コマンドを書かない**: 確かめる手順は自動テスト文書の TC に書き、ステップには「→ TC-XX」とだけ書く（TC にしていない確かめは実装中に飛ばされる）
6) **テスト計画**（自動/手動）: テストのために差し替え（monkeypatch・一時的なグローバルの書き換え・テスト専用の差し込み）が要るときは、本番の設計を変えて差し替えを不要にする案を第一候補にする（差し替えが要るのは設計の歪みのしるし）
7) **ロールバック**
8) **Risk & 回避策**（処遇は回避か受け入れ。受け入れはこの表の行に書く）
9) **確定事項と自律判断**: イシューに明記されていること／Claude が技術的に決めたことと理由。UI を変えるときは配置・順序・ラベルを書く。イシューで決まっていない UI の配置・文言・操作の流れは、計画レビューの前にユーザーに確かめる（`docs/runbooks/workflow.md`「止めて聞く条件」1）

### 条件付きセクション（当たる変更があるときだけ含める）
10) **データ整合性設計**（DB 変更があるとき）: DB 制約（NOT NULL・UNIQUE・FK・CHECK）／トランザクション境界・冪等性・同時更新／マイグレーションの安全性・戻せるか・後方互換
11) **運用設計**（外部 API・非同期処理・バッチがあるとき）: 構造化ログ（request_id・user_id・tenant_id）／タイムアウト・リトライ・フォールバック／Feature Flag・段階リリース・切り戻し
12) **コスト・保守見積もり**（新しいインフラ・外部サービス・大きな設計変更があるとき）: インフラ・外部 API・ジョブのコスト／運用者の手作業の増加／属人化・長期の維持
13) **性能・UX 設計**（画面の変更か性能要件があるとき）: N+1・キャッシュ・ページネーション／ローディング・空・エラーの表示／削除などの確認の導線／アクセシビリティ（キーボード・aria・コントラスト）
14) **学習効果設計**（学習機能・学習データ・学習体験に関わるとき）: 効果の指標（定着率・正答率の改善など）の定義と計測／間隔反復・出題順・難易度の根拠／つまずきの検知・復習の時期・動機づけ。参照: 品質基準 C1（`docs/proposals/learning_app_quality_criteria.md`）
15) **プライバシー・コンプライアンス設計**（個人情報・未成年データ・テナントデータを扱うとき）: 個人情報保護法・保護者の同意・教育データ利活用ガイドライン／保持期間・削除権・データ所有権（学校が管理者）／テナント横断の混在の禁止／開示・削除の請求の導線。参照: 品質基準 C2

### ルール変更時に関連ファイルを同時更新する
- 計画書を変えたら、関連文書（`docs/reviews/open/`・`docs/tests/open/` の auto_test・manual_test）も同時に直す。計画書を作っている途中で方針を変えたときも同じ
- 決まり（手順書・CLAUDE.md）を変えたら、対応するひな形（`docs/{issues,plans,reviews,tests}/templates/`）も同じ PR で直す
- `docs/runbooks/` に手順書を足す・名前を変える・消すときは、`CLAUDE.md`「0. 参照先」も同じ PR で直す

## 計画を書く前の事前調査

調べた結果は計画書の「調査結果」に書く。

### 環境の前提（手順が新しい道具・サービス・コマンドに頼るとき）
手順が前提とする道具がホストにあるかを確かめる（例: `which <tool>`・`<tool> --version`・`docker compose ps`）。無ければ入れる手順をステップ 1 に入れる。ハーネスのテストの道具は `bash scripts/claude/tests/check-tools.sh` で確かめる。

### 規約と依存の照合（仕組みを自作すると決める前・技術を選ぶ前）
- 取得・キャッシュ・状態管理・検証などの仕組みを自作すると決める前と、BP を問われて答える前に、`rules/` の当たる節と依存のファイル（`frontend/package.json`・`backend/requirements*.txt`）を開いて照らし、計画の技術選択に節と ファイル:行 を添える。新しいコードは、既存のファイルの書き方より規約を優先する（照らさずに自作すると、マージ依頼の後の作り直しになる）
- 公式の機能（Claude Code・GitHub・使っているライブラリ）と重なる設計は、公式だけで足りるかを先に確かめ、足りない部分だけを自作する。公式の処理を置き換える・無効にする案は、失う公式の機能をスパイクで確かめてから推奨する（I179）

### 外部/ハーネス挙動依存のスパイク実証（計画が「未知リスク」と認識するとき）
計画の正しさが不確かな外部（ハーネス・フレームワーク・ツール）の挙動に頼るときは、計画を確定する前に最小の実証で確かめる（上の「未知リスク先行」を計画の前に前倒ししたもの）。
- **(1) 今のセッションで確かめられる挙動**（CLI のフラグ・フレームワークの戻り値・設定ファイルの読まれ方など）: 計画の確定前に確かめ、成立／不成立を「調査結果」に書く。不成立なら設計をやり直してから計画レビューへ
- **(2) 今のセッションでは確かめられない挙動**（権限モード・フックの読み込みに頼るもの）: 下の「Claude が観測できる手段」で新しいセッションを起こして確かめる。それでも確かめられないときだけ「未実証」と書き、実装ステップ 1 で通常モード（Manual）の新しいセッションで確かめる。ステップ 1 の結果は後のステップを止めるゲートにし、不成立なら計画をやり直す
- 完了の基準: 想定した挙動を実行できる確認（コマンドの出力・Read での観測・CI のログ）で再現し、結果を「調査結果」に書いた時点

### 参照先実在性の全件機械検証（文書の整合・棚卸しのイシュー）
文書の中のパス・ファイル・ディレクトリへの参照を抜き出し、`test -f`・`ls` で全件の実在を確かめる。イシューの対象外で以前から切れている参照も直す（残すなら理由を計画書に書く）。見つけた不在の参照と直し方を「調査結果」に書く。

### 規約是正時の消費箇所の全件列挙（命名・フォーマット・規約の是正イシュー）
古い形をリポジトリ全体で grep し、宣言の箇所だけでなく消費の箇所（グロブ・ループ・相互参照・スクリプト）も全件を直す対象に挙げる。名前・形だけでなく、中核の概念・判定の基準（「何を正とするか」など）を変えるときも、その概念を使う箇所（止める条件・記録・後のステップ・分岐）を grep で洗い出して同時に直す。grep の結果は「調査結果」か影響範囲に書く。

### 指示ファイルへの条件分岐追加時のコマンド粒度パリティ
指示ファイル（`SKILL.md`・手順書）に条件分岐を足すときは、対になる既存の分岐と同じ粒度（具体的なコマンド・ステップまで）で書く。足したら、対の分岐が書いているコマンドと 1 行ずつ突き合わせ、片方だけが散文止まりになっていないかを確かめる。

### 検査ツール（lint・audit・scan・型）を入れる・強めるとき
- 計画の前にそのツールを実際に流し、見つかった問題の件数と中身・直す対象のファイル・直さず許す問題とその理由を「調査結果」に書く（初めて流したときに出る問題を計画の時点でつかみ、計画外の変更を防ぐ）。道具とコマンドの正は `docs/runbooks/pre-commit.md`
- 今のテストの状態（ベースライン）は、手元で流し直さず develop の最新の CI の結果（`gh run list --branch develop`）で見る。手元で流すのは関係するテストのファイルだけ（`docs/runbooks/common-commands.md`「テスト実行」）

### 否定・回帰系の決定論テストの自己検証（false-green 禁止）
否定・不在・回帰・無改変を確かめる決定論の TC（`grep` などで「無い」「壊れていない」「変わっていない」を判定するもの、lint・静的解析の異常系を含む）は、失敗の条件を入れて実際に不合格（非ゼロ終了）になることを確かめてから採る。
- 正常系で合格するだけの TC は、対象が壊れても合格する false-green になりうる
- 確かめ方: 対象を一時的に壊した入力（行を消した・書き換えた写し、対象を欠いたダミー）に TC を流し、非ゼロ終了を確かめる。確かめられない TC は判定を直してから採る
- 合否は終了コードで出す（合格=exit 0・不合格=非ゼロ）。出力の値を目で比べて合否にしない。不在は `! grep -q 文言 file` のように合格で exit 0 を返す形にし、値で判定するときも `[ "$(grep -c 文言 file)" -eq 3 ]` のように終了コードに畳み込む（合格で非ゼロを返す TC は、CI・`set -e` の下で合格が失敗に反転する）

### 決定論テストの対象の選び方（写しのテストを作らない）
決定論テストで守るのは「**壊れても気づきにくく、壊れると被害が大きい決まり**」だけにする（I213）。テストの数ではなく、事故を止める力で選ぶ。

- 作る: 普通の書き方で気づかずに壊しうるもの。例: action・土台イメージを中身（SHA・指紋）で固定する／pull_request で動くワークフローに secrets を置かない／秘密の伏せ字を書き込みより先に置く／起動のたびに作り直す保存領域の範囲／知らないと踏む設定の落とし穴（Dependabot の `target-branch` など）
- 作らない:
  - 設定ファイルの中身をテストにもう一度書いて照合するもの（対象の一覧・日数・ラベルなど）。設定を変えるたびに両方を直す手間が増えるだけで、守りの力が無い。形の誤りは公式のスキーマ検証・リンターに任せる
  - 消すのが意図的な変更でしか起きないものの有無（runbook の文言・フックがあるか・コマンドの並び）。意図的な変更はレビューで見る
- 迷ったら 2 つを問う:「普通の書き方で、気づかずに壊すことがあるか」「壊れたとき、CI・画面・すぐ後の作業で気づけるか」。前者が「いいえ」、または後者が「気づける」ならテストにしない
- 作ると決めたテストには、上の「否定・回帰系の決定論テストの自己検証」のとおり FG（失敗の注入）を付ける

### 高リスクの計画の「必ず確かめる項目」（I228）
高リスクに当たりうる計画の「## 必ず確かめる項目」（敵対的レビューが判定に使う表。形はひな形）で、項目を `実験必須` にする前に、決定論の TC（失敗の注入つき・本物のファイルを書き換えない）で覆えないかを考える。覆えるなら TC を auto_test に書き、項目の内容に `TC-xx` を書いて `読んで可` にする（敵対的レビューは「その TC が本当にその項目を確かめているか」を読む）。

- 特に次の性質は `実験必須` にしない: 守りを外すと落ちること（失敗の注入。`mock.patch`・一時の写しでテストの中で外す）／表と外部の正（コマンドの `--help` など）の突き合わせ
- 理由: 実験は、レビュー役が選ばない・実験の環境が無い・締め切りで走らない、のどれでも未検証になり、敵対的レビューの 1 周を失う（I446 の V6・I463 の V1）。決定論の TC なら CI が毎回確かめる
- `実験必須` に残すのは、実機でしか観測できない挙動（別プロセスの claude の承認・実際のコマンドの組み合わせ）だけ
- 前の周に実験で確かめた項目は、記録の場所の外と項目の行が変わっていなければ次の周に引き継がれる（`scripts/claude/adversarial-review.sh` の `carry_items`）。項目の文言を直すと引き継がれないので、直すのは中身が変わるときだけにする

### 見張り（`pretooluse_guard.py`）に判定を足す計画（I430）
`docs/runbooks/danger-ops.md`「見張りに判定を足すときの決まり」の 3 点（公式・GitHub で表せないか／事故の実例／意図的な回避の指摘の扱い）を計画書に書く。

## 計画書と実装の一致性保証ルール

### 基本原則
計画書に書いていない実装はしない（`CLAUDE.md` 絶対ルール 1。流れのゲートは `docs/runbooks/workflow.md`「ゲート」）。ここは、計画と違うことが要るときの直し方の正。
- 実装の前に「この方法が最適か」（性能・保守性・セキュリティ・拡張性・簡潔さ・既存との一貫性・フレームワークの推奨）を考え、より良い方法があれば実装の前に計画書を直す。ユーザーへの提案と承認待ちはしない
- 実装中に次のどれかに気づいたら、編集を止めて計画書を先に直す: ① 計画書に無い実装が要る ② 計画書より良い方法がある ③ 計画書の方法では実現できない ④ 計画書に無いファイル・関数・変数の変更が要る
- 計画レビューを通り直す条件は `docs/runbooks/workflow.md`「ゲート」。要件・基本設計・UI/UX が変わるときだけユーザーに確かめる（`docs/runbooks/workflow.md`「止めて聞く条件」1）
- あってはならない例: 計画書「`list` メソッドを修正」→ 実装で新しい `by_organization` メソッドを足す／計画書「変数名を `user_id` に」→ 実装で `userId`

### 計画変更記録の形
計画書の `## 計画変更記録` に足す（元の計画書を上書きしない）。
```markdown
- YYYY-MM-DD <段階>: 計画書の記載: [引用] → 採った方法: [内容] — 理由: [比べた案と、選んだ理由（複雑さ・性能・保守性・セキュリティ・リスク）]。計画レビューのやり直し: 要（方式・範囲・受け入れ条件を変える）/ 不要（findings への対応の追記だけ）
```
同じ要点を `docs/reviews/open/I###_review.md`「## 自律判断の記録」にも 1 行書く。

### 例外（計画書に先に書かなくてよいもの）
タイポ（明らかな誤字・全角/半角）・新しいメソッドに伴う自明な import・インデントや改行の整形。これらも自律判断の記録に書く。

計画書なしに直してしまったときは、計画変更記録に事後で書き、計画レビューを通す（再発防止は retro）。「1 行だけだから」「○○の対応だから」は例外にしない。

## 手動テスト文書のフォーマットルール

形はひな形 `docs/tests/templates/manual_test_template.md`。表には必ず「実施者」列を入れる。期待結果は「〜できる」ではなく、具体的な画面の表示・動き・コマンドの出力で書く。

**実施者の区別**:
| 値 | 意味 | 例 |
|----|------|-----|
| `Claude`（原則こちら） | test-gate 段階で Claude が自分で確かめられる（ファイル・コマンド・ログの確認、下の「Claude が観測できる手段」のどれか） | ファイルの有無、コマンドの出力、JSON の構文、画面の表示・遷移・画像、許可した操作が承認なしで通る／危ない操作に承認画面が出る（危ない操作は、同じ許可ルール・見張りに当たり実行されても困らない代わりの操作で確かめる。承認なしで通ると実際に実行されるため）、`/` の候補の出方 |
| `Human` | 下の観測手段を試し、どれでも観測できなかったものだけ。備考に `試した手段: <試した手段>。<観測できなかったわけ>` を必ず書く（例: `試した手段: Playwright MCP・tui-capture.sh。どちらも Figma の画面は開けない`）。「承認」「確認画面」「ダイアログ」などを含む行は、Claude Code の承認画面の話ではないこと〔`check-permission-prompt.sh` では確かめられないわけ〕も「試した手段:」に書く | 操作感・見た目の好み、外部サービス（Figma・Slack 等）での操作、ユーザー本人の判断が要るもの |

- この基準の正はこの節。`.claude/skills/plan-issue/SKILL.md`・`.claude/skills/test-gate/SKILL.md`・`docs/tests/templates/manual_test_template.md` は要約と参照だけを持つ（写しを増やさない。I195）
- `bash scripts/claude/check-manual-test-executor.sh I###` が Human の行の形（「試した手段:」の有無と中身・承認の言葉の扱い）を止める（`/plan-issue` はテスト文書を作った後、test-gate は Human の項目を出す前に流す）。中身の正しさは計画レビュー役が見る。進め方は test-gate のスキルが正

### Claude が観測できる手段（ハーネス挙動テストの実施環境）
ハーネスの権限モード・フック・承認画面・許可の設定に頼る挙動は、今のセッションでは承認の出どころ（フックの確認・通常の許可・モード）を区別できず確かめにならない（今のセッションが自動承認のモードなら、承認画面が出るはずの操作も通る）。新しいセッションを起こして確かめる。これらの TC を含む手動テスト文書では、表に「実施環境」列を足して行ごとに書く（ほかの文書では省いてよい）。

| 実施環境の値 | 手段 |
|------|------|
