# レビュー観点フレームワーク（8観点）整備案

- **作成日**: 2026-04-14
- **目的**: 現行レビュースキルの観点カバレッジを8観点フレームワークに整合させる
- **前提**: I043（停止条件・重大度・高リスク判定）実装済み、I044（/security-review）対応中

---

## 1. 背景

I043 でレビューの「構造」（停止条件・重大度区分・高リスク判定）を整備した。
しかし、**何を見るか（観点の網羅性）** は変えていない。

現行スキル（`/plan-issue-review`・`/code-review`）の観点は「ベストプラクティス / セキュリティ / モダン開発」という粗い3分類のままであり、以下の問題がある。

- 観点の境界が曖昧で、チェックリストとして使うと抜け漏れが生じやすい
- データ整合性・運用性・コスト保守の観点がゼロ
- セキュリティのサプライチェーン領域、テスト妥当性の code-review での確認が欠落

8観点フレームワークへの整合により、レビューの抜け漏れを構造的に防ぐ。

---

## 2. 8観点フレームワーク

現行の3分類を以下の8観点に再定義する。

| # | 観点 | 説明 | 現行カバレッジ |
|---|------|------|--------------|
| P1 | 要件適合性・業務ロジックの正しさ | 受け入れ条件・業務ルール・マルチテナントスコープの充足 | ⚠️ 部分 |
| P2 | セキュリティ（サプライチェーン含む） | 認証・認可・OWASP Top10・依存ライブラリ安全性 | ⚠️ 部分 |
| P3 | データ整合性・変更安全性 | DB制約・トランザクション・マイグレーション安全性 | ❌ ゼロ |
| P4 | テスト妥当性・回帰防止 | テストレベル選択・再発防止テスト・モック過多リスク | ⚠️ 部分 |
| P5 | 運用性・障害対応性 | ログ・メトリクス・タイムアウト・Feature Flag | ❌ ゼロ |
| P6 | 性能・UX・アクセシビリティ | N+1・キャッシュ・ローディング状態・コントラスト | ⚠️ 部分 |
| P7 | 設計・実装品質 | 責務分離・命名・null処理一貫性・例外処理方針 | ⚠️ 部分 |
| P8 | コスト・保守負荷 | インフラコスト・属人化リスク・維持コスト | ❌ ゼロ |

---

## 3. 現行スキルとの差分詳細

### P1. 要件適合性・業務ロジックの正しさ

**現行**: 受け入れ条件との照合のみ（`/code-review` step 4）

**不足している確認項目**:
- 勝手な仕様追加・仕様変更をしていないか
- マルチテナント・組織スコープの閲覧範囲・操作範囲の制約が正しいか
- ステータス遷移・承認条件・更新可否条件が正しいか
- 画面/API/DB/バッチで業務ルールの解釈が一致しているか
- 「一般論では正しいがこの案件要件では誤り」になっていないか

**対象スキル**: `plan-issue-review`（設計段階）・`code-review`（実装段階）

---

### P2. セキュリティ（サプライチェーン含む）

**現行**: 認証・認可・OWASP Top10・秘密情報露出

**不足している確認項目**:
- 依存ライブラリの保守状況・既知脆弱性（pip-audit / npm audit の観点として明示）
- lock file・バージョン固定・CI/CD の秘密情報管理
- レート制限・ブルートフォース対策が必要な箇所にあるか
- 監査ログが必要な操作に記録があるか
- SSRF・Path Traversal・Open Redirect（OWASP Top10 に含まれるが現行で明示なし）
- Cookie・CORS・HTTPS・セキュリティヘッダー設定

**対象スキル**: `plan-issue-review`・`code-review`（I044 /security-review でも一部カバー）

---

### P3. データ整合性・変更安全性（ゼロカバー）

**現行**: 確認項目なし

**追加する確認項目**:
- DB制約（NOT NULL・UNIQUE・FK・CHECK）が十分か
- アプリ側バリデーションとDB制約の責務分担が適切か
- トランザクション境界が適切か
- 冪等性が必要な処理に二重送信対策があるか
- 同時更新・競合更新・排他制御を考慮しているか
- マイグレーション手順が安全か（ロールバック可能か）
- 後方互換性を壊す変更になっていないか
- API/DB/イベント変更の影響範囲が把握されているか

**対象スキル**: `plan-issue-review`（設計段階で検出）・`code-review`（実装確認）

---

### P4. テスト妥当性・回帰防止

**現行**: `plan-issue-review` でテストレベルの使い分けを確認。`code-review` では未確認。

**不足している確認項目**:
- バグ修正に対して再発防止テストがあるか
- テストが実装詳細に依存しすぎていないか
- モック過多で実態を検証できていない状態になっていないか
- テストデータが実運用に近いか
- CI で最低限の品質ゲートとして機能するか
- 未テスト範囲がある場合にどこまで担保されているか明示されているか

**対象スキル**: `code-review`（実装後のテスト確認として追加）

---

### P5. 運用性・障害対応性（ゼロカバー）

**現行**: 確認項目なし

**追加する確認項目**:
- ログが構造化され原因追跡に必要な情報を持っているか（request_id・user_id・tenant_id）
- タイムアウト・リトライ・フォールバックの方針があるか
- 外部API・非同期ジョブ・バッチ失敗時の扱いが定義されているか
- Feature Flag や段階リリースが必要な変更ではないか
- 切り戻ししやすい構成か
- Runbook・管理者向け導線が必要な箇所で不足していないか

**対象スキル**: `plan-issue-review`（設計段階で方針確認）・`code-review`（実装確認）

---

### P6. 性能・UX・アクセシビリティ

**現行**: N+1クエリ・未ページネーション・aria属性・キーボード操作

**不足している確認項目**:
- キャッシュ戦略が妥当か
- バンドル肥大化・不要な初期ロードがないか
- ローディング・空状態・エラー状態の表示があるか
- 破壊的操作に確認導線があるか
- レスポンシブ対応が破綻していないか
- コントラスト・色だけに依存した表現になっていないか

**対象スキル**: `plan-issue-review`・`code-review`

---

### P7. 設計・実装品質

**現行**: 責務分離・重複コード・REST API設計一貫性

**不足している確認項目**:
- null / undefined / 空値の扱いが一貫しているか
- 例外処理方針が統一されているか
- 設定値がハードコードされていないか
- 状態管理・データ取得・非同期処理の設計が適切か
- 旧来のアンチパターンを惰性で採用していないか
- 新技術を採用する場合、採用理由が明確か

**対象スキル**: `plan-issue-review`・`code-review`

---

### P8. コスト・保守負荷（ゼロカバー）

**現行**: 確認項目なし

**追加する確認項目**:
- インフラ・DB・外部API・ジョブ実行のコストが妥当か
- 運用者の手作業が増えすぎないか
- 将来の機能追加・修正時に変更箇所が増えすぎないか
- 要件規模に対して過剰な構成を採用していないか
- 長期保守で属人化しやすい構造になっていないか
- 監視・テスト・デプロイ・リリース運用の維持コストが現実的か

**対象スキル**: `plan-issue-review`（設計判断段階）・`code-review`（実装確認）

---

## 4. 各観点の「含めないもの」定義

観点の境界を明確にし、チェック時の観点跨ぎを防ぐ。

| 観点 | 含めないもの |
|------|------------|
| P1. 要件適合性 | 脆弱性の有無 / テストの量・品質 / コードの書き方 |
| P2. セキュリティ | DB制約・トランザクション / テスト粒度 / UIの使いやすさ |
| P3. データ整合性 | 脆弱性一般 / コードの可読性 / 監視・アラート設計 |
| P4. テスト妥当性 | 本番監視 / パフォーマンスチューニング / 命名・責務分離 |
| P5. 運用性 | UIの使いやすさ / 技術比較のみの議論 / テストの数 |
| P6. 性能・UX | 認証認可・脆弱性 / 監視・Runbook / 依存ライブラリ保守 |
| P7. 設計・実装品質 | 脆弱性の有無 / DBロールバック安全性 / UX・アクセシビリティ |
| P8. コスト・保守負荷 | 直接的な脆弱性評価 / UI操作性詳細 / 業務ロジックの正しさ |

## 5. スキル別の追加観点マッピング

### `/plan-issue-review` への追加

| 追加観点 | 追加理由 |
|---------|---------|
| P1（業務ロジック・マルチテナント制約） | 設計段階で要件解釈の誤りを止める |
| P3（DB制約・トランザクション設計方針） | 実装前に整合性リスクを検出する |
| P5（ログ・タイムアウト・Feature Flag 設計方針） | 運用設計を計画書に含めさせる |
| P8（コスト・保守負荷の見積もり） | 過剰構成・属人化リスクを早期に検出する |

### `/code-review` への追加

| 追加観点 | 追加理由 |
|---------|---------|
| P1（仕様追加・業務ルール逸脱の検出） | 受け入れ条件照合だけでは勝手な追加を検出できない |
| P3（DB制約・トランザクション実装確認） | 設計方針が実装に反映されているかを確認する |
| P4（テスト妥当性・回帰防止） | 実装後にテストの質を確認する機会が現行でない |
| P5（ログ・フォールバック実装確認） | 設計方針の実装への反映を確認する |
| P6（キャッシュ・ローディング状態・色依存） | 現行確認項目の不足を補完する |
| P7（null処理・例外処理・ハードコード） | 現行確認項目の不足を補完する |
| P8（過剰構成・属人化の実装確認） | 実装段階でのコスト観点の確認 |

## 6. 実装イシュー計画

### 優先順位の考え方

- **最優先**: ゼロカバー（P3・P5・P8）は観点そのものが存在しないため先に追加する
- **次優先**: 部分カバー観点（P1・P2・P4・P6・P7）の不足項目を補完する
- **前提**: I044（/security-review）を先に完了させてから観点整備に着手する

### イシュー一覧

| # | タイトル | スコープ | 対象スキル | 優先度 |
|---|---------|---------|----------|--------|

## 7. 設計判断メモ

### P3・P5・P8 を1イシューにまとめる理由
変更対象が `plan-issue-review/SKILL.md` と `code-review/SKILL.md` の2ファイルに集中しており、1PRとしての規模が適切。かつ3観点とも「ゼロカバー」という同じ緊急度なので、一括対応が自然。

### P1・P2補完・P4・P6・P7 を後のイシューにする理由
これらは現行でも部分的にカバーされており、ゼロカバーほどの緊急度がない。I044・I045 の実装後にスキルの形が固まってから、不足項目を精緻に補完する方が整合性が高い。

### 観点の「含めないもの」を定義する理由
観点の境界を明示しないと、同じ問題が複数観点で二重チェックされるか、「どこかで誰かが見るはず」という思い込みで抜け漏れが発生する。境界の明示はチェックの一貫性を高める。
