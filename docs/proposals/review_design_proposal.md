# レビュー運用設計案の検討

- **作成日**: 2026-04-13
- **対象提案**: Claude Code レビュー運用設計（ユーザー提案）
- **目的**: 提案の批判的検討と、導入価値のある要素の選別

---

## エグゼクティブサマリー

提案は体系的で思想的に正しい。ただし **全面採用はしない** ことを推奨する。

提案の価値は2層に分けて評価すべきだ。

**第1層: フェーズ構造（採用を絞る）**
現行フローとの重複が大きく、フェーズとして新規に追加する価値がある要素は限定的だ。
高リスク変更に対して実装前の深掘りセキュリティレビューを追加する方針（高リスク判定 + `/security-review` スキル新設）を採用し、
それ以外のフェーズ追加は現行フローへの軽微な強化で吸収する。

**第2層: 各レビューの構造定義（横断的に採用する）**
提案は各レビューを「役割 / 入力 / 出力 / 停止条件」の形式で定義しており、これは現行スキルに欠けている重要な要素だ。
特に**停止条件の明示**と**Blocker/High/Medium/Low の重大度区分**は、フェーズ数とは独立して既存スキル全体に適用できる改善であり、高く評価する。

---

## 1. 現行フローとの対応関係

提案の各レビューが現行フローとどう重なるかを整理する。

| 提案レビュー | 現行での対応 | ギャップ |
|---|---|---|
| 1. 提案内容レビュー | `/grill-me` が設計曖昧点を解消、`/plan-issue-review` が計画を拒否できる | 小さい |
| 2. 計画書レビュー | `/plan-issue-review`（BP・セキュリティ・モダン開発観点あり） | 高リスク判定の出力がない |
| 3. セキュリティ設計・実装レビュー | なし（実装後の `/code-review` でのみ確認） | **大きい** |
| 4. 攻撃シナリオレビュー | なし（`/code-review` のOWASP Top10確認が最大） | **大きい** |
| 5. コードレビュー | `/code-review`（BP・セキュリティ・モダン開発観点あり） | 小さい |
| 6. 自動テストケースレビュー | `/plan-issue-review` でテストケース妥当性を確認 | 小さい |
| 7. ユーザーテストケースレビュー | `/test` で手動テスト確認項目を提示 | 小さい |

**フェーズとしてのギャップが大きいのは 3・4 のみ。** ただし、各フェーズの構造定義（停止条件・重大度区分）は全フェーズに共通して価値がある。

---

## 2. 要素別の批判的検討

### 2-1. 提案内容レビュー（不採用）

**採用しない。**

- `/grill-me` が設計の曖昧点をつぶし、`/plan-issue-review` が計画の妥当性を担保している。
- 「提案」段階でのレビューを独立フェーズにすると、イシューごとに1ステップ増える。
- イシュー起票→計画書作成の間に形式化されたレビューを挟む効果よりも、摩擦増加のコストが上回る。
- 提案の停止条件（要件曖昧・方針衝突・コスト対価値）はいずれも `/grill-me` と `/plan-issue-review` で判断できる。

**判断**: grill-me の質問観点に「実装する価値があるか」「既存方針との衝突」を明示的に加えることで吸収する。

---

### 2-2. 計画書レビューの「高リスク判定」出力（採用、軽微改善）

**採用する（ただし `/plan-issue-review` への追加として）。**

- 現行の `/plan-issue-review` はセキュリティ観点を含むが、「この変更が高リスクかどうか」を判定する明示的な出力がない。
- 計画書レビュー完了時に「高リスク判定: Yes/No」と「起動すべき横断レビュー」を出力するようにすることは、低コストで実現できる。
- 判定基準（認証・認可変更、マルチテナント境界、ファイルアップロード等）は提案のセクション4をそのまま採用できる。

**判断**: `/plan-issue-review` の手順に高リスク判定ステップを追加する。コスト低、効果大。

---

### 2-3. セキュリティ設計・実装レビュー（採用、攻撃シナリオと統合）

**採用する（攻撃シナリオレビューと統合した `/security-review` スキルとして）。**

現行フローの最大のギャップは「実装前に深掘りのセキュリティ設計レビューが存在しない」点だ。

- `/plan-issue-review` はセキュリティ観点を含むが、表層チェック（認可要件が計画書に明示されているか等）に留まる。
- `/code-review` は実装後のため、設計上の問題を発見してもコスト高なリワークが発生する。
- 認可モデル不整合・他テナント参照リスク・機微情報管理不備は、実装前に止めるべき。

**ただし、攻撃シナリオレビュー（2-4）と統合する。**

理由: 二つを別フェーズにする必要がない。設計レビューで「どんな攻撃経路が存在するか」まで考えるのが自然であり、別立てにすると形骸化しやすい。

---

### 2-4. 攻撃シナリオレビュー（採用、セキュリティ設計レビューに統合）

**単独フェーズとしては採用しない。セキュリティ設計レビューに統合する。**

- 攻撃シナリオ（入口・権限・操作・守るべき条件）の定義は、セキュリティ設計レビューの自然な延長であり別フェーズにする必然性がない。
- 高リスク変更時に「設計レビュー → 攻撃シナリオレビュー」と分けると2回のスキル呼び出しが必要になり、運用コストが高い。
- 統合した `/security-review` の中で「攻撃シナリオセクション」として扱えば同等の効果が得られる。

---

### 2-5. コードレビュー（現行維持）

**現行の `/code-review` で十分。追加不要。**

- 受け入れ条件照合・BP・セキュリティ・モダン開発観点はすでに実装されている。
- セキュリティレビュー結果との整合確認は、`/code-review` に「セキュリティレビュー結果との照合」ステップを追加するだけでよい。

---

### 2-6. 自動テストケースレビュー（不採用、現行強化で吸収）

**独立フェーズとしては採用しない。**

- `/plan-issue-review` がテストケースの妥当性（レベル使い分け・認可テスト・不正入力テスト等）をすでに確認している。
- 自動テストを書いた後・実行前に改めてテストケースをレビューするフェーズを挟むと、手順が増える割に発見できる問題が小さい。
- テストケースの不備は、テスト実行失敗・`/code-review` でのテスト不足指摘・`/fix-loop` で対処できる。

**判断**: `/plan-issue-review` のテスト観点に「攻撃シナリオ由来のテストが含まれているか（高リスク変更時）」を追加する。

---

### 2-7. ユーザーテストケースレビュー（不採用、/test に統合）

**独立フェーズとしては採用しない。**

- `/test` スキルが手動テスト確認項目を提示し、ユーザーがOK/NGを判断するフローが既にある。
- 「テストケースレビュー」と「テスト実施」を別フェーズにしても、実施前にレビューした項目がテスト時に変わることはない。
- UI変更時の表示確認・権限別表示確認の不足は、`/test` の手順を強化することで対応できる。

**判断**: `/test` の手動テスト確認項目生成ロジックに、UI変更時の表示・レスポンシブ・権限別差異チェックを明示的に含める。

---

### 2-8. 18ステップの高リスク変更フロー（reject）

**18ステップは多すぎる。採用しない。**

- 手順の多さは遵守率の低下を招く。形式だけ残って実質が空洞化するリスクがある。
- 現行の通常変更フロー（10ステップ）に対し、高リスク変更は `/security-review` を1ステップ追加した11ステップで収まる（セクション4参照）。

---

### 2-9. レビューの構造定義（役割 / 入力 / 出力 / 停止条件）（accept、横断適用）

**採用する。フェーズの追加とは独立して、既存スキル全体に横断的に適用する。**

現行スキルとの比較:

| 要素 | 現行スキル | 提案 |
|---|---|---|
| 役割定義 | 暗黙（スキル名から推測） | 明文化 |
| 入力定義 | スキルごとにバラバラ | 「何を読んで行うか」を明示 |
| 出力定義 | 「OK/NG + 任意コメント」のみ | 生成すべき成果物を定義 |
| **停止条件** | **記述なし（Claude の判断任せ）** | **「何があったら次に進めないか」を明示** |
| 重大度区分 | なし | Blocker / High / Medium / Low |

特に**停止条件の欠如**は現行スキルの構造的な問題だ。現行の `/plan-issue-review` には「何があったら実装を止めるか」が書かれておらず、同じ問題でもClaude の気分次第で OK/NG の判断がぶれる。提案の停止条件定義はこれを解消する。

**Blocker / High / Medium / Low の重大度区分**も同様に高い価値がある。現行は「NG」の一語で指摘の重みが表現されず、修正必須なのか推奨なのかが不明瞭になる。

これらの構造化は、フェーズを増やさずに既存スキルへ追加できる低コストの改善だ。

## 3. 採用・不採用のまとめ

| 提案要素 | 判定 | 理由 |
|---|---|---|
| 提案内容レビュー（独立フェーズ） | **不採用** | grill-me + plan-issue-review で吸収可能 |
| 計画書レビューへの高リスク判定追加 | **採用** | 低コスト・高効果 |
| セキュリティ設計・実装レビュー（/security-review） | **採用** | 実装前に深掘りする仕組みが現行にない |
| 攻撃シナリオレビュー（独立フェーズ） | **不採用** | /security-review に統合 |
| コードレビュー変更 | **不採用** | 現行で十分 |
| 自動テストケースレビュー（独立フェーズ） | **不採用** | plan-issue-review 強化で吸収 |
| ユーザーテストケースレビュー（独立フェーズ） | **不採用** | /test 強化で吸収 |
| **役割/入力/出力/停止条件の構造定義** | **採用（横断適用）** | 現行スキルに停止条件の記述がなく、判断がぶれる |
| Blocker/High/Medium/Low 区分 | **採用（横断適用）** | 指摘の重みが現行では「NG」の一語で不明瞭 |
| 18ステップ高リスクフロー | **不採用** | 複雑すぎる、遵守率低下リスク |
| GitHub Actions との接続定義（セクション6） | **別途検討** | 既存CIとの整合確認が必要。現行CIの整備状況を確認してからイシュー化する |

## 4. 推奨する実装

### 変更1: `/plan-issue-review` に高リスク判定を追加

レビュー完了時の出力に以下を追加する：

```
## 高リスク判定
判定: Yes / No
該当条件: [リスト]
推奨: `/security-review $ARGUMENTS` を先に実施してから `/implement` へ
```

高リスク条件（提案セクション4から）:
- 認証・認可・ロール変更
- マルチテナント境界変更
- 管理画面追加・変更
- ファイルアップロード/ダウンロード
- 外部公開API追加・変更
- Webhook・外部API連携
- 個人情報・機微情報の新規取り扱い
- DBスキーマ重要変更
- 既存事故の再発リスクが高い変更
- 画面制御していてもAPI直叩きで事故りうる変更

### 変更2: `/security-review` スキル新設

高リスク変更時に `/implement` 前に実行するスキル。
セキュリティ設計レビューと攻撃シナリオレビューを1スキルに統合する。

**入力**: 計画書・イシュー・API仕様・権限モデル・DB変更案

**出力（1スキルで両方をカバー）**:

_セキュリティ設計観点_
- 設計上の重大リスク
- 実装上の禁止事項
- 必須の防御条件

_攻撃シナリオ観点_
- 入口・想定権限・想定操作・守るべき条件
- 自動テスト化対象 / 手動確認対象
- 残余リスク

**停止条件**: Blocker（認可モデル不整合・他テナント参照リスク・高リスクシナリオ未対策等）がある場合は次工程へ進まない。

### 変更3: 既存スキル全体に構造定義を追加

フェーズ追加とは独立した、横断的な改善。

**停止条件の追加**: 各スキルに「この状態なら次工程へ進まない」を明示する。

| スキル | 停止条件（例） |
|---|---|
| `/plan-issue-review` | 認可モデル不整合がある / 影響範囲が不明 / 高リスク判定 Yes なのに security-review が計画されていない |
| `/code-review` | 受け入れ条件の未達がある / 重大セキュリティ欠陥がある / Blocker 指摘が残存している |
| `/test` | 自動テストが1件でも失敗（現行実装済み） / 手動テスト NG |

スキルの手順末尾に「Blocker が残っている場合は STOP し、次工程へ案内しない」と1行追加することで対応できる。

**重大度区分の追加**: 指摘を Blocker / High / Medium / Low で分類する。

指摘一覧テーブルに「重大度」列を追加する（例）:

```
| 重大度 | 指摘内容 | 該当箇所 | 対応 |
|--------|---------|---------|------|
| Blocker | 他テナントのデータを参照できる設計になっている | API設計 | 実装前に修正必須 |
| High | ページネーションが考慮されていない | 一覧API | 当該PRで修正推奨 |
| Medium | エラーレスポンスの形式が統一されていない | ... | チケット化して期限を切る |
| Low | 変数名がコーディング規約と微妙にズレている | ... | 改善提案、見送り可 |
```

### 推奨する高リスク変更フロー（11ステップ）

```
1. /issue-bootstrap
2. /grill-me（推奨）
3. /plan-issue
4. /plan-issue-review → 高リスク判定 Yes
5. /security-review（設計レビュー + 攻撃シナリオ）← 追加ステップ
6. /implement
7. /code-review（セキュリティレビュー結果との照合を含む）
8. /test（自動テスト + 手動テスト）
9. /retro（必須）
10. /close → PR → 人が承認 → マージ
```

通常変更（10ステップ）に `/security-review` を1ステップ追加するだけ。提案の18ステップから大幅に圧縮し、遵守率を維持する。

## 5. 提案の優れている点（残す考え方）

採用・不採用にかかわらず、以下の設計思想は正しく、スキル改善の指針として引き継ぐ。

1. **「各レビューを役割/入力/出力/停止条件で定義する」**: 現行スキルの最大の構造的欠如。採用して全スキルに横断適用する。
2. **「Blocker が残っている限り次工程へ進まない」**: 現行でも方針として存在するが、スキルの手順に明示されていない。
3. **「高リスク変更には実装前の深掘りが必要」**: 完全同意。現行フローの最大のフロー上のギャップ。
4. **「自動テストと人手確認の責務を明確に分ける」**: `/test` スキルの改善で反映する。
5. **「5本レビューの中にもセキュリティは内包する」**: 既存スキルの設計と一致している。

## 7. 内容面の未解決問題と推奨案

実装前に方針を決めておくべき論点を整理する。特に **7-1・7-3 はイシューA・Bの実装が止まる** ため先決する。

### 7-1. security-review の出力をどこに保存するか

**推奨: B（計画書に専用セクションを追記）**

| 選択肢 | 概要 | 判断 |
|---|---|---|
| A. `docs/security-reviews/` に新規ファイル | 参照は確実。新しいディレクトリ・命名規則・ライフサイクル管理が増える | 管理コスト過大 |
| **B. 計画書に `## セキュリティレビュー結果` セクションを追記** | **既存の plan_*.md に書き足すだけ。code-review が計画書を読む手順はすでにある** | **採用** |
| C. 会話コンテキストのみ | セッションをまたいだら消える。fix-loop 後に再開すると参照できない | リスク大 |

B を採用する理由:
- `/code-review` はすでに計画書を読む。保存先を増やさずに参照経路を確保できる。
- 計画書の肥大化は「セクションを追記する」構造にすれば許容範囲。
- A のようにファイルを新設すると命名規則・ステータス管理・移動ルールが増え、review-rules.md の複雑さが増す。

**実装方法**: `/security-review` の最後に「計画書の末尾に以下を追記する」ステップを追加し、テンプレートに `## セキュリティレビュー結果` セクションを設ける。

---

### 7-2. 残余リスクをどう追跡するか

**推奨: B+C の組み合わせ（計画書に記録 → retro で処遇を決定）**

| 選択肢 | 概要 | 判断 |
|---|---|---|
| A. 全件イシュー化 | 追跡は確実。Low 残余リスクまでイシューが増えてバックログが汚れる | 過剰 |
| **B. 計画書に記録のみ** | **7-1 の方針と一致。記録は残る** | **採用（ただし追跡手段が別途必要）** |
| **C. retro で処遇を決定** | **既存の振り返りの場を使う。追加コスト最小** | **採用（B と組み合わせ）** |

推奨する運用:
1. `/security-review` 実行時に残余リスクを計画書の `## セキュリティレビュー結果` に記録する（B）。
2. `/retro` の振り返り項目に「残余リスクの処遇」を追加し、High 以上はイシュー化・Medium 以下は判断任意とする（C）。

全件イシュー化（A）はバックログを汚す。記録のみ（B 単体）は埋もれる。retro で処遇を決める仕組みを組み合わせることで、追跡と実用性を両立する。

### 7-3. 高リスク判定のグレーゾーン

**推奨: A（1条件でも直接該当したら高リスク）＋ユーザーによる明示的なスキップ許可**

| 選択肢 | 概要 | 判断 |
|---|---|---|
| **A. 1条件でも該当したら高リスク** | **安全側の判断。過検知のコストはレビュー1回分** | **採用（ただしスキップ経路を設ける）** |
| B. Claude の総合判断 | 現実的だが、同じ変更でも判断がぶれる。ルールの安定性が失われる | 採用しない |
| C. 軽微該当は中間扱い | 「直接 vs 間接」の判断自体が曖昧で、結局 B と同じ問題を抱える | 採用しない |

推奨する運用:
- 条件に1つでも直接該当したら `/security-review` を推奨する（A）。
- ユーザーが「このイシューはセキュリティレビュー不要と判断する」と明示した場合のみスキップを許可し、その判断を計画書に記録する。
- セキュリティ上の見逃しコストは、過剰レビューのコストを大きく上回る。

B・C を採用しない理由: Claude の判断はセッションや文脈によってぶれる。「ルールは明確に、例外は人が明示的に承認する」形が運用の安定性を保つ。

---

### 7-4. security-review の知見を retro・ルール改善に循環させるか

**推奨: A（retro の振り返り観点に追加する）**

| 選択肢 | 概要 | 判断 |
|---|---|---|
| **A. retro に「設計ルール昇格」観点を追加** | **コスト低。security-review の知見が将来のイシューに活きる** | **採用** |
| B. 対応しない | 発見したパターンがそのイシューで消える。同じ問題が別イシューで再発する | 採用しない |

B を採用しない理由: セキュリティレビューで見つかる問題は往々にしてプロジェクト固有のアーキテクチャに起因する。その知見を retro でルール化しないと、同種の問題が毎回ゼロから発見されることになる。

**実装方法**: `/retro` の振り返り観点に「今回の security-review で発見した問題パターンを、grill-me の確認観点または plan-issue-review のチェック項目に昇格できるか」を1項目追加する。

### 決定事項まとめ

| 論点 | 決定 |
|---|---|
| 7-1. 出力の保存先 | 計画書に `## セキュリティレビュー結果` セクションを追記 |
| 7-2. 残余リスクの追跡 | 計画書に記録 → retro で High 以上はイシュー化・Medium 以下は判断任意 |
| 7-3. グレーゾーン判定 | 1条件でも直接該当したら高リスク。スキップは人が明示承認した場合のみ |
| 7-4. 知見の循環 | retro に「設計ルール昇格」観点を追加する |
