# 良い学習アプリの品質基準（マルチセグメント：学校・企業・個人）

- **作成日**: 2026-06-19
- **目的**: 「よりよい学習アプリ」の**設計思想（北極星）**を定義し、今後の開発全体（計画・実装・レビュー）がこれに沿うことを保証する。**現状の特定ロジックを即時修正するための指示ではない。**
- **対象セグメント**: 学校・教育機関／企業（社内研修）／個人 を併願（いずれも対象）。学習者は未成年・成人の双方を含む。
- **設計原則**: 品質基準は「最も要求の厳しいセグメントに合わせる（最厳格セグメント基準）」。複数セグメントを併願するため、未成年・学校を含む以上、プライバシー・コンプライアンス（C2）とアクセシビリティ（C3）は任意ではなく必須。
- **対象範囲**: プロダクト（学習アプリそのもの）の品質基準。開発プロセスのレビュー観点（`review_perspective_framework.md` の P1〜P9）とは別軸。

---

## 1. 背景

当初挙げられた評価基準は次の5つだった。

1. マルチテナント対応
2. 導入先での運用完結（学習アプリ画面上の操作のみで保守運用）
3. フールプルーフ
4. フェールセーフ
5. セキュリティ

この5つを分類すると、性質が偏っていることが分かる。

| 当初基準 | 性質 |
|---|---|
| マルチテナント | アーキテクチャ |
| 運用完結 | 運用性（保守性） |
| フールプルーフ | 誤操作防止（使いやすさ） |
| フェールセーフ | 信頼性（障害時の安全） |
| セキュリティ | セキュリティ |

**5つとも「容れ物（システムの堅牢さ・運用のしやすさ）」の基準であり、「中身＝学習アプリとして実際に学習効果があるか」を測る基準が1つもない。** この5基準を満点にしても「壊れず・安全で・誤操作しにくいが、誰も学習が捗らないアプリ」が成立し得る。学習アプリにとってこれは本末転倒である。

加えて対象セグメントに学校・教育機関を含み、学習者に未成年を含む以上、**未成年の個人情報**と**合理的配慮（アクセシビリティ）**は任意ではなく事実上の必須要件となる。複数セグメントを併願するため、品質基準は最も要求の厳しいセグメントに合わせる（**最厳格セグメント基準**）。これらはセキュリティとは別軸であり、当初の5基準では捕捉できない。

そこで、当初5基準に3基準を加えた**8基準**を「良い学習アプリの定義」として確定する。

---

## 2. 品質基準（8基準）

### グループA：学習価値（中身）

#### C1. 学習効果（教育的有効性）★最優先・新規

- **定義**: このアプリで学ぶと学習成果が上がることを測定・改善できる。
- **観点**: 定着率・正答率の改善、間隔反復（spaced repetition）の科学的根拠、つまずき検知、復習タイミング最適化、モチベーション維持。
- **なぜ重要か**: 学習アプリの存在理由そのもの。他の7基準は全てこれを支える手段。
- **現状**: `QuizSession` / `ProblemAttempt` / `StudyLog` / `DailyStudySummary` などログの器はある。間隔反復の「器」は存在するが、**学習効果を測る指標（KPI）と科学的根拠の明示がない**。
- **ギャップ**: 効果測定指標の定義、間隔反復アルゴリズムの根拠づけ、つまずき検知ロジック。

### グループB：法令・利用文脈（学校ゆえ必須）

#### C2. プライバシー・コンプライアンス（新規）

- **定義**: 正常稼働時でも個人情報を適法に扱う。
- **観点**: 個人情報保護法、未成年＝保護者同意、文科省「教育データの利活用」関連ガイドライン、データ保持期間・削除権・データ所有権（学校が管理者）、テナント横断のデータ混在をポリシーレベルで禁止。
- **セキュリティとの違い**: セキュリティ＝「攻撃者を防ぐ」。プライバシー＝「攻撃がなくても適法に扱う」。
- **現状**: メール検証・トークン管理はあるが、**保持期間・削除権・保護者同意・データ所有権の方針が未整備**。
- **ギャップ**: データ保持/削除ポリシー、同意管理、データ主体の権利対応（開示・削除）。

#### C3. アクセシビリティ（新規）

- **定義**: 障害のある児童生徒を含め誰もが操作できる。
- **観点**: WCAG準拠、キーボード操作、コントラスト比、スクリーンリーダー対応、合理的配慮。
- **なぜ重要か**: 教育機関導入では事実上の要件。
- **現状**: 体系的なアクセシビリティ対応・基準は未確認。`review_perspective_framework.md` の P6 に部分的に含まれるが、プロダクト基準としては未確立。
- **ギャップ**: アクセシビリティ基準の策定とUIコンポーネントの準拠。

### グループC：堅牢な容れ物（当初5基準・維持）

#### C4. マルチテナント

- **現状**: Row-level（`organization_id` カラム）の手作り実装。`get_queryset()` のフィルタ＋`AccessPermissionChecker`（ホワイトリスト）でテナント分離。django-tenants 等は未使用。
- **論点**: 学校・企業とも厳格分離が契約要件になりやすい。フィルタ漏れ1箇所＝個人情報（未成年含む）の越境漏洩に直結する。row-level 手作り継続でよいか、スキーマ分離等へ寄せるか要検討。
- **ギャップ**: 分離方式の妥当性レビュー、越境リスク箇所の網羅監査。

#### C5. 導入先での運用完結

- **現状**: ユーザー管理・科目管理・問題管理・統計の React UI は実装済み。テナント（学校）の作成/削除はスーパーユーザー＋手作業の可能性大。
- **論点**:
  - **テナントのライフサイクル全体**：プロビジョニング→運用→オフボーディング（卒業・転校・退職・解約時のデータ移行/削除）まで画面上で完結して初めて「運用完結」。
  - **ロールモデル**：現状 `user`/`admin` の2階層。セグメントごとに必要なロール階層が異なる（学校＝生徒/教員/学校管理者、企業＝受講者/講師/管理者、個人＝単独）。特に「指導者（教員・講師）が担当学習者の進捗を見る」テナント内アクセス制御が学校・企業セグメントの核になる。
- **ギャップ**: テナント自己プロビジョニング、オフボーディング/データ移出、ロール3階層化。

#### C6. フールプルーフ（誤操作防止）

- **現状**: フロント/バックのバリデーション、カスタム例外ハンドラー（main/sub message）あり。
- **ギャップ**: 破壊的操作（生徒データ削除等）の確認ステップ、取り消し可能性の体系化。

#### C7. フェールセーフ（障害時の安全）

- **現状**: 監視（RequestMonitor / ErrorTracker）、Redis キャッシュ、Celery、DBバックアップスクリプトあり。
- **拡張すべき軸**: **可観測性（オブザーバビリティ）** — 「壊れる前/壊れた時に気づける」こと。テナント管理者自身が見られる稼働状況・監査ログ。**パフォーマンス公平性** — 1テナントの重い処理が他に波及しない（noisy-neighbor 対策）。
- **ギャップ**: SLO/アラート、テナント向け稼働可視化、テナント間リソース公平性。

#### C8. セキュリティ

- **現状**: JWT (SimpleJWT)、rate limiting、CORS、パスワード強度、アカウントロック、bandit/Ruff。`/security-review` スキルは新設予定（I044）。
- **ギャップ**: 高リスク変更（認可・テナント境界）の実装前セキュリティレビュー運用（I044 と連動）。

## 3. 早期に決めるべき設計判断（後から変えると高くつく順）

1. **マルチテナント分離方式**（C4）— row-level 手作り継続か、スキーマ分離等か。テナント数規模と学校・企業の分離要件で判断。**最も高くつく決定。**
2. **ロール階層の一般化＋指導者-学習者の閲覧関係**（C5）— 既存2階層モデルを、セグメント差（学校/企業/個人）を吸収できる多階層へ拡張。データモデルに波及するため早期確定が望ましい。
3. **学習データの保持・削除ポリシー**（C2）— 卒業/退職/解約後のデータをいつまで持つか／誰が消せるか。

## 5. 位置づけと運用

1. 本基準セット（8基準）は**学習アプリ全体の設計思想**であり、ユーザー承認をもって今後の開発の前提（北極星）とする。
2. 今後の各イシュー・機能は、**計画段階とレビュー段階でこの8基準に照らして判断**する（`review_perspective_framework.md` の P1〜P9 と併用）。
3. 本文書中の「現状」「ギャップ」記述は**参考情報**であり、即時修正のタスクリストではない。§3 の設計判断は、関連する機能を新規に作る/変える際に本思想に沿って決める。

---

## 6. 補足：開発プロセスのレビュー観点との関係

本文書は**プロダクトの品質基準**であり、`review_perspective_framework.md` の9観点（P1〜P9、コードレビュー時に「何を見るか」）とは目的が異なる。両者は次のように対応する（重複は意図的）。

- C4 マルチテナント ↔ P1 要件適合性（組織スコープ）
- C8 セキュリティ ↔ P2 セキュリティ
- C2 プライバシー・コンプライアンス ↔ P9 プライバシー・コンプライアンス（I071 で確立。攻撃防御＝P2 / 平時の適法な取り扱い＝P9）
- C7 フェールセーフ/可観測性 ↔ P5 運用性
- C3 アクセシビリティ ↔ P6 性能・UX・アクセシビリティ
- C1 学習効果 ↔ レビュー観点なし（意図的）: 開発・レビュー時点では検証不能であり、リリース後の KPI 計測（定着率・正答率・継続率）で担保する。設計思想の全基準が必ず 1 対 1 でレビュー観点に対応するわけではない。

本基準（C1〜C8）は「何を作るか」を、レビュー観点（P1〜P9）は「正しく作れたか」を見る。
