# review-gate（レビュー段階）

止めてユーザーに聞くのは `docs/runbooks/workflow.md`「止めて聞く条件」に当たるときだけ。それ以外で決めたことは `docs/reviews/open/$ARGUMENTS_review.md` の「## 自律判断の記録」に `- [review-gate] 決めたこと — 理由` で書く。

## 1. 基本レビュー（CI 待ち・組み込みのレビュー・決定論ゲート実走つき）

**全体のレビューと差分のレビュー（台帳・I197）**: 1 回目はブランチ全体を見て、指摘を台帳（番号・重大度・状態）にする。やり直し（fix-loop の後）は、前の記録の `REVIEWED_COMMIT` からの直した差分と、台帳の止める指摘が直ったかだけを見る（全体を探し直さない）。合否はスクリプトが台帳の FINDING 行の欄（FILE・LINE・STOP・再現）から決定論で出す（I205。code-reviewer の VERDICT 行は合否に使わない）: アプリ本体はブランチで変えた行（と前後 3 行）または受け入れ条件の未達の、再現のある Blocker・High・Medium で止める。ハーネスは止める条件の一覧（流れが動かなくなる・秘密情報や個人情報が外に出る・develop/main や GitHub から戻せない設定を壊す・受け入れ条件の未達）に当たる、再現のある指摘だけで止める。GitHub から復旧できない例外（`path_risk_trigger()` の集合）は Blocker・High で止める。差分の外でも、セキュリティの Blocker は止める。止めない指摘は台帳に残り、retro が後続のイシューか軽い指摘の一覧へ回す（正は `docs/runbooks/review-rules.md`「検証の全体設計」）。どちらにするか・範囲・台帳はスクリプト（`scripts/claude/code-review.sh`）が決める（台帳のある最新の記録の `REVIEWED_COMMIT` が HEAD の祖先なら差分のレビュー）。高リスクかどうか（3. を走らせるか）は、計画レビューの判定・パスの判定・台帳の目印（code-reviewer が計画の見立てを超えた高リスクの変更に付ける `RISK=up`・I202）で決まる。一度 YES になったら戻らない。

Bash ツールの `run_in_background: true` で実行し、完了の通知で結果を受け取る（CI 待ちと組み込みのレビューで、前面の実行の上限 10 分を超えうるため。背景の実行が 10 分を超えても止まらないことは 2026-10-25 に 700 秒で実測した。それより長い上限があっても、下の「判定行が無いとき」の扱いで止まる側に倒れる）:

```bash
bash scripts/claude/code-review.sh "$ARGUMENTS"
```

終了コードの扱い:
- 出力に `FINAL_VERDICT:` 行が無い（途中で止まった・背景の実行が打ち切られた）: 終了コードによらず、1 回だけ実行し直す。2 回続けば止める（止める条件 3）。判定行が無いまま先へ進まない
- exit 0: 2. へ
- exit 3（CI 待ちの時間切れ）: 1 回だけ実行し直す。2 回続けば止める（止める条件 3: 安全側の選択肢が無い）
- exit 1 で出力に `CI_WAIT: FAIL` がある: CI の失敗を直すため `STAGE_DONE: review-gate NEXT: fix-loop` を書いて終わる
- exit 1 で出力に `CI_WAIT: NOT_PUSHED` がある（PR の最新のコミットが手元の HEAD と違う）: push してから 1 回だけ実行し直す。それでも同じなら止める（止める条件 3）
- exit 1 で出力に `CI_WAIT: NO_JOBS` がある（ワークフローのジョブ名を読めない。python3 の PyYAML が無いなど）: 原因を直して 1 回だけ実行し直す。直せなければ止める（止める条件 3）
- exit 1 で出力に `CI_WAIT: NO_PR` がある（PR を調べられない・開いている PR が無い）: 原因（gh の認証・ネットワーク・PR が閉じている）を直して 1 回だけ実行し直す。直せなければ止める（止める条件 3）。CI を確かめないまま先へ進まない
- 出力に `OFFICIAL_SECURITY: FAILED` がある（高リスクの変更で組み込みの `/security-review` が動かず、HIGH になった）: 直すものが無い基盤の失敗なので fix-loop に回さず、1 回だけ実行し直す。2 回続けば止める（止める条件 3）
- それ以外の exit 1（fetch の失敗・イシューファイルが無いなど）: 出力を記録に書き、止める条件 3 に当たるかを判定する（直せる原因なら直して実行し直す）

## 2. 出力の機械判定

スクリプト stdout の固定行（`ADVERSARIAL_STAGE:` と `FINAL_VERDICT:`）で分岐する:

- `FINAL_VERDICT: BLOCKER` または `FINAL_VERDICT: HIGH` → 4. の結線で `NEXT: fix-loop`（修正の後は fix-loop が必ずこの段階に戻す）
  - **繰り返しの上限**（review-gate ⇄ fix-loop が終わらないことを防ぐ・I193）: 記録の最後の `STAGE_DONE: review-gate NEXT: fix-loop` の行が、途中に `STAGE_DONE: review-gate NEXT: test-gate` か `STAGE_DONE: implement` の行を挟まずに数えて（実装をやり直したら数え直す）、今回で 5 回目になるときは、fix-loop へ回さずに止める（止める条件 3）。この上限は最後の安全網で、ほかの決まり（止める条件の一覧・行で決める範囲・再現の欄）で止まらなかったときだけ当たる。当たったら、止め方の見直しが要る兆しとして止めて聞く（I205）。fix-loop で直すのは、記録の `## 止める指摘（スクリプトが決めた・fix-loop が直すのはこれだけ）` の節にある指摘だけ（それ以外の台帳の指摘は直さない。台帳に残り retro。直して新しい穴を生む回り道をしない・I197）
- `FINAL_VERDICT: OK` かつ `ADVERSARIAL_STAGE: NOT_REQUIRED` → 4. の結線で `NEXT: test-gate`
- `FINAL_VERDICT: OK` かつ `ADVERSARIAL_STAGE: REQUIRED` → 3. の敵対的レビューステージを実行する

## 3. 敵対的レビューステージ（高リスク時のみ）

実装者・基本レビューの「合格」を反証する独立ステージ。実装者の自己レビューは判定根拠にしない（docs/runbooks/review-rules.md「高リスク変更の敵対的レビューステージ」参照）。1 周の段取りと判定は `scripts/claude/adversarial-review.sh` が行う（I197）: 読むだけのレビュー役（`.claude/agents/adversarial-reviewer.md`）を 3 観点で別プロセスの `claude -p` として並列に起動し、実験案は実験役（別プロセス・自動承認モード・承認なし）が実行して結果を返す。判定は計画書の「## 必ず確かめる項目」の一覧から決定論で出す。レビュー役も実験役も `--permission-prompts none` で起動するので、承認が要る操作は待たずに拒否されて記録に残る（この会話の中に確認画面は出ない）。

### 3-0. 対象と上限

- 対象は `ADVERSARIAL_STAGE: REQUIRED` のときだけ（判定の正は `scripts/claude/code-review.sh`。アプリの高リスク条件、ハーネスの「GitHub から復旧できない例外」に関わるファイルの変更、または台帳の目印 `RISK=up`）。計画書に「## 必ず確かめる項目」が無いまま台帳の目印で REQUIRED になったときは、3-2 の exit 2 の手順（一覧を足してコミットし、1 回だけ実行し直す）で扱う。
- 上限: **1 周 10 分（スクリプトが締め切る）・攻め筋は 1 観点 3 本まで・実験の往復は 1 観点 2 回まで・1 周 3 観点（固定）・イシュー全体で 2 周まで**（この段階をやり直しても数え直さない）。周回の数え方（過去の記録の `ROUNDS:` の合計・行の無い記録は 1）と見る範囲（最新の記録の `REVIEWED_COMMIT` から。無ければ `origin/develop`）はスクリプトが決める。
- 固定 3 観点: 1 ロジック回避・実機 repro／2 テストの false-green・tautology／3 要件・脅威モデルの網羅漏れ。

### 3-1. 起動

Bash ツールの `run_in_background: true` で 1 回実行し、完了の通知で結果を受け取る（この会話でサブエージェントやタイマーは起動しない）:

```bash
bash scripts/claude/adversarial-review.sh "$ARGUMENTS"
```

ユーザーが延長（下の「上限到達」の 2）を承認したときだけ、`ADV_ROUND_LIMIT=3` を前に付けて実行する。

### 3-2. 終わり方（終了コードと `ADVERSARIAL_VERDICT:` 行で決める）

- 出力に `ADVERSARIAL_VERDICT:` 行が無い（途中で止まった・背景の実行が打ち切られた）: 1 回だけ実行し直す。2 回続けば止める（止める条件 3）
- exit 0（`ADVERSARIAL_VERDICT: OK`）: ステージ通過。最終判定 OK
- exit 1（HIGH・BLOCKER。3 観点とも報告した）: 記録の「確かめる項目の結果」と findings を読み、3-3 で直す。直した後、`bash scripts/claude/code-review.sh "$ARGUMENTS"` を 1. と同じく背景で実行し直し（直した差分を基本レビューに通す）、OK なら 3-1 で次の周を起動する（スクリプトが前の周の `REVIEWED_COMMIT` からの差分だけを見る。修正の妥当性も反証対象）
- exit 3（報告の無い観点がある。記録は `ROUNDS: 0` で周に数えない）: **報告の無い観点を合格に数えない**（その観点の項目はすべて未検証。VERDICT は HIGH）。記録の「観点ごとの実行」の終わり方・最後のツール呼び出しを自律判断の記録に書き、1 回だけ実行し直す。2 回続けば止める（止める条件 3。時間切れ・失敗が続くのは仕組みの見直しが要る兆し）
- exit 4（`ADVERSARIAL_VERDICT: LIMIT`）: 下の「上限到達」へ
- exit 2（`ADVERSARIAL_ERROR:`。一覧が無い・形が違う・作業ツリーに記録の場所の外の変更がある・引数の誤り）: 原因が記録の場所で直せる（計画書に一覧を足す・形を直す）なら直してコミットし、1 回だけ実行し直す。一覧を足すのは計画の範囲を変えないので計画変更記録に 1 行書き、計画レビューは通り直さない。直せない・2 回続くときは止める（止める条件 3）
- **OK の周の後に差分を足さない**（足すと、その差分を見た OK の周が無くなり、`gate-check.sh` が通さない）。
- **アプリ本体のイシューに関係する Medium**（ブランチで変えた行の中、または受け入れ条件・計画の未達。I205）: 上限が残っていれば直して、1. の基本レビュー（差分のレビュー）を通し、次の周で確かめる（その周は直した差分だけを見る）。上限が残っていなければ直さずに記録し、retro が最優先の後続のイシューにする（上限は増やさない・`gate-check.sh` は変えない）。
- ハーネスの Medium・すべての Low は、次の周に進む理由にしない（記録に残し、retro が後続のイシューか軽い指摘の一覧へ回す）。
- **上限を使い切った後のコードの変更**: 通算 2 周を使い切った後に（最後の周が OK で終わっていても）、人の手動テストの NG などで fix-loop がコードを直して戻ってきたときは、直した差分を見る OK の周を作れないので、下の「上限到達」と同じに止める（止める条件 3。ユーザーの承認で 1 周だけ延長できる）。gate-check も、最後の敵対的レビューの後の変更を通さない
- **上限到達**（通算 2 周で Critical/High・未検証が残る）: 自動 OK にせず、最終判定を HIGH 以上に固定して止める（止める条件 3。セキュリティにかかわる指摘を受け入れて進む判断は Claude だけではしない）。「上限到達・未収束」と明記し、残った指摘と過去の周の指摘を**種類ごとに集計**する（種類 = 「どの仕組みのどんな穴か」を 1 行で名付けたもの。例: 「文字列の解析が bash の構文の一部を取り違える」）。ユーザーへの選択肢は次の順に出す:
  1. 同じ種類が 2 周続いていれば、先頭に「**止める場所・方式の見直し**」（列挙で塞ぐ方式の限界の疑い）
  2. 修正してもう 1 周（ユーザーの承認で 1 周だけ延長。`ADV_ROUND_LIMIT=3` で起動する）
  3. 残りを受け入れて進む（理由を記録）
  - ユーザーが 3 を選んだときだけ、受け入れの記録 `docs/reviews/I###_adversarial_review_<ts>.md` を新しく作る: ユーザーの言葉（そのまま）・日時・受け入れた指摘の一覧を書き、最終行の前に `REVIEWED_COMMIT: <受け入れた時点の HEAD>` と `ROUNDS: 0`（周回に数えない）、最終行に `VERDICT: OK`（gate-check はこの記録を読んで通す）。Claude が自分で受け入れを書くことはしない（止める条件 3）

### 3-3. findings と未検証の項目の修正（依頼側が実施）

- 修正は本スキル（メインセッション）が Edit/Write で行う。レビュー役には修正させない。
- 修正は findings 対応の範囲に限定し、修正内容を自律判断の記録に残して commit する。
- 要件・基本設計・UI/UX の判断が要る findings だけ、ユーザーに確認して止める（止める条件 1）。技術的な直し方は自分で決めて記録する。
- **未検証の項目**（実験が拒否された・時間が足りなかった・実験必須を読んで確認しただけ）: その項目を確かめる決定論の TC（失敗注入つき）を auto_test に足し、計画書の一覧のその行の内容に `TC-xx` を書き足して次の周へ進む。一覧の確かめ方を「読んで可」に下げてよいのは、決定論の TC で覆ったときだけ（計画変更記録に 1 行。方式・範囲・受け入れ条件は変えないので計画レビューは通り直さない）。

### 3-4. 記録

- 記録 `docs/reviews/I###_adversarial_review_<YYYYMMDD_HHMM>.md` はスクリプトが書いてコミットする（確かめる項目の結果・観点ごとの実行〔終わり方・所要・往復・拒否・最後のツール呼び出し〕・実験・各観点の本文。最後の行は `REVIEWED_COMMIT:`・`ROUNDS:`・`VERDICT:`）。
- PR コメント（失敗しても止めない。GitHub のコメントの上限を超えるときは、スクリプトが一部と記録への参照だけを載せる）:
  ```bash
  bash scripts/claude/post-review-comment.sh docs/reviews/I###_adversarial_review_<ts>.md
  ```
- 最終判定 = max(スクリプト FINAL_VERDICT, 敵対ステージ VERDICT)

## 4. 結線（必須）

`docs/reviews/open/$ARGUMENTS_review.md` の末尾に 1 行足して commit/push する:
- 最終判定 OK: `STAGE_DONE: review-gate NEXT: test-gate`
- 最終判定 HIGH / BLOCKER（上限到達で止める場合を除く）: `STAGE_DONE: review-gate NEXT: fix-loop`
- 止める条件に当たって止まるときは `STAGE_DONE:` を書かない（`/proceed` で再開すると、この段階からやり直す）
