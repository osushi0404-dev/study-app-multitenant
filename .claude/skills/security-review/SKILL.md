# /security-review

前提: `/plan-issue-review` で高リスク判定 Yes が出ている。`/implement` の前に実行する。

## 手順

### 1. 対象ドキュメントを読む

必須:
- `docs/issues/open/$ARGUMENTS.md`
- `docs/plans/open/plan_$ARGUMENTS.md`

計画書の「影響範囲」を確認し、バックエンドコード変更がある場合は関連ファイルを特定して読む:
- 認証・認可: `backend/*/permissions.py`、対象 View ファイル
- シリアライザ: `backend/*/serializers.py`（対象モデルのみ）
- モデル定義: `backend/*/models.py`（対象モデルのみ）
- URL: `backend/*/urls.py`

バックエンド変更がない場合は「コード変更なし」と明記してスキップする。

---

### 2. セキュリティ設計レビュー

以下の8分類すべてを確認し、問題を列挙する。問題がなければ「なし」と記載する。

| 分類 | 確認項目 |
|------|---------|
| 認証・認可 | エンドポイントごとの認証必須要件が明示されているか。最小権限の原則に従っているか |
| マルチテナント | 他テナントのデータを参照・操作できる設計になっていないか |
| 入力検証 | ユーザー入力のバリデーション・サニタイズ方針が計画書に含まれているか |
| 機密情報 | パスワード・トークン・個人情報がログ出力・レスポンスに露出しないか |
| OWASP Top 10 | XSS・SQLi・CSRF・IDOR・セキュリティ設定ミス等のリスクが考慮されているか |
| ファイル操作 | ファイルアップロード/ダウンロードがある場合、拡張子・サイズ・パス検証があるか |
| 外部通信 | 外部API・Webhook連携がある場合、SSRF・認証情報漏洩のリスクがあるか |
| 依存ライブラリ | 新規追加ライブラリに既知の重大脆弱性がないか |

**出力形式**:

```
## セキュリティ設計レビュー

| 重大度 | 分類 | 設計上のリスク | 対処（禁止事項 / 必須防御条件） |
|--------|------|--------------|-------------------------------|
| Blocker/High/Medium/Low | [分類] | [具体的なリスク] | [対処内容] |
```

リスクが見つからなければ以下を出力する:

```
## セキュリティ設計レビュー
設計上のリスクなし（コード変更なし、またはリスク該当なし）
```

---

### 3. 攻撃シナリオレビュー

今回の変更で新たに公開・変更されるエンドポイント・機能を特定し、攻撃シナリオを列挙する。

**分析手順**:
1. 計画書の変更点から「新規/変更されるエンドポイント・機能」を特定する
2. 攻撃者が試みうる操作（認証バイパス・権限昇格・他テナントアクセス等）を想定する
3. 「守るべき条件」が現在の設計で保証されているかを確認する
4. 自動テスト化できるシナリオと手動確認が必要なシナリオを区別する

**出力形式**:

```
## 攻撃シナリオレビュー

| # | 入口 | 想定権限 | 想定操作 | 守るべき条件 | 自動テスト化対象 | 手動確認対象 | 残余リスク | 重大度 |
|---|------|---------|---------|------------|----------------|------------|---------|--------|
| 1 | [API/機能] | [未認証/一般/管理者] | [具体的操作] | [防御条件] | [Yes: 概要 / No] | [Yes: 概要 / No] | [残る不確かさ] | Blocker/High/Medium/Low |
```

バックエンド・フロントエンドのコード変更がない場合（スキルファイル変更のみ等）は以下を出力する:

```
## 攻撃シナリオレビュー
攻撃シナリオなし（コード変更なし）
```

---

### 4. レビュー結果サマリーを出力する

```
## レビュー結果サマリー

| 重大度 | 設計レビュー | シナリオ |
|--------|------------|---------|
| Blocker | X件 | X件 |
| High    | X件 | X件 |
| Medium  | X件 | X件 |
| Low     | X件 | X件 |
```

---

### 5. 計画書に `## セキュリティレビュー結果` セクションを追記する

`docs/plans/open/plan_$ARGUMENTS.md` の末尾に以下を追記する（Edit ツールを使用）:

````markdown
## セキュリティレビュー結果

**実施日**: YYYY-MM-DD

### セキュリティ設計レビュー

[手順2の出力をそのまま貼る]

### 攻撃シナリオレビュー

[手順3の出力をそのまま貼る]

### 残余リスク処遇
（/retro で決定する）
````

---

### 6. 停止条件チェック

**Blocker が1件でも残っている場合**:

⛔ STOP。以下を出力して停止する。

```
Blocker が残っています。
計画書または設計を修正してから `/security-review $ARGUMENTS` を再実行してください。
`/implement` へは進まないでください。
```

**Blocker がない場合**:

✅ セキュリティレビュー完了。

```
`/implement $ARGUMENTS` を実行してください。
```
