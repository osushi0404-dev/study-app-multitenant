# /grill-me

計画書作成前に、イシューの設計上の曖昧な点をユーザーに確認する。

## 実施手順

### 1. イシューファイルを読み込む
```bash
cat docs/issues/open/$ARGUMENTS.md
```

### 2. コードベースを探索して自己解決できる疑問を除去する
- 関連スキルファイル・既存コード・runbooks を読み、コードを見れば分かる疑問は除く

### 3. 設計上の曖昧な点を一括提示する

**提示フォーマット**:
```
## 設計確認（/grill-me $ARGUMENTS）

以下の点について確認させてください。

1. [質問1]
2. [質問2]
...

回答いただけましたら `/plan-issue $ARGUMENTS` を実行してください。
```

設計上の疑問点がない場合は以下を表示する:
```
設計上の疑問点はありませんでした。
`/plan-issue $ARGUMENTS` を実行してください。
```

### 4. ユーザーの回答をイシューファイルに追記する

ユーザーが回答したら、イシューファイルの「## 関連資料」セクションの直後に以下を追記する:

```markdown
## 設計確認メモ（/grill-me）
- Q: [質問1] → A: [回答1]
- Q: [質問2] → A: [回答2]
```

**必須確認（全イシュー）**:
コードベースを読んで自己解決できる場合は、その旨を明示したうえで質問を省略してよい。
- 実装する価値があるか（類似機能・代替手段がないか・コストに見合う価値があるか）
- コスト・保守負荷が妥当か（インフラコスト・運用者の手作業増加・属人化リスク・長期維持コストが現実的か・要件規模に対して過剰な構成でないか）
- 既存方針との衝突がないか（既存アーキテクチャ・設計指針・運用ルールに反していないか）

**質問の観点（該当する場合のみ）**:
- UI のレイアウト・ラベル・フロー（フロントエンド変更がある場合）
- エラー時の挙動・フォールバック方針
- 認証・権限の扱い
- 外部サービスとの統合方針
- パフォーマンス要件・データ量・ページネーション
- 既存機能との互換性・後方互換の要否
- データ整合性設計（DB変更がある場合）: トランザクション境界・冪等性・同時更新の扱い・マイグレーション安全性
- 運用設計（外部API・非同期処理・バッチがある場合）: 構造化ログ方針・タイムアウト・リトライ・Feature Flag・段階リリースの要否
