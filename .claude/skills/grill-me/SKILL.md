# /grill-me

計画書作成前に、イシューの設計上の曖昧な点をユーザーに確認する。

## 実施手順

### 1. イシューファイルを読み込む
```bash
cat docs/issues/open/$ARGUMENTS.md
```

### 2. コードベースを探索して自己解決できる疑問を除去する
- 関連スキルファイル・既存コード・runbooks を読み、コードを見れば分かる疑問は除く

### 3. 設計上の曖昧な点を一括提示する

**提示フォーマット**:
```
## 設計確認（/grill-me $ARGUMENTS）

以下の点について確認させてください。

1. [質問1]
2. [質問2]
...

回答いただけましたら `/plan-issue $ARGUMENTS` を実行してください。
```

設計上の疑問点がない場合は以下を表示する:
```
設計上の疑問点はありませんでした。
`/plan-issue $ARGUMENTS` を実行してください。
```

### 4. ユーザーの回答をイシューファイルに追記する

ユーザーが回答したら、イシューファイルの「## 関連資料」セクションの直後に以下を追記する:

```markdown
## 設計確認メモ（/grill-me）
- Q: [質問1] → A: [回答1]
- Q: [質問2] → A: [回答2]
```

**本文整合（必須）**:
設計確認メモを追記したら、メモの確定値と矛盾する既存セクション（`解決方針` / `スコープ` / `実装対象` / `受け入れ条件`）を同じ確定値に整合更新する。「(a)/(b) どちらか」「併用（未確定）」等の grill 前の表現がメモの確定と矛盾したまま残らないようにする（`plan-writing-rules.md` の「ルール変更時に関連ファイルを同時更新する」不変条件を、イシュー本文内のセクション間にも適用する）。コンテキストを持たない担当者が本文を読んで方式未決と誤読しないことが目的。

**メモ↔本文の機械検証（必須・スクリプト不在なら skip）**:
本文整合の後、`bash scripts/claude/check-memo-body-paths.sh I###` を実行し、設計確認メモのファイルパスが本文（`## 実装対象` / `## 影響範囲`）に反映されているか（memo ⊆ body）を機械検証する。終了コード `1`（不一致）の場合は、列挙されたパスを本文に追記、または意図的除外であればその旨を本文に明記してから再実行し、`✅`（exit 0）を確認してから次へ進む。`2`（実行不可）やスクリプト不在の場合は非ブロックで skip してよい（警告のみ）。これは上記「本文整合（必須）」を散文の心がけで終わらせず決定論ゲートで締めるためのもの（`plan-writing-rules.md` の「消費箇所の全件更新」をイシュー本文に適用した決定論的インスタンス）。

**GitHub イシュー本文の同期（必須・`gh` 不可なら skip）**:
本文整合の後、`gh issue edit <GitHub#> --body-file docs/issues/open/IXXX.md` で GitHub イシュー本文をローカルと同期する（`--body "$(cat ...)"` は本文中の `"`/バックティック/`$(...)` でシェル展開エラーになり得るため `--body-file` を使う）。`gh` が使えない環境（未認証・headless 等）では skip してよい（非ブロック・警告メッセージのみ表示し停止しない）。

**具体化追求ルール（必須）**:
ユーザーの回答が以下の状態であれば、具体値が出るまで追加質問を行う:
- 「適切に対応する」「実装予定」などの動詞止まり
- 「〜したい」「〜するべき」などの方向性のみ
- 数値・クラス名・フィールド名が出てこない設計判断

例:
「認可はどうしますか?」→「認証ユーザーのみ」→「具体的には?」→「IsAuthenticated + IsOrganizationMember」
この最後の「具体的には?」の追加追求がイシューファイルに記録される値の品質を決める。

**必須確認（全イシュー）**:
コードベースを読んで自己解決できる場合は、その旨を明示したうえで質問を省略してよい。
- 実装する価値があるか（類似機能・代替手段がないか・コストに見合う価値があるか）
- コスト・保守負荷が妥当か（インフラコスト・運用者の手作業増加・属人化リスク・長期維持コストが現実的か・要件規模に対して過剰な構成でないか）
- 既存方針との衝突がないか（既存アーキテクチャ・設計指針・運用ルールに反していないか・旧来のアンチパターンを惰性で踏襲していないか・新技術を採用する場合は採用理由が明確か・状態管理の設計方針が既存コードと一貫しているか）

**ツール実行による完了基準の確定（必須・実行省略不可）**:
scope/AC が lint/audit/scan/型チェック等ツールの出力で決まるイシューでは、概算（個別バージョン照会等）で済ませず、**対象ツールを実際に実行して全件分類**し、達成可能な完了基準を確定してから AC を記録する。例: 「監査 high ゼロ」を AC にする前に監査を実走し、依存固着等で達成不可なら AC を見直す。**この項目はコード読解では代替できないため、上記「省略してよい」の対象外であり、ツール実行を省略してはならない。**

**質問の観点（該当する場合のみ）**:
- UI のレイアウト・ラベル・フロー（フロントエンド変更がある場合）
- エラー時の挙動・フォールバック方針
- 認証・権限の扱い
- 外部サービスとの統合方針
- パフォーマンス要件・データ量・ページネーション
- 既存機能との互換性・後方互換の要否
- 業務ロジック・マルチテナント制約（ビジネスロジックを変更する場合）: マルチテナントの閲覧範囲・操作範囲の制約・ステータス遷移の条件・エッジケースでの業務ルール
- テスト戦略（新規の振る舞いを追加する場合）: TDD 適用範囲・テストレベルの選択（ユニット/結合/E2E）・再発防止テストの要否・認可テストの有無
- データ整合性設計（DB変更がある場合）: トランザクション境界・冪等性・同時更新の扱い・マイグレーション安全性
- 運用設計（外部API・非同期処理・バッチがある場合）: 構造化ログ方針・タイムアウト・リトライ・Feature Flag・段階リリースの要否
