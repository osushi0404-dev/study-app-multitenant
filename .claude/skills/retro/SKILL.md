# /retro

対象イシューの対応全体を振り返り、学びと改善点を特定する。

## 手順

1) 対象イシューの関連ドキュメントと git log を確認して対応全体を把握する:
   ```bash
   git log --oneline --all -- "docs/**/*$ARGUMENTS*" "*$ARGUMENTS*"
   ```

2) 以下の観点で振り返りを実施する（すべての観点を確認すること）:

   | カテゴリ | 問い |
   |---------|------|
   | **成果** | 受け入れ条件を満たせたか？ユーザーの本当の課題を解決できたか？ |
   | **プロセス** | フロー通りに進められたか？フロー自体に無駄・不足はあったか？ |
   | **コミュニケーション** | ヒアリング・報告・確認のタイミングや質は適切だったか？ |
   | **技術選択** | 設計・ライブラリ・アプローチは最適だったか？より良い方法はあったか？ |
   | **ドキュメント** | 計画・テスト・レビュー文書は実際に役立ったか？ |
   | **スキル・規約** | 既存のスキルや規約で不足・不備・使いづらさはあったか？ |
   | **予期しない問題** | 想定外の障害は何があったか？なぜ想定外だったか？ |
   | **次回への教訓** | 次のイシューで変えるべきことは何か？ |
   | **ベストプラクティス** | コーディング規約の重大な逸脱はなかったか？責務分離・重複コードの問題は残っていないか？ |
   | **セキュリティ** | 認証・認可漏れ、入力検証漏れ、OWASP Top 10 相当のリスクは残っていないか？秘密情報の露出はないか？ |
   | **残余リスク処遇** | security-review を実施した場合、残余リスクの処遇を決定したか？High 以上はイシュー化・Medium 以下は判断任意。実施していない場合はスキップ。 |
   | **設計ルール昇格** | 今回の security-review で発見した問題パターンを、grill-me の確認観点または plan-issue-review のチェック項目に昇格できるか？実施していない場合はスキップ。 |
   | **モダン開発** | REST API 設計の一貫性・N+1 等のパフォーマンス問題・アクセシビリティに未対処の問題は残っていないか？ |
   | **指示ファイルメンテナンス** | 今回のイシューで発見した問題パターンを踏まえて `.claude/review-agents/plan-reviewer.md` / `code-reviewer.md` に追加・修正すべきレビュー観点はないか？発見した観点は `rules/` の更新とセットで行うことを推奨する。 |

2.5) 改善点の候補が出たら、まず「理想の状態」を定義してから 5 Whys を実施する:

   **理想の状態（ベースライン）を先に定める（必須）**

   問題ごとに「このフローを理想的に進めていた場合、どのステージで・何をしていたか」を明確にする:

   | フローステージ | 問い |
   |-------------|------|
   | grill-me | 理想的な grill-me はどんな質問を生成し、この問題を事前に発見していたか？ |
   | plan-issue（計画書） | 理想の計画書にはどのセクションに何が含まれていたか？ |
   | plan-issue-review | どのチェック項目があれば Blocker/High として止められていたか？ |
   | implement | 実装の順序・確認ステップをどう変えれば早期発見できたか？ |

   → **この差分（理想 vs 実際）が根本原因の候補**

   ---

   **5 Whys の実施（最低 3 回）**

   #### 5 Whys: [改善項目名]
   - Why 1: なぜその問題が起きたか？
   - Why 2: なぜそうなったか？
   - Why 3: なぜそうなったか？

   **抽象化テスト（必須）**: Why の連鎖が $ARGUMENTS 固有の技術名・ファイル名・事象で止まっていないか確認する。
   根本原因の文章から「$ARGUMENTS 固有の文脈」を取り除いても成立するか？成立しない場合はさらに Why を深掘りする。

   → 根本原因: 「〇〇スキルの△△ステップに□□の確認がなかった」「フローの〇〇ステージで△△を確認する習慣がなかった」というレベルで表現する
   → 一般化: この根本原因は今回の $ARGUMENTS に特有か、他のイシューや今後の作業全般にも起こり得るか？
     - 今回限りの事象 → 是正処置（corrective）
     - 他でも繰り返し起こり得る / プロセス・仕組みに問題がある → 予防処置（preventive）として一般化・ルール化
   → 分類: 是正処置 / 予防処置 / 両方（両方に属する場合は両テーブルに記載）

3) 以下の形式で報告する:

   ```
   ## $ARGUMENTS 振り返り

   ### 良かった点
   -

   ### 是正処置（Corrective）
   今回の事象への対処。同じ問題が再発しないための直接的な修正。
   | # | カテゴリ | 根本原因 | 対処内容 |
   |---|---------|---------|---------|

   ### 予防処置（Preventive）
   仕組み・ルール・スキルの変更により、類似の問題が他イシューでも起きないようにする。
   | # | カテゴリ | 根本原因 | 予防策 | 対象ファイル |
   |---|---------|---------|--------|------------|
   ```

   **改善案の選定基準（必須）**: 各改善案はベストプラクティス・セキュリティ・モダン開発の3観点から見て最適なアプローチを採用すること。
   複数の選択肢がある場合は、セキュリティリスクを低減する案 > ベストプラクティス・規約に沿った案 > モダンな手法を活用する案 の優先順で選定し、採用理由を簡潔に添える。

   **予防策の書き方（必須）**:
   - 「次回気をつける」「〇〇を確認する習慣をつける」は不可。必ず **「スキル・ルールファイルの具体的なステップへの追加」** として表現する
   - 予防策の文言から $ARGUMENTS 固有の技術名（特定ライブラリ名・ファイル名等）を取り除いた形で書く
   - 書き方の例:
     - ✗ 「proxy を使うときは ALLOWED_HOSTS を確認する」（技術固有・行動指針止まり）
     - ✅ 「grill-me の『運用設計』確認観点に『新しいネットワークホップを導入する場合、各ホップでの downstream サービスへの影響（ヘッダー・IP・設定要件）を分析する』を追加する（対象: grill-me/SKILL.md）」（スキルへの具体的な追加として表現）

4) 予防処置がある場合、以下のガイドを表示してユーザーの判断を待つ:

   ```
   ### 予防処置への対応

   予防処置のスコープに応じて以下の正規フローを使う（インライン修正は禁止）:

   **現イシューのスコープを大きく外れるもの**:
   → `/issue-bootstrap [予防策の内容]` で新イシューを起票して正規フローを開始

   **現イシューのスコープ内で対応できるもの**（軽微なルール・ドキュメント更新等）:
   → 現イシューの `/plan-issue` または既存計画書の更新で対応

   どちらの場合も `/plan-issue-review` → `/implement` → `/test` の正規フローを経由してマージする。
   禁止: インライン修正（その場での Edit/Write）は禁止。必ず正規フローを使う。
   ```

   **（ハンドオフ invariant）** `/issue-bootstrap` で起票したバックログのイシューファイルは **ローカル作成（未コミット）のまま**にする。develop 等のベースへコミットしない。コミットすると当該イシューの `/plan-issue` の初コミットが no-op 化し draft PR が失敗する（plan-issue の invariant 参照）。イシューは各自の `/plan-issue` が feature ブランチで初コミットする。

5) 是正処置がある場合、対応方法を確認する（ユーザーの判断を待つ）:

   ```
   ### 是正処置への対応
   各項目について対応方法を選択してください:
     a) その場でインライン修正
     b) 新規イシューとして採番
     c) 対応不要
   ```

   **承認ゲート**: ユーザーが「a）インライン修正」を選択した場合、変更内容（変更前/変更後）を先に
   提示してユーザー承認を得てから Edit/Write を実行する。承認なしの書き込みは禁止。

   改善点がない場合は `/close $ARGUMENTS` に進んでください。

6) 対応完了後: `/close $ARGUMENTS` を提案する
