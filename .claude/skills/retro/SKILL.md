# retro（振り返り段階）

対象イシューの対応全体を振り返り、学びと改善点を特定し、改善案の採否を Claude が決めて対応まで行う（ユーザーの判断は待たない。結果は close 段階のマージ依頼でまとめて報告する）。止めてユーザーに聞くのは `docs/runbooks/workflow.md`「止めて聞く条件」に当たるときだけ。

この段階が書いてよいのは `docs/reviews/`・`docs/tests/`・`docs/issues/`・`docs/plans/` だけ（それ以外を直すと、レビューを通り直す必要が出る）。手順書・スキル・スクリプトの直しが要る改善案は、既存イシューへの同梱か新規起票にする。

## 対ユーザー出力の平易化ルール（手順3 と close 段階の報告・必須）

ユーザーへの報告（チャット出力）は以下に従う。記録・分析の内部手続きは変えない。

1. **提示順**: 平易版を先に提示し、その後に詳細版（内部管理フォーマットの表）を併記する。詳細版を省略しない（チャットが唯一の記録のため）。
2. **置換（省略ではない）**: 専門用語・内部記号は平易な言葉に置換する（省略ではない）。
   - 例: 「是正処置（Corrective）」→「今回の問題への直接の対処」／「予防処置（Preventive）」→「同じ問題を次回から防ぐ改善」／「5 Whys」→「なぜを繰り返す原因分析」
   - 内部記号（表の # 列の C1・P1 等）は平易版では使わず、内容そのもので示す。
3. **経緯・理由を残す**: 各項目に「何が起きたか・なぜそうするのか」（経緯・理由・判断根拠）を一言添える。過度な要約で情報を削らない。
4. **記録は詳細維持**: 記録ファイル（`docs/reviews/` 等）は詳細フォーマットを維持する。本スキルへの記録ファイル新設はしない（詳細版はチャット併記で残す）。＝「資料は詳細・対話は平易」。
5. **平易化の対象外**: コマンド名（`/issue-bootstrap` `/plan-issue` 等）とイシュー番号は平易化の対象外とする（説明文のみ平易化する）。

**文例（変換前→変換後）**:
- 変換前: 「予防処置（Preventive）P1: 根本原因は grill-me の確認観点に運用設計の項目がなかったこと。grill-me/SKILL.md に観点を追加する。」
- 変換後: 「同じ問題を次回から防ぐ改善: 設計の確認をするとき、運用まわり（ログの残し方や失敗時のやり直しなど）を尋ねる項目がそもそも無かったため、問題を事前に見つけられませんでした。確認項目に追加して、次のイシューからは自動的に確認されるようにします。」

## 手順

1) 対象イシューの関連ドキュメントと git log を確認して対応全体を把握する:
   ```bash
   git log --oneline --all -- "docs/**/*$ARGUMENTS*" "*$ARGUMENTS*"
   ```

2) 以下の観点で振り返りを実施する（すべての観点を確認すること）:

   | カテゴリ | 問い |
   |---------|------|
   | **成果** | 受け入れ条件を満たせたか？ユーザーの本当の課題を解決できたか？ |
   | **プロセス** | フロー通りに進められたか？フロー自体に無駄・不足はあったか？ |
   | **コミュニケーション** | ヒアリング・報告・確認のタイミングや質は適切だったか？ |
   | **技術選択** | 設計・ライブラリ・アプローチは最適だったか？より良い方法はあったか？ |
   | **ドキュメント** | 計画・テスト・レビュー文書は実際に役立ったか？ |
   | **スキル・規約** | 既存のスキルや規約で不足・不備・使いづらさはあったか？ |
   | **予期しない問題** | 想定外の障害は何があったか？なぜ想定外だったか？ |
   | **次回への教訓** | 次のイシューで変えるべきことは何か？ |
   | **ベストプラクティス** | コーディング規約の重大な逸脱はなかったか？責務分離・重複コードの問題は残っていないか？ |
   | **セキュリティ** | 認証・認可漏れ、入力検証漏れ、OWASP Top 10 相当のリスクは残っていないか？秘密情報の露出はないか？ |
   | **残余リスク処遇** | security-review を実施した場合、残余リスクの処遇を決定したか？High 以上はイシュー化・Medium 以下は判断任意。実施していない場合はスキップ。 |
   | **設計ルール昇格** | 今回の security-review（design-security-review 段階・review-gate の組み込み /security-review）で発見した問題パターンを、grill-me の確認観点または plan-reviewer のチェック項目に昇格できるか？実施していない場合はスキップ。 |
   | **モダン開発** | REST API 設計の一貫性・N+1 等のパフォーマンス問題・アクセシビリティに未対処の問題は残っていないか？ |
   | **指示ファイルメンテナンス** | 今回のイシューで発見した問題パターンを踏まえて `.claude/agents/plan-reviewer.md` / `code-reviewer.md` に追加・修正すべきレビュー観点はないか？発見した観点は `rules/` の更新とセットで行うことを推奨する。 |

2.5) 改善点の候補が出たら、まず「理想の状態」を定義してから 5 Whys を実施する:

   **理想の状態（ベースライン）を先に定める（必須）**

   問題ごとに「このフローを理想的に進めていた場合、どのステージで・何をしていたか」を明確にする:

   | フローステージ | 問い |
   |-------------|------|
   | grill-me | 理想的な grill-me はどんな質問を生成し、この問題を事前に発見していたか？ |
   | plan-issue（計画書） | 理想の計画書にはどのセクションに何が含まれていたか？ |
   | plan-review | どのチェック項目があれば Blocker/High として止められていたか？ |
   | implement | 実装の順序・確認ステップをどう変えれば早期発見できたか？ |

   → **この差分（理想 vs 実際）が根本原因の候補**

   ---

   **5 Whys の実施（最低 3 回）**

   #### 5 Whys: [改善項目名]
   - Why 1: なぜその問題が起きたか？
   - Why 2: なぜそうなったか？
   - Why 3: なぜそうなったか？

   **抽象化テスト（必須）**: Why の連鎖が $ARGUMENTS 固有の技術名・ファイル名・事象で止まっていないか確認する。
   根本原因の文章から「$ARGUMENTS 固有の文脈」を取り除いても成立するか？成立しない場合はさらに Why を深掘りする。

   → 根本原因: 「〇〇スキルの△△ステップに□□の確認がなかった」「フローの〇〇ステージで△△を確認する習慣がなかった」というレベルで表現する
   → 一般化: この根本原因は今回の $ARGUMENTS に特有か、他のイシューや今後の作業全般にも起こり得るか？
     - 今回限りの事象 → 是正処置（corrective）
     - 他でも繰り返し起こり得る / プロセス・仕組みに問題がある → 予防処置（preventive）として一般化・ルール化
   → 分類: 是正処置 / 予防処置 / 両方（両方に属する場合は両テーブルに記載）

   **ユーザーへの提示（平易化ルール適用）**: 5 Whys をユーザーに提示する際は、経過（Why の連鎖）の提示を維持し、専門用語・内部記号のみ平易な言葉に置換する（分析の内部手続きは変えない）。

2.7) 改善案ごとに「本当に対応すべきか」を判定する（必須・Claude が決める）:

   判定は次の 2 つの基準を両方満たすかで行う。
   - **ハーネス・ループエンジニアリングのベストプラクティス**: 品質は手続き（スキルの手順・レビュー観点の追加）より、
     決定論のチェック（機械判定・fail-closed）で担保する。同じ穴を複数の工程で二重に塞がない。
   - **スピード**: 足す工程が毎回のイシューにかけるコストと、それで防げる損失を比べる。重くなる分に見合わないなら足さない。

   各改善案に次の 4 問を当てる:
   1. 実害（手戻り・見逃し・障害）が本当に出たか
   2. 既存の流れのどこかで、その場で捕まったのではないか（捕まって手戻りも無いなら、新しい手順は足さない）
   3. 決定論のチェックを直せば足りるのではないか（足りるなら、手順・観点の追加より優先する）
   4. 既存のイシュー（未着手のものを含む）に同梱できないか

   結果を「このイシューで直す（記録の場所だけで済むもの）／既存イシューに同梱／採用（新規起票）／見送り」のどれかに振り分け、理由を 1 行添える。
   新規起票は「実害があり、同梱先が無い」ものに限る。見送りにしたものも理由とともに記録する（黙って捨てない）。

3) 報告は**平易版 → 詳細版の順で併記**する（平易化ルール参照）。まず平易版:

   ```
   ## $ARGUMENTS 振り返り（かんたんなまとめ）

   ### 良かった点
   - [内容]（理由: なぜ良かったか）

   ### 今回の問題への直接の対処
   - [何が起きたか]。[なぜ起きたか（経緯・理由）]。→ [どう直すか・なぜその方法か]

   ### 同じ問題を次回から防ぐ改善
   - [何が起きたか]。[なぜ起きたか（経緯・理由）]。→ [どのルール・スキルをどう変えるか]
   ```

   続けて詳細版（記録用フォーマット・変更しない）:

   ```
   ## $ARGUMENTS 振り返り

   ### 良かった点
   -

   ### 是正処置（Corrective）
   今回の事象への対処。同じ問題が再発しないための直接的な修正。
   | # | カテゴリ | 根本原因 | 対処内容 |
   |---|---------|---------|---------|

   ### 予防処置（Preventive）
   仕組み・ルール・スキルの変更により、類似の問題が他イシューでも起きないようにする。
   | # | カテゴリ | 根本原因 | 予防策 | 対象ファイル |
   |---|---------|---------|--------|------------|
   ```

   **改善案の選定基準（必須）**: 手順 2.7 で「採用（新規起票）」または「既存イシューに同梱」と判定したものだけを、是正処置・予防処置の表に載せる（見送りは表に載せず、理由とともに別に示す）。
   各改善案はベストプラクティス・セキュリティ・モダン開発の3観点から見て最適なアプローチを採用すること。
   複数の選択肢がある場合は、セキュリティリスクを低減する案 > ベストプラクティス・規約に沿った案 > モダンな手法を活用する案 の優先順で選定し、採用理由を簡潔に添える。

   **予防策の書き方（必須）**:
   - 「次回気をつける」「〇〇を確認する習慣をつける」は不可。必ず **「スキル・ルールファイルの具体的なステップへの追加」** として表現する
   - 予防策の文言から $ARGUMENTS 固有の技術名（特定ライブラリ名・ファイル名等）を取り除いた形で書く
   - 書き方の例:
     - ✗ 「proxy を使うときは ALLOWED_HOSTS を確認する」（技術固有・行動指針止まり）
     - ✅ 「grill-me の『運用設計』確認観点に『新しいネットワークホップを導入する場合、各ホップでの downstream サービスへの影響（ヘッダー・IP・設定要件）を分析する』を追加する（対象: grill-me/SKILL.md）」（スキルへの具体的な追加として表現）

4-0) 台帳の残り（必須・I205）: レビューで止めなかった指摘（止める条件に当たらない・再現が無い・差分の外）を埋もれさせない。
   - 最新のコードレビューの記録（`docs/reviews/` と `docs/reviews/closed/` の `$ARGUMENTS_code_review_*.md` のうち、ファイル名の時刻が最後のもの）の、`STATUS=open` の台帳の行をすべて拾う:
     ```bash
     grep -h '^LEDGER: .*STATUS=open' <最新のコードレビューの記録>
     ```
   - 拾った指摘は、重さで 2 つに振り分ける（I207。判定は行の欄 `SEV`・`REPRO`・`SECURITY`・`KIND` だけで機械的に決める）:
     - **後続イシュー**: 再現のある Medium 以上（`SEV=Blocker|High|Medium` かつ `REPRO=yes`）・`SECURITY=yes`（重さに関係なく）・`KIND=app`（アプリ本体。`SCOPE=outside` も）のどれかに当たる行。1 件ずつ起票せず、1 件の後続イシュー（手順 4 の「採用（新規起票）」。タイトルに「$ARGUMENTS のレビューの残り」）にまとめるか、合う既存のイシューへのコメント（手順 4 の「既存イシューに同梱」）に入れる:
       ```bash
       grep -h '^LEDGER: .*STATUS=open' <最新のコードレビューの記録> | grep -E 'KIND=app|SECURITY=yes|SEV=(Blocker|High|Medium) .*REPRO=yes'
       ```
     - **一覧**: それ以外（Low、または再現なし）。イシューにせず、`docs/reviews/backlog/$ARGUMENTS.md`（起点のイシューごとに 1 ファイル。無ければ作る。形は `docs/reviews/backlog/I206.md` と同じ）に 1 行ずつ追記し、手順 4 の「このイシューで直す」と同じく commit/push する:
       ```bash
       grep -h '^LEDGER: .*STATUS=open' <最新のコードレビューの記録> | grep -vE 'KIND=app|SECURITY=yes|SEV=(Blocker|High|Medium) .*REPRO=yes'
       ```
       行の形: `- <番号> SEV=<…> REPRO=<…> KIND=<…> FILE=<パス|-> | <要約> | 一覧に回した理由: Low／再現なし`。`FILE=` は、その番号の FINDING 行（同じイシューのコードレビューの記録を新しい順に見て最初のもの）の値。見つからなければ `FILE=-`。一覧は計画（`/plan-issue` の「台帳の残りの一覧」）で、実装対象のファイルに当たる行を見る
   - 後続イシューに回した行に、判定の仕組み（`scripts/claude/code-review.sh`・`scripts/claude/adversarial-review.sh`・`scripts/claude/gate-check.sh`・`.claude/agents/`）に関わる指摘、または `SECURITY=yes` の指摘が入っていれば、その後続のイシュー（同梱ならコメント）に「次のハーネスの作業で最優先」と書く。
   - 「## 自律判断の記録」に、指摘の番号ごとの振り分け先（`#番号` か `docs/reviews/backlog/$ARGUMENTS.md`）を書く。0 件なら「台帳の残り 0 件」と書く。
   - 手順 2.7 の 4 問による見送りは、この台帳の残りには使わない（判定は後続のイシューの計画、または一覧を見る計画で行う）。

4) 振り分けに従って対応する（ユーザーの判断は待たない）:
   - **このイシューで直す**: 記録の場所（`docs/reviews/`・`docs/tests/`・`docs/issues/`・`docs/plans/`）だけで済むものは、その場で直して commit/push する
   - **既存イシューに同梱**: 同梱先のイシュー（未着手のものを含む）に、改善案の要約・根本原因・予防策・対象ファイルをコメントする。本文は一時ファイルに書いて `gh issue comment <番号> --body-file <ファイル>` で付ける
   - **採用（新規起票）**: Skill ツールで `issue-bootstrap` を呼ぶ（引数はタイトル。呼ぶときに「retro からの起票」であること・根本原因・予防策・対象ファイル・起点のイシュー番号を伝える。issue-bootstrap はこのとき質問せず、未確定は「未定・grill-me で確認」と書く）
   - **見送り**: 何もしない（理由は記録に残す）
   - 公開リポジトリなので、自動で書くイシューの本文・コメントには、コマンドの出力・ログ・環境変数・記録（JSONL）の中身・画面キャプチャ・コンソールの記録を貼らない。要約と `ファイル:行` の参照だけにする

   **（ハンドオフ invariant）** `issue-bootstrap` で起票したバックログのイシューファイルは **ローカル作成（未コミット）のまま**にする。develop 等のベースへコミットしない。コミットすると当該イシューの `/plan-issue` の初コミットが no-op 化し draft PR が失敗する（plan-issue の invariant 参照）。イシューは各自の `/plan-issue` が feature ブランチで初コミットする。

5) 記録: `docs/reviews/open/$ARGUMENTS_review.md` の「## 自律判断の記録」に、改善案ごとの振り分け（直した／同梱先 #番号／起票 I###・#番号／見送り）と理由を書く。手順 3 の平易版・詳細版の振り返りも同じファイルの「## 振り返り」に残す（close 段階のマージ依頼で、平易版をまとめて報告する）

6) 結線（必須）: commit/push してから、`docs/reviews/open/$ARGUMENTS_review.md` の末尾に次の 1 行を足して commit/push する
   ```
   STAGE_DONE: retro NEXT: close
   ```
