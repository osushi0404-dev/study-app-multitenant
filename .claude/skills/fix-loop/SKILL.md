# fix-loop（修正段階）

止めてユーザーに聞くのは `docs/runbooks/workflow.md`「止めて聞く条件」に当たるときだけ。それ以外で決めたこと（どの案で直したか など）は `docs/reviews/open/$ARGUMENTS_review.md` の「## 自律判断の記録」に `- [fix-loop] 決めたこと — 理由` で書く。

`$ARGUMENTS` = 対象イシュー（I###）。手順3.5 は `claude -p` のレビュー役による**ゲート**で、スクリプトの **exit code（0=次段へ／1=差し戻し）** を読む（補助として stdout 末尾に `FIX_GATE: PASS|REMAND|SKIP` を出力）。

## 何を直すか（I197）
- 直すのは、review-gate の最新のコードレビューの記録の **`## 止める指摘（スクリプトが決めた・fix-loop が直すのはこれだけ）` の節にある指摘**と、CI・テスト・人の手動テストの NG（と review-gate §3 が直すと決めた敵対的レビューの指摘）だけ。止めるかはスクリプトが決めたもので、自分で増やさない・減らさない（I205）。それ以外の台帳の指摘は直さない（retro が後続のイシューへ回す。直して新しい穴を生む回り道をしない）。
- 直した差分は、直後の review-gate の**差分のレビュー**（前の記録の `REVIEWED_COMMIT` からの差分と、台帳の止める指摘が直ったか）が見る。fix-loop の中では実装・テストのレビューをしない（I197 で廃止。同じ差分を重ねて見ていた）。

## 成果物とレビュー対応
| 成果物 | 記録先ドキュメント | 見るもの |
|--------|------------------|------------------|
| 失敗分解・根本原因（＝**原因調査結果**）＋対応方針（＝**修正方針**・全案＋推奨） | 手順3.5 の診断メモ `docs/reviews/${ARGUMENTS}_fix_diagnosis_<ts>.md` | **手順3.5 診断レビュー** |
| **修正内容** | 作業ツリー差分（`git diff`＋未追跡新規） | 直後の review-gate の差分のレビュー |
| **テスト結果** | 手順7 の再発防止記録（`docs/tests/open/$ARGUMENTS_auto_test.md`） | 手順6 の決定論のテスト（CI が正） |

## 診断レビューの共通ルール
- **しきい値**: VERDICT が `OK`（exit 0）のときのみ手順4 へ進む。**`BLOCKER`＋`HIGH` は差し戻し**（exit 1）＝手順2 で再診断・手順3 で別案を作って手順3.5 をやり直す。
- **ループ暴走ガード**: 診断レビューの連続 NG が **2 回**に達したら自動ループバックを止め、止める条件 3 に当たるかを判定する。範囲を狭める・別イシューに切り出す・確認を厳しめに倒すなど安全側の選択肢が取れれば、それを選んで記録し、計画書を直して（方式・範囲・受け入れ条件を変えるなら `plan-review` を通して）続ける。取れなければ止める。
- **`claude -p` 不可時（未認証/headless/タイムアウト）**: スクリプトは `FIX_GATE: SKIP`＋exit 0（非ブロック）で「レビュー未実施」を記録に残す。fix-loop は停止せず次段へ進む（直した後は必ず review-gate がレビューする）。

## 手順

1) 失敗内容を「再現手順 / 期待値 / 実際値 / ログ」に分解して報告する（口頭で終えず、**手順3.5 の診断メモ「失敗分解」に記録する**）
2) 根本原因を調査・分析して報告（なぜ失敗したか）（**手順3.5 の診断メモ「根本原因」に記録する**）
   - セキュリティ観点も確認する（認証・認可の欠落、インジェクション、XSS、機密データ露出等に該当しないか）
3) 対応方法を複数案提示。各案に以下の軸でメリット・デメリットを添える（**手順3.5 の診断メモ「対応方針＝全案＋推奨」に記録する**）:
   - セキュリティ影響（OWASP Top 10 関連リスクの有無、Django / React セキュリティガイドライン準拠）
   - ベストプラクティス適合（フレームワーク推奨パターン・コーディング規約との整合性）
   - 保守性・拡張性
   - リスク・副作用（直し方が新しいコードを大きく足すときは、それ自体が次の周の指摘の元になる。粗く確実な形を優先する）
   - 新しい安全装置（ガード・検出・確認・拒否リスト）を足す・強める案は、守る対象が GitHub から復旧できるか（`docs/runbooks/danger-ops.md`「GitHub から復旧できる範囲（I182）」）と最後の守りを先に書く。復旧できる対象には単純な規則だけを使い、コマンドの文字列からシェルの動きを読むような精密な判定は採らない（I179 retro P1）

3.5) **診断レビュー（修正前ゲート・常時必須）**:
   - 診断メモ `docs/reviews/${ARGUMENTS}_fix_diagnosis_<ts>.md` を書く（章立て: 失敗分解／根本原因／対応方針＝**全案＋Claude 推奨**／影響調査の実施有無と結果＝同型バグ・他の呼び出し箇所・関連機能への波及）。
   - `bash scripts/claude/fix-diagnosis-review.sh $ARGUMENTS docs/reviews/${ARGUMENTS}_fix_diagnosis_<ts>.md` を実行（`<ts>` は上で生成したファイルのものをそのまま渡す）。
   - exit 0（`FIX_GATE: PASS`）→ 手順4 へ。exit 1（`FIX_GATE: REMAND`）→ 指摘を受けて手順2 で再診断・手順3 で別案を作り、手順3.5 をやり直す（連続 2 回でループ暴走ガード）。`FIX_GATE: SKIP`（未実施）→ 記録して手順4 へ。

4) 案を決める（止まらない）: 診断レビューを通った推奨案で進め、選んだ案と理由を自律判断の記録に書く。案の選択が要件・基本設計・UI/UX の価値判断になる（どれを選ぶかで仕様や画面が変わる）ときだけ、選択肢をつけてユーザーに聞いて止まる（止める条件 1）
5) 決めた案で修正し、直したところを確かめるテスト（否定・不在の判定には失敗注入〔壊すと落ちること〕を付ける）を足す

6) 決定論のテストを流す:
   - 手元では、直したところに関係するテストだけを流す（全体は push の後に CI が流し、review-gate がその合格を待つ。手元で全体を流しても重なるだけ）
   - Backend: pytest / flake8（全エラー修正）/ bandit（MEDIUM 以上を修正対象。LOW は # nosec で抑制・理由記載必須）
   - Frontend: Jest / ESLint（error を修正対象、warning は記録）/ npm audit（high/critical を修正対象、moderate は記録・期限設定）
   - 成功（修正対象の警告・エラーなし）: 手順 7) へ
   - 失敗: 手順 1) に戻る（ループ）

7) 再発防止記録を docs/tests/open/$ARGUMENTS_auto_test.md に追記:
   - なぜ失敗したか
   - 何を変えたか
   - セキュリティ上の考慮点（該当する場合）
   - 次回どう防ぐか
   - 確かめた結果（手順6 で流したテストと結果）

8) 結線（必須・戻り先は 1 か所）: commit/push してから、`docs/reviews/open/$ARGUMENTS_review.md` の末尾に次の 1 行を足して commit/push する。どの NG（レビュー・CI・テスト・人の手動テスト）から来たときも同じで、直した後は必ず review-gate が差分のレビューで見直す
   ```
   STAGE_DONE: fix-loop NEXT: review-gate
   ```
