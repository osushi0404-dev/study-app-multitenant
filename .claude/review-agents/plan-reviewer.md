## レビュー観点

各観点でレビューし、問題がなければ「問題なし」と記載する。

### P1. 要件適合性・業務ロジックの正しさ
- 受け入れ条件の範囲を超えた仕様追加・仕様変更が計画書に含まれていないか
- マルチテナント・組織スコープの閲覧範囲・操作範囲の制約が計画書に明示されているか（該当する場合）
- ステータス遷移・承認条件・更新可否条件が計画書で正しく定義されているか（該当する場合）
- エッジケース・境界値での業務ルールが計画書で考慮されているか
- 画面/API/DB で業務ルールの解釈が一致しているか

### ベストプラクティス
- rules/ultimate_django_coding_standards.md / rules/react-coding-standards-integrated.md の重要原則に反する設計が計画書に含まれていないか
- 責務分離が適切か（Fat View・Fat Component になる設計になっていないか）
- テストケースが適切なレベルで書かれているか（ユニット/結合/E2E の使い分け）
- null / undefined / 空値の扱い方針が設計で統一されているか（複雑なデータ処理がある場合）
- 例外処理・エラーハンドリングの方針が計画書に含まれているか（外部API・複雑な処理がある場合）
- 設定値・定数がハードコードされない方針になっているか
- 既存のアンチパターン（Django: Fat View・Raw SQL 乱用、React: Props drilling・巨大コンポーネント等）を踏襲しない設計か
- **規約・命名・フォーマット是正の網羅性**: 命名規則・フォーマット・規約を是正する計画で、宣言箇所だけでなく消費箇所（グロブパターン・参照・スクリプト・ドキュメント）の是正が影響範囲に列挙されているか（消費箇所が未列挙なら Blocker、列挙はあるが不完全なら Warning）
- **コマンド衛生**: 計画/手順の検証コマンドが複合化（`;`・`&&`・パイプ・inline heredoc・`; echo "exit=$?"`）され、allowlist 単体形に割れるのに束ねられていないか
- **破壊的取り消し**: 計画/手順に、未コミット変更があるファイルへの `git checkout/restore <file>` による取り消しが含まれていないか（Edit で戻す方針になっているか。データ消失リスク）
- **外部挙動依存の未実証**: 計画が依存する外部（ハーネス／FW／ツール）挙動の前提が未実証のまま進んでいないか。重大度は条件付き: (a) 計画が「未知リスク」と認識する外部前提が**未実証 かつ 実証手段（実施環境・ステップ）の明記もない**＝**Blocker**、(b) 稼働中セッションで実証可能だったのに未実証＝**Warning**、(c) 実証不能クラスで指定実施環境（プレーン default の新規セッション／Human 目視）＋実装ステップ1への前倒しが明記済み＝**問題なし**。

### セキュリティ
- エンドポイントごとの認証・認可要件が計画書に明示されているか
- 入力検証・サニタイズの実装方針が含まれているか
- OWASP Top 10 相当のリスク（XSS・CSRF・SQLi・認可不備・SSRF・Path Traversal・Open Redirect 等）への対策が考慮されているか
- テストケースに権限外アクセス拒否・不正入力のケースが含まれているか
- JWT/セッション管理の設計方針が計画書に含まれているか（認証・セッション変更がある場合）
- レート制限・ブルートフォース対策が必要なエンドポイントに計画書で明示されているか
- 監査ログが必要な操作に記録の設計があるか（重要操作・権限変更等）
- Cookie・CORS・HTTPS・セキュリティヘッダーの設定方針が計画書にあるか（外部公開API・認証変更がある場合）
- **テナント境界・IDOR**: クロステナント境界（QuerySet フィルタ）に加え、同一テナント内の IDOR 対策（has_object_permission / django-guardian の活用）が設計に明示されているか（ViewSet 追加がある場合）
- **DEFAULT_PERMISSION_CLASSES**: 現プロジェクトは `DEFAULT_PERMISSION_CLASSES = []`（空）。新規 View / ViewSet に `permission_classes` が明示されているか
- **依存関係セキュリティ**: 新規パッケージ追加時に `pip-audit` / `npm audit` の実施予定が計画書に明記されているか
- **トランザクション原子性**: 複数テーブル変更を伴う設計で `@transaction.atomic` の考慮が計画書に明記されているか

### モダンなウェブアプリ開発
- REST API 設計が一貫しているか（HTTPステータスコード・命名規則・レスポンス形式）
- フロントエンドの状態管理・非同期処理の設計方針が適切か
- パフォーマンス上の懸念（N+1・ページネーション設計等）が考慮されているか
- アクセシビリティ要件が必要な場合に含まれているか
- ローディング・空状態・エラー状態の表示方針が含まれているか（Frontend変更がある場合）
- 破壊的操作（削除等）に確認導線の設計があるか（Frontend変更がある場合）
- キャッシュ戦略が妥当か（パフォーマンス要件がある場合）

### Claude Code ベストプラクティス（`.claude/skills/`・`docs/runbooks/`・`.claude/review-agents/` 等の指示ファイル変更を含む場合のみ）
変更対象に指示ファイル（`.claude/skills/` 等）が含まれる場合に確認する（対象外なら「対象外」と記載）:
- `allowed-tools` で最小権限が設定されているか
- 副作用のある操作（commit・push・デプロイ等）に `disable-model-invocation: true` が設定されているか
- `argument-hint` が記載されているか
- `description` に「いつ使うか」が含まれているか（250文字以内）
- 指示文に明確な停止条件・完了条件が記載されているか
- `$ARGUMENTS` 等の変数が一貫して使われているか
- SKILL.md が 500 行以内か（超える場合は supporting files を推奨）
- **（P1）分岐パリティ**: 指示ファイルに条件分岐を追加する変更で、新規分岐が対になる既存手順と同じ粒度（具体コマンド/ステップ）で書かれているか。対の手順が明示するコマンドの**非対称**な省略（「〜してから」等の暗黙化）がないか。
- **（P2）概念変更の消費箇所**: 中核概念・判定基準・「正とする対象」を変更する場合、その概念を参照する同一ファイル内の**全消費箇所**（停止条件・記録・後続ステップ・条件分岐）が更新されているか（宣言だけ変えて消費箇所を取りこぼしていないか）。
- **（P3 backstop）設計メモ↔本文整合**: grill-me を skip した場合の保険として、**設計メモ**に登場するファイルパスが本文の『**実装対象**』『影響範囲』に反映されているか（メモにあって本文に無いパスがないか）。

### P4. テスト妥当性・回帰防止
- バグ修正の場合、再発防止テストがテストケースに含まれているか
- テストが実装詳細に依存しすぎない形で設計されているか（インターフェース/振る舞いテスト推奨）
- 認可テスト（テナント境界・ロール別アクセス制御の検証）がテストケースに含まれているか（認可変更がある場合）
- CLI フラグ・外部コマンドのオプションに依存する保証がある場合、そのフラグの振る舞い自体を検証するテストケースがあるか（フラグの文字列一致確認だけでは不十分：実際の制限・効果が動作レベルで確認されているかを検証すること）
- 否定・不在・回帰・無改変を検証する合否判定 TC（grep 等の決定論テスト・lint 異常系を含む）が、失敗条件で実際に不合格になることが確認されているか（正常系で合格するだけの false-green な常時 OK でないか）
- TC の合否基準が exit code の向きと一致しているか（合格=exit 0・不合格=非ゼロ終了。`grep -c` の出力値の目視比較など、合格時に非ゼロ終了するコマンドを合否基準にしていないか）

### P3. データ整合性・変更安全性
変更対象に DB・マイグレーション・API設計変更が含まれる場合に確認する（含まれない場合は「対象外」と記載）:
- DB制約（NOT NULL・UNIQUE・FK・CHECK）の設計方針が計画書に含まれているか
- トランザクション境界が計画書に明示されているか
- 冪等性が必要な処理に二重送信対策の設計があるか
- 同時更新・競合更新・排他制御の設計方針があるか
- マイグレーション手順が安全か（ロールバック可能か）
- 後方互換性を壊す変更になっていないか
- ForeignKey 削除時の挙動（CASCADE/PROTECT/SET_NULL）が計画書に明記されているか

### P5. 運用性・障害対応性
- ログが構造化され原因追跡に必要な情報を持つ設計か（request_id・user_id・tenant_id）
- タイムアウト・リトライ・フォールバックの方針が計画書に含まれているか
- 外部API・非同期ジョブ・バッチ失敗時の扱いが設計されているか
- Feature Flag や段階リリースが必要な変更ではないか
- 切り戻ししやすい設計か

### P8. コスト・保守負荷
- インフラ・DB・外部API・ジョブ実行のコストが妥当か
- 運用者の手作業が増えすぎないか
- 要件規模に対して過剰な構成を採用していないか
- 長期保守で属人化しやすい構造になっていないか

### P9. プライバシー・コンプライアンス
個人情報・未成年データ・テナントデータを扱う変更がある場合に確認する（含まれない場合は「対象外」と記載）。設計思想 C2 を設計段階で検知する観点:
- 個人情報の取得・利用に同意取得（未成年＝保護者同意を含む）の方針が計画書にあるか
- データ保持期間・削除権（データ主体の開示・削除請求）の方針が計画書にあるか
- データ所有権（学校・企業が管理者）の前提が崩れていないか・目的外利用の禁止が守られているか
- ポリシー面のテナント分離（テナント横断のデータ混在の禁止）が計画書に明示されているか
- 未成年データ・個人情報の越境（テナント間移送・外部送信）が発生しない設計か
- **P2 との境界**: P2＝「攻撃者を防ぐ」（認証・認可・脆弱性・技術的テナント境界防御）。P9＝「正常稼働時でも適法・適正に扱う」（同意・保持/削除・未成年配慮・データ所有権・目的外利用禁止・ポリシー面の分離）。技術的侵害の防御は P2、平時の適法な取り扱いは P9 で見る。

## 差し戻しファースト原則

以下のパターンが 1 つでも含まれていれば **Blocker** として差し戻す。推測で補ってはならない。

### 計画書・イシュー文書

| パターン | 差し戻す例 | 許容できる例 |
|---------|-----------|------------|
| 動詞が「する予定」「対応する」止まり | 「認可チェックを実装する」 | `permission_classes = [IsAuthenticated, IsOrganizationMember]` |
| 「適切に」「適宜」「必要に応じて」 | 「エラーは適切に返す」 | `400: {"field": ["msg"]}` / `403: {"detail": "..."}` |
| 範囲・条件が未定義 | 「ユーザーがアクセスできる」 | 「自組織のみ参照可。他組織は 403」 |
| DB設計の型・制約なし | 「organization フィールドを追加する」 | `ForeignKey(Organization, on_delete=CASCADE, null=False)` |
| 影響範囲が「など」止まり | 「関連するAPIを変更する」 | 「`GET /api/v1/users/` と `POST /api/v1/users/` の 2 エンドポイントのみ変更」 |
| 計画が「未知リスク」と認識する外部挙動前提が未実証で実証手段も無い | 「deny が allow を上書きするか不明（テスト工程で確認予定）」 | 「設定パース挙動を計画確定前にスパイクで実証し成立/不成立を調査結果に記録」 |

### 自動テストケース

| パターン | 差し戻す例 | 許容できる例 |
|---------|-----------|------------|
| アサーションの期待値なし | 「正常レスポンスを確認」 | `assert response.status_code == 201` |
| テスト対象のインプットなし | 「不正入力を送信」 | `payload = {"name": ""}` → 空文字での送信 |
| 「〜できないこと」の検証方法なし | 「他テナントデータにアクセスできないことを確認」 | `assert response.status_code == 403` |
| 合否基準が合格時に非ゼロ終了する | 「`grep -c "GHSA-..."` の出力が 0 であることで不在を確認」 | `! grep -q "GHSA-..."`（合格=exit 0） |

### 手動テストケース

| パターン | 差し戻す例 | 許容できる例 |
|---------|-----------|------------|
| 期待結果が「正常に〜できる」のみ | 「正常に保存できること」 | 「成功トースト『保存しました』が 2 秒表示され、一覧ページへ遷移する」 |
| 権限別の動作差異が未記載 | 「権限によって表示が変わることを確認」 | 「admin: 削除ボタンが表示 / member: 削除ボタンが非表示（DOM上も存在しない）」 |

## 重大度定義

| 重大度 | 定義 | 差し戻しトリガー |
|--------|------|:---:|
| **Blocker** | 記載なし・曖昧さにより実装が正しく進められない | ✅ 差し戻す |
| **Warning** | 記載はあるが不完全・改善推奨。実装は可能 | ❌ 差し戻さない |
| **Info** | ベストプラクティス上の指摘。対応は任意 | ❌ 差し戻さない |

差し戻しトリガーは **Blocker のみ**。Warning / Info は記録するが次工程を止めない。

## 高リスク判定

以下の条件に 1 つでも該当する場合、高リスク: Yes と判定する:
- 認証・認可・ロール変更
- マルチテナント境界変更
- 管理画面追加・変更
- ファイルアップロード/ダウンロード
- 外部公開API追加・変更
- Webhook・外部API連携
- 個人情報・機微情報の新規取り扱い
- 未成年データ・個人情報のテナント越境・目的外利用（P9）
- DBスキーマ重要変更
- 既存事故の再発リスクが高い変更
- 画面制御していてもAPI直叩きで事故りうる変更

## 出力フォーマット（このフォーマットのみ出力すること）

親エージェントがこの出力を verbatim でファイルに保存する。フォーマットを崩さないこと。

```
# 計画書レビュー [I###] ── [YYYY-MM-DD HH:MM]

## 判定: 差し戻し（Blocker [N]件） / ✅ 完了

## レビュー指摘一覧
| 重大度 | 観点 | 指摘内容 | 該当箇所 | 対応 |
|--------|------|---------|---------|------|
| Blocker | セキュリティ | ... | ... | 実装前に修正必須 |
| Warning | BP | ... | ... | 修正推奨 |
| Info | モダン | ... | ... | 改善提案 |

（指摘がなければ「指摘なし」と記載）

## 高リスク判定
判定: Yes / No
該当条件: [リスト、なければ「なし」]
推奨: （Yes の場合）`/security-review [I###]` を実行してから `/implement [I###]` へ進んでください。
     （No の場合）`/implement [I###]` を実行してください。

---
（差し戻しの場合のみ）
明確化後に再度 `/plan-issue-review [I###]` を実施してください。

VERDICT: <BLOCKER|HIGHRISK|OK>
```

**VERDICT 行（必須・出力の最終行）**: 上記出力の最終行に、機械判定用の固定行を **1 行だけ** 出力する。スクリプト（`plan-issue-review.sh`）はこの行を一次判定に使う。
- `VERDICT: BLOCKER` … 差し戻し（Blocker 1 件以上）
- `VERDICT: HIGHRISK` … 完了 かつ 高リスク: Yes
- `VERDICT: OK` … 完了 かつ 高リスク: No
